    CHAPTER 01

    程序、进程、线程：从双击一个 exe 说起

    程序是静态的文件，进程是资源的容器，线程是执行的流。

    本章目标
    • 能准确说出程序、进程、线程的定义，以及"资源分配单位"和"调度单位"分别指谁
    • 说清楚为什么有了进程还要发明线程
    • 理解 Linux 内核眼中"进程和线程都是 task"的含义

    1.1 双击 notepad.exe 之后发生了什么

    磁盘上的 notepad.exe 只是一个文件。它按 PE 格式（Linux 上是 ELF 格式）存放了机器指令、只读常量、全局变量初值、需要导入的 DLL 列表和入口地址。这个文件就是程序（Program），它是静态的、被动的。你不运行它，它就只占一点磁盘空间。

    双击之后，操作系统大致做了这几件事：

    1. 建立一个新的虚拟地址空间，并把 exe 文件映射进去：代码段只读可执行，数据段可读写。
    2. 分配一张资源表：句柄表（Linux 上叫文件描述符表），以及安全令牌、当前目录、环境变量等。
    3. 创建第一个线程（主线程）：给它分配一块栈，把指令指针设到程序入口（经过加载器和 C 运行时初始化，最终调用到 main）。
    4. 把主线程放进就绪队列，等调度器选中它，它就开始在 CPU 上执行。

    前两步建出来的"一个地址空间 + 一组资源"就是进程（Process）；第 3 步建出来的那条"沿着指令一步步往下执行的流"就是线程（Thread）。

    🍳 一个类比：菜谱、厨房、厨师

    程序 = 菜谱：写在纸上，本身不会做出菜。进程 = 一间开张的厨房：有自己的灶台、冰箱、食材（地址空间和资源），厨房和厨房之间有墙隔开。线程 = 厨房里的厨师：真正干活的是厨师，同一间厨房的厨师共用冰箱和灶台，但每人手上有自己的步骤进度（程序计数器）和自己的案板（栈）。

    按这个类比，同一份菜谱可以同时开好几间厨房（同一个 exe 运行多次就是多个进程）；一间厨房至少要有一个厨师，否则就关门了（进程至少有一个线程）；厨师之间共用冰箱很方便，但两个人同时伸手拿同一块肉就会出问题（数据竞争）。

    1.2 进程：资源分配与保护的基本单位

    教科书定义：进程是程序的一次执行实例，是操作系统进行资源分配和保护的基本单位。这句话里有两个关键词：

    资源容器

    内存、文件、网络连接、设备等资源都以进程为单位申请和记账。进程退出时，操作系统会把它名下的资源一次性回收，即使程序员忘了 close 或 free。

    保护域

    每个进程有独立的虚拟地址空间。进程 A 里的地址 0x7FF6... 和进程 B 里的同一个地址，被各自的页表映射到不同的物理内存，所以 A 无法直接读写 B 的内存。这道墙由 MMU 硬件强制执行。

    1.3 线程：CPU 调度的基本单位

    线程是进程内的一条独立执行流，是 CPU 调度和分派的基本单位。CPU 只认识"从哪条指令开始执行、寄存器里是什么值、栈在哪"，这套状态就是一个线程。调度器做的事情，就是把某个线程的这套状态装进 CPU，让它跑一会儿，再换下一个。

    为什么有了进程还要线程？

    早期 Unix 只有进程，一个进程就是一条执行流。后来人们遇到了下面这些需求：

    1. 一个程序里有多件事要同时做：编辑器既要响应键盘，又要后台自动保存、做拼写检查。如果只有一条执行流，保存文件时界面就会卡住。
    2. 多核 CPU 出现了：单个进程只有一条执行流，最多只能用上一个核。
    3. 用多进程来做这些事太贵：每个进程有独立的地址空间，创建时要建页表、复制资源表；进程之间交换数据要走管道、共享内存等 IPC 机制，编程麻烦，开销也大。

    于是人们把进程拆成两部分：资源的部分留在进程里，执行的部分抽出来成为线程。同一进程的多个线程共享资源，各自独立执行。这样多件事可以同时进行，能用上多个核，而且线程之间交换数据只需要读写同一块内存。

    🔬 深入内核：Linux 眼里只有 task

    Linux 内核里没有单独的"线程"数据结构，进程和线程都用 task_struct 表示，统称 task。区别只在于创建时用 clone() 传了哪些共享标志：

    • fork() ≈ clone(SIGCHLD)：什么都不共享（地址空间写时复制），得到一个新进程。
    • pthread_create() ≈ clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | ...)：共享地址空间、文件表、信号处理，得到同一进程里的新线程。

    所以在 Linux 上，每个线程都有自己的 ID（内核叫 pid，用户态叫 tid，用 gettid() 获取）。同一进程的所有线程组成一个线程组，组长的 ID 叫 tgid，用户态调用 getpid() 拿到的其实就是 tgid。ps -eLf 里的 LWP 列就是每个线程的 tid。

    Windows 的做法相反：内核里有明确分开的进程对象（EPROCESS）和线程对象（ETHREAD），进程只是容器，本身不执行，最后一个线程退出时进程随之终止。

    ⚠️ 易错点
    • "进程在执行代码"：严格地说，执行代码的是线程。进程提供执行环境。
    • "线程没有资源"：线程不拥有系统资源（文件、内存映射归进程），但它有自己必需的执行状态：寄存器、栈、TLS 和内核里的 TCB。说"线程只拥有少量必不可少的资源"更准确。
    • "一个程序 = 一个进程"：一个程序可以运行出多个进程（开两个记事本），一个进程也可以通过 exec 换成运行另一个程序。
    本章小结
    • 程序是静态文件；进程是"地址空间 + 资源"，负责资源分配和隔离；线程是执行流，负责被 CPU 调度。
    • 线程的出现，是为了把"执行"从"资源"里拆出来：多条执行流共享一套资源，既能并发又省开销。
    • Linux 内核统一用 task_struct，进程和线程的区别只是 clone 时共享了多少；Windows 内核中进程对象和线程对象是分开的。
    自测：同一个 exe 双击两次，两个进程的全局变量 g_count 地址打印出来一样，它们是同一块内存吗？

    不是。打印的是虚拟地址，两个进程各有一套页表，同一个虚拟地址会映射到不同的物理页。第 3 章的 d3_isolation 实测：父子进程 &g_value 都是 00007FF79F558000，子进程改成 999，父进程仍然是 1。（在 Windows 上，同一个 exe 的映像基址在一次开机内通常相同，所以地址恰好一样。）

    CHAPTER 02

    并发与并行

    并发是一种结构，并行是一种执行方式。

    本章目标
    • 用一句话区分并发和并行，并能举出"并发但不并行"和"并行但不并发"的例子
    • 理解单核上为什么也需要并发
    • 会用 Amdahl 定律估算多核加速比

    2.1 定义

    并发 Concurrency

    多个任务在重叠的时间段内推进。宏观上同时进行，微观上可以交替执行。它描述的是程序的结构：程序被组织成多个可以独立推进的部分。

    并行 Parallelism

    多个任务在同一时刻真正同时执行，需要多个执行部件（多核、多 CPU、GPU 的众多核心）。它描述的是执行：物理上同时在算。

    Go 语言作者之一 Rob Pike 的说法最常被引用："Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once." 并发是"同时应对很多事"，并行是"同时做很多事"。

    2.2 四种组合

    并发和并行是两个维度，不是非此即彼：

    并行（多个执行部件同时算）不并行（同一时刻只有一个在算）
    并发（多个独立推进的任务）多线程程序跑在多核上：Web 服务器 8 个工作线程处理请求单核分时系统；Node.js / Redis 主线程的事件循环；单线程上的协程调度
    不并发（只有一个逻辑任务）SIMD 向量指令：一条指令同时算 8 个 float；GPU 对一个数组做同一操作普通的单线程顺序程序

    2.3 单核上为什么也需要并发

    如果只有一个核，并发不会让计算变快，因为总计算量不变，切换还有开销。并发的价值在于让等待和计算重叠。一次机械硬盘随机读要几毫秒，一次跨机房网络往返要几十毫秒，这段时间 CPU 足够执行上千万条指令。如果程序串行地"发请求 → 干等 → 处理"，CPU 大部分时间都在空转。并发的程序在一个任务等 I/O 时切换去执行别的任务，CPU 利用率和响应速度都会提高。

    所以要区分两种负载：

    • I/O 密集型（Web 服务、网络代理、数据库连接）：瓶颈在等待，并发结构（多线程、事件循环、协程）收益很大，单核也有效。
    • CPU 密集型（视频编码、物理模拟、寻路、压缩）：瓶颈在计算，只有真正的并行（多核）才能加速。线程数超过核数后基本没有收益，反而增加切换开销。

    2.4 并行的天花板：Amdahl 定律

    假设程序中可以并行的部分占比为 p，用 n 个核，理论加速比为：

    S(n) = 1 / ( (1 − p) + p / n )

    可并行比例 p4 核16 核无穷多核（上限 1/(1−p)）
    50%1.60×1.88×2×
    90%3.08×6.40×10×
    95%3.48×9.14×20×

    结论：串行部分决定上限。即使 90% 的代码完美并行，再多的核也最多快 10 倍。实际中串行部分不只是代码逻辑，还包括锁竞争、共享缓存行争用、内存带宽，所以实测加速比通常低于理论值。

    🔬 深入：超线程算并行吗

    Intel 的超线程（SMT）让一个物理核呈现为两个逻辑核，两个硬件线程共享同一套执行单元和 L1/L2 缓存，各自有独立的寄存器组。当一个线程因缓存未命中而停顿时，另一个线程可以用空闲的执行单元。所以它是"部分并行"：两个都在跑计算密集任务时，总吞吐通常只比单线程高 10%～30%，远达不到 2 倍。

    🎮 游戏开发视角

    UE 的 GameThread 和 RenderThread 是典型的流水线并行：第 N 帧在 RenderThread 上生成渲染命令时，GameThread 已经在计算第 N+1 帧的逻辑，两者在不同的核上同时运行。资源的异步加载则主要是并发：加载线程大部分时间在等磁盘 I/O，主线程不会因此卡住。分清这两者，才能判断优化方向：前者看 CPU 核心负载，后者看 I/O 等待。

    本章小结
    • 并发是程序结构（多个任务重叠推进），并行是物理执行（同一时刻多个部件在算）。并发不一定并行，并行也不一定是并发。
    • 单核上的并发能让 I/O 等待与计算重叠；CPU 密集型任务只有并行能加速。
    • Amdahl 定律：加速比上限是 1/(1−p)，串行部分（包括锁竞争）决定天花板。
    自测：Redis 6.0 之前的命令处理是单线程的，它是并发的吗？

    是并发但不并行。Redis 用 epoll 事件循环在一个线程里同时服务成千上万个客户端连接，所有连接的请求交替推进，这就是并发。但同一时刻只有一条命令在执行，没有并行。Redis 6.0 引入的 I/O 线程只并行处理网络读写和协议解析，命令执行仍然在主线程中串行完成。

    如果两条执行流同时使用某样东西而不冲突，它就可以共享；如果它记录的是"这条执行流自己执行到哪里了"，它就必须独立。

    • PC 和寄存器：两个线程执行到不同的指令，算着不同的中间值，只能各有一份。
    • 栈：栈保存函数调用链（返回地址、局部变量）。T1 在 main → load → parse，T2 在 main → render，两条调用链不同，用同一个栈会互相覆盖。
    • errno：T1 的 open 失败设置了 errno，T2 的 read 成功不能把它清零。所以现代 C 库把 errno 实现为线程局部变量（glibc 中是宏 (*__errno_location())）。Windows 的 GetLastError() 值存放在 TEB 中，同样是每线程一份。
    • 文件表：T1 打开的文件交给 T2 读取，是很常见的需求。共享是合理的。

    d1_share.cpp 中，主线程 new 了一个 int，把指针交给 3 个工作线程。每个线程打印：全局变量地址、堆指针、自己栈上局部变量的地址、thread_local 变量的地址，以及用 GetCurrentThreadStackLimits 查到的本线程栈范围。

    🔬 深入：栈多大？TLS 在哪？
    • Windows：线程栈默认保留 1MB 虚拟地址（由链接选项 /STACK 或 CreateThread 参数决定），但只提交很少的几页，栈顶下方有一个保护页（guard page），访问到它时触发异常，系统再提交下一页并把保护页下移。用完 1MB 就会抛出 STATUS_STACK_OVERFLOW。上面输出的 size=1024 KB 就是保留大小。
    • Linux：主线程栈大小由 ulimit -s 决定（通常 8MB），可动态向下增长；glibc 创建的线程栈默认也取这个值（8MB），用 mmap 分配，并在底部放一个不可访问的保护区。可用 pthread_attr_setstacksize 调整。
    • TLS 的实现：x86-64 上，Linux 用 FS 段寄存器指向当前线程的 TCB（其中有 TLS 块），Windows 用 GS 段寄存器指向当前线程的 TEB。线程切换时内核会切换这个寄存器的基址，所以同一条指令 mov eax, fs:[offset] 在不同线程里读到不同的变量。上面输出中 TLS 的地址落在堆附近的区域（0x0000018...），因为 MSVC 的 thread_local 块是为每个线程动态分配的。

    3.4 栈私有 ≠ 别人访问不到

    这是本章的重点问题。线程有自己的栈，指的是每个线程有一块专门给自己用的内存区域来保存调用链。但这块区域在进程的地址空间里，而同一进程的所有线程用的是同一套页表。MMU 只检查"这一页在当前页表里是否映射、是否可写"，它不知道也不关心当前是哪个线程在访问。

    所以只要线程 B 拿到了指向线程 A 栈上数据的指针，它就可以读写那块数据。d2_stack_ptr.cpp 验证了这一点：

    d2_stack_ptr.cpp（核心部分）
    std::thread A([&] {
    int buf[4] = {1, 2, 3, 4};         // 位于 A 线程的栈上
    shared = buf;                      // 把栈地址交给别的线程
    ready.count_down();
    modified.wait();                   // 等 B 改完（A 的栈帧此时仍然存活）
    printf("[A] 被 B 改写后的 buf = {%d, %d, %d, %d}\n", buf[0], buf[1], buf[2], buf[3]);
});
std::thread B([&] {
    ready.wait();
    for (int i = 0; i < 4; ++i) shared[i] *= 100;   // 跨线程直接写别人的栈
});
    d2_stack_ptr.exe —— 实测输出
    [A] buf=00000021219FF7F0  A的栈范围=[0000002121900000, 0000002121A00000)
[B] 我的栈范围=[0000002121A00000, 0000002121B00000)，但我拿着指针 00000021219FF7F0
[B] 写入成功：同一进程 = 同一地址空间，硬件不拦截

结论：栈“私有”只是约定（每个线程各用各的区域），不是硬件隔离。

    B 的栈范围是 [...2121A00000, ...2121B00000)，它手里的指针 ...21219FF7F0 明显落在 A 的栈范围内，写入照样成功。

    那为什么还说栈是私有的？三层含义

    1. 空间上私有：每个线程分到一段专属的地址区间，编译器生成的 push/call/局部变量访问只会使用自己的 SP 指向的区域，正常情况下不会碰到别人的栈。
    2. 生命周期私有：栈上对象的生命周期由拥有它的线程的函数调用决定。函数返回，栈帧就失效；线程退出，整块栈都会被释放。其他线程无权也无法延长它的寿命。
    3. 默认不共享：如果没有人主动把栈地址交出去，别的线程就没有办法找到它（没有名字，地址也不固定）。

    所以，跨线程访问栈上数据在语法和硬件上都是允许的，难点在生命周期：

    ⚠️ 易错点：悬垂的栈指针（最常见的真实 Bug）
    错误示范：把局部变量的地址交给异步任务
    void StartLoad(ThreadPool& pool)
{
    char path[260] = "data/level1.pak";
    pool.Submit([&path] {              // 按引用捕获了栈上的数组
        LoadFile(path);                // 工作线程执行时，StartLoad 很可能已经返回
    });
}   // ← path 所在栈帧在这里失效，之后这块内存会被下一次函数调用覆盖

    这种 Bug 很难复现：工作线程启动得快时程序正常，慢一点就读到垃圾数据，Debug 和 Release 表现还不一样。修复方法是让数据的生命周期覆盖所有使用者：按值捕获（[path = std::string(path)]），或者放到堆上用 std::shared_ptr 管理，或者保证在栈帧返回前 join/等待任务完成（d2 就是用 latch 保证了 A 的栈帧在 B 写完之前一直存活）。

    ✅ 合法而常见的跨线程访问栈的用法
    • std::thread + 引用传参 + 在同一作用域 join：主线程栈上的数组交给工作线程处理，处理完 join，生命周期是安全的。std::jthread 在析构时自动 join，更不容易出错。
    • 同步调用：线程 A 把栈上的请求结构体地址放入队列，然后阻塞等待工作线程处理完成，再继续执行。很多 RPC 框架和 Windows 的 SendMessage 都采用这种模式。
    • OpenMP / parallel_for：并行循环访问外层函数的局部数组，因为外层函数会等所有迭代结束才返回。
    🔬 深入：栈溢出会写坏别人的栈吗

    d1 的输出显示，各线程的栈在地址上首尾相连。理论上，T2 的栈向下溢出就会进入 T1 栈的高地址部分。实际上中间隔着保护页：Windows 的 guard page 和 Linux 的 guard area 都不可访问，溢出时会先触发异常（Windows STATUS_STACK_OVERFLOW，Linux SIGSEGV），程序直接崩溃。但如果在栈上开了一个比保护页还大的局部数组（例如 char buf[64*1024]）并且从远端开始写，就可能跳过保护页直接写到相邻区域。因此编译器会在大栈帧函数中插入栈探测（MSVC 的 __chkstk，GCC 的 -fstack-clash-protection），按页依次触碰，确保一定会碰到保护页。

    3.5 共享的代价：数据竞争

    共享地址空间让线程间通信几乎零成本，代价是：多个线程同时读写同一块内存，且至少有一个是写，又没有同步，就构成数据竞争。在 C++ 标准中，数据竞争是未定义行为。

    最经典的例子是 counter++。它看起来是一条语句，实际是三步：从内存读到寄存器 → 寄存器加 1 → 写回内存。两个线程交错执行就会丢失更新：

    d5_race.exe —— 4 线程各自增 100 万次，实测输出

普通变量 ++ (round) 结果=  3390547  期望=4000000  耗时=   2.8 ms
普通变量 ++ (round) 结果=  1737623  期望=4000000  耗时=   1.7 ms

    三点观察：

    1. 普通变量每次结果都不一样，最少的一次只有期望值的 30%。结果不确定正是数据竞争的特征。
    2. 代码中的 volatile 只是阻止编译器把循环优化成一条加法，它不提供原子性。这是 C++ 面试的常见陷阱（Java 的 volatile 语义不同，有可见性和有序性保证，但同样不保证复合操作的原子性）。
    3. 正确的版本更慢：atomic 慢约 2～10 倍，mutex 更慢。原因是多个核争抢同一条缓存行，每次写都要通过缓存一致性协议使其他核的副本失效。共享可写数据本身就有成本，所以高性能设计会尽量让每个线程写自己的数据（例如每线程一个局部计数器，最后汇总）。

    为什么不能只杀掉出错的那个线程？

    因为没有办法知道它破坏了什么。出错的线程可能已经写坏了堆上的数据结构，也可能正持有一把锁（如果只杀掉它，这把锁永远不会被释放，其他线程等这把锁时会死锁），还可能正在修改一个被所有线程共享的全局状态，修改到一半。由于地址空间是共享的，这些破坏对所有线程都可见，继续运行的结果不可预测。所以操作系统的默认策略是终止整个进程：

    • Linux：SIGSEGV 是发给线程组（整个进程）的致命信号，默认动作是终止整个进程并生成 core dump。
    • Windows：未处理的结构化异常最终交给系统的未处理异常过滤器，默认调用 WER（错误报告）并终止进程。

    4.1 五状态模型

    转换触发者典型例子
    ① 创建 → 就绪内核完成初始化fork / CreateProcess 返回前，新任务进入就绪队列
    ② 就绪 → 运行调度器当前任务让出 CPU，调度器从就绪队列选出下一个
    ③ 运行 → 就绪时钟中断 / 调度器时间片用完；更高优先级的任务被唤醒并抢占；调用 sched_yield / SwitchToThread
    ④ 运行 → 阻塞任务自己（经系统调用）read 磁盘、recv 网络、mutex.lock() 没抢到、sleep、cv.wait
    ⑤ 阻塞 → 就绪中断处理程序 / 其他任务磁盘 DMA 完成触发中断；持锁线程 unlock 唤醒等待者；定时器到期
    ⑥ 运行 → 终止任务自己 / 内核return 出 main；exit；收到 SIGKILL；访问违例
    ✅ 面试答法：为什么没有"阻塞 → 运行"和"就绪 → 阻塞"？

    阻塞 → 运行：事件发生只说明它可以运行了，但 CPU 可能正被别人占用，必须先进入就绪队列，由调度器统一决定谁上 CPU。（有些内核会在唤醒时检查优先级，若被唤醒者更高就立即触发抢占，但逻辑上仍是"先就绪、再被调度"。）

    就绪 → 阻塞：阻塞是任务自己执行了一个"等待"操作（系统调用）的结果，而就绪的任务根本没有在执行，不可能发起等待。

    ⚠️ 易错点：用户态/内核态 ≠ 运行/阻塞

    "用户态、内核态"说的是 CPU 的特权级；"运行、就绪、阻塞"说的是调度状态。一个线程执行系统调用时进入内核态，但它仍然是"运行"状态；只有在内核里发现需要等待并调用调度函数让出 CPU 时，它才变为"阻塞"。

    4.3 扩展：挂起状态（七状态模型）

    当内存紧张时，操作系统可能把某些进程整个换出到磁盘，这时就多出两个状态：就绪挂起（在磁盘上，换入就能跑）和阻塞挂起（在磁盘上，还在等事件）。现代通用操作系统以页为单位换出内存，很少整进程换出，所以这个模型更多出现在教材和考研题中。了解即可：挂起关注的是"在不在内存里"，阻塞关注的是"在不在等事件"，两者正交。

    4.4 真实系统里的状态

    Linux：ps 的 STAT 列

    STAT内核状态对应教科书说明
    RTASK_RUNNING就绪 + 运行Linux 不区分就绪和运行，都是 R，区别只在是否正在某个 CPU 上
    STASK_INTERRUPTIBLE阻塞可中断睡眠：信号可以把它唤醒（例如 sleep、等待 socket）
    DTASK_UNINTERRUPTIBLE阻塞不可中断睡眠：通常在等磁盘 / NFS I/O。kill -9 也杀不掉，大量 D 状态进程通常说明存储出了问题
    T / tTASK_STOPPED / TRACED（挂起）被 SIGSTOP/Ctrl+Z 暂停，或正被调试器跟踪
    ZEXIT_ZOMBIE终止已退出但父进程尚未 wait，第 8 章详述
    XEXIT_DEAD终止正在被彻底回收，几乎看不到

    Linux 的平均负载（load average）统计的是 R + D 状态的任务数。所以负载高不一定是 CPU 忙，也可能是大量任务卡在磁盘 I/O 上。

    Windows：线程状态

    Windows 调度的对象是线程，进程本身没有运行状态。线程状态（KTHREAD_STATE）比教科书更细：Initialized（创建中）→ Ready（就绪）→ Deferred Ready（已选定处理器，等待被分派）→ Standby（已被选为某处理器下一个要运行的线程）→ Running → Waiting（阻塞）→ Terminated。另外还有 Transition（就绪但内核栈被换出内存）。可以在 Process Explorer 中查看线程属性观察这些状态。

    4.5 上下文切换：状态转换的代价

    每次"运行 → 其他状态 → 运行"，CPU 都要从一个线程换到另一个线程，这叫上下文切换。它包括：

    1. 进入内核：通过时钟中断、系统调用或异常。
    2. 保存当前线程的上下文：通用寄存器、PC、SP、标志寄存器，必要时还有浮点 / SIMD 寄存器（AVX-512 状态可达 2KB 以上），保存到它的内核栈和 TCB 中。
    3. 调度器选择下一个线程。
    4. 如果下一个线程属于另一个进程：切换页表（x86 上写 CR3 寄存器）。
    5. 恢复下一个线程的上下文，切换内核栈、FS/GS 基址（TLS），返回用户态。
    🧪 实测证据：d4_cost 的 ping-pong 测试

    把进程绑定到同一个 CPU 核上，两个执行流用 Event 来回唤醒对方 10 万次，每一次交互必然发生一次上下文切换。测得的单次时间包含了 SetEvent/WaitForSingleObject 两次系统调用的开销。

    d4_cost.exe —— 实测输出（同核 ping-pong）
    单次切换(含事件系统调用)  线程间: 0.68 us   进程间: 1.50 us

    跨进程切换是线程切换的约 2.2 倍。需要注意，这个微基准中两个进程的工作集都极小，没有体现缓存和 TLB 被污染的间接开销。在真实程序中，切换后需要重新加载的缓存行和 TLB 项越多，差距越大。

    🔬 深入：PCID 与 KPTI

    早期 x86 写 CR3 会刷新整个 TLB（全局页除外）。现代 CPU 支持 PCID（进程上下文标识符），TLB 项带上地址空间标签，切换后旧进程的 TLB 项可以保留，切回来时继续使用。2018 年 Meltdown 漏洞之后，内核引入了 KPTI（内核页表隔离）：用户态和内核态使用两套页表，于是每次系统调用也要切换 CR3，PCID 在这里同样能大幅降低开销。这也是为什么当年打 Meltdown 补丁后，系统调用密集型的程序（数据库、I/O 密集服务）性能下降明显。

    本章小结
    • 五状态：创建、就绪、运行、阻塞、终止；六条合法转换。就绪是"差 CPU"，阻塞是"差事件"。
    • 阻塞由任务自己发起，唤醒由别人完成；唤醒后先回就绪队列，不能直接运行。
    • Linux 用 R 同时表示就绪和运行；D 状态不可被信号打断；Z 是僵尸。
    • 上下文切换要保存/恢复寄存器；跨进程还要切换页表，导致 TLB 和缓存失效。实测同核切换：线程 0.68μs，进程 1.50μs。

    进程控制块与线程控制块

    PCB 是进程在内核中的"档案"，TCB 是线程的"档案"。理解它们要记什么，就不用背字段。

    本章目标

    5.1 从需求推导 PCB 的内容

    不要背字段。问自己：操作系统要管理一个进程，需要做哪些事？每件事需要记住什么？

    操作系统要做的事因此必须记录放在 PCB 还是 TCB
    区分不同的进程 / 线程PID、TID、父进程 ID、所属用户两者都有各自的 ID
    暂停一个执行流，以后从原处继续CPU 上下文：PC、SP、通用寄存器、标志寄存器、浮点状态TCB

    5.2 PCB 如何被组织起来

    单个 PCB 只是档案，操作系统还要能快速找到"所有就绪的线程""等待某个磁盘请求的线程"。方法是把 TCB 挂到不同的队列 / 数据结构上：

    • 就绪队列：Linux CFS 调度器为每个 CPU 维护一棵按"虚拟运行时间"排序的红黑树，每次选最左边（运行得最少）的任务；Linux 6.6 起换成了 EEVDF 调度器，但仍然是每 CPU 一个运行队列。Windows 为每个处理器维护 32 个优先级的就绪队列，配合位图快速找到最高优先级的非空队列。
    • 等待队列：每个可等待的对象（一把锁、一个 socket、一个磁盘请求）都有自己的等待队列。线程阻塞时挂上去，事件发生时被摘下、放回就绪队列。
    • 全局索引：按 PID 查找（Linux 用 IDR/基数树），以及所有进程的链表。

    状态转换在实现上就是把 TCB 从一个队列移到另一个队列，再修改它的状态字段。

    5.3 Linux：task_struct

    如第 1 章所说，Linux 中进程和线程都由 task_struct 表示（定义在 include/linux/sched.h，有几百个字段）。它的巧妙之处在于：共享的资源不直接放在 task_struct 里，而是放在独立的结构体中，用指针引用。同一进程的线程，指针指向同一个结构体；不同进程的指针指向不同的结构体。

    task_struct 极简示意（非真实定义，只保留与本章相关的字段）
    struct task_struct {
    /* ---- 每个 task 自己的：相当于 TCB ---- */
    unsigned int          __state;      // TASK_RUNNING / TASK_INTERRUPTIBLE / ...
    pid_t                 pid;          // 内核视角的 ID，即用户态的 tid
    pid_t                 tgid;         // 线程组 ID，即用户态 getpid() 的返回值
    int                   prio;         // 动态优先级
    struct sched_entity   se;           // CFS/EEVDF 调度实体：vruntime、红黑树节点……
    void                 *stack;        // 内核栈
    struct thread_struct  thread;       // 体系结构相关的 CPU 上下文（sp、fs 基址……）
    sigset_t              blocked;      // 本线程的信号屏蔽字

    /* ---- 指向共享资源的指针：相当于 PCB 的内容 ---- */
    struct mm_struct      *mm;          // 地址空间：页表 pgd + 内存区域 VMA 列表
    struct files_struct   *files;       // 文件描述符表
    struct fs_struct      *fs;          // 根目录、当前工作目录
    struct signal_struct  *signal;      // 线程组共享的信号状态
    struct sighand_struct *sighand;     // 信号处理函数表
    const struct cred     *cred;        // uid / gid / capabilities

    /* ---- 家族关系 ---- */
    struct task_struct    *real_parent;
    struct list_head       children, sibling;
    int                    exit_code;   // 退出码，僵尸状态时保留给父进程
};
    🔬 深入：内核线程的 mm 为什么是 NULL

    内核线程（如 kworker、ksoftirqd）只在内核空间运行，不需要用户地址空间，所以它们的 mm 为 NULL。调度到内核线程时，内核会"借用"上一个用户进程的页表（记在 active_mm 中），因为所有进程页表中的内核部分都是相同的，这样就省掉了一次 CR3 切换。这是一个"不切换地址空间就能省开销"的实例，和第 4 章的分析一致。

    5.4 Windows：内核结构 + 用户态结构

    结构位于作用
    EPROCESS（内含 KPROCESS）内核空间进程对象：PID、页表目录基址、句柄表、访问令牌、线程列表、Job 归属……KPROCESS 是其中调度相关的部分
    ETHREAD（内含 KTHREAD）内核空间线程对象：TID、状态、优先级、内核栈、等待块、上下文……
    PEB（进程环境块）用户空间已加载模块列表、进程堆、命令行、环境变量指针。kernel32/ntdll 在用户态直接读取它，省去系统调用
    TEB（线程环境块）用户空间栈基址与栈限制、TLS 槽、LastErrorValue、SEH 链表头、指向 PEB 的指针。x64 下由 GS 寄存器指向

    PEB / TEB 的设计说明了一点："线程控制信息"不一定都在内核里。为了性能，那些用户态频繁读写、又不涉及安全的状态（如 GetLastError 的值、栈边界）被放在用户空间。d1 中调用的 GetCurrentThreadStackLimits 本质上就是从 TEB 中读取栈的上下界，不需要进入内核。

    ⚠️ 易错点

    面试问"PCB 包含什么"时，不要逐个背 Linux 字段名，而应该按"标识、处理器状态、调度信息、内存管理、资源清单、家族与统计"分类回答，再补一句"其中处理器状态和调度信息在多线程系统中下沉到了每个线程的 TCB"。这能体现你理解了 PCB 与 TCB 的分工。

    本章小结
    • PCB 记录进程的"标识 + 资源 + 控制信息"，TCB 记录线程的"执行上下文 + 调度信息"。两者的划分与第 3 章的资源边界一致。

    • Linux 的 task_struct 通过指针共享 mm/files/sighand 来区分进程和线程；Windows 有 EPROCESS/ETHREAD 以及用户态的 PEB/TEB。

    6.1 定义

    用户级线程（ULT）

    线程的创建、切换、调度全部由用户态的线程库完成。内核完全不知道它们的存在，在内核看来这个进程只有一条执行流（一个内核线程）。

    内核级线程（KLT）

    线程由内核创建和管理，每个线程有内核中的 TCB，由内核调度器调度到 CPU 上。pthread（Linux NPTL）、Windows 线程、std::thread 都是内核级线程。

    🧪 实测证据：Windows Fiber 一个阻塞，全部阻塞（d6_fiber_coro Part1）

    Windows 的 Fiber（纤程）是操作系统提供的用户级线程原语：每个 Fiber 有自己的栈和寄存器上下文，但由程序调用 SwitchToFiber 显式切换，内核完全不参与调度。程序在一个线程上创建两个 Fiber，主 Fiber 轮流切换它们。Fiber1 在第 1 步调用了 Sleep(300)：

  Fiber0 第0步  tid=20764  &local=00000009D3FFFE00
  Fiber1 第0步  tid=20764  &local=00000009D40FFCF0
  Fiber0 第1步  tid=20764  &local=00000009D3FFFE00
  Fiber1 第1步  tid=20764  &local=00000009D40FFCF0

    三点值得注意：

    1. tid 始终相同：两个 Fiber 都运行在同一个内核线程上，内核只看到这一个线程。
    2. &local 不同，且每次切回来都不变：每个 Fiber 有自己独立的栈（相距 1MB 左右），切换时保存和恢复栈指针，这和内核线程的栈私有是同一个原理，只是切换由用户代码完成。
    3. Fiber1 调用阻塞式系统调用后，Fiber0 整整 307ms 没有机会执行。内核让这个线程睡眠，它不知道线程里还有一个 Fiber0 可以运行。

    6.4 历史与现状：大家最后怎么选的

    • Linux：早期的 LinuxThreads 实现有很多不符合 POSIX 的地方（例如每个线程 getpid() 返回不同值）。2003 年 NPTL 随 Linux 2.6 推出，采用 1:1 模型，配合内核 clone 线程组和 futex，线程创建和同步都很快。IBM 曾经开发过 M:N 的 NGPT，最终被放弃。
    • Solaris：Solaris 8 之前是 M:N，Solaris 9 起改为 1:1，理由是 M:N 实现复杂、两层调度器互相干扰，而 1:1 在内核优化后已经足够快。
    • Windows：内核线程 1:1；另外提供 Fiber（N:1 用户态原语）。Windows 7 引入过用户模式调度（UMS），支持 M:N，后来已被弃用。
    • Go：goroutine 是 M:N。GMP 调度器：G 是 goroutine，M 是内核线程，P 是逻辑处理器（数量默认等于 CPU 核数）。它解决了"一个阻塞全部阻塞"：当 G 进入阻塞式系统调用时，M 与 P 分离，P 交给另一个 M 继续运行其他 G；网络 I/O 则由 netpoller（底层是 epoll/kqueue/IOCP）转成非阻塞，G 只是被挂起。Go 1.14 起还支持基于信号的异步抢占。
    • Java：长期使用 1:1 的平台线程；JDK 21 正式推出虚拟线程（M:N），阻塞 I/O 时虚拟线程从载体线程上卸载。
    ✅ 面试答法：M:N 模型如何解决用户级线程的缺点

    用户级线程有两个硬伤：无法利用多核和一个阻塞全部阻塞。M:N 用多个内核线程承载用户线程，解决了第一个；第二个则靠运行时拦截阻塞操作：网络 I/O 改用非阻塞 + 事件通知（epoll / IOCP），其他阻塞系统调用发生时把当前内核线程"让出去"、再启动或唤醒一个内核线程接管其余的用户线程。代价是运行时复杂度很高，而且对于运行时无法拦截的阻塞（比如 C 库里的阻塞调用、持有锁时的阻塞），仍然会占住内核线程。

    本章小结
    • 用户级线程：内核不可见，切换快、可定制，但不能用多核、一阻塞全阻塞。内核级线程：反之。
    • 主流操作系统线程都是 1:1；M:N 的复杂度转移到了语言运行时（Go、Java 虚拟线程）。
    • 实测：Fiber 上的 Sleep(300) 让同一线程上的另一个 Fiber 停了 307ms。

    线程、协程、任务

    线程是操作系统的执行单元，协程是语言层面的执行单元，任务是"要做的一件事"本身。

    本章目标
    • 说清楚协程是什么，和线程在调度方式、栈、开销上的区别
    • 区分有栈协程和无栈协程，理解 C++20 协程为什么是"无栈"的
    • 理解"任务"是更高层的抽象，它可以跑在线程池上，也可以由协程表达

    7.1 协程：可以暂停和恢复的函数

    普通函数调用只有"调用"和"返回"两个动作，一旦返回，它的局部变量就没了。协程多了"挂起"和"恢复"：执行到一半可以暂停，把控制权交还给调用者，之后再从暂停的位置继续，局部变量都还在。

    从这个意义上看，协程和第 6 章的用户级线程是一回事的两种叫法，侧重点不同：用户级线程强调"它是线程的一种实现"，协程强调"它是一种控制流结构"。两者共同的特征是：

    • 协作式调度：只在明确的挂起点（co_await、yield、SwitchToFiber）让出，不会在任意指令处被打断。
    • 用户态切换：不进入内核，代价是一次函数调用的量级。
    • 内核不可见：一个协程执行阻塞式系统调用，会阻塞它所在的整个线程。

    7.2 有栈协程与无栈协程

    d6 的 Part2 使用的是 C++20 协程。Download 函数里每次 co_await Yield{}，编译器会把它改写为大致这样的状态机：

    C++20 协程被编译器改写后的等价逻辑（示意）
    struct DownloadFrame {               // 分配在堆上（编译器可能优化掉）
    int   state = 0;                 // 下一次恢复时从哪个挂起点继续
    const char* name; int chunks;    // 参数
    int   i;                         // 跨越 co_await 存活的局部变量
    Task::promise_type promise;
};
void resume(DownloadFrame* f) {
    switch (f->state) {
    case 0: for (f->i = 1; f->i <= f->chunks; ++f->i) {
                printf("[%s] 下载块 %d/%d\n", f->name, f->i, f->chunks);
                f->state = 1; g_ready.push_back(handle_of(f)); return;   // 挂起：直接 return
    case 1:     ;                                                        // 恢复：跳回循环里
            }
            printf("[%s] 完成\n", f->name);
            f->state = 2; return;                                        // final_suspend
    }
}

    可以看到，无栈协程挂起时不保留栈帧，局部变量 i 被搬进了堆上的协程帧，恢复时用 switch 跳回去。这就是"无栈"的含义：它在运行时借用调用者线程的栈，挂起时什么都不留在栈上。

    ⚠️ 易错点：协程里同样有"栈上指针"的陷阱

    第 3 章讲过跨线程访问栈数据要注意生命周期，协程里也一样，而且更隐蔽：协程按引用接收的参数（const std::string&）在第一次挂起之后可能就失效了，因为调用者的临时对象在调用表达式结束时就被销毁。协程参数应该按值传递，让它被复制进协程帧。

    7.3 任务：要做的那件事

    任务（Task）不是一种执行机制，而是一个工作单元的抽象：一段要执行的计算，通常带有输入、结果和依赖关系。任务本身不规定由谁执行，可以：

    • 提交到线程池，由某个工作线程取出执行（std::async、Intel TBB、Java ExecutorService、UE TaskGraph/UE::Tasks）；
    • 由协程表达，在事件循环中被调度（C# Task、Python asyncio.Task、JS Promise）；
    • 按依赖关系组成 DAG，由调度器尽量并行执行（游戏引擎的 Job System）。
    ⚠️ 术语冲突

    Linux 内核源码里的 "task" 指 task_struct，也就是进程/线程，这和上面说的任务完全不同。面试中提到 task 时，最好先确认对方说的是哪个层面的概念。

    单线程上的协程不会有数据竞争（同一时刻只有一个在运行，不存在两个线程同时写同一内存），但仍然有逻辑上的竞态：

    跨越挂起点的检查-再执行
    Task Withdraw(Account& acc, int amount) {
    if (acc.balance >= amount) {     // ① 检查：余额够
        co_await AuditLog(amount);   // ② 挂起！另一个 Withdraw 协程在这期间也通过了检查
        acc.balance -= amount;       // ③ 执行：两笔都扣了，余额变成负数
    }
}

    🎮 游戏开发视角

    Unity 的 Coroutine（yield return）就是运行在主线程上的无栈协程，每帧由引擎恢复一次，所以它不能利用多核，也不能在里面执行耗时的同步计算，否则会卡帧。UE 的 TaskGraph / UE::Tasks 是任务系统，任务分发到工作线程上并行执行。Naughty Dog 的引擎在 GDC 演讲中介绍过基于 Fiber 的 Job System：每个 Job 运行在一个 Fiber 上，等待依赖时切换到别的 Fiber，内核线程数量固定等于核数，这样既有用户态切换的低开销，又能利用多核。

    本章小结
    • 协程是可以挂起和恢复的函数，协作式、用户态切换、内核不可见。
    • 有栈协程保存整条调用栈，可在任意深度挂起；无栈协程由编译器改写成状态机，帧在堆上，只能在协程函数自身挂起。C++20 协程是无栈的。
    • 任务是"工作单元"的抽象，与执行机制解耦，可以跑在线程池上，也可以用协程表达。
    • 单线程协程没有数据竞争，但跨挂起点的"检查-执行"仍然有逻辑竞态。

    Linux：fork、exec、wait，孤儿与僵尸

    fork 复制一个自己，exec 把自己换成别的程序，wait 给死去的子进程收尸。

    本章目标
    • 准确说出 fork 后哪些东西被复制、哪些被共享，理解写时复制
    • 说出 exec 保留了什么、替换了什么
    • 理解僵尸进程和孤儿进程的成因、危害和处理方法

    8.1 Shell 是怎么执行一条命令的

    在 bash 里输入 ls -l，bash 做了三件事：fork 出一个子进程（此时子进程还是 bash）；子进程调用 exec 把自己替换成 /usr/bin/ls；父进程 bash 调用 wait 等待子进程结束，拿到退出码（就是 $?），然后打印下一个提示符。

    8.2 fork：调用一次，返回两次

    fork 的返回值
    pid_t pid = fork();
if (pid < 0)       { /* 失败：进程数达到上限、内存不足 */ }
else if (pid == 0) { /* 子进程：fork 返回 0（可用 getppid() 找父亲） */ }
else               { /* 父进程：fork 返回子进程的 PID（父进程没有别的办法知道孩子是谁） */ }

    fork 之后，父子进程从同一个位置（fork 返回处）继续执行，区别只在返回值。至于谁先运行，由调度器决定，程序不能依赖任何顺序。

    fork 之后什么被复制，什么被共享

    项目fork 后说明
    地址空间（代码、数据、堆、栈）逻辑上复制，物理上写时复制见下文 COW
    文件描述符表表复制，但指向同一个打开文件表项文件偏移量和状态标志是共享的！父子进程交替写同一个 fd，内容会接在一起而不是互相覆盖
    信号处理方式、屏蔽字复制待处理信号集会被清空
    当前目录、umask、uid/gid、资源限制复制
    PID、PPID不同子进程获得新 PID，PPID 是父进程
    文件锁（fcntl 记录锁）不继承
    定时器、CPU 时间统计清零
    线程只复制调用 fork 的那一个多线程程序 fork 的大坑，见下文
    🎮 工程视角：COW 的妙用与代价

    Redis 的 RDB 持久化就是利用 fork + COW：主进程 fork 出子进程，子进程看到的是 fork 那一刻内存的"快照"，慢慢写到磁盘；主进程继续处理写请求，只有被修改的页才会被复制。代价是：如果快照期间写入很多，被复制的页会很多，内存可能接近翻倍；另外 fork 本身要复制页表，几十 GB 的实例 fork 一次可能要几十到几百毫秒，期间主进程是阻塞的。开启透明大页（THP）还会让每次 COW 复制 2MB 而不是 4KB，所以 Redis 建议关闭 THP。

    ⚠️ 易错点：多线程程序里 fork

    fork 只复制调用它的线程。假设 fork 时另一个线程恰好持有 malloc 内部的锁，子进程里这把锁仍然是"已锁定"状态，但持锁的线程在子进程中并不存在，永远不会解锁。子进程一调用 malloc（printf 内部也可能调用）就会死锁。因此 POSIX 规定：多线程程序 fork 后，子进程在调用 exec 之前只能调用异步信号安全的函数。实践建议：多线程程序要启动外部程序时，fork 后立刻 exec，或直接用 posix_spawn。pthread_atfork 可以注册在 fork 前后获取/释放锁的回调，但很难做到完备。

    8.3 exec：换掉灵魂，保留身份

    exec 系列函数把当前进程的程序映像整个替换为新程序：旧的代码、数据、堆、栈全部丢弃，按新程序的 ELF 文件重新建立地址空间，从新程序的入口开始执行。exec 成功后不会返回，因为调用它的代码已经不存在了。

    PID、PPID、进程组、会话
    文件描述符（除非设置了 FD_CLOEXEC）
    当前目录、umask、资源限制
    信号屏蔽字、待处理信号
    被设为忽略（SIG_IGN）的信号仍然忽略    		代码、数据、堆、栈、内存映射
    自定义的信号处理函数恢复为默认（函数地址在新程序里没有意义了）
    除调用线程外的所有线程被销毁
    用 O_CLOEXEC 打开的 fd 被关闭

    exec 家族命名规律：l（list，参数逐个列出）/ v（vector，参数用数组）；p（在 PATH 中查找程序）；e（自己指定环境变量）。真正的系统调用只有 execve，其余都是 libc 包装。

    ✅ 实践建议：fd 泄漏与 O_CLOEXEC

    如果服务进程打开了数据库连接、监听 socket，fork + exec 启动一个脚本后，脚本进程会继承这些 fd。轻则资源泄漏，重则服务重启时端口一直被脚本进程占着。现代代码应该在打开 fd 时就加上 O_CLOEXEC / SOCK_CLOEXEC。

    8.4 wait / waitpid：回收子进程

    waitpid 用法要点

pid_t w = waitpid(pid, &status, 0);        // pid=-1 表示任意子进程；options=WNOHANG 表示不阻塞
if (WIFEXITED(status))   printf("正常退出，码=%d\n", WEXITSTATUS(status));
if (WIFSIGNALED(status)) printf("被信号 %d 杀死\n",  WTERMSIG(status));   // 例如 SIGSEGV=11

    wait 有两个作用：获取子进程的退出状态，以及让内核释放子进程残留的 task_struct。第二个作用引出了僵尸进程。

    8.5 完整示例：fork_exec_wait.c

    demos/linux/fork_exec_wait.c
    int g_value = 1;
int main(void)
{
    printf("[parent] pid=%d  &g_value=%p\n", getpid(), (void*)&g_value);
    fflush(stdout);                      // 关键：fork 前清空 stdio 缓冲，否则缓冲区会被复制一份
    pid_t pid = fork();                  // 调用一次，返回两次
    if (pid == 0) {                      // ---- 子进程 ----
        g_value = 999;                   // 写时复制：此刻才真正复制这一页
        printf("[child ] pid=%d ppid=%d  &g_value=%p  g_value=%d\n",
               getpid(), getppid(), (void*)&g_value, g_value);
        fflush(stdout);
        execlp("ls", "ls", "-l", "/proc/self/exe", (char*)NULL);  // 用 ls 替换自身映像，PID 不变
        perror("execlp");                // 只有 exec 失败才会走到这里
        _exit(127);
    }
    int status;
    pid_t w = waitpid(pid, &status, 0);  // 阻塞等待并回收，避免僵尸
    if (WIFEXITED(status))
        printf("[parent] 回收子进程 %d，退出码=%d，g_value 仍然=%d\n", w, WEXITSTATUS(status), g_value);
    return 0;
}

    8.6 僵尸进程

    子进程退出时，内核释放它的大部分资源（内存、打开的文件），但保留 task_struct 中的 PID、退出码和资源使用统计，因为父进程可能还要通过 wait 读取它们。在父进程调用 wait 之前，这个只剩一个"档案"的进程就是僵尸进程（Zombie），ps 中显示为 Z，命令名后带 <defunct>。

    观察僵尸（demos/linux/zombie_orphan.c）
    $ ./zo zombie &
child 5301 exit now
parent 5300 不调用 wait，睡 60s；此时子进程是僵尸
$ ps -o pid,ppid,stat,cmd --ppid 5300
  PID  PPID STAT CMD
 5301  5300 Z    [zo] <defunct>
$ kill -9 5301        # 无效：它已经死了，信号对僵尸没有意义
$ kill 5300           # 杀掉父进程 → 僵尸被 init 收养并立即回收

    危害

    单个僵尸几乎不占内存，但它占用一个 PID。PID 数量有上限（/proc/sys/kernel/pid_max，以及 cgroup 的 pids.max）。一个不断创建子进程又从不回收的服务，最终会让系统无法创建新进程，报 fork: Resource temporarily unavailable。

    解决方法

    1. 父进程同步 wait：适合父进程本来就要等待子进程结束的场景（shell）。
    2. 处理 SIGCHLD，在 handler 里循环 waitpid(-1, NULL, WNOHANG)：适合父进程有自己的工作要做的场景（服务器）。必须循环，因为多个子进程同时退出时，标准信号不排队，多个 SIGCHLD 可能只被递送一次。
    3. 显式设置 signal(SIGCHLD, SIG_IGN)：POSIX 规定此时子进程退出后由内核自动回收，不产生僵尸（代价是父进程拿不到退出码）。
    4. 两次 fork：父进程 fork 出 A，A 再 fork 出 B 后立刻退出，父进程 wait 回收 A；B 成为孤儿，由 init 负责回收。传统守护进程的创建方法。
    正确回收：SIGCHLD handler（zombie_orphan.c 的 reap 模式）
    static void on_sigchld(int sig)
{
    int saved = errno;                         // 信号处理函数可能打断主流程，保护 errno
    while (waitpid(-1, NULL, WNOHANG) > 0) {}  // 必须循环：多个 SIGCHLD 可能被合并成一个
    errno = saved;
}

    8.7 孤儿进程

    父进程先于子进程退出，子进程就成了孤儿进程。内核会把它过继给 init 进程（PID 1，现在通常是 systemd），或者过继给离它最近的、设置了 PR_SET_CHILD_SUBREAPER 的祖先进程（Linux 3.4 起支持）。新的父进程会负责 wait 它。所以孤儿进程本身无害，它会继续正常运行，退出后也会被回收。

    8.8 笔试题：fork 计数与缓冲区陷阱

    经典题 1：会打印几个 "-"？
    int main() {
    for (int i = 0; i < 2; ++i) {
        fork();
        printf("-");
    }
}

    答案是 8 个，不是 6 个。逐步分析：

    • i=0：1 个进程 fork 成 2 个，各执行一次 printf("-")。注意 "-" 没有换行，而且 stdout 输出到管道或文件时是全缓冲，所以这个 "-" 只是写进了各自的用户态缓冲区，并没有真正输出。
    • i=1：2 个进程 fork 成 4 个。fork 会复制整个地址空间，包括 stdio 缓冲区，所以 4 个进程的缓冲区里都已经有一个 "-"。每个进程再 printf 一次，缓冲区变成 "--"。
    • 4 个进程退出时各自刷新缓冲区：4 × 2 = 8。

    如果改成 printf("-\n") 并输出到终端（终端上 stdout 是行缓冲），每次 printf 都会立即输出，答案就是 2 + 4 = 6。这就是 8.5 节代码里 fork 前要 fflush(stdout)、子进程里要用 _exit 而不是 exit 的原因。

    经典题 2：一共有几个进程（含原进程）？
    fork() && fork() || fork();
    点击查看答案：5 个

    利用短路求值：原进程执行第一个 fork（记为 A），得到父 P 和子 C1。

    • P 中 A>0 为真，继续执行第二个 fork（B），得到 P 和 C2。P 中 B>0，A && B 为真，|| 短路，不再 fork。C2 中 B=0，A && B 为假，执行第三个 fork，再产生 C3。
    • C1 中 A=0，&& 短路为假，执行第三个 fork，产生 C4。

    合计 P、C1、C2、C3、C4 共 5 个进程。

    本章小结
    • fork：返回两次；地址空间写时复制；fd 表复制但共享文件偏移；只复制调用线程。
    • exec：替换映像，保留 PID 和未设 CLOEXEC 的 fd；信号处理函数重置为默认；成功不返回。
    • wait：获取退出状态并释放残留的 task_struct。
    • 僵尸：子先死父未收，占 PID，用 wait / SIGCHLD / SIG_IGN / 两次 fork 解决；孤儿：父先死，被 init 或 subreaper 收养，无害。

    先挂起创建，在子进程运行任何代码之前做一些设置：把它放进 Job 对象、调整优先级、注入调试或性能分析用的 DLL，然后再 ResumeThread。这在功能上相当于 Linux 中 fork 和 exec 之间的那段"空隙"。

    9.2 进程是内核对象：句柄与引用计数

    在 Windows 中，进程和线程都是内核对象，用户态通过句柄引用它们。内核对象有引用计数，只有当所有句柄都关闭、且进程已经终止时，EPROCESS 才会被真正释放。

    • 进程终止（最后一个线程退出，或调用 ExitProcess/TerminateProcess）后，它的地址空间、句柄表等资源立刻被清理，进程对象变为有信号状态，等待它的 WaitForSingleObject 返回。
    • 但只要还有人持有它的句柄，进程对象本身就保留着，里面记录着退出码，可以用 GetExitCodeProcess 读取。
    ⚠️ 易错点：Windows 上的"僵尸"

    这和 Linux 的僵尸进程本质相同：进程已经结束，但为了让别人读取退出状态，内核对象被保留了下来。区别是 Linux 依赖"父进程 wait"，Windows 依赖"所有句柄被关闭"。如果程序反复 CreateProcess 却忘了 CloseHandle(pi.hProcess) 和 CloseHandle(pi.hThread)，就会泄漏内核对象，在任务管理器里看到句柄数持续增长。这是 Windows 服务程序中很常见的泄漏。

    9.3 父子关系很"松"

    • 没有强制的进程树：Windows 只在子进程中记录了创建者的 PID（InheritedFromUniqueProcessId），仅作参考。父进程退出不影响子进程，也不存在"过继给 init"的机制。记录的父 PID 可能已经被别的进程复用，所以不能依赖它。
    • 不需要父进程来回收：任何持有进程句柄的进程都可以等待它、读取它的退出码。
    • 想要"父进程退出时子进程一起退出"：要用 Job 对象。把子进程放进一个设置了 JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE 的 Job，当 Job 的最后一个句柄关闭（例如父进程崩溃）时，Job 中的所有进程都会被终止。Chrome、VS 的构建系统、各种游戏启动器都用这个机制管理子进程。

    9.4 句柄继承

    Linux 子进程默认继承所有 fd（除非设置 CLOEXEC）；Windows 正好相反，默认什么都不继承，必须同时满足两个条件：句柄在创建时被标记为可继承（SECURITY_ATTRIBUTES.bInheritHandle = TRUE 或 SetHandleInformation），并且 CreateProcess 的 bInheritHandles 参数为 TRUE。继承来的句柄在子进程中数值相同，所以通常通过命令行参数或 STARTUPINFO 中的标准输入输出字段把句柄值告诉子进程。为了避免把无关的可继承句柄也带过去，可以用 STARTUPINFOEX + PROC_THREAD_ATTRIBUTE_HANDLE_LIST 精确指定要继承的句柄列表。

    9.6 为什么 Windows 没有 fork

    Windows NT 的设计受 VMS 影响，一开始就采用"创建进程时指定程序"的模型。fork 的语义（复制整个进程状态）与 Windows 的很多机制不容易兼容：大量内核对象句柄、GUI 资源、多线程（fork 只复制调用线程的问题）、DLL 的初始化状态。NT 内核其实支持类似 fork 的能力（早期 POSIX 子系统和 WSL1 都依赖它实现了 fork，通过内部的克隆进程接口），但 Win32 API 从未公开。

    🔬 深入：学术界对 fork 的反思

    2019 年 HotOS 会议上，微软研究院和波士顿大学的研究者发表论文 A fork() in the road，认为 fork 已经不适合现代操作系统：它与多线程不兼容；默认继承所有资源，带来安全隐患；写时复制需要过量提交内存；为了一个 exec 先复制整个地址空间的页表，在大内存进程上很慢。论文建议用 posix_spawn 这类"一步创建"的接口替代 fork + exec。这和 Windows CreateProcess 的设计理念一致。不过 fork 在"复制当前进程状态"的场景中仍然很有价值（如 Redis 快照、Android Zygote 预加载后 fork 出应用进程）。

    10.2 选型的六个维度

    维度倾向多进程倾向多线程
    故障隔离某个模块可能崩溃（第三方插件、不可信输入解析、渲染不可控网页），不能连累主程序所有代码可控、质量统一
    安全隔离需要沙箱，限制某部分代码的权限（浏览器渲染进程）同一信任域
    数据共享各单元基本独立，偶尔通信频繁共享大量数据（游戏世界状态、内存缓存、大型矩阵）
    创建 / 切换频率长期运行、数量少需要频繁创建和切换的轻量任务
    扩展方式未来要扩展到多台机器（进程间本来就用消息通信，换成网络更容易）单机多核
    语言 / 运行时限制CPython 有 GIL，CPU 密集任务只能用多进程并行（3.13 起有实验性的无 GIL 构建）C++ / Java / Go / Rust 线程可以真正并行
    ✅ 一句话原则

    默认用多线程（共享方便、开销小）；当"隔离"带来的价值超过"共享"带来的便利时，用多进程。真实系统几乎都是混合使用：多进程负责隔离和扩展，每个进程内部用多线程利用多核，再在线程上用事件循环或协程处理大量 I/O。

    10.3 案例一：Chrome 为什么是多进程

    • 稳定性：网页内容不可控，渲染引擎和 JS 引擎极其复杂。一个页面崩溃只显示"喔唷，崩溃啦"，不影响其他标签页。这正是第 3.7 节"崩溃半径"的应用。
    • 安全：渲染进程运行在沙箱中，没有文件系统和网络的直接访问权限。即使 V8 被攻破，攻击者还需要另一个漏洞才能逃出沙箱。2018 年 Spectre 漏洞让"同一地址空间内的数据可能被推测执行读到"成为现实，Chrome 因此全面启用了站点隔离，让不同站点一定运行在不同进程中。这也说明：同进程内不存在真正的隔离（呼应第 11 章自测题 2）。
    • 代价：内存占用大（每个进程都有自己的 V8 堆、Blink 数据），所以 Chrome 在内存紧张时会让同站点的标签共享进程。

    10.4 案例二：Nginx 的 master-worker 多进程

    • master 进程：读配置、绑定端口、管理 worker，不处理请求。
    • worker 进程：数量通常等于 CPU 核数，每个 worker 是单线程 + epoll 事件循环，一个 worker 能同时处理上万个连接（并发不并行）。多个 worker 在多核上并行。
    • 为什么用多进程而不是多线程：worker 之间几乎不需要共享数据（每个连接独立处理），多进程带来了隔离：一个 worker 因第三方模块的 bug 崩溃，master 会立即拉起新的 worker。热重载也很自然：nginx -s reload 时 master 用新配置启动新 worker，旧 worker 处理完手上的连接后退出，服务不中断。
    • 补充：读磁盘文件可能阻塞事件循环，所以 Nginx 1.7.11 起提供了线程池（aio threads）专门处理阻塞的文件 I/O，又是一个混合使用的例子。

    10.6 案例四：游戏引擎与游戏服务器

    🎮 游戏客户端：多线程为主

    游戏世界状态（Actor、组件、物理、动画数据）在每一帧都要被逻辑、物理、动画、渲染频繁访问，共享量极大且对延迟敏感，跨进程通信无法承受，所以客户端以多线程为主。以 UE 为例：GameThread 执行游戏逻辑；RenderThread 把场景转换成渲染命令；RHIThread 把命令提交给图形 API；还有TaskGraph 工作线程执行动画、物理、粒子等并行任务，以及音频线程、异步加载线程。帧与帧之间通过流水线让 GameThread 和 RenderThread 并行。

    但也有例外：Shader 编译交给独立的 ShaderCompileWorker 进程。Shader 编译器是第三方的、可能崩溃，并且每个编译任务相互独立、几乎不共享数据，符合"隔离价值大于共享便利"的条件。编辑器侧还能用 Job 机制管理这些子进程的生命周期。

    🎮 游戏服务器：多进程为骨架

    大型在线游戏的服务端通常按功能或按房间拆成多个进程：网关、登录、匹配、战斗、聊天、存储代理等。对于 MOBA / 竞技类游戏，一场对局往往运行在战斗服务器进程（或进程中的一个独立房间）里。拆成多进程的理由是：故障隔离（一场对局出错不影响其他对局）、横向扩展（进程间本来就通过消息通信，部署到更多机器上很自然）、独立发布。进程内部则常见"单逻辑线程 + 若干网络 I/O 线程"的结构：逻辑单线程避免了复杂的锁，也让帧同步 / 状态同步的确定性更容易保证。

    10.7 面试答法模板

    ✅ "什么时候选多进程，什么时候选多线程？"
    1. 先说本质区别：进程隔离资源，线程共享资源。这一点决定了两者的所有优缺点。
    2. 多线程适合：需要频繁共享大量数据、对通信延迟敏感、需要频繁创建和切换执行单元的场景，例如游戏客户端、内存缓存、并行计算。代价是需要同步，而且一个线程出错可能让整个进程崩溃。
    3. 多进程适合：需要故障隔离或安全隔离、各单元相对独立、需要分布到多台机器、或者语言运行时限制了多线程并行的场景，例如浏览器、Nginx worker、Shader 编译、Python 的 CPU 密集任务。代价是创建和切换开销大、通信要走 IPC。
    4. 最后说混合：真实系统通常是多进程 + 多线程 + 事件循环 / 协程分层组合。举一个自己熟悉的例子，比如 Chrome 或 Nginx。
    本章小结
    • 实测：进程创建比线程贵 1～3 个数量级（受安全软件影响可能更大），跨进程切换约为线程切换的 2 倍。
    • 选型看六个维度：故障隔离、安全隔离、数据共享、创建切换频率、扩展方式、语言限制。
    • Chrome、Nginx、PostgreSQL 选多进程是为了隔离；游戏客户端、MySQL 选多线程是为了共享；真实系统几乎都是混合的。
    CHAPTER 11

    重点自测与面试题库

    先自己作答，再展开参考答案。两道重点题给出完整的答题结构。

    11.1 重点题一：进程与线程有什么区别？

    参考答案（按"定义 → 资源 → 开销 → 通信 → 健壮性 → 选型"组织）
    1. 定义：进程是资源分配和保护的基本单位；线程是 CPU 调度的基本单位。一个进程至少有一个线程，线程属于且只属于一个进程。
    2. 资源：进程拥有独立的虚拟地址空间、句柄 / 文件描述符表、安全凭据等；同一进程的线程共享这些资源，但各自维护寄存器上下文、栈、TLS、线程 ID 和调度状态。（可以引用 Microsoft Learn 的说法：同一进程内的线程共享虚拟地址空间和系统资源，但各自具有寄存器上下文、线程局部存储和栈等状态。）
    3. 开销：创建进程要建立地址空间和资源表，比创建线程贵 1～3 个数量级；切换进程要切换页表，导致 TLB 和缓存失效，比线程切换贵。（可以举自己实测的数据：同核切换线程 0.68μs、进程 1.50μs。）
    4. 通信：线程直接读写共享内存，但需要锁、原子操作等同步；进程间要通过管道、共享内存、socket 等 IPC。
    5. 健壮性：进程之间由 MMU 和独立页表强制隔离，一个进程崩溃不影响其他进程；线程共享地址空间，一个线程的非法访问会导致整个进程终止。
    6. 补充（加分）：Linux 内核里两者都是 task_struct，区别只在 clone 时共享哪些资源；Windows 内核中进程对象和线程对象是分开的，进程只是容器。
    追问：什么时候选多进程，什么时候选多线程？

    见 10.7 节的答题模板：需要共享、追求效率选多线程；需要隔离、追求稳定和安全选多进程；实际系统多为混合。结合 Chrome（隔离）、游戏客户端（共享）各举一例。

    11.2 重点题二：线程有自己的栈，是否意味着其他线程不能通过指针访问其中的数据？

    结论：不是。其他线程完全可以通过指针读写另一个线程栈上的数据。
    1. "栈私有"的真实含义：每个线程分配到一块专用的地址区间来保存自己的调用链，编译器生成的代码只通过本线程的栈指针访问它。这是分配上和约定上的私有，不是访问权限上的私有。
    2. 为什么能访问：线程的用户栈位于所属进程的虚拟地址空间中（Microsoft Learn 原文：线程上下文包括"a user stack in the address space of the thread's process"），而同一进程的所有线程共用一套页表。MMU 只检查页面是否映射、是否可写，不区分是哪个线程在访问。
    3. 实测证明：d2_stack_ptr 中，线程 A 把栈上数组 buf 的地址交给线程 B；B 自己的栈范围是 [...2121A00000, ...2121B00000)，指针 ...21219FF7F0 落在 A 的栈范围内，B 把数组每个元素乘以 100，A 随后读到 {100, 200, 300, 400}。
    4. 真正的风险：
      • 生命周期：栈上数据随函数返回而失效。如果 A 的函数已经返回、或者 A 线程已经退出，B 再访问就是悬垂指针，读到垃圾或者写坏 A 后续的栈帧，且极难复现。
      • 数据竞争：A、B 同时读写时，和共享全局变量一样需要同步。
    5. 正确用法：保证栈帧的生命周期覆盖所有使用者，例如在同一作用域内 join（或使用 std::jthread）、同步等待任务完成；否则就把数据放到堆上，用 shared_ptr 管理，或按值传递。
    6. 对比（加分）：不同进程之间才有硬件强制的隔离，另一个进程拿着同样的地址值也访问不到。即便如此，有权限的进程仍可以通过内核提供的接口（Windows 的 ReadProcessMemory/WriteProcessMemory，Linux 的 ptrace、process_vm_readv、/proc/<pid>/mem）访问其他进程的内存，调试器就是这么工作的，但这需要经过内核和权限检查。同理，thread_local 变量也只是"每线程一份副本"，取地址交给别的线程照样能访问。

    11.3 更多自测题

    1. 线程共享进程的哪些资源？各自独有哪些？

    共享：代码段、全局与静态变量、堆、内存映射、文件描述符 / 句柄表、当前目录、用户凭据、信号处理方式、PID。独有：线程 ID、寄存器（PC/SP 等）、用户栈与内核栈、TLS（包括 errno）、调度优先级与状态、信号屏蔽字、异常处理链。判断规则：记录"执行到哪里"的必须独有。

    2. 一个线程崩溃会导致整个进程崩溃吗？为什么？有没有例外？

    通常会。线程共享地址空间，出错的线程可能已经破坏了共享数据或持有锁，系统无法判断其余线程的状态是否可信，因此默认终止整个进程（Linux SIGSEGV 发给整个线程组；Windows 未处理异常终止进程）。d3 实测：工作线程空指针访问后，整个子进程以 0xC0000005 退出。例外：可以通过 SEH（__try/__except）或注册 SIGSEGV 处理函数"接住"异常，Java/JVM 会把某些空指针访问转换为 NullPointerException，但这通常只用于特定场景，不能作为一般的容错手段。

    3. 就绪和阻塞有什么区别？为什么阻塞不能直接变为运行？

    就绪是"除了 CPU，什么都有了"；阻塞是"在等某个事件，给它 CPU 也运行不了"。事件发生后，任务只是具备了运行条件，CPU 可能正被别人使用，必须进入就绪队列由调度器统一分配。

    4. 进程切换为什么比线程切换慢？

    两者都要保存和恢复寄存器、切换内核栈。进程切换还要切换页表（写 CR3），导致 TLB 失效（PCID 可以缓解）；而且新进程的代码和数据不在缓存中，缓存命中率下降。间接开销往往比直接开销更大。

    5. 什么是僵尸进程？如何避免？kill -9 能杀死僵尸吗？

    子进程已退出，父进程尚未调用 wait，内核保留其 PID 与退出状态，即为僵尸。避免：父进程 wait；处理 SIGCHLD 并循环 waitpid(-1, NULL, WNOHANG)；设置 SIGCHLD 为 SIG_IGN；两次 fork。kill -9 无效，因为它已经死了；只能让父进程回收，或杀死父进程让 init 接管回收。

    6. fork 之后父子进程共享文件偏移吗？

    共享。fork 复制的是 fd 表，但两个 fd 指向内核中同一个"打开文件表项"，偏移量和状态标志就记录在那里。所以父子进程交替 write 同一个 fd，内容会接在一起，不会互相覆盖。如果父子进程各自 open 同一个文件，则是两个独立的表项，偏移量不共享。

    7. 多线程程序中调用 fork 有什么风险？

    fork 只复制调用线程。其他线程持有的锁（包括 malloc、stdio 内部锁）在子进程中永远处于锁定状态，子进程调用相关函数会死锁。POSIX 要求子进程在 exec 之前只调用异步信号安全的函数。建议 fork 后立即 exec，或使用 posix_spawn。

    8. exec 之后，原来打开的文件还在吗？信号处理函数呢？

    未设置 FD_CLOEXEC 的 fd 仍然打开；PID 不变。自定义的信号处理函数被重置为默认（因为函数地址在新映像中已无意义），被设为忽略的信号保持忽略。

    9. 用户级线程和内核级线程的区别？M:N 模型解决了什么问题？

    根本区别是内核是否可见。用户级线程切换快、可定制调度，但不能用多核、一个阻塞全部阻塞（d6 实测 Fiber 阻塞 307ms）。M:N 用多个内核线程承载用户线程以利用多核，并通过把阻塞 I/O 转为非阻塞 + 事件通知、在阻塞系统调用时移交处理器等手段解决阻塞问题，代价是运行时复杂。Go、Java 21 虚拟线程是代表。

    10. 协程和线程有什么区别？有栈协程和无栈协程呢？

    线程由内核抢占式调度，切换要进内核，有独立的 MB 级栈；协程由用户态协作式调度，在明确的挂起点切换，开销是函数调用级别。有栈协程有独立栈，可以在调用链任意深度挂起；无栈协程由编译器改写成状态机，帧放在堆上，只能在协程函数本身挂起，C++20 协程属于后者。

    11. errno 是全局变量，多线程下为什么不会互相干扰？

    现代 C 库把 errno 定义为宏，展开后是对一个线程局部变量的访问（glibc：(*__errno_location())），每个线程一份。Windows 的 GetLastError 值保存在每线程的 TEB 中。

    12. 线程栈默认多大？如何避免栈溢出？

    Windows 默认保留 1MB（链接器 /STACK 或创建线程时指定），d1 实测每线程 1024KB；Linux 主线程由 ulimit -s 决定（常见 8MB），glibc 线程默认也是 8MB。避免：不要在栈上放大数组，改用堆或 std::vector；控制递归深度或改为迭代；必要时为工作线程指定更大的栈。

    13. 下面代码有什么问题？void f(){ int x = 0; std::thread t([&]{ x++; }); t.detach(); }

    线程按引用捕获了 f 栈上的 x，然后被 detach。f 返回后 x 的栈帧失效，工作线程如果还没执行或正在执行 x++，就会写入已经失效的栈内存，属于未定义行为，可能悄悄破坏调用 f 之后的其他函数的局部变量。这正是"其他线程可以通过指针访问栈"带来的生命周期问题。修复：按值捕获，或 join，或使用 std::jthread。

    14. Windows 上父进程退出，子进程会怎样？如何让子进程跟随父进程退出？

    不受影响，继续运行；Windows 没有强制的进程树，也没有过继机制。要让子进程跟随退出，把它放进设置了 JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE 的 Job 对象中，父进程（持有 Job 的最后一个句柄）退出或崩溃时，Job 内的所有进程都会被终止。

    15. 单核 CPU 上多线程有意义吗？

    对 I/O 密集任务有意义：一个线程等待 I/O 时，CPU 可以运行其他线程，提高利用率和响应性（例如 UI 线程不被后台任务卡住）。对纯 CPU 密集任务没有加速作用，反而增加切换开销。

    16. volatile 能保证多线程下 counter++ 正确吗？

    在 C++ 中不能。volatile 只保证每次访问都真正读写内存、不被编译器优化掉，不提供原子性，也不提供跨线程的顺序保证。d5 实测：volatile 变量 4 线程各加 100 万次，结果只有 118 万～339 万。应使用 std::atomic 或互斥锁。

    附录 · 考前速记卡

    面试前 10 分钟过一遍。

    ① 三者关系

    程序 = 静态文件；进程 = 资源容器（分配与保护单位）；线程 = 执行流（调度单位）。1 个程序 → N 个进程；1 个进程 → ≥1 个线程。

    ② 并发 vs 并行

    并发 = 结构上重叠推进（单核也行）；并行 = 物理上同时执行（需多核）。Amdahl：上限 1/(1−p)。

    ③ 共享

    地址空间（代码、全局、堆、映射、各线程栈所在区域）、fd / 句柄表、凭据、cwd、信号处置、PID。

    ④ 独立

    TID、寄存器（PC/SP）、用户栈 + 内核栈、TLS（errno）、调度状态 / 优先级、信号屏蔽字、SEH 链。

    ⑤ 栈私有 ≠ 不可访问

    同一地址空间 + 同一套页表 → 拿到指针就能读写。风险在生命周期和数据竞争。进程间才有硬件隔离。

    ⑥ 五状态

    新建 → 就绪 ⇄ 运行 → 终止；运行 → 阻塞 → 就绪。没有阻塞 → 运行、就绪 → 阻塞。就绪差 CPU，阻塞差事件。

    ⑦ Linux 状态

    R（就绪 + 运行）、S（可中断睡眠）、D（不可中断，kill -9 无效）、T（停止）、Z（僵尸）。load = R + D。

    ⑧ 上下文切换

    保存/恢复寄存器、换内核栈和 TLS 基址；跨进程还要换页表 → TLB/缓存失效。实测 0.68μs vs 1.50μs。

    ⑨ PCB / TCB

    PCB：标识、内存、资源、家族、统计。TCB：上下文、调度信息、栈。Linux task_struct 用 mm/files 指针表达共享。

    ⑩ ULT / KLT

    关键：内核是否可见。ULT 快但不能多核、一阻塞全阻塞；KLT 反之。1:1（Linux/Windows）、N:1（Fiber）、M:N（Go/虚拟线程）。

    ⑪ 协程 / 任务

    协程：用户态、协作式、可挂起的函数；有栈（Fiber、goroutine）vs 无栈（C++20，状态机 + 堆帧）。任务：工作单元抽象，跑在线程池或协程上。

    ⑫ fork

    返回两次（子 0，父 子PID）；COW；fd 表复制但共享偏移；只复制调用线程；fork 前 fflush。

    ⑬ exec / wait

    exec 换映像保 PID 和非 CLOEXEC 的 fd，handler 重置，成功不返回。wait 取退出码并释放 task_struct。

    ⑭ 僵尸 / 孤儿

    僵尸：子死父未收，占 PID，kill 不掉 → wait / SIGCHLD 循环 / SIG_IGN / 两次 fork。孤儿：父先死 → init/subreaper 收养，无害。

    ⑮ Windows

    CreateProcess 一步建新进程；CREATE_SUSPENDED 先设置后运行；句柄引用计数，忘关 = 泄漏；无进程树，用 Job 管理；句柄默认不继承。

    ⑯ 选型

    默认多线程（共享、高效）；隔离价值更大时多进程（稳定、安全、扩展、GIL）。真实系统 = 多进程 × 多线程 × 事件循环/协程。
