CHAPTER 03

进程拥有什么，线程共享什么，线程独占什么

共享的是资源，独立的是执行状态。但"独立"在很多时候只是约定，而不是硬件保护。

本章目标
  • 完整列出进程级资源和线程级状态，并说明每一项为什么放在那一侧
  • 用实测输出证明：全局变量和堆是共享的，栈和 TLS 是每线程一份
  • 理解"栈私有"不等于"别人访问不到"，以及由此带来的风险
  • 理解崩溃半径：为什么一个线程崩溃会让整个进程退出

3.1 一张图看清边界

判断规则：为什么这么划分

不需要死记表格，用一条规则推导即可：

✅ 推导规则

如果两条执行流同时使用某样东西而不冲突，它就可以共享；如果它记录的是"这条执行流自己执行到哪里了"，它就必须独立。

  • PC 和寄存器：两个线程执行到不同的指令，算着不同的中间值，只能各有一份。
  • 栈：栈保存函数调用链（返回地址、局部变量）。T1 在 main → load → parse，T2 在 main → render，两条调用链不同，用同一个栈会互相覆盖。
  • errno：T1 的 open 失败设置了 errno，T2 的 read 成功不能把它清零。所以现代 C 库把 errno 实现为线程局部变量（glibc 中是宏 (*__errno_location())）。Windows 的 GetLastError() 值存放在 TEB 中，同样是每线程一份。
  • 文件表：T1 打开的文件交给 T2 读取，是很常见的需求。共享是合理的。

Microsoft Learn 的官方表述

Windows 文档About Processes and Threads 对这个边界有一段很精确的描述，这里转述其要点：

  • 进程提供执行程序所需的资源：虚拟地址空间、可执行代码、指向系统对象的打开句柄、安全上下文、唯一的进程标识符、环境变量、优先级类、最小和最大工作集大小，以及至少一个执行线程。
  • 线程是进程中可以被调度执行的实体。一个进程的所有线程共享其虚拟地址空间和系统资源。此外，每个线程维护异常处理程序、调度优先级、线程局部存储、唯一的线程标识符，以及系统用来保存线程上下文的一组结构，直到线程被调度。
  • 线程上下文包括线程的机器寄存器集合、内核栈、线程环境块（TEB），以及位于所属进程地址空间中的用户栈。

最后一句值得仔细读：用户栈"位于所属进程的地址空间中"。这正是 3.4 节要讨论的问题的答案。另外请注意，每个线程实际上有两个栈：用户态执行时用用户栈，陷入内核（系统调用、中断）后用内核栈。内核栈位于内核地址空间，用户代码无法访问。

3.3 实测：谁共享，谁独立

d1_share.cpp 中，主线程 new 了一个 int，把指针交给 3 个工作线程。每个线程打印：全局变量地址、堆指针、自己栈上局部变量的地址、thread_local 变量的地址，以及用 GetCurrentThreadStackLimits 查到的本线程栈范围。

int g_global = 100; // 数据段：全进程共享 thread_local int t_tls = 0; // 线程局部存储：每个线程一份 void worker(int id, int* heapPtr) { int local = id * 10; // 栈：每个线程自己的栈 t_tls = id; // 只改到“自己那一份” ULONG_PTR lo = 0, hi = 0; GetCurrentThreadStackLimits(&lo, &hi); // 本线程栈的地址范围 printf("[T%d tid=%5lu] &g_global=%p heap=%p &local=%p &t_tls=%p(t_tls=%d)\n" ...); }
d1_share.exe —— 实测输出（Windows 11 x64，MSVC 14.44 /O2）
pid=69704  main tid=23692
[T3 tid=67952] &g_global=00007FF643858000  heap=0000018132781990  &local=0000000420DFFC20  &t_tls=00000181327B0394(t_tls=3)
              stack=[0000000420D00000, 0000000420E00000)  size=1024 KB
[T2 tid=76768] &g_global=00007FF643858000  heap=0000018132781990  &local=0000000420CFF8E0  &t_tls=00000181327C82F4(t_tls=2)
              stack=[0000000420C00000, 0000000420D00000)  size=1024 KB
[T1 tid= 6292] &g_global=00007FF643858000  heap=0000018132781990  &local=0000000420BFFB40  &t_tls=00000181327926F4(t_tls=1)
              stack=[0000000420B00000, 0000000420C00000)  size=1024 KB
main: t_tls=0 (主线程自己的 TLS 未被子线程改动)

逐项解读：

  1. 全局变量和堆：三个线程地址完全相同（绿色）。它们访问的是同一块内存。
  2. 局部变量：三个线程地址各不相同，并且分别落在各自的栈范围内。T1 的栈是 [...420B00000, ...420C00000)，T2 紧挨着是 [...420C00000, ...420D00000)，T3 是 [...420D00000, ...420E00000)。三块栈在同一个地址空间里首尾相连，每块正好 1024 KB。
  3. thread_local：每线程一个不同的地址，值也各不相同。主线程最后打印 t_tls=0，说明子线程写的是它们自己的副本。
  4. 线程是乱序完成的（T3 先打印）。线程的执行顺序由调度器决定，不能依赖创建顺序。
🔬 深入：栈多大？TLS 在哪？
  • Windows：线程栈默认保留 1MB 虚拟地址（由链接选项 /STACK 或 CreateThread 参数决定），但只提交很少的几页，栈顶下方有一个保护页（guard page），访问到它时触发异常，系统再提交下一页并把保护页下移。用完 1MB 就会抛出 STATUS_STACK_OVERFLOW。上面输出的 size=1024 KB 就是保留大小。
  • Linux：主线程栈大小由 ulimit -s 决定（通常 8MB），可动态向下增长；glibc 创建的线程栈默认也取这个值（8MB），用 mmap 分配，并在底部放一个不可访问的保护区。可用 pthread_attr_setstacksize 调整。
  • TLS 的实现：x86-64 上，Linux 用 FS 段寄存器指向当前线程的 TCB（其中有 TLS 块），Windows 用 GS 段寄存器指向当前线程的 TEB。线程切换时内核会切换这个寄存器的基址，所以同一条指令 mov eax, fs:[offset] 在不同线程里读到不同的变量。上面输出中 TLS 的地址落在堆附近的区域（0x0000018...），因为 MSVC 的 thread_local 块是为每个线程动态分配的。

3.4 栈私有 ≠ 别人访问不到

这是本章的重点问题。线程有自己的栈，指的是每个线程有一块专门给自己用的内存区域来保存调用链。但这块区域在进程的地址空间里，而同一进程的所有线程用的是同一套页表。MMU 只检查"这一页在当前页表里是否映射、是否可写"，它不知道也不关心当前是哪个线程在访问。

所以只要线程 B 拿到了指向线程 A 栈上数据的指针，它就可以读写那块数据。d2_stack_ptr.cpp 验证了这一点：

std::thread A([&] { int buf[4] = {1, 2, 3, 4}; // 位于 A 线程的栈上 shared = buf; // 把栈地址交给别的线程 ready.count_down(); modified.wait(); // 等 B 改完（A 的栈帧此时仍然存活） printf("[A] 被 B 改写后的 buf = {%d, %d, %d, %d}\n", buf[0], buf[1], buf[2], buf[3]); }); std::thread B([&] { ready.wait(); for (int i = 0; i < 4; ++i) shared[i] *= 100; // 跨线程直接写别人的栈 });
d2_stack_ptr.exe —— 实测输出
[A] buf=00000021219FF7F0  A的栈范围=[0000002121900000, 0000002121A00000)
[B] 我的栈范围=[0000002121A00000, 0000002121B00000)，但我拿着指针 00000021219FF7F0
[B] 写入成功：同一进程 = 同一地址空间，硬件不拦截
[A] 被 B 改写后的 buf = {100, 200, 300, 400}
结论：栈“私有”只是约定（每个线程各用各的区域），不是硬件隔离。

B 的栈范围是 [...2121A00000, ...2121B00000)，它手里的指针 ...21219FF7F0 明显落在 A 的栈范围内，写入照样成功。

那为什么还说栈是私有的？三层含义

  1. 空间上私有：每个线程分到一段专属的地址区间，编译器生成的 push/call/局部变量访问只会使用自己的 SP 指向的区域，正常情况下不会碰到别人的栈。
  2. 生命周期私有：栈上对象的生命周期由拥有它的线程的函数调用决定。函数返回，栈帧就失效；线程退出，整块栈都会被释放。其他线程无权也无法延长它的寿命。
  3. 默认不共享：如果没有人主动把栈地址交出去，别的线程就没有办法找到它（没有名字，地址也不固定）。

所以，跨线程访问栈上数据在语法和硬件上都是允许的，难点在生命周期：

⚠️ 易错点：悬垂的栈指针（最常见的真实 Bug） void StartLoad(ThreadPool& pool) { char path[260] = "data/level1.pak"; pool.Submit([&path] { // 按引用捕获了栈上的数组 LoadFile(path); // 工作线程执行时，StartLoad 很可能已经返回 }); } // ← path 所在栈帧在这里失效，之后这块内存会被下一次函数调用覆盖

这种 Bug 很难复现：工作线程启动得快时程序正常，慢一点就读到垃圾数据，Debug 和 Release 表现还不一样。修复方法是让数据的生命周期覆盖所有使用者：按值捕获（[path = std::string(path)]），或者放到堆上用 std::shared_ptr 管理，或者保证在栈帧返回前 join/等待任务完成（d2 就是用 latch 保证了 A 的栈帧在 B 写完之前一直存活）。

✅ 合法而常见的跨线程访问栈的用法
  • std::thread + 引用传参 + 在同一作用域 join：主线程栈上的数组交给工作线程处理，处理完 join，生命周期是安全的。std::jthread 在析构时自动 join，更不容易出错。
  • 同步调用：线程 A 把栈上的请求结构体地址放入队列，然后阻塞等待工作线程处理完成，再继续执行。很多 RPC 框架和 Windows 的 SendMessage 都采用这种模式。
  • OpenMP / parallel_for：并行循环访问外层函数的局部数组，因为外层函数会等所有迭代结束才返回。
🔬 深入：栈溢出会写坏别人的栈吗

d1 的输出显示，各线程的栈在地址上首尾相连。理论上，T2 的栈向下溢出就会进入 T1 栈的高地址部分。实际上中间隔着保护页：Windows 的 guard page 和 Linux 的 guard area 都不可访问，溢出时会先触发异常（Windows STATUS_STACK_OVERFLOW，Linux SIGSEGV），程序直接崩溃。但如果在栈上开了一个比保护页还大的局部数组（例如 char buf[64*1024]）并且从远端开始写，就可能跳过保护页直接写到相邻区域。因此编译器会在大栈帧函数中插入栈探测（MSVC 的 __chkstk，GCC 的 -fstack-clash-protection），按页依次触碰，确保一定会碰到保护页。

3.5 共享的代价：数据竞争

共享地址空间让线程间通信几乎零成本，代价是：多个线程同时读写同一块内存，且至少有一个是写，又没有同步，就构成数据竞争。在 C++ 标准中，数据竞争是未定义行为。

最经典的例子是 counter++。它看起来是一条语句，实际是三步：从内存读到寄存器 → 寄存器加 1 → 写回内存。两个线程交错执行就会丢失更新：

d5_race.exe —— 4 线程各自增 100 万次，实测输出
普通变量 ++ (round) 结果=  1180103  期望=4000000  耗时=   9.2 ms
普通变量 ++ (round) 结果=  3390547  期望=4000000  耗时=   2.8 ms
普通变量 ++ (round) 结果=  1737623  期望=4000000  耗时=   1.7 ms
std::atomic fetch_add  结果=  4000000  期望=4000000  耗时=  21.5 ms
std::mutex 加锁      结果=  4000000  期望=4000000  耗时=  78.1 ms

三点观察：

  1. 普通变量每次结果都不一样，最少的一次只有期望值的 30%。结果不确定正是数据竞争的特征。
  2. 代码中的 volatile 只是阻止编译器把循环优化成一条加法，它不提供原子性。这是 C++ 面试的常见陷阱（Java 的 volatile 语义不同，有可见性和有序性保证，但同样不保证复合操作的原子性）。
  3. 正确的版本更慢：atomic 慢约 2～10 倍，mutex 更慢。原因是多个核争抢同一条缓存行，每次写都要通过缓存一致性协议使其他核的副本失效。共享可写数据本身就有成本，所以高性能设计会尽量让每个线程写自己的数据（例如每线程一个局部计数器，最后汇总）。

3.6 进程之间：硬件强制的隔离

d3_isolation.cpp 用 CreateProcess 启动自身的另一个实例作为子进程，比较两边的全局变量：

d3_isolation.exe —— 实测输出（第一部分）
[parent pid=66436] &g_value=00007FF79F558000  g_value=1
  [child pid=75908] &g_value=00007FF79F558000  改成 999
[parent] 子进程退出码=7，父进程 g_value 仍然=1

两个进程中 g_value 的虚拟地址完全相同，子进程改成 999，父进程仍然是 1。同一个虚拟地址，在两套页表中映射到不同的物理页。这就是图 3-2 右半部分。

3.7 崩溃半径：线程崩溃，整个进程陪葬

共享地址空间的另一面是故障也共享。d3_isolation 的后两个实验：

d3_isolation.exe —— 实测输出（第二、三部分）
[parent] 子进程空指针崩溃，退出码=0xC0000005 (STATUS_ACCESS_VIOLATION)，父进程安然无恙

  [threadcrash] 主线程仍在工作 0
  [threadcrash] 主线程仍在工作 1
  [threadcrash] 主线程仍在工作 2
[parent] 子进程的“某个工作线程”崩溃 → 整个子进程被终止，退出码=0xC0000005
  • 子进程崩溃，父进程不受影响：进程边界把故障挡在了外面。
  • 在 threadcrash 模式下，子进程的主线程一直在正常打印，100ms 后一个工作线程解引用空指针，整个子进程（包括正常工作的主线程）立刻被终止。

为什么不能只杀掉出错的那个线程？

因为没有办法知道它破坏了什么。出错的线程可能已经写坏了堆上的数据结构，也可能正持有一把锁（如果只杀掉它，这把锁永远不会被释放，其他线程等这把锁时会死锁），还可能正在修改一个被所有线程共享的全局状态，修改到一半。由于地址空间是共享的，这些破坏对所有线程都可见，继续运行的结果不可预测。所以操作系统的默认策略是终止整个进程：

  • Linux：SIGSEGV 是发给线程组（整个进程）的致命信号，默认动作是终止整个进程并生成 core dump。
  • Windows：未处理的结构化异常最终交给系统的未处理异常过滤器，默认调用 WER（错误报告）并终止进程。
🎮 游戏开发视角

这就是为什么游戏客户端里一个线程（比如音频线程、资源加载线程）的空指针，会让整个游戏闪退，并在崩溃报告里看到崩溃线程不是 GameThread。也是为什么 Chrome、VS Code、Unreal Editor 的部分功能（Shader 编译、插件宿主、渲染进程）被拆到独立进程：它们崩溃时，主进程可以显示"页面崩溃，点击重新加载"或重启子进程，而不是整体退出。UE 的 ShaderCompileWorker.exe 就是一个例子。

本章小结
  • 进程共享：地址空间（代码、全局变量、堆、映射、以及所有线程的栈所在的区域）、句柄 / fd 表、凭据、工作目录、信号处置方式。
  • 线程独立：TID、寄存器上下文（PC/SP）、用户栈与内核栈、TLS（errno）、调度状态与优先级、信号屏蔽字 / 异常处理链。
  • 线程之间的"独立"是约定：栈和 TLS 只要拿到地址就能被别的线程访问，难点在生命周期。进程之间的隔离由 MMU + 独立页表强制执行。
  • 共享带来零成本通信，也带来数据竞争和"一个线程崩溃，整个进程退出"。
