CHAPTER 01

程序、进程、线程：从双击一个 exe 说起

程序是静态的文件，进程是资源的容器，线程是执行的流。

本章目标
  • 能准确说出程序、进程、线程的定义，以及"资源分配单位"和"调度单位"分别指谁
  • 说清楚为什么有了进程还要发明线程
  • 理解 Linux 内核眼中"进程和线程都是 task"的含义

1.1 双击 notepad.exe 之后发生了什么

磁盘上的 notepad.exe 只是一个文件。它按 PE 格式（Linux 上是 ELF 格式）存放了机器指令、只读常量、全局变量初值、需要导入的 DLL 列表和入口地址。这个文件就是程序（Program），它是静态的、被动的。你不运行它，它就只占一点磁盘空间。

双击之后，操作系统大致做了这几件事：

  1. 建立一个新的虚拟地址空间，并把 exe 文件映射进去：代码段只读可执行，数据段可读写。
  2. 分配一张资源表：句柄表（Linux 上叫文件描述符表），以及安全令牌、当前目录、环境变量等。
  3. 创建第一个线程（主线程）：给它分配一块栈，把指令指针设到程序入口（经过加载器和 C 运行时初始化，最终调用到 main）。
  4. 把主线程放进就绪队列，等调度器选中它，它就开始在 CPU 上执行。

前两步建出来的"一个地址空间 + 一组资源"就是进程（Process）；第 3 步建出来的那条"沿着指令一步步往下执行的流"就是线程（Thread）。

🍳 一个类比：菜谱、厨房、厨师

程序 = 菜谱：写在纸上，本身不会做出菜。进程 = 一间开张的厨房：有自己的灶台、冰箱、食材（地址空间和资源），厨房和厨房之间有墙隔开。线程 = 厨房里的厨师：真正干活的是厨师，同一间厨房的厨师共用冰箱和灶台，但每人手上有自己的步骤进度（程序计数器）和自己的案板（栈）。

按这个类比，同一份菜谱可以同时开好几间厨房（同一个 exe 运行多次就是多个进程）；一间厨房至少要有一个厨师，否则就关门了（进程至少有一个线程）；厨师之间共用冰箱很方便，但两个人同时伸手拿同一块肉就会出问题（数据竞争）。

1.2 进程：资源分配与保护的基本单位

教科书定义：进程是程序的一次执行实例，是操作系统进行资源分配和保护的基本单位。这句话里有两个关键词：

资源容器

内存、文件、网络连接、设备等资源都以进程为单位申请和记账。进程退出时，操作系统会把它名下的资源一次性回收，即使程序员忘了 close 或 free。

保护域

每个进程有独立的虚拟地址空间。进程 A 里的地址 0x7FF6... 和进程 B 里的同一个地址，被各自的页表映射到不同的物理内存，所以 A 无法直接读写 B 的内存。这道墙由 MMU 硬件强制执行。

1.3 线程：CPU 调度的基本单位

线程是进程内的一条独立执行流，是 CPU 调度和分派的基本单位。CPU 只认识"从哪条指令开始执行、寄存器里是什么值、栈在哪"，这套状态就是一个线程。调度器做的事情，就是把某个线程的这套状态装进 CPU，让它跑一会儿，再换下一个。

为什么有了进程还要线程？

早期 Unix 只有进程，一个进程就是一条执行流。后来人们遇到了下面这些需求：

  1. 一个程序里有多件事要同时做：编辑器既要响应键盘，又要后台自动保存、做拼写检查。如果只有一条执行流，保存文件时界面就会卡住。
  2. 多核 CPU 出现了：单个进程只有一条执行流，最多只能用上一个核。
  3. 用多进程来做这些事太贵：每个进程有独立的地址空间，创建时要建页表、复制资源表；进程之间交换数据要走管道、共享内存等 IPC 机制，编程麻烦，开销也大。

于是人们把进程拆成两部分：资源的部分留在进程里，执行的部分抽出来成为线程。同一进程的多个线程共享资源，各自独立执行。这样多件事可以同时进行，能用上多个核，而且线程之间交换数据只需要读写同一块内存。

🔬 深入内核：Linux 眼里只有 task

Linux 内核里没有单独的"线程"数据结构，进程和线程都用 task_struct 表示，统称 task。区别只在于创建时用 clone() 传了哪些共享标志：

  • fork() ≈ clone(SIGCHLD)：什么都不共享（地址空间写时复制），得到一个新进程。
  • pthread_create() ≈ clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD | ...)：共享地址空间、文件表、信号处理，得到同一进程里的新线程。

所以在 Linux 上，每个线程都有自己的 ID（内核叫 pid，用户态叫 tid，用 gettid() 获取）。同一进程的所有线程组成一个线程组，组长的 ID 叫 tgid，用户态调用 getpid() 拿到的其实就是 tgid。ps -eLf 里的 LWP 列就是每个线程的 tid。

Windows 的做法相反：内核里有明确分开的进程对象（EPROCESS）和线程对象（ETHREAD），进程只是容器，本身不执行，最后一个线程退出时进程随之终止。

1.5 用工具亲眼看一看

# 看某进程有哪些线程：LWP 列就是线程 tid，NLWP 是线程数 $ ps -eLf | grep -E "PID|chrome" | head # 每个线程在 /proc//task/ 下有一个目录 $ ls /proc/$(pgrep -n chrome)/task # 树形查看父子关系（{} 包起来的是线程） $ pstree -p $(pgrep -n sshd)

Windows 上打开任务管理器的"详细信息"页，右键列标题勾选"线程"，就能看到每个进程的线程数。Chrome 会显示很多个 chrome.exe，因为它是多进程架构：浏览器主进程、每个站点的渲染进程、GPU 进程、网络服务进程各自独立。第 10 章会专门分析它为什么这样设计。

⚠️ 易错点
  • "进程在执行代码"：严格地说，执行代码的是线程。进程提供执行环境。
  • "线程没有资源"：线程不拥有系统资源（文件、内存映射归进程），但它有自己必需的执行状态：寄存器、栈、TLS 和内核里的 TCB。说"线程只拥有少量必不可少的资源"更准确。
  • "一个程序 = 一个进程"：一个程序可以运行出多个进程（开两个记事本），一个进程也可以通过 exec 换成运行另一个程序。
本章小结
  • 程序是静态文件；进程是"地址空间 + 资源"，负责资源分配和隔离；线程是执行流，负责被 CPU 调度。
  • 线程的出现，是为了把"执行"从"资源"里拆出来：多条执行流共享一套资源，既能并发又省开销。
  • Linux 内核统一用 task_struct，进程和线程的区别只是 clone 时共享了多少；Windows 内核中进程对象和线程对象是分开的。
自测：同一个 exe 双击两次，两个进程的全局变量 g_count 地址打印出来一样，它们是同一块内存吗？

不是。打印的是虚拟地址，两个进程各有一套页表，同一个虚拟地址会映射到不同的物理页。第 3 章的 d3_isolation 实测：父子进程 &g_value 都是 00007FF79F558000，子进程改成 999，父进程仍然是 1。（在 Windows 上，同一个 exe 的映像基址在一次开机内通常相同，所以地址恰好一样。）

CHAPTER 02

并发与并行

并发是一种结构，并行是一种执行方式。

本章目标
  • 用一句话区分并发和并行，并能举出"并发但不并行"和"并行但不并发"的例子
  • 理解单核上为什么也需要并发
  • 会用 Amdahl 定律估算多核加速比

2.1 定义

并发 Concurrency

多个任务在重叠的时间段内推进。宏观上同时进行，微观上可以交替执行。它描述的是程序的结构：程序被组织成多个可以独立推进的部分。

并行 Parallelism

多个任务在同一时刻真正同时执行，需要多个执行部件（多核、多 CPU、GPU 的众多核心）。它描述的是执行：物理上同时在算。

Go 语言作者之一 Rob Pike 的说法最常被引用："Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once." 并发是"同时应对很多事"，并行是"同时做很多事"。

2.2 四种组合

并发和并行是两个维度，不是非此即彼：

并行（多个执行部件同时算）不并行（同一时刻只有一个在算）
并发（多个独立推进的任务）多线程程序跑在多核上：Web 服务器 8 个工作线程处理请求单核分时系统；Node.js / Redis 主线程的事件循环；单线程上的协程调度
不并发（只有一个逻辑任务）SIMD 向量指令：一条指令同时算 8 个 float；GPU 对一个数组做同一操作普通的单线程顺序程序
🧪 实测证据：并发但不并行（d6_fiber_coro Part2）

2.3 单核上为什么也需要并发

如果只有一个核，并发不会让计算变快，因为总计算量不变，切换还有开销。并发的价值在于让等待和计算重叠。一次机械硬盘随机读要几毫秒，一次跨机房网络往返要几十毫秒，这段时间 CPU 足够执行上千万条指令。如果程序串行地"发请求 → 干等 → 处理"，CPU 大部分时间都在空转。并发的程序在一个任务等 I/O 时切换去执行别的任务，CPU 利用率和响应速度都会提高。

所以要区分两种负载：

  • I/O 密集型（Web 服务、网络代理、数据库连接）：瓶颈在等待，并发结构（多线程、事件循环、协程）收益很大，单核也有效。
  • CPU 密集型（视频编码、物理模拟、寻路、压缩）：瓶颈在计算，只有真正的并行（多核）才能加速。线程数超过核数后基本没有收益，反而增加切换开销。

2.4 并行的天花板：Amdahl 定律

假设程序中可以并行的部分占比为 p，用 n 个核，理论加速比为：

S(n) = 1 / ( (1 − p) + p / n )

可并行比例 p4 核16 核无穷多核（上限 1/(1−p)）
50%1.60×1.88×2×
90%3.08×6.40×10×

结论：串行部分决定上限。即使 90% 的代码完美并行，再多的核也最多快 10 倍。实际中串行部分不只是代码逻辑，还包括锁竞争、共享缓存行争用、内存带宽，所以实测加速比通常低于理论值。

🔬 深入：超线程算并行吗

Intel 的超线程（SMT）让一个物理核呈现为两个逻辑核，两个硬件线程共享同一套执行单元和 L1/L2 缓存，各自有独立的寄存器组。当一个线程因缓存未命中而停顿时，另一个线程可以用空闲的执行单元。所以它是"部分并行"：两个都在跑计算密集任务时，总吞吐通常只比单线程高 10%～30%，远达不到 2 倍。

🎮 游戏开发视角

UE 的 GameThread 和 RenderThread 是典型的流水线并行：第 N 帧在 RenderThread 上生成渲染命令时，GameThread 已经在计算第 N+1 帧的逻辑，两者在不同的核上同时运行。资源的异步加载则主要是并发：加载线程大部分时间在等磁盘 I/O，主线程不会因此卡住。分清这两者，才能判断优化方向：前者看 CPU 核心负载，后者看 I/O 等待。

本章小结
  • 并发是程序结构（多个任务重叠推进），并行是物理执行（同一时刻多个部件在算）。并发不一定并行，并行也不一定是并发。
  • 单核上的并发能让 I/O 等待与计算重叠；CPU 密集型任务只有并行能加速。
  • Amdahl 定律：加速比上限是 1/(1−p)，串行部分（包括锁竞争）决定天花板。
自测：Redis 6.0 之前的命令处理是单线程的，它是并发的吗？

是并发但不并行。Redis 用 epoll 事件循环在一个线程里同时服务成千上万个客户端连接，所有连接的请求交替推进，这就是并发。但同一时刻只有一条命令在执行，没有并行。Redis 6.0 引入的 I/O 线程只并行处理网络读写和协议解析，命令执行仍然在主线程中串行完成。
