CHAPTER 07

HOK 上行：命令冗余、技能保序与确认

下行丢了有服务器冗余广播兜底，上行丢了就是丢了——服务器不会替你补。所以上行要自己做冗余，而且要区分“丢一次无所谓”的移动和“丢了就是真丢了”的技能。

本章目标
  • 说清上行包里除了命令还带了什么（期待帧 ACK、命令序号），以及“只在战斗中才产生有效输入”的原因。
  • 对比两种冗余：短冗余（当前 + 前两条，约 33 ms 重发）与技能全量冗余（所有未确认技能，约 200 ms 重发、1 s 超时）。
  • 用实测回答：在随机丢包和突发丢包下，三种发送策略的送达率、延迟、带宽各是多少。
  • 掌握技能序号的三个边界、三重保护和确认规则，以及追帧后序号 +100 的处理。
30 秒面试版答案

上行包除了命令，还带期待帧号（兼作下行 ACK）和递增的命令序号。冗余分两种：大多数关键命令（普攻、学技能、买装备）用短冗余——每个包带“当前 + 前两条”，约 33 ms 重发一次，代价低，能挡住零散丢包；三个主动技能用全量冗余——只要有技能没被确认，每约 200 ms 就把所有未确认技能重发一遍，按序号保序。确认的方式是客户端在下行帧里看到自己的技能被执行；序号等于期望值正常出队，大于则说明中间有技能丢了，小于则是重复。另有三重保护：同槽位重复点击去重（蓄力技豁免）、1 秒超时丢弃、队满丢最老；追帧结束后序号加一个大偏移（如 +100）把迟到的旧指令隔离掉。下行卡顿时主动降低上行重发频率，把带宽让给补帧。

7.1 从手指到上行包

序列化分两种形态：简单命令（移动）直接填协议结构体字段，极省字节；复杂命令（多参数目标技能）先打包成二进制再塞进缓冲。一次发送通常会捎带若干条历史命令——这就是冗余。

7.2 两种冗余策略

对比项短冗余技能全量冗余
适用普攻、学技能、买卖装备、蓄力技、联合技等关键命令；普通移动不入队（下一条移动会覆盖它）三个主动技能（目标型 / 方向型 / 位置型）
队列3 槽环形缓冲协议上限（较大）
重发间隔约 33 ms约 200 ms
每次发送内容当前 + 前 2 条所有未确认的技能
次数限制每条最多捎带若干次直到确认，或 1 s 超时，或队满被挤掉
保序无有（技能序号）
开关常开服务器开局下发（关闭时技能走短冗余）

所有发包统一在帧末 flush：冗余重发定时到期 → 技能重发定时到期 → 待确认的可靠包超时重发 → 本帧新入队的普通消息。一个精巧的细节：下行正在卡顿时，主动降低上行重发频率——下行卡顿往往意味着拥塞，此时疯狂重发上行只会和补帧抢带宽 HOK 文档。

7.3 实测：三种策略谁更可靠、谁更省 实测 E7

模型：上行每 33 ms 一个发送时隙（帧末 flush），同一时隙的包同生共死；单程 30 ms + 指数抖动（均值 20 ms）；10 分钟内 [[e7.b5.0.n|.0f]] 个技能（30% 是 80 ms 内的连招）。“确认”定义为技能到达服务器后约 60 ms 客户端在下行帧里看到它。两种信道：随机丢包 5%；突发丢包 10%、平均连丢 8 个时隙（约 264 ms，模拟 Wi-Fi 信号衰减）。

从数据里读出的四个结论

  1. 冗余的价值取决于丢包形态：随机 5% 时短冗余已经 [[e7.b5.1.deliv|.1f]]%；突发丢包时同样 3 份只有 [[e7.g10.1.deliv|.1f]]%——和第 6 章下行冗余的结论完全一致：挨在一起的副本会一起死。
  2. 全量冗余反而更省：每个技能平均只发了 [[e7.b5.2.copies|.2f]] 份（随机）/ [[e7.g10.2.copies|.2f]] 份（突发），远少于短冗余的 3 份——因为它“确认了就停”，只有真丢了才重发。这是选择性重传对盲目重复的胜利。
  3. 代价是尾延迟：全量冗余的 p99 延迟是 [[e7.g10.2.p99|.0f]] ms（突发）——重发间隔 200 ms，丢了就要多等一轮。所以技能用全量冗余，而对延迟最敏感、丢一次无所谓的移动根本不入队。
  4. 序号消除了乱序：单发时出现了 [[e7.b5.0.inv|.0f]] 次“后按的技能先生效”（抖动大时连招的第二个包先到）；全量冗余的包内按序号排列，服务器按序号生效，颠倒次数为 0。
对照 Unreal：CMC 的 ServerMove 也是“带上旧的”

CharacterMovementComponent 的移动 RPC 是不可靠的，但客户端会把“重要的、尚未确认的旧移动”（例如带跳跃 / 加速度突变的那一步）一起打包发送（ServerMoveOld / 打包移动数据里的 OldMove），服务器用时间戳去重 UE 源码。思路与 HOK 短冗余一致：用不可靠通道 + 冗余换低延迟，而不是用可靠通道换队头阻塞。第 12 章 E14 会量化可靠 RPC 的队头阻塞。

7.4 技能保序：与帧号无关的技能序号

三重保护

保护规则为什么
入队前去重与上一条未确认技能同槽位 → 丢弃（视为重复点击）；蓄力技豁免（开始与结束本就同槽位）紧张时狂点同一个按钮会产生大量无效指令
超时丢弃入队超过 1 s 仍未确认 → 出队，计入“过期丢弃”永远确认不了的技能会被每个包反复携带，白占带宽；且 1 s 前的技能再生效也没有意义
队满丢弃未确认技能超过容量 → 丢最老的，计入“限长丢弃”保证上行包不因冗余内容过多而超限

确认与出队

打乱序号连续性的场景问题处理
断线追帧结束追帧期间发出的技能可能在追帧完成后才到服务器，“迟到生效”清空队列，序号加一个大偏移（如 +100），让迟到的旧指令被自然过滤
切换主控英雄不同英雄的技能独立，序号语义断裂清空队列，重新起算

两个处理是同一个思路：与其精细地修补序号，不如用一个足够大的跳变把历史隔离掉——TCP 用随机初始序号隔离旧连接的迟到报文，是同一类技巧。

面试注意

“上行丢包怎么办”是 HOK 帧同步的必问追问（下行有服务器冗余，上行没有）。回答要分命令类型：移动可以丢（下一条覆盖），关键命令短冗余，技能全量冗余 + 序号保序 + 确认。能说出“全量冗余反而比短冗余省带宽、代价是尾延迟”和“突发丢包会让紧挨着的副本一起丢”，就超出了大多数候选人。

本章速记
  • 上行包 = 命令 + 期待帧（ACK） + 命令序号；非战斗输入丢弃；帧末统一 flush；下行卡顿时上行主动退让。
  • 短冗余：当前 + 前 2 条、约 33 ms；全量冗余：所有未确认技能、约 200 ms、1 s 超时、按序号保序。

  • 序号三边界 nBeginSeq / nMaxSeq / nCurSkillSeq；确认 = 在下行帧里看到自己；= 出队、> 有空洞、< 重复；追帧后 +100 隔离。
自测 1：为什么普通移动命令不进冗余队列？移动是“状态型”输入：下一条移动命令会覆盖上一条，偶尔丢一条只会让角色晚一帧转向；而技能、购买是“事件型”输入，丢了就是真丢了。冗余要花在事件型输入上。
自测 2：全量冗余的重发间隔设成 33 ms 会怎样？送达率在随机丢包下变化不大，但每个技能在确认前会被发很多份（确认需要约一个 RTT + 一帧），带宽上升；而且 33 ms 间隔的副本仍会被几百毫秒的突发丢包一起吞掉。间隔要大于典型突发长度，同时小于技能可容忍的延迟。
自测 3：服务器怎么知道技能是重复的？每条技能带单调递增的技能序号，服务器记录每个玩家已处理的最大序号，小于等于它的直接丢弃；同一个包里的多条技能按序号依次生效，从而同时解决了重复和乱序。
