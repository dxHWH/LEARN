CHAPTER 08

HOK 保障与延展：网络质量、一致性校验、录像与 CS 模式

前面的机制解决“能通”；这一章解决“通得怎么样、不好时怎么知道哪里不好”，以及帧同步那份“输入序列”还能派什么用场。

本章目标
  • 理解为什么“发包时刻 − 收包时刻”测出来的 ping 会偏大，并用实测看清偏差的量级与来源。
  • 能讲出卡顿归因的四个维度、卡顿三态状态机，以及双链路（Wi-Fi + 蜂窝）的触发条件与代价控制。
  • 说清一致性校验为什么是“帧 hash 上报比对”而不是“服务器养影子客户端”，以及录像“与实战走同一条路”的价值。
  • 理解 CC / CS 两种模式、同一接口两种实现的设计，并与 LoL、UE 的回放方案对照。
30 秒面试版答案

ping 不能用主线程时刻算，因为包到达后会在网络库缓冲里等主线程来取，测出来的值混入了排队时间，并随帧率和卡顿放大；HOK 用网络线程打的到达时间戳（还分协议栈层和解密重组后两级）。卡顿从四个维度归因：帧推进抖动分 10 档统计、卡顿三态状态机（超过 300 ms 没新帧进入卡顿，最近收包小于 70 ms 进入恢复）、包到达到被处理的滞留时间（区分网络慢还是本机慢）、卡顿期间有效帧的到达序列（零散丢包还是整段断流）。Wi-Fi 变差时可以 Wi-Fi + 蜂窝双发，先到者生效。一致性靠各端周期性上报帧 hash 横向比对，成本极低、顺带反作弊。录像就是输入序列，回放与实战走完全相同的分发链路。另有 CS 模式：同一份 C++ 逻辑跑在服务器，客户端收结果流，上层代码通过统一接口无感切换。

8.1 ping：一个容易测错的指标

回顾第 5 章：Apollo 有自己的网络线程负责收包、解密、组包，但 C# 侧是主线程同步轮询取包。于是包到达后要在缓冲区里等 0~N 个渲染帧才被主线程取走。用主线程时刻计算 ping，测出来的是“网络往返 + 排队等主线程”的时间 HOK 文档。实测（真实 RTT 均值约 55 ms，ping 在帧末发出）实测 E8：

所以 HOK 优先用 SDK 在网络线程打的到达时间戳，并提供两级：底层协议栈时间戳（更贴近网卡，精度最高）与协议层时间戳（解密与重组之后），可云控切换。注意这两个时间戳与主线程 Time 是不同的时间基准，不能混用。配套优化：有其它上行包时可以少发 ping（上行包本身带期待帧，已有 ACK 语义）；ping 包顺带回传丢帧数、抖动、补包统计；显示值做加权平滑。

对照 Unreal

UE 的 APlayerState 会复制一个压缩过的 ping 值（用 GetPingInMilliseconds() 读取），连接层还有 UNetConnection::AvgLag 等统计；UE 5.1 起新增了 NMT_Ping 控制消息与 NetPing 相关实现 UE 源码。UE 的网络收包发生在 UNetDriver::TickDispatch（游戏线程 tick 开头），同样存在“包在套接字缓冲里等一帧”的问题，所以 UE 的 ping 也会受服务器 / 客户端帧率影响——这是面试里可以主动指出的细节。

8.2 卡顿归因：把“卡”拆开看

维度做法 HOK 文档回答的问题
① 帧推进抖动每帧记录“实际间隔 − 66 ms”，按 10 档分桶（110 / 200 / … / 900 / 2000 ms+），随结算上报；保留具体卡顿帧号与时长（有上限）是普遍轻微抖动，还是偶发严重卡顿？
② 卡顿状态机三态：正常 / 卡顿 / 恢复中；进入卡顿时建档（前后收发包量、空洞长度、网络制式、持续时长），随 ping 回传一次卡顿事件的完整画像
③ 处理延迟单独统计“包到达 → 被主线程处理”的滞留时间慢的是网络，还是本机？
④ 帧到达序列卡顿期间有效帧的到达序列零散丢包，还是整段断流？

8.3 双链路、加速器、后台收发、UDP 假死

机制要点 HOK 文档
双链路（Wi-Fi + 蜂窝）触发：主动补帧请求超阈值（下行在丢）/ 移动命令上行后迟迟收不到回包（上行有问题）/ ping 或原始延迟超阈值。开启后通过 UDP 控制字通知通道层，同一份数据两条链路都发，先到者生效。约束：30 s 冷却、低功耗模式降级、服务器可下发关闭；结算时上报单 / 双链路时长与切换次数评估收益
加速器协同建连时把目标 IP / 端口注册给第三方加速 SDK（UDP 白名单）；局内持续上报实测延迟、均值 / 方差 / 丢包率
切后台Unity 主循环降频或暂停时，启动独立网络线程继续收发，与主线程用锁互斥（抢不到锁就跳过本轮）；能在后台处理的（维持连接、心跳）立即处理，涉及表现与场景的攒到回前台再消费
UDP 假死发包正常、一个包都收不到、连接状态却“正常”；判定：距上次收包超时且 ping 序号仍在推进 → 主动重建 UDP 连接并上报
双链路的本质是“空间冗余”

第 6、7 章的冗余是时间冗余（同一份数据在不同时刻再发一次），突发丢包会让挨得近的副本一起丢；双链路是空间冗余（同一份数据走两条独立的物理链路），两条链路同时突发的概率约为两者的乘积——这正是对付“Wi-Fi 信号衰减但还没断”这种突发丢包的正确工具。代价是流量和功耗，所以要有触发条件和冷却。

8.4 一致性校验：帧 hash 上报比对

还有可选的详细追踪开关：开启后记录更细的演算轨迹，用于排查棘手的不同步（代价是性能与存储，仅在需要时开）。第 4 章的蝴蝶效应实验说明了为什么 hash 要“周期性”而不是“结束时”：1 ulp 的差异在第 [[det.precise.D4s.first]] 帧就体现在 hash 上，而肉眼可见要到第 [[det.precise.D4s.f100]] 帧之后，越早发现，越容易定位到第一个分歧帧。

hash 能防什么、防不了什么

能防：改本地数值（攻击力、血量、CD）——改了就和其他九端不一致。防不了：透视 / 全图（客户端本来就有全量数据，只是读出来显示，不改状态）、脚本 / 宏（输入合法）。这两类要靠客户端反作弊、行为分析，或者 CS 模式（客户端拿不到完整逻辑）。“帧同步不能防作弊”和“帧同步完全能防作弊”都是错的。

8.5 录像：与实战走同一条路

帧同步的录像就是“把输入序列存下来”。HOK 更彻底：帧数据到达后第一时间写入录像缓冲，开局 / 开打 / 结算等关键协议也写入；回放时读录像、按协议号分派，遇到帧数据就喂给帧窗口——之后走完全相同的分发链路（交付逻辑层 → 授权推进 → 播放表现）HOK 文档。回放不是“另一套播放器”，而是“把实战的输入源换成文件”：录像能忠实复现实战中的 bug、不需要维护第二套逻辑、观战也复用同一机制（输入源换成实时转发）。由于逻辑在本地，观战可以自由切视角、看任意玩家，服务器不需要额外计算。

录什么输入序列 + 关键协议服务器发给客户端的复制数据流（以“观战连接”的视角录制）服务器的全部输入、对局设置与配置（Server Network Recording）

英雄联盟的例子很有启发：它是状态同步游戏，却为了“电竞比赛中出 bug 时回到某个时间点重开”（Project Chronobreak，2017 年首次在 LCS 赛场使用）把服务器做成了确定性的——录下服务器输入，重放时不限速，回到 40 分钟通常不到 3 分钟。而这项确定性工作最初是为了做可录制输入驱动的快速回归测试工具 Delta Checker Riot 技术博客。确定性不是帧同步的专利，而是一种可以单独购买的工程能力。

8.6 另一种形态：CS 模式

开局协议 SCID_MULTGAME_BEGINLOAD(1075) 的 bCsMode 决定本局是 CC 还是 CS HOK 文档：

CC（帧同步）CS
战斗逻辑在哪本地逻辑层全量运行服务器逻辑层运行，本地只跑轻量部分
服务器做什么帧号分配、汇总去重、定频广播、缓存直接算完整逻辑，下发结果
下行内容各玩家输入（1035）演算结果的通知流（切成连续 PIECE 分片）
接收窗口 / 补发 / 追帧需要由服务器的可靠有序流替代（分片滑动窗口 + 区间 ACK + 缺口重传）
优势带宽低、录像便宜、服务器成本低天然防作弊（客户端拿不到完整逻辑）、客户端算力要求低

“滑动窗口 + 按序消费 + 缺口重传”的思想在 CC 与 CS 下是一致的，只是承载内容不同：CC 下是输入，CS 下是结果。两种模式由服务器在开局时决定：常规 5v5 用 CC；对防作弊要求极高、低端机、部分娱乐玩法可用 CS。

CS 模式其实就是“服务器跑确定性逻辑的状态同步”

把 CS 模式放到第 1 章的谱系里看：逻辑在服务器、客户端收结果，这就是状态同步；但因为逻辑本身是确定性的，它同时保留了“录输入即可重放”的能力。HOK 的 CC / CS 双模式、LoL 的确定性服务器、守望先锋的确定性命令帧，说明的是同一件事：帧同步与状态同步不是两个阵营，而是“权威放在哪”和“传什么”两个旋钮的不同组合。第 14 章会把这两个旋钮展开。

面试注意

三个高频追问：“帧同步怎么检测不同步”（周期性 hash 上报比对，不是影子客户端）；“帧同步能防作弊吗”（能防改数值，防不了透视和脚本）；“帧同步录像为什么小”（只存输入，回放复用实战路径，代价是依赖确定性和版本）。答第三个时顺带对比 UE 的 DemoNetDriver 录的是复制数据流，体积大但不依赖确定性。

本章速记
  • ping 用网络线程到达时间戳；主线程时刻会多算最多约一帧，长帧时 p95 偏差 [[e8.60_1.p95|.0f]] ms（E8）。
  • 卡顿四维：抖动 10 档分桶 / 三态状态机（300 ms 进卡顿、70 ms 进恢复）/ 处理延迟 / 到达序列；双链路 = 空间冗余。
  • 一致性：帧 hash 上报横向比对，顺带反作弊；防得住改数值，防不住透视和脚本。
  • 录像 = 输入序列，回放与实战同路径；CS 模式 = 同一份确定性逻辑跑在服务器，统一接口切换传输实现。
自测 1：为什么不让服务器跑一个影子客户端来做一致性校验？成本：每局都要在服务器完整跑一份逻辑（这本来就是帧同步想省掉的）；而 hash 比对只需要各端多算一个摘要、多发几十字节，服务器做一次比较。十个客户端互相就是彼此的“标准答案”，多数一致即可判定少数异常。
自测 2：卡顿状态机为什么需要“恢复中”这个中间态？网络恢复初期往往不稳定，如果收到一个包就判回“正常”，紧接着又超时就判回“卡顿”，状态会来回抖动，建档和统计都会失真。中间态要求“连续两次帧间隔正常”才回到正常，这是迟滞设计。
自测 3：CS 模式下，第 6 章的接收窗口和补发还需要吗？帧级的窗口、补发、追帧不需要了（不再收输入帧），但同样的思想换了一种载体：服务器结果流被切成连续分片，客户端用滑动窗口排序、按序消费、区间 ACK、缺口请求重传，超时先探活、连续超时提示重连。
