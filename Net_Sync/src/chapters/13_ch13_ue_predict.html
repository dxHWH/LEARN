CHAPTER 13

Unreal 的预测：CMC、GAS、Mover 与网络物理

第 10 章的“预测 + 和解”落到 Unreal 里有三个实现：角色移动交给 CharacterMovementComponent，技能交给 GAS 的 Prediction Key，而 Mover 和网络物理是 Epic 把它们通用化的下一代尝试。

本章目标
  • 按时序讲完 CMC 的一次移动：SavedMove → 本地执行 → ServerMove → 服务器重放与误差判定 → ClientAckGoodMove / ClientAdjustPosition → 客户端重放未确认移动。
  • 会给 CMC 加一个可预测的自定义移动（冲刺），知道 SavedMove / 压缩标志 / CanCombineWith 各自的作用。
  • 说清 GAS 的预测：Prediction Key、LocalPredicted、哪些东西能预测、被拒绝时怎么撤销、为什么不会重复扣两次。
  • 了解 Mover、Network Prediction Plugin、Chaos 网络物理（预测插值 / 重模拟）的定位与成熟度。
30 秒面试版答案

CMC 是 Unreal 的角色移动预测：自主代理每帧把输入（加速度、跳跃等压缩标志）和时间戳存成 SavedMove，本地立刻执行，再通过不可靠的 ServerMove RPC 发给服务器（顺带一个重要的旧移动作冗余）；服务器用客户端时间戳算出时间差、重放这次移动，比较客户端声称的位置，误差在阈值内就回 ClientAckGoodMove，超出就回 ClientAdjustPosition；客户端收到纠正后设到权威位置，再把时间戳之后的 SavedMoves 全部重放——这就是第 10 章的和解。其他端的角色是模拟代理，靠复制的移动数据插值并平滑网格。GAS 用 Prediction Key 做技能预测：LocalPredicted 技能在客户端立即激活，生成一个 key 随 ServerTryActivateAbility 发给服务器，期间产生的 GE、GameplayCue、蒙太奇都挂在这个 key 上；服务器拒绝则整体撤销，接受则用复制下来的 key 对账、去掉本地预测的副本避免重复。Mover 是更模块化的新移动框架，网络物理提供预测插值和重模拟，二者在 UE5 中仍处于实验性 / Beta 阶段。

13.2 给 CMC 加一个可预测的冲刺

最常见的错误：客户端按下冲刺时直接改 MaxWalkSpeed，再用一个 Server RPC 通知服务器改。结果是客户端先跑快、服务器晚一个 RTT 才跑快，这段时间里每一步都和服务器对不上，被连续 ClientAdjustPosition 拉回（第 10 章“橡皮筋”）。正确做法是把“是否冲刺”放进 SavedMove，让它和移动输入一起被预测、发送、重放：

class FSavedMove_MyChar : public FSavedMove_Character { public: uint8 bWantsToSprint : 1; virtual void Clear() override { FSavedMove_Character::Clear(); bWantsToSprint = 0; } virtual uint8 GetCompressedFlags() const override { uint8 F = FSavedMove_Character::GetCompressedFlags(); if (bWantsToSprint) F |= FLAG_Custom_0; // 随 ServerMove 一起上行 return F; } virtual bool CanCombineWith(const FSavedMovePtr& New, ACharacter* C, float MaxDelta) const override { if (bWantsToSprint != ((FSavedMove_MyChar*)New.Get())->bWantsToSprint) return false; // 状态变化的移动不能合并 return FSavedMove_Character::CanCombineWith(New, C, MaxDelta); } virtual void SetMoveFor(ACharacter* C, float Dt, const FVector& Accel, FNetworkPredictionData_Client_Character& Data) override { FSavedMove_Character::SetMoveFor(C, Dt, Accel, Data); bWantsToSprint = Cast(C->GetCharacterMovement())->bWantsToSprint; // 记录这一步的输入 } virtual void PrepMoveFor(ACharacter* C) override { // 重放（和解）时恢复这一步的输入 FSavedMove_Character::PrepMoveFor(C); Cast(C->GetCharacterMovement())->bWantsToSprint = bWantsToSprint; } }; void UMyCMC::UpdateFromCompressedFlags(uint8 Flags) { // 服务器从标志位恢复输入 Super::UpdateFromCompressedFlags(Flags); bWantsToSprint = (Flags & FSavedMove_Character::FLAG_Custom_0) != 0; } float UMyCMC::GetMaxSpeed() const { // 两端用同一个函数、同一个输入算速度 return (bWantsToSprint && IsMovingOnGround()) ? SprintSpeed : Super::GetMaxSpeed(); } // 还需要：FNetworkPredictionData_Client_MyChar::AllocateNewMove() 返回 FSavedMove_MyChar， // 并在 UMyCMC::GetPredictionData_Client() 里创建它。

压缩标志只有 4 个自定义位（FLAG_Custom_0~3）；需要更多数据（例如冲刺能量、瞄准方向）时，UE 4.26 起可以继承 FCharacterNetworkMoveData 自定义打包的移动数据 UE 源码。这一节的原则对任何预测系统都成立：影响模拟结果的一切输入，都必须进入“被保存、被发送、被重放”的那份数据——和帧同步“所有输入都要进帧命令”完全一样。

13.3 模拟代理：别人的角色怎么平滑

其他客户端上的角色不跑预测，它们通过 Actor 的 ReplicatedMovement（位置、旋转、速度，可量化）接收服务器状态，CMC 在两次更新之间按速度模拟、收到新状态时做 SmoothCorrection：胶囊体直接到新位置，网格（Mesh）保留一个偏移、在若干帧内平滑收敛（NetworkSmoothingMode：Disabled / Linear / Exponential）。这就是第 10 章“逻辑位置精确、显示位置平滑”的实现：碰撞与判定用胶囊，玩家看到的是平滑后的网格。

为什么 CMC 不像 Source 那样做固定延迟的快照插值？

CMC 的模拟代理默认更接近“收到即用 + 模拟外推 + 平滑”，没有一个全局的“渲染过去 100 ms”的插值时间轴，所以延迟更低，但在高抖动下更容易看到修正。需要严格插值（例如电竞回放、观战）的项目会自己做快照缓冲。延迟补偿也不是引擎内置的：Unreal 没有通用的“服务器回溯命中盒”，射击游戏通常自己维护历史（或者像很多项目一样，客户端判定命中、服务器做合理性校验）推断（基于引擎源码中无通用回溯模块）。

13.5 下一代：Mover、Network Prediction Plugin、网络物理

系统定位状态（截至查阅的资料）
Network Prediction Plugin（NPP）通用的“输入 / 同步状态 / 辅助状态 + 固定 tick + 回滚重模拟”框架，把 CMC 那套写法抽象成模板实验性；社区反馈其开发重心已转向 Chaos 物理后端
Mover（Mover 2.0）CMC 的长期替代：移动模式（Movement Mode）+ 叠加移动（Layered Move）+ 修饰器，模块化、可用于非 Actor；网络预测由后端提供（NPP 或 Chaos）5.4 起以实验性插件提供，5.6~5.7 期间进入 Beta（不同资料说法不一，以官方 release notes 为准）；官方仍在做破坏性 API 调整
Chaos 网络物理物理复制模式：预测插值（Predictive Interpolation，在插值时间线上做局部预测）、重模拟（Resimulation，状态偏差超过阈值时回滚重算）；NetworkPhysicsComponent 管理输入 / 状态历史、输入冗余与衰减5.4：预测插值为 Beta、重模拟为实验性；项目设置里有“支持的最大 RTT”“触发重模拟的误差阈值（厘米）”等参数；物理复制 LOD 在 5.7 中仍在完善

来源：UE 文档 / 公开路线图 / 官方论坛。这些系统的共同点是把 GGPO 式的“历史 + 回滚重算”带进了服务器权威的状态同步——第 9 章的结论在这里再次成立：预测必然伴随回滚，回滚必然需要历史和确定性的重算（物理的重算只需要“足够接近”，不需要逐位一致，因为服务器会持续纠正）。

面试注意

“CMC 怎么做网络同步”几乎必考，答题顺序：自主代理保存 SavedMove 并本地执行 → 不可靠 ServerMove（带时间戳 + 旧移动冗余）→ 服务器重放并按误差阈值决定 Ack 还是 Adjust → 客户端纠正后重放未确认移动 → 模拟代理插值 + 网格平滑。追问“怎么加冲刺 / 翻滚”时，一定要说“把输入放进 SavedMove（压缩标志或自定义移动数据），不要用 RPC 改速度”。GAS 问到预测时，关键词是 Prediction Key、LocalPredicted、撤销与去重。

本章速记
  • CMC：SavedMove（加速度 + 标志 + 时间戳）→ 本地执行 → 不可靠 ServerMove（+ 旧移动）→ 服务器重放、误差阈值 → Ack / Adjust → 客户端重放未确认移动；模拟代理插值 + 网格平滑。
  • 自定义移动：输入进 SavedMove（FLAG_Custom_0~3 或自定义移动数据），实现 SetMoveFor / PrepMoveFor / CanCombineWith / UpdateFromCompressedFlags。
  • GAS：Prediction Key 挂住所有预测副作用；LocalPredicted；拒绝整体撤销，接受按 key 去重；GE 移除、周期效果不预测。
  • Mover / NPP / Chaos 网络物理：把“历史 + 回滚重算”通用化；仍在实验性 / Beta 阶段。
自测 1：CMC 为什么用不可靠 RPC 发 ServerMove？移动是高频、可被后续数据覆盖的输入；可靠 RPC 丢一个包就会阻塞后续所有移动（队头阻塞），延迟反而更高。丢了的移动由“旧移动冗余”补，或者由下一次移动的时间差覆盖，再不行就靠服务器纠正。
自测 2：客户端开了加速器（时间流速变快），CMC 怎么防？服务器用客户端时间戳算 DeltaTime，但会校验时间戳的增长与服务器真实时间的差异（时间差异检测），并限制单次移动的最大 DeltaTime；累计偏差超过阈值时拒绝或惩罚。
自测 3：GAS 预测扣蓝，服务器也扣了一次，为什么玩家不会看到扣两次？客户端预测的 GE 带着 Prediction Key；服务器施加的 GE 复制下来时也带着同一个 key（ReplicatedPredictionKey），客户端据此识别出“服务器已经确认了这次预测”，移除本地预测的那份，只保留服务器的那份。
