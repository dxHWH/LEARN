CHAPTER 12

Unreal 属性复制与 RPC：状态与事件

属性复制同步的是“现在是什么样”，RPC 传递的是“刚才发生了什么”。用错一个，就会出现“中途加入的人看不到门是开的”或者“满屏重复的受击特效”。

本章目标
  • 写出属性复制的完整声明（UPROPERTY、GetLifetimeReplicatedProps、条件、RepNotify、Push Model），知道 OnRep 在哪端触发。
  • 用实测理解属性复制的三个语义：只保证最终一致、中间值会被合并、丢包后发最新值。
  • 掌握 RPC 的三种类型 × 可靠性 × “从哪端调用、Actor 归谁所有 → 在哪执行”表，以及可靠 RPC 的队头阻塞与缓冲溢出。
  • 能根据数据的性质选择：属性 / 不可靠多播 / 可靠 RPC / GameplayCue / 计数器 + OnRep。
30 秒面试版答案

属性复制：在 UPROPERTY 上标 Replicated 或 ReplicatedUsing=OnRep_X，在 GetLifetimeReplicatedProps 里用 DOREPLIFETIME(_CONDITION) 注册，可加条件（OwnerOnly、SkipOwner、SimulatedOnly、InitialOnly 等）。服务器按连接保存影子状态，只发变化的属性；它只保证最终一致：短时间内的多次修改会被合并成一次，丢包后不重发旧包而是发最新值；中途加入的客户端也能拿到当前值。C++ 里 OnRep 只在客户端值变化时调用，服务器要自己手动调。RPC 分 Server（拥有者客户端 → 服务器）、Client（服务器 → 拥有者客户端）、NetMulticast（服务器 → 所有相关端），可靠 RPC 保证到达且在 Actor 通道内有序，但会队头阻塞、缓冲满了会断线；不可靠 RPC 可能丢。原则：持续状态用属性，一次性表现用不可靠多播或 GameplayCue，关键一次性事件才用可靠 RPC，而且尽量用“计数器属性 + OnRep”代替。

12.1 属性复制：声明与条件

// MyCharacter.h UPROPERTY(ReplicatedUsing = OnRep_Health) float Health = 100.f; UPROPERTY(Replicated) int32 Ammo = 30; // 只有自己需要知道弹药数 → OwnerOnly UPROPERTY(ReplicatedUsing = OnRep_BurstCounter) uint8 BurstCounter = 0; // 开火计数器：每开一枪 +1，用来驱动别人端的开火特效 UFUNCTION() void OnRep_Health(float OldHealth); // 可以带一个参数接收旧值 UFUNCTION() void OnRep_BurstCounter(); // MyCharacter.cpp void AMyCharacter::GetLifetimeReplicatedProps(TArray& OutLifetimeProps) const { Super::GetLifetimeReplicatedProps(OutLifetimeProps); FDoRepLifetimeParams Params; Params.bIsPushBased = true; // Push Model：只有标脏才检查 DOREPLIFETIME_WITH_PARAMS_FAST(AMyCharacter, Health, Params); Params.Condition = COND_OwnerOnly; DOREPLIFETIME_WITH_PARAMS_FAST(AMyCharacter, Ammo, Params); Params.Condition = COND_SkipOwner; // 开枪者自己本地预测过了，不需要 DOREPLIFETIME_WITH_PARAMS_FAST(AMyCharacter, BurstCounter, Params); } void AMyCharacter::ApplyDamage_Server(float Damage) // 只在服务器上调用 { const float Old = Health; Health = FMath::Max(0.f, Health - Damage); MARK_PROPERTY_DIRTY_FROM_NAME(AMyCharacter, Health, this); // Push Model 下必须标脏 OnRep_Health(Old); // C++ 中服务器不会自动调 OnRep }
复制条件（ELifetimeCondition）发给谁典型用途
COND_None所有相关连接（默认）血量、状态
COND_InitialOnly只在初始复制时发一次出生时确定、之后不变的配置（队伍、皮肤）
COND_OwnerOnly只发给拥有者弹药、背包、技能冷却等私有数据
COND_SkipOwner发给除拥有者外的所有人拥有者本地预测过的东西（开火计数器、预测的动画状态）
COND_SimulatedOnly / COND_AutonomousOnly只发给模拟代理 / 只发给自主代理只有旁观者需要的平滑数据 / 只有控制者需要的校正数据
COND_SimulatedOrPhysics模拟代理或物理模拟的对象物理相关数据
COND_InitialOrOwner初始复制 + 之后只给拥有者—
COND_Custom由 DOREPLIFETIME_ACTIVE_OVERRIDE 在 PreReplication 中动态开关按游戏状态决定是否复制
COND_ReplayOrOwner / COND_ReplayOnly / COND_SkipReplay 等与回放（DemoNetDriver）相关只为回放录制的数据
COND_Dynamic / COND_Never运行时可改的条件 / 永不复制（UE5 新增）—
OnRep 语义说明 UE 文档 / 源码
在哪端触发C++：只在客户端收到新值时触发，服务器修改不会自动调用；蓝图 RepNotify：服务器上通过蓝图设置变量时也会调用——两者不一致是常见坑
何时触发默认 REPNOTIFY_OnChanged：收到的值与本地不同才触发；REPNOTIFY_Always：每次收到都触发（客户端本地改过值、服务器再发同样的值时有用）
多个属性同一 Actor 一次更新里的多个属性会先全部写入、再依次调用各自的 OnRep，所以 OnRep 里读到的其他属性是“同一批”的新值
对象引用复制的是 NetGUID；客户端还没有那个对象时指针为空，等对象到达、映射完成后会再次触发 OnRep

数组与结构体：TArray 按元素做增量；大数组（背包、Buff 列表）用 FFastArraySerializer，元素变化时 MarkItemDirty，客户端有 PostReplicatedAdd / PostReplicatedChange / PreReplicatedRemove 逐元素回调（GAS 的激活效果列表就是这么做的）。结构体默认按成员增量复制；实现了 NetSerialize（WithNetSerializer 特征）就作为整体原子复制，常用来做量化（如 FVector_NetQuantize10）。

12.2 属性复制的三个语义

实测：同一组受击，属性 vs RPC 实测 E14

模型：0 / 10 / 20 / 30 ms 连续 4 次受击（100 → 75 → 50 → 25 → 10），300 ms 再受击一次（→ 0）。属性：NetUpdateFrequency = 10（每 100 ms 一次更新，相位随机），下行丢包 20%，单程 40 ms，丢包后约 90 ms 发现并在下次更新补发最新值。RPC：每次受击发一个多播；可靠 RPC 丢包后 100 ms 重传、按序交付。2 万次试验：

通道客户端收到什么延迟适合
复制属性 Health平均只触发 [[E14.onrep|.2f]] 次 OnRep（5 次变化中的中间值大多被合并），但最终值一定正确最终值平均在 [[E14.finalT|.0f]] ms 到达（第 5 次受击在 300 ms）持续状态；中途加入也能拿到
不可靠多播 RPC平均收到 [[E14.unrel|.2f]] / 5 个事件最低可以丢的表现（受击特效、音效）
可靠多播 RPC5 个都收到、按序平均 [[E14.relLat|.0f]] ms（前一个丢了，后面的即使先到也要等：队头阻塞）必须到达、次数要准的关键事件，且频率低

表 12-2 RPC 调用与执行端 UE 文档。最常见的 bug 是第五行：客户端对“不归自己所有”的 Actor 调 Server RPC，直接被丢弃。

可靠性保证代价 / 风险
Reliable一定到达；同一 Actor 通道内按调用顺序执行丢包时后面的可靠 RPC 要等它（E14 平均 [[E14.relLat|.0f]] ms）；可靠缓冲有上限，持续高频发送会溢出并断开连接
Unreliable不保证到达、不保证顺序带宽紧张或丢包时会丢；适合高频、可丢的数据（移动、表现）
多播与相关性

NetMulticast 只发给“当前与该 Actor 相关”的连接；之后才变得相关、或中途加入的客户端收不到之前的多播。所以“门打开了”“宝箱被开过”这种持续状态必须用属性（新来的人能拿到当前值），多播只用于“此刻播一下就行”的表现。传统复制系统下，同一 Actor 的属性与 RPC 到达顺序也没有固定保证（Iris 改为 RPC 在状态数据之后发送）UE 文档。

12.4 怎么选：状态、事件，还是计数器

对照 HOK

帧同步里没有“属性复制 vs RPC”的选择题：网络上只有输入，状态与事件都是本地演算出来的（第 5 章的结果事件）。HOK 的上行技能命令需要“必须到达、按序”，它没有用可靠通道，而是用“不可靠 + 全量冗余 + 序号”（第 7 章）——和这里“计数器属性 + OnRep”是同一个思路：用幂等的、可合并的表示代替可靠有序的消息流。

面试注意

高频题：“属性复制和 RPC 的区别、各自适用场景”（状态 vs 事件、最终一致 vs 逐条、新加入者能否拿到）；“OnRep 在服务器会调用吗”（C++ 不会、蓝图会）；“Reliable 有什么风险”（队头阻塞、缓冲溢出断线，Tick 里发 Reliable 是大忌）；“为什么客户端调 Server RPC 没执行”（所有权）。能讲出 E14 的“5 次变化只触发 2 次 OnRep”，说明你理解了属性复制的合并语义。

12.5 坑位

坑后果修正
用 OnRep 次数统计事件次数次数偏少（被合并）计数器差值，或事件通道
持续状态用多播中途加入 / 后来相关的人看不到属性
Tick 里发 Reliable RPC弱网下可靠缓冲溢出，连接被关闭高频数据用不可靠，或合并成属性
C++ 服务器改了属性却期待 OnRep 执行服务器端（Listen Server 主机）没表现服务器手动调用 OnRep 或抽出公共函数
Push Model 下忘记标脏属性永远不复制修改处统一 MARK_PROPERTY_DIRTY，或封装 Setter
_Validate 里做业务校验（射速等）网络抖动导致的正常玩家被踢_Validate 只查明显非法；业务校验在 _Implementation 里拒绝并回滚
大数组整体复制每次改一个元素都可能触发大量比较 / 发送FFastArraySerializer
本章速记
  • 属性：Replicated / ReplicatedUsing + DOREPLIFETIME(_CONDITION / _WITH_PARAMS_FAST)；条件 OwnerOnly / SkipOwner / InitialOnly …；Push Model 要标脏。
  • 语义：最终一致、中间值合并、丢包发最新值；E14：5 次变化平均 [[E14.onrep|.2f]] 次 OnRep。C++ OnRep 只在客户端触发。
  • RPC：Server（只能由拥有者客户端发起）/ Client / NetMulticast（只发给相关连接）；Reliable 有序但队头阻塞（E14 [[E14.relLat|.0f]] ms）且可能溢出断线。
  • 选择：状态 → 属性；可丢表现 → 不可靠多播 / GameplayCue；高频且要计数 → 计数器 + OnRep；低频关键 → 可靠 RPC。
自测 1：子弹打中墙留下弹孔，用什么同步？弹孔本身是表现，丢了不影响逻辑，用不可靠多播或 GameplayCue（或者干脆由每端根据复制下来的开火计数器 + 命中结果本地生成）；如果弹孔要长期存在且中途加入的人也要看到，就需要服务器维护一个复制的“弹孔列表”（FFastArraySerializer，限制数量）。
自测 2：为什么开火计数器要用 COND_SkipOwner？开枪的人自己在本地已经预测播放了开火表现；如果计数器也复制给他，OnRep 里会再播一次，出现重复特效。SkipOwner 让只有其他人（模拟代理）通过 OnRep 播放。
自测 3：Listen Server 上，主机玩家受伤时 C++ 的 OnRep_Health 会执行吗？不会自动执行——主机是服务器，C++ OnRep 只在客户端收到复制时调用。所以服务器改血量后要手动调用 OnRep_Health（或共同的处理函数），否则主机玩家看不到受伤表现。蓝图 RepNotify 则会在服务器上自动调用。
