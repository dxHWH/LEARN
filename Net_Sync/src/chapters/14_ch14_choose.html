CHAPTER 14

选型、混合方案与业界案例

帧同步和状态同步不是两个阵营，而是两个旋钮的不同位置：权威放在哪，网上传什么。

本章目标
  • 用“权威位置 × 传输内容”两个旋钮给任意同步方案定位，包括 HOK 的 CC / CS、LoL、守望先锋。
  • 掌握一张 14 个维度的全维对照表，能针对需求说出取舍。
  • 能把 HOK 的每个机制映射到 Unreal 中的对应物，反之亦然。
  • 知道如果要在 Unreal 里做帧同步，需要绕开哪些引擎设施、自己补哪些模块。
30 秒面试版答案

选型先问能不能做确定性（定点数、单线程、不用引擎物理），不能就只有状态同步；能的话再看单位规模、录像观战需求、网络环境、反作弊要求和对延迟的敏感度：单位多、要录像、移动网络、服务器成本敏感 → 定频广播帧同步（HOK）；2 人、状态小、帧级延迟敏感 → 回滚；透视敏感、单位少、要强权威 → 状态同步 + 预测 + 延迟补偿（Unreal 默认）。现实中的方案大多是混合的：LoL 是状态同步但服务器做成了确定性以支持回档，守望先锋是状态同步但输入驱动的系统用固定命令帧做预测回滚，HOK 同时有 CC 帧同步和 CS 服务器演算两种模式。

状态同步的服务器也需要输入缓冲：客户端输入到达服务器的时机有抖动，服务器在每个命令帧需要“刚好有一份输入可用”。守望先锋的做法是：服务器发现缓冲不够（丢包 / 抖动），就通知客户端略微加快命令帧的推进速度，让输入提前一点到达；网络变好再放慢回去 GDC 2017。这和 HOK 下行“窗口 + 补发”、格斗“输入延迟 d”、GGPO“时间同步”解决的是同一个问题：用一个小的、可调的缓冲吸收抖动。

14.5 在 Unreal 里做帧同步：工程清单

Unreal 的设施几乎全部围绕状态同步设计。要做 HOK 式帧同步，基本思路是把 UE 当成“表现层 + 输入层 + 传输层”，逻辑层自己写——就像 HOK 把 Unity 当表现层一样 推断：

模块做法要避开的坑
逻辑层独立的纯 C++ 模块（不依赖 UObject / 引擎时间），定点数数学库、确定性随机、数组式实体存储（ECS 风格），固定帧推进不要在逻辑里用 float / FVector、TMap 遍历、FMath::Rand、GetWorld()->GetTimeSeconds()、蓝图数学节点
物理 / 碰撞逻辑层自研定点碰撞（圆、胶囊、网格寻路）Chaos 物理不是逐位确定的，不能参与逻辑；根运动、动画通知不能驱动逻辑
表现层Actor 只是“视图”：逻辑层产出结果事件（生成、移动、播放技能、受击），Actor 订阅并插值；类似 HOK 的 AGE / UE 的 GameplayCue表现层不能改逻辑状态；Actor 不开复制（或只复制与逻辑无关的东西）
输入Enhanced Input 采集 → 量化成帧命令（方向量化到整数、技能槽 + 目标）→ 命令序号不要把浮点摇杆值直接送进逻辑
传输方案 A：独立 UDP（自研或 KCP）连 Relay 服务；方案 B：复用 NetDriver，用 PlayerController 上的不可靠 RPC 发命令、自己做冗余与序号不要用 Reliable RPC 发每帧命令（队头阻塞 + 缓冲溢出）
Relay 服务独立服务（定帧、汇总、广播、缓存、补发），或无渲染的 UE 专用服务器只跑转发逻辑服务器不等人；期待帧做 ACK
校验与录像逻辑层周期性算 hash 上报；录像 = 输入序列 + 版本号逻辑层版本必须与录像绑定
CI跨编译器 / 平台重放同一份录像比对 hash；回滚类项目再加同步测试模式只在一个平台测试等于没测

反过来，如果项目已经深度依赖 Unreal 的 Gameplay 框架（CMC、GAS、蓝图逻辑、Chaos），想“改成帧同步”几乎等于重写逻辑层——这正是 GGPO 资料里反复提到的“回滚无法后装”的问题：确定性与逻辑表现分离必须在项目第一天就决定。

14.6 常见混合设计

帧同步 + 服务器抽查

CC 模式为主，服务器对可疑对局（hash 少数派、举报）离线重放录像复核，兼顾成本和反作弊。

状态同步 + 确定性子模拟

弹道、技能时间轴、伤害公式写成确定性的，服务器只同步“开火事件 + 种子”，各端自己算轨迹，大幅减少投射物复制。

状态同步 + 局部预测回滚

只对本地玩家相关的系统（移动、技能起手）做预测回滚，其他一律插值（守望先锋、CMC、GAS）。

帧同步 + 关键事件可靠通道

帧命令走不可靠 UDP + 冗余，开局 / 结算 / 投降等走 TCP 或可靠通道（HOK 的 UDP + TCP 双通道）。

面试注意

设计题（“让你做一个 3v3 竞技游戏的网络同步”）的答题框架：① 先问约束（人数、单位规模、品类、平台与网络、反作弊等级、是否要录像 / 观战 / 断线重连、引擎）；② 用两个旋钮给出方案并说明理由；③ 讲三个关键机制（例如状态同步就讲预测和解、插值、延迟补偿，帧同步就讲确定性、冗余补发、追帧）；④ 讲度量与兜底（ping、卡顿归因、desync / 纠正统计、弱网测试）。不要一上来就说“用帧同步”或“用 UE 默认的就行”。

自测 1：为什么说“英雄联盟证明了确定性不是帧同步的专利”？LoL 是状态同步（服务器权威、复制状态给客户端），但 Riot 把服务器逻辑改造成了确定性的：记录服务器的全部输入和配置后，可以把服务器重放到任意时刻，用于自动化测试和赛场回档。确定性是一种独立的工程能力，帧同步只是它最出名的用途。
自测 2：一个 4 人合作 PVE 游戏，成本敏感、不强调反作弊、大量怪物，怎么选？怪物多 → 状态同步的带宽压力大；不强调反作弊 → 可以接受主机权威或帧同步。如果逻辑能做确定性，帧同步（或主机权威 + 怪物确定性子模拟）带宽最省；如果深度依赖引擎物理与动画，就用主机权威的状态同步 + 怪物 AOI + 低频复制，并把怪物的弹道 / 技能做成“事件 + 种子”的确定性子模拟。
自测 3：在 Unreal 里用 Reliable RPC 每帧发帧命令有什么问题？可靠 RPC 在 Actor 通道内有序，丢一个包后面的命令全部等重传（队头阻塞，延迟突增）；弱网下可靠缓冲会持续堆积，超过上限会直接断开连接。应该用不可靠通道 + 冗余 + 序号（HOK 上行的做法）。
