CHAPTER 02

时间、网络与固定步长

同步的敌人不是“慢”，而是“不确定”：抖动比平均延迟更致命，渲染帧率不能影响逻辑，各端的“现在”要对齐到同一条时间轴上。

本章目标
  • 说清延迟、抖动、丢包、乱序各自造成什么现象，为什么游戏用 UDP + 自定义可靠层。
  • 写出固定步长循环（accumulator），理解“插值多一帧延迟、外推会出错”的取舍，并看实测数据。
  • 会推 NTP 式对时公式，知道 UE GetServerWorldTimeSeconds 的精度局限。
30 秒面试版答案

网络有四个“坏”：延迟、抖动、丢包、乱序。TCP 可靠有序但会队头阻塞，一个包丢了后面全部等重传，所以实时游戏用 UDP，自己在上面做“按需可靠”：序号 + ACK 位图、只对关键数据重传、状态类数据直接发最新值。逻辑必须用固定步长推进（帧同步靠它保证确定性，状态同步靠它让服务器 / 客户端步调一致），渲染帧率任意；渲染时用两次逻辑状态插值保证平滑，代价是多一个逻辑帧的延迟。各端要对齐时间轴：用 NTP 式往返测量估计时钟偏移，取 RTT 最小的样本、做平滑。

2.1 网络的四个“坏”

现象定义玩家感受常见对策
延迟（Latency / RTT）单程或往返时间；物理距离 + 排队 + 处理按键到反馈慢、被“隔墙杀”预测、延迟补偿、就近部署
抖动（Jitter）延迟的波动一卡一卡、忽快忽慢抖动缓冲（插值延迟、输入缓冲）
丢包（Loss）包没到；移动网络常见突发丢包（连丢）操作没生效、画面停住冗余、选择性重传、补发
乱序（Reordering）后发先至状态回跳、技能顺序颠倒序号 + 接收窗口重排

经验量级（仅供建立直觉）：同城有线 RTT 几十毫秒以内；4G / 5G 通常几十到一百多毫秒，抖动明显；Wi-Fi 信号弱时会出现几百毫秒的突发停顿；跨国 150~300 ms。平均值能用缓冲吸收，抖动和突发丢包才是体验杀手——HOK 文档里所有的冗余、补发、卡顿统计都在对付后两者 HOK 文档。

2.2 为什么游戏用 UDP

实时游戏在 UDP 上自建可靠层，常见做法：

  • 序号 + ACK 位图：每个包带自己的序号、对方最新序号和一个 32 位位图（表示之前 32 个包哪些收到了），不用单独的 ACK 包 Gaffer On Games。
  • 分通道：不可靠（移动、状态）/ 可靠有序（聊天、结算）/ 可靠无序。Unreal 的 RPC 分 Reliable / Unreliable，属性复制丢了不重发旧包、而是下次发最新值 UE。
  • 冗余代替重传：状态和输入很小，与其等一个 RTT 重传，不如每个包把最近几份一起带上（HOK 下行一包多帧、上行三条历史，第 6、7 章）。
  • 以带宽换延迟：KCP 这类协议用快速重传、不做 TCP 式拥塞退让，换来更低的重传延迟。

HOK 用腾讯的 Apollo 中间件同时维持 UDP 和 TCP：帧命令、ping、补帧请求走 UDP；大厅协议、开局结算等必须可靠的走 TCP；取包时先读 UDP、再读 TCP，实时性优先 HOK 文档。

2.3 固定逻辑步长，渲染与之解耦

逻辑如果跟着渲染帧率走（pos += v * deltaTime），不同机器、不同帧率算出来的结果就不同——帧同步直接 desync，状态同步的预测也对不上服务器。所以逻辑一律用固定步长，渲染帧率随便：

const double kStep = 1.0 / 15; // 逻辑步长：HOK 约 66 ms 一帧 double accumulator = 0; State prev = state, cur = state; void OnRenderFrame(double frameDt) { // 渲染帧率任意（30 / 60 / 120 fps，还会抖） accumulator += std::min(frameDt, 0.25); // 防“死亡螺旋”：一帧最多补 0.25 s while (accumulator >= kStep) { // 落后几步就补几步，逻辑永远是整步 prev = cur; cur = Simulate(cur, kStep); // 确定性：只依赖 (状态, 输入, 固定步长) accumulator -= kStep; } double alpha = accumulator / kStep; // 0~1：当前时刻在两个逻辑帧之间的位置 Render(Lerp(prev, cur, alpha)); // 插值：平滑，但比最新逻辑晚约 1 帧 }

渲染时有三种选择：直接画最新逻辑状态、在上一帧和当前帧之间插值、按速度往前外推。实测如下 实测 E2：

渲染方式平均滞后（相对真实）每帧速度抖动（标准差）适用
直接画逻辑状态[[E2.lagRaw|.1f]] ms[[E2.jRaw|.0f]] cm/s只适合逻辑帧率 ≥ 渲染帧率
插值（prev → cur）[[E2.lagInt|.1f]] ms[[E2.jInt|.0f]] cm/s默认选择：平滑、永不出错

结论：插值把阶梯感降了一个数量级以上，代价是多一个逻辑帧（66 ms）的显示延迟。HOK 的做法是逻辑 15 Hz 由服务器驱动、客户端逻辑帧率可以更高，“表现插值就发生在多出来的帧里”，帧号按 客户端帧号 = 服务器帧号 × 服务器帧间隔 ÷ 客户端帧间隔 换算 HOK 文档。状态同步里同样的思想放大到网络层面就是第 10 章的“快照插值”。

Unreal 里的服务器时间

AGameStateBase::GetServerWorldTimeSeconds() 的实现是服务器周期性复制自己的世界时间，客户端在 OnRep 里用“收到的值 − 本地时间”算偏移——没有扣除单程延迟，所以客户端算出的服务器时间会落后约半个 RTT，且受复制间隔影响 UE 源码。做延迟补偿、技能倒计时、回放对齐等需要精确时间的功能时，通常自己用一对 RPC 做 NTP 式对时，或者像 CMC 那样用客户端时间戳 + 服务器校验。

面试注意

“为什么要固定步长”要答到确定性和与服务器步调一致两层；“插值有什么代价”要答出多一帧延迟；“怎么对时”要能写出偏移公式并说明取最小 RTT 样本的原因（不对称误差）。能顺带说出 UE 默认服务器时间不做延迟补偿，是加分项。

本章速记
  • 四个坏：延迟（预测 / 补偿）、抖动（缓冲）、丢包（冗余 / 重传）、乱序（序号 + 窗口）。突发丢包与抖动最致命。
  • TCP 队头阻塞 → 游戏用 UDP + 按需可靠（序号、ACK 位图、冗余、状态发最新值）。
  • 固定步长 + 渲染插值：平滑但晚一帧（实测 [[E2.lagInt|.0f]] ms，速度抖动 [[E2.jRaw|.0f]] → [[E2.jInt|.0f]] cm/s）。
  • 对时：$\theta = \frac{(t_1-t_0)+(t_2-t_3)}{2}$，取最小 RTT 样本 + 平滑；UE 默认服务器时间不扣单程延迟。
自测 1：渲染 120 fps、逻辑 15 Hz，不插值会怎样？连续 8 个渲染帧画的都是同一个逻辑状态，然后突然跳一格，看起来是 15 fps 的阶梯；插值后每个渲染帧都在两个逻辑帧之间取不同位置，看起来是 120 fps 的平滑运动，代价是整体晚一个逻辑帧。
自测 2：为什么 NTP 式对时要取 RTT 最小的样本？偏移估计的误差项是 $(\delta_{\downarrow}-\delta_{\uparrow})/2$，排队延迟越大越可能不对称；RTT 最小的样本排队最少，上下行最接近纯传播时延，最接近对称。
自测 3：Unreal 的属性复制丢包后会重发原来那个包吗？不会。属性复制只保证最终一致：丢包被检测到后，相关属性被标记为需要重发，下次发送的是当时的最新值；可靠 RPC 才会按序重传原内容。第 12 章有实测。
