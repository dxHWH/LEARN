CHAPTER 10

状态同步通论：插值、预测与和解、延迟补偿

状态同步的客户端同时活在三个时间里：看别人是在看过去，看自己是在看未来，开枪打别人时，服务器要替你回到过去。

本章目标
  • 画出“客户端的三个时间”：插值的他人（过去）、预测的自己（未来）、服务器的现在。
  • 用实测选插值延迟：快照间隔、抖动、丢包如何决定“该往回看多少毫秒”。
  • 写出预测 + 和解（reconciliation）的核心循环，用实测说明“直接覆盖”为什么会橡皮筋。
  • 说清延迟补偿的回溯量为什么是 RTT + 插值延迟、为什么要设上限、“隔墙杀”与“先开枪优势”从哪来。
30 秒面试版答案

状态同步里服务器权威，客户端用三件套弥补延迟：① 插值：别人的角色按“服务器时间 − 插值延迟（常见 100 ms 左右，约两个快照间隔）”渲染，在两份快照之间插值，丢一份快照也不卡，代价是看到的别人在过去；② 预测 + 和解：自己的输入立即在本地模拟（带序号保存），服务器回传“处理到第几号输入 + 权威状态”后，客户端回到这个状态、重放之后未确认的输入，预测对了就无感，错了只纠正差值，不会被拉回一个 RTT 之前；③ 延迟补偿：服务器收到开火命令时，把其他玩家的碰撞体回溯到射手当时看到的时刻（约 RTT + 插值延迟之前）做命中判定，再恢复；回溯要设上限，否则高延迟玩家会“隔墙杀”低延迟玩家。带宽靠增量压缩、量化、兴趣管理和优先级调度控制。

10.1 客户端的三个时间

10.2 插值：看别人是在看过去

服务器以固定频率（例如 20 Hz，每 50 ms 一份）下发快照。客户端不直接画最新快照，而是把它们放进缓冲区，渲染“估计的服务器时间 − 插值延迟 D”这一时刻的状态：找到前后两份快照线性插值；如果后一份还没到，只能外推（或停住）。D 越大越不容易缺快照，但画面越旧。Source 引擎的经典默认值是 100 ms 插值延迟（cl_interp 0.1，即 20 Hz 更新时两个快照间隔），这样丢一份快照仍有数据可插 Valve 开发者文档。

实测：插值延迟选多少 实测 E10

模型：服务器 20 Hz 快照，下行 40 ms + 指数抖动（均值 2 / 15 / 40 ms 三档），丢包 2%；目标做三角波横移（每 1.4 s 折返一次，带急转），客户端 60 fps 渲染。

10.3 外推：Dead Reckoning

外推（按最后已知的速度 / 加速度往前推）能让画面“不落后”，但运动一旦改变方向就会冲过头，再被拉回（图 2-2 的外推线、图 10-2 的红线）。它适合运动可预测的对象：载具、投射物、惯性大的物理物体；不适合会急转的人形角色。实践中常见的做法是：以插值为主，缺快照时短时间外推（设上限，如 250 ms），超时就停住；外推出错后不直接跳到正确位置，而是在几帧内把“显示位置”平滑收敛到“逻辑位置”（Unreal 的 SimulatedProxy 网格平滑就是这一类，第 13 章）。

10.4 预测与和解：看自己是在看未来

如果自己的角色也等服务器回来才动，每次按键都要多一个 RTT 的延迟。客户端预测（client-side prediction）让本地输入立即生效；服务器仍然权威，它回传“我处理到你第几号输入了，此时你在这里”。客户端拿到后有两种做法：

struct PendingInput { uint32_t seq; Input in; float dt; }; std::deque pending; // 已发出、服务器尚未确认的输入 State predicted; void OnLocalInput(Input in, float dt) { uint32_t seq = ++nextSeq; predicted = Simulate(predicted, in, dt); // ① 立即在本地模拟：零延迟手感 pending.push_back({seq, in, dt}); SendToServer(seq, in, dt /*, 以及最近几条未确认输入作冗余 */); } void OnServerState(uint32_t ackSeq, const State& authoritative) { while (!pending.empty() && pending.front().seq <= ackSeq) pending.pop_front(); // ② 丢掉服务器已经处理过的输入 State s = authoritative; // ③ 回到服务器的权威状态（“加载快照”） for (auto& p : pending) s = Simulate(s, p.in, p.dt); // ④ 重放尚未确认的输入（“重算”） ApplyCorrection(predicted, s); // ⑤ 预测对了：s == predicted，什么都不发生；错了：平滑修正差值 predicted = s; } // 错误做法（“直接覆盖”）：predicted = authoritative —— 丢掉了 pending， // 角色每次都被拉回到“一个 RTT 之前”的位置，然后再往前走：经典的橡皮筋。

实测：三种做法 实测 E11

模型：60 Hz 输入，移动速度 600 cm/s，按“右 1.2 s → 停 0.4 s → 左 1.2 s → 停 0.4 s”循环；RTT ≈ 100 ms，上行丢包 5%（每包带最近 3 个移动作冗余），服务器 30 Hz 回传确认；服务器在 3.0~3.5 s 判定玩家被定身（客户端不知道）。纵轴是“画面上的位置 − 服务器对同一组输入的权威结果”。

和解的关键是输入带序号、服务器回传“处理到第几号”。这正是 HOK 上行包里“命令序号”、Unreal CMC 里“时间戳”扮演的角色。被定身这种“预测必错”的情况无法避免，能做的是让纠正平滑（把视觉位置在几帧内插值到正确位置），以及在玩家能感知的地方给出合理的表现（被控时的特效、音效）。

预测什么、不预测什么

只预测由本地输入直接决定、且失败代价可接受的东西：自己的移动、开火的枪口特效与弹道、技能的起手动画。不预测或谨慎预测：伤害数值、死亡、拾取物归属（错了要撤销会很尴尬）、与别人强交互的结果（推人、抓取）。GAS 把这一点做成了框架：能被预测的东西都挂在一个 Prediction Key 上，服务器拒绝时整体撤销（第 13 章）。

10.5 延迟补偿：开枪时服务器替你回到过去

射手看到的敌人是插值后的“过去的敌人”（图 10-1 左侧）。如果服务器用自己“现在”的敌人位置判定命中，射手只能“提前量瞄准”，延迟越高越打不中。延迟补偿（lag compensation）的做法是：服务器为每个玩家保存最近一段时间（例如 1 s）的碰撞体历史；收到开火命令时，把其他玩家回溯到“射手开火时屏幕上看到的那一刻”，判定命中，再恢复。

实测（目标 600 cm/s 横移、随机折返，命中半径 34 cm，射手瞄得很准、只有 6 cm 手抖，插值延迟 100 ms）实测 E12：

回溯的代价落在被打的人身上：低 ping 的受害者已经躲到墙后，高 ping 射手的命令到达后服务器回溯到过去，判定命中——受害者体验到“我明明躲进去了还是死了”（隔墙杀）。所以要设回溯上限（Source 的 sv_maxunlag 默认 1 秒 Valve 开发者文档；很多竞技游戏设得更低），把“高 ping 不公平”限制在一个范围内。另一个副作用是先手优势（peeker's advantage）：从掩体后探出的人先看到对方（对方看到的是插值后的过去），提高 tick 率、降低插值延迟可以缓解——这是 Valorant 选择 128 tick 服务器的动机之一 Riot 技术博客。

面试注意

“状态同步怎么解决延迟”的标准答案就是三件套：插值（别人）、预测与和解（自己）、延迟补偿（命中）。高频追问：① 插值延迟设多少、为什么（快照间隔 × 2 + 抖动）；② 预测错了怎么办（回到权威状态 + 重放未确认输入，不是直接覆盖）；③ 延迟补偿回溯多少、有什么副作用（RTT + 插值延迟；隔墙杀、先手优势；设上限）。

本章速记
  • 三个时间：别人在 t − (RTT/2 + D)，服务器在 t，自己在 ≈ t + RTT/2。
  • 插值：$D \gtrsim \Delta_{snap}(1+n_{loss}) + J_{p99}$，20 Hz 时约 100 ms；E10：抖动 40 ms 时 D = 100 仍有 [[e10.40_100.ext|.1f]]% 帧外推。
  • 预测 + 和解：输入带序号，服务器回 ack + 权威状态，客户端回到权威状态并重放未确认输入；E11 纠正 [[e11.1.corr|.0f]] → [[e11.2.corr|.0f]] 次。
  • 延迟补偿：回溯 RTT + D；代价是隔墙杀与先手优势，要设上限。带宽：增量 + 量化 + AOI + 优先级 + 休眠。
自测 1：为什么不对其他玩家做预测，而是插值？预测需要知道对方的输入，而对方的输入只有服务器（和对方自己）知道；本地只能猜，猜错就要回滚和跳变。插值只用已经确定的历史快照，永远不会出错，代价是看到的是过去——对“看别人”来说，正确比及时更重要。
自测 2：一个 FPS 服务器 tick 30 Hz、快照 30 Hz，插值延迟大概设多少？快照间隔 33 ms，容忍连丢 1 份需要约 66 ms，再加抖动的高分位（比如 20~30 ms），约 90~100 ms；如果提高到 60 Hz 快照，可以降到 50 ms 左右，先手优势也随之减小。
自测 3：和解时如果服务器的权威位置和预测只差 2 cm，要不要纠正？一般设阈值：差异很小时直接接受（或缓慢平滑过去），避免浮点误差导致每次都纠正；Unreal CMC 就是用位置误差阈值决定服务器要不要发 ClientAdjustPosition（第 13 章）。
