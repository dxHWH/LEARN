CHAPTER 09

回滚网络：把 Lockstep 推到极限

格斗游戏把“等待”逼到了不可接受的地步：一帧 16.7 ms，目押窗口只有一两帧。回滚的答案是“不等了，先猜”——代价是保存每一帧的世界、并随时准备重写过去。

本章目标
  • 写出回滚的核心循环：存快照 → 预测缺失输入 → 推进 → 真值到达 → 回到分歧帧 → 重算到当前帧。
  • 用实测和公式说清“输入延迟 d 与回滚深度”的关系，理解为什么现代格斗游戏用“回滚 + 2~3 帧输入延迟”。
  • 知道回滚的四个代价：画面跳变、音频无法回滚、更严苛的确定性、成倍的 CPU 预算——以及各自的缓解方式。
  • 把回滚思想迁移到状态同步：守望先锋、Rocket League、UE 网络物理、CMC 都在用。
30 秒面试版答案

回滚（Rollback，GGPO 2006 年提出、2019 年以 MIT 协议开源）是 P2P 帧同步的一种：每帧保存游戏状态快照；缺远端输入时先预测（通常重复对方上一帧输入）立即推进，本地操作零等待；远端真实输入到达后若与预测不同，就加载分歧那一帧的快照，用正确输入重算到当前帧，画面瞬间修正。回滚深度约等于“单程延迟 + 抖动”折算的帧数减去输入延迟，所以现代格斗游戏会加 2~3 帧输入延迟，用几十毫秒换回滚深度和跳变的大幅下降。代价：每帧快照与多帧重算（模拟必须远快于一帧）、画面跳变、音效收不回来、对确定性要求更高；而且预测窗口用完之后仍要等待，木桶效应只是被推迟了。适合 2 人、状态小、延迟极敏感的格斗；不适合 10 人、状态大、移动网络的 MOBA。

9.2 核心循环

// 每个渲染帧调用一次；frame = 本地已推进到的帧号，d = 输入延迟（帧） void RollbackTick() { // ① 收网络包：远端第 n 帧的真实输入到达 for (auto& [player, n, input] : net.Receive()) { known[player][n] = input; if (n < frame && used[player][n] != input) // 当时用的是预测值，而且猜错了 firstMismatch = std::min(firstMismatch, n); } // ② 回滚：回到最早的分歧帧，用（新的）最佳输入重算到当前帧 if (firstMismatch < frame) { LoadState(snapshot[firstMismatch]); // 快照保存的是“执行第 n 帧之前”的状态 for (int n = firstMismatch; n < frame; ++n) { snapshot[n] = SaveState(); Simulate(InputsFor(n)); // 已知就用真值，未知仍用预测值 } firstMismatch = INT_MAX; } // ③ 推进：本地输入排到 d 帧之后；预测窗口还没用完就继续往前走 known[me][frame + d] = SampleLocalInput(); if (frame - MinConfirmedFrameOfOthers() > kMaxPrediction) // 窗口用完：只能等（木桶效应回来了） return; snapshot[frame] = SaveState(); Simulate(InputsFor(frame)); // InputsFor：已知用真值，未知用“上一个已知输入” ++frame; net.SendRecentInputs(me, /*带最近若干帧，抗丢包*/ 24); }
GGPO 的 API 长什么样

游戏只需要实现几个回调：save_game_state / load_game_state（快照）、advance_frame（回滚重算时由 GGPO 驱动推进一帧）、free_buffer、on_event；主循环里调 ggpo_add_local_input 提交本地输入、ggpo_synchronize_input 取本帧所有玩家输入（含预测值）、ggpo_advance_frame 通知推进；ggpo_set_frame_delay 设置输入延迟 GGPO 源码。注意 GGPO 完全不关心你的游戏逻辑，它只要求“给定输入就能确定性地推进一帧、并能存取完整状态”——这就是回滚的全部前提。

还有一个容易忽略的机制：时间同步。如果一方的时钟持续领先，它会一直在“预测对方”，对方却一直在“等它的输入”，回滚全落在领先方。GGPO 会估算双方的帧领先量，让领先的一方主动等待几帧，把预测负担平摊到两边 GGPO 源码。

9.3 实测：输入延迟 d 换回滚深度 实测 E9

模型：2 人、60 帧/秒（16.7 ms）、每帧有 20% 概率改变输入（相当于每秒 12 次操作变化），丢包 1%，单程 = RTT/2、指数抖动均值 1 + 0.04·RTT ms；回滚最多预测 8 帧。对每个 RTT 扫描输入延迟 d = 0~4，并对照“不回滚、只靠输入延迟”的纯延迟型。

回滚深度可以这样估算：远端在第 $n-d$ 帧采样的输入要排到第 $n$ 帧执行，送到本地需要单程延迟 $\frac{\mathrm{RTT}}{2}$ 加抖动 $J$；本地执行第 $n$ 帧时它还没到，就只能预测，等它到了再回滚：

为什么不把 d 设得很大、干脆不回滚？因为 d 是所有人的操作都要等的：d = 4 帧就是 67 ms 的固定延迟，对格斗游戏的“目押”是不可接受的。现代格斗游戏的做法是 2~3 帧基础延迟 + 回滚：几十毫秒的延迟在容忍范围内，却把大多数网络下的回滚深度压到 1~3 帧，跳变几乎看不出来 HOK 文档 公开资料。不少游戏还允许玩家在设置里自己调这个值（GGPO 时代起就有）。

9.4 回滚的四个代价

代价表现缓解
画面跳变角色瞬移、已经播出的攻击被“收回”、特效突然消失限制回滚深度；对表现层做位置平滑（逻辑仍然精确）；只在真正分歧时回滚；动画从“重算后的帧”继续播放而不是从头
音频无法回滚该响的没响、不该响的响了、同一音效播两次音频不参与回滚：按 (帧号, 事件 id) 去重，重算时已播过的不再播；预测时播出的错误音效通常只能接受
确定性更严苛同一段帧被反复重算，任何不确定都会暴露成“回滚后对不上”定点数、确定性随机、状态完整序列化（漏存一个变量 = 重算结果错）
CPU 预算成倍深度 D 时一个渲染帧里要模拟 D + 1 帧见下面的预算推导；状态要小、模拟要快

实测里 RTT 160 ms、d = 0 时每秒要额外重算 [[e9.160_0.resim|.0f]] 帧，相当于在 60 帧/秒之外又多跑了 [[e9.160_0.resim|.0f]] 帧的逻辑；d = 2 时降到 [[e9.160_2.resim|.0f]] 帧。输入延迟不仅减少跳变，也直接降低 CPU 负担。

9.5 回滚在状态同步里的化身

“保存历史 → 回到分歧点 → 用正确数据重算”并不是帧同步独有的。状态同步里只要做了客户端预测，就一定有它：

系统回滚的范围“真值”从哪来来源
GGPO / 格斗游戏整个游戏状态远端玩家的真实输入GGPO
Unreal CMC只回滚本地角色的移动服务器发回的权威位置（ClientAdjustPosition），然后重放未确认的 SavedMovesUE 源码（第 13 章）
守望先锋本地玩家相关的、由输入驱动的 System 状态服务器对这些命令帧的权威结果GDC 2017
Rocket League车与球的物理状态服务器物理状态；客户端回滚后重新模拟GDC 2018
UE 网络物理（Resimulation）物理对象服务器状态与本地历史不一致超过阈值时触发重模拟；NetworkPhysicsComponent 负责输入 / 状态历史UE 文档（5.4 起，Resimulation 为实验性）

区别在于“真值”：帧同步回滚等的是别人的输入，状态同步预测等的是服务器的结果。但数据结构完全一样：一个按帧（或时间戳）索引的历史环形缓冲 + 一个“从某帧开始重算”的函数。理解了这一点，第 10、13 章的“预测与和解”就只是换了个名字。

面试注意

被问“王者荣耀为什么不用回滚”时，从回滚的四个前提逐条对照：人数（2 vs 10）、状态规模（快照成本）、每帧重算成本（CPU 预算推导）、网络环境（移动网络抖动会让回滚持续触发、画面持续抽动）。再补一句“回滚并没有消灭木桶效应，只是推迟到超过预测窗口才暴露”，这道题就答满了。

9.6 坑位

坑后果修正
快照漏存某个状态（如随机数生成器、技能冷却的小数部分）回滚后与对方对不上 → desync状态集中管理（ECS / 单块内存），整体拷贝；回归测试：每帧都强制回滚一次再比对 hash（同步测试模式）
表现层在预测帧里触发了不可撤销的事件（成就、结算、网络请求）“幽灵事件”不可撤销的副作用只在确认帧（所有人的输入都已知）上触发
输入延迟 d = 0回滚频繁且深、CPU 吃紧2~3 帧基础延迟，或按网络动态调整
不做时间同步一方长期领先，回滚全落在它身上估算帧领先量，领先方等待
预测策略过于“聪明”猜错时跳变更大最常用的仍是“重复上一个输入”，简单且错误代价可控
本章速记
  • 回滚 = 每帧快照 + 预测缺失输入 + 真值不符时加载分歧帧快照重算到当前；GGPO 2006 年提出、2019 年 MIT 开源。
  • 深度 $\approx (\mathrm{RTT}/2+J)/T - d + 1$：每加 1 帧输入延迟深度少约 1 帧；回滚次数 ≈ 对方输入变化频率。
  • 四个代价：跳变、音频、确定性 + 完整序列化、CPU（$t_{sim} \le (T - t_{render})/(D+1)$，60 fps 回滚 8 帧时约 1 ms）。
  • 预测窗口用完仍要等；同样的“历史 + 重算”结构就是 CMC / 守望先锋 / Rocket League / UE 网络物理的预测和解。
自测 1：回滚的“同步测试模式”（sync test）是什么？为什么有用？单机运行时，每一帧都强制回滚若干帧再重算，比较重算前后的状态 hash；只要快照漏存了任何状态或有不确定性，hash 立刻对不上。它把“联网偶发 desync”变成了“单机必现的断言失败”，是回滚项目最重要的回归测试。
自测 2：RTT 120 ms、60 帧/秒、d = 2，估算平均回滚深度。(60 + 约 6 ms 抖动)/16.7 ≈ 3.95，减 d 得 1.95，再加 1 帧离散化误差 ≈ 3；实测 [[e9.120_2.depth|.2f]]。
自测 3：为什么说 CMC 的“纠正后重放 SavedMoves”就是回滚？客户端保存了每一步移动（输入 + 时间戳），服务器发回某个时间戳的权威位置后，客户端把角色设到那个位置（相当于加载快照），再把之后所有未确认的移动重新执行一遍（相当于重算）。区别只是范围只有本地角色、真值来自服务器而不是远端输入。
