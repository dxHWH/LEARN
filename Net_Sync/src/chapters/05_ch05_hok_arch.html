CHAPTER 05

HOK 架构：三层分工与逻辑表现分离

C# 懂协议、懂表现，但对战斗一无所知；C++ 懂战斗，但不碰引擎、不收网络包。这条窄边界是整套帧同步能够长期维护的根本。

本章目标
  • 画出 HOK 的三层架构（表现层 C# / 逻辑层 C++ GameCore / Relay 服务器），说清每层“不做什么”。
  • 理解一条命令的三条命运：OnReceive 立即交付逻辑、ExecLocal 延迟表现、以及真正承载战斗表现的“结果事件”。
  • 按顺序说出客户端主循环的七个阶段，以及“收在帧首、发在帧末”的原因。
  • 理解 C# ⇄ C++ 共享内存 FIFO 的“预留 → 写入 → 提交”，以及单帧限流与延迟队列。
  • 把这套分层与 Unreal（GAS 的 GameplayCue）、守望先锋（ECS）的同类设计对照起来。
30 秒面试版答案

HOK 分三层：Unity C# 只做输入采集、收发包、协议编解码和表现播放；独立的 C++ GameCore 做确定性战斗模拟（定点数、帧随机、单线程），不依赖引擎；Relay 服务器做帧号分配、汇总去重、定频广播和历史缓存。解出一条帧命令后立即写进 C++ 的共享内存（逻辑必须准点），表现另走一条路：战斗表现不是“收到命令就播”，而是 C++ 算完这一帧后把命中、伤害、死亡等结果事件推回 C#，由 AGE 时间轴系统执行；不依赖结果的反馈（技能指示器）在按键时就本地响应。帧号由 C++ 回报，C# 被逻辑拖着走，所以表现天然与逻辑同步。C# 与 C++ 之间是共享内存上的 FIFO 字节流，零序列化，单帧限流 1000 条防止卡顿雪崩。

5.1 三层全景

把战斗逻辑放进独立 C++ 层的四个收益：① 确定性（脱离引擎浮点、调度、容器）；② 可脱离 Unity 单独运行（服务器、自动化测试、录像校验都能跑）；③ 服务器复用同一份代码（CC / CS 双模式，第 8 章）；④ 性能可控（大批单位演算）。

5.2 一条命令的三条命运

逻辑（路径 ①）命令表现（路径 ②）结果表现（路径 ③）
对时间的要求必须精确落在第 N 帧大致跟上即可跟着演算结果走
能否等待 / 乱序都不能都可以可以延迟、可以限流
依赖演算结果—不依赖完全依赖
例子位移、技能、伤害结算移除“等待服务器确认”的超时定时器、聊天输入框开关命中特效、伤害飘字、死亡、音效
占比全部命令很小（多数为空）绝大部分战斗表现

一个佐证：早期版本里“技能指示器显示 / 关闭”写在命令的 ExecLocal 里，后来被挪到了输入处——玩家一按键指示器就本地响应，根本不等帧回来 HOK 文档。这就是预表现：不依赖演算结果的反馈，一律按键即响应；依赖结果的（中没中、扣多少），老实等 C++ 通知。

对照 Unreal：GameplayCue 是同一个思想

GAS 把“逻辑效果”（GameplayEffect 改属性）和“表现”（GameplayCue：粒子、音效、镜头抖动）严格分开：Cue 由效果的执行 / 添加 / 移除触发，在各端本地执行，可以走不可靠多播、可以被本地预测、丢了也不影响逻辑 UE 文档。同样是“逻辑定义发生了什么，表现决定长什么样”。区别只在于 UE 的逻辑结果来自服务器复制，HOK 的来自本地确定性演算。

AGE：控制权在 C++，执行在 C#

AGE 是 HOK 的表现时间轴系统：一次技能编排成一条时间轴，挂着“持续段”和“瞬时事件”（播动画、触发粒子、震屏、改材质、切镜头、刷 HUD）。C++ 持有时间轴和帧同步时钟，进入 / 离开某段、变速时通过 cpp2cs 共享内存发出 NtfAgePlayAnimDurEnter / Leave / SpeedModified 等指令；C# 侧数十种 AGEWrapXxx 只负责实例化、按帧推进、收到结束指令后销毁。wrapper 的 id 由逻辑层的演出序号 + 类型编号组成，局内不存在 C# 自行读演出文件播放的路径 HOK 文档。代码量大说明“执行复杂”，不说明“控制权在 C#”。

5.3 帧号由谁说了算

客户端逻辑帧率可以高于服务器广播帧率（例如服务器 15 帧/秒、客户端 30 帧/秒），帧号按 $\text{客户端帧号} = \text{服务器帧号} \times \frac{\text{服务器帧间隔}}{\text{客户端帧间隔}}$ 换算，表现插值发生在多出来的帧里。

5.5 C# 与 C++ 如何对话：共享内存上的 FIFO

两层之间既不是普通的跨语言函数调用，也不是操作系统的管道，而是“用共享内存实现的 FIFO 字节流”：一次通信只有“取指针 + 写内存 + 提交游标”，没有序列化、系统调用和内核拷贝，成本是纳秒级 HOK 文档。

// 单生产者（C#）/ 单消费者（C++ 逻辑层）的追加式字节流 struct CmdStream { uint8_t* buf; uint32_t cap; uint32_t write = 0; // 已提交的写游标：消费者只看得到 [read, write) uint32_t pending = 0; // 预留但尚未提交的位置 uint32_t read = 0; void* Reserve(uint32_t n) { // ① 预留 n 字节，返回裸指针 if (pending + n > cap) Grow(pending + n); void* p = buf + pending; pending += n; return p; } void Commit() { write = pending; } // ③ 提交：这一批数据对逻辑层“原子地”生效 template void Drain(F&& exec) { // 逻辑层推进时按顺序取出执行 while (read < write) { uint32_t fn; memcpy(&fn, buf + read, 4); // 4 字节函数编号 read += 4 + exec(fn, buf + read + 4); // exec 返回参数长度 } read = write = pending = 0; // 本帧取空后复位 } void Grow(uint32_t need); }; // C# 侧：p = Reserve(4 + sizeof(Args)); *(int*)p = FN_MOVE; *(Args*)(p+4) = args; // ② 不安全指针直接写 // ... 一帧所有命令写完 → Commit()
通道承载本地模式服务器（CS）模式
主逻辑通道逻辑层调用与事件共享内存本地攒批（约 2 KB 或帧末）→ CSID_GAMECORE_CLT_INPUTMSG 网络包
轻量逻辑通道轻量逻辑调用共享内存共享内存
表现通道表现插值数据独立的“表现缓冲区”同左
反向（C++ → C#）结果事件C# 启动时分配约 1 MB 非托管缓冲，每帧把地址交给 C++，C++ 直接填；填满则 C# 容量翻倍再拉，直到取空

两个保护 HOK 文档：

  • 单帧限流：反向通道每帧最多处理 1000 条（服务器可配），超出留到下一帧——避免“事件多 → 这帧卡 → 下帧事件更多”的恶性循环。
  • 延迟队列：标记为“可以晚点处理”的事件进入独立的约 512 KB 缓冲错峰消费。

另有一条同步立即通道（C++ 直接回调 C#），只用于极少数必须立即得到结果的场景，并有明确约束（跨线程同步回调在部分编译后端有性能代价）。

发散：守望先锋的 ECS 与“确定性子集”

守望先锋（GDC 2017《Overwatch Gameplay Architecture and Netcode》）是状态同步，但同样把“需要按输入预测的系统”和“纯表现系统”分开：需要预测的 System 不用 Update 而用 UpdateFixed，在固定的 16 ms 命令帧上运行（比赛服 7 ms），这部分逻辑在客户端和服务器上用同一份代码、同一组输入演算，所以能在客户端预测、出错时回滚重放 GDC 2017。HOK 是把整个战斗做成确定性子集，守望先锋是只把本地玩家相关的那部分做成确定性子集——这是理解第 13 章 CMC 的钥匙。

面试注意

被问“帧同步里逻辑和表现怎么分离”，要答出三点：① 逻辑层独立（不依赖引擎，保证确定性）；② 表现由演算结果驱动，而不是由输入命令驱动（否则会出现“特效播了但其实没打中”）；③ 不依赖结果的反馈做预表现（按键即响应）。能补一句“表现可以限流、可以晚到，逻辑不行”就很完整了。

本章速记
  • 三层：C#（输入 / 网络 / 表现，不做战斗判断）· C++ GameCore（确定性模拟，不碰引擎）· Relay（定序与可靠投递，不做战斗逻辑）。
  • 三条命运：OnReceive 立即入逻辑、ExecLocal 延迟表现（多数为空）、结果事件驱动战斗表现（AGE：C++ 决策、C# 执行）。
  • 帧号被 C++ 拖着走；七阶段：输入 → 抽干收包 → 窗口维护 → 推进 → 反向通知（限流）→ CS 流 → 帧同步器；帧末统一发包。
  • C# ⇄ C++：共享内存 FIFO，预留 → 写入 → 提交；同一接口在 CS 模式下换成网络包。
自测 1：为什么技能指示器可以按键即显示，而伤害飘字必须等 C++？指示器不依赖演算结果（只表达“我想放这个技能”），伤害飘字依赖演算结果（中没中、扣多少只有 C++ 演算完才知道）。依赖结果的表现如果提前播，就可能和十端一致的逻辑结果矛盾。
自测 2：反向通道为什么要限流？不限流会怎样？团战大招时一帧可能产生几千条事件，一次全处理会让这一渲染帧特别长；而这一帧越长，下一帧要处理的网络包和事件越多，形成雪崩。限流把峰值摊到多帧，代价是部分表现晚几帧出现——表现可以晚，逻辑不受影响。
自测 3：GameplayCue 和 HOK 的结果事件有什么相同点和不同点？相同：都由逻辑结果触发、只负责表现、可以丢失或延迟而不影响逻辑。不同：GameplayCue 的触发源是服务器复制下来的 GE 状态或预测，HOK 结果事件的触发源是本地确定性演算；GAS 还允许 Cue 被本地预测，预测失败时要撤销。
