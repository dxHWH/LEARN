CHAPTER 11

Unreal 网络架构与复制管线

Unreal 的复制系统回答的是一个调度问题：每个服务器 tick、每条连接、成百上千个 Actor，带宽有限，先发谁、发什么、发给谁。

本章目标
  • 画出 NetDriver / NetConnection / Channel / PackageMap 的结构，说清 Bunch、可靠性在哪一层实现。
  • 熟练回答 NetMode、Role / RemoteRole、所有权（Owner → PlayerController → Connection）三组概念，以及 Gameplay 框架各类存在于哪一端。
  • 按顺序讲出 ServerReplicateActors 的流程：频率门控 → 休眠 → 相关性 → 优先级排序 → 饱和截断。
  • 用实测理解“优先级 × 等待时间”为什么能避免饿死；知道 Replication Graph 和 Iris 分别解决了什么。
30 秒面试版答案

Unreal 默认是服务器权威的状态同步。服务器的 NetDriver 为每个客户端维护一个 NetConnection，连接里有控制通道和每个复制 Actor 一条 ActorChannel；数据以 Bunch 为单位打进 UDP 包，可靠 Bunch 由通道负责重传和排序，对象引用靠 PackageMap 把 UObject 映射成 NetGUID。每个 Actor 在各端有 Role：服务器上是 Authority，拥有它的客户端上可以是 AutonomousProxy（本地控制、做预测），其他客户端上是 SimulatedProxy（插值播放）。所有权沿 Owner 链找到 PlayerController，进而确定连接——Server RPC 只能从拥有者连接发起。每个网络 tick，服务器对需要复制的 Actor 做：按 NetUpdateFrequency 门控、跳过休眠、按连接判相关性、按“NetPriority × 距上次复制时间”（再按距离和视野加权）排序、依次复制直到带宽饱和，没发出去的下一 tick 优先级更高。大规模用 Replication Graph 把相关性做成空间网格等节点，UE5 的新复制系统 Iris 把过滤、优先级改成显式 API，并与游戏线程数据解耦以并行化。

11.2 NetMode、Role 与所有权

NetMode含义
NM_Standalone单机，不联网（同时是“服务器”和“客户端”）
NM_DedicatedServer专用服务器：无本地玩家、不渲染
NM_ListenServer主机：既是服务器又有一个本地玩家（主机玩家没有延迟，存在主机优势）
NM_Client连接到服务器的客户端
Role（GetLocalRole()）出现在哪该做什么
ROLE_Authority服务器上的所有 Actor；客户端本地生成、不复制的 Actor 也是跑权威逻辑、改复制属性、发 Client / Multicast RPC
ROLE_AutonomousProxy拥有它的客户端上（被本地 PlayerController 控制的 Pawn、PlayerController 自己）采集输入、本地预测、发 Server RPC
ROLE_SimulatedProxy其他客户端上插值 / 平滑播放，不做权威判断
ROLE_None不复制的对象—

服务器上 Pawn 的 RemoteRole 是 AutonomousProxy，但复制给非拥有者连接时会被降级为 SimulatedProxy——同一个 Actor 在不同客户端上的 Role 不同 UE 文档。所有权：沿 GetOwner() 链一路往上找到 PlayerController，它的 NetConnection 就是这个 Actor 的“拥有者连接”。它决定了三件事：Server RPC 能否发出（只有拥有者客户端能对该 Actor 调用 Server RPC）、COND_OwnerOnly 等条件复制发给谁、bOnlyRelevantToOwner 的 Actor 复制给谁。

11.4 实测：带宽饱和时先发谁 实测 E13

模型：30 Hz 网络 tick，每 tick 预算 1200 B；10 个英雄（优先级 3、希望 100 Hz、每次 60 B）、20 个投射物（2、30 Hz、30 B）、100 个可拾取物 / 机关（1、10 Hz、20 B）、10 个 PlayerState（1、1 Hz、40 B）。总需求明显超出预算。三种调度：UE 式（优先级 × 距上次发送时间）、静态优先级（永远先发优先级高的）、轮询。

“优先级 × 等待时间”的本质

它是老化（aging）调度：一个对象越久没被服务，分数就线性增长，迟早会超过任何高优先级对象，所以不会饿死；而高优先级对象的分数涨得更快，所以平均更新更勤。操作系统的进程调度、网络的加权公平队列都是同一类思想。HOK 的帧同步里没有这个问题——它每帧只发输入，不需要在对象之间分配带宽。

11.5 规模化：Replication Graph 与 Iris

传统 ServerReplicateActorsReplication GraphIris
相关性计算每个 Actor × 每个连接调用 IsNetRelevantFor（虚函数）Actor 按类路由到节点（空间网格 GridSpatialization2D、总是相关、按连接总是相关……），每个连接直接从节点收集列表，结果可跨连接复用过滤器（Filter）API：NetObjectFilter、网格过滤器等，替代 IsNetRelevantFor

RPC 与属性顺序没有固定保证同左RPC 默认在同一连接的状态数据之后发送
适用中小规模大世界、大逃杀（Fortnite 使用）新一代系统；与 Replication Graph 不兼容
状态默认插件，生产可用UE 5.1 引入，截至 5.6 官方文档仍标注为 Experimental

Iris、Mover、网络物理都是 UE5 中仍在快速演进的系统，面试时说“我了解它们的设计目标和当前状态（实验性 / Beta），生产项目仍以传统复制 + CMC 为主”比背 API 更稳妥。引用版本号时说清楚“截至我看的 5.x 文档”。

面试注意

高频题：“Role 有哪几种、AutonomousProxy 和 SimulatedProxy 区别”“为什么客户端调 Server RPC 没反应”（Actor 不归这个客户端所有，比如对场景里的门直接调 Server RPC——要通过自己的 PlayerController / Pawn 转发）“NetUpdateFrequency 和 tick 什么关系”（门控上限，实际还受 NetServerMaxTickRate 和带宽限制）“带宽不够怎么办”（相关性、休眠、频率、优先级、量化、Replication Graph）。

11.6 坑位

坑后果修正
对不归自己所有的 Actor 调 Server RPCRPC 被丢弃，日志里有“No owning connection”类警告经 PlayerController / 自己的 Pawn 转发，或设置 Owner
在客户端读 GameMode空指针需要客户端可见的数据放 GameState / PlayerState
PlayerState 上挂了频繁变化的数据却没调频率更新明显滞后调高 NetUpdateFrequency 或改用 ForceNetUpdate
大量静止 Actor 不休眠服务器每 tick 白白检查DORM_Initial / DormantAll，改变前 Flush
bAlwaysRelevant 滥用大世界里带宽爆炸用距离 / 队伍 / Replication Graph 节点控制
依赖“属性先到、RPC 后到”传统复制下顺序不保证，偶发空引用RPC 里带上需要的数据，或在 OnRep 中处理
本章速记
  • NetDriver → NetConnection（每客户端）→ Control / Actor 通道；Bunch 级可靠性；PackageMap 映射 NetGUID；FRepLayout + 影子状态做增量。
  • Role：Authority / AutonomousProxy / SimulatedProxy；所有权沿 Owner 链找 PlayerController → 连接，决定 Server RPC 与 OwnerOnly 复制。
  • 管线：频率门控 → PreReplication → 相关性 → 休眠 → 优先级（NetPriority × 等待时间，距离 / 视野加权）→ 复制变化属性 → 饱和停止。
  • E13：静态优先级会饿死低优先级对象，老化调度不会；规模化用 Replication Graph，新一代 Iris（5.1 引入、仍为实验性）。
自测 1：Listen Server 上，主机玩家的 Pawn 的 Role 是什么？客户端玩家的 Pawn 在主机上是什么？在主机（服务器）进程里两者的 LocalRole 都是 Authority。区别在 RemoteRole 和“是否本地控制”：主机玩家的 Pawn IsLocallyControlled() 为真；客户端玩家的 Pawn 在主机上 RemoteRole 是 AutonomousProxy（复制给它的拥有者时），复制给其他客户端时是 SimulatedProxy。
自测 2：一个 Actor 的 NetUpdateFrequency 设成 200，服务器 tick 30 Hz，它每秒最多复制几次？最多约 30 次——NetUpdateFrequency 只是“允许检查的上限”，复制发生在网络 tick 里，而网络 tick 受 NetServerMaxTickRate 限制；另外还要过相关性、优先级和带宽这几关。
自测 3：为什么 Replication Graph 能比传统方式快很多？传统方式对每个连接、每个 Actor 都调用一次相关性和优先级虚函数，复杂度约 O(连接数 × Actor 数)；Replication Graph 把 Actor 预先放进节点（如空间网格单元），每个连接只需收集自己所在单元及周边的列表，而且同一份列表可以被多个连接复用。
