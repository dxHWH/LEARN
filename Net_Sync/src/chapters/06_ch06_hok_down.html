CHAPTER 06

HOK 下行：冗余广播、900 帧窗口、补发与追帧

“不等人”把丢包的代价全部留给了丢包者，所以下行需要一整套让丢包者自救的机制：冗余能补的冗余补，冗余补不了的主动要，要不回来的整段追。

本章目标
  • 说清下行三层兜底的分工边界：丢帧 ≤ k 靠冗余，k < 丢帧 < 900 靠补发，超窗或断线靠 Recover。
  • 理解冗余帧为什么“倒序 + 命中即截断”，并用实测和闭式解回答“一包带几帧够用”——尤其是突发丢包下为什么冗余会失灵。
  • 能手画 900 帧接收窗口的状态变化：入窗即消费、找洞、区间合并请求、超窗转 Recover。
  • 按时序讲完 Recover：问大厅 → 重连 Relay → 拉缓存分片 → 回放 → 追帧 → 上报完成；以及两层缓存、快速恢复。
30 秒面试版答案

下行三层兜底：第一层，服务器每个广播包都带最近 k 帧（倒序排列，客户端从新往旧解，遇到已处理的帧就停，平时只解一帧），挡住零散丢包；第二层，客户端 900 帧循环接收窗口发现“期待帧缺失但后面的帧已到”或 90 ms 没推进，就把缺失帧合并成区间请求补发（1036），请求频率两级：卡顿初期约 120 ms 一次，持续卡顿降到约 1000 ms 一次防请求风暴；第三层，帧号超出窗口或断线重连，走 Recover：先问大厅“我还在局里吗”，重连 Relay 后用 1090 请求缓存帧、1091 分片返回，顺序回放，缺口小于 15 帧算追上，上报 1093。补发回来的帧和正常帧走完全相同的路径，客户端不需要特殊逻辑。

6.2 第一层：一包多帧的冗余广播

服务器广播第 N 帧时，同一个 SCID_FRAPBOOTINFO(1035) 包里还带着 N−1、N−2…N−k+1 帧，于是同一帧会在连续 k 个包里重复出现。包内按从新到旧排列，客户端从最新帧开始遍历，遇到已经处理过的帧就立即停止解包 HOK 文档：

void OnFramePacket(const FramePkt& pkt) { // pkt.frames[0] 是最新帧，越往后越旧 for (const FrameInfo& f : pkt.frames) { if (f.no < window.beg || window.Has(f.no)) // 已经消费过 / 已在窗口里 break; // 更旧的必然也处理过 → 停止解包 window.Put(f); // 解包、入窗 } window.ConsumeContiguous(); // 入窗即消费（第 6.3 节） } // 不丢包时，每个包只解第一帧；只有真丢了包，才会往旧帧多解几帧。 // 如果冗余帧是正序排列的，这个 break 就不成立了——所以工程注释特意强调“必须倒序”。

一包带几帧够用？实测 + 闭式解 实测 E5

“需要补发”等价于“某一帧所在的连续 k 个包全丢了”。在两种丢包模型下仿真 40 万个包：

  • 随机丢包：每个包独立地以概率 $p$ 丢失，k 个全丢的概率是 $p^k$。
  • 突发丢包（Gilbert-Elliott 两状态模型）：好状态不丢、坏状态全丢，平均丢包率 $p$，平均连丢长度 $L$。移动网络、Wi-Fi 切换、基站切换都属于这一类。

结论：冗余是对付零散丢包的利器，对付突发丢包几乎无效。HOK 的 k 由服务器配置，配合“补发 + 追帧”兜底，而不是靠无限加大 k——k 每多 1 帧，每个下行包都要多带一帧的字节，而突发丢包时收益却只有 25%。

6.3 第二层的舞台：900 帧接收窗口

客户端维护一个长度 900（约 60 秒）的循环数组 _receiveWindow，用 下标 = (帧号 − _basFrqNo) % 900 映射，数组不移动、只滚动基址 HOK 文档：

变量含义
_begFrqNo期待帧：下一个必须处理的帧号；同时写进每个上行包头，充当上行 ACK
_maxFrqNo已收到的最大帧号
_basFrqNo循环数组基址（帧号 → 下标换算）
FRQ_WIN_LEN窗口长度，固定 900

收到帧号 $f$ 的三种命运：$f \lt \text{beg}$ → 已过期，丢弃；$\text{beg} \le f \lt \text{beg}+900$ → 入窗，然后立刻从期待帧开始连续出窗、交付逻辑层，直到遇到空洞；$f \ge \text{beg}+900$ → 中间有洞且超出窗口，转 Recover。每帧一次的“帧窗口维护”（主循环 ③）不消费帧，只做三件事：找洞决定是否补发、判断是否超时未推进、更新卡顿状态机——“入窗即消费，维护只管找洞、要洞、记账”。

补发的触发、请求与记账

要点内容 HOK 文档
空洞判定_receiveWindow[beg] == null 且 _maxFrqNo > beg 且 _maxFrqNo < beg + 900（第三条不满足就该走 Recover）
触发一：快速补洞事件驱动：后面的帧到了、期待帧还缺 → 立即请求；有最小请求间隔做节流（后续包可能马上就到）
触发二：超时补发距上次成功推进超过 90 ms → 请求“之后的都给我”；频率两级：卡顿初期约 120 ms 一次，超过紧急时长后约 1000 ms 一次
请求内容扫描 [beg, min(max+1, beg+900))，把连续缺失合并成区间；区间数有上限，最后一个区间留给“窗口之外”，用 −1 作区间尾表示开放区间
补回的帧仍用 1035 返回，照常入窗、出窗、交付——客户端没有任何“补发帧专用”逻辑
两次记账请求时记“区间 + 时刻”，该区间的帧真正渲染出来后再记一次耗时——把“等网络补帧”和“本机处理慢”分开度量
为什么补发请求要降频？

持续卡顿通常意味着链路已经拥塞或断开。此时每 120 ms 发一次请求，请求本身就会和下行抢带宽，服务器每收到一次还要回一大段帧——“越卡越请求，越请求越卡”。两级频率是典型的退避（backoff）思想。第 3 章 E3 实测里，断流者在 2 秒断流窗口内卡了 [[e3.relay.bfzIn|.0f]] ms，多出来的几百毫秒正是退避的代价：用恢复速度换系统稳定。

6.4 从帧数据到逻辑推进

一帧 1035 的 payload 是这一帧内所有参与者的操作集合，分四类 HOK 文档：

类型含义例子
CC客户端之间同步的通用帧命令复杂操作、状态同步
CS需要经过服务器处理的帧命令技能释放、普攻、学技能、买卖装备
SC服务器主动下发的帧命令出生、传送、PVE 对象通知
通知类非玩家操作的服务器通知游戏结束、暂停、投降、掉线 / 重连、AI 接管

分派用“启动期反射注册 + 运行期查表”：启动时扫描带标注的命令类型和构造器，按编号注册；运行期按编号造命令对象（来自对象池，避免 GC），填入帧号与玩家标识，推入帧同步器：立即 OnReceive 交付逻辑层，同时排队等表现到期；一帧全部交付后才授权推进。消费每一帧时顺手做两件事：写入录像缓冲；记录已处理的数据长度（断线重连时“从哪补起”）。

实践中的坑（来自原文档）

协议处理函数的注册需要“类型被登记进列表”和“方法带协议标注”两个条件同时满足；只加标注、忘了登记类型，处理函数永远不会被调用，而且不报错。反射注册的好处是新增命令不改分派代码，坏处就是这种静默失败——建议启动时打印注册表并做自检。

6.5 第三层：Recover 追帧与断线重连

两种情况必须向服务器索取一段历史：帧号超出窗口（本地落后太多，旧数据已被循环覆盖），以及断线后重连。本质相同：缺失帧数超过了本地窗口能容纳的范围。

缓冲层次存什么
m_laterPkgListUDP 包层面追帧期间到达、尚未处理的完整网络包；追帧结束后统一走正常分发
_receiveWindow帧信息层面帧数据，无论来自实时包还是历史回放

两者不是“两个缓存”，而是两个不同的抽象层：历史回放往帧窗口里填，实时包在包层面排队，互不干扰。另外，收包后、分发前有一道重连闸门：处于恢复流程时，包被扣下暂存，等历史帧回放完再处理。

快速恢复是一个激进但有效的优化：追帧期间，反向通道只放行“帧推进通知”，特效、音效、UI 等事件全部跳过——追帧的唯一目标是让逻辑帧尽快跑上去，此时的表现毫无意义（甚至会特效刷屏）。代价是追帧期间画面朴素，换来更短的黑屏 HOK 文档。这再次体现了第 5 章逻辑表现分离的价值：如果表现与逻辑耦合，这个开关根本做不出来。

追帧要多久？一个估算 推断

设断线 $T_d$ 秒，逻辑帧率 $f=15$，本机全速演算（跳过表现）的速度是 $s$ 倍实时。追帧期间对局仍在推进，所以追上需要满足 $s \cdot t = f T_d + f t$，即 $t = \dfrac{T_d}{s-1}$。断线 30 秒、全速 20 倍实时时约 1.6 秒；如果不跳过表现、只能跑 3 倍实时，就要 15 秒——这就是快速恢复的意义。帧同步录像的“快进”、观战的“追直播”是同一个公式。

本章速记
  • 三层：冗余（n ≤ k）→ 补发 1036（k < n < 900）→ Recover 1090/1091/1093（超窗 / 断线）。
  • 冗余倒序 + 命中即截断；随机丢包 $p^k$，突发丢包 $p(1-1/L)^{k-1}$——k=8 时突发 5% 仍有 [[e5.tab.7.g5|.1%]] 需补发。
  • 窗口：900 槽循环数组，期待帧兼作上行 ACK；入窗即消费；维护只找洞、要洞、记账；区间合并 + 末区间 −1 开放。
  • 补发两级频率（≈120 ms / ≈1000 ms）；Recover 三态 + 两层缓存 + 快速恢复只放行帧推进通知。
自测 1：为什么期待帧号可以当 ACK 用？期待帧 = 已经连续处理到的最后一帧 + 1，它单调递增，且隐含“之前的帧全收到了”。服务器拿到它就知道该客户端的进度，可以据此决定补发什么，不需要额外的确认协议——和 TCP 的累积确认是同一个思想。
自测 2：补发请求的最后一个区间为什么要留给“窗口之外”？补发请求有区间数上限，窗口内的洞可能很多；如果把名额都给了窗口内的洞，“我已经落后太多、窗口外还缺”的需求就无法表达。用 −1 作区间尾表示“从这里开始之后能给的都给我”，一个区间就能覆盖。
自测 3：断线 10 秒和断线 3 分钟，恢复过程有什么不同？10 秒（150 帧）仍在 900 帧窗口内，理论上补发就能救回；3 分钟（2700 帧）超出窗口，必须走 Recover 拉服务器缓存整段回放，并且追帧期间对局继续推进，需要靠跳过表现提高回放速度。两者都要先过连接层的退避重连。
