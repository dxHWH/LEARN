第一部分　骨骼与动画数据

动画系统的输入是什么：骨骼怎么存、姿势怎么表示、空间怎么换算，网格怎么跟着骨骼动，动画数据怎么压到几十 KB。

1.1 资产关系：一切围绕 Skeleton

  • USkeleton：骨骼名和父子关系（FReferenceSkeleton）、插槽（Socket）、虚拟骨骼、动画曲线名、Slot 组、同步标记名、重定向设置。它是一套“命名约定”，动画数据按骨骼名对上号。
  • USkeletalMesh：可见的网格。每个顶点有若干骨骼影响和权重；自己也存一份参考骨骼（可以比 Skeleton 少骨骼，但必须是它的子集，层级一致）。
  • UAnimSequence：一条动画。每根有动画的骨骼一条轨道（旋转 / 平移 / 缩放），另外还有曲线、Notify、同步标记、Root Motion 设置、加性设置、压缩设置。
  • SkeletalMeshComponent：运行时把 Mesh 和动画实例（AnimClass 指定的动画蓝图）组合起来，每帧拿到姿势、算蒙皮矩阵、交给渲染。
游戏客户端实战：换装为什么能共享动画

角色换装的常见做法是：身体、头、衣服是同一 Skeleton 的多个 SkeletalMesh。主 Mesh 跑动画蓝图，其余部件用 Leader Pose Component（UE 5.1 之前叫 Master Pose）直接复用主 Mesh 的骨骼变换，不再各自求值（第 9 章）。部件骨骼必须是主骨架的子集且名字一致，否则对不上。

1.2 骨骼怎么存：数组 + 父下标，按拓扑序

UE 不用指针树存骨骼，而是用一个数组：每根骨骼存名字和父骨骼下标（FMeshBoneInfo{Name, ParentIndex}），并且保证父骨骼的下标一定小于子骨骼（拓扑序）。参考姿势 RefBonePose 是同样长度的局部变换数组。

拓扑序带来三个好处：

  1. FK 只需一个 for 循环，不需要递归，也不需要访问标记；数据是连续数组，缓存友好。
  2. 任意“前缀”或“保持顺序的子集”仍是合法骨架。LOD 减骨、只算必需骨骼（Required Bones）时，把下标数组过滤一遍就行。
  3. 父子关系判断很便宜：沿 ParentIndex 往上走，下标单调递减，一定会终止。

三套骨骼下标：面试时很容易被问晕

下标相对谁用在哪
Skeleton Bone IndexUSkeleton 的骨骼数组动画序列的轨道按它（经映射表）对应骨骼
Mesh Bone IndexUSkeletalMesh 自己的参考骨骼蒙皮、Socket、物理资产；Mesh 可能比 Skeleton 少骨骼
Compact Pose Bone Index本帧实际需要计算的骨骼（FBoneContainer 的 RequiredBones）AnimGraph 求值时的 FCompactPose；随 LOD 变化
面试注意：写自定义动画节点时的经典 bug

在 Evaluate_AnyThread 里拿到的是 FCompactPose，下标是 FCompactPoseBoneIndex。如果直接用 Skeleton 或 Mesh 的骨骼下标去取，切 LOD 后骨骼变少，就会取错骨骼甚至越界。正确做法是在 CacheBones_AnyThread 里用 FBoneReference::Initialize(RequiredBones) 预先解析，求值时调用 GetCompactPoseIndex，并检查是否有效（这根骨骼在当前 LOD 可能被剔掉了）。

1.3 三种空间与 FK

空间相对于谁在用
局部空间（Local / Bone / Parent Space）父骨骼动画序列存的就是它；大部分混合在这里做
组件空间（Component / Mesh Space）SkeletalMeshComponent 的原点IK、Look At、Mesh Space 混合、蒙皮矩阵
世界空间（World Space）世界原点Socket 挂武器、射线检测、脚 IK 的地面高度

UE 的 FTransform 是“旋转（四元数）+ 平移 + 三维缩放”，乘法 A * B 的含义是先应用 A，再应用 B。于是组件空间变换就是：

// 与 FCSPose::CalculateComponentSpaceTransform 的语义一致 // 骨骼按拓扑序存放：处理 i 时，Parent[i] 一定已经算完 ComponentSpace[0] = LocalSpace[0]; for (int32 i = 1; i < NumBones; ++i) { ComponentSpace[i] = LocalSpace[i] * ComponentSpace[Parent[i]]; // 先局部，再父骨骼 } // 世界空间再乘一次组件到世界的变换 WorldSpace[i] = ComponentSpace[i] * ComponentToWorld;

反过来，组件空间转回局部空间：Local[i] = Component[i] * Component[Parent].Inverse()（也就是 GetRelativeTransform）。IK 节点改的是组件空间，改完要转回局部空间，这就是 AnimGraph 里 “Local To Component / Component To Local” 转换节点存在的原因。

实测 E1：68 根骨骼（仿 Mannequin，平均深度 6.8、最大 11），2000 个角色
写法每角色耗时相对说明
A 线性数组：comp[i]=local[i]*comp[par[i]]1.12 us1.00x67 次复合
B 指针树递归 DFS（节点散落在堆上）3.95 us3.54x同样 67 次复合，多了指针追逐和递归
C 每根骨骼单独回溯到根6.31 us5.65x459 次复合（Σ深度），结果一样但浪费

三种写法结果一致（最大位置差 4.2e-5，float 舍入）。指针树的计算量和线性数组完全一样，慢在内存访问：节点散落在堆上，每访问一个子节点都可能是一次缓存未命中（这个倍数对内存布局很敏感：本书两次完整运行分别测得 1.28x 和 3.54x，表中是最终版本的数字）。这是每个角色每帧都要做的事：拓扑序数组让它成为一个最简单的线性循环，也方便 SIMD 和多线程。

1.4 参考姿势与蒙皮矩阵

美术在 DCC 里把网格“绑”到骨骼上时，骨骼处在某个姿势（通常是 T-Pose 或 A-Pose），这就是参考姿势 / 绑定姿势。顶点坐标是在这个姿势下给出的。运行时骨骼动了，顶点要跟着动：

SkinMatrix[b] = InvRefPoseComponent[b] * CurrentComponent[b] // UE 的 A*B：先 A 后 B 顶点新位置 = Σ_k weight_k * ( SkinMatrix[bone_k] 作用于 绑定位置 )

直观理解：先用 InvRefPose 把顶点从“绑定时的组件空间”搬到“这根骨骼的局部空间”，再用当前姿势搬回组件空间。InvRefPose 在加载时就算好缓存起来。骨骼一动不动时，SkinMatrix 是单位矩阵，网格保持绑定时的样子。

1.5 插槽、虚拟骨骼与重定向

Socket（插槽）

挂在某根骨骼上的一个相对变换，用来挂武器、特效、摄像机。可以加在 Skeleton 上（所有 Mesh 共享）或某个 Mesh 上（只对它生效）。运行时 GetSocketTransform = 相对变换 × 骨骼的组件 / 世界变换。

Virtual Bone（虚拟骨骼）

在 Skeleton 里加的、DCC 里不存在的骨骼（名字带 VB 前缀）：它是源骨骼（父）的子骨骼，但变换跟随目标骨骼，即“目标骨骼的位置，用源骨骼的空间来表达”。不参与蒙皮，常用作 IK 目标、瞄准参考点，不用回 DCC 改骨架、重导所有动画。

重定向（Retargeting）

同一 Skeleton、不同体型：设置每根骨骼的平移重定向方式（Animation / Skeleton / AnimationScaled 等），让平移按骨骼比例缩放。不同 Skeleton：UE5 用 IK Rig + IK Retargeter 做链到链的映射，可离线导出，也可运行时重定向。

深入：为什么 Translation Retargeting 通常只让 root / pelvis 用 Animation

动画里大部分骨骼的“平移”其实就是骨长。高个子角色播放矮个子的动画时，若所有骨骼都用动画里的平移（Animation 模式），骨长被改成矮个子的，网格就会被拉扯变形。所以常见设置是：其余骨骼用 Skeleton 模式（保留自己的骨长，只用动画的旋转）；pelvis 用 AnimationScaled（按身高比例缩放上下起伏）；root 用 Animation（保留位移）。

1.6 FTransform 的坑：非均匀缩放

FTransform 用“四元数 + 平移 + 缩放”而不是 4×4 矩阵，好处是插值简单、内存小（UE5 双精度版本更大，动画内部大多用 float 版本的数据）。代价是：父骨骼有非均匀缩放、子骨骼有旋转时，真实结果包含剪切（shear），而 FTransform 表达不了，复合后会有误差。所以绑定时尽量避免非均匀缩放的骨骼带有旋转的子骨骼；需要“压扁 / 拉伸”效果时，把缩放放在叶子骨骼或单独的辅助骨骼上。

本章速记
  • 动画资产和动画蓝图都绑定 Skeleton；同 Skeleton 的多个 Mesh 共享动画，换装部件可用 Leader Pose 复用骨骼。
  • 骨骼 = 数组 + 父下标，拓扑序；FK 是一个循环：comp[i] = local[i] * comp[parent]（E1：比指针树快 3.54x，比逐根回溯快 5.6x）。
  • 三套下标：Skeleton / Mesh / Compact Pose；自定义节点要在 CacheBones 里用 FBoneReference 解析。
  • 蒙皮矩阵 = 参考姿势逆 × 当前组件空间变换；IK 在组件空间做，完成后转回局部空间。
  • Socket 挂东西，Virtual Bone 做 IK 目标，Retarget 处理体型差异；FTransform 不支持剪切。
自测：一个武器 Mesh 想挂在右手上，并且随动画抖动，应该挂在骨骼上还是 Socket 上？两者的区别？

都可以 Attach，但推荐 Socket：Socket 在骨骼上再叠一个可调的相对变换（握把位置、角度），美术可以在编辑器里预览调整，不用改代码；直接挂骨骼的话相对偏移只能写在代码或组件上。两者都会每帧跟随骨骼的世界变换。

自测：为什么 LOD 减骨不需要重新构建骨骼层级？

骨骼按拓扑序存放，删掉若干骨骼（连同它们的所有子孙）后，剩下的骨骼保持原有相对顺序，仍然满足“父下标小于子下标”。运行时只需要一个“本 LOD 需要的骨骼下标列表”（RequiredBones），FK 照样一个循环。被删骨骼上的顶点在制作 LOD 时已经被重新绑定到它的祖先骨骼。
