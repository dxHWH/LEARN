    一条主线：可靠性是一组机制，而不是一个开关

    传输层的知识点乍看很散：端口、校验和、序号、三次握手、滑动窗口、拥塞控制、TIME_WAIT、KCP、QUIC……面试时也常被拆成一道道独立的题来问。但它们其实都在回答同一个问题：

    🧭 全书主线

    IP 网络只承诺"尽力而为"：包会丢、会乱序、会重复、会出错、会因为拥塞而变慢。要想在它上面提供"可靠"的服务，就要拿出一组机制去对付这些问题，而每个机制都有代价（延迟、带宽、内存、复杂度）。

    从一次网页请求说起

    在浏览器里敲下一个网址，到页面开始出现，网线上依次走过了 UDP、TCP、TLS、HTTP。

    本章目标

    1.1 敲下回车之后：一张时序图看全流程

    假设你在浏览器里输入 https://www.example.com 并回车，且本机没有任何缓存。抛开浏览器内部的解析和渲染，单看网络，大致会发生四件事：

    1. DNS 解析：把域名翻译成 IP 地址。浏览器（通过操作系统）向 DNS 服务器发一个查询，通常用 UDP 的 53 端口，一问一答。
    2. TCP 三次握手：和 Web 服务器的 443 端口建立一条 TCP 连接。
    3. TLS 握手：在 TCP 连接之上协商加密参数、验证服务器证书。TLS 1.3 需要 1 个 RTT。
    4. HTTP 请求与响应：发送 GET /，收到 HTML。

    这张图里已经藏着本书的大部分主题：

    • DNS 为什么用 UDP？一问一答、报文小，用 TCP 光握手就要多花 1 个 RTT，丢了重问一次即可（第 2 章、第 4 章）。
    • SYN、SYN+ACK、ACK 各自携带了什么、为什么是三次？（第 5 章）
    • HTML 被拆成很多个 TCP 段，丢了一个怎么办？乱序了怎么办？发太快怎么办？（第 3 章）
    • 能不能把 TCP 握手和 TLS 握手合并，把 4 个 RTT 压缩下来？这正是 QUIC / HTTP/3 的动机之一（第 10 章）。
    📦 场景案例：RTT 才是网页慢的主因

    很多人以为网页慢是因为"带宽不够"。实际上，打开一个普通网页只需要几百 KB，100 Mbps 的带宽传完只要几十毫秒；真正拖慢首屏的是来回次数（RTT 的个数）。这就是为什么工程上大量优化都在"省 RTT"：DNS 预解析、TCP 连接复用（HTTP Keep-Alive）、TLS 会话恢复、TCP Fast Open、HTTP/3 的 0-RTT。记住这个视角，后面讨论握手次数时你会更有体感。

    1.2 分层模型：每层只做一件事

    网络通信被拆成若干层，每一层只依赖下一层提供的服务，并向上一层提供服务。教科书里有两套模型：

    OSI 七层TCP/IP 四层（五层教学版）负责什么典型协议PDU 名称
    应用层 / 表示层 / 会话层应用层具体业务语义HTTP、DNS、TLS*、SSH、游戏协议报文（message）
    传输层传输层进程到进程：端口复用、可靠性、流量 / 拥塞控制TCP、UDP、SCTP、QUIC*TCP 段（segment）/ UDP 数据报（datagram）
    网络层网际层主机到主机：寻址与路由，跨越多个网络IPv4、IPv6、ICMP分组 / 包（packet）
    数据链路层网络接口层（链路层 + 物理层）同一链路上相邻节点之间传帧以太网、Wi-Fi、PPP帧（frame）
    物理层比特 ↔ 电 / 光 / 无线信号双绞线、光纤比特

    * TLS 通常被视为位于传输层和应用层之间；QUIC 运行在 UDP 之上，但承担的是传输层职责，所以常被称为"用户态传输层"。

    封装与解封装

    发送时，数据从上往下走，每经过一层就在前面加上一层"信封"（头部）；接收时从下往上走，每一层拆掉属于自己的信封，再根据头部里的字段决定交给上面的谁。

    ✅ 面试答法：为什么要分层？

    ① 解耦：每层只关心自己的职责，换掉其中一层（如把有线换成 Wi-Fi、把 IPv4 换成 IPv6）不影响其他层；② 复用：所有应用共享同一套 TCP/IP 实现；③ 标准化：不同厂商只要遵守层间接口就能互通。代价是每层都有头部开销，层与层之间也可能出现信息不对称（例如 TCP 不知道底层是无线链路，把无线干扰导致的丢包误当成拥塞，第 3 章会讲）。

    1.3 IP 的承诺：尽力而为

    网络层的 IP 协议负责把一个包从源主机送到目标主机，中间可能经过几十个路由器。但 IP 只承诺"尽力而为"（best effort），具体来说：

    ❌ 不保证送达

    路由器队列满了就直接丢包；TTL 减到 0 也丢。丢了不会通知任何人（最多偶尔回一个 ICMP）。

    ❌ 不保证顺序

    先发的包可能走了更长的路径，后发先至。

    ❌ 不保证不重复

    链路层重发、路由抖动都可能让同一个包到达两次。

    ❌ 不保证数据正确

    IPv4 头部校验和只校验头部，不管数据；IPv6 连头部校验和都去掉了。

    ❌ 不控制速率

    你发多快它就转多快，直到某个路由器扛不住开始丢包。

    ✅ 只保证一件事

    按目标 IP 地址尽量把包往正确的方向转发。

    为什么不让 IP 层直接做可靠？——端到端原则

    如果让每个路由器都保证可靠（逐跳确认、逐跳重传），路由器就得为每条流保存状态、缓存数据，成本极高；而且即使每一跳都可靠，数据仍可能在终端主机的内存里出错，最终还是要由两端再确认一次。这就是著名的端到端原则（End-to-End Argument）：

    📐 端到端原则

    某个功能只有在通信的端点才能被完整、正确地实现时，就应该放在端点实现；网络中间只做简单、通用、高效的事情。
    → 所以 IP 保持"笨而快"，可靠性交给两端主机的传输层（TCP），或者干脆交给应用自己（UDP + 应用层可靠）。

    这条原则也解释了本书最后一部分的存在：既然可靠性本来就是端点的事，那它放在内核里的 TCP 还是用户态的 KCP / QUIC，只是工程取舍，没有原则上的对错。

    1.4 端口、套接字与五元组：找到具体的进程

    IP 地址只能定位到主机，而一台主机上同时跑着浏览器、微信、游戏客户端。传输层的第一个职责就是复用与分用（multiplexing / demultiplexing）：发送时把多个进程的数据汇入同一个 IP 层，接收时再按端口号分发给正确的进程。

    • 端口（port）：16 位无符号整数，0～65535。0～1023 是知名端口（HTTP 80、HTTPS 443、DNS 53、SSH 22），1024～49151 是注册端口，49152～65535 是动态（临时）端口。Linux 默认的临时端口范围是 32768～60999（net.ipv4.ip_local_port_range）。
    • 套接字（socket）：操作系统提供给应用的通信端点抽象。应用读写 socket，内核负责把数据交给 TCP/UDP 协议栈。
    • 五元组：{协议, 源 IP, 源端口, 目的 IP, 目的端口}，唯一标识一条通信。
    ⚠️ 易错点：一台服务器最多只能有 65535 个 TCP 连接？

    错。端口号的 65535 限制针对的是同一个四元组中的一个端口字段。服务器只监听一个端口（443），每条连接由{客户端 IP, 客户端端口}区分，理论上限是"客户端 IP 数 × 客户端端口数"，远超 65535。实际限制来自文件描述符上限和内存（每条连接的内核结构加收发缓冲区要占几 KB 到几十 KB）。
    反过来，客户端连同一个服务器的同一个端口时，确实最多只能用掉约 2.8 万个（Linux 默认临时端口范围）本地端口——这就是第 6 章 TIME_WAIT 过多会导致"端口耗尽"的根源。

    1.5 MTU、MSS 与分片

    链路层一次能承载的最大数据长度叫 MTU（Maximum Transmission Unit），以太网是 1500 字节。比 MTU 大的 IP 包要么被分片（IPv4 允许路由器分片），要么被丢弃并回一个 ICMP "需要分片"（设置了 DF 位或 IPv6）。

    • 分片的坏处：任何一个分片丢了，整个 IP 包都要作废；分片重组消耗接收方资源；很多防火墙和 NAT 会直接丢弃分片。所以无论 TCP 还是 UDP，都应该尽量避免 IP 分片。
    • TCP 怎么避免：三次握手时双方在 SYN 里通过 MSS 选项告诉对方"我能收的最大段长"，一般是 MTU − 40 = 1460；之后 TCP 自己把字节流切成不超过 MSS 的段。再配合路径 MTU 发现（PMTUD）适应中间更小的 MTU（如 PPPoE 的 1492）。
    • UDP 怎么避免：UDP 不切分，应用交给它多大，它就发多大的数据报。所以应用必须自己控制每个数据报的大小：以太网下 UDP 负载不超过 1500 − 20 − 8 = 1472 字节；考虑到隧道、VPN、移动网络，实践中常取 1200～1400（QUIC 规定 IPv4/IPv6 下至少支持 1200 字节，KCP 默认 MTU 为 1400）。
    🎮 游戏开发视角

    游戏的同步包通常只有几十到几百字节，天然不会触发分片；但"进入场景时下发全量状态""发送一张大地图快照"这类大消息就必须在应用层手动分片、编号、重组，这正是第 8 章可靠 UDP 里"消息分片"机制要解决的问题。UE 的网络层把一个大的 Bunch 拆成多个 Partial Bunch 也是同一个道理。

    本章小结
    • 一次冷启动 HTTPS 请求 ≈ DNS(UDP) + TCP 握手 + TLS 握手 + HTTP，约 4 个 RTT；网页慢多半慢在 RTT 个数。
    • TCP/IP 四层：应用 → 传输（进程到进程）→ 网际（主机到主机）→ 网络接口；PDU 依次叫报文、段 / 数据报、分组、帧。
    • IP 尽力而为：可能丢、乱、重、错、拥塞。按端到端原则，可靠性放在端点做。
    • 端口 16 位；TCP 连接按四元组区分，UDP socket 按目的地址区分；服务器连接数不受 65535 限制。
    • MTU 1500 → TCP MSS 1460、UDP 安全负载 ≤ 1472（实践取 1200～1400）；尽量避免 IP 分片。
    思考题 1：为什么 DNS 一般用 UDP，什么情况下又会改用 TCP？

    一般用 UDP：查询和应答都很小，一问一答，没有必要先花 1 个 RTT 建连接；丢了由客户端超时重问即可，DNS 解析器也不需要为每个客户端维护连接状态，抗并发能力强。
    改用 TCP 的情况：① 应答超过 512 字节（未使用 EDNS0 时）或超过 EDNS0 协商的大小，服务器会在 UDP 应答中设置 TC（截断）位，客户端改用 TCP 重新查询；② 主从 DNS 服务器之间的区域传送（AXFR/IXFR）数据量大，必须用 TCP；③ DNS over TLS（DoT，端口 853）基于 TCP。

    思考题 2：服务器只监听 443 一个端口，为什么能同时服务几十万个客户端？瓶颈在哪？

    TCP 连接由四元组标识，服务器侧的 IP 和端口相同，但客户端的 IP 和端口不同，所以每条连接都是唯一的，不受 65535 的限制。瓶颈在于：进程 / 系统级文件描述符上限（ulimit -n、fs.file-max）、每条连接的内核内存（sock 结构 + 收发缓冲区）、CPU（中断、协议栈处理、应用逻辑），以及 I/O 模型（需要 epoll / IOCP 之类的多路复用）。

    思考题 3：一个游戏要用 UDP 发送 10 KB 的场景快照，直接 sendto 一次行不行？

    技术上可以（UDP 最大负载约 64 KB），但会被 IP 层切成 7～8 个分片，任何一个分片丢失整个数据报就作废，丢包率被放大约 7 倍，还可能被中间设备直接丢弃。正确做法是在应用层把快照切成若干个 ≤ 1200 字节的片，每片带上"消息 ID + 片序号 + 总片数"，可靠发送并在对端重组；或者只发送和上一个已确认快照的差量（delta）。

    CHAPTER 02

    UDP：薄到极致的传输层

    UDP = IP + 端口 + 校验和。它的价值恰恰在于"不做什么"。

    本章目标
    • 背出 UDP 头部 4 个字段及含义，会算最大负载，知道伪首部为什么存在
    • 理解"无连接""保留消息边界""尽力交付"三个特性的具体含义，并能用实测输出佐证
    • 掌握 UDP 与 TCP 的 socket 编程调用序列差异
    • 说出 UDP 的优缺点与典型应用场景，以及使用 UDP 时必须由应用补上的东西

    2.1 一句话定义

    UDP（User Datagram Protocol，用户数据报协议，RFC 768）是一种无连接、不可靠、面向数据报的传输层协议。它在 IP 之上只额外提供了两样东西：端口（让数据能交给正确的进程）和校验和（检测数据是否损坏）。RFC 768 全文只有 3 页，这在 IETF 的协议里极其罕见。

    📮 一个类比：寄明信片

    UDP 像寄明信片：写上地址（IP）和收件人（端口）就丢进邮筒，不需要事先打电话确认对方在家；每张明信片独立投递，可能丢、可能晚到、两张寄出的顺序和收到的顺序可能相反；但每张明信片都是完整的一张，不会出现半张。TCP 则像打电话：先拨号接通（握手），然后连续说话，对方听不清会让你重说，最后说再见挂断（挥手）。

    2.2 报文结构：只有 8 字节

    字段位数含义与细节
    源端口16发送方端口。客户端一般由系统分配临时端口；如果不需要对方回复，可以填 0。
    目的端口16接收方端口，内核据此找到目标 socket。找不到时回复 ICMP "端口不可达"。
    长度16UDP 头部加数据的总长度，最小 8。最大 65535，所以 IPv4 下数据最多 65535 − 8 − 20（IP 头）= 65507 字节。
    校验和16把伪首部 + UDP 头部 + 数据按 16 位反码求和再取反。IPv4 下可以填 0 表示"未计算"；IPv6 下必须计算（因为 IPv6 去掉了 IP 头部校验和）。

    伪首部：为什么校验和要把 IP 地址也算进去

    计算校验和时，会在 UDP 报文前面临时拼一个 12 字节的伪首部（pseudo header）：源 IP、目的 IP、一个全 0 字节、协议号 17、UDP 长度。伪首部不会被发送，只参与计算。

    目的是检测"送错了地方"：如果 IP 头部在传输中出错，导致一个本该发给 A 的数据报被交给了 B，单看 UDP 头部和数据是发现不了的；把 IP 地址纳入校验后，B 计算出的校验和就对不上，会丢弃这个数据报。TCP 的校验和用的是同样的方法（协议号为 6）。

    16 位反码求和（UDP / TCP / IP 校验和通用算法）
    uint16_t InternetChecksum(const uint8_t* data, size_t len, uint32_t sum = 0) {
    for (size_t i = 0; i + 1 < len; i += 2)
        sum += (uint32_t(data[i]) << 8) | data[i + 1];   // 按 16 位大端累加
    if (len & 1) sum += uint32_t(data[len - 1]) << 8;    // 奇数长度：末尾补 0
    while (sum >> 16) sum = (sum & 0xFFFF) + (sum >> 16); // 进位回卷（反码加法）
    return uint16_t(~sum);                                // 取反
}
// 计算 UDP 校验和：先把伪首部（源IP、目的IP、0、17、UDP长度）累加进 sum，再累加 UDP 头部和数据
// 接收方对"伪首部 + 整个 UDP 报文（含校验和字段）"再算一遍，结果为 0 说明无错
    ⚠️ 易错点：校验和能保证数据正确吗？

    不能完全保证。16 位反码和很弱：两个 16 位字互换位置、或两处错误恰好抵消，它都发现不了。链路层的 CRC32 能挡住绝大部分随机错误，但对恶意篡改毫无办法。需要防篡改就必须用密码学手段（TLS、DTLS、QUIC 的 AEAD 加密认证）。

    2.3 无连接：想发就发，发完不管

    "无连接"的意思是：通信前不需要握手，内核里不为"对方"保存任何状态。一个 UDP socket 可以给任意多个地址发数据，也可以收任意多个地址发来的数据。这带来三个直接后果：

    1. 发送没有前置延迟：第一个包就能携带业务数据，省掉握手的 1 个 RTT。
    2. 服务器没有连接状态：一个 socket 就能服务海量客户端，内存占用极低，也不存在 TIME_WAIT 之类的连接管理问题。
    3. 发送方不知道对方是否存在：sendto 返回成功，只说明数据已经交给了本机内核，不代表对方收到了，甚至不代表对方存在。
    🧪 实测证据（d1 · E2）：发给一个没人监听的端口
    d1_tcp_udp_behaviors.exe · E2
    == E2 UDP 无连接：发给没人监听的端口 ==
  sendto 返回 4（发送"成功"——UDP 不知道对方在不在）
  随后 recvfrom 返回 -1，WSAGetLastError=10054（10054=WSAECONNRESET：内核收到 ICMP 端口不可达）
  关闭 SIO_UDP_CONNRESET 后：recvfrom 返回 -1，WSAGetLastError=10060（10060=超时，错误被静默丢弃）

    sendto 照样返回发出的 4 字节。对方主机的内核发现 40012 端口没人监听，回了一个 ICMP 端口不可达。Windows 会把这个 ICMP 错误"记"在 socket 上，让下一次 recvfrom 报 WSAECONNRESET——对一个"无连接"协议来说这个错误名相当有迷惑性。

    🎮 游戏开发视角：Windows 上 UDP 服务器的经典坑

    游戏服务器用一个 UDP socket 服务所有玩家。某个玩家断线后，服务器继续往他的地址发包，对端回 ICMP 端口不可达，于是服务器的下一次 recvfrom 报 WSAECONNRESET。如果代码把这个错误当成"socket 坏了"去关闭重建，所有玩家都会掉线。解决办法就是实测中的 WSAIoctl(SIO_UDP_CONNRESET, FALSE)，或者把这个错误码当作可忽略的提示。Linux 上，只有对 UDP socket 调用过 connect() 时才会把 ICMP 错误报给应用（ECONNREFUSED），未 connect 的 socket 默认不报。

    UDP 上的 connect() 是什么意思

    UDP socket 也可以调用 connect()，但不会发送任何报文，只是在内核里记下一个默认对端：之后可以用 send/recv 代替 sendto/recvfrom，内核只接收来自这个对端的数据报，并且能把 ICMP 错误报告给应用。它是"本地过滤器"，不是"连接"。QUIC 客户端和很多游戏客户端都会对 UDP socket 调用 connect()，顺便还能让内核少做一次路由查找。

    2.4 面向数据报：保留消息边界

    UDP 的每一次 sendto 都对应一个独立的数据报，接收方每次 recvfrom 恰好取出一个完整的数据报，既不会把两个合并，也不会只给你半个。这叫"保留消息边界"。TCP 则是字节流，没有消息边界的概念。

    🧪 实测证据（d1 · E1）：三次发送，两种结果
    d1_tcp_udp_behaviors.exe · E1
    == E1 消息边界：UDP 保留边界，TCP 是字节流 ==
  UDP recvfrom #1 ->  5 字节: "hello"
  UDP recvfrom #2 -> 12 字节: "tcp-udp-book"
  UDP recvfrom #3 -> 27 字节: "reliable-transport-over-udp"
  TCP 发送方 send() 3 次（5+12+27=44 字节），接收方 recv() 1 次 -> 44 字节: "hellotcp-udp-bookreliable-transport-over-udp"

    同样是发送三条消息、接收方稍晚一点再读：UDP 原样收到三条；TCP 一次 recv 就把 44 个字节全拿走了，三条消息"粘"在一起，接收方无从知道原来的边界在哪——这就是第 3 章要讲的粘包。

    ⚠️ 易错点：接收缓冲区比数据报小会怎样？

    数据报多出来的部分会被直接丢弃，不会留到下一次 recvfrom。Linux 会在 msg_flags 里置 MSG_TRUNC，Windows 的 recvfrom 返回错误 WSAEMSGSIZE（缓冲区里仍是截断后的数据）。所以 UDP 接收缓冲区要按协议的最大包长来开（例如 1500 或 64 KB）。

    2.5 尽力交付：UDP 不做的事

    不做的事具体表现如果你需要，应该怎么补
    不确认、不重传丢了就是丢了，发送方完全不知道应用层序号 + ACK + 重传（第 8 章）
    不排序按到达顺序交给应用应用层序号 + 接收缓冲重排，或只取"最新"的
    不去重网络重复的包会被交付两次序号 + 已收集合（滑动位图）
    不做流量控制接收方 socket 缓冲区满了，新来的数据报被内核静默丢弃增大 SO_RCVBUF；应用层窗口通告
    不做拥塞控制应用以多快的速度 sendto，内核就以多快的速度往外发应用层限速（令牌桶）、拥塞控制算法
    不分片超过 MTU 的数据报交给 IP 分片应用层控制包长 ≤ 1200～1400，大消息自己切

    看到这里可能会疑惑：UDP 什么都不做，凭什么被大量使用？答案是："不做"本身就是一种能力——它把这些决定权留给了最了解业务需求的应用。语音通话里一个 20 ms 的语音帧丢了，最好的处理是让解码器插值补上，而不是等 200 ms 重传过来时这句话早已说完。这个思路是第四部分的出发点。

    2.6 编程模型：UDP 与 TCP 的调用序列

    最小 UDP 回显服务器（Winsock，省略错误处理）
    SOCKET s = socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP);
sockaddr_in addr{}; addr.sin_family = AF_INET; addr.sin_port = htons(7777); addr.sin_addr.s_addr = INADDR_ANY;
bind(s, (sockaddr*)&addr, sizeof addr);
char buf[1500];
for (;;) {
    sockaddr_in from{}; int fromLen = sizeof from;
    int n = recvfrom(s, buf, sizeof buf, 0, (sockaddr*)&from, &fromLen);  // 一次取一个完整数据报
    if (n > 0) sendto(s, buf, n, 0, (sockaddr*)&from, fromLen);          // 原样发回给来源地址
}

    2.7 UDP 独有的能力：广播与多播

    TCP 是严格的一对一连接，而 UDP 因为无连接，可以把一个数据报发往广播地址（如 255.255.255.255 或子网广播 192.168.1.255）或多播组（224.0.0.0/4），一次发送、多个接收者同时收到。

    • DHCP：新设备还没有 IP 地址，只能用广播（客户端 68 → 服务器 67）寻找 DHCP 服务器。
    • 局域网游戏发现：客户端广播"有房间吗"，局域网内的主机回复房间信息。
    • mDNS / SSDP：打印机、投屏设备的自动发现。
    • IPTV / 行情分发：机房内用多播把同一份数据推给大量订阅者。

    2.8 优缺点与典型应用

    优点

    ① 低延迟：无握手，第一个包就能带数据；无重传等待，不会被前面丢失的包卡住。
    ② 开销小：头部 8 字节，内核无连接状态。
    ③ 保留消息边界：天然适合"一个包一条消息"的协议。
    ④ 灵活：支持广播 / 多播；可靠性、拥塞控制都能按需在应用层定制。

    缺点

    ① 不可靠：丢、乱、重全要应用自己处理。
    ② 无拥塞控制：滥发会挤占网络，也会被运营商 QoS 限速。
    ③ NAT 不友好：NAT 映射超时短（常见 30 s～数分钟），必须定期发心跳保活。
    ④ 易被滥用：源地址可伪造，可被用于反射放大攻击（DNS、NTP、Memcached）。

    场景为什么用 UDP可靠性怎么补
    DNS 查询小报文一问一答，省掉握手 RTT超时重问；大应答回退 TCP
    DHCP没有 IP 时只能广播超时重发
    语音 / 视频通话（RTP、WebRTC）实时性第一，迟到的数据没用FEC、NACK 选择性重传、丢帧插值、抖动缓冲
    低延迟直播减少重传卡顿FEC + 有限重传（SRT 等协议）
    在线游戏位置、输入只关心最新值；每毫秒都很宝贵按消息分级：状态不可靠、指令可靠（第 8、11 章）
    HTTP/3绕开内核 TCP，实现多路复用与 0-RTTQUIC 在用户态完整实现可靠传输（第 10 章）
    VPN / 隧道（WireGuard、VXLAN）避免"TCP 套 TCP"的双重重传交给隧道内部的 TCP 处理
    ✅ 面试答法：说说你对 UDP 的理解

    UDP 是无连接、不可靠、面向数据报的传输层协议，头部只有 8 字节：源端口、目的端口、长度、校验和。它在 IP 之上只加了端口复用和差错检测，不建立连接、不确认、不重传、不排序、不做流量和拥塞控制，但保留消息边界、支持广播多播。优点是延迟低、开销小、灵活，缺点是可靠性和拥塞控制都要应用自己负责。典型场景是 DNS、DHCP、音视频实时通信、在线游戏，以及 HTTP/3 底层的 QUIC。（加分项）如果在 UDP 上需要可靠性，可以在应用层实现序号、确认、重传和窗口，比如 KCP 或 QUIC。

    本章小结
    • UDP 头部 8 字节：源端口、目的端口、长度、校验和；IPv4 最大负载 65507 字节。
    • 校验和覆盖伪首部（IP 地址、协议号、长度），用来发现"送错地方"；IPv4 可选、IPv6 必选；弱校验，防不了篡改。
    • 无连接：sendto 成功 ≠ 对方收到；Windows 上 ICMP 端口不可达会让下一次 recvfrom 报 WSAECONNRESET（实测）。
    • 保留消息边界：一次 sendto 对应一次 recvfrom（实测）；缓冲区不够时多余部分被丢弃。
    • 不重传、不排序、不去重、不限速，这些"缺点"正是它灵活、低延迟的来源。
    思考题 1：UDP 包长度字段已经有了，为什么还需要 IP 头部的总长度字段？反过来呢？

    严格来说 UDP 长度字段是冗余的：UDP 长度 = IP 总长度 − IP 头部长度。保留它的原因是让 UDP 的校验和计算、报文解析可以不依赖下层（分层独立），而且伪首部中也用到这个长度。IP 头部的总长度则是网络层自己需要的（转发、分片），不能依赖上层协议。

    思考题 2：UDP 服务器的接收缓冲区满了会怎样？TCP 呢？

    UDP：内核直接丢弃新到的数据报，发送方毫不知情（可以通过 netstat -su 的 "receive buffer errors" 观察）。TCP：接收方通过窗口字段告诉发送方"我还能收多少"，缓冲区满时通告窗口为 0，发送方暂停发送并周期性发零窗口探测，数据不会丢——这就是流量控制。

    思考题 3：既然 UDP 不可靠，为什么说"UDP 更适合游戏"？这句话完全对吗？

    不完全对，应该说"UDP 让游戏有机会做得更好"。游戏里大量数据（位置、朝向）是"状态"，只关心最新值，丢了等下一帧即可，用 TCP 反而会因为重传和队头阻塞让后面的新状态被卡住。但游戏里也有必须可靠的数据（技能释放、购买道具、聊天），所以实际是"UDP + 应用层按需可靠"。另外，很多回合制、卡牌、MMO 的非战斗部分直接用 TCP 也完全够用，实时性要求高的 FPS、MOBA、格斗才更依赖 UDP。

    TCP：可靠字节流的全套机制

    序号、确认、重传、窗口、拥塞控制——把一个会丢会乱的网络，包装成一根"不丢不乱的管道"。

    本章目标

    • 理解"字节流"与序号 / 确认号的计算，能解释粘包、拆包并给出解决方案
    • 讲清超时重传（RTO 计算、Karn 算法、指数退避）、快速重传与 SACK
    • 讲清滑动窗口、流量控制、零窗口、Nagle 与延迟确认
    • 讲清慢启动、拥塞避免、快速恢复，以及 CUBIC、BBR 的思想；区分流量控制与拥塞控制

    3.1 一句话定义

    TCP（Transmission Control Protocol，传输控制协议，现行标准 RFC 9293）是一种面向连接的、可靠的、基于字节流的、全双工传输层协议。拆开看：

    面向连接

    通信前先三次握手，双方各自建立连接状态（序号、窗口、缓冲区）；结束后四次挥手释放。只能一对一，不支持广播多播。

    可靠

    数据不丢、不重、不错、按序交付给应用。靠校验和 + 序号 + 确认 + 重传实现。

    字节流

    TCP 眼里只有一串连续的字节，没有"消息"的概念。应用写入的边界不会被保留。

    全双工

    双方可以同时收发，两个方向各有独立的序号空间和窗口，因此关闭时也要两个方向分别关闭。

    3.2 头部结构：20 字节固定 + 最多 40 字节选项

    字段位数作用

    发送方在收到确认之前最多能发"一个窗口"的数据，所以吞吐上限 ≈ 窗口 / RTT。窗口最大 64 KB、RTT 100 ms（北京到美西）时，吞吐上限只有 64 KB / 0.1 s ≈ 5 Mbps——哪怕你的带宽是 1 Gbps。要跑满带宽，窗口至少要达到带宽时延积（BDP）：1 Gbps × 100 ms = 12.5 MB，所以必须用窗口扩大选项。下载海外大文件时速度上不去，常见原因之一就是某一端的接收窗口太小。

    3.3 字节流、序号与"粘包"

    序号按字节编号

    TCP 给字节流中的每一个字节都编号，而不是给每个段编号。段的序号是它第一个字节的编号，确认号是"期望的下一个字节"。例如 ISN = 1000，SYN 占用 1 个序号，于是第一个数据字节的编号是 1001：

    报文seq数据长度接收方回复的 ack
    段 110011001101
    段 211012001301
    段 3（丢失）1301100—
    段 41401100仍然是 1301（累计确认：1301 还没到，后面到了也不能确认）

    最后一行引出两个问题：发送方怎么知道段 3 丢了（3.4 节的重传），以及段 4 已经到了却不能确认是不是太浪费（3.4 节的 SACK）。

    粘包与拆包

    因为 TCP 没有消息边界，应用写入的"消息"和接收方读出来的"块"之间没有任何对应关系：

    第 2 章的 d1 · E1 实测就是这种情况：三次 send 的 44 字节被一次 recv 全部读出。粘包可能发生在发送端（Nagle 算法把小块合并成一个段）、也可能发生在接收端（多个段到达后还没被读走，在接收缓冲区里连成一片）。常见的应用层分帧方案有三种：

    方案做法优点缺点例子
    定长消息每条消息固定 N 字节最简单浪费空间，不灵活一些硬件 / 金融行情协议

    长度前缀分帧：处理"粘包 + 半包"的标准写法
    // 接收缓冲 buf 里累积了从 socket 读到的字节；每次 recv 后调用一次
// 帧格式：[4 字节大端长度 len][len 字节消息体]
void OnBytes(std::vector<uint8_t>& buf, auto&& onMessage) {
    size_t off = 0;
    while (buf.size() - off >= 4) {                                   // 1) 头部够不够
        uint32_t len = (buf[off] << 24) | (buf[off+1] << 16) | (buf[off+2] << 8) | buf[off+3];
        if (len > kMaxMessage) throw std::runtime_error("bad frame");  // 2) 防御恶意长度
        if (buf.size() - off - 4 < len) break;                         // 3) 半包：消息体还没收全，等下次
        onMessage(&buf[off + 4], len);                                 // 4) 一条完整消息
        off += 4 + len;                                                // 5) 可能还有下一条（粘包）
    }
    buf.erase(buf.begin(), buf.begin() + off);                         // 保留不完整的尾巴
}
    ⚠️ 易错点："UDP 会不会粘包？"

    不会。UDP 每个数据报都是独立的，内核按数据报为单位排队，recvfrom 一次只取一个。但 UDP 会丢包、乱序，以及缓冲区太小时截断。所以"粘包"是字节流协议特有的问题，面试里如果被问"怎么解决 TCP 粘包"，一定要先说明"这是因为 TCP 是字节流、没有消息边界"。

    3.4 可靠传输之一：确认与重传

    可靠传输的核心逻辑一句话就能说完：发送方给数据编号并保留副本，接收方收到后回确认，发送方在一定时间内没有收到确认就重发。难点全在细节：多久算"没收到"？怎么更早发现丢包？只丢了一个时能不能只重发一个？

    超时重传：RTO 怎么定

    重传超时时间 RTO（Retransmission TimeOut）太短会导致大量不必要的重传，太长则丢包后要干等很久。TCP 根据测得的往返时间 RTT 动态计算（RFC 6298）：

    RFC 6298：RTO 计算
    首次测得 RTT 样本 R：   SRTT = R          RTTVAR = R / 2
之后每个新样本 R'：     RTTVAR = (1 - 1/4) * RTTVAR + 1/4 * |SRTT - R'|
                       SRTT   = (1 - 1/8) * SRTT   + 1/8 * R'
                       RTO    = SRTT + max(G, 4 * RTTVAR)        // G 为时钟粒度
约束：RTO 下限 1 s（RFC 建议；Linux 实际用 200 ms），上限 ≥ 60 s；首个样本之前 RTO = 1 s
超时后：RTO = RTO × 2（指数退避），直到收到新的确认后重新计算
    • 为什么要加 4 × RTTVAR：只用平均值的话，RTT 一抖动就会误判超时。方差项让 RTO 在网络抖动大时自动变宽。
    • Karn 算法：重传过的段收到 ACK 时，不能用来采样 RTT——因为分不清这个 ACK 是对原始段还是对重传段的确认（重传歧义）。时间戳选项可以解决这个歧义；QUIC 则用"包号永不重复"从根本上消除了它（第 10 章）。
    • 指数退避：连续超时说明网络可能严重拥塞，每次把 RTO 翻倍，避免雪上加霜。代价是：连续丢几次后，RTO 会变成几秒甚至几十秒——这是游戏场景最痛恨的地方，也是 KCP 要改的第一件事（第 9 章）。

    快速重传：不等超时

    超时重传至少要等一个 RTO（Linux 至少 200 ms）。能不能更早发现丢包？可以利用累计确认的特性：当某个段丢失后，后续每个段到达时接收方都会回复同样的确认号（重复 ACK）。发送方收到 3 个重复 ACK，就认为该段丢了，立即重传，不等定时器。

    🔬 为什么是 3 个重复 ACK，而不是 1 个？

    因为网络存在轻微乱序：段 3 比段 2 先到，也会产生 1 个重复 ACK，但随后段 2 到达就恢复了。阈值设为 3，是在"尽早发现丢包"和"把乱序误判成丢包"之间的经验折中。现代 Linux 默认还启用了 RACK（基于时间而不是计数判断丢包，RFC 8985）和 TLP 尾部丢失探测（解决"最后几个段丢了，后面没有段来触发重复 ACK"的问题）。KCP 把这个阈值做成了可调参数 resend，游戏场景常设为 2（第 9 章）。

    SACK：只重传真正丢了的

    累计确认只能说"我连续收到哪里为止"。如果一个窗口里丢了多个不连续的段，发送方只靠重复 ACK 无法知道到底丢了哪几个，要么一个 RTT 只能修复一个洞，要么把后面全部重发（类似回退 N 步）。SACK（选择确认，RFC 2018）在 ACK 的选项中附带最多 3～4 个"已收到的不连续块"，例如 ack=101, SACK=[201-501]，发送方就能精确地只重传 101～200。Linux 默认开启 SACK（net.ipv4.tcp_sack=1）。

    3.5 可靠传输之二：滑动窗口与流量控制

    如果每发一个段都要等确认再发下一个（停等协议），信道利用率极低：RTT 100 ms、每次 1460 字节，吞吐只有 14.6 KB/s。解决办法是允许连续发送多个段而不等确认，这些"已发出未确认"加上"允许发出"的部分就构成了发送窗口。

    流量控制：别把对方淹死

    接收方的应用可能读得很慢（比如游戏服务器卡在一次数据库查询上），接收缓冲区就会逐渐被填满。TCP 让接收方在每个 ACK 的窗口字段里告诉发送方"我还剩多少空间"（rwnd），发送方保证在途数据不超过 rwnd。这就是流量控制：端到端、由接收方驱动，保护的是接收方。

    • 零窗口：rwnd = 0 时发送方停止发送，并启动坚持定时器（persist timer），周期性发 1 字节的零窗口探测，防止"接收方窗口恢复的那个通告 ACK 丢了，双方永远互相等待"的死锁。
    • 糊涂窗口综合征（Silly Window Syndrome）：接收方每腾出几个字节就通告一次，发送方就发几个字节的小段，头部开销远大于数据。对策：接收方等腾出足够空间（一个 MSS 或缓冲区一半）再通告；发送方用 Nagle 算法。

    Nagle 算法与延迟确认：一对"好心办坏事"的组合

    Nagle 算法（发送方）

    如果还有已发送未确认的数据，新产生的小数据（不足一个 MSS）先攒着，等收到 ACK 或攒满一个 MSS 再发。目的是减少网络上的小包数量。

    延迟确认（接收方）

    收到数据后不立即回 ACK，而是等一会儿（Linux 最少约 40 ms，Windows 默认 200 ms），希望能把 ACK 捎带在应答数据里，或者攒两个段一起确认。

    两者单独都合理，叠加起来却会出问题：客户端发了一个小请求的前半段，Nagle 要等 ACK 才发后半段；服务器收到前半段，延迟确认要等 40～200 ms 才回 ACK——于是每个请求都凭空多出几十到上百毫秒。

    🎮 游戏开发视角：TCP 游戏连接一定要开 TCP_NODELAY

    游戏的操作消息都很小、要求立即发出。用 TCP 承载时，务必 setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &one, sizeof one) 关闭 Nagle；Linux 上还可以用 TCP_QUICKACK 临时关闭延迟确认。Redis、gRPC、大多数 RPC 框架默认都会开启 TCP_NODELAY。

    3.6 拥塞控制：别把网络挤爆

    流量控制只关心接收方，但路径中间的路由器也有容量。如果所有发送方都只看 rwnd 全速发，路由器队列被打满，丢包、重传、更多丢包，网络吞吐会断崖式下跌——这在 1986 年真实发生过（"拥塞崩溃"，NSFNET 吞吐一度跌到原来的千分之一），之后才有了 Van Jacobson 的拥塞控制算法。

    TCP 发送方维护一个拥塞窗口 cwnd，表示"我估计网络还能承受多少在途数据"，实际发送窗口取 min(rwnd, cwnd)。经典 Reno 算法有四个部分：

    阶段触发条件cwnd 怎么变直觉
    慢启动连接开始 / 超时之后，cwnd < ssthresh每收到一个 ACK，cwnd += 1 → 每 RTT 翻倍。初始窗口现在通常为 10 个 MSS（RFC 6928）"慢"是指起点低，增长其实是指数级的
    拥塞避免cwnd ≥ ssthresh每 RTT cwnd += 1（线性增长）接近上次出事的位置了，小心试探
    快速重传 + 快速恢复3 个重复 ACKssthresh = cwnd / 2；cwnd = ssthresh（+3）；然后进入拥塞避免还能收到重复 ACK 说明网络还通，只是轻度拥塞
    超时RTO 到期ssthresh = cwnd / 2；cwnd = 1；重新慢启动连 ACK 都收不到了，说明拥塞严重

    现代算法：CUBIC 与 BBR

    CUBIC（Linux 默认，RFC 9438）

    仍然以丢包为拥塞信号，但 cwnd 的增长按"距离上次丢包的时间"的三次函数变化：远离上次丢包点时增长快，接近时放缓并在附近长时间停留，丢包后再快速探测。增长和 RTT 无关，对长肥管道更公平、更高效。

    BBR（Google，2016）

    不再把丢包当拥塞信号，而是持续测量瓶颈带宽 BtlBw和最小往返时延 RTprop，按 BtlBw × RTprop 控制在途数据量、按 BtlBw 控制发送速率（pacing）。在有随机丢包的链路（无线、跨国）上吞吐远好于 CUBIC，也不会把路由器缓冲区塞满。

    ⚠️ 易错点：流量控制 vs 拥塞控制
    流量控制拥塞控制
    保护谁接收方（别把它的缓冲区淹了）网络（别把路由器挤爆）
    信息来源接收方在 ACK 中显式通告 rwnd发送方根据丢包、RTT 等自己推测 cwnd
    作用范围点对点全局（所有共享瓶颈的流）
    发送窗口两者同时生效：发送窗口 = min(rwnd, cwnd)
    🎮 游戏开发视角：基于丢包的拥塞控制在弱网下的副作用

    移动网络、Wi-Fi 上的丢包很多是随机干扰而不是拥塞，但 Reno / CUBIC 一律把它当成拥塞信号去减窗。对下载大文件来说只是速度慢一点；对每秒几十个小包的游戏来说，窗口被压到比实际需要还小，消息就会在发送缓冲里排队，延迟越积越高。第 8 章的仿真会量化这件事，第 9 章的 KCP 提供了关闭拥塞控制的开关 nc=1。

    ✅ 面试答法：TCP 如何保证可靠传输？

    按"问题 → 机制"答：① 数据出错：校验和，错了直接丢弃，当作丢包处理；② 丢包：序号 + 确认 + 重传，包括基于 RTT 动态计算 RTO 的超时重传，以及 3 个重复 ACK 触发的快速重传，配合 SACK 只重传缺失部分；③ 乱序和重复：接收方按序号在接收缓冲区里重排、丢弃重复段，只把连续数据交给应用；④ 接收方处理不过来：滑动窗口流量控制；⑤ 网络拥塞：拥塞控制（慢启动、拥塞避免、快速重传、快速恢复）；⑥ 双方状态同步：三次握手和四次挥手的连接管理。

    本章小结
    • TCP：面向连接、可靠、字节流、全双工。头部 20～60 字节；关键字段 seq / ack / 窗口 / 标志位。
    • 序号按字节编号，ack 是"期望的下一个字节"（累计确认）；SYN、FIN 各占 1 个序号。
    • 字节流没有边界 → 粘包 / 拆包；用长度前缀等应用层分帧解决；UDP 不存在粘包。
    • RTO = SRTT + 4·RTTVAR，Karn 算法，超时指数退避；3 个重复 ACK 快速重传；SACK 精确重传。
    • 发送窗口 = min(rwnd, cwnd)：rwnd 是流量控制（保护接收方），cwnd 是拥塞控制（保护网络）。
    • Reno：慢启动（翻倍）→ 拥塞避免（+1）→ 3 dup ACK 减半 / 超时归 1；CUBIC 是 Linux 默认，BBR 基于带宽和时延建模。
    • Nagle + 延迟确认会制造几十～几百毫秒延迟，交互式应用要开 TCP_NODELAY。
    思考题 1：ISN = 5000，客户端依次发送 300 字节、200 字节两个段，服务器全部收到，最后的 ack 是多少？

    SYN 占用一个序号，所以第一个数据字节编号 5001。第一个段 seq=5001、长度 300；第二个段 seq=5301、长度 200；服务器累计确认 ack = 5301 + 200 = 5501。

    思考题 2：接收方通告窗口为 0 后，发送方怎么知道什么时候可以继续发？如果通告恢复的那个 ACK 丢了呢？

    接收方腾出空间后会主动发一个窗口更新 ACK。但纯 ACK 不会被重传，如果它丢了，发送方一直认为窗口为 0，接收方一直等数据，形成死锁。所以发送方在收到零窗口后启动坚持定时器，周期性发送零窗口探测报文（携带 1 字节数据或序号为 SND.UNA−1 的段），强迫接收方回复当前窗口。

    思考题 3：为什么说"TCP 的拥塞控制在无线网络上表现不好"？有哪些改进？

    Reno / CUBIC 把丢包视为拥塞信号，而无线链路上的丢包很多来自信号干扰、切换基站，并非拥塞。于是 TCP 频繁地无谓减窗，吞吐上不去。改进方向：① 基于时延 / 带宽建模的算法，如 BBR；② 链路层本地重传（Wi-Fi、4G 本身有 ARQ/HARQ），减少暴露给 TCP 的丢包；③ ECN 显式拥塞通知，让路由器直接标记"我拥塞了"，而不是靠丢包传达；④ 应用层自定义传输（QUIC 可插拔拥塞控制、KCP 关闭拥塞控制）。

    思考题 4：发送窗口是不是越大越好？

    不是。窗口达到带宽时延积（BDP）就足以跑满带宽，再大也不会更快，只会让更多数据堆在路由器队列里，增加排队时延（即 Bufferbloat），并在丢包时需要重传更多数据、占用更多内存。这正是 BBR 把在途数据控制在 BDP 附近的原因。

    TCP vs UDP：全面对比与场景选型

    上表中最影响实时应用的一行是"丢包时的时延"。TCP 承诺按序交付：只要第 2 个段没到，就算第 3～6 个段早已躺在接收缓冲区里，应用也一个字节都读不到。这叫队头阻塞（Head-of-Line Blocking，HOL）。

    📦 场景案例：HTTP/2 的"多路复用"为什么还会卡

    HTTP/1.1 一条 TCP 连接同一时间只能处理一个请求，浏览器只好对同一域名开 6 条连接。HTTP/2 在一条 TCP 连接里同时传多个请求（多个流），解决了应用层的队头阻塞。可是这些流共享同一个 TCP 字节流：只要丢一个 TCP 段，所有流都被卡住——这是传输层的队头阻塞。在丢包率 2% 的弱网下，HTTP/2 甚至可能比开 6 条连接的 HTTP/1.1 更慢。HTTP/3 把传输层换成 QUIC，让每个流独立排序，才真正解决了这个问题（第 10 章）。

    4.3 三个场景的选型分析

    场景一：网页与 API

    网页、REST API、文件下载的数据一个字节都不能错，晚几十毫秒用户感知不强，所以长期以来都用 TCP（HTTP/1.1、HTTP/2 over TLS over TCP）。变化发生在移动互联网时代：弱网、高 RTT、频繁切换网络让"握手太多、队头阻塞、换网断连"成了主要矛盾，于是出现了 HTTP/3 over QUIC over UDP。截至目前，主流浏览器和大型 CDN 都已支持 HTTP/3，但 TCP 依然是服务端内部通信的绝对主力。

    场景二：视频

    子场景对延迟的要求常用传输理由
    点播（看剧、短视频）可以缓冲几秒到几十秒HTTP（TCP 或 QUIC）分片下载：HLS / DASH有缓冲区兜底，可靠更重要；可以借用 CDN
    普通直播2～10 秒RTMP 推流（TCP）+ HLS / FLV 拉流生态成熟，延迟可接受
    低延迟直播 / 连麦< 1 秒WebRTC、SRT（UDP）TCP 重传造成的卡顿不可接受
    视频会议 / 语音通话< 200～300 ms 端到端RTP / SRTP over UDP（WebRTC）迟到的帧没有意义；用 FEC、NACK、抖动缓冲、丢帧插值替代重传

    规律很清楚：延迟预算越小，越倾向 UDP + 应用层定制的可靠性。视频会议的 NACK 机制其实就是"有选择的重传"：只有当 RTT 足够小、重传的包还来得及在播放前到达时才请求重传，否则直接放弃——这是 TCP 做不到的"可靠性按需"。

    场景三：在线游戏

    游戏类型典型延迟要求常用方案
    回合制、卡牌、棋牌数百毫秒都可接受TCP（或 WebSocket）足够，开发简单
    MMORPG 非战斗部分100～300 msTCP 为主，部分项目战斗走 UDP

    🎮 游戏开发视角：游戏数据要拆成三类

    一个实时对战游戏里，数据对可靠性的需求截然不同：
    ① 状态类（位置、朝向、血量快照）：只要最新值，旧的丢了就丢了 → 不可靠、只取最新；
    ② 事件类（释放技能、购买装备、聊天）：一个都不能丢 → 可靠，但不同事件之间未必需要严格有序；
    ③ 输入流（帧同步下每帧的操作）：每帧都需要，且必须按帧序执行 → 可靠有序，常用"每个包冗余携带最近几帧"的方式降低重传依赖。
    TCP 只能对所有数据一视同仁地"可靠有序"，所以①会被②③的丢包重传拖累。这就是游戏需要可靠 UDP 的根本原因，第 7 章会系统展开。

    4.4 选型决策树

    4.5 高频追问

    Q1：TCP 一定比 UDP 慢吗？

    不一定，要区分吞吐和时延。
    吞吐：大块数据传输时 TCP 往往更快。内核对 TCP 有大量优化（TSO/GSO 分段卸载、GRO 合并、零拷贝 sendfile），而 UDP 每个数据报都要走一遍系统调用和协议栈，高包率下 CPU 开销更大（需要 sendmmsg/recvmmsg、UDP GSO 等手段弥补）。这也是 QUIC 服务端 CPU 开销通常高于 TCP+TLS 的原因之一。
    时延：网络良好时两者几乎一样（都是一个 RTT/2 的传播时延）；差别出现在丢包和建连：TCP 需要 1 RTT 握手，且丢包时有队头阻塞和 RTO 退避。

    Q2：同一个端口号能同时被 TCP 和 UDP 绑定吗？

    可以。TCP 和 UDP 是两个独立的端口空间，内核按 IP 头的协议字段先区分 TCP/UDP，再查各自的端口表。DNS 服务器就同时监听 TCP 53 和 UDP 53。

    Q3：既然 UDP 不可靠，QUIC 为什么还要基于 UDP，而不是设计一个新的 IP 协议号？

    因为中间设备僵化（ossification）：互联网上大量 NAT、防火墙只认识 TCP 和 UDP，一个新的协议号（比如 SCTP 的 132）基本无法穿越公网。同时，TCP 实现在操作系统内核里，升级要等系统更新，周期以年计。基于 UDP 就能穿越现有网络，在用户态快速迭代。UDP 在这里只充当"能穿越网络的最薄封装"。

    Q4：用 TCP 做实时游戏会有什么问题？如果必须用 TCP 怎么优化？

    问题：① 队头阻塞，一个丢包卡住后面所有新状态；② RTO 指数退避，连续丢包时卡顿可达秒级；③ Nagle + 延迟确认带来额外几十～几百毫秒；④ 拥塞控制把弱网随机丢包当拥塞，降低发送速率。优化：开 TCP_NODELAY；减小发送缓冲区避免数据在内核堆积（过时的状态宁可在应用层丢弃）；应用层心跳快速检测断线；状态同步只发最新值并做合并；必要时开多条连接隔离不同优先级的数据。

    Q5：UDP 包丢了，发送方知道吗？

    不知道。UDP 没有确认机制，唯一可能的反馈是 ICMP（如端口不可达），但它不可靠、可能被防火墙过滤，也不对应"包在中途丢失"的情况。需要知道就要在应用层实现 ACK。

    ✅ 面试答法：TCP 和 UDP 的区别（30 秒版）

    TCP 面向连接、可靠、有序、基于字节流，有流量控制和拥塞控制，头部 20 字节起，只支持一对一，适合要求数据完整的场景，比如网页、文件传输。UDP 无连接、不保证可靠和顺序、面向数据报、保留消息边界，头部只有 8 字节，没有流控和拥塞控制，支持广播多播，延迟低开销小，适合实时性要求高、能容忍丢包的场景，比如音视频、游戏、DNS。（追加一句体现深度）两者实时性差异的根源是 TCP 的按序可靠交付带来的队头阻塞，所以 QUIC、KCP 这类协议在 UDP 之上按需实现可靠性。

    本章小结
    • 选型的核心问题：数据怕丢还是怕晚；是否混有必须送达的数据；是否需要广播多播。
    • 实时场景中 TCP 的根本劣势是队头阻塞：按序交付让一个丢包拖住后面所有数据。
    • HTTP/2 解决了应用层队头阻塞，却仍受 TCP 层队头阻塞影响 → HTTP/3 改用 QUIC。
    • 视频：点播 TCP、普通直播 TCP、低延迟直播与通话 UDP；游戏：回合制 TCP、实时对战 UDP + 分级可靠。
    • TCP 并不一定慢：大流量吞吐往往更优；差异主要在建连与丢包时的时延。
    思考题 1：直播推流常用 RTMP（基于 TCP），而视频会议用 UDP。同样是实时视频，为什么选择不同？

    延迟预算不同。直播是单向的，观众感知不到 3～5 秒的延迟，播放端有缓冲区吸收 TCP 重传带来的抖动，而且 TCP 能穿越几乎所有网络、生态成熟。视频会议是双向交互，端到端延迟超过 300 ms 就会出现"抢话"，没有余地缓冲，所以必须用 UDP，并用 FEC、选择性重传、丢帧等手段在质量和延迟之间做实时取舍。连麦、互动直播对延迟要求高，也逐渐改用 WebRTC / SRT。

    思考题 2：一个 MOBA 游戏如果把"位置同步"和"技能释放"放进同一条可靠有序的通道，会有什么问题？

    一旦某个技能消息丢包重传，排在它后面的所有位置更新都会被阻塞（队头阻塞），玩家看到其他英雄"卡住再瞬移"。而且位置消息本身是可以丢弃的旧状态，却因为在可靠通道里而被反复重传，浪费带宽。正确做法是分通道：位置走不可靠（或只保留最新）的通道，技能走可靠通道，不同通道互不阻塞。

    思考题 3：为什么说"UDP 的无拥塞控制"既是优点也是社会责任问题？

    优点是应用可以完全掌控发送节奏，不会被算法误判降速。但互联网是共享的：如果一个应用用 UDP 无节制地发包，会挤占同一瓶颈链路上其他 TCP 流的带宽（TCP 会礼让，UDP 不会），极端情况下造成拥塞崩溃。所以 IETF 的 RFC 8085 要求 UDP 应用自行实现拥塞控制或至少限速；QUIC 内置了与 TCP 等价的拥塞控制；KCP 在关闭拥塞控制时也应该配合应用层限速。

    CHAPTER 05

    三次握手：建立一条连接需要什么

    握手的本质不是"打招呼"，而是让双方就各自的初始序号达成一致，并确认双向通路都是通的。

    本章目标
    • 画出三次握手的完整时序：每一步的标志位、seq、ack 以及双方状态变化
    • 说清 ISN 为什么要随机，以及"为什么是三次而不是两次或四次"的三个理由
    • 理解内核中的半连接队列与全连接队列，以及它们满了之后的行为
    • 讲清 SYN Flood 攻击原理和 SYN Cookie 等防御手段
    • 逐一分析握手中每个报文丢失、端口未监听、队列溢出等异常

    5.1 握手要完成的四件事

    1. 确认双方的收发能力：客户端能发、服务器能收；服务器能发、客户端能收。
    2. 同步双方的初始序号（ISN）：TCP 是全双工的，两个方向各有一套序号，双方都要把自己的 ISN 告诉对方，并得到对方的确认。这是最核心的一件事，SYN 就是 Synchronize Sequence Numbers 的缩写。
    3. 协商连接参数：MSS、窗口扩大因子、是否支持 SACK 和时间戳。这些选项只能出现在 SYN 报文中。
    4. 分配连接资源：双方各自建立 TCB（传输控制块）、收发缓冲区。

    5.2 逐步拆解

    步骤方向标志位seq / ack状态变化这一步证明了什么
    ①C → SSYNseq = xC：CLOSED → SYN_SENT
    S（收到后）：LISTEN → SYN_RCVD    		服务器知道：客户端能发、自己能收
    ②S → CSYN + ACKseq = y，ack = x+1C（收到后）：SYN_SENT → ESTABLISHED客户端知道：双方都能收发；自己的 ISN 已被确认
    ③C → SACKseq = x+1，ack = y+1S（收到后）：SYN_RCVD → ESTABLISHED服务器知道：客户端能收；自己的 ISN 已被确认
    tcpdump 中的一次握手（典型输出，地址与序号为示例）
    10:00:00.000 IP 10.0.0.1.52344 > 10.0.0.2.443: Flags [S],  seq 1705322911, win 64240, options [mss 1460,sackOK,TS val 1 ecr 0,nop,wscale 7], length 0
10:00:00.030 IP 10.0.0.2.443 > 10.0.0.1.52344: Flags [S.], seq 3891201650, ack 1705322912, win 65160, options [mss 1460,sackOK,TS val 9 ecr 1,nop,wscale 7], length 0

    tcpdump 中 S 表示 SYN，. 表示 ACK，S. 即 SYN+ACK；第三行的 ack 默认显示为相对值时会是 1。win 502 是窗口扩大前的原始值，实际窗口 = 502 × 2⁷ = 64256 字节。

    ⚠️ 易错点

    ① ack 不是"收到的序号"，而是"期望的下一个序号"，所以是 x+1 而不是 x。
    ② SYN 不携带数据，却消耗一个序号（FIN 也一样）；纯 ACK 不消耗序号，所以第三次握手后客户端发的第一个数据段 seq 仍是 x+1。
    ③ 服务端的 accept() 并不参与握手：握手完全由内核完成，accept 只是从全连接队列里取出一个已完成握手的连接。即使应用从不调用 accept，客户端的 connect 也能成功返回。
    ④ "SYN_RCVD"在一些资料里写作 "SYN_RECV"（Linux ss 的显示），两者是同一个状态。

    5.3 ISN 为什么要随机

    如果每条连接的 ISN 都从 0 开始，会有两个问题：

    • 与旧连接的报文混淆：同一个四元组的连接关闭后又马上重建，旧连接在网络中滞留的报文可能恰好落在新连接的序号窗口里，被当成新数据接收。
    • 序号预测攻击：攻击者如果能猜到 ISN，就能伪造源地址完成握手、向连接中注入数据（1994 年著名的 Mitnick 攻击就是利用了当时可预测的 ISN）。

    RFC 6528 推荐的生成方式是 ISN = M + F(本地IP, 本地端口, 远端IP, 远端端口, 密钥)：M 是一个大约每 4 微秒加 1 的计时器（32 位约 4.55 小时回绕一次），F 是带密钥的哈希函数。这样同一四元组的 ISN 随时间单调递增（避免和旧连接重叠），而外人无法预测（因为有密钥）。Linux 的 secure_tcp_seq() 就是按这个思路实现的。

    5.4 为什么是三次，而不是两次或四次

    📞 先看类比：打电话

    A："喂，听得到吗？"（A 确认自己能说）
    B："听得到，你听得到我吗？"（B 确认自己能听、也能说）
    A："听得到。"（B 这才确认 A 能听）
    少了第三句，B 无法知道自己的声音 A 是否听见了。但类比只能解释"双向确认"，面试真正要的是下面三条技术理由。

    理由一（RFC 793 给出的首要原因）：阻止历史连接

    网络可能把一个很久以前发出的 SYN 延迟送达。例如客户端先发了 SYN(seq=90)，迟迟没回应就放弃了（或者客户端重启了），接着又发了新的 SYN(seq=100)。如果旧 SYN 先到：

    关键在于：只有发起方（客户端）才知道哪个 SYN 是"当前有效"的。三次握手把"最终拍板"的权力留给了客户端：服务器回 SYN+ACK 之后先不建立连接，由客户端根据确认号判断，是当前连接就回 ACK，是历史连接就回 RST。

    理由二：可靠地同步双方的初始序号

    双方都有自己的 ISN，每个 ISN 都需要"告知 + 确认"一来一回，理论上需要 4 个报文：C 发 SYN(x)、S 确认 x、S 发 SYN(y)、C 确认 y。中间两个都是服务器发给客户端的，可以合并成一个 SYN+ACK，所以是 3 个。两次握手只能保证客户端的 ISN 被确认，服务器的 ISN 发出去后不知道对方有没有收到。

    理由三：避免重复连接浪费资源

    如果只有两次握手，客户端因为超时重传了多个 SYN，服务器每收到一个 SYN 就建立一条连接、分配一次资源，而客户端只会使用其中一条，其余全部成为空占资源的"僵尸连接"。

    为什么不是四次？

    四次也能工作（同时打开时其实就是四个报文），只是没必要：服务器的"确认"和"自己的 SYN"可以放在同一个报文里发出，合并后三次已经足以完成全部目标。三次是满足可靠同步的最少次数。

    ✅ 面试答法：为什么是三次握手？

    三次握手的目的是同步双方的初始序号并确认双向通路。三次是最少次数：① 主要原因是防止历史连接，旧的 SYN 到达服务器后，客户端可以在第三步通过 RST 否决，两次握手做不到；② 双方的 ISN 都需要被对方确认，两次只能确认客户端的；③ 两次握手下，重传的重复 SYN 会让服务器建立多条无用连接。不需要四次，因为服务器的 ACK 和 SYN 可以合并在一个报文里。

    5.6 SYN Flood 攻击与防御

    原理

    攻击者伪造大量不存在的源 IP 发送 SYN。服务器为每个 SYN 在半连接队列中分配一个条目并回复 SYN+ACK，但这些 SYN+ACK 发往不存在的地址，永远收不到第三次握手的 ACK。每个半连接要等 SYN+ACK 重传若干次（Linux 默认 tcp_synack_retries=5，总计约 63 秒）才会被清理。只要攻击者发送 SYN 的速度超过清理速度，半连接队列很快就会被占满，正常用户的 SYN 被丢弃，服务不可用。它的厉害之处在于：攻击者几乎没有成本（不需要维持任何状态），却能耗尽服务器的资源——这是"状态不对称"导致的。

    防御手段

    手段做法作用

    本章小结
    • 三次握手：SYN(seq=x) → SYN+ACK(seq=y, ack=x+1) → ACK(ack=y+1)；状态 C：SYN_SENT → ESTABLISHED，S：LISTEN → SYN_RCVD → ESTABLISHED。
    • SYN 不带数据但占 1 个序号；第三次握手可以携带数据；accept 不参与握手。
    • ISN 随机且随时间递增：防止与旧连接混淆、防止序号预测攻击（RFC 6528）。
    • 为什么三次：防历史连接（首要）、同步双方 ISN、避免重复连接；ACK 与 SYN 合并所以不需要四次。
    • 半连接队列（tcp_max_syn_backlog）/ 全连接队列（min(backlog, somaxconn)）；全连接队列满默认丢第三次 ACK。
    • SYN Flood 利用状态不对称耗尽半连接队列；SYN Cookie 把状态编码进 ISN；另有调参、SYN Proxy、清洗。
    • 异常：SYN 丢 → 客户端退避重传；SYN+ACK 丢 → 双方都重传；ACK 丢 → 服务端重传，客户端的数据段可代替 ACK。
    思考题 1：第三次握手的 ACK 丢了，客户端紧接着发送了数据，会发生什么？

    客户端发送的数据段同样带 ACK 标志、ack = y+1。服务器在 SYN_RCVD 状态收到它，确认号正确，于是直接进入 ESTABLISHED 并接收数据（相当于第三次握手的 ACK "搭了数据的便车"）。所以第三次 ACK 丢失通常不会造成影响。只有在客户端一直不发数据、而服务器的 SYN+ACK 重传全部失败时，服务器才会删除这个半连接，客户端之后再发数据会收到 RST。

    思考题 2：服务器 listen(fd, 1024)，但 net.core.somaxconn = 128，全连接队列多大？大量短连接突发时会怎样？

    全连接队列上限取两者较小值 128。突发时如果应用 accept 不够快，队列溢出，默认会丢弃第三次握手的 ACK，表现为客户端连接成功但请求超时、服务器重传 SYN+ACK、客户端出现 1 秒以上的延迟。排查：ss -lnt 看 Recv-Q 是否接近 Send-Q，netstat -s | grep overflowed 看溢出计数。解决：调大 somaxconn 和 backlog，提高 accept 效率（多线程 / SO_REUSEPORT 多个监听 socket）。

    思考题 3：为什么 SYN Cookie 默认只在半连接队列满时才启用，而不是一直开着？

    因为 SYN Cookie 有代价：服务器不保存状态，就不能重传丢失的 SYN+ACK；MSS 只能取少数几个预设值之一；窗口扩大、SACK 等选项只有在开启时间戳时才能部分编码保存，否则会丢失，影响高带宽链路的性能。正常情况下用完整的半连接队列能获得最好的连接质量，只有在被攻击（队列溢出）时才退而求其次。

    思考题 4：客户端 connect 一个公网服务器，30 秒都没有返回，可能是什么原因？

    说明客户端一直处于 SYN_SENT，在指数退避重传 SYN，从未收到任何回应（收到 RST 会立即失败）。可能原因：① 服务器或中间防火墙静默丢弃了 SYN（安全组未放行端口最常见）；② 路由不可达但 ICMP 被过滤；③ 服务器半连接队列满且没开 SYN Cookie；④ 服务器的 SYN+ACK 在回程被丢弃（例如非对称路由被防火墙拦截）。排查可在两端抓包对照，或用 tcptraceroute 看 SYN 走到了哪一跳。

    6.2 为什么是四次？什么时候会是三次？

    建立连接时，服务器的 SYN 和 ACK 可以合并，是因为服务器收到 SYN 时"没有什么需要等待的"，可以立刻发出自己的 SYN。关闭时则不同：收到对方 FIN 只说明对方不再发数据，自己可能还有数据没发完。所以 ACK（内核立即回）和 FIN（等应用处理完、调用 close 时才发）通常分两次发出，中间就是半关闭阶段。

    🔬 抓包时常看到的"三次挥手"

    如果被动方收到 FIN 时恰好没有待发数据，且应用很快就调用了 close（例如 HTTP 服务器读到 EOF 后立即关闭），由于延迟确认的存在，内核还没来得及发出单独的 ACK，FIN 就已经要发了，于是 ACK 和 FIN 合并成一个 FIN+ACK 报文，挥手就变成了 3 个报文。这完全合法，并不违反协议——"四次"是逻辑上的四个动作，不是必须的四个报文。

    ✅ 面试答法：为什么挥手要四次？

    因为 TCP 是全双工的，两个方向需要分别关闭。主动方发 FIN 只表示它不再发送数据，但还能接收；被动方收到 FIN 后先由内核回 ACK，此时它可能还有数据要发，必须等应用发完并调用 close 才能发出自己的 FIN，所以 ACK 和 FIN 一般不能合并，总共四次。如果被动方此时没有数据要发，且启用了延迟确认，ACK 和 FIN 可以合并，就会变成三次。

    6.3 TIME_WAIT：面试最爱问的状态

    为什么需要 TIME_WAIT

    为什么是 2MSL

    MSL（Maximum Segment Lifetime）是报文在网络中的最大生存时间。等待 2MSL 可以覆盖最坏情况：最后的 ACK 在路上最多走 1 个 MSL 后丢失，对方超时重传的 FIN 最多再走 1 个 MSL 到达——一来一回。同时，2MSL 也足以让两个方向上旧连接的所有报文都在网络中消亡。

    TIME_WAIT 过多有什么危害

    TIME_WAIT 在主动关闭方产生。每个 TIME_WAIT 只占很少的内存（Linux 有专门的轻量结构），真正的问题是它占用四元组：

    • 客户端（或作为客户端的代理 / 网关）：频繁对同一个 服务器IP:端口 发起短连接并主动关闭，本地临时端口（约 2.8 万个）会被 TIME_WAIT 占满，新的 connect 报错 EADDRNOTAVAIL（端口耗尽）。按 60 秒计，每秒超过约 470 个新连接就会耗尽。
    • 服务器：服务端作为主动关闭方（如 HTTP 短连接由服务器关闭）时也会积累大量 TIME_WAIT，但由于对端 IP 和端口各不相同，一般不会耗尽什么，主要是统计数字吓人；监控和表项数量（tcp_max_tw_buckets）需要关注。

    让客户端主动关闭TIME_WAIT 落在分散的客户端上需要协议配合（如 HTTP 的 Connection: close 由谁发起）
    SO_LINGER {on, 0}close 时直接发 RST，不进入 TIME_WAIT危险：未发送的数据被丢弃，对端收到"连接被重置"；只在明确知道后果时使用
    ⚠️ 易错点：SO_REUSEADDR 和 TIME_WAIT 是什么关系？

    服务器进程重启时 bind(:8080) 报 "Address already in use"，往往是因为旧进程的连接还有 TIME_WAIT 占着 8080。设置 SO_REUSEADDR 后，即使有 TIME_WAIT 连接，也允许监听 socket 绑定该端口（Linux 语义）。所以服务器的监听 socket 几乎都应该设置 SO_REUSEADDR。它解决的是"重启 bind 失败"，和"客户端端口耗尽"是两个不同的问题。另外注意 Windows 上 SO_REUSEADDR 的语义不同（允许抢占端口），应使用 SO_EXCLUSIVEADDRUSE 保护服务端口。

    6.4 CLOSE_WAIT 与 FIN_WAIT_2：两种"卡住"

    大量 CLOSE_WAIT：几乎一定是你的 bug

    CLOSE_WAIT 表示"对方已经关了，我的应用还没 close"。内核不会替应用关闭，所以如果代码在读到 EOF（recv 返回 0）后忘了 close，或者异常分支漏掉了 close，或者连接池没有检测并回收被对端关闭的连接，CLOSE_WAIT 就会一直堆积，直到耗尽文件描述符。
    排查：ss -tanp state close-wait 找到进程和对端，再检查对应代码路径。

    FIN_WAIT_2 悬挂：等对方的 FIN

    主动方发完 FIN 收到 ACK 后，要等对方发 FIN。如果对方迟迟不关（正好处于 CLOSE_WAIT 的 bug 状态），主动方就挂在 FIN_WAIT_2。
    如果主动方是用 close() 关闭的（连接已成为孤儿），Linux 最多等 tcp_fin_timeout（默认 60 秒）后直接回收；如果是用 shutdown(SHUT_WR) 关闭的，应用还能读，内核会一直等。

    6.5 挥手过程中的异常

    异常谁会察觉处理
    ① FIN 丢失主动方收不到 ACK主动方在 FIN_WAIT_1 超时重传 FIN；孤儿连接的重传次数由 tcp_orphan_retries 控制，耗尽后直接关闭
    ② ACK 丢失主动方收不到 ACK主动方重传 FIN，被动方（已在 CLOSE_WAIT）再次回 ACK；若被动方的 FIN 先到，主动方从 FIN_WAIT_1 收到 FIN+ACK 也能直接进入 TIME_WAIT
    ③ 被动方的 FIN 丢失被动方收不到 ACK被动方在 LAST_ACK 重传 FIN；主动方仍在 FIN_WAIT_2 等待（孤儿连接最多等 tcp_fin_timeout）
    ④ 最后的 ACK 丢失被动方收不到 ACK被动方重传 FIN；主动方在 TIME_WAIT 中重发 ACK 并重置 2MSL 计时器（图 6-2 左）
    同时关闭双方同时发 FIN双方：FIN_WAIT_1 → 收到对方 FIN → CLOSING → 收到 ACK → TIME_WAIT。双方都会有 TIME_WAIT
    进程崩溃 / 被 kill—进程退出时内核会关闭它所有的 fd，照常发送 FIN，对端看到的是正常关闭（若接收缓冲区有未读数据则发 RST）
    主机断电 / 网线被拔对端完全不知道没有任何报文发出，对端连接会一直保持 ESTABLISHED（"半打开"连接），直到它发送数据超时，或者 Keepalive / 应用心跳探测失败
    close 时接收缓冲区还有未读数据对端收到 RSTLinux 会直接发 RST 而不是 FIN（RFC 2525 建议的行为），提示对方"你发的数据我没读到"

    6.6 RST：不体面但有时必要的结束方式

    RST（Reset）表示"立即终止连接，不用再回复"。它不需要确认，收到 RST 的一方立即释放连接，并把未发送的数据全部丢弃，应用的下一次读写会得到 ECONNRESET（"Connection reset by peer"）；发 RST 的一方也不会进入 TIME_WAIT。常见触发场景：

    • SYN 发往无人监听的端口（第 5 章 E3 实测）；
    • 收到不属于任何连接的报文（例如服务器重启后，客户端仍用旧连接发数据）；
    • 设置了 SO_LINGER {1, 0} 后调用 close（下方实测）；
    • close 时接收缓冲区有未读数据；
    • 防火墙、负载均衡主动掐断连接（"连接被重置"在跨境网络中很常见）。

    close() 与 shutdown() 的区别

    close(fd)shutdown(fd, SHUT_WR)
    作用对象文件描述符：引用计数减 1，减到 0 才真正关闭连接（fork 后父子进程共享 socket 时要注意）直接作用于连接，不管有多少个 fd 引用
    方向同时关闭读和写可以只关写（发 FIN）、只关读、或都关
    之后还能读吗不能（连接成为孤儿）SHUT_WR 后仍然可以读，用于"半关闭"
    典型用途普通关闭"我发完了，但还要等你的回复"：例如客户端上传完文件后 shutdown 写端，再读取服务器的结果

    6.7 保活：Keepalive 与应用层心跳

    "主机断电"那一行说明：TCP 本身无法及时发现对端消失。TCP 提供了 Keepalive 机制，但默认参数非常保守：

    参数（Linux）默认值含义
    tcp_keepalive_time7200 秒连接空闲 2 小时后才开始探测
    tcp_keepalive_intvl75 秒探测间隔
    tcp_keepalive_probes9 次连续失败多少次判定断开

    默认要 2 小时 11 分钟才能发现死连接，且 Keepalive 需要每个 socket 用 SO_KEEPALIVE 显式开启（可以用 TCP_KEEPIDLE 等选项为单个连接缩短时间）。更重要的是，Keepalive 只能证明对端内核还活着，证明不了对端应用没有卡死。

    🎮 游戏开发视角：为什么游戏都用应用层心跳

    游戏需要在几秒内发现玩家掉线（以便托管 AI 接管、通知队友、判定逃跑），而且要知道的是"客户端逻辑是否还在运行"。所以几乎所有游戏都在应用层每隔 1～5 秒发一个心跳包，服务器若连续 N 个周期没有收到任何包就判定断线。心跳还能顺便测量 RTT、给 NAT 映射保活（UDP 尤其需要）。对于基于 UDP 的可靠协议，这就是它的"连接管理"的一部分（第 8 章）。

    思考题 1：服务器上用 netstat 看到大量 TIME_WAIT，说明了什么？要不要处理？

    说明这台服务器是大量连接的主动关闭方，常见于 HTTP 短连接（服务器响应完主动关闭）或服务器作为客户端去调用下游（数据库、其他服务）且使用短连接。如果是前者，TIME_WAIT 只占少量内存，四元组也不冲突，一般不影响服务，可以通过开启 Keep-Alive 减少；如果是后者，要警惕本地端口耗尽，应改用连接池，或开启 tcp_tw_reuse。不建议用 SO_LINGER 0 粗暴消灭 TIME_WAIT。

    思考题 2：线上服务出现几千个 CLOSE_WAIT，并且还在增长，你怎么排查？

    CLOSE_WAIT 表示对端已关闭而本端应用没有调用 close。① 用 ss -tanp state close-wait 找到所属进程和对端地址，确认是和哪个下游 / 客户端的连接；② 检查对应代码：读到 EOF（返回 0）后是否 close，异常、超时分支是否 close，连接池是否在借出前检测连接可用、归还时是否处理已关闭的连接；③ 检查是否有线程阻塞导致处理不过来（例如 accept 后一直没处理）；④ 修复前可以临时重启进程释放 fd。CLOSE_WAIT 不会因为内核超时自动消失。

    思考题 3：为什么 TIME_WAIT 放在主动关闭方，而不是被动关闭方？

    因为发出"最后一个 ACK"的是主动关闭方：只有它需要确保这个 ACK 送达（对方没收到会重传 FIN，自己要能再回 ACK），也只有它在发出最后一个报文后需要等旧报文消亡。被动方在收到最后的 ACK 时就已确认双方都关闭完毕，没有不确定性，可以直接进入 CLOSED。

    思考题 4：客户端进程被 kill -9 和客户端机器断电，服务器看到的现象有什么不同？

    kill -9 时进程虽然没有机会执行清理代码，但内核会关闭它的所有 socket，正常发送 FIN（若有未读数据则发 RST），服务器很快就会读到 EOF 或 ECONNRESET。机器断电时没有任何报文发出，服务器上的连接仍然是 ESTABLISHED：如果服务器不发数据，它永远不会知道；如果发数据，会经历一段 RTO 重传（Linux 默认 tcp_retries2=15，约十几分钟）后才报错。所以需要 Keepalive 或应用层心跳。

    7.1 TCP 在实时场景下的六个痛点

    #痛点来自哪个机制实时场景下的后果能在 TCP 内解决吗
    1队头阻塞按序可靠交付（第 3、4 章）一个包丢了，后面所有新数据都要等它不能，这是 TCP 语义本身
    2重传慢RTO 下限 200 ms、指数退避；快速重传需要 3 个重复 ACK小流量时凑不够 3 个重复 ACK，只能等 RTO；连续丢包时等待时间翻倍增长部分（Linux 可按路由调 rto_min，有 TLP/RACK，但不能每个连接随意改）
    3拥塞控制误判丢包即拥塞（Reno / CUBIC）无线随机丢包导致窗口被压缩，数据在发送缓冲排队，延迟越积越大部分（可换 BBR，但不能关掉）
    4延迟确认 + Nagle减少小包的优化（第 3 章）额外 40～200 ms能（TCP_NODELAY、TCP_QUICKACK）
    5握手与换网三次握手 + TLS；连接绑定四元组首包 2～3 RTT；Wi-Fi 切 4G 时 IP 变化，连接直接断开，要重新握手基本不能（TFO 部署受限；MPTCP 不普及）
    6一视同仁 + 难以迭代实现在内核；中间设备僵化不能对不同消息选择不同的可靠性 / 优先级；新算法要等操作系统升级不能
    📦 场景案例：一次 300 ms 的"卡顿"是怎么来的

    手游玩家在地铁里，网络 RTT 80 ms、丢包率 5%。游戏每 66 ms 发一个操作包（15 Hz），用 TCP 承载。某个包丢了：
    ① 后面每 66 ms 才有一个新包，要凑够 3 个重复 ACK 需要约 200 ms，往往还没凑够 RTO 先到了；
    ② 于是等到 RTO（≥ 200 ms，弱网下 RTTVAR 大，RTO 常常 300 ms 以上）才重传；
    ③ 这期间到达的所有新操作都被队头阻塞挡在内核缓冲区里；
    ④ 重传成功后，积压的操作一起交付，角色表现为"卡住 → 瞬移"。如果重传的包又丢了，RTO 翻倍，卡顿就变成 600 ms 以上。
    而同样的网络，用 UDP + 应用层可靠，可以做到"后面的包不等前面"（痛点 1）、"被跳过 2 次就重传"（痛点 2）、"每个包都冗余携带最近 3 帧操作"（干脆不需要重传），把卡顿压到一个 RTT 甚至零。

    ✅ 面试答法：为什么游戏要用可靠 UDP 而不是 TCP？

    核心是"可靠性可选"。游戏数据分为不同类别：位置等状态只要最新值，丢了不需要重传；技能、交易等事件必须送达但不一定需要和其他消息保持顺序；帧同步的输入需要可靠有序。TCP 只能对所有数据提供可靠有序的字节流，一个丢包会通过队头阻塞拖累所有数据，加上 RTO 下限高、指数退避、拥塞控制把随机丢包当拥塞，弱网下延迟抖动很大。在 UDP 上自己实现，可以按消息类型分通道、选择不同可靠级别，并且激进地调整重传策略（如 KCP 的 RTO×1.5、快速重传阈值 2），用一些带宽换取更低更稳定的延迟。

    这张图同时回答了"KCP 和 QUIC 有什么区别"这个常见问题：KCP 是一个纯 ARQ 算法库，只负责第 ③ 层，连接、加密、FEC 都要使用者自己补；QUIC 是一个完整的传输协议，从流复用到加密到连接迁移全都标准化了，可以直接替代 TCP + TLS。

    7.4 代价与风险：不要为了"用 UDP"而用 UDP

    复杂度与正确性

    可靠传输的边界情况极多：序号回绕、重传歧义、窗口死锁、ACK 风暴、分片丢失、重连时的状态残留……TCP 用了四十年打磨，自研协议的 bug 往往在线上弱网环境才暴露。

    网络环境的敌意

    部分运营商对 UDP 做 QoS 限速，部分企业 / 校园网直接封禁 UDP，一些公共 Wi-Fi 的 NAT 对 UDP 映射超时极短。必须准备 TCP 兜底通道并做自动降级。

    CPU 开销

    用户态协议栈没有 TCP 的硬件卸载（TSO/GRO），每个包都要系统调用、加解密、定时器管理。服务器端单机承载量可能明显低于 TCP，需要批量收发、多线程分片等优化。

    网络公平性

    "关掉拥塞控制"在一个玩家的手机上很好，在一个网吧几十台机器同时这么做时就会互相挤爆出口带宽。至少要有发送速率上限，以及在 RTT 明显上升时主动降级。

    本章小结
    • TCP 的实时痛点：队头阻塞、重传慢（RTO 下限 + 退避）、拥塞误判、Nagle/延迟确认、握手与换网断连、一视同仁且难迭代。
    • 可靠性光谱 = {可靠, 不可靠} × {无序, 只要最新, 有序}；游戏数据大多落在"不可靠 · 只要最新"和"可靠 · 无序"。
    • RakNet / ENet / UE 的可靠性分级与光谱一一对应；UE 属性复制属于"可靠 · 只要最新"。
    • 可靠 UDP 六层：通道调度、分片、可靠传输、拥塞 / FEC、安全、连接管理。KCP 只做可靠传输层，QUIC 做全部。
    • 代价：复杂度、UDP 被限速 / 封禁（需 TCP 兜底）、CPU 开销、公平性。
    思考题 1：为什么"不可靠 · 严格有序"基本没有用途？

    严格有序意味着第 n 个包没到时，第 n+1 个包必须等待；而不可靠意味着第 n 个包可能永远不会再来（没有重传）。两者组合的结果就是接收方可能无限期等待，或者只能设置一个超时后放弃第 n 个包继续往下交付——这时它实际上退化成了"只要最新 / 允许跳号"的语义。所以实际协议里提供的都是"sequenced（丢弃过期的）"而不是"ordered（等待缺失的）"。

    思考题 2：一个 MOBA 游戏中，以下数据分别应该放在可靠性光谱的哪一格？英雄位置、技能释放指令、击杀公告、小地图信号、商店购买、结算数据。

    英雄位置：不可靠 · 只要最新。技能释放指令：在状态同步架构下是可靠事件（可靠 · 无序或与同一英雄的其他指令有序）；在帧同步架构下属于输入流的一部分，可靠有序。击杀公告：可靠 · 无序（丢了玩家会错过信息，但不必和别的消息排序；也可以设计成不可靠，由状态推导）。小地图信号：不可靠或可靠无序均可，看产品要求。商店购买：可靠（并且要服务器确认结果）。结算数据：可靠，且通常走 TCP/HTTP 等更稳妥的通道。

    思考题 3：既然 QUIC 已经标准化了，为什么很多游戏还是用 KCP 或自研协议？

    ① QUIC 的流仍然是"可靠有序"的语义（虽然流之间没有队头阻塞），对"不可靠 · 只要最新"的状态数据支持有限（需要 RFC 9221 的 DATAGRAM 扩展）；② QUIC 强制 TLS 1.3 加密和较复杂的握手，客户端和服务器的 CPU、包体开销较大；③ QUIC 的拥塞控制和重传策略遵循 RFC 9002，偏向公平和吞吐，而游戏更想要激进的低延迟策略；④ KCP 代码量小、可以嵌入任意引擎和平台、参数可调，且游戏已有成熟的连接和加密方案。当然，随着 QUIC 库的成熟（以及 DATAGRAM 扩展），也有游戏开始采用。

    8.2 序列号：回绕与比较

    序号字段总有上限：32 位约 43 亿，16 位只有 65536。游戏每秒 60 个包，16 位序号 18 分钟就会回绕。回绕后 5 < 65530 这样的直接比较就错了。正确做法是序列号算术（RFC 1982）：把差值解释成有符号数。

    回绕安全的序号比较（TCP 内核中的 before()/after() 也是这么写的）
    // a 是否"在 b 之后"：差值按有符号数解释，只要两者相距不超过序号空间的一半就是对的
inline bool SeqAfter(uint32_t a, uint32_t b)  { return int32_t(a - b) > 0; }
inline bool SeqBefore(uint32_t a, uint32_t b) { return int32_t(a - b) < 0; }
inline int32_t SeqDiff(uint32_t a, uint32_t b) { return int32_t(a - b); }

// 16 位序号同理（Glenn Fiedler 的游戏网络协议就用 16 位以节省包头）
inline bool Seq16After(uint16_t a, uint16_t b) { return int16_t(uint16_t(a - b)) > 0; }

// 例：Seq16After(5, 65530) == true，因为 (uint16_t)(5 - 65530) = 11 > 0
    ⚠️ 易错点：窗口必须小于序号空间的一半

    如果在途的包跨度超过序号空间的一半，SeqAfter 就无法分辨"新包"和"很旧的包"。所以发送窗口必须远小于 231（32 位）或 215（16 位）。TCP 在高速网络中序号回绕更快（10 Gbps 下 32 位字节序号只要 3.4 秒），所以要靠时间戳选项做 PAWS 保护。

    8.3 确认：三种方式及其组合

    方式做法优点缺点代表
    逐包 ACK每收到一个包，回一条 ACK(sn, ts)，可以把多条合并进一个包信息最精确，每条都能测 RTTACK 本身丢了就丢了这条信息；ACK 量大KCP 的 ACK 列表
    累计确认 UNA只告诉对方"una 之前的全收到了"一个数字就能确认很多包，对 ACK 丢失不敏感（下一个 ACK 包含了上一个的信息）无法表达"una 之后收到了哪些"，会导致不必要的重传TCP 的 ack、KCP 的 una
    ACK 位图una（或最新收到的 sn）+ 后续 32 个包的接收位图高度冗余：同一个包的确认信息会在连续 32 个 ACK 里重复出现，ACK 丢几个也无所谓只能覆盖 32（或 64）个包的范围Glenn Fiedler《Reliability over UDP》、很多游戏引擎
    🎮 游戏开发视角：ACK 捎带与"ACK 也会丢"

    游戏双向都在持续发包（客户端发输入，服务器发状态），所以确认信息捎带在每个数据包的头部里，几乎没有单独的 ACK 包。由于每个包都带"最近 32 个包的接收情况"，即使一半的包都丢了，发送方仍然能收到足够的确认信息。这比 TCP 的"一个 ACK 丢了就只能等下一个"要健壮得多。

    8.4 超时重传：RTT、RTO 与退避

    测量 RTT

    发送时在包头写入当前时间 ts，接收方在确认中原样回显，发送方收到后 rtt = now − ts。因为回显的是那一次发送的时间戳，重传的包也能被正确采样，不存在重传歧义。计算 RTO 时直接套用 RFC 6298 的公式（第 3 章），差别在于各个参数可以自由调整：

    参数TCP（Linux）可靠 UDP 常见取值考虑
    RTO 下限200 ms30～100 ms（KCP 极速模式 30 ms）越小重传越快，但 RTT 抖动大时会产生伪重传
    超时后退避× 2（指数）× 1.5（KCP）、固定不退避、或设上限（如不超过 4×SRTT）退避是为了在严重拥塞时让网络喘口气；实时应用更怕等
    定时器粒度每连接一个重传定时器每个包各自记录 resend_at，由一个固定周期的 update 统一检查按包定时更灵活；update 周期（KCP 的 interval，常设 10 ms）决定了时延精度
    快速重传阈值3 个重复 ACK被后续包"跳过" 2 次（KCP resend=2）越小越快，但对乱序越敏感

    快速重传：用"跳过次数"代替"重复 ACK"

    有了逐包确认或 ACK 位图，就不需要靠重复 ACK 去猜了：每当发送方得知某个比 X 更大的包已被收到，就给 X 的 fastack 计数加一；计数达到阈值就立即重传 X。图 8-2 中的 101 已经被 102、103、105、108 跳过了 4 次。

    🔬 实现细节：别对刚重传的包重复计数

    如果 X 刚被重传过，那些在重传之前就已经发出的更大的包，它们的确认会继续"跳过" X，导致 X 被反复快速重传。严谨的做法是：只有发送时间晚于 X 最近一次发送的包被确认，才算一次有效跳过（这就是 Linux RACK 算法的思想）。KCP 选择了更简单的做法：照常计数，但用 fastlimit（默认 5）限制一个包最多被快速重传几次——宁可多发一点，也不要等。本书的仿真程序两种都实现了。

    8.5 三种 ARQ 策略

    ARQ（Automatic Repeat reQuest，自动重传请求）是"确认 + 超时重传"这一类机制的统称。按照一次允许多少个未确认的包和出错时重传哪些包，分为三种：

    信道利用率

    设发送一个包需要 T（发送时延 = 包长 / 带宽），往返时延 RTT，窗口 W 个包，无丢包时的利用率：

    滑动窗口的信道利用率
    U = min(1,  W × T / (T + RTT))

停等（W=1）：T = 1 ms（1200 字节 @ ~10 Mbps），RTT = 60 ms  →  U = 1 / 61 ≈ 1.6%
滑动窗口 W=64：                                         →  U = min(1, 64 / 61) = 100%
跑满带宽所需的最小窗口 W ≥ (T + RTT) / T ≈ RTT / T = 带宽时延积（以包为单位）

    这就是为什么第 3 章说"窗口要至少等于 BDP"。三种 ARQ 的完整对比：

    停等回退 N 步（GBN）选择重传（SR）
    发送窗口1NN
    接收窗口11（只收按序包）N（缓存乱序包）
    确认方式逐包累计确认逐包 / 选择确认（+ 累计）
    出错时重传当前包从丢失包开始的整个窗口只重传丢失的包
    序号空间要求≥ 2≥ N + 1≥ 2N（否则新旧包混淆）
    适用低速 / 简单链路低误码率链路高时延、有丢包的链路（TCP+SACK、KCP、QUIC 都属于此类）

    8.6 滑动窗口与流量控制

    发送端维护三个窗口取最小值：可发送数 = min(本地发送窗口, 对端通告的接收窗口 wnd, 拥塞窗口 cwnd) − 在途包数。接收端在每个包头里填写 wnd = 接收缓冲区剩余槽位。

    • 窗口为 0 时：和 TCP 一样会有"窗口更新包丢了导致双方死等"的风险。KCP 的做法是发送方定时发送 WASK（询问窗口）命令，接收方回 WINS（告知窗口）——相当于 TCP 的零窗口探测。
    • 接收窗口要比发送窗口大：KCP 默认发送窗口 32、接收窗口 128。因为接收方还要容纳乱序到达的包，接收窗口太小时，乱序包会因为"超出窗口"被丢弃，然后被重传。

    8.7 乱序处理与去重：接收端环形缓冲

    接收端：乱序重排 + 去重 + 按序交付（可靠有序通道）
    struct Receiver {
    static constexpr uint32_t kWnd = 128;
    uint32_t rcvNxt = 0;                                   // 下一个期望交付的 sn
    std::array<std::optional<std::string>, kWnd> slots;    // 环形缓冲，下标 sn % kWnd
    std::vector<uint32_t> ackList;                         // 待回复的确认

    void OnData(uint32_t sn, std::string payload, auto&& deliver) {
        ackList.push_back(sn);                             // ① 不管新旧，先记下要确认（重复包也要确认）
        if (SeqBefore(sn, rcvNxt)) return;                 // ② 已经交付过的旧包：去重
        if (SeqDiff(sn, rcvNxt) >= int32_t(kWnd)) return;  // ③ 超出接收窗口：丢弃，等对方重传
        auto& slot = slots[sn % kWnd];
        if (slot) return;                                  // ④ 窗口内的重复包：去重
        slot = std::move(payload);                         // ⑤ 乱序暂存
        while (slots[rcvNxt % kWnd]) {                     // ⑥ 从 rcvNxt 起把连续的包按序交付
            deliver(std::move(*slots[rcvNxt % kWnd]));
            slots[rcvNxt % kWnd].reset();
            ++rcvNxt;
        }
    }
    uint16_t Wnd() const { /* 剩余空槽数，填进包头的 wnd */ return uint16_t(kWnd - CountUsed()); }
    uint32_t Una() const { return rcvNxt; }
    uint32_t AckBits() const {                             // una+1 .. una+32 的接收位图
        uint32_t bits = 0;
        for (uint32_t i = 1; i <= 32 && i < kWnd; ++i) if (slots[(rcvNxt + i) % kWnd]) bits |= 1u << (i - 1);
        return bits;
    }
    uint32_t CountUsed() const { uint32_t n = 0; for (auto& s : slots) n += s.has_value(); return n; }
};

    8.8 发送端：定时驱动的主循环

    可靠 UDP 通常由一个固定周期（例如每 10 ms）调用的 Update(now) 驱动：检查超时、处理快速重传、在窗口允许时发送新数据、把 ACK 和数据合并成包发出去。

    发送端：超时重传 + 快速重传 + 窗口发送（选择重传）
    struct Segment { uint32_t sn; uint32_t ts; uint32_t resendAt; uint32_t rto; int xmit = 0; int fastack = 0; std::string data; };

struct Sender {
    std::deque<std::string> sendQueue;         // 应用提交、尚未进入窗口的消息
    std::map<uint32_t, Segment> sendBuf;       // 已发送未确认（按 sn 有序）
    uint32_t sndNxt = 0, sndUna = 0, rmtWnd = 128, sndWnd = 64;
    RttEstimator rtt;                          // SRTT / RTTVAR / RTO（RFC 6298）
    int fastResend = 2; double backoff = 1.5;  // KCP 极速模式的取值

    void OnAck(uint32_t una, uint32_t ackBits, uint32_t echoTs, uint32_t now) {
        rtt.Sample(now - echoTs);                                  // 时间戳回显：重传包也能采样
        for (auto it = sendBuf.begin(); it != sendBuf.end() && SeqBefore(it->first, una);) it = sendBuf.erase(it);
        uint32_t maxAcked = una - 1;
        for (int i = 0; i < 32; ++i) if (ackBits >> i & 1) { sendBuf.erase(una + 1 + i); maxAcked = una + 1 + i; }
        for (auto& [sn, seg] : sendBuf) if (SeqBefore(sn, maxAcked)) seg.fastack++;   // 被更大的包"跳过"
        sndUna = sendBuf.empty() ? sndNxt : sendBuf.begin()->first;
    }

    void Update(uint32_t now, auto&& output) {
        for (auto& [sn, seg] : sendBuf) {
            bool timeout = int32_t(now - seg.resendAt) >= 0;
            bool fast = fastResend > 0 && seg.fastack >= fastResend;
            if (!timeout && !fast) continue;
            if (timeout) seg.rto = std::min<uint32_t>(uint32_t(seg.rto * backoff), 10000);   // 温和退避
            seg.xmit++; seg.fastack = 0; seg.ts = now; seg.resendAt = now + seg.rto;
            output(seg);                                                                     // 只重传这一个
        }
        uint32_t cwnd = std::min(sndWnd, rmtWnd);                                            // (+ 拥塞窗口)
        while (!sendQueue.empty() && SeqDiff(sndNxt, sndUna) < int32_t(cwnd)) {
            Segment seg{sndNxt++, now, now + rtt.Rto(), rtt.Rto(), 1, 0, std::move(sendQueue.front())};
            sendQueue.pop_front();
            output(seg);
            sendBuf.emplace(seg.sn, std::move(seg));
        }
    }
};

    8.9 拥塞避免：关掉它之前要想清楚

    可靠 UDP 的拥塞控制有三种常见取舍：

    策略做法适用
    照搬 TCP在用户态实现慢启动 / AIMD，或 CUBIC、BBR（QUIC 就是这样）大流量传输（文件、视频），需要与其他流公平共享
    关闭拥塞窗口 + 限速KCP nc=1，再用令牌桶限制最大发送速率；发送窗口仍受接收窗口限制游戏：流量小（几 KB/s～几十 KB/s）而稳定，远低于瓶颈带宽，丢包多为随机丢包
    基于时延的降级监测 RTT 相对基线的上升（排队在加剧）或丢包率突增，主动降低快照频率 / 精度游戏、实时音视频（WebRTC 的 GCC 算法就是基于时延梯度）
    令牌桶限速：允许短时突发，长期速率不超过 rate
    struct TokenBucket {
    double rate, burst, tokens, last;            // rate：字节/秒；burst：桶容量
    bool TrySend(size_t bytes, double nowSec) {
        tokens = std::min(burst, tokens + (nowSec - last) * rate);
        last = nowSec;
        if (tokens < bytes) return false;        // 令牌不够：本轮先不发（留在队列里）
        tokens -= bytes;
        return true;
    }
};

    8.10 用带宽换延迟：冗余发送与 FEC

    重传至少要付出一个 RTT 的代价。如果能预先多发一些数据，让接收方在部分丢包时自己恢复出原文，就可以完全不等重传。

    冗余发送（游戏最常用）

    每个包除了本帧的输入，还捎带最近 k 帧的输入。只要连续 k+1 个包没有全丢，接收方就能拿到每一帧。独立丢包率为 p 时，残余丢失率约为 pk+1：p=10%、k=3 时只有万分之一。输入数据很小（几字节到几十字节），冗余几乎不增加带宽。

    FEC 前向纠错

    每 n 个数据包额外生成 m 个校验包，收到任意 n 个就能恢复全部。最简单的是异或（m=1）；Reed-Solomon 码可以任意配置 (n, m)。实时音视频（WebRTC 的 FlexFEC / ULPFEC）、kcp-go、加速器广泛使用。

    8.11 分片、连接管理与安全

    分片与重组

    大于 MTU 的消息在发送端切片，每片独立编号（占用连续的 sn），并在 frg 字段中标注"后面还有几片"。接收端按序收到 frg = 0 的那一片时，把前面连续的片拼接成完整消息交给应用。KCP 正是这样做的：在消息模式下，ikcp_recv 只有在一条消息的所有分片都到齐后才返回。

    连接管理

    • 握手：客户端发 CONNECT；服务器不分配会话资源，回一个带 Cookie（如 HMAC(客户端地址, 时间, 密钥)）的 CHALLENGE；客户端带着 Cookie 再发一次，服务器校验通过才分配 conv 和会话。这同时防住了"伪造源地址耗尽会话"（SYN Flood 的 UDP 版）和"反射放大"。服务器的第一次回复不应该比客户端的请求大。
    • 会话识别：用 conv 而不是四元组查找会话；收到同一 conv 但源地址变了的包（NAT 重绑定），验证后更新地址。
    • 心跳与断线：没有数据时定期发 PING（顺便测 RTT、保活 NAT 映射）；N 秒内没有收到对方任何包就判定断线。
    • 关闭：发 CLOSE 并重复几次（它也可能丢），对方收到后释放资源；最终仍以超时兜底。

    安全

    UDP 包很容易伪造和篡改。面向公网的可靠 UDP 至少需要：认证加密（AES-GCM / ChaCha20-Poly1305，或直接用 DTLS），包含序号的 nonce 防重放，握手阶段的密钥协商（如 ECDH）。KCP 不提供任何安全能力，kcp-go 提供了多种对称加密可选；QUIC 则强制 TLS 1.3。

    思考题 1：为什么选择重传要求序号空间至少是窗口的 2 倍？

    设窗口为 N。接收方收完一整窗 0～N−1 并发出确认后，接收窗口移动到 N～2N−1。如果这些确认全部丢失，发送方会重传 0～N−1。若序号空间只有 N（序号模 N），重传的旧包 0 和新窗口期望的包 N 编号相同，接收方会把旧包当成新包接收。序号空间 ≥ 2N 时，新旧窗口的序号不重叠，才能区分。

    思考题 2：为什么接收方收到重复包时还要回 ACK？

    发送方重传一个包，说明它没有收到这个包的确认——要么数据包丢了，要么 ACK 丢了。如果是 ACK 丢了，接收方其实已经收到过数据，若此时对重复包不回 ACK，发送方会一直重传下去。所以去重只是"不重复交付给应用"，确认必须照发。

    思考题 3：帧同步游戏中，"每个包冗余携带最近 3 帧输入"和"用 KCP 可靠传输每帧输入"相比，各有什么优缺点？

    冗余发送：不需要等待重传，单包丢失对时延零影响；独立丢包下残余丢失率约 p⁴，非常低；输入数据很小，冗余开销可以忽略。缺点是不能保证 100% 送达（连续 4 个包全丢时缺帧），所以通常还要配合"缺帧时通过可靠通道请求补发"。KCP：保证每帧都送达且有序，但丢包时至少等一次重传（约 1 个 RTT），时延抖动更大。实际工程中常两者结合：冗余发送解决绝大部分丢包，可靠通道兜底。

    思考题 4：如果你的可靠 UDP 只用 UNA 而不用任何选择确认，会退化成哪种 ARQ？

    发送方只知道"una 之前都收到了"，不知道 una 之后哪些已收到。如果接收端会缓存乱序包，发送方在超时时只重传 una 那一个包（下一个 ACK 的 una 会跳到更后面），效果接近选择重传但发现丢包很慢（只能靠超时、每 RTT 修一个洞）；如果发送方超时后把 una 之后的全部重发，就退化成了回退 N 步。这正是 TCP 早期没有 SACK 时的困境。

    9.1 KCP 是什么

    KCP 是由林伟（skywind3000）开源的一个快速可靠传输协议，项目 README 中对它的描述是：能以比 TCP 浪费 10%～20% 带宽的代价，换取平均延迟降低 30%～40%、最大延迟降低三倍的传输效果。它在手游、实时音视频、网络加速器等领域被广泛使用，也衍生出 kcp-go、KCP-Net 等多语言实现。

    纯算法实现

    KCP 不负责收发 UDP，使用者通过回调函数 output 告诉它"怎么把一个包发出去"，收到包后调用 ikcp_input 喂给它。连时钟都由外部传入，内部没有任何系统调用——所以能嵌入任何引擎、平台和 IO 模型。

    只做 ARQ

    对应图 7-2 中的第 ③ 层（外加消息分片）：序号、确认、重传、窗口、拥塞控制。不包含连接建立、会话管理、心跳、加密、FEC，这些都要使用者自己补。

    流速优先，而非流量优先

    TCP 的设计目标是充分利用带宽（每秒传多少 KB）；KCP 的目标是降低单个包从发出到交付的时间（一个包花多少毫秒）。两者的取舍方向不同。

    9.4 接入代码

    KCP 接入骨架（客户端，单会话；省略错误处理）
    #include "ikcp.h"

static int UdpOutput(const char* buf, int len, ikcpcb* kcp, void* user) {
    auto* s = static_cast<Session*>(user);
    return sendto(s->sock, buf, len, 0, (sockaddr*)&s->peer, sizeof s->peer);   // KCP 只管"要发什么"
}

void Init(Session* s, uint32_t conv) {
    s->kcp = ikcp_create(conv, s);           // conv 双方必须一致（通常由服务器在登录时分配）
    s->kcp->output = UdpOutput;
    ikcp_nodelay(s->kcp, 1, 10, 2, 1);       // 极速模式：nodelay=1, interval=10ms, resend=2, nc=1
    ikcp_wndsize(s->kcp, 128, 128);          // 发送 / 接收窗口（默认 32 / 128）
    ikcp_setmtu(s->kcp, 1200);               // 默认 1400；移动网络建议更保守
    s->kcp->rx_minrto = 10;                  // 可选：进一步降低 RTO 下限
}

void Tick(Session* s, uint32_t nowMs) {      // 游戏主循环里每帧调用
    char buf[1500];
    for (int n; (n = recvfrom(s->sock, buf, sizeof buf, 0, nullptr, nullptr)) > 0;)
        ikcp_input(s->kcp, buf, n);          // ① 把收到的 UDP 包喂给 KCP（非阻塞 socket）
    ikcp_update(s->kcp, nowMs);              // ② 驱动时钟：发 ACK、发新数据、检查重传
    for (int n; (n = ikcp_recv(s->kcp, buf, sizeof buf)) > 0;)
        OnMessage(buf, n);                   // ③ 取出按序、完整的消息
}

void Send(Session* s, const void* msg, int len) {
    ikcp_send(s->kcp, (const char*)msg, len);   // 放入 snd_queue，下一次 update/flush 时才真正发出
    // 想更低延迟：ikcp_flush(s->kcp) 立即发送（会多一些小包）
}
    🔬 ikcp_check：服务器上省 CPU 的关键

    服务器上可能有上万个 KCP 会话，每 10 ms 对每个会话调用一次 ikcp_update 很浪费。ikcp_check(kcp, now) 返回"下一次真正需要调用 update 的时刻"（最近的重传时间或下一个 interval），服务器可以把会话按这个时间放进定时器堆或时间轮，只在需要时调度；收到包或有新消息要发时再立即调度一次。

    9.7 工程实践：KCP 之外还要补什么

    KCP 不提供的常见做法
    连接建立与 conv 分配先用 TCP / HTTP 登录拿到 conv 和密钥，再切到 UDP；或者自己实现带 Cookie 的 UDP 握手
    会话识别服务器用 conv 查会话（ikcp_getconv 可以从包头取出 conv），不依赖源地址，可支持 NAT 换端口
    心跳与断线应用层心跳；监控 kcp->state == -1（dead_link）；N 秒无包判定断线
    加密与防篡改在 output / input 处加一层 AEAD 加密；kcp-go 内置了多种加密
    FECkcp-go 内置 Reed-Solomon FEC；或自己实现异或 FEC
    不可靠消息KCP 只有可靠有序一种语义；状态同步等不可靠数据绕过 KCP 直接走 UDP，在同一个 socket 上用首字节区分
    TCP 兜底UDP 不通时自动降级到 TCP（KCP over TCP 没有意义，直接用 TCP 传消息即可）
    ⚠️ 易错点：KCP 不是"更快的 TCP"

    KCP 降低的是丢包场景下的时延和抖动，代价是更多的带宽和 CPU。在不丢包的网络上，KCP 和 TCP 的时延几乎一样（实验 B 的 0% 行）；在大文件下载这类追求吞吐的场景，关闭拥塞控制的 KCP 可能挤占带宽、造成更多丢包，反而得不偿失。用 KCP 之前先确认：你的问题是"延迟抖动"而不是"带宽不够"。

    ✅ 面试答法：KCP 为什么比 TCP 快？

    KCP 是一个运行在 UDP 之上的 ARQ 协议，"快"指的是丢包时延迟更低。它对 TCP 做了几处改动：① 超时重传时 RTO 只乘 1.5 而不是翻倍，RTO 下限也更低；② 选择性重传，只重传丢失的包；③ 快速重传阈值可配（比如被跳过 2 次就重传），不必等 3 个重复 ACK；④ ACK 不做延迟；⑤ 同时使用 UNA 和逐包 ACK；⑥ 可以关闭拥塞控制，避免随机丢包导致降速。代价是 10%～20% 甚至更多的额外带宽，以及需要自己处理连接管理、加密和不可靠消息。

    本章小结
    • KCP：纯算法 ARQ 库，无 IO、无系统调用；只做可靠传输层，不含连接、加密、FEC。
    • 四个队列：snd_queue → snd_buf → output；input → rcv_buf → rcv_queue；由 ikcp_update 时钟驱动。
    • 24 字节头：conv、cmd（PUSH/ACK/WASK/WINS）、frg、wnd、ts、sn、una、len。
    • 六处改动：RTO×1.5、选择重传、快速重传（resend）、非延迟 ACK、UNA+ACK、非退让流控（nc）。
    • 极速模式 ikcp_nodelay(kcp, 1, 10, 2, 1)；窗口默认 32/128，MTU 1400，RTO 下限 100/30 ms。
    • 仿真：随机丢包下拥塞控制是 TCP 时延崩溃的主因；KCP 在此基础上把 P99 再降 40%～70%，多花 16%～37% 带宽。
    思考题 1：KCP 关闭拥塞控制后，会不会把网络挤爆？应该怎么做？

    有可能。nc=1 后发送窗口只受 sndwnd 和对端 rcvwnd 限制，如果应用持续提交超过链路容量的数据，KCP 会把整个窗口塞进网络，造成排队和丢包，丢包又引发更多重传，形成恶性循环。做法：① 只在小流量实时数据（游戏、信令）上关闭拥塞控制；② 合理设置 sndwnd（≈ 期望速率 × RTT / 包长）；③ 应用层令牌桶限速；④ 监控 RTT 和重传率，异常时降低发送频率或数据精度；⑤ 大流量数据（资源下载）走 TCP / HTTP。

    思考题 2：KCP 的 interval 设为 100 ms 和 10 ms，对延迟有什么影响？

    KCP 所有的发送（包括 ACK）都在 flush 中完成，flush 每 interval 执行一次。interval = 100 ms 时，ACK 最多被延迟 100 ms，重传检查的精度也是 100 ms，RTT 测量会偏大，实际延迟明显变差；10 ms 时这些延迟都降到 10 ms 以内，代价是 CPU 占用增加、小包更多。也可以在 ikcp_send / ikcp_input 后主动调用 ikcp_flush 来降低延迟。

    思考题 3：为什么 KCP 的接收窗口默认比发送窗口大（128 vs 32）？

    接收窗口需要容纳乱序到达、等待前面缺失包的数据。如果接收窗口和发送窗口一样大甚至更小，丢包后后续到达的包可能因超出接收窗口被丢弃，引发额外的重传。另外，一条大消息被分成多个分片时，所有分片都要能放进接收窗口，ikcp_recv 才能把整条消息取出，所以 KCP 要求 rcvwnd 不小于最大分片数（源码注释中的 must >= max fragment size）。

    CHAPTER 10

    QUIC：把 TCP + TLS 搬到用户态重写一遍

    KCP 是一个 ARQ 算法，QUIC 是一个完整的、标准化的、加密的传输协议，也是 HTTP/3 的底座。

    本章目标
    • 说清 QUIC 的分层位置和它要解决的四个问题
    • 理解 1-RTT / 0-RTT 握手、连接 ID 与连接迁移
    • 理解 QUIC 的流为什么没有队头阻塞，以及"包号与流偏移分离"如何消除重传歧义
    • 掌握 QUIC 的 ACK 帧、丢包检测（包阈值 / 时间阈值 / PTO）、两级流量控制、可插拔拥塞控制
    • 知道 QUIC 的安全设计（抗放大、Retry、头部保护）与部署代价

    10.1 背景与定位

    QUIC 最早由 Google 于 2012 年前后提出并在 Chrome 中部署（后称 gQUIC），之后由 IETF 标准化：RFC 9000（传输协议）、RFC 9001（与 TLS 1.3 的结合）、RFC 9002（丢包检测与拥塞控制）于 2021 年发布，基于 QUIC 的 HTTP/3（RFC 9114）于 2022 年发布。它要解决的正是第 4、7 章列出的 TCP 痛点：

    ① 握手太慢

    TCP 握手 1 RTT + TLS 1～2 RTT → QUIC 把传输握手和加密握手合并为 1 RTT，恢复连接时 0 RTT。

    ② 队头阻塞

    HTTP/2 的多个流共享一个 TCP 字节流 → QUIC 原生支持多个独立的流，丢包只影响所在的流。

    ③ 换网断连

    TCP 连接绑定四元组 → QUIC 用连接 ID 标识连接，IP / 端口变了连接仍在。

    ④ 协议僵化

    TCP 在内核里、头部明文、被中间设备"看懂"并干预 → QUIC 在用户态实现，几乎所有头部字段都加密，可以快速迭代。

    10.2 握手：1-RTT 与 0-RTT

    • 1-RTT：客户端的第一个包（Initial）就包含 TLS 1.3 的 ClientHello 和 QUIC 的传输参数（初始流控窗口、最大流数量等），服务器一次回复就完成密钥协商，客户端随即可以发送应用数据。传输握手和加密握手共用同一个往返。
    • 0-RTT：客户端曾经连过这台服务器，保存了会话票据（session ticket），再次连接时可以用它派生的密钥直接加密应用数据，和 Initial 一起发出。
    ⚠️ 易错点：0-RTT 数据可以被重放

    0-RTT 数据在服务器回复之前就发出了，不具备前向安全性，而且攻击者截获后可以原样重放给服务器。所以 0-RTT 只能用于幂等请求（如 GET），服务器端通常也会限制 0-RTT 能做的操作。这和 TCP Fast Open 面临的问题本质相同。

    10.3 连接 ID 与连接迁移

    这和第 8 章自研协议用 conv 识别会话是同一个思想。QUIC 做得更完整：双方可以通过 NEW_CONNECTION_ID 帧提前交换多个连接 ID，迁移时换用新 ID 以保护隐私；切换到新路径时必须先用 PATH_CHALLENGE / PATH_RESPONSE 验证对方确实在新地址上（防止被利用来攻击第三方），并重新评估这条路径的 RTT 和拥塞窗口。

    10.4 流：没有队头阻塞的多路复用

    QUIC 的流用 62 位的流 ID 标识，最低两位表示由哪一方发起、是双向还是单向。HTTP/3 中每个请求 / 响应占用一个双向流。流的开销很小，开新流不需要握手，这让 HTTP/3 可以随意并发请求。

    10.5 可靠性设计：包号与流偏移分离

    这是 QUIC 相对 TCP 最精巧的设计之一。TCP 用同一个序号同时表示"这是哪个包"和"这是字节流的哪个位置"，所以重传的段和原段序号相同，ACK 到达时分不清确认的是哪一次发送（第 3 章的重传歧义）。QUIC 把两者拆开：

    丢包检测（RFC 9002）

    机制规则对应 TCP 的
    包阈值某个包之后又有 3 个更大包号的包被确认（kPacketThreshold = 3），判定它丢失3 个重复 ACK
    时间阈值某个包发出后超过 9/8 × max(SRTT, 最新 RTT) 仍未被确认，而它之后发送的包已被确认，判定丢失RACK（RFC 8985）
    PTO 探测超时一段时间（SRTT + max(4×RTTVAR, 1ms) + max_ack_delay）内收不到任何确认时，发送 1～2 个探测包，而不是直接判定丢失RTO + TLP；但 PTO 触发时不会把拥塞窗口降到 1，只有持续拥塞时才大幅降窗

    10.6 流量控制与拥塞控制

    • 两级流量控制：每个流有自己的接收上限（MAX_STREAM_DATA），整个连接还有一个总上限（MAX_DATA）；另外用 MAX_STREAMS 限制对方能同时打开多少个流。这样一个"慢流"不会吃光整个连接的缓冲。
    • 可插拔拥塞控制：RFC 9002 给出了一个类似 NewReno 的参考算法，但实现可以自由替换为 CUBIC、BBR 等。因为在用户态，升级拥塞算法只需要更新应用，不需要等操作系统——这正是 Google 能在 QUIC 上快速迭代 BBR 的原因。
    • Pacing：推荐按速率平滑发包，而不是一次性把整个窗口突发出去，减少路由器队列压力。

    10.7 安全设计

    几乎全部加密

    除了少量必要字段（标志位、连接 ID），QUIC 头部和所有帧都被加密；连包号也用"头部保护"加密了。中间设备看不到、也就改不了 QUIC 的内部字段——这是对抗协议僵化的主动设计。

    抗放大攻击

    在验证客户端地址之前，服务器发送的数据不得超过收到数据的 3 倍；客户端的 Initial 包必须填充到至少 1200 字节，既保证了路径 MTU，也让放大倍数可控。

    Retry 令牌

    服务器可以先回一个 Retry 包，要求客户端带着令牌重新发送 Initial，证明自己真的拥有这个源地址——这就是 SYN Cookie 思想在 QUIC 中的体现（第 5 章）。

    10.8 代价与现状

    • CPU 开销：用户态协议栈、每包加解密、缺少成熟的硬件卸载，服务器 CPU 消耗通常高于 TCP + TLS。业界通过 UDP GSO / GRO、sendmmsg、内核旁路等手段优化。
    • UDP 被限制：部分企业网络封禁 UDP 443，部分运营商对 UDP 限速。浏览器会通过 Alt-Svc 头部发现服务器支持 HTTP/3，并在 QUIC 失败时自动回退到 TCP。
    • 实现复杂：一个完整的 QUIC 实现动辄数万行代码。主流开源实现有 Chromium QUIC、Cloudflare quiche、Microsoft MsQuic、ngtcp2、quic-go、LiteSpeed lsquic 等。
    • 扩展：RFC 9221 定义了 DATAGRAM 帧，在 QUIC 连接中发送不可靠、不重传的数据（共享加密和拥塞控制），使 QUIC 也能承载"不可靠 · 只要最新"类的实时数据（WebTransport 就基于此）。

    ✅ 面试答法：QUIC 相比 TCP 有哪些改进？

    ① 握手更快：传输和 TLS 1.3 握手合并，首次 1 RTT，恢复连接 0 RTT；② 无队头阻塞：原生多流，每个流独立排序，一个丢包只影响所在的流；③ 连接迁移：用连接 ID 而不是四元组标识连接，切换网络不断线；④ 更好的丢包恢复：包号单调递增、与流偏移分离，消除重传歧义，ACK 帧可以携带大量范围和 ACK 延迟；⑤ 用户态实现：拥塞控制可插拔、迭代快，且头部加密防止中间设备僵化；⑥ 内置抗放大和地址验证。代价是 CPU 开销更高，以及部分网络对 UDP 的限制需要回退 TCP。

    本章小结
    • QUIC：RFC 9000/9001/9002（2021），HTTP/3 RFC 9114（2022）；= 可靠传输 + TLS 1.3 + 流复用，跑在 UDP 上。
    • 握手 1-RTT，恢复 0-RTT（0-RTT 数据可被重放，只用于幂等请求）。
    • 连接 ID 标识连接 → 连接迁移；迁移需 PATH_CHALLENGE 验证，换用新 ID 保护隐私。
    • 多流复用：流间无队头阻塞，流内仍有序。

    • 两级流控（MAX_STREAM_DATA / MAX_DATA）；拥塞控制可插拔；抗放大 3 倍、Initial ≥ 1200 字节、Retry 令牌。

    思考题 1：HTTP/3 一定比 HTTP/2 快吗？

    不一定。在低丢包、低 RTT 的有线网络中，两者差别很小，HTTP/3 甚至可能因为 CPU 开销更高、UDP 未被优化而略慢。HTTP/3 的优势集中在：高 RTT（握手少）、有丢包（无流间队头阻塞、恢复更快）、频繁切换网络（连接迁移）的移动场景。此外如果网络限制 UDP，浏览器会回退到 HTTP/2。

    思考题 2：为什么说 QUIC 的"包号永不重复"解决了 TCP 的重传歧义？KCP 是怎么解决的？

    TCP 重传段与原段序号相同，ACK 到来时无法判断确认的是哪一次发送，RTT 采样只能放弃（Karn 算法）或依赖时间戳选项。QUIC 每次发送都使用新的包号，ACK 确认的是具体包号，因此一定能对应到唯一一次发送，可以精确测量 RTT 并判断丢包。KCP 的重传仍然使用相同的 sn，但每次发送都更新 ts，接收方在 ACK 中回显 ts，发送方用 now − ts 计算 RTT，同样避免了歧义。

    思考题 3：QUIC 运行在用户态，那它还能利用内核的拥塞控制吗？这对公平性有什么影响？

    不能直接使用内核 TCP 的拥塞控制，QUIC 在用户态自己实现拥塞控制（RFC 9002 要求必须实现，不能不做）。这使得每个应用可以选择不同的算法，迭代更快；但也意味着公平性依赖于实现者的自律——如果某个实现采用过于激进的算法，会挤占同一瓶颈上其他 TCP 流的带宽。IETF 通过标准中的拥塞控制要求和互操作测试来约束这一点。

    🎮 游戏开发视角：几个容易忽略的细节

    ① 上行冗余的终止条件：客户端持续冗余发送某帧输入，直到服务器的包头 ACK 表明已收到——这就是第 8 章 UNA + ACK 位图的直接应用。
    ② 帧缓冲的大小要自适应：根据实测抖动动态调整缓冲帧数，网络好时减少输入延迟，网络差时增加平滑度。
    ③ 包要小：控制在 MTU 以内，避免 IP 分片（第 1 章）；10 个玩家 × 若干字节的操作，一个帧包通常只有几十到一两百字节。
    ④ 不要让一个慢玩家拖住所有人：服务器按固定节奏推进帧号，没收到某玩家的输入就当作"无操作"，这和 TCP 的"必须等"截然不同。

    11.3 实战二：状态同步

    状态同步（如 UE 的 Actor 复制）由服务器计算权威状态，按需把属性变化发给客户端。它的传输策略可以对照可靠性光谱来理解：

    数据可靠性机制
    属性复制（位置、血量……）可靠 · 只要最新不可靠发送；检测到包丢失时，不重传旧包，而是把相关属性标记为"脏"，在下一次复制时发送当前值
    Reliable RPC（开火、技能、交互）可靠有序（同一 Actor 通道内）丢失后重传；过多的可靠 RPC 积压会导致通道溢出、连接被断开，所以要节制使用
    Unreliable RPC（特效、音效）不可靠发了就不管；带宽紧张时可能被丢弃
    移动同步不可靠 + 客户端预测 / 服务器校正客户端先本地执行移动，服务器验证后纠正；输入用不可靠 RPC 高频发送，并冗余携带最近的移动

    另外，状态同步还要做相关性裁剪（只同步玩家附近 / 视野内的对象）和优先级与带宽预算（每帧按优先级在预算内挑选要发送的对象），本质上是第 7 章架构图中"通道与调度层"的工作。

    11.4 实战三：实时音视频（WebRTC）

    RTP / RTCP over UDP

    RTP 携带媒体数据（序号 + 时间戳），RTCP 反馈接收质量（丢包率、抖动、RTT）。全部通过 SRTP / DTLS 加密。

    NACK：有条件的重传

    接收方发现缺包时发 NACK 请求重传，但只有在"重传的包能在播放截止前到达"时才有意义——RTT 大时就放弃，改靠 FEC 或丢帧。

    FEC + 抖动缓冲

    FlexFEC / ULPFEC 用冗余包恢复丢包；抖动缓冲（jitter buffer）动态调整缓冲时长，平滑到达时间的波动。

    基于时延的拥塞控制

    GCC（Google Congestion Control）监测包到达间隔的变化趋势，在队列开始积压时就降低码率，而不是等到丢包。码率调整直接作用于编码器。

    对比游戏和音视频会发现一个共同规律：越是实时的场景，越倾向于"用带宽和画质换时延"——FEC、冗余发送、主动降码率、降低快照频率，都是这个思路。

    思考题 1：帧同步中，如果某个玩家网络特别差，服务器应该等他吗？

    不应该。如果服务器等最慢的玩家（严格锁步），所有人都会被拖慢，体验极差。现代帧同步服务器按固定节奏推进帧号，迟到的输入被放入下一帧（或丢弃），该玩家看到的是自己的操作稍有延迟；他的客户端如果落后太多，会进入"追帧"模式快速执行积压的帧。网络长时间不可用时，服务器可以让 AI 托管该玩家。

    思考题 2：为什么说"只看平均时延会骗人"？请用本书的仿真数据说明。

    实验 B 中 5% 丢包时，T'（关闭拥塞控制的类 TCP）平均时延 60.7 ms，看起来只比无丢包时多 30 ms；但 P99 是 185 ms、最大 215 ms，意味着每 100 条消息里就有 1 条要等 6 倍的单程时延。游戏中这 1% 正好对应玩家感知到的"卡了一下"。KCP 把平均值从 60.7 降到 42.9（降 29%），P99 从 185 降到 95（降 49%），尾部的改善远比平均值明显——这也是 KCP 官方说"最大延迟降低三倍"比"平均延迟降低 30%～40%"更有意义的原因。

    思考题 3：设计一个手游的网络层，UDP 被运营商封了怎么办？

    ① 登录时（走 TCP/HTTPS）由服务器下发 UDP 地址与会话票据；② 客户端先尝试 UDP 握手，若在限定时间（如 1～2 秒）内失败，或运行中连续一段时间收不到 UDP 包，则切换到 TCP 通道；③ 业务层对两种通道使用统一的消息接口（TCP 上直接传输应用消息，开 TCP_NODELAY，不再套 KCP）；④ 记录降级比例，作为网络质量监控指标；⑤ 可选：对 UDP 流量做端口随机化、伪装等对抗策略（需评估合规性）。

    12.1 基础（8 题）

    1. ★ TCP 和 UDP 的区别？

    连接（面向连接 / 无连接）、可靠性（可靠 / 尽力交付）、有序性、数据单位（字节流 / 数据报，粘包问题）、头部（20～60 / 8 字节）、流量与拥塞控制（有 / 无）、通信模式（一对一 / 支持广播多播）、开销与时延。实时性差异的根源是 TCP 按序可靠交付导致的队头阻塞。【→ 第 4 章】

    2. UDP 头部有哪些字段？最大能发多大的数据报？

    源端口、目的端口、长度、校验和，各 16 位共 8 字节。长度字段最大 65535，减去 8 字节 UDP 头和 20 字节 IPv4 头，最大负载 65507 字节。但实际应控制在 MTU 以内（≤ 1472，常取 1200～1400）避免分片。【→ 第 2 章】

    3. 校验和为什么要加伪首部？

    伪首部包含源 / 目的 IP、协议号和长度，不发送、只参与计算，用于检测"数据报被送到了错误的主机或协议"——仅校验 UDP/TCP 报文本身发现不了 IP 头部出错导致的误投递。【→ 第 2 章】

    4. 什么是 MTU 和 MSS？为什么要避免 IP 分片？

    MTU 是链路层能承载的最大数据长度（以太网 1500）；MSS 是 TCP 段能携带的最大数据长度（MTU − IP 头 − TCP 头 = 1460），在 SYN 中协商。IP 分片后任何一片丢失整个包都要作废，重组耗资源，且常被防火墙丢弃。TCP 靠 MSS + PMTUD 避免，UDP 要靠应用控制包长。【→ 第 1 章】

    5. 一台服务器最多能支持多少个 TCP 连接？

    不受 65535 限制。连接由四元组标识，服务器端口固定时，理论上限是客户端 IP 数 × 端口数。实际受限于文件描述符上限、内存（每连接几 KB 到几十 KB）、CPU 和 I/O 模型。客户端连同一个服务器地址时，才受本地临时端口数量限制。【→ 第 1 章】

    6. 同一个端口能同时被 TCP 和 UDP 使用吗？

    可以，两者是独立的端口空间，内核先按 IP 头的协议号区分 TCP/UDP。DNS 就同时使用 TCP 53 和 UDP 53。【→ 第 4 章】

    7. DNS 为什么用 UDP？什么时候用 TCP？

    查询应答小、一问一答，UDP 省去握手 RTT，服务器无需维护连接。应答被截断（TC 位）、区域传送、DNS over TLS 时用 TCP。【→ 第 1 章思考题】

    8. UDP 调用 connect() 有什么作用？

    不发送任何报文，只在内核记录默认对端：之后可用 send/recv，只接收该对端的数据，并能收到 ICMP 错误（如 ECONNREFUSED）。【→ 第 2 章】

    12.2 TCP 机制（10 题）

    9. ★ TCP 如何保证可靠传输？

    校验和（检错）、序号（排序、去重）、确认 + 重传（超时重传、快速重传、SACK）、滑动窗口流量控制、拥塞控制、连接管理（握手 / 挥手）。按"网络问题 → 机制"的对应关系答最清晰。【→ 第 3 章】

    10. ★ 什么是粘包 / 拆包？怎么解决？

    TCP 是字节流，不保留应用写入的边界，接收方一次读到的可能是多条消息的拼接或半条消息。发生在发送端（Nagle 合并）或接收端（缓冲区累积）。解决：应用层分帧——定长、分隔符、长度前缀（最常用）。UDP 不存在粘包。【→ 第 3 章，d1 · E1 实测】

    11. RTO 是怎么计算的？Karn 算法是什么？

    RFC 6298：SRTT = 7/8 SRTT + 1/8 R；RTTVAR = 3/4 RTTVAR + 1/4 |SRTT − R|；RTO = SRTT + 4·RTTVAR，下限 1 s（Linux 200 ms），超时后指数退避。Karn 算法：重传过的段不参与 RTT 采样，因为无法区分 ACK 对应哪一次发送。时间戳选项可以解决这个歧义。【→ 第 3 章】

    12. ★ 快速重传是什么？为什么是 3 个重复 ACK？

    收到 3 个重复 ACK 就认为对应段丢失，不等 RTO 立即重传。阈值 3 是"尽早发现丢包"与"不把轻微乱序误判为丢包"的折中。现代 Linux 还有 RACK（基于时间判断）和 TLP（尾部丢包探测）。【→ 第 3 章】

    13. ★ 滑动窗口和流量控制是怎么工作的？零窗口怎么办？

    发送方维护 [SND.UNA, SND.UNA+SND.WND) 的窗口，窗口内可以连续发送而不等确认；接收方在 ACK 中通告剩余接收缓冲 rwnd。rwnd = 0 时发送方暂停，并用坚持定时器周期性发零窗口探测，防止窗口更新报文丢失导致死锁。【→ 第 3 章】

    14. ★ 拥塞控制有哪几个阶段？

    慢启动（cwnd 每 RTT 翻倍，直到 ssthresh）、拥塞避免（每 RTT +1）、快速重传 + 快速恢复（3 dup ACK：ssthresh = cwnd/2，cwnd = ssthresh，进入拥塞避免）、超时（ssthresh = cwnd/2，cwnd = 1，重新慢启动）。发送窗口 = min(rwnd, cwnd)。【→ 第 3 章】

    15. 流量控制和拥塞控制的区别？

    流量控制保护接收方，由接收方显式通告 rwnd，点对点；拥塞控制保护网络，由发送方根据丢包 / 时延推测 cwnd，关注全局。两者共同决定发送窗口。【→ 第 3 章】

    16. CUBIC 和 BBR 有什么区别？

    CUBIC 是 Linux 默认算法，仍以丢包为拥塞信号，cwnd 按距上次丢包时间的三次函数增长，与 RTT 无关。BBR 不依赖丢包，测量瓶颈带宽和最小 RTT，按 BDP 控制在途数据、按带宽 pacing，在随机丢包链路上吞吐更好，且不会塞满路由器缓冲。【→ 第 3 章】

    17. Nagle 算法和延迟确认是什么？为什么游戏要关闭 Nagle？

    Nagle：有未确认数据时，小数据先攒着，收到 ACK 或攒满 MSS 再发。延迟确认：收到数据后等一段时间（40～200 ms）再回 ACK，希望捎带或合并。两者叠加会让小请求多等几十～几百毫秒。游戏消息小且要求实时，必须 TCP_NODELAY。【→ 第 3 章】

    18. TCP 头部有哪些标志位？各自含义？

    URG（紧急指针有效）、ACK（确认号有效）、PSH（尽快交付）、RST（重置连接）、SYN（同步序号，建连）、FIN（数据发送完毕，关闭）；另有 ECE、CWR 用于 ECN 显式拥塞通知。【→ 第 3 章】

    12.3 三次握手（8 题）

    19. ★ 描述三次握手的过程和状态变化。

    ① C 发 SYN(seq=x)，C：CLOSED → SYN_SENT；S 收到后 LISTEN → SYN_RCVD。② S 回 SYN+ACK(seq=y, ack=x+1)，C 收到后 → ESTABLISHED。③ C 回 ACK(ack=y+1)，S 收到后 → ESTABLISHED。SYN 占 1 个序号；第三次握手可携带数据。【→ 第 5 章】

    20. ★ 为什么是三次握手，不是两次或四次？

    ① 防止历史连接（首要原因）：旧 SYN 到达后，客户端可在第三步用 RST 否决，两次握手时服务器会直接建立无效连接；② 同步双方 ISN，每个 ISN 都需要被确认，两次只能确认客户端的；③ 避免重复 SYN 建立多条无用连接。服务器的 ACK 和 SYN 可合并，所以不需要四次。【→ 第 5 章】

    21. ISN 为什么要随机？

    防止旧连接的延迟报文落入新连接的序号窗口；防止序号预测攻击（伪造连接、注入数据）。RFC 6528：ISN = 计时器 M + Hash(四元组, 密钥)，随时间递增且不可预测。【→ 第 5 章】

    22. ★ 什么是半连接队列和全连接队列？满了会怎样？

    半连接队列存放 SYN_RCVD 的连接（上限约 tcp_max_syn_backlog），全连接队列存放已完成握手、等待 accept 的连接（上限 min(backlog, somaxconn)）。半连接队列满时启用 SYN Cookie 或丢弃 SYN；全连接队列满且 tcp_abort_on_overflow=0 时丢弃第三次 ACK，服务器重传 SYN+ACK，客户端表现为"连接成功但请求超时"。可用 ss -lnt 观察。【→ 第 5 章】

    23. ★ SYN Flood 是什么？怎么防？

    伪造源 IP 大量发送 SYN，服务器为每个 SYN 分配半连接并重传 SYN+ACK，却永远等不到 ACK，半连接队列被占满，正常用户无法建连。防御：SYN Cookie（把状态编码进 ISN，握手完成前不存状态）、增大半连接队列、减少 tcp_synack_retries、SYN Proxy / 防火墙、流量清洗。【→ 第 5 章】

    24. 第三次握手的 ACK 丢了会怎样？

    客户端已 ESTABLISHED，服务器仍在 SYN_RCVD 并重传 SYN+ACK。客户端若发送数据，数据段带有 ACK 和正确确认号，服务器收到后直接进入 ESTABLISHED。若客户端不发数据且服务器重传耗尽，服务器删除半连接，之后客户端发数据会收到 RST。【→ 第 5 章，交互实验 1】

    25. 第一次、第二次握手的报文丢了分别会怎样？

    SYN 丢失：客户端在 SYN_SENT 指数退避重传（1、2、4… s，tcp_syn_retries=6，约 127 s 后 ETIMEDOUT）。SYN+ACK 丢失：客户端重传 SYN，服务器重传 SYN+ACK（tcp_synack_retries=5），任一成功即可。【→ 第 5 章】

    26. connect 到一个没人监听的端口会怎样？

    对端内核回 RST，connect 返回 ECONNREFUSED。Linux 立即失败；Windows 会重试 SYN，本书实测回环地址也要约 2 秒才失败。若是防火墙静默丢弃，则表现为 SYN 超时。【→ 第 5 章，d1 · E3 实测】

    12.4 四次挥手（7 题）

    27. ★ 描述四次挥手的过程和状态变化。

    ① 主动方发 FIN，→ FIN_WAIT_1；被动方收到 → CLOSE_WAIT。② 被动方内核回 ACK，主动方 → FIN_WAIT_2（半关闭，仍可接收）。③ 被动方应用 close，发 FIN，→ LAST_ACK；主动方收到 → TIME_WAIT。④ 主动方回 ACK，被动方 → CLOSED；主动方等 2MSL 后 CLOSED。【→ 第 6 章，d1 · E4 实测】

    28. ★ 为什么挥手需要四次？什么时候是三次？

    TCP 全双工，两个方向分别关闭；被动方收到 FIN 时可能还有数据要发，ACK（内核立即回）和 FIN（应用 close 时发）通常分开。被动方无数据可发且有延迟确认时，ACK 与 FIN 合并为三次。【→ 第 6 章】

    29. ★ TIME_WAIT 为什么存在？为什么是 2MSL？

    ① 保证最后的 ACK 送达：若丢失，被动方重传 FIN，主动方还能重发 ACK（否则只能回 RST）；② 让旧连接的报文在网络中消亡，不污染相同四元组的新连接。2MSL 覆盖"ACK 最多走 1 MSL + 重传 FIN 最多走 1 MSL"。Linux 固定 60 秒。【→ 第 6 章】

    30. ★ TIME_WAIT 过多有什么危害？怎么解决？

    主动关闭方产生。客户端（或代理调用下游）会耗尽本地临时端口，connect 报 EADDRNOTAVAIL。解决：长连接 / 连接池（首选）、tcp_tw_reuse（客户端、需时间戳）、扩大端口范围、让客户端主动关闭；tcp_tw_recycle 在 NAT 下有问题且已在 Linux 4.12 删除；SO_LINGER 0 会丢数据，慎用。【→ 第 6 章】

    31. 大量 CLOSE_WAIT 说明什么？

    对端已关闭而本端应用没有调用 close，几乎都是代码 bug（读到 EOF 未关闭、异常分支漏关、连接池未回收）。用 ss -tanp state close-wait 定位进程和对端，再检查代码。CLOSE_WAIT 不会自动超时消失。【→ 第 6 章】

    32. close 和 shutdown 的区别？SO_LINGER 有什么用？

    close 减少 fd 引用计数，为 0 时关闭读写两个方向；shutdown 直接作用于连接，可只关写（发 FIN 但仍可读，半关闭）。SO_LINGER {1, 0} 让 close 直接发 RST，不进 TIME_WAIT，但会丢弃未发送数据，对端得到 ECONNRESET。【→ 第 6 章，d1 · E5 / E6 实测】

    33. 对端机器突然断电，本端能发现吗？

    不能立即发现，连接仍是 ESTABLISHED。本端发数据时会经历多次 RTO 重传（tcp_retries2，十几分钟）后报错；不发数据就只能靠 Keepalive（默认空闲 2 小时才探测）或应用层心跳。进程崩溃则不同，内核会正常发 FIN / RST。【→ 第 6 章】

    12.5 可靠 UDP（5 题）

    34. ★ 如何基于 UDP 实现可靠传输？

    报文头加会话 ID、序号、累计确认 UNA、选择确认（位图或逐包 ACK）、时间戳、窗口；发送端缓存未确认包，按 RTO 超时重传、被跳过 N 次快速重传；接收端用环形缓冲乱序暂存、去重、按序交付，重复包也要回 ACK；滑动窗口做流量控制；拥塞控制或限速；大消息分片重组；连接管理（Cookie 握手、心跳、超时断线）；加密认证。可以按需对不同消息提供不同可靠级别。【→ 第 8 章】

    35. ★ KCP 为什么比 TCP 快？代价是什么？

    RTO ×1.5 而非 ×2，RTO 下限更低；选择性重传；快速重传阈值可配（跳过 2 次即重传）；不延迟 ACK；UNA + 逐包 ACK；可关闭拥塞控制。代价：多消耗 10%～20% 甚至更多带宽，无连接管理 / 加密 / 不可靠消息，需要自己补。不丢包时与 TCP 时延相当。【→ 第 9 章，d2 实测】

    36. 停等、回退 N 步、选择重传的区别？

    停等：窗口 1，利用率 ≈ T/(T+RTT)。GBN：发送窗口 N，接收方只收按序包，丢包后从丢失点重发整窗。SR：发送和接收窗口都为 N，接收方缓存乱序包，只重传丢失的包，序号空间需 ≥ 2N。本书仿真中 GBN 80% 的发送是重传。【→ 第 8 章】

    37. ★ QUIC 相比 TCP 有哪些改进？

    握手与 TLS 1.3 合并（1-RTT / 0-RTT）；多流无流间队头阻塞；连接 ID 支持连接迁移；包号永增与流偏移分离，消除重传歧义；ACK 帧多 Range + ACK Delay；用户态实现、拥塞控制可插拔；头部加密防僵化；抗放大与 Retry。代价是 CPU 高、UDP 可能被封。【→ 第 10 章】

    38. 序号回绕怎么处理？

    使用序列号算术：int32_t(a - b) > 0 表示 a 在 b 之后（16 位同理），前提是窗口远小于序号空间的一半。TCP 在高速网络下还要依靠时间戳选项的 PAWS 机制；QUIC 包号 62 位，实际上不会回绕。【→ 第 8 章】

    12.6 场景设计（2 题）

    39. ★ 如果让你设计一个 MOBA 游戏的网络同步方案，传输层怎么选？

    先给数据分类：输入流（帧同步，可靠有序）、状态（只要最新）、事件（可靠）、非实时业务（登录、商城、结算）。战斗用 UDP：输入和帧包冗余发送最近若干帧，配合 ACK 位图停止冗余；缺帧通过 KCP 可靠通道补发；客户端帧缓冲吸收抖动；服务器按固定节奏推进不等慢玩家。非实时业务走 TCP/HTTPS。心跳秒级断线检测，UDP 不通时整体降级 TCP。全部加密防作弊。用弱网工具验证 P99 时延。【→ 第 11 章】

    40. 视频会议为什么不用 TCP？它怎么应对丢包？

    端到端时延预算只有 200～300 ms，TCP 的重传等待和队头阻塞会造成卡顿，迟到的帧没有意义。WebRTC 用 RTP over UDP：NACK 有条件重传（来得及才重传）、FEC 冗余恢复、抖动缓冲、丢帧与插值，以及基于时延的拥塞控制（GCC）动态调整码率。【→ 第 4、11 章】

    A.3 三个口述模板（各约 1 分钟）

    三次握手

    "客户端发 SYN，带上随机的初始序号 x，进入 SYN_SENT；服务器收到后进入 SYN_RCVD，回复 SYN+ACK，带自己的序号 y 和确认号 x+1；客户端收到后进入 ESTABLISHED，再回 ACK，确认号 y+1，服务器收到后也进入 ESTABLISHED。三次是最少的次数：主要是为了防止历史连接——旧的 SYN 到达时，客户端能在第三步用 RST 拒绝；同时双方的初始序号都需要被确认；还能避免重复 SYN 建立无用连接。服务器的 ACK 和 SYN 合并了，所以不用四次。另外，内核里有半连接和全连接两个队列，SYN Flood 攻击的就是半连接队列，可以用 SYN Cookie 防御。"

    四次挥手

    "主动方发 FIN 进入 FIN_WAIT_1；被动方内核回 ACK，进入 CLOSE_WAIT，主动方收到后进入 FIN_WAIT_2，这时是半关闭，被动方还能继续发数据；被动方应用调用 close 后发 FIN，进入 LAST_ACK；主动方收到后回 ACK 进入 TIME_WAIT，等 2MSL 后关闭，被动方收到 ACK 就关闭。之所以四次，是因为 TCP 全双工，两个方向要分别关闭，被动方的 ACK 和 FIN 之间可能还有数据要发；如果没有数据并且有延迟确认，也可能合并成三次。"

    TIME_WAIT

    "TIME_WAIT 出现在主动关闭方，持续 2MSL，Linux 是固定的 60 秒。它有两个作用：一是保证最后一个 ACK 能到达，如果丢了，对方会重传 FIN，主动方还能重新回 ACK，否则只能回 RST；二是让这个连接在网络中残留的旧报文全部过期，避免被相同四元组的新连接误收。2MSL 就是一个来回的最长时间。TIME_WAIT 太多时，客户端会耗尽本地端口，最好的办法是用长连接或连接池，其次可以开 tcp_tw_reuse；tcp_tw_recycle 在 NAT 环境下有问题，已经从内核删除了。"

    A.4 一句话串起全书

    🧭 回到起点

    IP 只尽力而为；UDP 把选择权留给应用；TCP 用序号、确认、重传、窗口、拥塞控制和连接管理把网络包装成可靠有序的字节流，并为此付出了握手延迟和队头阻塞的代价；三次握手同步序号、四次挥手分别关闭两个方向、TIME_WAIT 收尾；而 KCP、QUIC 和游戏引擎的网络层，则是在用户态把同一套机制按自己的需求重新组合——可靠性不是一个开关，而是一组可以挑选、可以调参的机制，每一个都有代价。
