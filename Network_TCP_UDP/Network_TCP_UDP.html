    一条主线：可靠性是一组机制，而不是一个开关

    传输层的知识点乍看很散：端口、校验和、序号、三次握手、滑动窗口、拥塞控制、TIME_WAIT、KCP、QUIC……面试时也常被拆成一道道独立的题来问。但它们其实都在回答同一个问题：

    🧭 全书主线

    IP 网络只承诺"尽力而为"：包会丢、会乱序、会重复、会出错、会因为拥塞而变慢。要想在它上面提供"可靠"的服务，就要拿出一组机制去对付这些问题，而每个机制都有代价（延迟、带宽、内存、复杂度）。

    从一次网页请求说起

    在浏览器里敲下一个网址，到页面开始出现，网线上依次走过了 UDP、TCP、TLS、HTTP。

    本章目标

    1.1 敲下回车之后：一张时序图看全流程

    假设你在浏览器里输入 https://www.example.com 并回车，且本机没有任何缓存。抛开浏览器内部的解析和渲染，单看网络，大致会发生四件事：

    1. DNS 解析：把域名翻译成 IP 地址。浏览器（通过操作系统）向 DNS 服务器发一个查询，通常用 UDP 的 53 端口，一问一答。
    2. TCP 三次握手：和 Web 服务器的 443 端口建立一条 TCP 连接。
    3. TLS 握手：在 TCP 连接之上协商加密参数、验证服务器证书。TLS 1.3 需要 1 个 RTT。
    4. HTTP 请求与响应：发送 GET /，收到 HTML。

    这张图里已经藏着本书的大部分主题：

    • DNS 为什么用 UDP？一问一答、报文小，用 TCP 光握手就要多花 1 个 RTT，丢了重问一次即可（第 2 章、第 4 章）。
    • SYN、SYN+ACK、ACK 各自携带了什么、为什么是三次？（第 5 章）
    • HTML 被拆成很多个 TCP 段，丢了一个怎么办？乱序了怎么办？发太快怎么办？（第 3 章）
    • 能不能把 TCP 握手和 TLS 握手合并，把 4 个 RTT 压缩下来？这正是 QUIC / HTTP/3 的动机之一（第 10 章）。
    📦 场景案例：RTT 才是网页慢的主因

    很多人以为网页慢是因为"带宽不够"。实际上，打开一个普通网页只需要几百 KB，100 Mbps 的带宽传完只要几十毫秒；真正拖慢首屏的是来回次数（RTT 的个数）。这就是为什么工程上大量优化都在"省 RTT"：DNS 预解析、TCP 连接复用（HTTP Keep-Alive）、TLS 会话恢复、TCP Fast Open、HTTP/3 的 0-RTT。记住这个视角，后面讨论握手次数时你会更有体感。

    1.2 分层模型：每层只做一件事

    网络通信被拆成若干层，每一层只依赖下一层提供的服务，并向上一层提供服务。教科书里有两套模型：

    OSI 七层TCP/IP 四层（五层教学版）负责什么典型协议PDU 名称
    应用层 / 表示层 / 会话层应用层具体业务语义HTTP、DNS、TLS*、SSH、游戏协议报文（message）
    传输层传输层进程到进程：端口复用、可靠性、流量 / 拥塞控制TCP、UDP、SCTP、QUIC*TCP 段（segment）/ UDP 数据报（datagram）
    网络层网际层主机到主机：寻址与路由，跨越多个网络IPv4、IPv6、ICMP分组 / 包（packet）
    数据链路层网络接口层（链路层 + 物理层）同一链路上相邻节点之间传帧以太网、Wi-Fi、PPP帧（frame）
    物理层比特 ↔ 电 / 光 / 无线信号双绞线、光纤比特

    * TLS 通常被视为位于传输层和应用层之间；QUIC 运行在 UDP 之上，但承担的是传输层职责，所以常被称为"用户态传输层"。

    封装与解封装

    发送时，数据从上往下走，每经过一层就在前面加上一层"信封"（头部）；接收时从下往上走，每一层拆掉属于自己的信封，再根据头部里的字段决定交给上面的谁。

    ✅ 面试答法：为什么要分层？

    ① 解耦：每层只关心自己的职责，换掉其中一层（如把有线换成 Wi-Fi、把 IPv4 换成 IPv6）不影响其他层；② 复用：所有应用共享同一套 TCP/IP 实现；③ 标准化：不同厂商只要遵守层间接口就能互通。代价是每层都有头部开销，层与层之间也可能出现信息不对称（例如 TCP 不知道底层是无线链路，把无线干扰导致的丢包误当成拥塞，第 3 章会讲）。

    1.3 IP 的承诺：尽力而为

    网络层的 IP 协议负责把一个包从源主机送到目标主机，中间可能经过几十个路由器。但 IP 只承诺"尽力而为"（best effort），具体来说：

    ❌ 不保证送达

    路由器队列满了就直接丢包；TTL 减到 0 也丢。丢了不会通知任何人（最多偶尔回一个 ICMP）。

    ❌ 不保证顺序

    先发的包可能走了更长的路径，后发先至。

    ❌ 不保证不重复

    链路层重发、路由抖动都可能让同一个包到达两次。

    ❌ 不保证数据正确

    IPv4 头部校验和只校验头部，不管数据；IPv6 连头部校验和都去掉了。

    ❌ 不控制速率

    你发多快它就转多快，直到某个路由器扛不住开始丢包。

    ✅ 只保证一件事

    按目标 IP 地址尽量把包往正确的方向转发。

    为什么不让 IP 层直接做可靠？——端到端原则

    如果让每个路由器都保证可靠（逐跳确认、逐跳重传），路由器就得为每条流保存状态、缓存数据，成本极高；而且即使每一跳都可靠，数据仍可能在终端主机的内存里出错，最终还是要由两端再确认一次。这就是著名的端到端原则（End-to-End Argument）：

    📐 端到端原则

    某个功能只有在通信的端点才能被完整、正确地实现时，就应该放在端点实现；网络中间只做简单、通用、高效的事情。
    → 所以 IP 保持"笨而快"，可靠性交给两端主机的传输层（TCP），或者干脆交给应用自己（UDP + 应用层可靠）。

    这条原则也解释了本书最后一部分的存在：既然可靠性本来就是端点的事，那它放在内核里的 TCP 还是用户态的 KCP / QUIC，只是工程取舍，没有原则上的对错。

    1.4 端口、套接字与五元组：找到具体的进程

    IP 地址只能定位到主机，而一台主机上同时跑着浏览器、微信、游戏客户端。传输层的第一个职责就是复用与分用（multiplexing / demultiplexing）：发送时把多个进程的数据汇入同一个 IP 层，接收时再按端口号分发给正确的进程。

    • 端口（port）：16 位无符号整数，0～65535。0～1023 是知名端口（HTTP 80、HTTPS 443、DNS 53、SSH 22），1024～49151 是注册端口，49152～65535 是动态（临时）端口。Linux 默认的临时端口范围是 32768～60999（net.ipv4.ip_local_port_range）。
    • 套接字（socket）：操作系统提供给应用的通信端点抽象。应用读写 socket，内核负责把数据交给 TCP/UDP 协议栈。
    • 五元组：{协议, 源 IP, 源端口, 目的 IP, 目的端口}，唯一标识一条通信。
    ⚠️ 易错点：一台服务器最多只能有 65535 个 TCP 连接？

    错。端口号的 65535 限制针对的是同一个四元组中的一个端口字段。服务器只监听一个端口（443），每条连接由{客户端 IP, 客户端端口}区分，理论上限是"客户端 IP 数 × 客户端端口数"，远超 65535。实际限制来自文件描述符上限和内存（每条连接的内核结构加收发缓冲区要占几 KB 到几十 KB）。
    反过来，客户端连同一个服务器的同一个端口时，确实最多只能用掉约 2.8 万个（Linux 默认临时端口范围）本地端口——这就是第 6 章 TIME_WAIT 过多会导致"端口耗尽"的根源。

    1.5 MTU、MSS 与分片

    链路层一次能承载的最大数据长度叫 MTU（Maximum Transmission Unit），以太网是 1500 字节。比 MTU 大的 IP 包要么被分片（IPv4 允许路由器分片），要么被丢弃并回一个 ICMP "需要分片"（设置了 DF 位或 IPv6）。

    • 分片的坏处：任何一个分片丢了，整个 IP 包都要作废；分片重组消耗接收方资源；很多防火墙和 NAT 会直接丢弃分片。所以无论 TCP 还是 UDP，都应该尽量避免 IP 分片。
    • TCP 怎么避免：三次握手时双方在 SYN 里通过 MSS 选项告诉对方"我能收的最大段长"，一般是 MTU − 40 = 1460；之后 TCP 自己把字节流切成不超过 MSS 的段。再配合路径 MTU 发现（PMTUD）适应中间更小的 MTU（如 PPPoE 的 1492）。
    • UDP 怎么避免：UDP 不切分，应用交给它多大，它就发多大的数据报。所以应用必须自己控制每个数据报的大小：以太网下 UDP 负载不超过 1500 − 20 − 8 = 1472 字节；考虑到隧道、VPN、移动网络，实践中常取 1200～1400（QUIC 规定 IPv4/IPv6 下至少支持 1200 字节，KCP 默认 MTU 为 1400）。
    🎮 游戏开发视角

    游戏的同步包通常只有几十到几百字节，天然不会触发分片；但"进入场景时下发全量状态""发送一张大地图快照"这类大消息就必须在应用层手动分片、编号、重组，这正是第 8 章可靠 UDP 里"消息分片"机制要解决的问题。UE 的网络层把一个大的 Bunch 拆成多个 Partial Bunch 也是同一个道理。

    本章小结
    • 一次冷启动 HTTPS 请求 ≈ DNS(UDP) + TCP 握手 + TLS 握手 + HTTP，约 4 个 RTT；网页慢多半慢在 RTT 个数。
    • TCP/IP 四层：应用 → 传输（进程到进程）→ 网际（主机到主机）→ 网络接口；PDU 依次叫报文、段 / 数据报、分组、帧。
    • IP 尽力而为：可能丢、乱、重、错、拥塞。按端到端原则，可靠性放在端点做。
    • 端口 16 位；TCP 连接按四元组区分，UDP socket 按目的地址区分；服务器连接数不受 65535 限制。
    • MTU 1500 → TCP MSS 1460、UDP 安全负载 ≤ 1472（实践取 1200～1400）；尽量避免 IP 分片。
    思考题 1：为什么 DNS 一般用 UDP，什么情况下又会改用 TCP？

    一般用 UDP：查询和应答都很小，一问一答，没有必要先花 1 个 RTT 建连接；丢了由客户端超时重问即可，DNS 解析器也不需要为每个客户端维护连接状态，抗并发能力强。
    改用 TCP 的情况：① 应答超过 512 字节（未使用 EDNS0 时）或超过 EDNS0 协商的大小，服务器会在 UDP 应答中设置 TC（截断）位，客户端改用 TCP 重新查询；② 主从 DNS 服务器之间的区域传送（AXFR/IXFR）数据量大，必须用 TCP；③ DNS over TLS（DoT，端口 853）基于 TCP。

    思考题 2：服务器只监听 443 一个端口，为什么能同时服务几十万个客户端？瓶颈在哪？

    TCP 连接由四元组标识，服务器侧的 IP 和端口相同，但客户端的 IP 和端口不同，所以每条连接都是唯一的，不受 65535 的限制。瓶颈在于：进程 / 系统级文件描述符上限（ulimit -n、fs.file-max）、每条连接的内核内存（sock 结构 + 收发缓冲区）、CPU（中断、协议栈处理、应用逻辑），以及 I/O 模型（需要 epoll / IOCP 之类的多路复用）。

    思考题 3：一个游戏要用 UDP 发送 10 KB 的场景快照，直接 sendto 一次行不行？

    技术上可以（UDP 最大负载约 64 KB），但会被 IP 层切成 7～8 个分片，任何一个分片丢失整个数据报就作废，丢包率被放大约 7 倍，还可能被中间设备直接丢弃。正确做法是在应用层把快照切成若干个 ≤ 1200 字节的片，每片带上"消息 ID + 片序号 + 总片数"，可靠发送并在对端重组；或者只发送和上一个已确认快照的差量（delta）。

    CHAPTER 02

    UDP：薄到极致的传输层

    UDP = IP + 端口 + 校验和。它的价值恰恰在于"不做什么"。

    本章目标
    • 背出 UDP 头部 4 个字段及含义，会算最大负载，知道伪首部为什么存在
    • 理解"无连接""保留消息边界""尽力交付"三个特性的具体含义，并能用实测输出佐证
    • 掌握 UDP 与 TCP 的 socket 编程调用序列差异
    • 说出 UDP 的优缺点与典型应用场景，以及使用 UDP 时必须由应用补上的东西

    2.1 一句话定义

    UDP（User Datagram Protocol，用户数据报协议，RFC 768）是一种无连接、不可靠、面向数据报的传输层协议。它在 IP 之上只额外提供了两样东西：端口（让数据能交给正确的进程）和校验和（检测数据是否损坏）。RFC 768 全文只有 3 页，这在 IETF 的协议里极其罕见。

    📮 一个类比：寄明信片

    UDP 像寄明信片：写上地址（IP）和收件人（端口）就丢进邮筒，不需要事先打电话确认对方在家；每张明信片独立投递，可能丢、可能晚到、两张寄出的顺序和收到的顺序可能相反；但每张明信片都是完整的一张，不会出现半张。TCP 则像打电话：先拨号接通（握手），然后连续说话，对方听不清会让你重说，最后说再见挂断（挥手）。

    2.2 报文结构：只有 8 字节

    字段位数含义与细节
    源端口16发送方端口。客户端一般由系统分配临时端口；如果不需要对方回复，可以填 0。
    目的端口16接收方端口，内核据此找到目标 socket。找不到时回复 ICMP "端口不可达"。
    长度16UDP 头部加数据的总长度，最小 8。最大 65535，所以 IPv4 下数据最多 65535 − 8 − 20（IP 头）= 65507 字节。
    校验和16把伪首部 + UDP 头部 + 数据按 16 位反码求和再取反。IPv4 下可以填 0 表示"未计算"；IPv6 下必须计算（因为 IPv6 去掉了 IP 头部校验和）。

    伪首部：为什么校验和要把 IP 地址也算进去

    计算校验和时，会在 UDP 报文前面临时拼一个 12 字节的伪首部（pseudo header）：源 IP、目的 IP、一个全 0 字节、协议号 17、UDP 长度。伪首部不会被发送，只参与计算。

    目的是检测"送错了地方"：如果 IP 头部在传输中出错，导致一个本该发给 A 的数据报被交给了 B，单看 UDP 头部和数据是发现不了的；把 IP 地址纳入校验后，B 计算出的校验和就对不上，会丢弃这个数据报。TCP 的校验和用的是同样的方法（协议号为 6）。

    16 位反码求和（UDP / TCP / IP 校验和通用算法）
    uint16_t InternetChecksum(const uint8_t* data, size_t len, uint32_t sum = 0) {
    for (size_t i = 0; i + 1 < len; i += 2)
        sum += (uint32_t(data[i]) << 8) | data[i + 1];   // 按 16 位大端累加
    if (len & 1) sum += uint32_t(data[len - 1]) << 8;    // 奇数长度：末尾补 0
    while (sum >> 16) sum = (sum & 0xFFFF) + (sum >> 16); // 进位回卷（反码加法）
    return uint16_t(~sum);                                // 取反
}
// 计算 UDP 校验和：先把伪首部（源IP、目的IP、0、17、UDP长度）累加进 sum，再累加 UDP 头部和数据
// 接收方对"伪首部 + 整个 UDP 报文（含校验和字段）"再算一遍，结果为 0 说明无错
    ⚠️ 易错点：校验和能保证数据正确吗？

    不能完全保证。16 位反码和很弱：两个 16 位字互换位置、或两处错误恰好抵消，它都发现不了。链路层的 CRC32 能挡住绝大部分随机错误，但对恶意篡改毫无办法。需要防篡改就必须用密码学手段（TLS、DTLS、QUIC 的 AEAD 加密认证）。

    2.3 无连接：想发就发，发完不管

    "无连接"的意思是：通信前不需要握手，内核里不为"对方"保存任何状态。一个 UDP socket 可以给任意多个地址发数据，也可以收任意多个地址发来的数据。这带来三个直接后果：

    1. 发送没有前置延迟：第一个包就能携带业务数据，省掉握手的 1 个 RTT。
    2. 服务器没有连接状态：一个 socket 就能服务海量客户端，内存占用极低，也不存在 TIME_WAIT 之类的连接管理问题。
    3. 发送方不知道对方是否存在：sendto 返回成功，只说明数据已经交给了本机内核，不代表对方收到了，甚至不代表对方存在。
    🧪 实测证据（d1 · E2）：发给一个没人监听的端口
    d1_tcp_udp_behaviors.exe · E2
    == E2 UDP 无连接：发给没人监听的端口 ==
  sendto 返回 4（发送"成功"——UDP 不知道对方在不在）
  随后 recvfrom 返回 -1，WSAGetLastError=10054（10054=WSAECONNRESET：内核收到 ICMP 端口不可达）
  关闭 SIO_UDP_CONNRESET 后：recvfrom 返回 -1，WSAGetLastError=10060（10060=超时，错误被静默丢弃）

    sendto 照样返回发出的 4 字节。对方主机的内核发现 40012 端口没人监听，回了一个 ICMP 端口不可达。Windows 会把这个 ICMP 错误"记"在 socket 上，让下一次 recvfrom 报 WSAECONNRESET——对一个"无连接"协议来说这个错误名相当有迷惑性。

    🎮 游戏开发视角：Windows 上 UDP 服务器的经典坑

    游戏服务器用一个 UDP socket 服务所有玩家。某个玩家断线后，服务器继续往他的地址发包，对端回 ICMP 端口不可达，于是服务器的下一次 recvfrom 报 WSAECONNRESET。如果代码把这个错误当成"socket 坏了"去关闭重建，所有玩家都会掉线。解决办法就是实测中的 WSAIoctl(SIO_UDP_CONNRESET, FALSE)，或者把这个错误码当作可忽略的提示。Linux 上，只有对 UDP socket 调用过 connect() 时才会把 ICMP 错误报给应用（ECONNREFUSED），未 connect 的 socket 默认不报。

    UDP 上的 connect() 是什么意思

    UDP socket 也可以调用 connect()，但不会发送任何报文，只是在内核里记下一个默认对端：之后可以用 send/recv 代替 sendto/recvfrom，内核只接收来自这个对端的数据报，并且能把 ICMP 错误报告给应用。它是"本地过滤器"，不是"连接"。QUIC 客户端和很多游戏客户端都会对 UDP socket 调用 connect()，顺便还能让内核少做一次路由查找。

    2.4 面向数据报：保留消息边界

    UDP 的每一次 sendto 都对应一个独立的数据报，接收方每次 recvfrom 恰好取出一个完整的数据报，既不会把两个合并，也不会只给你半个。这叫"保留消息边界"。TCP 则是字节流，没有消息边界的概念。

    🧪 实测证据（d1 · E1）：三次发送，两种结果
    d1_tcp_udp_behaviors.exe · E1
    == E1 消息边界：UDP 保留边界，TCP 是字节流 ==
  UDP recvfrom #1 ->  5 字节: "hello"
  UDP recvfrom #2 -> 12 字节: "tcp-udp-book"
  UDP recvfrom #3 -> 27 字节: "reliable-transport-over-udp"
  TCP 发送方 send() 3 次（5+12+27=44 字节），接收方 recv() 1 次 -> 44 字节: "hellotcp-udp-bookreliable-transport-over-udp"

    同样是发送三条消息、接收方稍晚一点再读：UDP 原样收到三条；TCP 一次 recv 就把 44 个字节全拿走了，三条消息"粘"在一起，接收方无从知道原来的边界在哪——这就是第 3 章要讲的粘包。

    ⚠️ 易错点：接收缓冲区比数据报小会怎样？

    数据报多出来的部分会被直接丢弃，不会留到下一次 recvfrom。Linux 会在 msg_flags 里置 MSG_TRUNC，Windows 的 recvfrom 返回错误 WSAEMSGSIZE（缓冲区里仍是截断后的数据）。所以 UDP 接收缓冲区要按协议的最大包长来开（例如 1500 或 64 KB）。

    2.5 尽力交付：UDP 不做的事

    不做的事具体表现如果你需要，应该怎么补
    不确认、不重传丢了就是丢了，发送方完全不知道应用层序号 + ACK + 重传（第 8 章）
    不排序按到达顺序交给应用应用层序号 + 接收缓冲重排，或只取"最新"的
    不去重网络重复的包会被交付两次序号 + 已收集合（滑动位图）
    不做流量控制接收方 socket 缓冲区满了，新来的数据报被内核静默丢弃增大 SO_RCVBUF；应用层窗口通告
    不做拥塞控制应用以多快的速度 sendto，内核就以多快的速度往外发应用层限速（令牌桶）、拥塞控制算法
    不分片超过 MTU 的数据报交给 IP 分片应用层控制包长 ≤ 1200～1400，大消息自己切

    看到这里可能会疑惑：UDP 什么都不做，凭什么被大量使用？答案是："不做"本身就是一种能力——它把这些决定权留给了最了解业务需求的应用。语音通话里一个 20 ms 的语音帧丢了，最好的处理是让解码器插值补上，而不是等 200 ms 重传过来时这句话早已说完。这个思路是第四部分的出发点。

    2.6 编程模型：UDP 与 TCP 的调用序列

    最小 UDP 回显服务器（Winsock，省略错误处理）
    SOCKET s = socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP);
sockaddr_in addr{}; addr.sin_family = AF_INET; addr.sin_port = htons(7777); addr.sin_addr.s_addr = INADDR_ANY;
bind(s, (sockaddr*)&addr, sizeof addr);
char buf[1500];
for (;;) {
    sockaddr_in from{}; int fromLen = sizeof from;
    int n = recvfrom(s, buf, sizeof buf, 0, (sockaddr*)&from, &fromLen);  // 一次取一个完整数据报
    if (n > 0) sendto(s, buf, n, 0, (sockaddr*)&from, fromLen);          // 原样发回给来源地址
}

    2.7 UDP 独有的能力：广播与多播

    TCP 是严格的一对一连接，而 UDP 因为无连接，可以把一个数据报发往广播地址（如 255.255.255.255 或子网广播 192.168.1.255）或多播组（224.0.0.0/4），一次发送、多个接收者同时收到。

    • DHCP：新设备还没有 IP 地址，只能用广播（客户端 68 → 服务器 67）寻找 DHCP 服务器。
    • 局域网游戏发现：客户端广播"有房间吗"，局域网内的主机回复房间信息。
    • mDNS / SSDP：打印机、投屏设备的自动发现。
    • IPTV / 行情分发：机房内用多播把同一份数据推给大量订阅者。

    2.8 优缺点与典型应用

    优点

    ① 低延迟：无握手，第一个包就能带数据；无重传等待，不会被前面丢失的包卡住。
    ② 开销小：头部 8 字节，内核无连接状态。
    ③ 保留消息边界：天然适合"一个包一条消息"的协议。
    ④ 灵活：支持广播 / 多播；可靠性、拥塞控制都能按需在应用层定制。

    缺点

    ① 不可靠：丢、乱、重全要应用自己处理。
    ② 无拥塞控制：滥发会挤占网络，也会被运营商 QoS 限速。
    ③ NAT 不友好：NAT 映射超时短（常见 30 s～数分钟），必须定期发心跳保活。
    ④ 易被滥用：源地址可伪造，可被用于反射放大攻击（DNS、NTP、Memcached）。

    场景为什么用 UDP可靠性怎么补
    DNS 查询小报文一问一答，省掉握手 RTT超时重问；大应答回退 TCP
    DHCP没有 IP 时只能广播超时重发
    语音 / 视频通话（RTP、WebRTC）实时性第一，迟到的数据没用FEC、NACK 选择性重传、丢帧插值、抖动缓冲
    低延迟直播减少重传卡顿FEC + 有限重传（SRT 等协议）
    在线游戏位置、输入只关心最新值；每毫秒都很宝贵按消息分级：状态不可靠、指令可靠（第 8、11 章）
    HTTP/3绕开内核 TCP，实现多路复用与 0-RTTQUIC 在用户态完整实现可靠传输（第 10 章）
    VPN / 隧道（WireGuard、VXLAN）避免"TCP 套 TCP"的双重重传交给隧道内部的 TCP 处理
    ✅ 面试答法：说说你对 UDP 的理解

    UDP 是无连接、不可靠、面向数据报的传输层协议，头部只有 8 字节：源端口、目的端口、长度、校验和。它在 IP 之上只加了端口复用和差错检测，不建立连接、不确认、不重传、不排序、不做流量和拥塞控制，但保留消息边界、支持广播多播。优点是延迟低、开销小、灵活，缺点是可靠性和拥塞控制都要应用自己负责。典型场景是 DNS、DHCP、音视频实时通信、在线游戏，以及 HTTP/3 底层的 QUIC。（加分项）如果在 UDP 上需要可靠性，可以在应用层实现序号、确认、重传和窗口，比如 KCP 或 QUIC。

    本章小结
    • UDP 头部 8 字节：源端口、目的端口、长度、校验和；IPv4 最大负载 65507 字节。
    • 校验和覆盖伪首部（IP 地址、协议号、长度），用来发现"送错地方"；IPv4 可选、IPv6 必选；弱校验，防不了篡改。
    • 无连接：sendto 成功 ≠ 对方收到；Windows 上 ICMP 端口不可达会让下一次 recvfrom 报 WSAECONNRESET（实测）。
    • 保留消息边界：一次 sendto 对应一次 recvfrom（实测）；缓冲区不够时多余部分被丢弃。
    • 不重传、不排序、不去重、不限速，这些"缺点"正是它灵活、低延迟的来源。
    思考题 1：UDP 包长度字段已经有了，为什么还需要 IP 头部的总长度字段？反过来呢？

    严格来说 UDP 长度字段是冗余的：UDP 长度 = IP 总长度 − IP 头部长度。保留它的原因是让 UDP 的校验和计算、报文解析可以不依赖下层（分层独立），而且伪首部中也用到这个长度。IP 头部的总长度则是网络层自己需要的（转发、分片），不能依赖上层协议。

    思考题 2：UDP 服务器的接收缓冲区满了会怎样？TCP 呢？

    UDP：内核直接丢弃新到的数据报，发送方毫不知情（可以通过 netstat -su 的 "receive buffer errors" 观察）。TCP：接收方通过窗口字段告诉发送方"我还能收多少"，缓冲区满时通告窗口为 0，发送方暂停发送并周期性发零窗口探测，数据不会丢——这就是流量控制。

    思考题 3：既然 UDP 不可靠，为什么说"UDP 更适合游戏"？这句话完全对吗？

    不完全对，应该说"UDP 让游戏有机会做得更好"。游戏里大量数据（位置、朝向）是"状态"，只关心最新值，丢了等下一帧即可，用 TCP 反而会因为重传和队头阻塞让后面的新状态被卡住。但游戏里也有必须可靠的数据（技能释放、购买道具、聊天），所以实际是"UDP + 应用层按需可靠"。另外，很多回合制、卡牌、MMO 的非战斗部分直接用 TCP 也完全够用，实时性要求高的 FPS、MOBA、格斗才更依赖 UDP。

    TCP：可靠字节流的全套机制

    序号、确认、重传、窗口、拥塞控制——把一个会丢会乱的网络，包装成一根"不丢不乱的管道"。

    本章目标

    • 理解"字节流"与序号 / 确认号的计算，能解释粘包、拆包并给出解决方案
    • 讲清超时重传（RTO 计算、Karn 算法、指数退避）、快速重传与 SACK
    • 讲清滑动窗口、流量控制、零窗口、Nagle 与延迟确认
    • 讲清慢启动、拥塞避免、快速恢复，以及 CUBIC、BBR 的思想；区分流量控制与拥塞控制

    3.1 一句话定义

    TCP（Transmission Control Protocol，传输控制协议，现行标准 RFC 9293）是一种面向连接的、可靠的、基于字节流的、全双工传输层协议。拆开看：

    面向连接

    通信前先三次握手，双方各自建立连接状态（序号、窗口、缓冲区）；结束后四次挥手释放。只能一对一，不支持广播多播。

    可靠

    数据不丢、不重、不错、按序交付给应用。靠校验和 + 序号 + 确认 + 重传实现。

    字节流

    TCP 眼里只有一串连续的字节，没有"消息"的概念。应用写入的边界不会被保留。

    全双工

    双方可以同时收发，两个方向各有独立的序号空间和窗口，因此关闭时也要两个方向分别关闭。

    3.2 头部结构：20 字节固定 + 最多 40 字节选项

    字段位数作用

    发送方在收到确认之前最多能发"一个窗口"的数据，所以吞吐上限 ≈ 窗口 / RTT。窗口最大 64 KB、RTT 100 ms（北京到美西）时，吞吐上限只有 64 KB / 0.1 s ≈ 5 Mbps——哪怕你的带宽是 1 Gbps。要跑满带宽，窗口至少要达到带宽时延积（BDP）：1 Gbps × 100 ms = 12.5 MB，所以必须用窗口扩大选项。下载海外大文件时速度上不去，常见原因之一就是某一端的接收窗口太小。

    3.3 字节流、序号与"粘包"

    序号按字节编号

    TCP 给字节流中的每一个字节都编号，而不是给每个段编号。段的序号是它第一个字节的编号，确认号是"期望的下一个字节"。例如 ISN = 1000，SYN 占用 1 个序号，于是第一个数据字节的编号是 1001：

    报文seq数据长度接收方回复的 ack
    段 110011001101
    段 211012001301
    段 3（丢失）1301100—
    段 41401100仍然是 1301（累计确认：1301 还没到，后面到了也不能确认）

    最后一行引出两个问题：发送方怎么知道段 3 丢了（3.4 节的重传），以及段 4 已经到了却不能确认是不是太浪费（3.4 节的 SACK）。

    粘包与拆包

    因为 TCP 没有消息边界，应用写入的"消息"和接收方读出来的"块"之间没有任何对应关系：

    第 2 章的 d1 · E1 实测就是这种情况：三次 send 的 44 字节被一次 recv 全部读出。粘包可能发生在发送端（Nagle 算法把小块合并成一个段）、也可能发生在接收端（多个段到达后还没被读走，在接收缓冲区里连成一片）。常见的应用层分帧方案有三种：

    方案做法优点缺点例子
    定长消息每条消息固定 N 字节最简单浪费空间，不灵活一些硬件 / 金融行情协议

    长度前缀分帧：处理"粘包 + 半包"的标准写法
    // 接收缓冲 buf 里累积了从 socket 读到的字节；每次 recv 后调用一次
// 帧格式：[4 字节大端长度 len][len 字节消息体]
void OnBytes(std::vector<uint8_t>& buf, auto&& onMessage) {
    size_t off = 0;
    while (buf.size() - off >= 4) {                                   // 1) 头部够不够
        uint32_t len = (buf[off] << 24) | (buf[off+1] << 16) | (buf[off+2] << 8) | buf[off+3];
        if (len > kMaxMessage) throw std::runtime_error("bad frame");  // 2) 防御恶意长度
        if (buf.size() - off - 4 < len) break;                         // 3) 半包：消息体还没收全，等下次
        onMessage(&buf[off + 4], len);                                 // 4) 一条完整消息
        off += 4 + len;                                                // 5) 可能还有下一条（粘包）
    }
    buf.erase(buf.begin(), buf.begin() + off);                         // 保留不完整的尾巴
}
    ⚠️ 易错点："UDP 会不会粘包？"

    不会。UDP 每个数据报都是独立的，内核按数据报为单位排队，recvfrom 一次只取一个。但 UDP 会丢包、乱序，以及缓冲区太小时截断。所以"粘包"是字节流协议特有的问题，面试里如果被问"怎么解决 TCP 粘包"，一定要先说明"这是因为 TCP 是字节流、没有消息边界"。

    3.4 可靠传输之一：确认与重传

    可靠传输的核心逻辑一句话就能说完：发送方给数据编号并保留副本，接收方收到后回确认，发送方在一定时间内没有收到确认就重发。难点全在细节：多久算"没收到"？怎么更早发现丢包？只丢了一个时能不能只重发一个？

    超时重传：RTO 怎么定

    重传超时时间 RTO（Retransmission TimeOut）太短会导致大量不必要的重传，太长则丢包后要干等很久。TCP 根据测得的往返时间 RTT 动态计算（RFC 6298）：

    RFC 6298：RTO 计算
    首次测得 RTT 样本 R：   SRTT = R          RTTVAR = R / 2
之后每个新样本 R'：     RTTVAR = (1 - 1/4) * RTTVAR + 1/4 * |SRTT - R'|
                       SRTT   = (1 - 1/8) * SRTT   + 1/8 * R'
                       RTO    = SRTT + max(G, 4 * RTTVAR)        // G 为时钟粒度
约束：RTO 下限 1 s（RFC 建议；Linux 实际用 200 ms），上限 ≥ 60 s；首个样本之前 RTO = 1 s
超时后：RTO = RTO × 2（指数退避），直到收到新的确认后重新计算
    • 为什么要加 4 × RTTVAR：只用平均值的话，RTT 一抖动就会误判超时。方差项让 RTO 在网络抖动大时自动变宽。
    • Karn 算法：重传过的段收到 ACK 时，不能用来采样 RTT——因为分不清这个 ACK 是对原始段还是对重传段的确认（重传歧义）。时间戳选项可以解决这个歧义；QUIC 则用"包号永不重复"从根本上消除了它（第 10 章）。
    • 指数退避：连续超时说明网络可能严重拥塞，每次把 RTO 翻倍，避免雪上加霜。代价是：连续丢几次后，RTO 会变成几秒甚至几十秒——这是游戏场景最痛恨的地方，也是 KCP 要改的第一件事（第 9 章）。

    快速重传：不等超时

    超时重传至少要等一个 RTO（Linux 至少 200 ms）。能不能更早发现丢包？可以利用累计确认的特性：当某个段丢失后，后续每个段到达时接收方都会回复同样的确认号（重复 ACK）。发送方收到 3 个重复 ACK，就认为该段丢了，立即重传，不等定时器。

    🔬 为什么是 3 个重复 ACK，而不是 1 个？

    因为网络存在轻微乱序：段 3 比段 2 先到，也会产生 1 个重复 ACK，但随后段 2 到达就恢复了。阈值设为 3，是在"尽早发现丢包"和"把乱序误判成丢包"之间的经验折中。现代 Linux 默认还启用了 RACK（基于时间而不是计数判断丢包，RFC 8985）和 TLP 尾部丢失探测（解决"最后几个段丢了，后面没有段来触发重复 ACK"的问题）。KCP 把这个阈值做成了可调参数 resend，游戏场景常设为 2（第 9 章）。

    SACK：只重传真正丢了的

    累计确认只能说"我连续收到哪里为止"。如果一个窗口里丢了多个不连续的段，发送方只靠重复 ACK 无法知道到底丢了哪几个，要么一个 RTT 只能修复一个洞，要么把后面全部重发（类似回退 N 步）。SACK（选择确认，RFC 2018）在 ACK 的选项中附带最多 3～4 个"已收到的不连续块"，例如 ack=101, SACK=[201-501]，发送方就能精确地只重传 101～200。Linux 默认开启 SACK（net.ipv4.tcp_sack=1）。

    3.5 可靠传输之二：滑动窗口与流量控制

    如果每发一个段都要等确认再发下一个（停等协议），信道利用率极低：RTT 100 ms、每次 1460 字节，吞吐只有 14.6 KB/s。解决办法是允许连续发送多个段而不等确认，这些"已发出未确认"加上"允许发出"的部分就构成了发送窗口。

    流量控制：别把对方淹死

    接收方的应用可能读得很慢（比如游戏服务器卡在一次数据库查询上），接收缓冲区就会逐渐被填满。TCP 让接收方在每个 ACK 的窗口字段里告诉发送方"我还剩多少空间"（rwnd），发送方保证在途数据不超过 rwnd。这就是流量控制：端到端、由接收方驱动，保护的是接收方。

    • 零窗口：rwnd = 0 时发送方停止发送，并启动坚持定时器（persist timer），周期性发 1 字节的零窗口探测，防止"接收方窗口恢复的那个通告 ACK 丢了，双方永远互相等待"的死锁。
    • 糊涂窗口综合征（Silly Window Syndrome）：接收方每腾出几个字节就通告一次，发送方就发几个字节的小段，头部开销远大于数据。对策：接收方等腾出足够空间（一个 MSS 或缓冲区一半）再通告；发送方用 Nagle 算法。

    Nagle 算法与延迟确认：一对"好心办坏事"的组合

    Nagle 算法（发送方）

    如果还有已发送未确认的数据，新产生的小数据（不足一个 MSS）先攒着，等收到 ACK 或攒满一个 MSS 再发。目的是减少网络上的小包数量。

    延迟确认（接收方）

    收到数据后不立即回 ACK，而是等一会儿（Linux 最少约 40 ms，Windows 默认 200 ms），希望能把 ACK 捎带在应答数据里，或者攒两个段一起确认。

    两者单独都合理，叠加起来却会出问题：客户端发了一个小请求的前半段，Nagle 要等 ACK 才发后半段；服务器收到前半段，延迟确认要等 40～200 ms 才回 ACK——于是每个请求都凭空多出几十到上百毫秒。

    🎮 游戏开发视角：TCP 游戏连接一定要开 TCP_NODELAY

    游戏的操作消息都很小、要求立即发出。用 TCP 承载时，务必 setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &one, sizeof one) 关闭 Nagle；Linux 上还可以用 TCP_QUICKACK 临时关闭延迟确认。Redis、gRPC、大多数 RPC 框架默认都会开启 TCP_NODELAY。

    3.6 拥塞控制：别把网络挤爆

    流量控制只关心接收方，但路径中间的路由器也有容量。如果所有发送方都只看 rwnd 全速发，路由器队列被打满，丢包、重传、更多丢包，网络吞吐会断崖式下跌——这在 1986 年真实发生过（"拥塞崩溃"，NSFNET 吞吐一度跌到原来的千分之一），之后才有了 Van Jacobson 的拥塞控制算法。

    TCP 发送方维护一个拥塞窗口 cwnd，表示"我估计网络还能承受多少在途数据"，实际发送窗口取 min(rwnd, cwnd)。经典 Reno 算法有四个部分：

    阶段触发条件cwnd 怎么变直觉
    慢启动连接开始 / 超时之后，cwnd < ssthresh每收到一个 ACK，cwnd += 1 → 每 RTT 翻倍。初始窗口现在通常为 10 个 MSS（RFC 6928）"慢"是指起点低，增长其实是指数级的
    拥塞避免cwnd ≥ ssthresh每 RTT cwnd += 1（线性增长）接近上次出事的位置了，小心试探
    快速重传 + 快速恢复3 个重复 ACKssthresh = cwnd / 2；cwnd = ssthresh（+3）；然后进入拥塞避免还能收到重复 ACK 说明网络还通，只是轻度拥塞
    超时RTO 到期ssthresh = cwnd / 2；cwnd = 1；重新慢启动连 ACK 都收不到了，说明拥塞严重

    现代算法：CUBIC 与 BBR

    CUBIC（Linux 默认，RFC 9438）

    仍然以丢包为拥塞信号，但 cwnd 的增长按"距离上次丢包的时间"的三次函数变化：远离上次丢包点时增长快，接近时放缓并在附近长时间停留，丢包后再快速探测。增长和 RTT 无关，对长肥管道更公平、更高效。

    BBR（Google，2016）

    不再把丢包当拥塞信号，而是持续测量瓶颈带宽 BtlBw和最小往返时延 RTprop，按 BtlBw × RTprop 控制在途数据量、按 BtlBw 控制发送速率（pacing）。在有随机丢包的链路（无线、跨国）上吞吐远好于 CUBIC，也不会把路由器缓冲区塞满。

    ⚠️ 易错点：流量控制 vs 拥塞控制
    流量控制拥塞控制
    保护谁接收方（别把它的缓冲区淹了）网络（别把路由器挤爆）
    信息来源接收方在 ACK 中显式通告 rwnd发送方根据丢包、RTT 等自己推测 cwnd
    作用范围点对点全局（所有共享瓶颈的流）
    发送窗口两者同时生效：发送窗口 = min(rwnd, cwnd)
    🎮 游戏开发视角：基于丢包的拥塞控制在弱网下的副作用

    移动网络、Wi-Fi 上的丢包很多是随机干扰而不是拥塞，但 Reno / CUBIC 一律把它当成拥塞信号去减窗。对下载大文件来说只是速度慢一点；对每秒几十个小包的游戏来说，窗口被压到比实际需要还小，消息就会在发送缓冲里排队，延迟越积越高。第 8 章的仿真会量化这件事，第 9 章的 KCP 提供了关闭拥塞控制的开关 nc=1。

    ✅ 面试答法：TCP 如何保证可靠传输？

    按"问题 → 机制"答：① 数据出错：校验和，错了直接丢弃，当作丢包处理；② 丢包：序号 + 确认 + 重传，包括基于 RTT 动态计算 RTO 的超时重传，以及 3 个重复 ACK 触发的快速重传，配合 SACK 只重传缺失部分；③ 乱序和重复：接收方按序号在接收缓冲区里重排、丢弃重复段，只把连续数据交给应用；④ 接收方处理不过来：滑动窗口流量控制；⑤ 网络拥塞：拥塞控制（慢启动、拥塞避免、快速重传、快速恢复）；⑥ 双方状态同步：三次握手和四次挥手的连接管理。

    本章小结
    • TCP：面向连接、可靠、字节流、全双工。头部 20～60 字节；关键字段 seq / ack / 窗口 / 标志位。
    • 序号按字节编号，ack 是"期望的下一个字节"（累计确认）；SYN、FIN 各占 1 个序号。
    • 字节流没有边界 → 粘包 / 拆包；用长度前缀等应用层分帧解决；UDP 不存在粘包。
    • RTO = SRTT + 4·RTTVAR，Karn 算法，超时指数退避；3 个重复 ACK 快速重传；SACK 精确重传。
    • 发送窗口 = min(rwnd, cwnd)：rwnd 是流量控制（保护接收方），cwnd 是拥塞控制（保护网络）。
    • Reno：慢启动（翻倍）→ 拥塞避免（+1）→ 3 dup ACK 减半 / 超时归 1；CUBIC 是 Linux 默认，BBR 基于带宽和时延建模。
    • Nagle + 延迟确认会制造几十～几百毫秒延迟，交互式应用要开 TCP_NODELAY。
    思考题 1：ISN = 5000，客户端依次发送 300 字节、200 字节两个段，服务器全部收到，最后的 ack 是多少？

    SYN 占用一个序号，所以第一个数据字节编号 5001。第一个段 seq=5001、长度 300；第二个段 seq=5301、长度 200；服务器累计确认 ack = 5301 + 200 = 5501。

    思考题 2：接收方通告窗口为 0 后，发送方怎么知道什么时候可以继续发？如果通告恢复的那个 ACK 丢了呢？

    接收方腾出空间后会主动发一个窗口更新 ACK。但纯 ACK 不会被重传，如果它丢了，发送方一直认为窗口为 0，接收方一直等数据，形成死锁。所以发送方在收到零窗口后启动坚持定时器，周期性发送零窗口探测报文（携带 1 字节数据或序号为 SND.UNA−1 的段），强迫接收方回复当前窗口。

    思考题 3：为什么说"TCP 的拥塞控制在无线网络上表现不好"？有哪些改进？

    Reno / CUBIC 把丢包视为拥塞信号，而无线链路上的丢包很多来自信号干扰、切换基站，并非拥塞。于是 TCP 频繁地无谓减窗，吞吐上不去。改进方向：① 基于时延 / 带宽建模的算法，如 BBR；② 链路层本地重传（Wi-Fi、4G 本身有 ARQ/HARQ），减少暴露给 TCP 的丢包；③ ECN 显式拥塞通知，让路由器直接标记"我拥塞了"，而不是靠丢包传达；④ 应用层自定义传输（QUIC 可插拔拥塞控制、KCP 关闭拥塞控制）。

    思考题 4：发送窗口是不是越大越好？

    不是。窗口达到带宽时延积（BDP）就足以跑满带宽，再大也不会更快，只会让更多数据堆在路由器队列里，增加排队时延（即 Bufferbloat），并在丢包时需要重传更多数据、占用更多内存。这正是 BBR 把在途数据控制在 BDP 附近的原因。
