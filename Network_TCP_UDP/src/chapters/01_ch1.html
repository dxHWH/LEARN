第一部分　网络基础：传输层站在哪里

先搞清楚传输层上面是谁、下面是谁、下面的 IP 到底承诺了什么、没承诺什么。TCP 和 UDP 的一切设计，都是对"IP 只尽力而为"这件事的回应。

CHAPTER 01

从一次网页请求说起

在浏览器里敲下一个网址，到页面开始出现，网线上依次走过了 UDP、TCP、TLS、HTTP。

本章目标
  • 能画出一次 HTTPS 网页请求的完整时序，并说出每一段属于哪一层、花了几个 RTT
  • 说清 TCP/IP 分层模型、封装与解封装，以及各层 PDU 的名字
  • 理解 IP 的"尽力而为"和端到端原则，明白为什么可靠性要放在传输层做
  • 掌握端口、套接字、五元组、MTU 与 MSS 这几个后面反复出现的基本概念

1.1 敲下回车之后：一张时序图看全流程

假设你在浏览器里输入 https://www.example.com 并回车，且本机没有任何缓存。抛开浏览器内部的解析和渲染，单看网络，大致会发生四件事：

  1. DNS 解析：把域名翻译成 IP 地址。浏览器（通过操作系统）向 DNS 服务器发一个查询，通常用 UDP 的 53 端口，一问一答。
  2. TCP 三次握手：和 Web 服务器的 443 端口建立一条 TCP 连接。
  3. TLS 握手：在 TCP 连接之上协商加密参数、验证服务器证书。TLS 1.3 需要 1 个 RTT。
  4. HTTP 请求与响应：发送 GET /，收到 HTML。

这张图里已经藏着本书的大部分主题：

  • DNS 为什么用 UDP？一问一答、报文小，用 TCP 光握手就要多花 1 个 RTT，丢了重问一次即可（第 2 章、第 4 章）。
  • SYN、SYN+ACK、ACK 各自携带了什么、为什么是三次？（第 5 章）
  • HTML 被拆成很多个 TCP 段，丢了一个怎么办？乱序了怎么办？发太快怎么办？（第 3 章）
  • 能不能把 TCP 握手和 TLS 握手合并，把 4 个 RTT 压缩下来？这正是 QUIC / HTTP/3 的动机之一（第 10 章）。
📦 场景案例：RTT 才是网页慢的主因

很多人以为网页慢是因为"带宽不够"。实际上，打开一个普通网页只需要几百 KB，100 Mbps 的带宽传完只要几十毫秒；真正拖慢首屏的是来回次数（RTT 的个数）。这就是为什么工程上大量优化都在"省 RTT"：DNS 预解析、TCP 连接复用（HTTP Keep-Alive）、TLS 会话恢复、TCP Fast Open、HTTP/3 的 0-RTT。记住这个视角，后面讨论握手次数时你会更有体感。

1.2 分层模型：每层只做一件事

网络通信被拆成若干层，每一层只依赖下一层提供的服务，并向上一层提供服务。教科书里有两套模型：

OSI 七层TCP/IP 四层（五层教学版）负责什么典型协议PDU 名称
应用层 / 表示层 / 会话层应用层具体业务语义HTTP、DNS、TLS*、SSH、游戏协议报文（message）
传输层传输层进程到进程：端口复用、可靠性、流量 / 拥塞控制TCP、UDP、SCTP、QUIC*TCP 段（segment）/ UDP 数据报（datagram）
网络层网际层主机到主机：寻址与路由，跨越多个网络IPv4、IPv6、ICMP分组 / 包（packet）
数据链路层网络接口层（链路层 + 物理层）同一链路上相邻节点之间传帧以太网、Wi-Fi、PPP帧（frame）
物理层比特 ↔ 电 / 光 / 无线信号双绞线、光纤比特

* TLS 通常被视为位于传输层和应用层之间；QUIC 运行在 UDP 之上，但承担的是传输层职责，所以常被称为"用户态传输层"。

封装与解封装

发送时，数据从上往下走，每经过一层就在前面加上一层"信封"（头部）；接收时从下往上走，每一层拆掉属于自己的信封，再根据头部里的字段决定交给上面的谁。

✅ 面试答法：为什么要分层？

① 解耦：每层只关心自己的职责，换掉其中一层（如把有线换成 Wi-Fi、把 IPv4 换成 IPv6）不影响其他层；② 复用：所有应用共享同一套 TCP/IP 实现；③ 标准化：不同厂商只要遵守层间接口就能互通。代价是每层都有头部开销，层与层之间也可能出现信息不对称（例如 TCP 不知道底层是无线链路，把无线干扰导致的丢包误当成拥塞，第 3 章会讲）。

1.3 IP 的承诺：尽力而为

网络层的 IP 协议负责把一个包从源主机送到目标主机，中间可能经过几十个路由器。但 IP 只承诺"尽力而为"（best effort），具体来说：

❌ 不保证送达

路由器队列满了就直接丢包；TTL 减到 0 也丢。丢了不会通知任何人（最多偶尔回一个 ICMP）。

❌ 不保证顺序

先发的包可能走了更长的路径，后发先至。

❌ 不保证不重复

链路层重发、路由抖动都可能让同一个包到达两次。

❌ 不保证数据正确

IPv4 头部校验和只校验头部，不管数据；IPv6 连头部校验和都去掉了。

❌ 不控制速率

你发多快它就转多快，直到某个路由器扛不住开始丢包。

✅ 只保证一件事

按目标 IP 地址尽量把包往正确的方向转发。

为什么不让 IP 层直接做可靠？——端到端原则

如果让每个路由器都保证可靠（逐跳确认、逐跳重传），路由器就得为每条流保存状态、缓存数据，成本极高；而且即使每一跳都可靠，数据仍可能在终端主机的内存里出错，最终还是要由两端再确认一次。这就是著名的端到端原则（End-to-End Argument）：

📐 端到端原则

某个功能只有在通信的端点才能被完整、正确地实现时，就应该放在端点实现；网络中间只做简单、通用、高效的事情。
→ 所以 IP 保持"笨而快"，可靠性交给两端主机的传输层（TCP），或者干脆交给应用自己（UDP + 应用层可靠）。

这条原则也解释了本书最后一部分的存在：既然可靠性本来就是端点的事，那它放在内核里的 TCP 还是用户态的 KCP / QUIC，只是工程取舍，没有原则上的对错。

1.4 端口、套接字与五元组：找到具体的进程

IP 地址只能定位到主机，而一台主机上同时跑着浏览器、微信、游戏客户端。传输层的第一个职责就是复用与分用（multiplexing / demultiplexing）：发送时把多个进程的数据汇入同一个 IP 层，接收时再按端口号分发给正确的进程。

  • 端口（port）：16 位无符号整数，0～65535。0～1023 是知名端口（HTTP 80、HTTPS 443、DNS 53、SSH 22），1024～49151 是注册端口，49152～65535 是动态（临时）端口。Linux 默认的临时端口范围是 32768～60999（net.ipv4.ip_local_port_range）。
  • 套接字（socket）：操作系统提供给应用的通信端点抽象。应用读写 socket，内核负责把数据交给 TCP/UDP 协议栈。
  • 五元组：{协议, 源 IP, 源端口, 目的 IP, 目的端口}，唯一标识一条通信。
⚠️ 易错点：一台服务器最多只能有 65535 个 TCP 连接？

错。端口号的 65535 限制针对的是同一个四元组中的一个端口字段。服务器只监听一个端口（443），每条连接由{客户端 IP, 客户端端口}区分，理论上限是"客户端 IP 数 × 客户端端口数"，远超 65535。实际限制来自文件描述符上限和内存（每条连接的内核结构加收发缓冲区要占几 KB 到几十 KB）。
反过来，客户端连同一个服务器的同一个端口时，确实最多只能用掉约 2.8 万个（Linux 默认临时端口范围）本地端口——这就是第 6 章 TIME_WAIT 过多会导致"端口耗尽"的根源。

1.5 MTU、MSS 与分片

链路层一次能承载的最大数据长度叫 MTU（Maximum Transmission Unit），以太网是 1500 字节。比 MTU 大的 IP 包要么被分片（IPv4 允许路由器分片），要么被丢弃并回一个 ICMP "需要分片"（设置了 DF 位或 IPv6）。

  • 分片的坏处：任何一个分片丢了，整个 IP 包都要作废；分片重组消耗接收方资源；很多防火墙和 NAT 会直接丢弃分片。所以无论 TCP 还是 UDP，都应该尽量避免 IP 分片。
  • TCP 怎么避免：三次握手时双方在 SYN 里通过 MSS 选项告诉对方"我能收的最大段长"，一般是 MTU − 40 = 1460；之后 TCP 自己把字节流切成不超过 MSS 的段。再配合路径 MTU 发现（PMTUD）适应中间更小的 MTU（如 PPPoE 的 1492）。
  • UDP 怎么避免：UDP 不切分，应用交给它多大，它就发多大的数据报。所以应用必须自己控制每个数据报的大小：以太网下 UDP 负载不超过 1500 − 20 − 8 = 1472 字节；考虑到隧道、VPN、移动网络，实践中常取 1200～1400（QUIC 规定 IPv4/IPv6 下至少支持 1200 字节，KCP 默认 MTU 为 1400）。
🎮 游戏开发视角

游戏的同步包通常只有几十到几百字节，天然不会触发分片；但"进入场景时下发全量状态""发送一张大地图快照"这类大消息就必须在应用层手动分片、编号、重组，这正是第 8 章可靠 UDP 里"消息分片"机制要解决的问题。UE 的网络层把一个大的 Bunch 拆成多个 Partial Bunch 也是同一个道理。

本章小结
  • 一次冷启动 HTTPS 请求 ≈ DNS(UDP) + TCP 握手 + TLS 握手 + HTTP，约 4 个 RTT；网页慢多半慢在 RTT 个数。
  • TCP/IP 四层：应用 → 传输（进程到进程）→ 网际（主机到主机）→ 网络接口；PDU 依次叫报文、段 / 数据报、分组、帧。
  • IP 尽力而为：可能丢、乱、重、错、拥塞。按端到端原则，可靠性放在端点做。
  • 端口 16 位；TCP 连接按四元组区分，UDP socket 按目的地址区分；服务器连接数不受 65535 限制。
  • MTU 1500 → TCP MSS 1460、UDP 安全负载 ≤ 1472（实践取 1200～1400）；尽量避免 IP 分片。
思考题 1：为什么 DNS 一般用 UDP，什么情况下又会改用 TCP？

一般用 UDP：查询和应答都很小，一问一答，没有必要先花 1 个 RTT 建连接；丢了由客户端超时重问即可，DNS 解析器也不需要为每个客户端维护连接状态，抗并发能力强。
改用 TCP 的情况：① 应答超过 512 字节（未使用 EDNS0 时）或超过 EDNS0 协商的大小，服务器会在 UDP 应答中设置 TC（截断）位，客户端改用 TCP 重新查询；② 主从 DNS 服务器之间的区域传送（AXFR/IXFR）数据量大，必须用 TCP；③ DNS over TLS（DoT，端口 853）基于 TCP。

思考题 2：服务器只监听 443 一个端口，为什么能同时服务几十万个客户端？瓶颈在哪？

TCP 连接由四元组标识，服务器侧的 IP 和端口相同，但客户端的 IP 和端口不同，所以每条连接都是唯一的，不受 65535 的限制。瓶颈在于：进程 / 系统级文件描述符上限（ulimit -n、fs.file-max）、每条连接的内核内存（sock 结构 + 收发缓冲区）、CPU（中断、协议栈处理、应用逻辑），以及 I/O 模型（需要 epoll / IOCP 之类的多路复用）。

思考题 3：一个游戏要用 UDP 发送 10 KB 的场景快照，直接 sendto 一次行不行？

技术上可以（UDP 最大负载约 64 KB），但会被 IP 层切成 7～8 个分片，任何一个分片丢失整个数据报就作废，丢包率被放大约 7 倍，还可能被中间设备直接丢弃。正确做法是在应用层把快照切成若干个 ≤ 1200 字节的片，每片带上"消息 ID + 片序号 + 总片数"，可靠发送并在对端重组；或者只发送和上一个已确认快照的差量（delta）。
