CHAPTER 12

面试题库：40 道高频题

先自己口述一遍，再展开答案对照。每题末尾的【→】标出了对应章节，答不上来就回去重读。

使用方法
  • 按"基础 → TCP 机制 → 握手 → 挥手 → 可靠 UDP → 场景设计"的顺序，难度递增
  • 标 ★ 的是出现频率最高的题，至少要能完整说出 2 分钟
  • 答题结构推荐"结论 → 原因 → 细节 / 数字 → 延伸"，延伸部分最能体现知识体系

12.1 基础（8 题）

1. ★ TCP 和 UDP 的区别？

连接（面向连接 / 无连接）、可靠性（可靠 / 尽力交付）、有序性、数据单位（字节流 / 数据报，粘包问题）、头部（20～60 / 8 字节）、流量与拥塞控制（有 / 无）、通信模式（一对一 / 支持广播多播）、开销与时延。实时性差异的根源是 TCP 按序可靠交付导致的队头阻塞。【→ 第 4 章】

2. UDP 头部有哪些字段？最大能发多大的数据报？

源端口、目的端口、长度、校验和，各 16 位共 8 字节。长度字段最大 65535，减去 8 字节 UDP 头和 20 字节 IPv4 头，最大负载 65507 字节。但实际应控制在 MTU 以内（≤ 1472，常取 1200～1400）避免分片。【→ 第 2 章】

3. 校验和为什么要加伪首部？

伪首部包含源 / 目的 IP、协议号和长度，不发送、只参与计算，用于检测"数据报被送到了错误的主机或协议"——仅校验 UDP/TCP 报文本身发现不了 IP 头部出错导致的误投递。【→ 第 2 章】

4. 什么是 MTU 和 MSS？为什么要避免 IP 分片？

MTU 是链路层能承载的最大数据长度（以太网 1500）；MSS 是 TCP 段能携带的最大数据长度（MTU − IP 头 − TCP 头 = 1460），在 SYN 中协商。IP 分片后任何一片丢失整个包都要作废，重组耗资源，且常被防火墙丢弃。TCP 靠 MSS + PMTUD 避免，UDP 要靠应用控制包长。【→ 第 1 章】

5. 一台服务器最多能支持多少个 TCP 连接？

不受 65535 限制。连接由四元组标识，服务器端口固定时，理论上限是客户端 IP 数 × 端口数。实际受限于文件描述符上限、内存（每连接几 KB 到几十 KB）、CPU 和 I/O 模型。客户端连同一个服务器地址时，才受本地临时端口数量限制。【→ 第 1 章】

6. 同一个端口能同时被 TCP 和 UDP 使用吗？

可以，两者是独立的端口空间，内核先按 IP 头的协议号区分 TCP/UDP。DNS 就同时使用 TCP 53 和 UDP 53。【→ 第 4 章】

7. DNS 为什么用 UDP？什么时候用 TCP？

查询应答小、一问一答，UDP 省去握手 RTT，服务器无需维护连接。应答被截断（TC 位）、区域传送、DNS over TLS 时用 TCP。【→ 第 1 章思考题】

8. UDP 调用 connect() 有什么作用？

不发送任何报文，只在内核记录默认对端：之后可用 send/recv，只接收该对端的数据，并能收到 ICMP 错误（如 ECONNREFUSED）。【→ 第 2 章】

12.2 TCP 机制（10 题）

9. ★ TCP 如何保证可靠传输？

校验和（检错）、序号（排序、去重）、确认 + 重传（超时重传、快速重传、SACK）、滑动窗口流量控制、拥塞控制、连接管理（握手 / 挥手）。按"网络问题 → 机制"的对应关系答最清晰。【→ 第 3 章】

10. ★ 什么是粘包 / 拆包？怎么解决？

TCP 是字节流，不保留应用写入的边界，接收方一次读到的可能是多条消息的拼接或半条消息。发生在发送端（Nagle 合并）或接收端（缓冲区累积）。解决：应用层分帧——定长、分隔符、长度前缀（最常用）。UDP 不存在粘包。【→ 第 3 章，d1 · E1 实测】

11. RTO 是怎么计算的？Karn 算法是什么？

RFC 6298：SRTT = 7/8 SRTT + 1/8 R；RTTVAR = 3/4 RTTVAR + 1/4 |SRTT − R|；RTO = SRTT + 4·RTTVAR，下限 1 s（Linux 200 ms），超时后指数退避。Karn 算法：重传过的段不参与 RTT 采样，因为无法区分 ACK 对应哪一次发送。时间戳选项可以解决这个歧义。【→ 第 3 章】

12. ★ 快速重传是什么？为什么是 3 个重复 ACK？

收到 3 个重复 ACK 就认为对应段丢失，不等 RTO 立即重传。阈值 3 是"尽早发现丢包"与"不把轻微乱序误判为丢包"的折中。现代 Linux 还有 RACK（基于时间判断）和 TLP（尾部丢包探测）。【→ 第 3 章】

13. ★ 滑动窗口和流量控制是怎么工作的？零窗口怎么办？

发送方维护 [SND.UNA, SND.UNA+SND.WND) 的窗口，窗口内可以连续发送而不等确认；接收方在 ACK 中通告剩余接收缓冲 rwnd。rwnd = 0 时发送方暂停，并用坚持定时器周期性发零窗口探测，防止窗口更新报文丢失导致死锁。【→ 第 3 章】

14. ★ 拥塞控制有哪几个阶段？

慢启动（cwnd 每 RTT 翻倍，直到 ssthresh）、拥塞避免（每 RTT +1）、快速重传 + 快速恢复（3 dup ACK：ssthresh = cwnd/2，cwnd = ssthresh，进入拥塞避免）、超时（ssthresh = cwnd/2，cwnd = 1，重新慢启动）。发送窗口 = min(rwnd, cwnd)。【→ 第 3 章】

15. 流量控制和拥塞控制的区别？

流量控制保护接收方，由接收方显式通告 rwnd，点对点；拥塞控制保护网络，由发送方根据丢包 / 时延推测 cwnd，关注全局。两者共同决定发送窗口。【→ 第 3 章】

16. CUBIC 和 BBR 有什么区别？

CUBIC 是 Linux 默认算法，仍以丢包为拥塞信号，cwnd 按距上次丢包时间的三次函数增长，与 RTT 无关。BBR 不依赖丢包，测量瓶颈带宽和最小 RTT，按 BDP 控制在途数据、按带宽 pacing，在随机丢包链路上吞吐更好，且不会塞满路由器缓冲。【→ 第 3 章】

17. Nagle 算法和延迟确认是什么？为什么游戏要关闭 Nagle？

Nagle：有未确认数据时，小数据先攒着，收到 ACK 或攒满 MSS 再发。延迟确认：收到数据后等一段时间（40～200 ms）再回 ACK，希望捎带或合并。两者叠加会让小请求多等几十～几百毫秒。游戏消息小且要求实时，必须 TCP_NODELAY。【→ 第 3 章】

18. TCP 头部有哪些标志位？各自含义？

URG（紧急指针有效）、ACK（确认号有效）、PSH（尽快交付）、RST（重置连接）、SYN（同步序号，建连）、FIN（数据发送完毕，关闭）；另有 ECE、CWR 用于 ECN 显式拥塞通知。【→ 第 3 章】

12.3 三次握手（8 题）

19. ★ 描述三次握手的过程和状态变化。

① C 发 SYN(seq=x)，C：CLOSED → SYN_SENT；S 收到后 LISTEN → SYN_RCVD。② S 回 SYN+ACK(seq=y, ack=x+1)，C 收到后 → ESTABLISHED。③ C 回 ACK(ack=y+1)，S 收到后 → ESTABLISHED。SYN 占 1 个序号；第三次握手可携带数据。【→ 第 5 章】

20. ★ 为什么是三次握手，不是两次或四次？

① 防止历史连接（首要原因）：旧 SYN 到达后，客户端可在第三步用 RST 否决，两次握手时服务器会直接建立无效连接；② 同步双方 ISN，每个 ISN 都需要被确认，两次只能确认客户端的；③ 避免重复 SYN 建立多条无用连接。服务器的 ACK 和 SYN 可合并，所以不需要四次。【→ 第 5 章】

21. ISN 为什么要随机？

防止旧连接的延迟报文落入新连接的序号窗口；防止序号预测攻击（伪造连接、注入数据）。RFC 6528：ISN = 计时器 M + Hash(四元组, 密钥)，随时间递增且不可预测。【→ 第 5 章】

22. ★ 什么是半连接队列和全连接队列？满了会怎样？

半连接队列存放 SYN_RCVD 的连接（上限约 tcp_max_syn_backlog），全连接队列存放已完成握手、等待 accept 的连接（上限 min(backlog, somaxconn)）。半连接队列满时启用 SYN Cookie 或丢弃 SYN；全连接队列满且 tcp_abort_on_overflow=0 时丢弃第三次 ACK，服务器重传 SYN+ACK，客户端表现为"连接成功但请求超时"。可用 ss -lnt 观察。【→ 第 5 章】

23. ★ SYN Flood 是什么？怎么防？

伪造源 IP 大量发送 SYN，服务器为每个 SYN 分配半连接并重传 SYN+ACK，却永远等不到 ACK，半连接队列被占满，正常用户无法建连。防御：SYN Cookie（把状态编码进 ISN，握手完成前不存状态）、增大半连接队列、减少 tcp_synack_retries、SYN Proxy / 防火墙、流量清洗。【→ 第 5 章】

24. 第三次握手的 ACK 丢了会怎样？

客户端已 ESTABLISHED，服务器仍在 SYN_RCVD 并重传 SYN+ACK。客户端若发送数据，数据段带有 ACK 和正确确认号，服务器收到后直接进入 ESTABLISHED。若客户端不发数据且服务器重传耗尽，服务器删除半连接，之后客户端发数据会收到 RST。【→ 第 5 章，交互实验 1】

25. 第一次、第二次握手的报文丢了分别会怎样？

SYN 丢失：客户端在 SYN_SENT 指数退避重传（1、2、4… s，tcp_syn_retries=6，约 127 s 后 ETIMEDOUT）。SYN+ACK 丢失：客户端重传 SYN，服务器重传 SYN+ACK（tcp_synack_retries=5），任一成功即可。【→ 第 5 章】

26. connect 到一个没人监听的端口会怎样？

对端内核回 RST，connect 返回 ECONNREFUSED。Linux 立即失败；Windows 会重试 SYN，本书实测回环地址也要约 2 秒才失败。若是防火墙静默丢弃，则表现为 SYN 超时。【→ 第 5 章，d1 · E3 实测】

12.4 四次挥手（7 题）

27. ★ 描述四次挥手的过程和状态变化。

① 主动方发 FIN，→ FIN_WAIT_1；被动方收到 → CLOSE_WAIT。② 被动方内核回 ACK，主动方 → FIN_WAIT_2（半关闭，仍可接收）。③ 被动方应用 close，发 FIN，→ LAST_ACK；主动方收到 → TIME_WAIT。④ 主动方回 ACK，被动方 → CLOSED；主动方等 2MSL 后 CLOSED。【→ 第 6 章，d1 · E4 实测】

28. ★ 为什么挥手需要四次？什么时候是三次？

TCP 全双工，两个方向分别关闭；被动方收到 FIN 时可能还有数据要发，ACK（内核立即回）和 FIN（应用 close 时发）通常分开。被动方无数据可发且有延迟确认时，ACK 与 FIN 合并为三次。【→ 第 6 章】

29. ★ TIME_WAIT 为什么存在？为什么是 2MSL？

① 保证最后的 ACK 送达：若丢失，被动方重传 FIN，主动方还能重发 ACK（否则只能回 RST）；② 让旧连接的报文在网络中消亡，不污染相同四元组的新连接。2MSL 覆盖"ACK 最多走 1 MSL + 重传 FIN 最多走 1 MSL"。Linux 固定 60 秒。【→ 第 6 章】

30. ★ TIME_WAIT 过多有什么危害？怎么解决？

主动关闭方产生。客户端（或代理调用下游）会耗尽本地临时端口，connect 报 EADDRNOTAVAIL。解决：长连接 / 连接池（首选）、tcp_tw_reuse（客户端、需时间戳）、扩大端口范围、让客户端主动关闭；tcp_tw_recycle 在 NAT 下有问题且已在 Linux 4.12 删除；SO_LINGER 0 会丢数据，慎用。【→ 第 6 章】

31. 大量 CLOSE_WAIT 说明什么？

对端已关闭而本端应用没有调用 close，几乎都是代码 bug（读到 EOF 未关闭、异常分支漏关、连接池未回收）。用 ss -tanp state close-wait 定位进程和对端，再检查代码。CLOSE_WAIT 不会自动超时消失。【→ 第 6 章】

32. close 和 shutdown 的区别？SO_LINGER 有什么用？

close 减少 fd 引用计数，为 0 时关闭读写两个方向；shutdown 直接作用于连接，可只关写（发 FIN 但仍可读，半关闭）。SO_LINGER {1, 0} 让 close 直接发 RST，不进 TIME_WAIT，但会丢弃未发送数据，对端得到 ECONNRESET。【→ 第 6 章，d1 · E5 / E6 实测】

33. 对端机器突然断电，本端能发现吗？

不能立即发现，连接仍是 ESTABLISHED。本端发数据时会经历多次 RTO 重传（tcp_retries2，十几分钟）后报错；不发数据就只能靠 Keepalive（默认空闲 2 小时才探测）或应用层心跳。进程崩溃则不同，内核会正常发 FIN / RST。【→ 第 6 章】

12.5 可靠 UDP（5 题）

34. ★ 如何基于 UDP 实现可靠传输？

报文头加会话 ID、序号、累计确认 UNA、选择确认（位图或逐包 ACK）、时间戳、窗口；发送端缓存未确认包，按 RTO 超时重传、被跳过 N 次快速重传；接收端用环形缓冲乱序暂存、去重、按序交付，重复包也要回 ACK；滑动窗口做流量控制；拥塞控制或限速；大消息分片重组；连接管理（Cookie 握手、心跳、超时断线）；加密认证。可以按需对不同消息提供不同可靠级别。【→ 第 8 章】

35. ★ KCP 为什么比 TCP 快？代价是什么？

RTO ×1.5 而非 ×2，RTO 下限更低；选择性重传；快速重传阈值可配（跳过 2 次即重传）；不延迟 ACK；UNA + 逐包 ACK；可关闭拥塞控制。代价：多消耗 10%～20% 甚至更多带宽，无连接管理 / 加密 / 不可靠消息，需要自己补。不丢包时与 TCP 时延相当。【→ 第 9 章，d2 实测】

36. 停等、回退 N 步、选择重传的区别？

停等：窗口 1，利用率 ≈ T/(T+RTT)。GBN：发送窗口 N，接收方只收按序包，丢包后从丢失点重发整窗。SR：发送和接收窗口都为 N，接收方缓存乱序包，只重传丢失的包，序号空间需 ≥ 2N。本书仿真中 GBN 80% 的发送是重传。【→ 第 8 章】

37. ★ QUIC 相比 TCP 有哪些改进？

握手与 TLS 1.3 合并（1-RTT / 0-RTT）；多流无流间队头阻塞；连接 ID 支持连接迁移；包号永增与流偏移分离，消除重传歧义；ACK 帧多 Range + ACK Delay；用户态实现、拥塞控制可插拔；头部加密防僵化；抗放大与 Retry。代价是 CPU 高、UDP 可能被封。【→ 第 10 章】

38. 序号回绕怎么处理？

使用序列号算术：int32_t(a - b) > 0 表示 a 在 b 之后（16 位同理），前提是窗口远小于序号空间的一半。TCP 在高速网络下还要依靠时间戳选项的 PAWS 机制；QUIC 包号 62 位，实际上不会回绕。【→ 第 8 章】

12.6 场景设计（2 题）

39. ★ 如果让你设计一个 MOBA 游戏的网络同步方案，传输层怎么选？

先给数据分类：输入流（帧同步，可靠有序）、状态（只要最新）、事件（可靠）、非实时业务（登录、商城、结算）。战斗用 UDP：输入和帧包冗余发送最近若干帧，配合 ACK 位图停止冗余；缺帧通过 KCP 可靠通道补发；客户端帧缓冲吸收抖动；服务器按固定节奏推进不等慢玩家。非实时业务走 TCP/HTTPS。心跳秒级断线检测，UDP 不通时整体降级 TCP。全部加密防作弊。用弱网工具验证 P99 时延。【→ 第 11 章】

40. 视频会议为什么不用 TCP？它怎么应对丢包？

端到端时延预算只有 200～300 ms，TCP 的重传等待和队头阻塞会造成卡顿，迟到的帧没有意义。WebRTC 用 RTP over UDP：NACK 有条件重传（来得及才重传）、FEC 冗余恢复、抖动缓冲、丢帧与插值，以及基于时延的拥塞控制（GCC）动态调整码率。【→ 第 4、11 章】

A.3 三个口述模板（各约 1 分钟）

三次握手

"客户端发 SYN，带上随机的初始序号 x，进入 SYN_SENT；服务器收到后进入 SYN_RCVD，回复 SYN+ACK，带自己的序号 y 和确认号 x+1；客户端收到后进入 ESTABLISHED，再回 ACK，确认号 y+1，服务器收到后也进入 ESTABLISHED。三次是最少的次数：主要是为了防止历史连接——旧的 SYN 到达时，客户端能在第三步用 RST 拒绝；同时双方的初始序号都需要被确认；还能避免重复 SYN 建立无用连接。服务器的 ACK 和 SYN 合并了，所以不用四次。另外，内核里有半连接和全连接两个队列，SYN Flood 攻击的就是半连接队列，可以用 SYN Cookie 防御。"

四次挥手

"主动方发 FIN 进入 FIN_WAIT_1；被动方内核回 ACK，进入 CLOSE_WAIT，主动方收到后进入 FIN_WAIT_2，这时是半关闭，被动方还能继续发数据；被动方应用调用 close 后发 FIN，进入 LAST_ACK；主动方收到后回 ACK 进入 TIME_WAIT，等 2MSL 后关闭，被动方收到 ACK 就关闭。之所以四次，是因为 TCP 全双工，两个方向要分别关闭，被动方的 ACK 和 FIN 之间可能还有数据要发；如果没有数据并且有延迟确认，也可能合并成三次。"

TIME_WAIT

"TIME_WAIT 出现在主动关闭方，持续 2MSL，Linux 是固定的 60 秒。它有两个作用：一是保证最后一个 ACK 能到达，如果丢了，对方会重传 FIN，主动方还能重新回 ACK，否则只能回 RST；二是让这个连接在网络中残留的旧报文全部过期，避免被相同四元组的新连接误收。2MSL 就是一个来回的最长时间。TIME_WAIT 太多时，客户端会耗尽本地端口，最好的办法是用长连接或连接池，其次可以开 tcp_tw_reuse；tcp_tw_recycle 在 NAT 环境下有问题，已经从内核删除了。"

A.4 一句话串起全书

🧭 回到起点

IP 只尽力而为；UDP 把选择权留给应用；TCP 用序号、确认、重传、窗口、拥塞控制和连接管理把网络包装成可靠有序的字节流，并为此付出了握手延迟和队头阻塞的代价；三次握手同步序号、四次挥手分别关闭两个方向、TIME_WAIT 收尾；而 KCP、QUIC 和游戏引擎的网络层，则是在用户态把同一套机制按自己的需求重新组合——可靠性不是一个开关，而是一组可以挑选、可以调参的机制，每一个都有代价。
