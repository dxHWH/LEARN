CHAPTER 06

四次挥手：一条连接如何体面地结束

常被口误为"四次握手"。它之所以是四次，是因为 TCP 是全双工的：两个方向要各自说一次"我说完了"。

本章目标
  • 画出四次挥手的时序与双方状态，理解"半关闭"
  • 说清为什么是四次、什么时候会变成三次
  • 彻底讲透 TIME_WAIT：为什么存在、为什么是 2MSL、过多怎么办
  • 会排查 CLOSE_WAIT 堆积、FIN_WAIT_2 悬挂；理解 RST、close 与 shutdown、Keepalive 与心跳
  • 用实测输出佐证状态变化，用交互实验回放各种握手 / 挥手异常

6.1 逐步拆解

假设客户端先调用 close()（谁先关闭谁就是主动关闭方，服务器也可以是主动方）。客户端已发送的最后一个字节序号为 u−1，服务器为 v−1：

步骤方向报文发送后 / 收到后的状态含义
①C → SFIN, seq=uC：ESTABLISHED → FIN_WAIT_1
S：ESTABLISHED → CLOSE_WAIT（收到后）		"我没有数据要发了"
②S → CACK, ack=u+1C：FIN_WAIT_1 → FIN_WAIT_2（收到后）"知道了"——由内核自动回复，不需要应用参与
③S → CFIN, seq=wS：CLOSE_WAIT → LAST_ACK
C：FIN_WAIT_2 → TIME_WAIT（收到后）		服务器应用调用 close 后才发出："我也说完了"
④C → SACK, ack=w+1S：LAST_ACK → CLOSED（收到后）
C：TIME_WAIT 等待 2MSL → CLOSED		"知道了，再见"
🧪 实测证据（d1 · E4 / E5）：用系统连接表看四次挥手

程序在本机建立一条回环连接，在每一步之后调用 GetTcpTable（相当于 netstat -an）打印双方状态：

d1_tcp_udp_behaviors.exe · E4 / E5
== E4/E5 四次挥手的状态变化 + 半关闭 ==
  [① 三次握手完成，accept 返回后]
    服务端监听 127.0.0.1:40031 -> 127.0.0.1:0      LISTEN
    服务端  127.0.0.1:40031 -> 127.0.0.1:53735  ESTABLISHED
    客户端  127.0.0.1:53735 -> 127.0.0.1:40031  ESTABLISHED
  [② 客户端 shutdown(SD_SEND) 发出 FIN，服务端内核自动回 ACK 之后]
    服务端监听 127.0.0.1:40031 -> 127.0.0.1:0      LISTEN
    服务端  127.0.0.1:40031 -> 127.0.0.1:53735  CLOSE_WAIT
    客户端  127.0.0.1:53735 -> 127.0.0.1:40031  FIN_WAIT_2
  服务端 recv 返回 0（0 = 读到 FIN，对方不会再发数据了）
  客户端在 FIN_WAIT_2 中仍收到 21 字节: "server-still-can-send"  <- 这就是"半关闭"
  客户端 recv 返回 0（读到服务端 FIN）
  [③ 服务端 closesocket 发 FIN、客户端回最后一个 ACK 之后]
    服务端监听 127.0.0.1:40031 -> 127.0.0.1:0      LISTEN
    客户端  127.0.0.1:53735 -> 127.0.0.1:40031  TIME_WAIT

三个结论都被验证了：① 收到 FIN 的一方立刻进入 CLOSE_WAIT（内核自动回了 ACK，应用还什么都没做）；② 主动方在 FIN_WAIT_2 中仍然可以接收数据；③ 最后只有主动关闭方留下 TIME_WAIT，被动方的连接条目直接消失了。

6.2 为什么是四次？什么时候会是三次？

建立连接时，服务器的 SYN 和 ACK 可以合并，是因为服务器收到 SYN 时"没有什么需要等待的"，可以立刻发出自己的 SYN。关闭时则不同：收到对方 FIN 只说明对方不再发数据，自己可能还有数据没发完。所以 ACK（内核立即回）和 FIN（等应用处理完、调用 close 时才发）通常分两次发出，中间就是半关闭阶段。

🔬 抓包时常看到的"三次挥手"

如果被动方收到 FIN 时恰好没有待发数据，且应用很快就调用了 close（例如 HTTP 服务器读到 EOF 后立即关闭），由于延迟确认的存在，内核还没来得及发出单独的 ACK，FIN 就已经要发了，于是 ACK 和 FIN 合并成一个 FIN+ACK 报文，挥手就变成了 3 个报文。这完全合法，并不违反协议——"四次"是逻辑上的四个动作，不是必须的四个报文。

✅ 面试答法：为什么挥手要四次？

因为 TCP 是全双工的，两个方向需要分别关闭。主动方发 FIN 只表示它不再发送数据，但还能接收；被动方收到 FIN 后先由内核回 ACK，此时它可能还有数据要发，必须等应用发完并调用 close 才能发出自己的 FIN，所以 ACK 和 FIN 一般不能合并，总共四次。如果被动方此时没有数据要发，且启用了延迟确认，ACK 和 FIN 可以合并，就会变成三次。

6.3 TIME_WAIT：面试最爱问的状态

为什么需要 TIME_WAIT

为什么是 2MSL

MSL（Maximum Segment Lifetime）是报文在网络中的最大生存时间。等待 2MSL 可以覆盖最坏情况：最后的 ACK 在路上最多走 1 个 MSL 后丢失，对方超时重传的 FIN 最多再走 1 个 MSL 到达——一来一回。同时，2MSL 也足以让两个方向上旧连接的所有报文都在网络中消亡。

系统TIME_WAIT 时长说明
RFC 7932MSL = 4 分钟MSL 建议 2 分钟（工程上普遍认为过长）
Linux60 秒，写死在内核宏 TCP_TIMEWAIT_LEN不能通过 sysctl 修改；tcp_fin_timeout 控制的是 FIN_WAIT_2，不是 TIME_WAIT（常见误解）
Windows默认 120 秒左右（老版本 240 秒）注册表 TcpTimedWaitDelay 可调

TIME_WAIT 过多有什么危害

TIME_WAIT 在主动关闭方产生。每个 TIME_WAIT 只占很少的内存（Linux 有专门的轻量结构），真正的问题是它占用四元组：

  • 客户端（或作为客户端的代理 / 网关）：频繁对同一个 服务器IP:端口 发起短连接并主动关闭，本地临时端口（约 2.8 万个）会被 TIME_WAIT 占满，新的 connect 报错 EADDRNOTAVAIL（端口耗尽）。按 60 秒计，每秒超过约 470 个新连接就会耗尽。
  • 服务器：服务端作为主动关闭方（如 HTTP 短连接由服务器关闭）时也会积累大量 TIME_WAIT，但由于对端 IP 和端口各不相同，一般不会耗尽什么，主要是统计数字吓人；监控和表项数量（tcp_max_tw_buckets）需要关注。

怎么优化

方法原理注意事项
长连接 / 连接池（首选）HTTP Keep-Alive、数据库连接池，不再频繁建连关连从根源上消除问题
net.ipv4.tcp_tw_reuse = 1允许新发起的连接复用处于 TIME_WAIT 超过 1 秒的四元组，靠时间戳判断旧报文只对客户端（connect 方）有效；需开启 tcp_timestamps；较新内核默认值为 2（仅对回环地址生效）
tcp_tw_recycle快速回收 TIME_WAIT在 NAT 后的多个客户端时间戳不一致时会导致连接失败，Linux 4.12 已删除，面试时要指出它的坑

⚠️ 易错点：SO_REUSEADDR 和 TIME_WAIT 是什么关系？

服务器进程重启时 bind(:8080) 报 "Address already in use"，往往是因为旧进程的连接还有 TIME_WAIT 占着 8080。设置 SO_REUSEADDR 后，即使有 TIME_WAIT 连接，也允许监听 socket 绑定该端口（Linux 语义）。所以服务器的监听 socket 几乎都应该设置 SO_REUSEADDR。它解决的是"重启 bind 失败"，和"客户端端口耗尽"是两个不同的问题。另外注意 Windows 上 SO_REUSEADDR 的语义不同（允许抢占端口），应使用 SO_EXCLUSIVEADDRUSE 保护服务端口。

6.4 CLOSE_WAIT 与 FIN_WAIT_2：两种"卡住"

大量 CLOSE_WAIT：几乎一定是你的 bug

CLOSE_WAIT 表示"对方已经关了，我的应用还没 close"。内核不会替应用关闭，所以如果代码在读到 EOF（recv 返回 0）后忘了 close，或者异常分支漏掉了 close，或者连接池没有检测并回收被对端关闭的连接，CLOSE_WAIT 就会一直堆积，直到耗尽文件描述符。
排查：ss -tanp state close-wait 找到进程和对端，再检查对应代码路径。

FIN_WAIT_2 悬挂：等对方的 FIN

主动方发完 FIN 收到 ACK 后，要等对方发 FIN。如果对方迟迟不关（正好处于 CLOSE_WAIT 的 bug 状态），主动方就挂在 FIN_WAIT_2。
如果主动方是用 close() 关闭的（连接已成为孤儿），Linux 最多等 tcp_fin_timeout（默认 60 秒）后直接回收；如果是用 shutdown(SHUT_WR) 关闭的，应用还能读，内核会一直等。

6.5 挥手过程中的异常

异常谁会察觉处理
① FIN 丢失主动方收不到 ACK主动方在 FIN_WAIT_1 超时重传 FIN；孤儿连接的重传次数由 tcp_orphan_retries 控制，耗尽后直接关闭
② ACK 丢失主动方收不到 ACK主动方重传 FIN，被动方（已在 CLOSE_WAIT）再次回 ACK；若被动方的 FIN 先到，主动方从 FIN_WAIT_1 收到 FIN+ACK 也能直接进入 TIME_WAIT
③ 被动方的 FIN 丢失被动方收不到 ACK被动方在 LAST_ACK 重传 FIN；主动方仍在 FIN_WAIT_2 等待（孤儿连接最多等 tcp_fin_timeout）
④ 最后的 ACK 丢失被动方收不到 ACK被动方重传 FIN；主动方在 TIME_WAIT 中重发 ACK 并重置 2MSL 计时器（图 6-2 左）
同时关闭双方同时发 FIN双方：FIN_WAIT_1 → 收到对方 FIN → CLOSING → 收到 ACK → TIME_WAIT。双方都会有 TIME_WAIT
进程崩溃 / 被 kill—进程退出时内核会关闭它所有的 fd，照常发送 FIN，对端看到的是正常关闭（若接收缓冲区有未读数据则发 RST）
主机断电 / 网线被拔对端完全不知道没有任何报文发出，对端连接会一直保持 ESTABLISHED（"半打开"连接），直到它发送数据超时，或者 Keepalive / 应用心跳探测失败
close 时接收缓冲区还有未读数据对端收到 RSTLinux 会直接发 RST 而不是 FIN（RFC 2525 建议的行为），提示对方"你发的数据我没读到"

6.6 RST：不体面但有时必要的结束方式

RST（Reset）表示"立即终止连接，不用再回复"。它不需要确认，收到 RST 的一方立即释放连接，并把未发送的数据全部丢弃，应用的下一次读写会得到 ECONNRESET（"Connection reset by peer"）；发 RST 的一方也不会进入 TIME_WAIT。常见触发场景：

  • SYN 发往无人监听的端口（第 5 章 E3 实测）；
  • 收到不属于任何连接的报文（例如服务器重启后，客户端仍用旧连接发数据）；
  • 设置了 SO_LINGER {1, 0} 后调用 close（下方实测）；
  • close 时接收缓冲区有未读数据；
  • 防火墙、负载均衡主动掐断连接（"连接被重置"在跨境网络中很常见）。
🧪 实测证据（d1 · E6）：SO_LINGER{1,0} 直接发 RST
d1_tcp_udp_behaviors.exe · E6
== E6 SO_LINGER{1,0}：用 RST 代替四次挥手 ==
  服务端 recv 返回 -1，WSAGetLastError=10054（10054=WSAECONNRESET）
  [RST 之后（注意：客户端没有 TIME_WAIT）]

对比 E4 的结果：正常挥手后主动方留下了 TIME_WAIT；用 RST 关闭后双方的连接条目都立即消失，但对端得到的是"连接被重置"的错误，而不是表示正常结束的 recv 返回 0。

close() 与 shutdown() 的区别

close(fd)shutdown(fd, SHUT_WR)
作用对象文件描述符：引用计数减 1，减到 0 才真正关闭连接（fork 后父子进程共享 socket 时要注意）直接作用于连接，不管有多少个 fd 引用
方向同时关闭读和写可以只关写（发 FIN）、只关读、或都关
之后还能读吗不能（连接成为孤儿）SHUT_WR 后仍然可以读，用于"半关闭"
典型用途普通关闭"我发完了，但还要等你的回复"：例如客户端上传完文件后 shutdown 写端，再读取服务器的结果

6.7 保活：Keepalive 与应用层心跳

"主机断电"那一行说明：TCP 本身无法及时发现对端消失。TCP 提供了 Keepalive 机制，但默认参数非常保守：

参数（Linux）默认值含义
tcp_keepalive_time7200 秒连接空闲 2 小时后才开始探测
tcp_keepalive_intvl75 秒探测间隔
tcp_keepalive_probes9 次连续失败多少次判定断开

默认要 2 小时 11 分钟才能发现死连接，且 Keepalive 需要每个 socket 用 SO_KEEPALIVE 显式开启（可以用 TCP_KEEPIDLE 等选项为单个连接缩短时间）。更重要的是，Keepalive 只能证明对端内核还活着，证明不了对端应用没有卡死。

🎮 游戏开发视角：为什么游戏都用应用层心跳

游戏需要在几秒内发现玩家掉线（以便托管 AI 接管、通知队友、判定逃跑），而且要知道的是"客户端逻辑是否还在运行"。所以几乎所有游戏都在应用层每隔 1～5 秒发一个心跳包，服务器若连续 N 个周期没有收到任何包就判定断线。心跳还能顺便测量 RTT、给 NAT 映射保活（UDP 尤其需要）。对于基于 UDP 的可靠协议，这就是它的"连接管理"的一部分（第 8 章）。

本章小结
  • 四次挥手：FIN → ACK →（半关闭，可继续发数据）→ FIN → ACK；主动方 FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED，被动方 CLOSE_WAIT → LAST_ACK → CLOSED（已实测）。

  • RST 立即终止、丢弃数据、不进 TIME_WAIT；close 按引用计数关闭两个方向，shutdown 可单向半关闭。

思考题 1：服务器上用 netstat 看到大量 TIME_WAIT，说明了什么？要不要处理？

说明这台服务器是大量连接的主动关闭方，常见于 HTTP 短连接（服务器响应完主动关闭）或服务器作为客户端去调用下游（数据库、其他服务）且使用短连接。如果是前者，TIME_WAIT 只占少量内存，四元组也不冲突，一般不影响服务，可以通过开启 Keep-Alive 减少；如果是后者，要警惕本地端口耗尽，应改用连接池，或开启 tcp_tw_reuse。不建议用 SO_LINGER 0 粗暴消灭 TIME_WAIT。

思考题 2：线上服务出现几千个 CLOSE_WAIT，并且还在增长，你怎么排查？

CLOSE_WAIT 表示对端已关闭而本端应用没有调用 close。① 用 ss -tanp state close-wait 找到所属进程和对端地址，确认是和哪个下游 / 客户端的连接；② 检查对应代码：读到 EOF（返回 0）后是否 close，异常、超时分支是否 close，连接池是否在借出前检测连接可用、归还时是否处理已关闭的连接；③ 检查是否有线程阻塞导致处理不过来（例如 accept 后一直没处理）；④ 修复前可以临时重启进程释放 fd。CLOSE_WAIT 不会因为内核超时自动消失。

思考题 3：为什么 TIME_WAIT 放在主动关闭方，而不是被动关闭方？

因为发出"最后一个 ACK"的是主动关闭方：只有它需要确保这个 ACK 送达（对方没收到会重传 FIN，自己要能再回 ACK），也只有它在发出最后一个报文后需要等旧报文消亡。被动方在收到最后的 ACK 时就已确认双方都关闭完毕，没有不确定性，可以直接进入 CLOSED。

思考题 4：客户端进程被 kill -9 和客户端机器断电，服务器看到的现象有什么不同？

kill -9 时进程虽然没有机会执行清理代码，但内核会关闭它的所有 socket，正常发送 FIN（若有未读数据则发 RST），服务器很快就会读到 EOF 或 ECONNRESET。机器断电时没有任何报文发出，服务器上的连接仍然是 ESTABLISHED：如果服务器不发数据，它永远不会知道；如果发数据，会经历一段 RTO 重传（Linux 默认 tcp_retries2=15，约十几分钟）后才报错。所以需要 Keepalive 或应用层心跳。
