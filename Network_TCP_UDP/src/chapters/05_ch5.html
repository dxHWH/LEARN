PART THREE

第三部分　连接管理：握手与挥手

面试出现频率最高的两道题。不仅要背出流程，更要讲清每一步"为什么"，以及每一步出了问题会怎样。

CHAPTER 05

三次握手：建立一条连接需要什么

握手的本质不是"打招呼"，而是让双方就各自的初始序号达成一致，并确认双向通路都是通的。

本章目标
  • 画出三次握手的完整时序：每一步的标志位、seq、ack 以及双方状态变化
  • 说清 ISN 为什么要随机，以及"为什么是三次而不是两次或四次"的三个理由
  • 理解内核中的半连接队列与全连接队列，以及它们满了之后的行为
  • 讲清 SYN Flood 攻击原理和 SYN Cookie 等防御手段
  • 逐一分析握手中每个报文丢失、端口未监听、队列溢出等异常

5.1 握手要完成的四件事

  1. 确认双方的收发能力：客户端能发、服务器能收；服务器能发、客户端能收。
  2. 同步双方的初始序号（ISN）：TCP 是全双工的，两个方向各有一套序号，双方都要把自己的 ISN 告诉对方，并得到对方的确认。这是最核心的一件事，SYN 就是 Synchronize Sequence Numbers 的缩写。
  3. 协商连接参数：MSS、窗口扩大因子、是否支持 SACK 和时间戳。这些选项只能出现在 SYN 报文中。
  4. 分配连接资源：双方各自建立 TCB（传输控制块）、收发缓冲区。

5.2 逐步拆解

步骤方向标志位seq / ack状态变化这一步证明了什么
①C → SSYNseq = xC：CLOSED → SYN_SENT
S（收到后）：LISTEN → SYN_RCVD		服务器知道：客户端能发、自己能收
②S → CSYN + ACKseq = y，ack = x+1C（收到后）：SYN_SENT → ESTABLISHED客户端知道：双方都能收发；自己的 ISN 已被确认
③C → SACKseq = x+1，ack = y+1S（收到后）：SYN_RCVD → ESTABLISHED服务器知道：客户端能收；自己的 ISN 已被确认
tcpdump 中的一次握手（典型输出，地址与序号为示例）
10:00:00.000 IP 10.0.0.1.52344 > 10.0.0.2.443: Flags [S],  seq 1705322911, win 64240, options [mss 1460,sackOK,TS val 1 ecr 0,nop,wscale 7], length 0
10:00:00.030 IP 10.0.0.2.443 > 10.0.0.1.52344: Flags [S.], seq 3891201650, ack 1705322912, win 65160, options [mss 1460,sackOK,TS val 9 ecr 1,nop,wscale 7], length 0
10:00:00.060 IP 10.0.0.1.52344 > 10.0.0.2.443: Flags [.],  ack 3891201651, win 502, length 0

tcpdump 中 S 表示 SYN，. 表示 ACK，S. 即 SYN+ACK；第三行的 ack 默认显示为相对值时会是 1。win 502 是窗口扩大前的原始值，实际窗口 = 502 × 2⁷ = 64256 字节。

⚠️ 易错点

① ack 不是"收到的序号"，而是"期望的下一个序号"，所以是 x+1 而不是 x。
② SYN 不携带数据，却消耗一个序号（FIN 也一样）；纯 ACK 不消耗序号，所以第三次握手后客户端发的第一个数据段 seq 仍是 x+1。
③ 服务端的 accept() 并不参与握手：握手完全由内核完成，accept 只是从全连接队列里取出一个已完成握手的连接。即使应用从不调用 accept，客户端的 connect 也能成功返回。
④ "SYN_RCVD"在一些资料里写作 "SYN_RECV"（Linux ss 的显示），两者是同一个状态。

5.3 ISN 为什么要随机

如果每条连接的 ISN 都从 0 开始，会有两个问题：

  • 与旧连接的报文混淆：同一个四元组的连接关闭后又马上重建，旧连接在网络中滞留的报文可能恰好落在新连接的序号窗口里，被当成新数据接收。
  • 序号预测攻击：攻击者如果能猜到 ISN，就能伪造源地址完成握手、向连接中注入数据（1994 年著名的 Mitnick 攻击就是利用了当时可预测的 ISN）。

RFC 6528 推荐的生成方式是 ISN = M + F(本地IP, 本地端口, 远端IP, 远端端口, 密钥)：M 是一个大约每 4 微秒加 1 的计时器（32 位约 4.55 小时回绕一次），F 是带密钥的哈希函数。这样同一四元组的 ISN 随时间单调递增（避免和旧连接重叠），而外人无法预测（因为有密钥）。Linux 的 secure_tcp_seq() 就是按这个思路实现的。

5.4 为什么是三次，而不是两次或四次

📞 先看类比：打电话

A："喂，听得到吗？"（A 确认自己能说）
B："听得到，你听得到我吗？"（B 确认自己能听、也能说）
A："听得到。"（B 这才确认 A 能听）
少了第三句，B 无法知道自己的声音 A 是否听见了。但类比只能解释"双向确认"，面试真正要的是下面三条技术理由。

理由一（RFC 793 给出的首要原因）：阻止历史连接

网络可能把一个很久以前发出的 SYN 延迟送达。例如客户端先发了 SYN(seq=90)，迟迟没回应就放弃了（或者客户端重启了），接着又发了新的 SYN(seq=100)。如果旧 SYN 先到：

关键在于：只有发起方（客户端）才知道哪个 SYN 是"当前有效"的。三次握手把"最终拍板"的权力留给了客户端：服务器回 SYN+ACK 之后先不建立连接，由客户端根据确认号判断，是当前连接就回 ACK，是历史连接就回 RST。

理由二：可靠地同步双方的初始序号

双方都有自己的 ISN，每个 ISN 都需要"告知 + 确认"一来一回，理论上需要 4 个报文：C 发 SYN(x)、S 确认 x、S 发 SYN(y)、C 确认 y。中间两个都是服务器发给客户端的，可以合并成一个 SYN+ACK，所以是 3 个。两次握手只能保证客户端的 ISN 被确认，服务器的 ISN 发出去后不知道对方有没有收到。

理由三：避免重复连接浪费资源

如果只有两次握手，客户端因为超时重传了多个 SYN，服务器每收到一个 SYN 就建立一条连接、分配一次资源，而客户端只会使用其中一条，其余全部成为空占资源的"僵尸连接"。

为什么不是四次？

四次也能工作（同时打开时其实就是四个报文），只是没必要：服务器的"确认"和"自己的 SYN"可以放在同一个报文里发出，合并后三次已经足以完成全部目标。三次是满足可靠同步的最少次数。

✅ 面试答法：为什么是三次握手？

三次握手的目的是同步双方的初始序号并确认双向通路。三次是最少次数：① 主要原因是防止历史连接，旧的 SYN 到达服务器后，客户端可以在第三步通过 RST 否决，两次握手做不到；② 双方的 ISN 都需要被对方确认，两次只能确认客户端的；③ 两次握手下，重传的重复 SYN 会让服务器建立多条无用连接。不需要四次，因为服务器的 ACK 和 SYN 可以合并在一个报文里。

5.5 内核视角：半连接队列与全连接队列

队列满了Linux 的行为如何观察 / 调整
半连接队列满默认开启 SYN Cookie（tcp_syncookies=1）时改用 Cookie 继续服务；否则丢弃新的 SYNnetstat -s | grep "SYNs to LISTEN"；调大 tcp_max_syn_backlog
全连接队列满tcp_abort_on_overflow=0（默认）：丢弃第三次握手的 ACK，服务器停留在 SYN_RCVD 并重传 SYN+ACK，期望应用稍后腾出空间；=1：直接回 RSTss -lnt 中监听 socket 的 Recv-Q（当前积压）/ Send-Q（队列上限）；netstat -s | grep overflowed；调大 listen 的 backlog 和 net.core.somaxconn（Linux 5.4 起默认 4096，之前为 128）
⚠️ 易错点：客户端 connect 成功了，服务端却"没有这条连接"

全连接队列满且 tcp_abort_on_overflow=0 时，客户端收到 SYN+ACK 就进入了 ESTABLISHED，connect 返回成功，开始发送请求；而服务端把第三次握手的 ACK 丢了，连接还在半连接队列里。客户端的请求数据会被服务端丢弃或者等待，表现为"连接成功但请求超时"。线上排查"偶发连接超时"时，监听 socket 的 Recv-Q 是第一个要看的指标。

5.6 SYN Flood 攻击与防御

原理

攻击者伪造大量不存在的源 IP 发送 SYN。服务器为每个 SYN 在半连接队列中分配一个条目并回复 SYN+ACK，但这些 SYN+ACK 发往不存在的地址，永远收不到第三次握手的 ACK。每个半连接要等 SYN+ACK 重传若干次（Linux 默认 tcp_synack_retries=5，总计约 63 秒）才会被清理。只要攻击者发送 SYN 的速度超过清理速度，半连接队列很快就会被占满，正常用户的 SYN 被丢弃，服务不可用。它的厉害之处在于：攻击者几乎没有成本（不需要维持任何状态），却能耗尽服务器的资源——这是"状态不对称"导致的。

防御手段

手段做法作用
SYN Cookienet.ipv4.tcp_syncookies = 1（Linux 默认）根治"半连接队列被打满"，代价见上图

🎮 延伸：这件事对可靠 UDP 有什么启示

UDP 服务器没有半连接队列，看上去不怕 SYN Flood，但自己实现的"连接握手"如果在收到第一个包时就分配会话资源，就会重蹈覆辙；如果对一个很小的请求回复很大的应答，还会被利用来做反射放大攻击。QUIC 的应对方式值得借鉴：服务器在验证客户端地址之前，发送的数据量不得超过收到的 3 倍，并且可以发送 Retry 令牌（本质就是 SYN Cookie 的思想）要求客户端证明自己真的拥有这个地址（第 10 章）。

5.8 握手优化：TCP Fast Open

普通握手中，客户端最早要在第三步才能发送数据，HTTP 请求至少要等 1 个 RTT。TCP Fast Open（TFO，RFC 7413）允许在 SYN 里就携带数据：

TFO 的局限：① SYN 中的数据可能被重放（攻击者截获后重发），所以只适合幂等请求；② 不少中间设备会丢弃带数据的 SYN 或去掉未知选项；③ 需要客户端和服务器双方都支持（Linux 用 net.ipv4.tcp_fastopen 开启）。实际部署并不广泛，"省握手 RTT"这个目标后来主要由 TLS 1.3 的 0-RTT 和 QUIC 实现。

本章小结
  • 三次握手：SYN(seq=x) → SYN+ACK(seq=y, ack=x+1) → ACK(ack=y+1)；状态 C：SYN_SENT → ESTABLISHED，S：LISTEN → SYN_RCVD → ESTABLISHED。
  • SYN 不带数据但占 1 个序号；第三次握手可以携带数据；accept 不参与握手。
  • ISN 随机且随时间递增：防止与旧连接混淆、防止序号预测攻击（RFC 6528）。
  • 为什么三次：防历史连接（首要）、同步双方 ISN、避免重复连接；ACK 与 SYN 合并所以不需要四次。
  • 半连接队列（tcp_max_syn_backlog）/ 全连接队列（min(backlog, somaxconn)）；全连接队列满默认丢第三次 ACK。
  • SYN Flood 利用状态不对称耗尽半连接队列；SYN Cookie 把状态编码进 ISN；另有调参、SYN Proxy、清洗。
  • 异常：SYN 丢 → 客户端退避重传；SYN+ACK 丢 → 双方都重传；ACK 丢 → 服务端重传，客户端的数据段可代替 ACK。
思考题 1：第三次握手的 ACK 丢了，客户端紧接着发送了数据，会发生什么？

客户端发送的数据段同样带 ACK 标志、ack = y+1。服务器在 SYN_RCVD 状态收到它，确认号正确，于是直接进入 ESTABLISHED 并接收数据（相当于第三次握手的 ACK "搭了数据的便车"）。所以第三次 ACK 丢失通常不会造成影响。只有在客户端一直不发数据、而服务器的 SYN+ACK 重传全部失败时，服务器才会删除这个半连接，客户端之后再发数据会收到 RST。

思考题 2：服务器 listen(fd, 1024)，但 net.core.somaxconn = 128，全连接队列多大？大量短连接突发时会怎样？

全连接队列上限取两者较小值 128。突发时如果应用 accept 不够快，队列溢出，默认会丢弃第三次握手的 ACK，表现为客户端连接成功但请求超时、服务器重传 SYN+ACK、客户端出现 1 秒以上的延迟。排查：ss -lnt 看 Recv-Q 是否接近 Send-Q，netstat -s | grep overflowed 看溢出计数。解决：调大 somaxconn 和 backlog，提高 accept 效率（多线程 / SO_REUSEPORT 多个监听 socket）。

思考题 3：为什么 SYN Cookie 默认只在半连接队列满时才启用，而不是一直开着？

因为 SYN Cookie 有代价：服务器不保存状态，就不能重传丢失的 SYN+ACK；MSS 只能取少数几个预设值之一；窗口扩大、SACK 等选项只有在开启时间戳时才能部分编码保存，否则会丢失，影响高带宽链路的性能。正常情况下用完整的半连接队列能获得最好的连接质量，只有在被攻击（队列溢出）时才退而求其次。

思考题 4：客户端 connect 一个公网服务器，30 秒都没有返回，可能是什么原因？

说明客户端一直处于 SYN_SENT，在指数退避重传 SYN，从未收到任何回应（收到 RST 会立即失败）。可能原因：① 服务器或中间防火墙静默丢弃了 SYN（安全组未放行端口最常见）；② 路由不可达但 ICMP 被过滤；③ 服务器半连接队列满且没开 SYN Cookie；④ 服务器的 SYN+ACK 在回程被丢弃（例如非对称路由被防火墙拦截）。排查可在两端抓包对照，或用 tcptraceroute 看 SYN 走到了哪一跳。
