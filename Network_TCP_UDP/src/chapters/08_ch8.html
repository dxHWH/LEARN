8.1 报文设计

先设计一个教学用的报文头。它和 KCP 的头部（第 9 章）非常接近，只多了一个"通道"字段和一个 ACK 位图：

字段对应 TCP 的为什么这样设计
conv四元组移动网络下 NAT 可能更换客户端的公网端口（NAT 重绑定），用会话 ID 识别连接就不会因此断线；还可以在一个 UDP 端口上复用很多会话
snseq按包编号而不是按字节编号：UDP 本身就保留消息边界，按包编号更简单，确认与重传也以包为单位
unaack累计确认，语义和 TCP 的 ack 一样："下一个期望的包"
ack_bitsSACK 选项定长 32 位，比 TCP 的 SACK 块更紧凑，每个包都能带
ts时间戳选项接收方在 ACK 里回显发送时间，发送方 now − ts 就是 RTT，重传的包也能正确采样（解决 Karn 问题）
wnd窗口流量控制
chan（无）不同通道有独立的序号空间和可靠级别，互不阻塞
frg（无，TCP 是字节流）大消息分片：还剩几片，为 0 表示最后一片

8.2 序列号：回绕与比较

序号字段总有上限：32 位约 43 亿，16 位只有 65536。游戏每秒 60 个包，16 位序号 18 分钟就会回绕。回绕后 5 < 65530 这样的直接比较就错了。正确做法是序列号算术（RFC 1982）：把差值解释成有符号数。

// a 是否"在 b 之后"：差值按有符号数解释，只要两者相距不超过序号空间的一半就是对的 inline bool SeqAfter(uint32_t a, uint32_t b) { return int32_t(a - b) > 0; } inline bool SeqBefore(uint32_t a, uint32_t b) { return int32_t(a - b) < 0; } inline int32_t SeqDiff(uint32_t a, uint32_t b) { return int32_t(a - b); } // 16 位序号同理（Glenn Fiedler 的游戏网络协议就用 16 位以节省包头） inline bool Seq16After(uint16_t a, uint16_t b) { return int16_t(uint16_t(a - b)) > 0; } // 例：Seq16After(5, 65530) == true，因为 (uint16_t)(5 - 65530) = 11 > 0
⚠️ 易错点：窗口必须小于序号空间的一半

如果在途的包跨度超过序号空间的一半，SeqAfter 就无法分辨"新包"和"很旧的包"。所以发送窗口必须远小于 231（32 位）或 215（16 位）。TCP 在高速网络中序号回绕更快（10 Gbps 下 32 位字节序号只要 3.4 秒），所以要靠时间戳选项做 PAWS 保护。

8.3 确认：三种方式及其组合

方式做法优点缺点代表
逐包 ACK每收到一个包，回一条 ACK(sn, ts)，可以把多条合并进一个包信息最精确，每条都能测 RTTACK 本身丢了就丢了这条信息；ACK 量大KCP 的 ACK 列表
累计确认 UNA只告诉对方"una 之前的全收到了"一个数字就能确认很多包，对 ACK 丢失不敏感（下一个 ACK 包含了上一个的信息）无法表达"una 之后收到了哪些"，会导致不必要的重传TCP 的 ack、KCP 的 una
ACK 位图una（或最新收到的 sn）+ 后续 32 个包的接收位图高度冗余：同一个包的确认信息会在连续 32 个 ACK 里重复出现，ACK 丢几个也无所谓只能覆盖 32（或 64）个包的范围Glenn Fiedler《Reliability over UDP》、很多游戏引擎
🎮 游戏开发视角：ACK 捎带与"ACK 也会丢"

游戏双向都在持续发包（客户端发输入，服务器发状态），所以确认信息捎带在每个数据包的头部里，几乎没有单独的 ACK 包。由于每个包都带"最近 32 个包的接收情况"，即使一半的包都丢了，发送方仍然能收到足够的确认信息。这比 TCP 的"一个 ACK 丢了就只能等下一个"要健壮得多。

8.4 超时重传：RTT、RTO 与退避

测量 RTT

发送时在包头写入当前时间 ts，接收方在确认中原样回显，发送方收到后 rtt = now − ts。因为回显的是那一次发送的时间戳，重传的包也能被正确采样，不存在重传歧义。计算 RTO 时直接套用 RFC 6298 的公式（第 3 章），差别在于各个参数可以自由调整：

参数TCP（Linux）可靠 UDP 常见取值考虑
RTO 下限200 ms30～100 ms（KCP 极速模式 30 ms）越小重传越快，但 RTT 抖动大时会产生伪重传
超时后退避× 2（指数）× 1.5（KCP）、固定不退避、或设上限（如不超过 4×SRTT）退避是为了在严重拥塞时让网络喘口气；实时应用更怕等
定时器粒度每连接一个重传定时器每个包各自记录 resend_at，由一个固定周期的 update 统一检查按包定时更灵活；update 周期（KCP 的 interval，常设 10 ms）决定了时延精度
快速重传阈值3 个重复 ACK被后续包"跳过" 2 次（KCP resend=2）越小越快，但对乱序越敏感

快速重传：用"跳过次数"代替"重复 ACK"

有了逐包确认或 ACK 位图，就不需要靠重复 ACK 去猜了：每当发送方得知某个比 X 更大的包已被收到，就给 X 的 fastack 计数加一；计数达到阈值就立即重传 X。图 8-2 中的 101 已经被 102、103、105、108 跳过了 4 次。

🔬 实现细节：别对刚重传的包重复计数

如果 X 刚被重传过，那些在重传之前就已经发出的更大的包，它们的确认会继续"跳过" X，导致 X 被反复快速重传。严谨的做法是：只有发送时间晚于 X 最近一次发送的包被确认，才算一次有效跳过（这就是 Linux RACK 算法的思想）。KCP 选择了更简单的做法：照常计数，但用 fastlimit（默认 5）限制一个包最多被快速重传几次——宁可多发一点，也不要等。本书的仿真程序两种都实现了。

8.5 三种 ARQ 策略

ARQ（Automatic Repeat reQuest，自动重传请求）是"确认 + 超时重传"这一类机制的统称。按照一次允许多少个未确认的包和出错时重传哪些包，分为三种：

信道利用率

设发送一个包需要 T（发送时延 = 包长 / 带宽），往返时延 RTT，窗口 W 个包，无丢包时的利用率：

U = min(1, W × T / (T + RTT)) 停等（W=1）：T = 1 ms（1200 字节 @ ~10 Mbps），RTT = 60 ms → U = 1 / 61 ≈ 1.6% 滑动窗口 W=64： → U = min(1, 64 / 61) = 100% 跑满带宽所需的最小窗口 W ≥ (T + RTT) / T ≈ RTT / T = 带宽时延积（以包为单位）

这就是为什么第 3 章说"窗口要至少等于 BDP"。三种 ARQ 的完整对比：

停等回退 N 步（GBN）选择重传（SR）
发送窗口1NN
接收窗口11（只收按序包）N（缓存乱序包）
确认方式逐包累计确认逐包 / 选择确认（+ 累计）
出错时重传当前包从丢失包开始的整个窗口只重传丢失的包
序号空间要求≥ 2≥ N + 1≥ 2N（否则新旧包混淆）
适用低速 / 简单链路低误码率链路高时延、有丢包的链路（TCP+SACK、KCP、QUIC 都属于此类）

8.6 滑动窗口与流量控制

发送端维护三个窗口取最小值：可发送数 = min(本地发送窗口, 对端通告的接收窗口 wnd, 拥塞窗口 cwnd) − 在途包数。接收端在每个包头里填写 wnd = 接收缓冲区剩余槽位。

  • 窗口为 0 时：和 TCP 一样会有"窗口更新包丢了导致双方死等"的风险。KCP 的做法是发送方定时发送 WASK（询问窗口）命令，接收方回 WINS（告知窗口）——相当于 TCP 的零窗口探测。
  • 接收窗口要比发送窗口大：KCP 默认发送窗口 32、接收窗口 128。因为接收方还要容纳乱序到达的包，接收窗口太小时，乱序包会因为"超出窗口"被丢弃，然后被重传。

8.7 乱序处理与去重：接收端环形缓冲

struct Receiver { static constexpr uint32_t kWnd = 128; uint32_t rcvNxt = 0; // 下一个期望交付的 sn std::array, kWnd> slots; // 环形缓冲，下标 sn % kWnd std::vector ackList; // 待回复的确认 void OnData(uint32_t sn, std::string payload, auto&& deliver) { ackList.push_back(sn); // ① 不管新旧，先记下要确认（重复包也要确认） if (SeqBefore(sn, rcvNxt)) return; // ② 已经交付过的旧包：去重 if (SeqDiff(sn, rcvNxt) >= int32_t(kWnd)) return; // ③ 超出接收窗口：丢弃，等对方重传 auto& slot = slots[sn % kWnd]; if (slot) return; // ④ 窗口内的重复包：去重 slot = std::move(payload); // ⑤ 乱序暂存 while (slots[rcvNxt % kWnd]) { // ⑥ 从 rcvNxt 起把连续的包按序交付 deliver(std::move(*slots[rcvNxt % kWnd])); slots[rcvNxt % kWnd].reset(); ++rcvNxt; } } uint16_t Wnd() const { /* 剩余空槽数，填进包头的 wnd */ return uint16_t(kWnd - CountUsed()); } uint32_t Una() const { return rcvNxt; } uint32_t AckBits() const { // una+1 .. una+32 的接收位图 uint32_t bits = 0; for (uint32_t i = 1; i <= 32 && i < kWnd; ++i) if (slots[(rcvNxt + i) % kWnd]) bits |= 1u << (i - 1); return bits; } uint32_t CountUsed() const { uint32_t n = 0; for (auto& s : slots) n += s.has_value(); return n; } };

8.8 发送端：定时驱动的主循环

可靠 UDP 通常由一个固定周期（例如每 10 ms）调用的 Update(now) 驱动：检查超时、处理快速重传、在窗口允许时发送新数据、把 ACK 和数据合并成包发出去。

struct Segment { uint32_t sn; uint32_t ts; uint32_t resendAt; uint32_t rto; int xmit = 0; int fastack = 0; std::string data; }; struct Sender { std::deque sendQueue; // 应用提交、尚未进入窗口的消息 std::map sendBuf; // 已发送未确认（按 sn 有序） uint32_t sndNxt = 0, sndUna = 0, rmtWnd = 128, sndWnd = 64; RttEstimator rtt; // SRTT / RTTVAR / RTO（RFC 6298） int fastResend = 2; double backoff = 1.5; // KCP 极速模式的取值 void OnAck(uint32_t una, uint32_t ackBits, uint32_t echoTs, uint32_t now) { rtt.Sample(now - echoTs); // 时间戳回显：重传包也能采样 for (auto it = sendBuf.begin(); it != sendBuf.end() && SeqBefore(it->first, una);) it = sendBuf.erase(it); uint32_t maxAcked = una - 1; for (int i = 0; i < 32; ++i) if (ackBits >> i & 1) { sendBuf.erase(una + 1 + i); maxAcked = una + 1 + i; } for (auto& [sn, seg] : sendBuf) if (SeqBefore(sn, maxAcked)) seg.fastack++; // 被更大的包"跳过" sndUna = sendBuf.empty() ? sndNxt : sendBuf.begin()->first; } void Update(uint32_t now, auto&& output) { for (auto& [sn, seg] : sendBuf) { bool timeout = int32_t(now - seg.resendAt) >= 0; bool fast = fastResend > 0 && seg.fastack >= fastResend; if (!timeout && !fast) continue; if (timeout) seg.rto = std::min(uint32_t(seg.rto * backoff), 10000); // 温和退避 seg.xmit++; seg.fastack = 0; seg.ts = now; seg.resendAt = now + seg.rto; output(seg); // 只重传这一个 } uint32_t cwnd = std::min(sndWnd, rmtWnd); // (+ 拥塞窗口) while (!sendQueue.empty() && SeqDiff(sndNxt, sndUna) < int32_t(cwnd)) { Segment seg{sndNxt++, now, now + rtt.Rto(), rtt.Rto(), 1, 0, std::move(sendQueue.front())}; sendQueue.pop_front(); output(seg); sendBuf.emplace(seg.sn, std::move(seg)); } } };

8.9 拥塞避免：关掉它之前要想清楚

可靠 UDP 的拥塞控制有三种常见取舍：

策略做法适用
照搬 TCP在用户态实现慢启动 / AIMD，或 CUBIC、BBR（QUIC 就是这样）大流量传输（文件、视频），需要与其他流公平共享
关闭拥塞窗口 + 限速KCP nc=1，再用令牌桶限制最大发送速率；发送窗口仍受接收窗口限制游戏：流量小（几 KB/s～几十 KB/s）而稳定，远低于瓶颈带宽，丢包多为随机丢包
基于时延的降级监测 RTT 相对基线的上升（排队在加剧）或丢包率突增，主动降低快照频率 / 精度游戏、实时音视频（WebRTC 的 GCC 算法就是基于时延梯度）
struct TokenBucket { double rate, burst, tokens, last; // rate：字节/秒；burst：桶容量 bool TrySend(size_t bytes, double nowSec) { tokens = std::min(burst, tokens + (nowSec - last) * rate); last = nowSec; if (tokens < bytes) return false; // 令牌不够：本轮先不发（留在队列里） tokens -= bytes; return true; } };

8.10 用带宽换延迟：冗余发送与 FEC

重传至少要付出一个 RTT 的代价。如果能预先多发一些数据，让接收方在部分丢包时自己恢复出原文，就可以完全不等重传。

冗余发送（游戏最常用）

每个包除了本帧的输入，还捎带最近 k 帧的输入。只要连续 k+1 个包没有全丢，接收方就能拿到每一帧。独立丢包率为 p 时，残余丢失率约为 pk+1：p=10%、k=3 时只有万分之一。输入数据很小（几字节到几十字节），冗余几乎不增加带宽。

FEC 前向纠错

每 n 个数据包额外生成 m 个校验包，收到任意 n 个就能恢复全部。最简单的是异或（m=1）；Reed-Solomon 码可以任意配置 (n, m)。实时音视频（WebRTC 的 FlexFEC / ULPFEC）、kcp-go、加速器广泛使用。

8.11 分片、连接管理与安全

分片与重组

大于 MTU 的消息在发送端切片，每片独立编号（占用连续的 sn），并在 frg 字段中标注"后面还有几片"。接收端按序收到 frg = 0 的那一片时，把前面连续的片拼接成完整消息交给应用。KCP 正是这样做的：在消息模式下，ikcp_recv 只有在一条消息的所有分片都到齐后才返回。

连接管理

  • 握手：客户端发 CONNECT；服务器不分配会话资源，回一个带 Cookie（如 HMAC(客户端地址, 时间, 密钥)）的 CHALLENGE；客户端带着 Cookie 再发一次，服务器校验通过才分配 conv 和会话。这同时防住了"伪造源地址耗尽会话"（SYN Flood 的 UDP 版）和"反射放大"。服务器的第一次回复不应该比客户端的请求大。
  • 会话识别：用 conv 而不是四元组查找会话；收到同一 conv 但源地址变了的包（NAT 重绑定），验证后更新地址。
  • 心跳与断线：没有数据时定期发 PING（顺便测 RTT、保活 NAT 映射）；N 秒内没有收到对方任何包就判定断线。
  • 关闭：发 CLOSE 并重复几次（它也可能丢），对方收到后释放资源；最终仍以超时兜底。

安全

UDP 包很容易伪造和篡改。面向公网的可靠 UDP 至少需要：认证加密（AES-GCM / ChaCha20-Poly1305，或直接用 DTLS），包含序号的 nonce 防重放，握手阶段的密钥协商（如 ECDH）。KCP 不提供任何安全能力，kcp-go 提供了多种对称加密可选；QUIC 则强制 TLS 1.3。

8.12 实测：仿真对比各种 ARQ 策略

配套程序 d2_rudp_sim 用虚拟时钟仿真：链路 1 包/ms、RTT ≈ 60 ms、双向独立丢包 5%、1% 的包"绕路"制造轻微乱序，传输 2000 个包。各方案的协议逻辑与本章代码同构。

逐行解读：

  • A1 停等：每个包至少等 1 个 RTT，2000 × 61 ms ≈ 122 s，再加上丢包后的超时等待，171 s。和 8.5 节"利用率 1.6%"的计算吻合。
  • A2 GBN：窗口 64 本应很快，但每丢一个包就要把后面整窗重发一遍，80% 的发送是重传，反而只比停等好 4.7 倍。
  • A3 → A4：同样是选择重传，加上快速重传后耗时减半——绝大多数丢包在约 1 个 RTT 内就被发现，不必等 200 ms 的 RTO。
  • T vs T'：两者唯一的区别是 Reno 拥塞控制。5% 的随机丢包让 Reno 不停地减半窗口，耗时多了近 9 倍。（再次提醒：这里的"类 TCP"缺少现代 Linux 的 TLP / RACK / PRR / CUBIC 等优化，绝对值偏悲观，但"随机丢包被误判为拥塞"的方向是真实的。）
  • K 类 KCP：最快，但重传占比 29.7%，是 A4 的 3.5 倍——更激进的快速重传阈值和 KCP 式计数带来了大量"其实没丢"的重传。这就是 KCP 官方描述的"以 10%～20% 的带宽浪费换取更低的延迟"，这里因为仿真丢包率较高，浪费得更多。

本章小结
  • 报文头：conv（会话 ID）、sn、una、ack_bits、ts、wnd、chan、frg；按包编号，ACK 捎带在数据包里。
  • 序号比较用 int32_t(a - b) > 0；窗口必须小于序号空间的一半（SR 要求序号空间 ≥ 2N）。
  • 确认 = UNA（累计，抗 ACK 丢失）+ 逐包 ACK 或位图（选择确认，避免多余重传）。
  • 时间戳回显测 RTT，避免重传歧义；RTO 下限、退避倍数、快速重传阈值都可以按业务调。
  • 停等利用率 ≈ T/(T+RTT)；GBN 丢一个重发一窗；SR 只重发丢失的包，是现代协议的共同选择。
  • 接收端环形缓冲：乱序暂存、按序交付、重复检测（重复包也要回 ACK）。
  • 拥塞：照搬 TCP / 关窗 + 令牌桶限速 / 基于时延降级；冗余发送与 FEC 用带宽换零 RTT 恢复。
  • 连接管理：Cookie 握手防伪造与放大、conv 识别会话、心跳、超时断线；公网必须加密认证。
  • 仿真：SR + 快速重传比 SR 快一倍；GBN 80% 都是重传；随机丢包下 Reno 慢近 9 倍；类 KCP 最快但多花约 30% 带宽。
思考题 1：为什么选择重传要求序号空间至少是窗口的 2 倍？

设窗口为 N。接收方收完一整窗 0～N−1 并发出确认后，接收窗口移动到 N～2N−1。如果这些确认全部丢失，发送方会重传 0～N−1。若序号空间只有 N（序号模 N），重传的旧包 0 和新窗口期望的包 N 编号相同，接收方会把旧包当成新包接收。序号空间 ≥ 2N 时，新旧窗口的序号不重叠，才能区分。

思考题 2：为什么接收方收到重复包时还要回 ACK？

发送方重传一个包，说明它没有收到这个包的确认——要么数据包丢了，要么 ACK 丢了。如果是 ACK 丢了，接收方其实已经收到过数据，若此时对重复包不回 ACK，发送方会一直重传下去。所以去重只是"不重复交付给应用"，确认必须照发。

思考题 3：帧同步游戏中，"每个包冗余携带最近 3 帧输入"和"用 KCP 可靠传输每帧输入"相比，各有什么优缺点？

冗余发送：不需要等待重传，单包丢失对时延零影响；独立丢包下残余丢失率约 p⁴，非常低；输入数据很小，冗余开销可以忽略。缺点是不能保证 100% 送达（连续 4 个包全丢时缺帧），所以通常还要配合"缺帧时通过可靠通道请求补发"。KCP：保证每帧都送达且有序，但丢包时至少等一次重传（约 1 个 RTT），时延抖动更大。实际工程中常两者结合：冗余发送解决绝大部分丢包，可靠通道兜底。

思考题 4：如果你的可靠 UDP 只用 UNA 而不用任何选择确认，会退化成哪种 ARQ？

发送方只知道"una 之前都收到了"，不知道 una 之后哪些已收到。如果接收端会缓存乱序包，发送方在超时时只重传 una 那一个包（下一个 ACK 的 una 会跳到更后面），效果接近选择重传但发现丢包很慢（只能靠超时、每 RTT 修一个洞）；如果发送方超时后把 una 之后的全部重发，就退化成了回退 N 步。这正是 TCP 早期没有 SACK 时的困境。
