9.1 KCP 是什么

KCP 是由林伟（skywind3000）开源的一个快速可靠传输协议，项目 README 中对它的描述是：能以比 TCP 浪费 10%～20% 带宽的代价，换取平均延迟降低 30%～40%、最大延迟降低三倍的传输效果。它在手游、实时音视频、网络加速器等领域被广泛使用，也衍生出 kcp-go、KCP-Net 等多语言实现。

纯算法实现

KCP 不负责收发 UDP，使用者通过回调函数 output 告诉它"怎么把一个包发出去"，收到包后调用 ikcp_input 喂给它。连时钟都由外部传入，内部没有任何系统调用——所以能嵌入任何引擎、平台和 IO 模型。

只做 ARQ

对应图 7-2 中的第 ③ 层（外加消息分片）：序号、确认、重传、窗口、拥塞控制。不包含连接建立、会话管理、心跳、加密、FEC，这些都要使用者自己补。

流速优先，而非流量优先

TCP 的设计目标是充分利用带宽（每秒传多少 KB）；KCP 的目标是降低单个包从发出到交付的时间（一个包花多少毫秒）。两者的取舍方向不同。

9.3 KCP 对 TCP 的六处改动

KCP 的 README 用"vs TCP"的方式列出了它的关键设计，每一条都和前面讲过的 TCP 机制一一对应：

#TCP 的做法KCP 的做法效果 / 代价
1RTO 翻倍：连续超时 3 次，等待时间变成 RTO × 8nodelay 模式下每次超时 RTO × 1.5；RTO 下限从 100 ms 降为 30 ms连续丢包时等待时间增长慢得多（见图 9-3）；代价是严重拥塞时退让不足
2（早期 / 无 SACK）丢包后可能重传丢失点之后的所有数据选择性重传：只重传真正丢失的包减少无效重传
33 个重复 ACK 触发快速重传被跳过 resend 次即重传（极速模式 resend=2）：发送 1～5，收到 ACK 1、3、4 时，2 已被跳过 2 次，立即重传更早修复丢包；代价是轻微乱序也会触发重传
4延迟确认（最多数百毫秒）ACK 不刻意延迟，在下一次 flush（≤ interval，极速模式 10 ms）时发出RTT 测量更准、重传更及时；代价是 ACK 包更多
5只有 UNA（累计确认），SACK 是可选扩展UNA + 逐包 ACK：每个包都带 una，同时有单独的 ACK 段ACK 丢失时 UNA 兜底，逐包 ACK 保证精确
6公平退让：发送窗口受拥塞窗口约束，丢包即减窗非退让流控（nc=1）：发送窗口只由发送缓冲和对端接收窗口决定，跳过慢启动和丢包退让小流量实时数据不会因随机丢包降速；代价是失去对网络的"礼让"

9.4 接入代码

#include "ikcp.h" static int UdpOutput(const char* buf, int len, ikcpcb* kcp, void* user) { auto* s = static_cast(user); return sendto(s->sock, buf, len, 0, (sockaddr*)&s->peer, sizeof s->peer); // KCP 只管"要发什么" } void Init(Session* s, uint32_t conv) { s->kcp = ikcp_create(conv, s); // conv 双方必须一致（通常由服务器在登录时分配） s->kcp->output = UdpOutput; ikcp_nodelay(s->kcp, 1, 10, 2, 1); // 极速模式：nodelay=1, interval=10ms, resend=2, nc=1 ikcp_wndsize(s->kcp, 128, 128); // 发送 / 接收窗口（默认 32 / 128） ikcp_setmtu(s->kcp, 1200); // 默认 1400；移动网络建议更保守 s->kcp->rx_minrto = 10; // 可选：进一步降低 RTO 下限 } void Tick(Session* s, uint32_t nowMs) { // 游戏主循环里每帧调用 char buf[1500]; for (int n; (n = recvfrom(s->sock, buf, sizeof buf, 0, nullptr, nullptr)) > 0;) ikcp_input(s->kcp, buf, n); // ① 把收到的 UDP 包喂给 KCP（非阻塞 socket） ikcp_update(s->kcp, nowMs); // ② 驱动时钟：发 ACK、发新数据、检查重传 for (int n; (n = ikcp_recv(s->kcp, buf, sizeof buf)) > 0;) OnMessage(buf, n); // ③ 取出按序、完整的消息 } void Send(Session* s, const void* msg, int len) { ikcp_send(s->kcp, (const char*)msg, len); // 放入 snd_queue，下一次 update/flush 时才真正发出 // 想更低延迟：ikcp_flush(s->kcp) 立即发送（会多一些小包） }
🔬 ikcp_check：服务器上省 CPU 的关键

服务器上可能有上万个 KCP 会话，每 10 ms 对每个会话调用一次 ikcp_update 很浪费。ikcp_check(kcp, now) 返回"下一次真正需要调用 update 的时刻"（最近的重传时间或下一个 interval），服务器可以把会话按这个时间放进定时器堆或时间轮，只在需要时调度；收到包或有新消息要发时再立即调度一次。

9.6 实测：100 Hz 实时消息流下的时延

批量传输看的是"多久传完"，实时应用更关心"每条消息花了多少毫秒"。d2 的实验 B 模拟一个每 10 ms 产生一条消息（100 Hz，接近游戏的输入 / 状态发送频率）的流，持续 10 秒，测量每条消息从产生到按序交付给应用的时延。

从这组数据可以读出三个层次的结论：

  1. T → T'：随机丢包下，基于丢包的拥塞控制把发送速率压到了应用速率（100 条/秒）以下，消息在发送队列里越堆越多，时延滚雪球般增长到十几秒。这对应 Mathis 公式：Reno 的吞吐上限约为 MSS / RTT × 1.22 / √p，RTT 60 ms、p = 5% 时约 91 包/秒，恰好低于 100 Hz。真实 Linux 有更多优化，不会这么极端，但"随机丢包被误判为拥塞"的问题确实存在。
  2. T' → K：同样没有拥塞控制，KCP 式参数（快重传 2、RTO 下限 30 ms、×1.5 退避、立即 ACK）把 P99 从 185/213/513 ms 压到 95/123/163 ms。
  3. 代价：K 的发送次数是 1249/1474/1907，比 T' 多 16%～37%——这就是 KCP 所说的"带宽浪费"。而在 0% 丢包时它也多发了 11 个包（轻微乱序触发的伪快速重传）。

9.7 工程实践：KCP 之外还要补什么

KCP 不提供的常见做法
连接建立与 conv 分配先用 TCP / HTTP 登录拿到 conv 和密钥，再切到 UDP；或者自己实现带 Cookie 的 UDP 握手
会话识别服务器用 conv 查会话（ikcp_getconv 可以从包头取出 conv），不依赖源地址，可支持 NAT 换端口
心跳与断线应用层心跳；监控 kcp->state == -1（dead_link）；N 秒无包判定断线
加密与防篡改在 output / input 处加一层 AEAD 加密；kcp-go 内置了多种加密
FECkcp-go 内置 Reed-Solomon FEC；或自己实现异或 FEC
不可靠消息KCP 只有可靠有序一种语义；状态同步等不可靠数据绕过 KCP 直接走 UDP，在同一个 socket 上用首字节区分
TCP 兜底UDP 不通时自动降级到 TCP（KCP over TCP 没有意义，直接用 TCP 传消息即可）
⚠️ 易错点：KCP 不是"更快的 TCP"

KCP 降低的是丢包场景下的时延和抖动，代价是更多的带宽和 CPU。在不丢包的网络上，KCP 和 TCP 的时延几乎一样（实验 B 的 0% 行）；在大文件下载这类追求吞吐的场景，关闭拥塞控制的 KCP 可能挤占带宽、造成更多丢包，反而得不偿失。用 KCP 之前先确认：你的问题是"延迟抖动"而不是"带宽不够"。

✅ 面试答法：KCP 为什么比 TCP 快？

KCP 是一个运行在 UDP 之上的 ARQ 协议，"快"指的是丢包时延迟更低。它对 TCP 做了几处改动：① 超时重传时 RTO 只乘 1.5 而不是翻倍，RTO 下限也更低；② 选择性重传，只重传丢失的包；③ 快速重传阈值可配（比如被跳过 2 次就重传），不必等 3 个重复 ACK；④ ACK 不做延迟；⑤ 同时使用 UNA 和逐包 ACK；⑥ 可以关闭拥塞控制，避免随机丢包导致降速。代价是 10%～20% 甚至更多的额外带宽，以及需要自己处理连接管理、加密和不可靠消息。

本章小结
  • KCP：纯算法 ARQ 库，无 IO、无系统调用；只做可靠传输层，不含连接、加密、FEC。
  • 四个队列：snd_queue → snd_buf → output；input → rcv_buf → rcv_queue；由 ikcp_update 时钟驱动。
  • 24 字节头：conv、cmd（PUSH/ACK/WASK/WINS）、frg、wnd、ts、sn、una、len。
  • 六处改动：RTO×1.5、选择重传、快速重传（resend）、非延迟 ACK、UNA+ACK、非退让流控（nc）。
  • 极速模式 ikcp_nodelay(kcp, 1, 10, 2, 1)；窗口默认 32/128，MTU 1400，RTO 下限 100/30 ms。
  • 仿真：随机丢包下拥塞控制是 TCP 时延崩溃的主因；KCP 在此基础上把 P99 再降 40%～70%，多花 16%～37% 带宽。
思考题 1：KCP 关闭拥塞控制后，会不会把网络挤爆？应该怎么做？

有可能。nc=1 后发送窗口只受 sndwnd 和对端 rcvwnd 限制，如果应用持续提交超过链路容量的数据，KCP 会把整个窗口塞进网络，造成排队和丢包，丢包又引发更多重传，形成恶性循环。做法：① 只在小流量实时数据（游戏、信令）上关闭拥塞控制；② 合理设置 sndwnd（≈ 期望速率 × RTT / 包长）；③ 应用层令牌桶限速；④ 监控 RTT 和重传率，异常时降低发送频率或数据精度；⑤ 大流量数据（资源下载）走 TCP / HTTP。

思考题 2：KCP 的 interval 设为 100 ms 和 10 ms，对延迟有什么影响？

KCP 所有的发送（包括 ACK）都在 flush 中完成，flush 每 interval 执行一次。interval = 100 ms 时，ACK 最多被延迟 100 ms，重传检查的精度也是 100 ms，RTT 测量会偏大，实际延迟明显变差；10 ms 时这些延迟都降到 10 ms 以内，代价是 CPU 占用增加、小包更多。也可以在 ikcp_send / ikcp_input 后主动调用 ikcp_flush 来降低延迟。

思考题 3：为什么 KCP 的接收窗口默认比发送窗口大（128 vs 32）？

接收窗口需要容纳乱序到达、等待前面缺失包的数据。如果接收窗口和发送窗口一样大甚至更小，丢包后后续到达的包可能因超出接收窗口被丢弃，引发额外的重传。另外，一条大消息被分成多个分片时，所有分片都要能放进接收窗口，ikcp_recv 才能把整条消息取出，所以 KCP 要求 rcvwnd 不小于最大分片数（源码注释中的 must >= max fragment size）。
