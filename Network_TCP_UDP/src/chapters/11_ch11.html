11.2 实战一：帧同步 MOBA 的网络层设计

帧同步（Lockstep）的核心思想是：服务器不计算游戏逻辑，只负责收集所有玩家每个逻辑帧的操作并转发；每个客户端用相同的初始状态、相同的操作序列、确定性的逻辑，独立算出一致的结果。它对网络的要求是：每一帧的操作必须送达且按帧序执行（可靠有序），但又必须低延迟、低抖动，否则所有玩家都会卡。

🎮 游戏开发视角：几个容易忽略的细节

① 上行冗余的终止条件：客户端持续冗余发送某帧输入，直到服务器的包头 ACK 表明已收到——这就是第 8 章 UNA + ACK 位图的直接应用。
② 帧缓冲的大小要自适应：根据实测抖动动态调整缓冲帧数，网络好时减少输入延迟，网络差时增加平滑度。
③ 包要小：控制在 MTU 以内，避免 IP 分片（第 1 章）；10 个玩家 × 若干字节的操作，一个帧包通常只有几十到一两百字节。
④ 不要让一个慢玩家拖住所有人：服务器按固定节奏推进帧号，没收到某玩家的输入就当作"无操作"，这和 TCP 的"必须等"截然不同。

11.3 实战二：状态同步

状态同步（如 UE 的 Actor 复制）由服务器计算权威状态，按需把属性变化发给客户端。它的传输策略可以对照可靠性光谱来理解：

数据可靠性机制
属性复制（位置、血量……）可靠 · 只要最新不可靠发送；检测到包丢失时，不重传旧包，而是把相关属性标记为"脏"，在下一次复制时发送当前值
Reliable RPC（开火、技能、交互）可靠有序（同一 Actor 通道内）丢失后重传；过多的可靠 RPC 积压会导致通道溢出、连接被断开，所以要节制使用
Unreliable RPC（特效、音效）不可靠发了就不管；带宽紧张时可能被丢弃
移动同步不可靠 + 客户端预测 / 服务器校正客户端先本地执行移动，服务器验证后纠正；输入用不可靠 RPC 高频发送，并冗余携带最近的移动

另外，状态同步还要做相关性裁剪（只同步玩家附近 / 视野内的对象）和优先级与带宽预算（每帧按优先级在预算内挑选要发送的对象），本质上是第 7 章架构图中"通道与调度层"的工作。

11.4 实战三：实时音视频（WebRTC）

RTP / RTCP over UDP

RTP 携带媒体数据（序号 + 时间戳），RTCP 反馈接收质量（丢包率、抖动、RTT）。全部通过 SRTP / DTLS 加密。

NACK：有条件的重传

接收方发现缺包时发 NACK 请求重传，但只有在"重传的包能在播放截止前到达"时才有意义——RTT 大时就放弃，改靠 FEC 或丢帧。

FEC + 抖动缓冲

FlexFEC / ULPFEC 用冗余包恢复丢包；抖动缓冲（jitter buffer）动态调整缓冲时长，平滑到达时间的波动。

基于时延的拥塞控制

GCC（Google Congestion Control）监测包到达间隔的变化趋势，在队列开始积压时就降低码率，而不是等到丢包。码率调整直接作用于编码器。

对比游戏和音视频会发现一个共同规律：越是实时的场景，越倾向于"用带宽和画质换时延"——FEC、冗余发送、主动降码率、降低快照频率，都是这个思路。

11.6 弱网测试与质量指标

模拟工具

Windows：clumsy（可注入延迟、丢包、乱序、重复）；Linux：tc qdisc add dev eth0 root netem delay 100ms 20ms loss 5%；macOS / iOS：Network Link Conditioner；移动端还要实测地铁、电梯、弱信号场景。

关键指标

RTT 均值与 P99、抖动（RTT 的波动）、丢包率（上下行分别统计）、重传占比、消息端到端时延的 P99 / 最大值、卡顿次数（例如帧缓冲被打空的次数）、断线率与重连耗时。

经验法则

只看平均值会骗人：实验 B 中 T' 的平均时延只有 61 ms，但 P99 是 185 ms。玩家感知到的"卡"几乎都来自尾部时延，所以优化目标应该写成 P99 / P999。

本章小结
  • 选型先看数据的可靠性需求，再看是否需要多路复用、加密、连接迁移、浏览器兼容。
  • 帧同步：UDP 冗余发送为主（仿真中 20% 丢包 P99 仍只有 51 ms），可靠通道兜底，帧缓冲吸收抖动，TCP 处理非实时业务与降级。
  • 状态同步：属性复制"只发最新值"、Reliable RPC 节制使用、相关性与优先级调度。
  • 音视频：NACK 有条件重传 + FEC + 抖动缓冲 + 基于时延的拥塞控制。
  • 网页：减少 RTT 个数是主线（预连接、长连接、TLS 1.3、HTTP/3、CDN）。
  • 弱网测试看 P99 和抖动，不要只看平均值。
思考题 1：帧同步中，如果某个玩家网络特别差，服务器应该等他吗？

不应该。如果服务器等最慢的玩家（严格锁步），所有人都会被拖慢，体验极差。现代帧同步服务器按固定节奏推进帧号，迟到的输入被放入下一帧（或丢弃），该玩家看到的是自己的操作稍有延迟；他的客户端如果落后太多，会进入"追帧"模式快速执行积压的帧。网络长时间不可用时，服务器可以让 AI 托管该玩家。

思考题 2：为什么说"只看平均时延会骗人"？请用本书的仿真数据说明。

实验 B 中 5% 丢包时，T'（关闭拥塞控制的类 TCP）平均时延 60.7 ms，看起来只比无丢包时多 30 ms；但 P99 是 185 ms、最大 215 ms，意味着每 100 条消息里就有 1 条要等 6 倍的单程时延。游戏中这 1% 正好对应玩家感知到的"卡了一下"。KCP 把平均值从 60.7 降到 42.9（降 29%），P99 从 185 降到 95（降 49%），尾部的改善远比平均值明显——这也是 KCP 官方说"最大延迟降低三倍"比"平均延迟降低 30%～40%"更有意义的原因。

思考题 3：设计一个手游的网络层，UDP 被运营商封了怎么办？

① 登录时（走 TCP/HTTPS）由服务器下发 UDP 地址与会话票据；② 客户端先尝试 UDP 握手，若在限定时间（如 1～2 秒）内失败，或运行中连续一段时间收不到 UDP 包，则切换到 TCP 通道；③ 业务层对两种通道使用统一的消息接口（TCP 上直接传输应用消息，开 TCP_NODELAY，不再套 KCP）；④ 记录降级比例，作为网络质量监控指标；⑤ 可选：对 UDP 流量做端口随机化、伪装等对抗策略（需评估合规性）。
