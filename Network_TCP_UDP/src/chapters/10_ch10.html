CHAPTER 10

QUIC：把 TCP + TLS 搬到用户态重写一遍

KCP 是一个 ARQ 算法，QUIC 是一个完整的、标准化的、加密的传输协议，也是 HTTP/3 的底座。

本章目标
  • 说清 QUIC 的分层位置和它要解决的四个问题
  • 理解 1-RTT / 0-RTT 握手、连接 ID 与连接迁移
  • 理解 QUIC 的流为什么没有队头阻塞，以及"包号与流偏移分离"如何消除重传歧义
  • 掌握 QUIC 的 ACK 帧、丢包检测（包阈值 / 时间阈值 / PTO）、两级流量控制、可插拔拥塞控制
  • 知道 QUIC 的安全设计（抗放大、Retry、头部保护）与部署代价

10.1 背景与定位

QUIC 最早由 Google 于 2012 年前后提出并在 Chrome 中部署（后称 gQUIC），之后由 IETF 标准化：RFC 9000（传输协议）、RFC 9001（与 TLS 1.3 的结合）、RFC 9002（丢包检测与拥塞控制）于 2021 年发布，基于 QUIC 的 HTTP/3（RFC 9114）于 2022 年发布。它要解决的正是第 4、7 章列出的 TCP 痛点：

① 握手太慢

TCP 握手 1 RTT + TLS 1～2 RTT → QUIC 把传输握手和加密握手合并为 1 RTT，恢复连接时 0 RTT。

② 队头阻塞

HTTP/2 的多个流共享一个 TCP 字节流 → QUIC 原生支持多个独立的流，丢包只影响所在的流。

③ 换网断连

TCP 连接绑定四元组 → QUIC 用连接 ID 标识连接，IP / 端口变了连接仍在。

④ 协议僵化

TCP 在内核里、头部明文、被中间设备"看懂"并干预 → QUIC 在用户态实现，几乎所有头部字段都加密，可以快速迭代。

10.2 握手：1-RTT 与 0-RTT

  • 1-RTT：客户端的第一个包（Initial）就包含 TLS 1.3 的 ClientHello 和 QUIC 的传输参数（初始流控窗口、最大流数量等），服务器一次回复就完成密钥协商，客户端随即可以发送应用数据。传输握手和加密握手共用同一个往返。
  • 0-RTT：客户端曾经连过这台服务器，保存了会话票据（session ticket），再次连接时可以用它派生的密钥直接加密应用数据，和 Initial 一起发出。
⚠️ 易错点：0-RTT 数据可以被重放

0-RTT 数据在服务器回复之前就发出了，不具备前向安全性，而且攻击者截获后可以原样重放给服务器。所以 0-RTT 只能用于幂等请求（如 GET），服务器端通常也会限制 0-RTT 能做的操作。这和 TCP Fast Open 面临的问题本质相同。

10.3 连接 ID 与连接迁移

这和第 8 章自研协议用 conv 识别会话是同一个思想。QUIC 做得更完整：双方可以通过 NEW_CONNECTION_ID 帧提前交换多个连接 ID，迁移时换用新 ID 以保护隐私；切换到新路径时必须先用 PATH_CHALLENGE / PATH_RESPONSE 验证对方确实在新地址上（防止被利用来攻击第三方），并重新评估这条路径的 RTT 和拥塞窗口。

10.4 流：没有队头阻塞的多路复用

QUIC 的流用 62 位的流 ID 标识，最低两位表示由哪一方发起、是双向还是单向。HTTP/3 中每个请求 / 响应占用一个双向流。流的开销很小，开新流不需要握手，这让 HTTP/3 可以随意并发请求。

10.5 可靠性设计：包号与流偏移分离

这是 QUIC 相对 TCP 最精巧的设计之一。TCP 用同一个序号同时表示"这是哪个包"和"这是字节流的哪个位置"，所以重传的段和原段序号相同，ACK 到达时分不清确认的是哪一次发送（第 3 章的重传歧义）。QUIC 把两者拆开：

丢包检测（RFC 9002）

机制规则对应 TCP 的
包阈值某个包之后又有 3 个更大包号的包被确认（kPacketThreshold = 3），判定它丢失3 个重复 ACK
时间阈值某个包发出后超过 9/8 × max(SRTT, 最新 RTT) 仍未被确认，而它之后发送的包已被确认，判定丢失RACK（RFC 8985）
PTO 探测超时一段时间（SRTT + max(4×RTTVAR, 1ms) + max_ack_delay）内收不到任何确认时，发送 1～2 个探测包，而不是直接判定丢失RTO + TLP；但 PTO 触发时不会把拥塞窗口降到 1，只有持续拥塞时才大幅降窗

10.6 流量控制与拥塞控制

  • 两级流量控制：每个流有自己的接收上限（MAX_STREAM_DATA），整个连接还有一个总上限（MAX_DATA）；另外用 MAX_STREAMS 限制对方能同时打开多少个流。这样一个"慢流"不会吃光整个连接的缓冲。
  • 可插拔拥塞控制：RFC 9002 给出了一个类似 NewReno 的参考算法，但实现可以自由替换为 CUBIC、BBR 等。因为在用户态，升级拥塞算法只需要更新应用，不需要等操作系统——这正是 Google 能在 QUIC 上快速迭代 BBR 的原因。
  • Pacing：推荐按速率平滑发包，而不是一次性把整个窗口突发出去，减少路由器队列压力。

10.7 安全设计

几乎全部加密

除了少量必要字段（标志位、连接 ID），QUIC 头部和所有帧都被加密；连包号也用"头部保护"加密了。中间设备看不到、也就改不了 QUIC 的内部字段——这是对抗协议僵化的主动设计。

抗放大攻击

在验证客户端地址之前，服务器发送的数据不得超过收到数据的 3 倍；客户端的 Initial 包必须填充到至少 1200 字节，既保证了路径 MTU，也让放大倍数可控。

Retry 令牌

服务器可以先回一个 Retry 包，要求客户端带着令牌重新发送 Initial，证明自己真的拥有这个源地址——这就是 SYN Cookie 思想在 QUIC 中的体现（第 5 章）。

10.8 代价与现状

  • CPU 开销：用户态协议栈、每包加解密、缺少成熟的硬件卸载，服务器 CPU 消耗通常高于 TCP + TLS。业界通过 UDP GSO / GRO、sendmmsg、内核旁路等手段优化。
  • UDP 被限制：部分企业网络封禁 UDP 443，部分运营商对 UDP 限速。浏览器会通过 Alt-Svc 头部发现服务器支持 HTTP/3，并在 QUIC 失败时自动回退到 TCP。
  • 实现复杂：一个完整的 QUIC 实现动辄数万行代码。主流开源实现有 Chromium QUIC、Cloudflare quiche、Microsoft MsQuic、ngtcp2、quic-go、LiteSpeed lsquic 等。
  • 扩展：RFC 9221 定义了 DATAGRAM 帧，在 QUIC 连接中发送不可靠、不重传的数据（共享加密和拥塞控制），使 QUIC 也能承载"不可靠 · 只要最新"类的实时数据（WebTransport 就基于此）。

✅ 面试答法：QUIC 相比 TCP 有哪些改进？

① 握手更快：传输和 TLS 1.3 握手合并，首次 1 RTT，恢复连接 0 RTT；② 无队头阻塞：原生多流，每个流独立排序，一个丢包只影响所在的流；③ 连接迁移：用连接 ID 而不是四元组标识连接，切换网络不断线；④ 更好的丢包恢复：包号单调递增、与流偏移分离，消除重传歧义，ACK 帧可以携带大量范围和 ACK 延迟；⑤ 用户态实现：拥塞控制可插拔、迭代快，且头部加密防止中间设备僵化；⑥ 内置抗放大和地址验证。代价是 CPU 开销更高，以及部分网络对 UDP 的限制需要回退 TCP。

本章小结
  • QUIC：RFC 9000/9001/9002（2021），HTTP/3 RFC 9114（2022）；= 可靠传输 + TLS 1.3 + 流复用，跑在 UDP 上。
  • 握手 1-RTT，恢复 0-RTT（0-RTT 数据可被重放，只用于幂等请求）。
  • 连接 ID 标识连接 → 连接迁移；迁移需 PATH_CHALLENGE 验证，换用新 ID 保护隐私。
  • 多流复用：流间无队头阻塞，流内仍有序。
  • 包号永增、与流偏移分离 → 无重传歧义；重传的是帧不是包；丢包检测：包阈值 3、时间阈值 9/8 RTT、PTO。
  • 两级流控（MAX_STREAM_DATA / MAX_DATA）；拥塞控制可插拔；抗放大 3 倍、Initial ≥ 1200 字节、Retry 令牌。
  • 代价：CPU 高、UDP 可能被封需回退 TCP、实现复杂；DATAGRAM 扩展支持不可靠数据。
思考题 1：HTTP/3 一定比 HTTP/2 快吗？

不一定。在低丢包、低 RTT 的有线网络中，两者差别很小，HTTP/3 甚至可能因为 CPU 开销更高、UDP 未被优化而略慢。HTTP/3 的优势集中在：高 RTT（握手少）、有丢包（无流间队头阻塞、恢复更快）、频繁切换网络（连接迁移）的移动场景。此外如果网络限制 UDP，浏览器会回退到 HTTP/2。

思考题 2：为什么说 QUIC 的"包号永不重复"解决了 TCP 的重传歧义？KCP 是怎么解决的？

TCP 重传段与原段序号相同，ACK 到来时无法判断确认的是哪一次发送，RTT 采样只能放弃（Karn 算法）或依赖时间戳选项。QUIC 每次发送都使用新的包号，ACK 确认的是具体包号，因此一定能对应到唯一一次发送，可以精确测量 RTT 并判断丢包。KCP 的重传仍然使用相同的 sn，但每次发送都更新 ts，接收方在 ACK 中回显 ts，发送方用 now − ts 计算 RTT，同样避免了歧义。

思考题 3：QUIC 运行在用户态，那它还能利用内核的拥塞控制吗？这对公平性有什么影响？

不能直接使用内核 TCP 的拥塞控制，QUIC 在用户态自己实现拥塞控制（RFC 9002 要求必须实现，不能不做）。这使得每个应用可以选择不同的算法，迭代更快；但也意味着公平性依赖于实现者的自律——如果某个实现采用过于激进的算法，会挤占同一瓶颈上其他 TCP 流的带宽。IETF 通过标准中的拥塞控制要求和互操作测试来约束这一点。
