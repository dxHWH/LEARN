## 面试官提问

> 如何设计一个内存泄漏的工具？

## 0. 两分钟口述版（先背这个）

> 我会把它拆成 **采集 → 记录 → 判定 → 展示** 四层来设计。
>
> **采集层**：拦截所有分配/释放。最通用的是替换全局 `operator new/delete`，但它抓不到 `malloc` 和第三方库，所以生产中会在更底层做：引擎自己的分配器接口（比如 UE 的 `FMalloc` 包一层代理）、平台级 hook（Windows 的 Detours/IAT、Android 的 PLT hook、iOS 的 `malloc_logger`），Lua 用自定义 `lua_Alloc`，显存在 RHI 层包装。
>
> **记录层**：用一张**外部哈希表**记录「指针 → 大小、调用栈、分配序号、帧号、内存标签」。调用栈运行时**只存返回地址**，不在线符号化，并且对栈做**哈希去重**，每条记录只存一个 stackId。追踪器自己的容器必须走 `malloc` 之类的原始分配，加 `thread_local` 重入保护，否则会无限递归。
>
> **判定层**：「程序退出时还活着」只能抓最简单的情况，而且游戏里误报多、逻辑泄漏抓不到。游戏里最有效的是**快照 diff**：在进关卡前打一个标记，退回大厅后看这段时间里分配、但到现在还活着的内存，而且**反复进出 N 次**，第一次的增长可能是合理缓存，之后每次都线性增长的就是泄漏。另一种是 LSan/Valgrind 那样的**可达性分析**：停住所有线程，从栈、寄存器、全局区出发扫描指针，扫不到的块就是真泄漏。
>
> **展示层**：按调用点聚合、按字节排序，离线用 PDB/dSYM 符号化，配合内存标签（按系统/场景分类），接进 CI 自动跑「进出关卡 20 次」，曲线持续上涨就告警，并附上 Top 调用栈。
>
> 难点主要是**性能**（栈回溯是大头，可以用帧指针回溯、按字节采样、TLS 缓冲加后台线程批量处理来降低开销）和**游戏特有的泄漏**（UObject/C# 的引用泄漏、Lua 引用、资源引用计数不平衡、显存），这些要在对应的层用同一套「配对 + 调用栈 + 快照 diff」的思路去做。

后面每一节就是把这段话里的每个点展开讲透。

## 1. 先把问题定义清楚

面试时先花 20 秒界定问题，能体现工程素养：**“泄漏”并不只有一种**。

### 1.1 三类“泄漏”

| 类型 | 定义 | 典型例子 | 能用什么发现 |
|---|---|---|---|
| **真泄漏**（Unreachable） | 内存已经没有任何指针指向，永远不可能被释放 | `new` 了忘记 `delete`、异常/提前 `return` 跳过释放、`shared_ptr` 循环引用 | 退出检测、可达性分析、快照 diff |
| **逻辑泄漏**（Reachable but useless） | 还有引用，但业务上已经不需要了，并且**持续增长** | 全局缓存只增不删、事件监听没注销、对象池只借不还、`std::map` 当日志用 | **只能靠快照 diff / 增长趋势**，可达性分析认为它“合法” |
| **资源泄漏**（非 CPU 堆） | 泄漏的不是 `malloc` 内存 | 纹理/RT/Buffer 显存、文件句柄、线程、Socket、`UObject` 被根引用、Lua registry 引用、C# 静态事件 | 在对应层做“申请/释放配对计数 + 调用栈” |

> 游戏客户端里，**逻辑泄漏和资源泄漏往往比真泄漏更常见、危害更大**。所以只回答“重载 new/delete，退出时打印没释放的”只能拿基础分。

### 1.2 游戏客户端的特殊约束

1. **长会话 + 场景切换**：一局 15～20 分钟、大厅 ↔ 对局反复切换，每次漏一点，打几局就爆。
2. **移动端没有 swap**：iOS 由 Jetsam、Android 由 LMK（Low Memory Killer）直接杀进程，表现为“闪退”，往往没有崩溃堆栈。
3. **分配频率极高**：每帧可能有成千上万次小块分配，工具开销稍大，游戏就没法玩，帧率一掉，测试场景都跑不起来。
4. **分配器众多**：引擎分配器、STL、Lua VM、Mono/IL2CPP、图形驱动、第三方 SDK（音频、语音、渠道 SDK），只 hook 一处会有大面积盲区。
5. **发布包是 Release + 去符号**：调用栈只能拿到地址，必须离线符号化。
6. **不能长时间卡住**：可达性扫描要 stop-the-world，几百 MB 的堆扫一遍可能要秒级，只能在特定时机做。

### 1.3 设计目标（顺便给出评价指标）

| 指标 | 含义 |
|---|---|
| 覆盖率 | 能拦截多少种分配来源 |
| 准确率 | 误报（把缓存当泄漏）和漏报 |
| 开销 | CPU（ns/次分配）、额外内存（元数据 + 栈） |
| 可定位 | 能不能直接给出“哪一行、哪个系统、哪个关卡” |
| 可自动化 | 能不能接进 CI，无人值守出报告 |

## 2. 总体架构

```text
┌──────────────────────────── 运行时（设备/游戏进程内） ────────────────────────────┐
│                                                                                   │
│  ① 采集层 Hook                                                                    │
│     operator new/delete │ malloc/free/realloc │ 引擎 FMalloc │ lua_Alloc │ RHI 资源 │
│              │                                                                    │
│              ▼                                                                    │
│  ② 记录层 Recorder                                                                │
│     重入保护 → 栈回溯(只存 PC) → 栈哈希去重 → 记录 {ptr,size,seq,frame,tag,stackId} │
│     存储：分片哈希表（在线模式） 或 TLS 环形缓冲 → 后台线程（事件流模式）          │
│              │                                                                    │
└──────────────┼────────────────────────────────────────────────────────────────────┘
               │  快照 / 事件流文件 / Socket
               ▼
┌──────────────────────────── 离线（PC 分析工具） ──────────────────────────────────┐
│  ③ 判定层：退出存活 │ 区间快照 diff │ 可达性扫描 │ 增长趋势 / 存活年龄              │
│  ④ 展示层：符号化(PDB/dSYM/so) → 按调用点/标签聚合 → 调用树/火焰图 → CI 告警       │
└───────────────────────────────────────────────────────────────────────────────────┘
```

两种部署形态要能说出来：

- **在线模式**（Demo 用的就是这种）：进程内维护“存活分配表”，随时可以出报告。实现简单，但设备端的内存和 CPU 开销都比较大。
- **事件流模式**（UE Memory Insights、heaptrack 的思路）：运行时只往线程本地缓冲里追加 `alloc/free` 事件，后台线程压缩后写文件或发到 PC，**所有分析都离线做**。设备端开销最低，而且可以回放任意时刻的堆状态。

## 3. 采集层：怎么拦截所有分配

### 3.1 拦截方式对比

| 方式 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| 宏替换 `#define new new(__FILE__, __LINE__)` | 编译期把文件行号传进去 | 零依赖，能拿到精确行号 | 只覆盖包含了头文件的代码；和 placement new、`operator new` 重载冲突；拿不到调用链 |
| **替换全局 `operator new/delete`** | 链接期替换（C++ 标准允许的“可替换函数”） | 标准、跨平台，所有 C++ `new` 都会经过 | 抓不到 `malloc`、C 库、第三方库；每个 DLL 各自链接各自的版本 |
| CRT 钩子 `_CrtSetAllocHook` | MSVC Debug CRT 提供的回调 | 简单 | 仅 Debug CRT 可用 |
| **平台级函数 hook** | Windows：Detours/MinHook（inline hook）、IAT hook；Linux：`LD_PRELOAD`；Android：PLT/GOT hook（xhook、ByteHook）；iOS：`malloc_logger` 回调、fishhook、替换 `malloc_zone` | 能抓到第三方 so/dll 里的 `malloc` | 平台相关、维护成本高；inline hook 有稳定性风险 |
| **引擎分配器接口**（首选） | UE 的 `GMalloc` 是一个 `FMalloc*`，引擎本身就有多层代理（如 `FMallocPoisonProxy`），可以再包一层；自研引擎一般也有统一的 `Allocator` 接口 | 覆盖引擎 + 业务的绝大多数分配，还能拿到引擎上下文（标签、帧号） | 引擎外的分配仍然需要平台 hook 兜底 |
| 专用分配器 | Lua：`lua_newstate(l_alloc, ud)` 自定义分配函数；GPU：在 RHI/图形 API 包装层统计 `Create*/Release` | 能统计非 CPU 堆的“资源泄漏” | 每种资源要单独接入 |

> 注意：glibc 的 `__malloc_hook` 系列已经在 **glibc 2.34** 中移除，现在 Linux 上一般用 `LD_PRELOAD` 或在分配器层面做。

### 3.2 替换 `operator new/delete` 的坑（面试高频）

1. **要替换全套**：`new / new[] / nothrow 版`、`delete / delete[] / sized delete（C++14）/ nothrow 版`。C++17 还有 `align_val_t` 对齐版本，不替换的话，过对齐类型（`alignas(64)` 的结构体）会走默认实现，导致**这部分分配没有被追踪**。Demo 替换了 10 个重载。
2. **递归**：追踪器自己的哈希表、vector 如果也用 `new`，就会无限递归。解决办法：
   - 追踪器的容器用一个**直接调用 `malloc` 的分配器**（Demo 中的 `RawAlloc<T>`）；
   - 再加一层 `thread_local bool t_inHook` **重入保护**（栈回溯、符号化、日志打印内部都可能分配内存）。
3. **静态初始化顺序**：全局对象的构造函数在 `main` 之前就会 `new`，这时追踪器可能还没构造好。解决办法：用“首次使用时构造”的函数内静态对象，并且**放在静态缓冲区里、永不析构**，这样在全局析构阶段（`main` 返回之后）仍然可以使用：
   ```cpp
   Tracker& T() {
       alignas(Tracker) static unsigned char buf[sizeof(Tracker)];
       static Tracker* t = ::new (static_cast<void*>(buf)) Tracker();  // 永不析构
       return *t;
   }
   ```
4. **跨模块**：Windows 下每个用 `/MT` 链接的 DLL 都有自己的 CRT 堆和自己的 `operator new`。在 A 模块分配、B 模块释放本身就是 bug，而你在 exe 里替换的 `operator new` **对 DLL 内部不生效**。所以生产上要么统一用 `/MD`，要么在引擎分配器层或系统 API 层（`HeapAlloc`）做 hook。
5. **`realloc`**：要按“释放旧块 + 分配新块”来记录，并且注意**原地扩容**时指针不变的情况。
6. **placement new** 不分配内存，不要追踪；`delete` 空指针要直接返回。

### 3.3 Demo 中的采集代码（节选）

```cpp
void* operator new(size_t n)   { void* p = mt::Alloc(n, false); if (!p) throw std::bad_alloc(); return p; }
void* operator new[](size_t n) { void* p = mt::Alloc(n, true);  if (!p) throw std::bad_alloc(); return p; }
void  operator delete(void* p) noexcept            { mt::Free(p, false); }
void  operator delete[](void* p) noexcept          { mt::Free(p, true);  }
void  operator delete(void* p, size_t) noexcept    { mt::Free(p, false); }   // sized delete
// ... nothrow 版本略
```

## 4. 记录层：记什么、怎么存

### 4.1 元数据放哪：外部哈希表 vs 内嵌头部

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **内嵌头部** | 多分配 `sizeof(Header)`，把信息写在用户指针前面（MSVC Debug Heap 的 `_CrtMemBlockHeader` 就是这样） | O(1) 查找，不需要锁住全局表 | 改变了对齐和布局；如果内存被另一个分配器 `free`，或者发生越界写，头部会损坏；对 `_aligned_malloc` 之类的接口要特殊处理 |
| **外部哈希表**（Demo 采用） | `unordered_map<void*, AllocInfo>` | 不改动用户内存，通用，可以挂在任意分配器上 | 每次分配都要查一次表；需要加锁（可以分片） |

每条记录至少包含：

```cpp
struct AllocInfo {
    size_t      size;
    uint64_t    seq;      // 全局单调递增分配序号 → 用来做“区间快照”
    uint32_t    stackId;  // 去重后的调用栈 ID
    const char* tag;      // 内存标签：哪个系统 / 哪个关卡（类似 UE 的 LLM_SCOPE）
    bool        isArray;  // new[] 还是 new，用于检查 delete 是否配对
    // 生产上还会加：帧号 frame、线程 id、时间戳、模块 id
};
```

### 4.2 调用栈采集

| 方法 | 原理 | 速度 | 备注 |
|---|---|---|---|
| **帧指针回溯**（FP walking） | 沿着 `rbp/x29` 链表往上走，读出每层返回地址 | 最快（几十 ns 量级） | 需要编译时保留帧指针（`-fno-omit-frame-pointer`）；iOS arm64 ABI 要求保留帧指针，Android 默认不保证 |
| **基于 unwind 表** | Windows x64 读 `.pdata/.xdata`（`RtlCaptureStackBackTrace`），Linux/Android 读 `.eh_frame`（`_Unwind_Backtrace`、libunwind） | 慢（微秒级） | 不依赖帧指针，结果准确 |
| 编译器插桩 | `-finstrument-functions`，维护一个影子栈 | 回溯 O(1) | 对每次函数调用都有开销，侵入性大 |

关键原则：

- **运行时只存 PC（返回地址），绝不在线符号化**。`SymFromAddr`/`dladdr` 慢、需要加锁、内部还会分配内存，必须放到出报告时或离线做。
- **返回地址指向 call 的下一条指令**，查行号时要用 `addr - 1`，否则行号会偏到下一行（Demo 里就是这样处理的）。
- 栈深度一般限制在 16～32 层，跳过追踪器自己的帧（Demo 中 `CaptureStackBackTrace(2, ...)` 跳过了 `Alloc` 和 `operator new` 两层）。
- 开启 ASLR 后，要记录**模块基址**，把 PC 转成 `模块 + 偏移`，离线才能对上符号。

### 4.3 调用栈去重（省内存的关键）

算一笔账：每个栈 16 帧 × 8 字节 = 128 字节，100 万个存活块就要 **128 MB** 只用来存栈，这在手机上完全不可接受。

但实际上**不同的调用点只有几千到几万个**，所以：

```text
栈哈希 (FNV/xxHash) ──► stackIndex: hash → stackId ──► stacks[stackId] = 栈内容（只存一份）
每条分配记录只存 4 字节的 stackId
```

Demo 实测：**28 万次分配只产生了 18 个唯一调用栈**。生产上还可以用前缀树（Trie）存储，共享公共的栈底部分。

### 4.4 采样：开销扛不住时怎么办

全量追踪太贵时，可以用**按字节泊松采样**（tcmalloc、Android heapprofd 都是这个思路）：

- 平均每分配 N 字节采样一次，大块几乎一定会被采到，小块按概率采样；
- 统计时用“采样大小 × 权重”估算真实值；
- **对查泄漏来说足够了**：泄漏点通常会被反复执行，持续泄漏，迟早会被采到。

## 5. 线程安全与性能

### 5.1 并发设计的演进

1. **全局一把锁**（Demo 用的 `SRWLOCK`）：最简单，多线程分配密集时会竞争得很厉害。
2. **分片锁**：按 `ptr >> 4` 哈希到 64 个分片，每个分片有独立的锁和哈希表，竞争基本消失。
3. **TLS 缓冲 + 后台线程**：分配线程只往自己的线程本地环形缓冲里追加事件（无锁），后台线程批量合并进全局表，或者直接写文件。需要处理的问题：同一块内存的 `free` 事件可能先于另一个线程的 `alloc` 事件到达，所以事件要带全局序号或时间戳，合并时排序。

### 5.2 实测开销（Demo）

```text
==== 性能 ====
  裸 malloc/free: 19 ns/次；带追踪 new/delete: 593 ns/次（约 32 倍）
```

拆一下这 ~570 ns 花在哪里：x64 Windows 上 `CaptureStackBackTrace` 要读 unwind 表，逐帧展开，**这是大头**；其次是哈希表的查找和插入、加锁。优化方向：

| 优化 | 效果 |
|---|---|
| 帧指针回溯替代 unwind | 栈回溯从微秒级降到几十 ns |
| 采样 | 开销按采样率线性下降 |
| 只追踪超过阈值的大块，或者只开指定标签 | 显著降低记录量 |
| 事件流 + 离线分析 | 设备端只剩“写缓冲”的开销 |
| 运行时开关 | 默认关闭，测试包按需开启 |

### 5.3 内存开销

每个存活块的元数据大约 32～48 字节，再加上哈希表的负载因子。如果游戏里有大量 16～32 字节的小对象，**追踪器自身的内存可能和业务内存一样多**，在移动端会直接改变 OOM 的行为（“开了工具就复现不了”）。所以移动端一般用采样或者事件流模式。

## 6. 判定层：怎么认定“这是泄漏”（核心）

### 6.1 方法一：退出时仍存活

`_CrtDumpMemoryLeaks()`、Visual Leak Detector、Demo 的最后一个报告都是这种方式。问题很多：

1. **游戏经常不是正常退出的**：手机上被切后台、被系统杀掉，根本走不到退出流程。
2. **全局单例和静态对象误报**：如果在 `main` 结束前出报告，全局对象还活着，就会被当成泄漏。Demo 最后一个报告里就出现了这种情况：`g_TextureCache` 持有的纹理是全局对象，进程退出时会被析构。正确的做法是**在全局析构之后再出报告**（例如让追踪器的 `atexit` 回调最先注册、最后执行；MSVC 可以用 `#pragma init_seg(lib)` 调整初始化顺序）。
3. **最致命的一点：逻辑泄漏完全抓不到**。Demo 场景 3 里的纹理缓存，在进程退出时会随着全局 vector 析构被正常释放，**退出检测看到的是“没有泄漏”**，但实际上每进一次关卡就漏 64 KB。

### 6.2 方法二：区间快照 diff（游戏里最实用）

思路：给每次分配打上**单调递增的序号**，在一个“理论上应该回到原状”的时间点前后做对比：

```text
Mark = 当前序号          // 进关卡前（或者回到大厅后）
...进关卡、打一局、退出、回到大厅...
Report(seq >= Mark && 仍存活)   // 这段时间分配、但现在还活着的内存 = 嫌疑
```

**为什么要反复进出 N 次**：第一次进关卡，可能会合理地建立缓存（Shader 缓存、字体图集、对象池扩容），这些不是泄漏。**第 2～N 次每次都等量增长**的，才是泄漏。Demo 场景 3 的实测：

```text
== 场景 3：反复进出森林关卡 ==

  第 2 次进出后，存活内存变化 +65663 字节
  第 3 次进出后，存活内存变化 +65663 字节      ← 每次都等量增长，100% 是泄漏
```

现成的同类工具：MSVC 的 `_CrtMemCheckpoint / _CrtMemDifference`、Windows 的 **UMDH**（用 `gflags +ust` 开启分配栈记录，拍两次快照做对比）、UE 的 `memreport -full` 前后对比、Unity Memory Profiler 的快照对比。

> 游戏里天然的快照点：**大厅 → 对局 → 结算 → 回大厅**。回到大厅时，所有对局内的东西都应该被释放干净。

### 6.3 方法三：可达性分析（判定“真泄漏”）

LeakSanitizer（LSan）、Valgrind Memcheck 用的就是这种方式，思路类似 GC 的标记阶段：

1. **暂停所有线程**（stop-the-world）；
2. **根集**：所有线程的栈和寄存器、全局/静态数据段、TLS；
3. 把根集里每个对齐的 8 字节都当成“可能的指针”，如果它落在某个存活块的地址范围内，就标记这个块为可达，然后**递归扫描这个块的内容**；
4. 扫描结束后，**没有被标记的块就是真泄漏**。只被其他泄漏块引用的块，算作“间接泄漏”（LSan 的 Indirect leak，Valgrind 的 indirectly lost）。

这是**保守式扫描**，有两个局限：

- **漏报**：某个整数的值恰好等于某个块的地址，会被误认为是指针；
- **误报**：指针被编码过（tagged pointer、XOR 链表、压缩指针、用句柄或下标代替指针的 ECS/资源系统），扫描器认不出来；
- 而且它**原理上就抓不到逻辑泄漏**：缓存被全局变量引用着，是“可达”的。

### 6.4 方法四：增长趋势 / 存活年龄

适合长时间跑的压测：按调用点统计**存活块数随时间的斜率**，长期单调增长的调用点排在最前面；或者统计“在第 F 帧分配、至今仍存活、并且已经跨越了 N 次场景切换”的块。这种方式不需要人工选快照点，适合接进自动化测试。

### 6.5 对比总结

| 方法 | 真泄漏 | 逻辑泄漏 | 误报 | 开销 | 游戏里的定位 |
|---|---|---|---|---|---|
| 退出存活 | ✅ | ❌ | 多（全局对象） | 低 | 单元测试、工具程序 |
| **区间快照 diff** | ✅ | ✅ | 少（多次进出可消除缓存噪声） | 低 | **主力方案** |
| 可达性扫描 | ✅ 精确 | ❌ | 编码指针会误报 | 扫描时卡顿 | 夜间自动化、ASan 包 |
| 增长趋势 | ✅ | ✅ | 少 | 中 | 长时间挂机压测 |

## 8. 游戏客户端专项（加分项）

### 8.1 引擎托管对象的“引用泄漏”

- **UE 的 UObject**：由 GC 管理，`delete` 意义上不会泄漏，但会因为**被强引用而无法回收**：`UPROPERTY` 引用、`AddToRoot()` 之后忘了 `RemoveFromRoot()`、`TStrongObjectPtr`、静态容器持有、委托绑定没有解绑。排查工具：`obj list` 看对象数量变化，`obj refs name=xxx` 看引用链，`memreport -full` 前后对比，LLM（Low Level Memory Tracker）按标签统计，Unreal Insights 的 Memory 视图。
- **Unity / C#**：静态字段、事件订阅没有 `-=`、闭包捕获了 `this`、`Texture`/`AssetBundle` 没有 `Unload`。用 Memory Profiler 做两次快照对比，查看引用链。

### 8.2 Lua 泄漏

很多手游的业务逻辑写在 Lua 里，常见泄漏：

- 漏写 `local` 变成全局变量；
- 缓存 table 只增不删；
- 事件回调、定时器、闭包没有注销；
- **跨语言引用环**：Lua 通过 userdata 或 ref 持有 C++/C# 对象，C++/C# 又通过 `luaL_ref` 或委托持有 Lua 函数，两边的 GC 都认为对方还活着。

检测方法：

1. 自定义 `lua_Alloc`，按 `osize/nsize` 统计 Lua 堆大小，配合 `collectgarbage("count")` 看趋势；
2. **对象图快照 diff**：从 `_G` 和 registry 出发遍历所有 table、函数、userdata、upvalue，记录“对象 → 引用路径”，两次快照之间新增并且一直存活的对象，打印出它的引用链（例如 `_G.EventMgr.listeners[37].callback.upvalue.self`）。

### 8.3 显存和其他资源

- 显存不在 CPU 堆里，`operator new` 看不到。需要在 RHI 或图形 API 包装层统计 `CreateTexture/CreateBuffer/CreateRenderTarget` 和对应的释放，**用同一套“配对 + 调用栈 + 快照”的框架**，key 换成资源句柄即可。
- **资源管理器的引用计数不平衡**（AddRef/Release 不配对）：同样给每次 `AddRef` 和 `Release` 记录调用栈，泄漏时把“多出来的那次 `AddRef`”的栈打出来。
- 句柄、线程、Socket、文件、定时器等，思路相同。

### 8.4 移动端

- **看对指标**：iOS 看 `phys_footprint`（Jetsam 依据它判断是否杀进程），Android 看 PSS 和 Native Heap，而不是虚拟内存。
- 平台工具：Xcode Instruments 的 Allocations/Leaks、Memory Graph Debugger；Android Studio Memory Profiler（Native 部分基于 heapprofd）、Perfetto。
- 腾讯开源方案可以了解一下：**OOMDetector**（iOS，基于 `malloc_logger` 记录分配栈）、**Matrix**（iOS/Android 的性能监控框架，包含内存监控）。
- **线上方案**：只对少量灰度用户开启采样，设备端只上报“栈哈希 + 字节数”，服务器端聚合后再离线符号化，避免影响玩家体验和流量。

## 10. 配套 Demo 详解

### 10.1 实现了什么

`leak_tracker_demo.cpp`（约 470 行），单文件，覆盖了上面讲的核心机制：

| 模块 | 实现 |
|---|---|
| 采集 | 替换 10 个全局 `operator new/delete` 重载 |
| 防递归 | `RawAlloc<T>`（直接调用 `malloc`）+ `thread_local t_inHook` |

| 记录 | `unordered_map<void*, AllocInfo>`，`CaptureStackBackTrace` 只存 PC，FNV 哈希去重 |

### 10.3 输出里值得深挖的细节

1. **65663 字节是怎么来的？** 每次进出关卡泄漏的是：
   - 像素 buffer：`std::vector<unsigned char>(65536)`，实际分配 **65575** 字节。多出来的 39 字节，是因为 MSVC STL 对 ≥ 4096 字节的大块分配会额外申请 `32 - 1 + sizeof(void*)` 字节，用来做 32 字节对齐，并保存原始指针（`_Allocate_manually_vector_aligned`；定义了 `_DEBUG` 的 Debug CRT 下还会再多一个哨兵指针，变成 47 字节）；
   - `make_shared<Texture>` 的控制块 + `Texture` 对象：**72** 字节（一次分配）；
   - 全局缓存 vector 扩容带来的净增长：**16** 字节（一个 `shared_ptr` 的大小，旧 buffer 已经释放）；
   - 合计 65575 + 72 + 16 = **65663**。这说明工具统计的是**分配器实际收到的请求大小**，而不是 `sizeof`。
2. **28 万次分配只有 18 个唯一栈**：栈去重的收益非常明显。
3. **最后一个报告是“误报”的示范**：`main` 结束前，`g_TextureCache` 这个全局对象还活着，它持有的纹理会被报告出来。如果把报告放到全局析构之后，这部分反而会“消失”，**这恰恰证明了退出检测抓不到逻辑泄漏，必须靠场景 3 的区间快照**。
4. **32 倍开销**：主要来自 x64 上基于 unwind 表的栈回溯，这就是生产中要用帧指针回溯、采样、事件流的原因。

### 10.4 离“生产级”还差什么

- [ ] 平台级 `malloc/realloc/calloc` hook，覆盖第三方库
- [ ] C++17 对齐版 `operator new(size_t, std::align_val_t)`
- [ ] 分片锁 / TLS 缓冲 + 后台线程
- [ ] 帧指针回溯 + 采样
- [ ] 记录模块基址，支持离线符号化
- [ ] 事件流落盘 + PC 端可视化（调用树、火焰图、曲线）
- [ ] 在全局析构之后出最终报告，并支持白名单
- [ ] 帧号/场景切换事件，支持“存活年龄”分析

## 11. 面试官可能的追问

**Q1：重载 `operator new` 能抓到 `malloc` 吗？**
不能。`operator new` 只覆盖 C++ 的 `new` 表达式。C 代码、第三方库、`strdup` 之类的函数直接调用 `malloc`，需要在 `malloc` 层或系统 API 层（`HeapAlloc`、`mmap`）做 hook，或者在引擎分配器层统一入口。

**Q2：追踪器自己也要分配内存，怎么避免递归？**
两层保护：追踪器的容器用直接调用 `malloc` 的分配器（或者用预先 `VirtualAlloc`/`mmap` 的内存池）；再加 `thread_local` 重入标志，hook 里面再触发的分配直接放行，不做记录。

**Q3：为什么不在分配时直接把函数名、行号记下来？**
符号化非常慢（要查 PDB/DWARF，而且需要加锁），还会分配内存。运行时只存 PC，出报告时或离线再符号化；同时栈去重之后，每个唯一栈只需要符号化一次。

**Q4：工具开销太大，游戏卡得没法测怎么办？**
帧指针回溯替代 unwind；按字节采样；只追踪特定标签或者大于阈值的块；事件流模式，把分析挪到 PC 上。并且要说明采样的正确性：泄漏点会被持续执行，采样迟早会命中，统计值可以用权重还原。

**Q5：怎么区分“缓存”和“泄漏”？**
看**增长是否收敛**。缓存一般有上限，第一次进场景后就稳定了；泄漏是随着进出次数线性增长。所以要反复进出 N 次，只看第 2 次以后的增量。另外，缓存应该有明确的淘汰策略和上限，可以要求缓存模块打上专门的标签，在报告里单独展示。

**Q6：`shared_ptr` 循环引用能被检测到吗？**
引用计数本身发现不了（双方计数都是 1）。但从分配器的角度看，这两个块在快照 diff 里是“新增并且一直存活”的，一样会被报出来（Demo 场景 2）；可达性分析也能发现它们从根集不可达。修复用 `weak_ptr` 打破环。

**Q7：多线程下怎么设计？**
从全局锁 → 分片锁 → TLS 无锁缓冲 + 后台合并逐步演进。要注意跨线程的 `alloc/free` 顺序问题，事件需要带全局序号。出报告时持锁只做数据拷贝，耗时的符号化放在锁外。

**Q8：重复释放和野指针怎么检测？**
`free` 时查表找不到，就说明是重复释放或者野指针（Demo 的做法是报错并拦截，不真正 `free`）。更强的方案是 ASan 的**隔离区（quarantine）**：释放的内存不立刻复用，先放进一个 FIFO，并标记为不可访问，之后有人访问就能当场抓到 use-after-free。

**Q9：越界写怎么检测？**
三档方案：① **尾部哨兵**（Demo，释放时才能发现，开销最低）；② **页堆**（Windows `gflags /p /enable xxx.exe /full`，每个块放在页的末尾，后面紧跟一个不可访问的保护页，越界的瞬间就触发访问冲突，能拿到现场，但内存开销巨大）；③ **ASan shadow memory**（编译插桩，每次访存都检查，开销约 2 倍）。

**Q10：Release 包、玩家设备上能用吗？**
可以，但要“轻”：灰度开关、低采样率、设备端只记录栈哈希和字节数，服务器端聚合，再用对应版本的符号文件离线符号化。重点关注 OOM 前的最后一次快照（OOMDetector 就是这个思路）。

**Q11：内存一直涨，但工具说没有泄漏，可能是什么？**
① **内存碎片**：存活字节数稳定，但进程的提交内存（RSS/footprint）持续上涨，可以对比“分配器统计的存活量”和“操作系统看到的提交量”；② 分配器自己缓存不还给系统（各种 free list、tcmalloc/mimalloc 的线程缓存）；③ 不经过被 hook 的分配器的内存：显存、驱动内部内存、第三方 SDK、`mmap` 直接映射的文件、Lua/Mono 等 VM 的堆。

**Q12：如果让你在现有项目里落地，第一步做什么？**
先**定义快照点 + 加内存标签**：在大厅 ↔ 对局切换处打点，在各系统入口加标签，在引擎分配器入口加一层代理做统计（先不记栈，开销很低）。先看“哪个标签在每局之后都涨”，缩小范围后，再只对这个标签开启调用栈记录。**先粗后细，按需开栈**，这是在大项目里能真正落地的路线。

> 内存泄漏工具 = **拦截**（覆盖所有分配来源）+ **记录**（只存 PC、栈去重、序号与标签）+ **判定**（游戏里以“反复进出的区间快照 diff”为主，可达性分析为辅）+ **展示**（按调用点聚合、离线符号化、接进 CI）。真正的难点在于**开销控制**，以及游戏特有的**逻辑泄漏、资源泄漏和跨语言引用泄漏**。
