    CHAPTER 01

    一帧画面是怎么来的

    16.6 毫秒里，CPU 准备"画什么"，GPU 决定"每个像素长什么样"。

    本章目标

    1.1 两颗处理器的接力：CPU 和 GPU 怎样分工

    假设你在玩一局 MOBA，屏幕上有地图、10 个英雄、小兵、技能特效和 UI。每一帧，引擎都要回答两个问题：

    1. 画什么、按什么顺序画——这是 CPU 的工作。游戏线程更新逻辑（移动、技能、动画），渲染线程据此做视锥剔除、按材质排序、合批，再把"设置状态 + 绘制"翻译成图形 API 调用。
    2. 每个像素是什么颜色——这是 GPU 的工作。它接收命令，把成千上万个三角形变换、光栅化成几百万个像素，并为每个像素运行着色器。

    两者之间隔着一条命令缓冲（Command Buffer）：CPU 往里写命令，GPU 从里读命令，两边是异步的。CPU 调用 Draw 时 GPU 并不会马上开始画——命令只是被记录下来，稍后才被提交、执行。

    这张图有两个直接的工程含义：

    • 帧率取决于最慢的那条泳道。游戏线程慢叫"逻辑瓶颈"，渲染线程/驱动慢叫"CPU 渲染瓶颈"（通常是 Draw Call 太多），GPU 慢叫"GPU 瓶颈"（顶点、填充率或带宽）。优化之前必须先知道是哪一条——第 12 章专门讲定位方法。
    • CPU 读 GPU 的结果代价极高。如果 CPU 在帧 N+1 里同步读回帧 N 的渲染结果（比如 ReadPixels、遮挡查询立即取结果），就会让流水线"排空"：CPU 停下来等 GPU 画完，GPU 画完又等 CPU 发新命令。这就是为什么遮挡查询结果通常延迟一两帧使用。

    1.2 Draw Call：一条命令为什么会贵

    一次 Draw Call 就是 CPU 对 GPU 说"用当前的状态，画这些三角形"。真正贵的不是 Draw 这一下本身，而是它前面要准备的东西和驱动做的工作：

    开销来源具体是什么典型优化
    状态切换换 Shader 程序、混合/深度状态、渲染目标；驱动可能要重新编译/链接管线状态按材质/Shader 排序，减少 SetPass；DX12/Vulkan 预编译 PSO
    资源绑定绑定纹理、常量缓冲、顶点缓冲；上传每个物体的矩阵等常量SRP Batcher（常量常驻 GPU，只更新变化的部分）、Bindless
    驱动校验旧 API（GL/DX11）每次调用都要检查状态合法性、跟踪资源依赖换现代 API，命令缓冲多线程录制
    提交与同步命令缓冲刷新、用户态到内核态切换减少 flush，批量提交

    减少 Draw Call 的三种常见手段，省的东西各不相同：

    静态合批

    离线把共享材质的静态网格合并成一个大网格。省 Draw Call，代价是内存变大（每份实例的顶点都复制了一份）、无法单独剔除。

    动态合批

    每帧在 CPU 上把小网格的顶点变换到世界空间后拼起来。省 Draw Call，但CPU 要做顶点变换，只适合顶点很少的物体。

    GPU Instancing

    一次 Draw 画 N 份同一网格，每份的矩阵/颜色放在实例缓冲里，由顶点着色器用 SV_InstanceID 读取。适合草、树、小兵这种同网格大量重复的物体。

    SRP Batcher

    不减少 Draw Call 数量，而是让每个 Draw Call 变便宜：材质常量常驻显存，只在变化时更新，相同 Shader 变体的物体之间不再重复设置状态。

    ⚠️ 面试易错

    "合批就是为了减少 Draw Call"只说对了一半。更准确的说法是：合批是为了减少 CPU 端每次绘制的准备开销（主要是状态切换和常量上传）。在 DX12/Vulkan/Metal 下单次 Draw 本身已经很便宜，真正的成本更多在 SetPass（换材质/Shader）。所以面试官常追问："SRP Batcher 不减少 Draw Call，为什么也能提速？"——答案就是它减少的是每次 Draw 之间的状态设置。

    1.3 GPU 为什么快：成千上万个"慢而简单"的线程

    CPU 为了让一个线程尽可能快，花大量晶体管做分支预测、乱序执行和大缓存；GPU 反其道而行：把晶体管堆成大量简单的计算单元，同时跑成千上万个线程，用"线程多"来掩盖"内存慢"。

    这个模型直接解释了 Shader 编写里的几条经验：

    • 分支发散（Divergence）：同一 Warp 的线程如果走了 if 的不同分支，硬件只能两条分支都执行，用掩码屏蔽不该写结果的线程。所以"按像素随机的分支"很贵，而"按材质/按 Draw Call 一致的分支"（uniform branch）几乎免费。
    • 寄存器压力与 Occupancy：一个复杂 Shader 用了很多寄存器，SM 上能同时驻留的 Warp 就变少，掩盖延迟的能力就下降。这是"Shader 变复杂，即使 ALU 不是瓶颈也变慢"的常见原因。
    • 像素着色器按 2×2 Quad 打包：一个 Warp 的 32 个线程其实是 8 个 2×2 像素块。第 6 章会看到，这是导数 ddx/ddy 能工作的前提，也是小三角形浪费的根源。
    🧠 深入：统一着色器架构

    早期 GPU（DX9 时代）有专门的"顶点单元"和"像素单元"，场景顶点多时像素单元闲着，反之亦然。从 DX10 / Xbox 360 开始，GPU 改为统一着色器架构：同一批计算单元按需运行顶点、像素、计算着色器。今天说"管线有 VS、PS 两个阶段"指的是逻辑阶段，物理上它们跑在同一批 SM 上。

    1.4 可编程与固定功能：哪些能写代码，哪些只能配置

    回到图 0-1，管线里的阶段分两类：

    类型阶段你能控制什么
    可编程顶点着色器、（外壳/域/几何着色器）、像素着色器、计算着色器；新架构下的任务/网格着色器任意代码：变换、光照、采样、discard、写深度
    固定功能、可配置输入装配、裁剪、透视除法、视口变换、背面剔除、光栅化、深度/模板测试、混合只能设置状态：剔除模式、深度函数、混合因子、模板操作、多重采样数……

    固定功能阶段之所以不开放编程，是因为它们是极高频、极规则的操作（每秒数十亿次的覆盖测试、深度比较），做成专用硬件比通用 ALU 快一到两个数量级、也更省电。这也解释了为什么"在 PS 里 discard"或"在 PS 里写深度"会破坏性能：你让一个本可以在固定硬件里提前完成的决定，被迫推迟到可编程阶段之后（第 8 章）。

    1.5 两种画法：光栅化与光线追踪

    光栅化的核心优势是数据访问高度规则：一个三角形覆盖的像素在屏幕上是连续的一片，访问的纹理也在一小块区域里，缓存命中率极高；光线追踪的光线会四散到场景各处，访存随机。这正是光栅化能在手机上以 60fps 跑的原因，也是本书只讲光栅化管线的原因。

    🎮 游戏实战：为什么 MOBA 手游这么在意 Overdraw 和带宽

    MOBA 镜头是固定俯视角，屏幕中央经常同时出现十几个技能特效叠在一起，团战时半透明粒子的 Overdraw 能达到十几层；而手机 GPU 的带宽只有桌面显卡的几分之一、还要和 CPU 共享、发热就降频。所以手游渲染优化的第一优先级通常是"少写像素、少读写显存"，而不是"少算几条 ALU 指令"。第 10 章的 TBR 架构和第 12 章的优化清单都是从这个约束出发的。

    本章小结
    • CPU 决定画什么（剔除、排序、录制命令），GPU 决定每个像素长什么样；两者通过命令缓冲异步协作，通常错开 1～2 帧。
    • 帧率由最慢的泳道决定；CPU 同步读 GPU 结果会让流水线排空。
    • Draw Call 贵在状态切换、资源绑定和驱动校验；静态合批、动态合批、Instancing、SRP Batcher 省的东西各不相同。
    • GPU 用 SIMT + 大量驻留 Warp 来掩盖访存延迟；分支发散和寄存器压力是 Shader 性能的两大隐形杀手。
    • 固定功能阶段（光栅化、深度测试、混合）比可编程阶段快得多，破坏它们的"提前决定"会付出代价。
    自测：GPU Instancing 和静态合批都能减少 Draw Call，什么情况下选哪个？

    看是否是同一个网格和内存预算。大量重复的同一网格（草、树、小兵）用 Instancing：只存一份顶点，实例数据很小，还能逐实例剔除。不同网格但同材质的静态物体（场景摆件）用静态合批：能合成一次绘制，但要付出顶点数据复制的内存，且合并后整体剔除。

    自测：为什么说"一个 Shader 里写了 if 不一定慢"？

    分支的代价取决于同一 Warp 内的线程是否走同一条路。如果条件来自常量（材质参数、关键字），整个 Draw Call 的所有线程走同一分支，只执行一侧，几乎没有代价；如果条件按像素随机变化（例如依赖噪声纹理），同一 Warp 内两侧分支都要执行，代价接近两侧之和。

    坐标空间与变换

    一个顶点要换五次"身份证"：局部、世界、观察、裁剪、屏幕。

    本章目标

    • 能手推 LookAt 矩阵，能证明法线要用"模型矩阵的逆转置"

    2.1 五个空间，四次变换

    为什么要分这么多空间，而不是一步到位？因为每个空间都有它最方便做的事：

    • 局部空间：美术建模、骨骼蒙皮都在这里定义，一份网格可以被摆放到场景里任意多次（实例化的前提）。
    • 世界空间：光源、碰撞、寻路都用它；光照计算常在这里做（也可以在观察空间做）。
    • 观察空间：相机固定在原点、看向固定方向，投影公式就变得很简单；深度就是 −z。
    • 裁剪空间：视锥体被变成一个"规整"的形状，判断"在不在视野里"只需要比较 |x| ≤ w。
    • 屏幕空间：光栅化在这里做，单位是像素。

    2.2 齐次坐标：为什么用 4 个数表示 3D 点

    3×3 矩阵能表示旋转和缩放，但表示不了平移——因为平移不是线性变换（它把原点移走了）。给坐标加一个分量 w，就能把平移写进矩阵乘法里：

    T · p = ⎡1 0 0 tx⎤ ⎡x⎤　 ⎡x + tx⎤
    　　　　⎢0 1 0 ty⎥ ⎢y⎥ = ⎢y + ty⎥
    　　　　⎢0 0 1 tz⎥ ⎢z⎥　 ⎢z + tz⎥
    　　　　⎣0 0 0 1 ⎦ ⎣1⎦　 ⎣　1　⎦

    这样做还有两个额外的好处：

    点 vs 方向

    点写成 (x,y,z,1)，方向（法线、光照方向、速度）写成 (x,y,z,0)。平移项乘以 w=0 后消失——方向不应该被平移，齐次坐标自动保证了这一点。

    透视投影

    透视的本质是"除以距离"，这不是线性运算。齐次坐标的约定是 (x,y,z,w) 表示 3D 点 (x/w, y/w, z/w)，于是投影矩阵只需要把距离放进 w，除法交给硬件。这是第 3 章的主角。

    2.3 模型矩阵：先缩放，再旋转，最后平移

    模型矩阵通常由 TRS 组合而成：M = T · R · S。在列向量约定下矩阵从右往左作用，所以顺序是先缩放 → 再旋转 → 最后平移。顺序不能换：如果先平移再旋转，物体会绕世界原点"公转"而不是绕自己的中心"自转"。

    实测程序里 E1 用的模型矩阵是 translate(0,0,-5) * rotY(30°)，也就是"先绕自己的 Y 轴转 30°，再放到 z=-5 处"。

    2.4 观察矩阵：把相机搬到原点

    观察矩阵 V 是"相机在世界中的变换"的逆：相机往右移 1 米，等价于整个世界往左移 1 米。最常用的构造方式是 LookAt：给定相机位置 eye、目标点 at 和大致的上方向 up，先求出相机的三个正交基，再拼成旋转部分，平移部分是 −(基·eye)：

    soft_raster.cpp · lookAt（右手系，相机看向 -Z）
    static M4 lookAt(V3 eye, V3 at, V3 up) {
    V3 f = nrm(at - eye);          // 前方（forward）
    V3 s = nrm(cross(f, up));      // 右方（side）= f × up
    V3 u = cross(s, f);            // 真正的上方，保证三者正交
    M4 r = ident();
    r.m[0][0] = s.x;  r.m[0][1] = s.y;  r.m[0][2] = s.z;  r.m[0][3] = -dot(s, eye);
    r.m[1][0] = u.x;  r.m[1][1] = u.y;  r.m[1][2] = u.z;  r.m[1][3] = -dot(u, eye);
    r.m[2][0] = -f.x; r.m[2][1] = -f.y; r.m[2][2] = -f.z; r.m[2][3] = dot(f, eye);  // 前方映射到 -Z
    return r;
}

    为什么旋转部分可以直接"把基向量写成行"？因为相机的世界矩阵旋转部分是以 s、u、−f 为列的正交矩阵，正交矩阵的逆就是它的转置，转置后基向量就变成了行。这样省掉了一次通用矩阵求逆。

    ⚠️ 面试易错：up 和视线平行

    如果相机正好朝正上方或正下方看，cross(f, up) 的长度为 0，归一化得到 NaN，整个画面消失或闪烁。俯视角游戏（MOBA、RTS）的相机经常接近这个角度，工程上的做法是：检测到 |f·up| 接近 1 时换一个备用 up（例如 (0,0,1)），或者直接用欧拉角/四元数构造相机矩阵。

    2.5 法线为什么要用逆转置矩阵

    如果模型矩阵包含非均匀缩放（比如 x 方向拉长 2 倍），直接用 M 变换法线，法线就不再垂直于表面了：

    证明只要一行。设表面切线 t 与法线 n 垂直：nᵀt = 0。切线跟着表面走，变换后 t′ = M t。要找矩阵 G 使 n′ = G n 仍然垂直于 t′：

    n′ᵀ t′ = (G n)ᵀ (M t) = nᵀ (GᵀM) t = 0　⇐　GᵀM = I　⇒　G = (M⁻¹)ᵀ
    • 如果 M 只有旋转和均匀缩放，(M⁻¹)ᵀ 与 M 只差一个标量，归一化后方向相同，可以直接用 M（实测程序 E13 里的 stdVS 就是这么做的）。
    • 只需要取左上角 3×3（法线是方向，不受平移影响）。
    • 引擎通常在 CPU 端预先算好"世界到物体"矩阵（Unity 的 unity_WorldToObject），Shader 里用它的转置去乘法线。

    2.8 游戏实战：大世界的浮点精度

    float 只有 24 位有效数字。在距离原点 10 公里的地方，float 能表示的最小间隔约为 1 毫米；到 100 公里就是 8 毫米左右。如果顶点着色器里先算 world = M·p 再算 V·world，两个很大的数相减（物体位置 − 相机位置）会丢掉大量精度，表现为远离原点时模型抖动、顶点颤动。

    🎮 游戏实战：相机相对渲染（Camera-Relative Rendering）

    做法是在 CPU 上用 double 计算 物体位置 − 相机位置，把结果（一个不大的数）放进模型矩阵，然后观察矩阵里只保留旋转、不带平移。这样 GPU 上所有坐标都是"相对相机"的小数值。UE5 的大世界坐标（LWC）、Unity HDRP 的 Camera Relative Rendering 都是这个思路。MOBA 地图只有一两百米见方，一般遇不到这个问题，但开放世界、飞行类游戏必须处理。

    本章小结
    • 链路：局部 →(M) 世界 →(V) 观察 →(P) 裁剪 →(÷w) NDC →(视口) 屏幕；VS 只负责到裁剪空间。
    • 齐次坐标让平移和透视都能用矩阵表达；点 w=1、方向 w=0。
    • TRS 顺序是先缩放、再旋转、后平移（列向量约定下写作 T·R·S）。
    • 观察矩阵是相机世界矩阵的逆，LookAt 利用正交矩阵"逆 = 转置"直接拼出来。
    • 法线变换用 (M⁻¹)ᵀ，因为要保持 nᵀt=0；只有旋转+均匀缩放时可以直接用 M。
    • 行/列向量是数学约定，行/列主序是存储约定，两者无关。
    自测：骨骼蒙皮在哪个空间、哪个阶段做？

    通常在顶点着色器里、局部空间做：每个顶点按权重混合若干根骨骼的"蒙皮矩阵"（骨骼当前姿态矩阵 × 绑定姿态的逆矩阵），得到动画后的局部坐标，再乘 MVP。法线同样要用蒙皮矩阵变换（骨骼矩阵一般无非均匀缩放，可直接用）。也有引擎用计算着色器预先蒙皮，结果写入缓冲供多个 Pass 复用。

    自测：为什么 W 分量对方向向量是 0？如果你不小心传了 1 会怎样？

    方向只表示"朝向"，与位置无关，平移不应改变它。w=0 时平移列乘以 0 被消掉。如果传了 1，光照方向会被加上物体的世界位置，在原点附近看起来正常、远离原点后光照方向越来越歪——这是一个很典型的"只在某些地方出错"的 Bug。

    3.1 视锥体：正交投影与透视投影

    3.2 推导透视投影矩阵

    在观察空间里，相机在原点、看向 −Z。一个点 (x, y, z) 投影到距离为 n 的近平面上，由相似三角形：

    xproj = n · x / (−z)　　　yproj = n · y / (−z)

    除以 −z 不是线性运算，矩阵做不到。办法是：让矩阵输出 w = −z，把除法推迟给硬件。所以投影矩阵的第 4 行是 (0, 0, −1, 0)。

    x 和 y 再乘一个缩放，使视野边缘落到 ±1：设垂直视场角为 fovy、宽高比为 aspect，令 t = 1 / tan(fovy/2)，则第 1、2 行是 (t/aspect, 0, 0, 0) 和 (0, t, 0, 0)。

    最后是 z。我们也需要深度用于遮挡判断，而且希望它在除以 w 之后落在固定区间。z 只能写成 zclip = A·z + B（第 3 行是 (0,0,A,B)），于是：

    zndc = (A·z + B) / (−z) = −A − B / z　　令 z=−n ⇒ 0，z=−f ⇒ 1（D3D 约定）

    解这两个方程得 A = f/(n−f)，B = n·f/(n−f)。整理得到右手系、深度范围 [0,1] 的透视矩阵（实测程序 perspective() 的 DM_D3D 分支）：

    P = ⎡ t/aspect　0　　0　　　0　　⎤
    　　⎢ 0　　　　t　　0　　　0　　⎥
    　　⎢ 0　　　　0　 f/(n−f)　 nf/(n−f) ⎥
    　　⎣ 0　　　　0　 −1　　　　0　　⎦
    soft_raster.cpp · 四种深度约定的投影矩阵（只有第 3 行不同）
    static M4 perspective(float fovyDeg, float aspect, float n, float f, int mode) {
    M4 r{};
    float t = 1.f / tanf(fovyDeg * (float)M_PI / 360.f);
    r.m[0][0] = t / aspect; r.m[1][1] = t; r.m[3][2] = -1;  // w_clip = -z_view
    switch (mode) {
    case DM_D3D:    r.m[2][2] = f / (n - f);       r.m[2][3] = n * f / (n - f); break;  // near->0, far->1
    case DM_REV:    r.m[2][2] = n / (f - n);       r.m[2][3] = n * f / (f - n); break;  // near->1, far->0
    case DM_GL:     r.m[2][2] = (f + n) / (n - f); r.m[2][3] = 2 * f * n / (n - f); break;  // [-1,1]
    case DM_REVINF: r.m[2][2] = 0;                 r.m[2][3] = n; break;  // far->∞，z_ndc = n / d
    }
    return r;
}

    3.3 一个关键事实：NDC 深度是"距离倒数"的线性函数

    把上面的 zndc 换成距离 d = −z：

    zndc(d) = −A + B/d　＝　a + b · (1/d)

    深度值和 1/d 成线性关系，而不是和 d 成线性关系。这个看似不起眼的事实，在后面会被引用三次：

    ① 深度可以在屏幕空间线性插值

    在屏幕空间里，1/w 是线性变化的（第 6 章证明），所以 zndc 也是。硬件可以直接用重心坐标线性插值深度，不需要透视校正。

    ② 属性插值必须做透视校正

    反过来，uv、颜色这些属性是在三维空间里线性分布的，在屏幕空间就不是线性的，必须借助 1/w 校正（第 6 章 E5）。

    ③ 深度精度极不均匀

    1/d 在近处变化剧烈、远处几乎不变，深度值大量集中在近平面附近。E6 实测：near=0.1 时，一半的深度值花在了前 0.2 米（第 8 章）。

    3.4 为什么必须在除以 w 之前裁剪

    直觉上，先除以 w 得到 NDC，再把超出 [−1,1] 的部分切掉，似乎更简单。但这在有顶点位于相机背后时会出大问题：

    • 相机背后的点 z>0，于是 w = −z < 0。除以负数会让 x、y 变号——点被"翻"到屏幕另一侧。
    • 恰好在相机平面上的点 w = 0，除法直接得到无穷大。

    实测程序 E2 构造了这样一个三角形：A、B 在相机前方 2 米，C 在相机背后 1 米（想象一块从你脚下延伸到前方的地面）：

    在齐次空间里，"点在视锥内"可以写成 6 个不需要除法的不等式：

    −w ≤ x ≤ w　　−w ≤ y ≤ w　　0 ≤ z ≤ w（D3D/Vulkan/Metal）或 −w ≤ z ≤ w（OpenGL）

    每个不等式都是 4D 空间里的一个"平面"，裁剪就是用 Sutherland–Hodgman 算法依次用平面切多边形：保留在内侧的顶点，对跨越平面的边按有符号距离插值出新顶点。一个三角形被一个平面切，最多变成四边形；被 6 个平面切，最多变成 9 边形，再拆成扇形三角形送去光栅化。

    soft_raster.cpp · 近平面裁剪（Sutherland–Hodgman，单平面）
    static float nearDist(int mode, const V4& c) {        // 有符号距离：>=0 在内侧
    switch (mode) { case DM_D3D: return c.z;         // 0 <= z
                    case DM_GL:  return c.z + c.w;   // -w <= z
                    default:     return c.w - c.z; } // Reversed-Z：z <= w
}
static int clipNear(const State& s, const VOut* in, VOut* out, int na) {
    int n = 0;
    for (int i = 0; i < 3; i++) {
        const VOut& a = in[i]; const VOut& b = in[(i + 1) % 3];
        float da = nearDist(s.clip, a.c), db = nearDist(s.clip, b.c);
        if (da >= 0) out[n++] = a;                                       // a 在内侧，保留
        if ((da >= 0) != (db >= 0)) out[n++] = lerpV(a, b, da / (da - db), na);  // 边跨越平面，插出交点
    }
    return n;   // 0、3 或 4 个顶点
}
    🧠 深入：为什么在 4D 里线性插值是对的

    裁剪空间到观察空间之间只差一个线性变换（投影矩阵可逆），所以观察空间里的直线在裁剪空间里仍是直线，在裁剪空间里对 (x,y,z,w) 和所有属性按同一个 t 线性插值，得到的就是三维空间中那条边上的真实点。一旦除以 w，这条性质就没有了——这又是"必须在除法之前裁剪"的一个理由。

    3.5 保护带：GPU 其实很少真的裁 x/y

    注意 E2 输出里的 P2：屏幕坐标 (2450, 1739)，远远超出 640×360 的屏幕。实测程序并没有对 x/y 平面做裁剪，而是让光栅化器直接遍历被钳制到屏幕范围内的包围盒——超出屏幕的像素根本不会被访问。

    真实 GPU 也是这么做的，叫保护带（Guard Band）：光栅化器的定点坐标范围远大于屏幕（例如 ±32K 像素），只要三角形落在这个大范围内，就不需要真正生成新顶点，靠 Scissor 和包围盒丢掉屏幕外的部分即可。真正必须裁剪的只有：

    • 近平面：因为 w≤0 会导致除法翻转或除零，保护带帮不了；
    • 超出保护带范围的极大三角形（定点数会溢出）；
    • 远平面（可选，D3D 有 DepthClipEnable 开关；关掉时叫"深度钳制"，阴影渲染常用来避免投射体被远/近平面切掉）。
    ✅ 面试答法

    问"裁剪是怎么做的"，可以分三层答：①在哪：在齐次裁剪空间、透视除法之前；②为什么：避免 w≤0 导致的翻转和除零，且 4D 空间插值保持线性；③实际硬件：x/y 依赖保护带 + 包围盒钳制，真正生成新顶点的只有近平面（以及超出保护带的情况），因为裁剪会改变图元数量、打断流水，硬件尽量避免。

    3.6 视口变换与各 API 的差异

    3.7 游戏实战：近平面和 FOV 怎么设

    近平面不能太小

    深度精度主要由 near 决定（第 8 章）：E6 实测中 near 从 0.1 改成 1.0，1000 米处的 Z-Fighting 从 30.5% 降到 0%。第一人称游戏常设 0.01～0.1，第三人称/俯视角可以设到 0.3～1。

    近平面不能太大

    太大时相机贴近墙壁或角色会被"切开"（穿模）。第一人称的手臂/武器经常用单独的相机或单独的投影矩阵渲染。

    宽屏适配

    固定垂直 FOV、让水平 FOV 随宽高比变大（Hor+），宽屏玩家能看到更多。MOBA 这类竞技游戏会限制最大视野，避免超宽屏获得信息优势。

    正交相机

    UI、小地图、平行光阴影都用正交投影。正交投影 w 恒为 1，深度与距离线性相关，精度均匀，不需要透视校正。

    本章小结
    • 透视投影矩阵用第 4 行 (0,0,−1,0) 把距离放进 w，除法由硬件完成；x、y 由 fovy 和 aspect 缩放，z 的两个系数由"near→0、far→1"解出。
    • NDC 深度是 1/d 的线性函数：所以深度能在屏幕空间线性插值、属性插值需要透视校正、深度精度集中在近处。
    • 裁剪必须在齐次空间、除以 w 之前：避免 w<0 翻转和 w=0 除零；4D 中线性插值仍正确。
    • 硬件依赖保护带，x/y 基本不真正裁剪，近平面才必须裁。
    • D3D/Vulkan/Metal 深度 [0,1]，GL 默认 [−1,1]；Vulkan NDC y 向下。
    自测：正交投影需要透视除法吗？深度精度有什么特点？

    正交投影矩阵的第 4 行是 (0,0,0,1)，w 恒为 1，透视除法相当于什么都没做；深度与观察空间 z 呈线性关系，精度在 near 到 far 之间均匀分布。所以平行光阴影贴图通常用正交投影，精度问题比透视的聚光灯阴影小，主要矛盾是"覆盖范围 vs 分辨率"（级联阴影 CSM 就是为此而生）。

    自测：一个三角形三个顶点都在视锥外，它一定看不见吗？

    不一定。三个顶点分别在左、右、上三个平面外侧时，三角形的中间部分仍可能横穿视锥。只有三个顶点都在同一个平面外侧时才能直接剔除（这就是实测程序里 clipOut 的判断条件：三个顶点都在近平面外）。视锥剔除包围盒时也是同理。

    本章目标

    4.1 输入装配：从显存里读出顶点

    一个网格在显存里通常由两块数据组成：

    • 顶点缓冲（VB）：每个顶点的属性——位置、法线、切线、uv、颜色、骨骼索引和权重等。布局可以交错（一个顶点的所有属性挨着放，AoS）也可以分流（每种属性一个流，SoA）。只画深度的 Pass 只需要位置，把位置单独放一个流可以减少带宽——这是很多引擎把 Position 单独成流的原因。
    • 索引缓冲（IB）：每 3 个索引组成一个三角形（Triangle List）。16 位索引最多引用 65536 个顶点，大网格要用 32 位或拆成多段。

    输入装配（IA）阶段按照"输入布局"（Input Layout / Vertex Descriptor）解析这两块数据，把顶点送进顶点着色器。

    4.2 顶点着色器与顶点缓存：为什么要用索引

    顶点着色器对每个顶点运行一次，最少要输出裁剪空间位置 SV_Position，以及要传给像素着色器的插值属性（varyings）。

    一个最小的顶点着色器（HLSL）
    cbuffer PerObject { float4x4 _MVP; float4x4 _ObjectToWorld; float4x4 _WorldToObject; };
struct VSIn  { float3 pos : POSITION; float3 nrm : NORMAL; float2 uv : TEXCOORD0; };
struct VSOut { float4 posCS : SV_Position; float3 nrmWS : TEXCOORD0; float2 uv : TEXCOORD1; };

VSOut VS(VSIn v) {
    VSOut o;
    o.posCS = mul(_MVP, float4(v.pos, 1));                          // 裁剪空间，交给硬件裁剪与 ÷w
    o.nrmWS = normalize(mul(v.nrm, (float3x3)_WorldToObject));      // 行向量乘 = 乘以逆矩阵的转置
    o.uv    = v.uv;
    return o;
}

    一个封闭网格里，每个顶点平均被 5～6 个三角形共享。如果直接用三角形列表把每个三角形的 3 个顶点都存一份，顶点着色器要做 3 倍于"顶点数"的工作。索引缓冲配合 GPU 的Post-Transform 顶点缓存解决这个问题：GPU 记住最近处理过的若干个顶点索引的输出，遇到重复索引直接复用结果。

    衡量缓存效率的指标叫 ACMR（平均每个三角形的缓存未命中数）：理想的规则网格接近 0.5，完全随机的索引顺序接近 3。离线的网格优化工具（如 meshoptimizer、Forsyth 算法）会重排三角形顺序，让共享顶点的三角形挨在一起提交。

    ⚠️ 面试易错：立方体为什么是 24 个顶点而不是 8 个

    "顶点"在 GPU 眼里是所有属性的组合，而不只是位置。立方体的一个角被三个面共享，但三个面的法线（和 uv）不同，所以要拆成 3 个顶点：8×3=24。同理，模型的 UV 接缝、硬边（法线不连续处）都会让顶点数增加。美术报给你的"面数"和引擎统计的"顶点数"差很多，原因就在这里。

    4.3 可选的几何阶段：曲面细分、几何着色器、Mesh Shader

    阶段能做什么代价/现状
    曲面细分（Hull Shader → Tessellator → Domain Shader）在 GPU 上把粗网格细分成细网格，配合位移贴图做地形、海面；按距离自适应细分小三角形会让光栅化和 Quad 效率急剧下降（第 6 章 E8）；移动端支持差、功耗高
    几何着色器（GS）以图元为单位输入，可以输出 0～N 个新图元：广告牌扩展、阴影体、单 Pass 渲染立方体贴图输出数量不定，硬件难以并行，普遍很慢；Metal 根本不支持。现代做法改用计算着色器或 Mesh Shader
    任务/网格着色器（Task/Amplification + Mesh Shader）用类似计算着色器的方式直接生成"小块网格"（Meshlet，约 64 顶点 / 126 三角形），并在 GPU 上逐 Meshlet 做视锥/背面/遮挡剔除DX12 Ultimate / Vulkan 扩展 / Metal 3；UE5 Nanite 思路的硬件化。替代 IA + VS + GS

    4.4 图元装配与背面剔除

    顶点着色完毕，经过裁剪和透视除法，3 个顶点被组装成一个屏幕空间三角形。下一步是背面剔除：一个封闭物体背对相机的那一半表面一定被正面挡住，没必要光栅化。

    "背面"怎么判定？约定从外面看三角形顶点是逆时针（CCW，GL/本书默认）或顺时针（CW，D3D 默认）排列的为正面。投影到屏幕后，背面三角形的绕序会反过来——所以只需要计算屏幕空间的有符号面积：

    2A = (x₁ − x₀)(y₂ − y₀) − (y₁ − y₀)(x₂ − x₀)　　符号决定正反面，A = 0 为退化三角形
    soft_raster.cpp · rasterTri 开头：用定点坐标算有符号面积，做背面剔除
    i64 area = (X[1] - X[0]) * (Y[2] - Y[0]) - (Y[1] - Y[0]) * (X[2] - X[0]);
if (area == 0) { T.st.degenerate++; return; }        // 零面积（包括被吸附到同一点的微小三角形）
bool front = area < 0;  // NDC 中逆时针 = 屏幕(y 向下)中有符号面积为负
if (s.cull && !front) { T.st.culled++; return; }

    为什么不用"法线点乘视线"判断？在透视投影下，同一个三角形上不同点看过去的视线方向不同，用某一个点的视线判断可能出错；而屏幕空间面积的符号是精确的（它就是"投影之后这个三角形朝哪边"），而且光栅化本来就要算这个面积（第 5 章的边函数），几乎零额外开销。

    • 小兵和野怪：同一模型大量重复，适合 GPU Instancing；骨骼动画则用 GPU 蒙皮或把动画烘焙进纹理（Vertex Animation Texture / 骨骼矩阵纹理），让 Instancing 不受"每个实例动画不同"的限制。

    自测：模型导入后有一半的面"消失"了，可能是什么原因？

    最常见的是绕序或手性不一致：建模软件和引擎的正面绕序约定不同，或者模型做了负缩放（镜像）——负缩放会翻转所有三角形在屏幕上的绕序，导致正面被当成背面剔除。引擎通常检测模型矩阵行列式的符号，为负时自动翻转剔除模式。另一个原因是法线朝内（建模时翻转了法线）。

    自测：为什么几何着色器慢，而 Mesh Shader 快？

    几何着色器每个输入图元可以输出不定数量的图元，硬件必须保持输出顺序与输入一致、预留最坏情况的输出缓冲，导致并行度低、片上存储压力大。Mesh Shader 以"工作组"为单位一次性生成一个固定上限的小网格，模型和计算着色器一样规则，可以充分并行，还能在生成前就剔除整个 Meshlet。

    5.1 光栅化在回答什么问题

    光栅化的输入是一个屏幕空间三角形（三个顶点的浮点坐标），输出是一组片元（Fragment）——"这个像素被这个三角形覆盖了，它的深度和插值属性是多少"。

    "覆盖"的标准定义是：像素的采样点落在三角形内部。不开 MSAA 时，每个像素只有一个采样点，就在像素中心 (x+0.5, y+0.5)。三角形哪怕盖住了一个像素 49% 的面积，只要没盖住中心，这个像素就不算覆盖——这就是锯齿（几何走样）的来源。

    5.2 边函数：用三个半平面圈出三角形

    对有向边 a→b 和任意点 p，定义边函数：

    Eab(p) = (b.x − a.x)(p.y − a.y) − (b.y − a.y)(p.x − a.x)

    它是向量 ab 与 ap 的二维叉积，有三层含义：

    ① 半平面测试

    E > 0 表示 p 在边的一侧，E < 0 在另一侧，E = 0 恰好在边上。三条边的 E 同号 ⇔ p 在三角形内。

    ② 面积

    Eab(p) 等于三角形 abp 面积的 2 倍（有符号）。把 p 换成第三个顶点 c，就得到整个三角形的 2 倍面积——也就是第 4 章背面剔除用的那个数。

    ③ 重心坐标

    Ebc(p)/Ebc(a) 正是 p 相对顶点 a 的重心坐标 λa。光栅化算出来的边函数值，插值时直接复用（第 6 章）。

    实测程序的光栅化内循环就是这三个边函数（为了可读性没有写成增量形式）：

    soft_raster.cpp · rasterTri 内循环（每像素、每采样点）

    5.3 定点亚像素：为什么不直接用浮点数

    GPU 在三角形设置阶段会把顶点的屏幕坐标吸附（snap）到一个定点网格上：D3D11 要求 8 位亚像素精度，即每个像素被细分为 256×256 个格子，坐标用整数表示。这样做有三个理由：

    1. 精确：边函数变成整数乘法和加法，结果没有舍入误差。共享同一条边的两个三角形，它们对这条边计算的 E 值恰好互为相反数，不会出现一个说"在内"、另一个也说"在内"（或都说"在外"）的情况——这叫水密（Watertight）。
    2. 便宜：整数加法器比浮点加法器小得多、快得多。
    3. 确定：结果不依赖运算顺序，同一个三角形每次光栅化结果完全一致——这是深度 EQUAL 测试（Z-Prepass）能工作的前提。

    5.4 Top-Left 规则：边上的像素归谁

    定点数解决了"算得准"，但还有一个逻辑问题：采样点恰好落在共享边上（E = 0）时，这个像素归哪个三角形？

    • 如果"E ≥ 0 就算覆盖"，两个三角形都会画它——重复画（半透明叠两次、模板计数加两次）。
    • 如果"E > 0 才算覆盖"，两个三角形都不画它——漏画（一条缝）。

    D3D 和 OpenGL 采用 Top-Left 规则：E = 0 的采样点只有在上边或左边上才算覆盖。

    • 上边：完全水平、且三角形其余部分在它下方的边；
    • 左边：三角形左侧的边（沿顺时针绕行时向上走的边）。

    一条共享边对一个三角形是"左边"，对另一个三角形必然是"右边"，所以 E=0 的像素恰好只归其中一个。实现上非常简单：对不是上边/左边的边，在比较前给 E 减去 1（定点最小单位），把 E ≥ 0 变成 E > 0：

    soft_raster.cpp · Top-Left 偏置（屏幕 y 向下、面积已调整为正）
    auto isTL = [&](int a, int b) { i64 dx = X[b] - X[a], dy = Y[b] - Y[a];
                                 return (dy == 0 && dx > 0) || dy < 0; };   // 上边：水平且向右；左边：向上
i64 b0 = (s.topLeft && !isTL(1, 2)) ? -1 : 0;

    5.7 游戏实战：光栅化相关的几个工程问题

    模型"闪点"

    相邻三角形之间偶尔漏一个像素，通常不是光栅化器的问题（硬件是水密的），而是两个三角形的共享顶点坐标不完全相同：比如 LOD 接缝、地形块之间顶点高度不一致、顶点着色器里对同一顶点算出了不同结果（不同的计算顺序、precise 缺失）。

    细长三角形

    边函数测试浪费多、2×2 Quad 效率低（E8 实测只有约 48%），还容易产生插值走样。建模时避免长条三角形，程序生成网格时注意剖分方式。

    保守光栅化

    只要三角形和像素有任何重叠就算覆盖（而不只看中心）。用于体素化（GI）、光源分块剔除、遮挡剔除的软件光栅等"宁可多、不可漏"的场景。

    CPU 软件光栅

    很多引擎在 CPU 上跑一个低分辨率、只写深度的软件光栅器做遮挡剔除（如 Intel 的 Masked Occlusion Culling），原理正是本章的边函数 + 分块。

    本章小结
    • 覆盖 = 采样点（默认像素中心）落在三角形内；部分覆盖但没盖住中心的像素不算，这是几何走样的根源。
    • 边函数 E 是二维叉积：同号即在内；它是线性函数，可增量计算、可整块判断；它还直接给出重心坐标。
    • 顶点吸附到定点亚像素网格（8 位），使边函数精确、水密、确定；E4 实测浮点边函数在大坐标下会漏画/重复。
    • Top-Left 规则决定边上的像素归谁，保证共享边的像素恰好被画一次（E4：2131 个边上像素零误差）。
    • 硬件用分块 + 层次化遍历，配合 Hi-Z 和 Quad 打包。
    自测：为什么 D3D 要求 8 位亚像素精度，而不是 16 位？

    精度越高，定点数需要的位数越多：坐标范围（含保护带）若为 ±16K 像素需要 15 位整数部分，再加 8 位小数共 24 位；边函数是两个坐标差的乘积，需要约 48 位的乘法器。精度再翻倍，乘法器和面积会显著增大。8 位亚像素（1/256 像素）已经远小于人眼能察觉的顶点抖动，是精度与成本的折中。

    自测：一个三角形面积不为 0，却一个像素都没覆盖，可能吗？

    可能，而且很常见：微小三角形或细长三角形可能夹在像素中心之间，一个采样点都没盖住。E8 里面积 0.5 像素的三角形，3000 个中有 1511 个零覆盖——但它们仍然走完了顶点着色、裁剪和三角形设置，这部分开销白白浪费了。这就是"远处物体要用 LOD 降面数"的直接原因。

    6.1 重心坐标

    三角形内任一点 p 都可以唯一写成三个顶点的加权和：

    p = λ₀·v₀ + λ₁·v₁ + λ₂·v₂，　λ₀ + λ₁ + λ₂ = 1，　内部时 λᵢ ≥ 0

    λᵢ 就是 p 与"对边"围成的小三角形面积占总面积的比例。而第 5 章的边函数恰好是 2 倍有符号面积，所以光栅化时重心坐标几乎是免费的：

    λ₀ = E₁₂(p) / 2A，　λ₁ = E₂₀(p) / 2A，　λ₂ = E₀₁(p) / 2A

    有了重心坐标，任何顶点属性都可以插值：attr(p) = λ₀·a₀ + λ₁·a₁ + λ₂·a₂。问题在于：这里的 λ 是在屏幕空间算的，而属性是在三维空间里沿三角形表面线性分布的。

    6.2 为什么屏幕空间线性插值是错的

    推导：什么在屏幕空间里是线性的

    考虑观察空间中一条线段，端点的齐次裁剪坐标为 c₀、c₁（w 分别为 w₀、w₁）。线段上的点 c(t) = (1−t)c₀ + t·c₁，它的 w 也是 w(t) = (1−t)w₀ + t·w₁。屏幕坐标是 x/w，设屏幕上的插值参数为 s：

    xs(t) = [(1−t)x₀ + t·x₁] / [(1−t)w₀ + t·w₁]　＝　(1−s)·(x₀/w₀) + s·(x₁/w₁)

    解出 s 与 t 的关系，可以得到一个关键结论（把 s 看成屏幕上的线性参数）：

    1/w(s) = (1−s)·(1/w₀) + s·(1/w₁)　　a/w(s) = (1−s)·(a₀/w₀) + s·(a₁/w₁)

    即：1/w 和 a/w 在屏幕空间是线性的，a 本身不是。所以透视校正插值的做法是：插值 a/w 和 1/w，再相除：

    a(p) = ( Σ λᵢ · aᵢ / wᵢ ) / ( Σ λᵢ / wᵢ )
    soft_raster.cpp · Tri::interp（透视校正插值）
    void interp(float px, float py, float* out) const {
    // 屏幕空间重心坐标：三个边函数 / 总面积
    float e0 = (sx[2] - sx[1]) * (py - sy[1]) - (sy[2] - sy[1]) * (px - sx[1]);
    float e1 = (sx[0] - sx[2]) * (py - sy[2]) - (sy[0] - sy[2]) * (px - sx[2]);
    float e2 = (sx[1] - sx[0]) * (py - sy[0]) - (sy[1] - sy[0]) * (px - sx[0]);
    float s = e0 + e1 + e2; float b0 = e0 / s, b1 = e1 / s, b2 = e2 / s;
    if (persp) {  // 透视校正：权重乘以各顶点的 1/w，再归一化
        float w0 = b0 * iw[0], w1 = b1 * iw[1], w2 = b2 * iw[2]; float r = 1.f / (w0 + w1 + w2);
        b0 = w0 * r; b1 = w1 * r; b2 = w2 * r;
    }
    for (int i = 0; i < na; i++) out[i] = b0 * a[0][i] + b1 * a[1][i] + b2 * a[2][i];
}
    🧠 深入：为什么深度不需要透视校正

    zndc = zclip/w 本身就是"某个量除以 w"的形式，而 zclip 在三维中是线性的，所以 zndc 和 a/w 一样在屏幕空间线性。硬件直接用屏幕空间重心坐标插值深度（实测程序里 zs[si] 就是这样算的）。这也是"深度缓冲存的是 z/w 而不是 z"的根本原因：为了能线性插值，而代价是第 8 章的精度不均匀。

    • 细长三角形面积 256 像素，效率却只有 48%，和面积 8 像素的等边三角形差不多——因为它几乎全是边缘。
    🎮 游戏实战：Micro-Triangle 问题

    远处的高模角色、过度细分的地形、密集的毛发卡片都会产生大量 1～2 像素的三角形。对策：① LOD：保证三角形在屏幕上至少有约 10 像素量级的面积；② 不要对远处开曲面细分；③ UE5 Nanite 的做法是对小三角形改用计算着色器软光栅，绕过硬件的 Quad 打包——这在本章的数据下就很好理解了。

    7.1 像素着色器做什么

    像素着色器（Fragment Shader）对每个片元运行一次，输入是插值好的属性（uv、法线、世界坐标……）和系统值（SV_Position 的像素坐标、SV_IsFrontFace、MSAA 的 SV_SampleIndex 等），输出是一个或多个颜色（MRT），可选输出深度和覆盖掩码。

    在 PS 里做的事对管线的影响
    纹理采样、光照计算正常；开销取决于 ALU 指令数和纹理带宽
    discard / clip()（Alpha Test）深度写入必须等 PS 执行完才能决定 → Early-Z 的写入被推迟，移动端 TBDR 的隐藏面消除也会失效（第 8、10 章）
    写 SV_Depth深度要等 PS 算完才知道 → Early-Z 完全关闭；可以用 SV_DepthGreaterEqual 等保守深度挽回一部分
    写 UAV / 原子操作有副作用的 PS 不能被跳过，需要 [earlydepthstencil] 显式要求早测

    7.2 纹理是被采样的信号

    纹理是一张离散的 texel 网格，而像素着色器给出的 uv 是连续的。于是有两种情况：

    缩小时的走样有一个精确的信号处理解释：采样定理要求采样频率至少是信号最高频率的两倍。一个像素覆盖 8×8 个 texel，相当于每 8 个 texel 只采一次，纹理里任何周期小于 16 texel 的细节都会"折叠"成错误的低频图案——这就是远处地面的摩尔纹，镜头移动时它还会闪烁。解决办法只有一个：采样之前先把高频去掉。

    7.3 Mipmap：预先滤好波的金字塔

    Mipmap 预先把纹理逐级缩小一半（box 滤波或更好的 Kaiser 滤波），得到 Level 0（原图）、1（1/2）、2（1/4）……直到 1×1。采样时根据"一个像素覆盖多少个 texel"选择合适的层级，于是每次采样都只需要读少量 texel，却得到了大范围的平均值。

    • 内存开销：1 + 1/4 + 1/16 + … = 4/3，只多 33%。
    • 带宽收益：远处像素读的是小 Mip，texel 在内存里很集中，缓存命中率大幅提高（E9：80.8% → 99.3%）。

    LOD 怎么算

    用第 6 章的屏幕空间导数：一个像素在纹理空间里的"脚印"可以用两个向量近似——沿屏幕 x 方向走一个像素，uv 变化 (∂u/∂x, ∂v/∂x)；沿 y 方向变化 (∂u/∂y, ∂v/∂y)。乘以纹理尺寸换成 texel 单位后：

    ρ = max( √((∂u/∂x·W)² + (∂v/∂x·H)²),　√((∂u/∂y·W)² + (∂v/∂y·H)²) )　　LOD λ = log₂ ρ
    soft_raster.cpp · Tex::sampleGrad（各向同性部分）
    float lx = std::sqrt(dudx * W * dudx * W + dvdx * H * dvdx * H);   // 像素 x 方向在纹理中的长度（texel）
float ly = std::sqrt(dudy * W * dudy * W + dvdy * H * dvdy * H);   // 像素 y 方向
float lod = log2f(std::max(std::max(lx, ly), 1e-8f));             // 取长边 → 宁可模糊，不可闪烁
return trilinear(u, v, lod);                                        // 在 floor(lod) 和 floor(lod)+1 两层间插值

    7.6 纹理缓存、压缩与格式

    纹理采样的瓶颈通常不是计算，而是带宽和延迟。几个关键事实：

    纹理缓存按块组织

    texel 在显存中按 Tile / Morton（Z 序）排列，2D 上相邻的 texel 在内存里也相邻；缓存行一次取一小块（实测程序模拟为 4×4）。所以"屏幕上相邻像素采样纹理上相邻位置"时命中率极高——这依赖 Mipmap 和规则的 uv。

    块压缩（BCn / ASTC / ETC2）

    以 4×4（ASTC 可变）为块固定码率压缩，GPU 解压是硬件完成的、可随机访问。RGBA8 是 32 bpp，BC1/ETC2 RGB 是 4 bpp，ASTC 6×6 约 3.56 bpp——带宽直接降为 1/8～1/9。移动端统一用 ASTC。

    sRGB 纹理

    颜色贴图以 sRGB 存储（感知均匀，8 位够用），采样时硬件自动转成线性空间再插值和计算；法线、粗糙度、遮罩等"数据纹理"必须标记为线性，否则数值被错误地做了伽马变换。

    依赖纹理读取

    用一次采样的结果去算另一次采样的 uv（视差、扭曲特效）会让第二次采样无法提前发出，延迟隐藏能力下降；在 Warp 数少（寄存器多）时尤其明显。

    ⚠️ 面试易错
    • "Mipmap 是为了让远处的纹理更清楚"——错，Mipmap 让远处更模糊，它是为了消除走样和闪烁、提高缓存命中率。
    • "UI 也应该开 Mipmap"——不一定。UI 通常 1:1 显示，不会缩小，开 Mipmap 只会多占 33% 内存；但会被缩放显示的图标、世界空间 UI 应该开。
    • "纹理 Wrap 模式不影响 Mip"——图集（Atlas）里相邻的子图在低 Mip 会互相渗色，需要留出足够的 padding 或使用 Texture Array。

    7.7 游戏实战：贴图预算与 Mip Streaming

    • Mip Streaming / 纹理流送：根据物体在屏幕上的大小只加载需要的 Mip 层级（例如远处的建筑只加载 256×256 及以下），内存可省一半以上。Unity 的 Mipmap Streaming、UE 的 Texture Streaming 都基于第 7.3 节的 LOD 估计。
    • MOBA 的地表：俯视 45°～60° 左右，各向异性需求没有第一/三人称游戏强，但地面贴图分辨率大、重复多，Mipmap + ASTC 必不可少；地表常用多层混合（Splat Map），每多一层就多一组采样。
    • 特效贴图：粒子常用小尺寸的序列帧图集，注意图集 padding 和 Mip 渗色；全屏扭曲/热浪是依赖纹理读取，移动端要控制使用范围。

    自测：为什么非 2 的幂（NPOT）纹理在老设备上有限制？

    Mip 链每级减半，NPOT 尺寸在逐级缩小时会出现奇数，需要定义取整规则和滤波方式；Wrap 寻址对 2 的幂可以用位与实现（实测程序里就是 x &= w-1）；部分压缩格式要求 4 的倍数。早期 GLES2 设备对 NPOT 纹理不支持 Mipmap 和 Repeat。现代硬件都支持，但 2 的幂仍是贴图制作的默认规范。

    自测：同样的 Shader，换成更小的贴图为什么能明显变快？

    有两种情况：①纹理被缩小显示时，更小的贴图意味着更少的未命中（虽然 Mip 已经在帮你选小层级，但若没开 Mipmap，效果就非常明显）；②纹理被放大显示时，小贴图更容易整体放进纹理缓存。这两种都说明该 Pass 是纹理带宽受限。如果换小贴图毫无变化，说明瓶颈在别处（ALU、顶点或 ROP）。这正是第 12 章"改变一个变量看帧时间"的定位思路。

    8.1 Z-Buffer：为每个像素记住"目前最近的距离"

    深度缓冲为每个像素（MSAA 下为每个采样点）存一个深度值。每个片元到达时，拿它的深度与缓冲中的值比较：通过则写入颜色（和深度），不通过则丢弃。

    优点：与绘制顺序无关

    不透明物体以任意顺序绘制，最终结果都正确（深度相等的情况除外）。这让引擎可以按材质排序来减少状态切换，而不必严格按距离排序。

    局限：只能记住一层

    每个像素只存最近的一个深度，无法处理半透明（需要知道多层）。所以半透明物体必须单独排序绘制，且通常关闭深度写入（第 9 章）。

    深度比较函数可配置：LESS（默认）、LEQUAL、GREATER（Reversed-Z 用）、EQUAL（Z-Prepass 后的着色 Pass 用）、ALWAYS（UI、全屏后处理）。深度写入也可以单独开关（ZWrite On/Off）。

    8.2 Early-Z：在着色之前就丢掉被挡住的片元

    按照逻辑管线，深度测试在像素着色器之后（输出合并阶段）。但如果一个片元注定被挡住，它的像素着色就白做了。现代 GPU 会尽量把深度测试提前到像素着色之前，这就是 Early-Z：

    Hi-Z（Hierarchical Z）是 Early-Z 的粗粒度版本：硬件为每个 Tile（如 8×8 像素）维护一个保守的最远深度。三角形光栅化到某个 Tile 时，如果它在这个 Tile 内的最近深度都比 Tile 的最远深度还远，整个 Tile 直接跳过，连逐像素的深度读取都省了。

    ✅ Z-Prepass 值不值？

    值得的情况：像素着色很重（复杂 PBR、多光源）、场景 Overdraw 高、很难精确排序（大物体互相穿插）；同时深度缓冲还能被后续的 SSAO、屏幕空间反射、软粒子等复用。不值得的情况：顶点很多而像素着色便宜（多一遍几何得不偿失）；移动端 TBDR：硬件自带隐藏面消除（HSR/FPK，第 10 章），Prepass 往往是纯开销。

    自测：Alpha Test 的物体为什么会影响 Early-Z？应该怎么画？

    像素是否被丢弃要等 PS 执行完才知道，所以硬件不能在 PS 之前就把深度写进去（否则被 discard 的像素也挡住了后面的东西）。它仍然可以"早测"（用已有深度剔除自己），但"早写"被推迟，导致后续物体的 Early-Z 效果变差；在 TBDR 上更会打断隐藏面消除。做法：把 Alpha Test 物体放在不透明物体之后绘制；或者对它们做一个只写深度的 Prepass，然后着色 Pass 用 EQUAL 测试且不再 discard。

    自测：深度缓冲里存的是线性深度吗？后处理要用线性深度怎么办？

    不是，存的是 z/w（与 1/d 线性相关）。后处理（雾、景深、SSAO）需要线性深度时要做反变换：标准 D3D 下 d = n·f / (f − z·(f − n))，Reversed-Z 下 d = n·f / (z·(f − n) + n)。Unity 的 LinearEyeDepth()、UE 的 ConvertFromDeviceZ() 就是这个公式；实测程序 E6 的 dStd/dRev 函数也是。

    E11 在白色背景上依次叠加 3 层 alpha=0.5 的红、绿、蓝，穷举全部 6 种顺序：

    soft_raster.exe · E11
    白色背景上依次叠加 3 层 alpha=0.5 的 红/绿/蓝（Over 混合 src*a + dst*(1-a)）：
  顺序 R->G->B : Over 结果 (0.250, 0.375, 0.625)    Additive 结果 (1.30, 1.30, 1.30)
  顺序 R->B->G : Over 结果 (0.250, 0.625, 0.375)    Additive 结果 (1.30, 1.30, 1.30)
  顺序 G->R->B : Over 结果 (0.375, 0.250, 0.625)    Additive 结果 (1.30, 1.30, 1.30)
  顺序 G->B->R : Over 结果 (0.625, 0.250, 0.375)    Additive 结果 (1.30, 1.30, 1.30)
  顺序 B->R->G : Over 结果 (0.375, 0.625, 0.250)    Additive 结果 (1.30, 1.30, 1.30)

结论：Over 混合不满足交换律 -> 半透明必须排序；Additive 满足交换律 -> 粒子特效常用加法混合免排序。

    Over 混合 dst' = a·src + (1−a)·dst 的含义是"src 盖在 dst 上面"，所以必须先画远的（dst）、后画近的（src）。半透明物体的标准做法：

    1. 先画完所有不透明物体（写深度）；
    2. 半透明物体从后往前排序，开启深度测试（被不透明物体挡住的不画）、关闭深度写入（否则近处的半透明会把后画的、更远的半透明挡掉——但我们已经排过序了，这种情况本不该发生；关闭写入是为了让排序不完美时也不至于"消失"）。
    ⚠️ 面试易错：按物体排序也不完全对

    引擎按物体中心到相机的距离排序，但物体之间可能互相穿插（两片交叉的玻璃），或者一个物体自身有多层（一个半透明的球，前表面和后表面）——这些情况下物体级排序必然有错。常见缓解手段：自身多层的模型先画背面再画正面（Cull Front 再 Cull Back 两个 Pass）；或先用一个 Pass 只写深度、再用 LEQUAL 只画最前面一层（"半透明但只显示最外层"）；彻底解决需要 OIT。

    顺序无关透明（OIT）

    深度剥离 Depth Peeling

    每个 Pass 剥出"下一层"最近的表面，N 层需要 N 个 Pass。结果精确但开销与层数成正比。

    逐像素链表 / A-Buffer

    每个像素用原子操作把所有片元追加到链表，最后排序合成。精确，显存不可控。

    加权混合 WBOIT

    用与深度相关的权重做可交换的加权平均，一个 Pass 完成。近似，但对烟雾、粒子足够好，移动端也可用。

    Moment / MLAB / 等

    用矩或固定数量的片上层数近似透射率，在质量和成本之间折中；移动端可借助 Pixel Local Storage 实现。

    9.6 抗锯齿：三种走样，四种方案

    "锯齿"其实是几种不同的走样：

    几何走样

    三角形边缘：每个像素只看中心一个点是否被覆盖（第 5 章）。

    着色走样

    像素内部：高频的高光、法线贴图、细条纹在每个像素只算一次时闪烁。

    纹理走样

    纹理缩小时（第 7 章），由 Mipmap/各向异性解决。

    方案做法解决代价
    SSAA（超采样）以 N 倍分辨率渲染再降采样；每个样本都跑 PS几何 + 着色PS、带宽、显存全部 ×N
    MSAA（多重采样）每像素 N 个覆盖/深度样本，PS 只跑一次，结果写入所有被覆盖的样本；最后 Resolve 平均几何（边缘）深度/颜色存储 ×N；PS 几乎不变；对着色走样无效

    TAA（时域）每帧对投影矩阵做亚像素抖动，用运动矢量把历史帧重投影后与当前帧混合几何 + 着色 + 部分纹理需要运动矢量；会产生拖影/鬼影，需要邻域裁剪；画面偏软

    🧠 深入：MSAA 的几个细节
    • 采样点位置：4× 用旋转栅格（实测程序里的 (-2,-6),(6,-2),(-6,2),(2,6)/16），让接近水平和竖直的边也能得到 4 级灰度。
    • PS 在哪里求值：默认在像素中心，即使中心不在三角形内（外插）；用 centroid 改为在被覆盖样本的重心处求值。
    • Alpha To Coverage：把 PS 输出的 alpha 转成覆盖掩码（alpha=0.5 → 覆盖 2 个样本），让 Alpha Test 的树叶边缘也能被 MSAA 平滑，且不需要排序。
    • 延迟渲染与 MSAA 不兼容：G-Buffer 要按样本存储，带宽和显存爆炸；这是延迟渲染普遍用 TAA 的原因之一（第 11 章）。
    🎮 游戏实战：移动端 MOBA 选哪种 AA

    移动端 TBR 上 MSAA 很便宜：多重采样的颜色和深度只存在片上 Tile 内存里，Resolve 也在片上完成，只写回最终的 1× 结果（第 10 章）。所以前向渲染的手游通常首选 MSAA 2×/4×，并把 MSAA 渲染目标设为 memoryless（不分配系统内存）。注意如果中途需要把颜色或深度"拷出来"给后处理用（比如读深度做软粒子），就会触发 Resolve + 写回，MSAA 的优势就没了。TAA 在移动端则要考虑运动矢量 Pass 的开销和快速镜头移动下的拖影。

    本章小结
    • 输出合并顺序：Scissor → 模板 → 深度 → 混合 → 写掩码（硬件会把模板/深度尽量提前）。
    • 模板缓冲是 8 位"像素标签"：描边、遮挡剪影、UI 遮罩、传送门、光源体积；引擎要统一分配模板位。
    • Over 混合不满足交换律（E11：6 种顺序 6 种颜色），半透明必须从后往前、开深度测试、关深度写入；加法和乘法混合可交换，可免排序。
    • 预乘 Alpha 让过滤和混合在数学上一致，消除黑边，还能把 Over 和 Additive 合并成一种混合状态。
    • E10：MSAA 4× 对几何走样等效于 SSAA 4×，PS 只多 5%；但对着色走样无效，且存储/带宽是 4 倍。
    自测：UI 为什么是移动端 Overdraw 的大户？怎么优化？

    UI 几乎全是半透明（圆角、阴影、渐隐），无法利用深度测试剔除，而且常常是全屏面板层层叠加，每层都要读写帧缓冲。优化：全屏不透明面板打开时关闭下层 UI 和 3D 场景的渲染；图片尽量裁掉透明区域（用多边形网格代替四边形，减少透明像素）；合并图集减少批次；静态 UI 缓存成一张 RT；避免大面积的全透明点击区域仍参与渲染。

    自测：为什么开了 MSAA，角色身上的高光还是在闪？

    MSAA 只对三角形覆盖做多次采样，像素着色仍然每像素一次，所以着色走样（高光、法线贴图、细节纹理的高频变化）完全不受影响。解决办法是从源头降低着色频率：法线贴图做 Mip 并配合 Toksvig / LEAN 之类的方法调整粗糙度（"镜面抗锯齿"），或者用 TAA。

    CHAPTER 10

    GPU 硬件视角：IMR 与 TBR / TBDR

    桌面 GPU 拿到一个三角形就立刻画；手机 GPU 先把整帧的三角形分到小块里，再一块一块在片上画完。

    本章目标
    • 说清立即模式渲染（IMR）和分块渲染（TBR/TBDR）的流程差异
    • 理解 TBR 为什么能大幅节省带宽，以及"带宽 = 功耗 = 发热"对移动端的意义
    • 掌握 Load/Store Action、Memoryless、Framebuffer Fetch / Subpass 这些移动端专属概念
    • 理解 TBDR 的隐藏面消除（HSR），以及为什么 Alpha Test 在移动端格外昂贵
    • 知道 TBR 的代价：Binning 开销、中途读回帧缓冲导致的 Flush

    10.1 两种架构

    为什么手机要搞得这么复杂？因为访问 DRAM 是移动 SoC 上最耗电的操作之一：读写一次 DRAM 的能耗比片上 SRAM 高一到两个数量级，而手机的散热和电池都极其有限。桌面 GPU 有几百 GB/s 的独立显存和几百瓦的功耗预算，可以用大缓存和压缩硬扛；手机 GPU 只有几十 GB/s，还和 CPU 共享，于是选择从架构上减少带宽。

    10.2 实测：一帧的显存流量

    E12 用 E7 的统计数据（400 个随机方块、640×360）估算一帧的 DRAM 流量。模型很简化——IMR 每次深度读、深度写、颜色写都按 4 字节打到 DRAM，忽略缓存和压缩；TBR 只在每个 Tile 结束时写回 4 字节/像素的颜色：

    🔬 怎么读这组数据
    • 这是上限估算：真实 IMR 有 L2 缓存、深度压缩（Hi-Z、平面方程压缩）和颜色压缩（DCC），实际流量会小得多；真实 TBR 还有 Binning 阶段读写图元列表的流量。但量级关系是可靠的。
    • Late-Z 和 Early-Z 随机顺序的 IMR 流量相同：深度测试的读取次数不变，Early-Z 省的是着色而不是深度带宽。
    • TBR 的流量与 Overdraw、绘制顺序、MSAA 都无关——这些都在片上消化了。这就是为什么在 TBR 上 MSAA 4× 几乎免费，而 IMR 上 MSAA 的流量是 4 倍。
    • 反过来，TBR 上 Overdraw 也不是零成本：它仍然消耗片上的 ALU 和纹理带宽（半透明片元每一层都要着色、都要采样纹理）。

    10.3 Load / Store Action：告诉驱动哪些数据不用搬

    TBR 在开始渲染一个 Tile 时，要决定 Tile 内存的初始内容；结束时要决定写不写回 DRAM。现代 API 让你显式声明：

    动作选项带宽什么时候用
    Load（开始）Clear0（片上直接清）每帧开始的颜色和深度（最常见）
    DontCare0（内容未定义）确定会被完全覆盖，如全屏后处理的目标
    Load读整个 RT需要在上一个 Pass 的结果上继续画
    Store（结束）Store写整个 RT后面还要用：最终颜色、要采样的阴影贴图
    DontCare / Memoryless0深度/模板（用完就扔）、MSAA 多采样缓冲（Resolve 后就不要了）
    ⚠️ 面试易错：每帧 Clear 是浪费吗？

    在 IMR 上，Clear 要写整个缓冲（虽然有快速清除优化）；在 TBR 上 Clear 是最便宜的选择——它只是把 Tile 内存初始化，反而是"不 Clear"（Load）要把上一帧内容从 DRAM 读进来。所以移动端的规范是：每个 Pass 开始时颜色和深度都 Clear（或 DontCare），结束时深度 DontCare。Unity 里"相机不清除"或"Clear Flags = Don't Clear"在移动端是性能陷阱。

    Vulkan 的 Subpass 和 Metal 的 Programmable Blending / Tile Shader（GLES 的 EXT_shader_framebuffer_fetch）更进一步：让后一个 Pass 直接读取当前像素在 Tile 内存里的值（例如 G-Buffer），整个延迟渲染可以在一个 Tile 里完成、G-Buffer 永远不写回 DRAM（Memoryless G-Buffer）。

    10.4 HSR：硬件替你做 Z-Prepass

    TBDR（PowerVR 的 HSR、Apple GPU、Mali 的 FPK—Forward Pixel Kill、Adreno 的 LRZ 等机制类似）在一个 Tile 的所有图元光栅化完之后、着色之前，先做一次完整的可见性判定，只为每个像素最终可见的那个不透明片元着色。效果相当于 E7 里"Z-Prepass"的结果，却不需要你多画一遍——所以：

    • 在 TBDR 上，不透明物体的前后排序收益变小（但仍建议大致排序，因为并非所有移动 GPU 的 HSR 都同样彻底，且 Binning 有容量上限）；
    • 手动 Z-Prepass 在 TBDR 上通常是纯开销；
    • Alpha Test（discard）和写深度会打断 HSR：硬件无法在着色前确定这个片元是否真的不透明，只能让它和它后面的东西都去着色。这就是"移动端少用 Alpha Test、多用 Alpha Blend 或者干脆用实体几何"的原因。

    10.5 TBR 的代价与陷阱

    Binning 开销

    所有顶点要先处理一遍、结果（图元列表 + 变换后的顶点）写入 DRAM 再读回来。顶点越多，这部分越贵——TBR 对高面数场景比 IMR 更敏感。部分 GPU 只在 Binning 时计算位置（Position-only shading），把其他属性推迟到渲染阶段。

    中途读回帧缓冲

    在一个 Pass 中间去采样当前的颜色或深度（"抓屏"做扭曲、读深度做软粒子），会强制把所有 Tile 写回 DRAM 再重新开始（Flush / Resolve）。一帧里 RenderTarget 切来切去是移动端最常见的性能杀手。

    巨大的三角形

    一个全屏三角形会被登记到所有 Tile 里；大量覆盖全屏的半透明面片会让每个 Tile 的图元列表都很长。

    Tile 内存容量

    MRT 数量、像素格式（如 RGBA16F）、MSAA 倍数都会占用 Tile 内存；超过容量时驱动会自动缩小 Tile 尺寸，增加 Tile 数和开销。

    🎮 游戏实战：一个 MOBA 后处理的例子

    一个常见的反模式：Bloom 需要降采样链（1/2、1/4、1/8……），每级一个 RT；再加上屏幕扭曲（要抓屏）、颜色校正、FXAA，每帧切换十几次 RT。在 TBR 手机上，这可能比整个场景渲染还贵。优化方向：Bloom 用更少的级数、在低分辨率 RT 上完成；扭曲特效用"预先渲染到单独 RT"而不是抓取主屏；颜色校正（LUT）、暗角、FXAA 合并成一个最终 Pass；能用 Framebuffer Fetch 的效果就别抓屏。

    本章小结
    • IMR：三角形按提交顺序流过管线，深度/颜色直接读写 DRAM，靠大缓存和压缩扛带宽。
    • TBR/TBDR：先 Binning 把整帧图元分到 Tile，再逐 Tile 在片上完成光栅化、深度、混合、MSAA，只写回最终颜色；TBDR 还在着色前做 HSR。
    • E12 简化模型：IMR 流量是 TBR 的 28～78 倍，MSAA 4× 时 134 倍；TBR 的 DRAM 流量与 Overdraw、顺序、MSAA 无关。
    • Load/Store Action 决定 Tile 内存的进出；Clear 和 DontCare 在 TBR 上最便宜；Memoryless 让深度和 MSAA 缓冲根本不占系统内存。
    • TBR 的敌人：顶点过多（Binning）、中途读回帧缓冲（Flush）、Alpha Test（打断 HSR）、RT 频繁切换。
    自测：同一个游戏，为什么 PC 上很流畅的"屏幕扭曲"特效在手机上掉帧严重？

    扭曲需要采样"当前已经画好的屏幕颜色"（GrabPass / Opaque Texture）。在 IMR 上，这只是一次拷贝或直接采样已有 RT；在 TBR 上，它强制结束当前 RenderPass，把所有 Tile 的颜色（可能还有深度）写回 DRAM，再开一个新的 RenderPass 把内容读回来——两次整屏的带宽，还打断了 HSR 和 MSAA 的片上优势。手机上应限制扭曲的使用，或改用不需要读屏的近似做法。

    自测：TBR 是不是在所有场景下都比 IMR 好？

    不是。TBR 用 Binning 的开销换取帧缓冲带宽：顶点数极多、三角形极小的场景（高面数模型、大量曲面细分），Binning 的图元列表读写会变得很贵；需要在一帧中频繁读回帧缓冲的渲染方式也不适合 TBR。桌面 GPU 选择 IMR + 大缓存，是因为它们有足够的带宽和功耗预算，而且要应对极高的几何复杂度。实际上现代桌面 GPU 也引入了部分分块思想（如 NVIDIA 自 Maxwell 起的 Tiled Caching）。

    Shadow Pass 的 Shader 通常只有顶点着色器（或只有一个空 PS）——没有颜色输出、没有纹理采样，是最"纯粹"的几何负载。所以阴影 Pass 的开销主要取决于投射阴影物体的顶点数和 Draw Call 数，优化手段是：给远处物体关闭投影、用更低的 LOD 渲染阴影、对静态物体缓存阴影贴图。Alpha Test 的树叶在 Shadow Pass 里需要 PS 做 discard，会让这个 Pass 显著变贵。

    11.3 Pass 2：查询阴影

    主 Pass 的像素着色器拿到片元的世界坐标 P，用同一个 lightVP 把它变换到光源的裁剪空间，得到它在阴影贴图上的位置 (sx, sy) 和它到光源的深度 z，然后比较：

    lit = ( z − bias ≤ ShadowMap[sx, sy] ) ? 1 : 0
    soft_raster.cpp · E13 阴影查询（含偏移与 PCF）
    auto smLookup = [&](V3 P, V3 N, int mode, int pcf) -> float {
    V4 lp = lightVP * V4{P.x, P.y, P.z, 1};                          // 世界 → 光源裁剪空间（正交：w=1）
    float sx = (lp.x * 0.5f + 0.5f) * SM, sy = (0.5f - 0.5f * lp.y) * SM, z = lp.z;
    float ndl = std::max(dot(N, toL), 0.f);
    float tanT = std::sqrt(std::max(1 - ndl * ndl, 0.f)) / std::max(ndl, 0.05f);   // 表面与光线夹角的正切
    float bias = /* mode 3：斜率缩放 */ std::min(0.0002f + 0.0006f * tanT, 0.01f);
    int r = pcf ? 1 : 0; float lit = 0; int n = 0;
    for (int dy = -r; dy <= r; dy++) for (int dx = -r; dx <= r; dx++) {          // PCF：3x3 次比较取平均
        int ix = (int)floorf(sx) + dx, iy = (int)floorf(sy) + dy; n++;
        lit += (z - bias <= SMT.depth[(size_t)iy * SM + ix]) ? 1.f : 0.f;
    }
    return lit / n;
};

    • 常量 bias 1.5cm 已经消除了大部分痤疮，9cm 基本干净；但 60cm 时漏光比例是最小 bias 时的 2.7 倍。这个场景里光线比较陡，所以常量 bias 和斜率缩放的差异不大；光线越斜（日出日落），常量 bias 的"两难"越明显。
    • 主 Pass：2348 个三角形中背面剔除掉 1246 个（53%）；先画立方体和球、最后画地面，让地面被遮挡的 8215 个片元在 Early-Z 阶段就被丢弃——第 4、8 章的结论在这里同时生效。
    🧠 深入：真实引擎里的阴影
    • 硬件深度偏移：D3D 的 DepthBias / SlopeScaledDepthBias（GL 的 glPolygonOffset）在光栅化阶段直接按三角形的深度斜率加偏移，Shadow Pass 里设置一次即可。另一种思路是 Normal Offset：查询时把 P 沿法线推出去一点。
    • PCF：硬件支持"比较采样器"（SampleCmp / sampler2DShadow），一次采样就返回 2×2 比较结果的双线性加权，比手写 3×3 循环便宜得多。
    • 级联阴影 CSM：把主相机视锥按距离切成 2～4 段，每段一张阴影贴图，近处精度高、远处覆盖广。MOBA 视角固定、范围小，通常一级或两级就够。
    • MOBA 手游的折中：英雄用实时 Shadow Map（甚至只给英雄投影），场景静态阴影烘焙进光照贴图；低端机退化为脚底的圆形"假阴影"贴片。

    11.4 渲染路径：前向、延迟与 Forward+

    场景里只有一盏光时，怎么画都行；当有几十上百盏动态光（技能光效、路灯、爆炸）时，"每个像素要算哪些光"就成了架构问题。

    ⚠️ 面试易错：延迟渲染"光源再多也不影响性能"

    不对。延迟渲染把光照开销从"物体数 × 光源数"降到了"像素数 × 每像素光源数"，但每盏光仍要读一遍它覆盖范围内的 G-Buffer（带宽），大量重叠的光源依然很贵——Tiled/Clustered Deferred 就是为此而生，让每个像素一次读 G-Buffer、在寄存器里累加所有光。另外，G-Buffer 本身的写入和读取是固定的高额带宽成本，这在移动端往往比光照计算更致命。

    11.5 一帧的真实结构：读懂截帧

    用 RenderDoc（PC/Android）、Xcode GPU Capture（iOS）、Snapdragon Profiler / Mali Graphics Debugger 截一帧，事件列表大致是这样的（以一款延迟渲染的 PC 游戏为例）：

    本章小结
    • Shadow Map = 两遍渲染：Pass 1 从光源只写深度（无 PS），Pass 2 把片元变换到光源空间比较深度。
    • 阴影 texel 覆盖一段表面却只存一个深度 → bias=0 时近一半受光像素误判（E13：46.65%）；bias 太大 → 阴影与物体脱开（漏光增加 2.7 倍）；光线越斜需要的 bias 越大 → 斜率缩放偏移。PCF 柔化边缘。
    • 前向：简单、MSAA/半透明友好、移动端主流；延迟：光照与几何解耦，但 G-Buffer 带宽大、不支持半透明和 MSAA；Forward+/Clustered：用计算着色器做光源分块，兼顾两者。
    • 读截帧时按 Pass 对应到管线阶段，逐个检查剔除、排序、Overdraw、RT 切换。
    自测：Shadow Pass 为什么经常剔除正面而不是背面？

    剔除正面后，写入阴影贴图的是物体的背面深度。对封闭物体而言，受光的正面离"背面深度"有整个物体厚度的距离，自然不会出现自阴影痤疮，相当于免费得到了一个很大的 bias。缺点是薄物体（单面的墙、叶片）没有背面，和地面接触处仍可能漏光；且背光面本来就在阴影里，所以背面的痤疮被 N·L ≤ 0 掩盖。

    自测：延迟渲染里半透明物体怎么画？

    G-Buffer 每个像素只存一层表面属性，无法表达半透明的多层叠加。所以延迟渲染管线在不透明物体完成光照后，再单独走一个前向 Pass 绘制半透明物体（从后往前、关深度写入），光照用前向方式或借助 Clustered 光源列表计算。这也是为什么即便是延迟渲染引擎，也必须同时维护一套前向光照代码。

    12.4 案例：MOBA 团战掉帧排查（典型流程示例）

    下面是一个典型问题的排查思路（数字为示意，不同项目差异很大）：中端安卓机平时 60fps，十人团战放大招时掉到 35fps。

    ① 先分 CPU / GPU

    引擎 Profiler 显示团战时渲染线程从 6ms 涨到 9ms（技能特效多了 Draw Call），但 GPU 帧时间从 14ms 涨到 28ms → 主要是 GPU 瓶颈，CPU 的增量是次要问题。

    ② GPU 里分像素 / 顶点

    把渲染分辨率从 100% 降到 70%，团战帧率从 35 升到 52 → 像素相关。开 Overdraw 视图：大招范围内特效层数达到 15～20 层。

    ③ 定位具体资源

    RenderDoc 截帧，按耗时排序 Draw Call：前 10 名中有 7 个是某两个英雄的大招特效——全屏大小的半透明面片、Additive + 扭曲（Grab Pass）、每层采样 3 张 512² 纹理。扭曲特效还触发了一次额外的 RenderPass 切换（第 10 章）。

    ④ 对症优化
    • 特效面片按实际形状裁剪（四边形 → 多边形网格），透明区域面积减少约一半；
    • 同屏同类特效设上限，远离镜头中心的特效降级（减少层数和粒子数）；
    • 扭曲改为只对英雄技能开启、低端机关闭，避免 Grab Pass；
    • 特效纹理检查 Mipmap 和 ASTC 压缩，合并 Mask 通道减少采样次数；
    • （可选）特效统一渲染到 1/2 分辨率 RT 再合成。
    ⑤ 验证与防回退

    同一回放录像重跑，统计团战段的平均帧率、1% Low 帧率和功耗；把"特效 Overdraw 层数""单特效最大面积"做成资源规范和自动检查，防止新英雄再次引入。

    ✅ 面试答法

    面试官问"遇到掉帧怎么查"，按"复现 → CPU/GPU 归因 → GPU 内部归因（改变量） → 截帧定位到 Pass/Draw Call → 对症优化 → 回归验证与规范化"的顺序讲，并在每一步说出一个具体工具和一个具体判据。比直接罗列"合批、LOD、压缩纹理"更能体现工程能力。

    12.5 几条容易被忽视的经验

    • Shader 变体爆炸：每个 multi_compile 关键字翻倍变体数，导致包体、内存和首次加载编译卡顿（"Shader 编译卡顿"）。用 shader_feature、变体剥离、预热（Warmup）和 PSO 缓存。
    • 精度：移动端 PS 默认用 half，但世界坐标、UV 大范围平铺、时间累加量必须用 float，否则远处或长时间运行后出现抖动和条纹。
    • 动态分辨率：GPU 时间超标时自动降低 3D 渲染分辨率（UI 保持原分辨率），是对像素瓶颈最"兜底"的手段。
    • 帧率稳定比峰值重要：一次 50ms 的卡顿比平均帧率低 5fps 更伤体验；资源加载、Shader 编译、GC 都会造成尖峰。
    本章小结
    • 先分 CPU / GPU：看各线程耗时与 GPU 耗时，谁 ≈ 帧时间谁就是瓶颈。
    • GPU 内部用"改一个变量"定位：降分辨率 → 像素相关；减面 → 顶点相关；换小纹理 → 纹理带宽；PS 输出常量 → ALU；关混合/MSAA → ROP 与帧缓冲带宽。
    • 每个管线阶段都有对应的典型问题和优化手段（表 12.3），优化前要先对号入座。
    • 排查流程：复现 → 归因 → 截帧定位 → 对症优化 → 回归验证 → 规范化防回退。

    13.1 "请介绍一下渲染管线"——30 秒 / 2 分钟版

    30 秒版

    渲染管线分三大段：应用阶段在 CPU 上做剔除、排序、合批并提交 Draw Call；几何阶段在 GPU 上由顶点着色器把顶点从局部空间经 MVP 变换到裁剪空间，然后硬件做裁剪、透视除法、视口变换和背面剔除；光栅化与像素阶段把三角形离散成片元、做透视校正插值，经过 Early-Z 后运行像素着色器（纹理采样和光照），最后在输出合并阶段做模板/深度测试和混合，写入帧缓冲。可编程的是顶点和像素着色器，其余是可配置的固定功能。

    2 分钟版要额外点出的 5 个"深度信号"
    1. w 的意义：投影矩阵把距离放进 w；裁剪必须在除以 w 之前做，否则相机背后的点会翻转（E2）。
    2. 光栅化的精确性：定点亚像素 + Top-Left 规则保证共享边不漏不重（E4）。
    3. 透视校正：1/w 在屏幕空间线性，属性要插值 a/w 和 1/w 再相除（E5）。
    4. Early-Z 与排序：不透明从前往后画，PS 次数可降到可见像素数；discard 和写深度会破坏它（E7）。
    5. 移动端 TBR：深度、混合、MSAA 在片上完成，带宽是第一约束（E12）。

    13.2 高频题与参考答案

    A · 坐标变换与投影

    Q1 MVP 分别做什么？为什么不一步到位？

    M 把局部坐标变到世界，V 把世界变到以相机为原点的观察空间，P 把视锥映射到裁剪空间（齐次）。分开是因为每个空间各有用途：局部空间便于实例化和蒙皮，世界空间做光照物理，观察空间让投影公式简单。实际上 CPU 通常预乘成一个 MVP 传给 Shader，但世界坐标仍需要单独的 M。

    Q2 为什么要用齐次坐标？w=0 和 w=1 分别表示什么？

    为了用矩阵表示平移和透视。w=1 是点（受平移影响），w=0 是方向（不受平移影响）。透视时 w 存放距离，硬件除以 w 实现"近大远小"。

    Q3 推一下透视投影矩阵。

    相似三角形得 x'=n·x/(−z)；令第 4 行 (0,0,−1,0) 使 w=−z；x、y 按 1/tan(fov/2) 和宽高比缩放；z 行写成 (0,0,A,B)，由"−n→0、−f→1"解出 A=f/(n−f)、B=nf/(n−f)（D3D [0,1] 约定）。关键结论：z_ndc 与 1/d 线性相关。（第 3.2 节）

    Q4 法线为什么用逆转置矩阵？

    要保持法线与切线垂直：nᵀt=0，t'=Mt，设 n'=Gn，则需 GᵀM=I，即 G=(M⁻¹)ᵀ。只有旋转和均匀缩放时可直接用 M。（第 2.5 节）

    Q5 为什么在裁剪空间裁剪，而不是 NDC？

    相机背后的点 w<0，除以 w 会翻转到屏幕另一侧；w=0 会除零；而且裁剪空间与观察空间是线性关系，插值出的新顶点正确。E2：一个顶点在相机后 1 米，朴素除法把它投到屏幕上方，近平面裁剪后得到 4 个顶点、拆成 2 个三角形。实际硬件靠保护带几乎只裁近平面。（第 3.4、3.5 节）

    Q6 D3D 和 OpenGL 在投影上有什么不同？

    NDC 深度范围 D3D/Vulkan/Metal 为 [0,1]，GL 为 [−1,1]；Vulkan 的 NDC y 向下；纹理坐标原点 GL 在左下、其他在左上；传统上 D3D 左手系、GL 右手系（这只是约定，由矩阵决定）。（第 3.6 节）

    B · 光栅化与插值

    Q7 光栅化是怎么判断像素在三角形内的？

    用三条边函数 E(p)=(b−a)×(p−a)，三个值同号则采样点在内。边函数是线性函数，可增量计算、可对整块像素快速接受/拒绝，三者除以面积就是重心坐标。（第 5.2 节）

    Q8 两个三角形共享一条边，边上的像素会被画两次吗？

    不会。硬件把顶点吸附到 8 位亚像素定点网格，用整数算边函数（精确、水密），并用 Top-Left 规则决定 E=0 的样本归谁。E4：顶点对齐像素中心的网格里 2131 个边上像素，"全收"重复 2131 次、"全不收"漏 2131 个，Top-Left 零误差；float 边函数在大坐标下会出现个别漏画/重复。（第 5.3、5.4 节）

    Q9 什么是透视校正插值？为什么深度不需要？

    屏幕空间里 1/w 和 a/w 是线性的，a 不是；所以插值 a/w 和 1/w 再相除。深度存的是 z/w，本身就是"除以 w"的形式，可直接线性插值。E5：不校正时地面 uv 平均误差 17 个纹理重复，校正后与射线求交真值一致。（第 6.2、6.3 节）

    Q10 ddx/ddy 是怎么来的？为什么 PS 按 2×2 执行？

    PS 以 2×2 Quad 为单位执行，导数就是 Quad 内相邻像素的差分；三角形外的像素作为 Helper Lane 陪跑。这让 Mipmap LOD 选择成为可能，代价是小三角形浪费：E8 中 1 像素三角形 Quad 效率 27%，细长三角形不到 50%。（第 6.5、6.6 节）

    Q11 为什么小三角形对 GPU 不友好？

    ① Quad 效率低（边缘 Quad 半空）；② 很多三角形一个像素都不覆盖却走完了顶点和设置（E8：0.5 像素三角形一半零覆盖）；③ 光栅化器每周期处理的三角形数有上限；④ TBR 上 Binning 开销随三角形数增长。对策是 LOD，以及 Nanite 式的软光栅。

    C · 深度、模板与可见性

    Q12 什么是 Early-Z？什么时候失效？

    把深度测试提前到 PS 之前，丢弃被挡住的片元。PS 写深度时完全失效；discard/Alpha Test、Alpha To Coverage 会推迟深度写入；写 UAV 需要显式声明；中途改变深度比较方向会让 Hi-Z 失效；从后往前画时剔不掉任何东西。（第 8.2 节）

    Q13 不透明物体为什么要从前往后画？效果有多大？

    让 Early-Z 尽早建立近处深度，后面被挡的片元不再着色。E7：400 个矩形、平均 Overdraw 26.7 层，Late-Z PS 执行 599 万次，Early-Z 随机顺序 74 万次，从前往后 22.4 万次（等于可见像素数），耗时 3764ms → 191ms；从后往前和 Late-Z 一样慢。（第 8.3 节）

    Q14 Z-Prepass 有什么用？什么时候不该用？

    先只写深度再用 EQUAL 着色，不依赖排序就能让 PS 次数等于可见像素数（E7：224506 次，248ms），深度还能被 SSAO 等复用。代价是多一遍几何。PS 便宜而顶点多的场景、以及移动端 TBDR（硬件 HSR 已经做了同样的事）不该用。

    Q15 什么是 Z-Fighting？怎么解决？

    两个面的深度差小于深度缓冲在该距离处的分辨率，前后关系随机。标准 Z 的精度集中在近处（near=0.1 时一半深度值用于前 0.2 米，1000 米处只能分辨 0.6 米）。解决：增大 near（最有效）、Reversed-Z + D32F、避免共面、深度偏移、贴花改用模板或延迟贴花。（第 8.4、8.6 节）

    Q16 Reversed-Z 为什么能提高精度？24 位深度能用吗？

    投影让远处的深度挤在一起，浮点数让可表示值挤在 0 附近；反转后远处映射到 0，两种不均匀互相抵消，相对精度近似恒定。E6：1000 米处可分辨距离从 0.6m 降到 0.00007m，8 公里内零 Z-Fighting。24 位定点是均匀的，反转无效。

    Q17 模板缓冲能做什么？举三个游戏里的例子。

    8 位像素标签。描边（先写模板再外扩画轮廓）、角色被墙遮挡时显示剪影、UI 遮罩、传送门/镜子、延迟渲染光源体积、阴影体。（第 9.2 节）

    D · 纹理与像素

    Q18 Mipmap 解决什么问题？代价是什么？

    纹理缩小时一个像素覆盖很多 texel，只采一个点会走样（摩尔纹、闪烁）。Mipmap 预先滤波，按 LOD 选层。代价是多 1/3 内存；收益是走样消失且缓存命中率大幅提高（E9：80.8% → 99.3%）。它让远处更模糊而不是更清楚。

    Q19 LOD 怎么计算？

    由 Quad 差分得到 uv 的屏幕导数，乘纹理尺寸得到像素在纹理中的两个边长，取较长者 ρ，LOD=log₂ρ。三线性在 floor 和 floor+1 两层之间插值。（第 7.3 节）

    Q20 双线性、三线性、各向异性的区别？

    双线性：一层内 2×2 加权（4 texel）；三线性：两层各一次双线性再插值（8 texel），解决 Mip 层切换的接缝；各向异性：斜视时像素脚印是细长的，按短边选 LOD、沿长边取多个样本。E9：全图误差 0.221 → 0.087 → 0.026，取样数 4 → 7.6 → 39.3。

    Q21 discard 为什么在移动端特别贵？

    它让硬件无法在着色前确定片元是否不透明：Early-Z 无法提前写深度，TBDR 的 HSR 被打断，被挡住的片元也得着色。移动端尽量用 Alpha Blend 或实体几何代替，必须用时放在不透明物体之后绘制。

    Q22 Shader 里的 if 一定慢吗？

    不一定。同一 Warp 走同一分支（uniform 分支，例如由材质参数决定）几乎无开销；按像素发散时两侧都要执行。另外分支里不能用依赖导数的 Sample()。（第 1.3、6.5 节）

    E · 混合与抗锯齿

    Q23 半透明物体为什么要从后往前画、关闭深度写入？

    Over 混合不满足交换律（E11：三层 RGB 六种顺序得到六种颜色），正确的物理含义是近的盖在远的上面，所以从后往前；深度写入关闭，避免排序不完美时近处半透明把远处半透明整个挡掉。深度测试仍开启，被不透明物体挡住的不画。

    Q24 物体互相穿插的半透明怎么办？

    物体级排序必然有错。缓解：拆分网格、先背面后正面两个 Pass、深度预写只保留最外层；根本解决用 OIT：深度剥离、逐像素链表、加权混合 WBOIT（近似、单 Pass、移动端可用）。

    Q25 什么是预乘 Alpha？

    颜色预先乘以 alpha 存储，混合因子用 One / OneMinusSrcAlpha。它让过滤和混合在数学上一致，消除透明边缘的黑边（E11：直通 Alpha 结果 (0.25,0.75,0.25)，预乘 (0.5,1,0.5)），并能用同一混合状态表达 Over 与 Additive。

    Q26 MSAA 和 SSAA 的区别？

    SSAA 每个样本都着色；MSAA 每像素多个覆盖/深度样本，PS 只跑一次。对几何边缘两者等效（E10：纯色边缘误差都是 0.1063，MSAA 的 PS 只多 5%），但 MSAA 对着色走样无效（内部误差与无 AA 相同 0.1683）。两者的存储都是 N 倍。

    Q27 为什么延迟渲染不好做 MSAA？TAA 的原理和缺点？

    G-Buffer 要按样本存储和光照，带宽与显存乘以 N。TAA 每帧亚像素抖动投影矩阵，用运动矢量重投影历史帧并混合，等效于时间上的超采样；缺点是拖影、鬼影（需要邻域裁剪）、画面偏软、需要运动矢量 Pass。

    F · 架构与性能

    Q28 IMR 和 TBR 的区别？

    IMR 来一个三角形画一个，深度和颜色直接读写显存；TBR 先 Binning 把整帧图元分到 Tile，再逐 Tile 在片上完成光栅化、深度、混合、MSAA，只写回最终颜色。TBDR 还在着色前做隐藏面消除。E12 简化模型：IMR 流量是 TBR 的 28～78 倍，MSAA 4× 时 134 倍。（第 10 章）

    Q29 移动端渲染要注意什么？

    带宽第一：Load/Store 用 Clear/DontCare、深度 Memoryless；减少 RT 切换和抓屏；MSAA 片上 Resolve；少用 Alpha Test；控制半透明面积；ASTC + Mipmap；half 精度；控制顶点数。（第 10.6 节）

    Q30 Draw Call 为什么贵？怎么优化？

    贵在 CPU 端的状态切换、资源绑定、驱动校验和提交。优化：静态合批（省 DC、费内存）、动态合批（CPU 变换顶点）、GPU Instancing（同网格大量重复）、SRP Batcher（不减 DC 但让每次 DC 更便宜）、减少材质和变体、现代 API 多线程录制。（第 1.2 节）

    Q31 前向渲染和延迟渲染怎么选？

    光源少、要 MSAA、半透明多、移动端带宽紧 → 前向（或 Forward+）；大量动态光源、复杂屏幕空间效果、PC/主机 → 延迟（Tiled/Clustered）。（第 11.4 节）

    Q32 怎么定位 GPU 瓶颈？

    先看 GPU 时间是否 ≈ 帧时间，再"改一个变量"：降分辨率有效 → 像素相关；换小纹理有效 → 纹理带宽；PS 输出常量有效 → ALU；关混合/MSAA 有效 → ROP/带宽；减面有效 → 顶点。然后截帧定位到具体 Pass 和 Draw Call。（第 12 章）

    Q33 阴影痤疮和彼得潘是什么？

    阴影贴图的一个 texel 覆盖一段表面却只存一个深度，bias 太小时表面一半判为自阴影（E13：46.65% 误判）；bias 太大时接触处漏光、阴影脱离物体（漏光增加 2.7 倍）。用斜率缩放偏移、Normal Offset、剔除正面、PCF 缓解。（第 11.3 节）

    13.5 附录：速记卡

    ① 管线顺序

    应用(CPU) → IA → VS → (HS/DS/GS) → 裁剪 → ÷w → 视口 → 背面剔除 → 光栅化 → 插值 → Early-Z → PS → 模板/深度 → 混合 → 帧缓冲

    ② 投影矩阵

    第 4 行 (0,0,−1,0) → w=−z；z_ndc = a + b/d；D3D: A=f/(n−f), B=nf/(n−f)；Reversed: A=n/(f−n), B=nf/(f−n)

    ③ 裁剪

    齐次空间：−w≤x,y≤w，0≤z≤w；先裁后除；硬件靠保护带，主要裁近平面（E2：3→4 顶点）

    ④ 光栅化

    边函数同号即内；8 位亚像素定点；Top-Left：上边（水平向右）与左边（向上）包含 E=0（E4：零漏零重）

    ⑤ 透视校正

    a = Σλᵢaᵢ/wᵢ ÷ Σλᵢ/wᵢ；深度 z/w 直接线性插值（E5：误差 17 → 0.0001）

    ⑥ 2×2 Quad

    导数 = Quad 差分；Helper Lane 陪跑；1px 三角形效率 27%，细长 48%（E8）

    ⑦ Mipmap

    LOD = log₂(max(|∂uv/∂x|,|∂uv/∂y|)·size)；+33% 内存；三线性 8 texel；各向异性按短边选层（E9）

    ⑧ Early-Z

    失效：写深度、discard、A2C、UAV；从前往后 PS 次数=可见像素（E7：599 万 → 22 万）

    ⑨ 深度精度

    精度 ∝ near/d²；增大 near 最有效；Reversed-Z + D32F：1000m 处 0.6m → 0.07mm（E6）

    ⑩ 混合

    Over 不可交换 → 从后往前、关 ZWrite；Additive 可交换；预乘 Alpha 消黑边（E11）

    ⑪ 抗锯齿

    SSAA 全治全贵；MSAA 治边不治着色、PS ≈1×、存储 N×；FXAA 便宜偏糊；TAA 全面但拖影（E10）

    ⑫ TBR

    Binning → 逐 Tile 片上渲染 → 只写颜色；Clear/DontCare/Memoryless；怕抓屏、RT 切换、Alpha Test、顶点多（E12）

    ⑬ 阴影

    两遍：光源深度 → 比较；bias 小痤疮、大漏光；斜率缩放 + PCF（E13：46.65% → 0.02%）

    ⑭ 渲染路径

    前向：简单/MSAA/半透明/移动端；延迟：多光源/G-Buffer 带宽；Forward+：计算着色器分块光源

    ⑮ 定位瓶颈

    CPU/GPU → 降分辨率 → 换小纹理 → PS 输出常量 → 关混合/MSAA → 减面 → 截帧定位

    ⑯ Draw Call

    贵在状态切换/绑定/驱动；静态合批、动态合批、Instancing、SRP Batcher 各省不同的东西
