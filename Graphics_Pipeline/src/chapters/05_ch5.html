第三部分　光栅化：连续的三角形变成离散的像素

几何阶段输出的是三个浮点坐标，像素阶段需要的是"哪些像素被覆盖、每个像素的属性是多少"。这一步是整条管线最"离散"的地方，也是走样、裂缝、精度问题的发源地。

CHAPTER 05

光栅化：像素归谁

三条边函数、一个定点网格、一条 Top-Left 规则，保证相邻三角形不漏一个像素、也不多画一个像素。

本章目标
  • 理解"覆盖"的定义：像素中心（采样点）是否落在三角形内
  • 掌握边函数：几何意义、增量计算、与重心坐标的关系
  • 说清为什么 GPU 要把顶点吸附到定点亚像素网格上，以及 Top-Left 填充规则解决什么问题
  • 了解包围盒遍历、分块遍历和层次化光栅化
  • 能在交互实验里亲手观察覆盖、Top-Left 和 2×2 Quad

5.1 光栅化在回答什么问题

光栅化的输入是一个屏幕空间三角形（三个顶点的浮点坐标），输出是一组片元（Fragment）——"这个像素被这个三角形覆盖了，它的深度和插值属性是多少"。

"覆盖"的标准定义是：像素的采样点落在三角形内部。不开 MSAA 时，每个像素只有一个采样点，就在像素中心 (x+0.5, y+0.5)。三角形哪怕盖住了一个像素 49% 的面积，只要没盖住中心，这个像素就不算覆盖——这就是锯齿（几何走样）的来源。

5.2 边函数：用三个半平面圈出三角形

对有向边 a→b 和任意点 p，定义边函数：

Eab(p) = (b.x − a.x)(p.y − a.y) − (b.y − a.y)(p.x − a.x)

它是向量 ab 与 ap 的二维叉积，有三层含义：

① 半平面测试

E > 0 表示 p 在边的一侧，E < 0 在另一侧，E = 0 恰好在边上。三条边的 E 同号 ⇔ p 在三角形内。

② 面积

Eab(p) 等于三角形 abp 面积的 2 倍（有符号）。把 p 换成第三个顶点 c，就得到整个三角形的 2 倍面积——也就是第 4 章背面剔除用的那个数。

③ 重心坐标

Ebc(p)/Ebc(a) 正是 p 相对顶点 a 的重心坐标 λa。光栅化算出来的边函数值，插值时直接复用（第 6 章）。

实测程序的光栅化内循环就是这三个边函数（为了可读性没有写成增量形式）：

auto E = [&](int a, int b, i64 px, i64 py) { return (X[b] - X[a]) * (py - Y[a]) - (Y[b] - Y[a]) * (px - X[a]); }; for (int py = y0; py <= y1; py++) for (int px = x0; px <= x1; px++) { for (int si = 0; si < T.S; si++) { // S = 采样数（1 或 MSAA 的 4） i64 SX = (i64)px * ONE + T.offX[si], SY = (i64)py * ONE + T.offY[si]; // 采样点（定点） i64 w0 = E(1, 2, SX, SY), w1 = E(2, 0, SX, SY), w2 = E(0, 1, SX, SY); cov[si] = (w0 + b0 >= 0) && (w1 + b1 >= 0) && (w2 + b2 >= 0); // b0..b2：Top-Left 偏置 if (cov[si]) zs[si] = ((float)w0 * t.z[0] + (float)w1 * t.z[1] + (float)w2 * t.z[2]) * invArea; } ... }

5.3 定点亚像素：为什么不直接用浮点数

GPU 在三角形设置阶段会把顶点的屏幕坐标吸附（snap）到一个定点网格上：D3D11 要求 8 位亚像素精度，即每个像素被细分为 256×256 个格子，坐标用整数表示。这样做有三个理由：

  1. 精确：边函数变成整数乘法和加法，结果没有舍入误差。共享同一条边的两个三角形，它们对这条边计算的 E 值恰好互为相反数，不会出现一个说"在内"、另一个也说"在内"（或都说"在外"）的情况——这叫水密（Watertight）。
  2. 便宜：整数加法器比浮点加法器小得多、快得多。
  3. 确定：结果不依赖运算顺序，同一个三角形每次光栅化结果完全一致——这是深度 EQUAL 测试（Z-Prepass）能工作的前提。

🧠 深入：PS1 为什么"顶点抖动"

初代 PlayStation 的 GTE 把顶点坐标直接取整到整像素，没有亚像素精度，物体缓慢移动时顶点会一格一格地跳，于是整个模型看起来在"抖"。再加上它不做透视校正（第 6 章 E5），就成了今天被刻意模仿的"PS1 风格"。8 位亚像素精度意味着顶点每次跳 1/256 像素，肉眼完全看不出来。

5.4 Top-Left 规则：边上的像素归谁

定点数解决了"算得准"，但还有一个逻辑问题：采样点恰好落在共享边上（E = 0）时，这个像素归哪个三角形？

  • 如果"E ≥ 0 就算覆盖"，两个三角形都会画它——重复画（半透明叠两次、模板计数加两次）。
  • 如果"E > 0 才算覆盖"，两个三角形都不画它——漏画（一条缝）。

D3D 和 OpenGL 采用 Top-Left 规则：E = 0 的采样点只有在上边或左边上才算覆盖。

  • 上边：完全水平、且三角形其余部分在它下方的边；
  • 左边：三角形左侧的边（沿顺时针绕行时向上走的边）。

一条共享边对一个三角形是"左边"，对另一个三角形必然是"右边"，所以 E=0 的像素恰好只归其中一个。实现上非常简单：对不是上边/左边的边，在比较前给 E 减去 1（定点最小单位），把 E ≥ 0 变成 E > 0：

auto isTL = [&](int a, int b) { i64 dx = X[b] - X[a], dy = Y[b] - Y[a]; return (dy == 0 && dx > 0) || dy < 0; }; // 上边：水平且向右；左边：向上 i64 b0 = (s.topLeft && !isTL(1, 2)) ? -1 : 0; i64 b1 = (s.topLeft && !isTL(2, 0)) ? -1 : 0; i64 b2 = (s.topLeft && !isTL(0, 1)) ? -1 : 0;

E4 的网格测试把这件事量化了：15×15 个四边形（450 个三角形）组成的网格，所有顶点都放在像素中心上，让共享边尽可能多地穿过采样点：

5.7 游戏实战：光栅化相关的几个工程问题

模型"闪点"

相邻三角形之间偶尔漏一个像素，通常不是光栅化器的问题（硬件是水密的），而是两个三角形的共享顶点坐标不完全相同：比如 LOD 接缝、地形块之间顶点高度不一致、顶点着色器里对同一顶点算出了不同结果（不同的计算顺序、precise 缺失）。

细长三角形

边函数测试浪费多、2×2 Quad 效率低（E8 实测只有约 48%），还容易产生插值走样。建模时避免长条三角形，程序生成网格时注意剖分方式。

保守光栅化

只要三角形和像素有任何重叠就算覆盖（而不只看中心）。用于体素化（GI）、光源分块剔除、遮挡剔除的软件光栅等"宁可多、不可漏"的场景。

CPU 软件光栅

很多引擎在 CPU 上跑一个低分辨率、只写深度的软件光栅器做遮挡剔除（如 Intel 的 Masked Occlusion Culling），原理正是本章的边函数 + 分块。

本章小结
  • 覆盖 = 采样点（默认像素中心）落在三角形内；部分覆盖但没盖住中心的像素不算，这是几何走样的根源。
  • 边函数 E 是二维叉积：同号即在内；它是线性函数，可增量计算、可整块判断；它还直接给出重心坐标。
  • 顶点吸附到定点亚像素网格（8 位），使边函数精确、水密、确定；E4 实测浮点边函数在大坐标下会漏画/重复。
  • Top-Left 规则决定边上的像素归谁，保证共享边的像素恰好被画一次（E4：2131 个边上像素零误差）。
  • 硬件用分块 + 层次化遍历，配合 Hi-Z 和 Quad 打包。
自测：为什么 D3D 要求 8 位亚像素精度，而不是 16 位？

精度越高，定点数需要的位数越多：坐标范围（含保护带）若为 ±16K 像素需要 15 位整数部分，再加 8 位小数共 24 位；边函数是两个坐标差的乘积，需要约 48 位的乘法器。精度再翻倍，乘法器和面积会显著增大。8 位亚像素（1/256 像素）已经远小于人眼能察觉的顶点抖动，是精度与成本的折中。

自测：一个三角形面积不为 0，却一个像素都没覆盖，可能吗？

可能，而且很常见：微小三角形或细长三角形可能夹在像素中心之间，一个采样点都没盖住。E8 里面积 0.5 像素的三角形，3000 个中有 1511 个零覆盖——但它们仍然走完了顶点着色、裁剪和三角形设置，这部分开销白白浪费了。这就是"远处物体要用 LOD 降面数"的直接原因。
