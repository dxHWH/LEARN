CHAPTER 10

GPU 硬件视角：IMR 与 TBR / TBDR

桌面 GPU 拿到一个三角形就立刻画；手机 GPU 先把整帧的三角形分到小块里，再一块一块在片上画完。

本章目标
  • 说清立即模式渲染（IMR）和分块渲染（TBR/TBDR）的流程差异
  • 理解 TBR 为什么能大幅节省带宽，以及"带宽 = 功耗 = 发热"对移动端的意义
  • 掌握 Load/Store Action、Memoryless、Framebuffer Fetch / Subpass 这些移动端专属概念
  • 理解 TBDR 的隐藏面消除（HSR），以及为什么 Alpha Test 在移动端格外昂贵
  • 知道 TBR 的代价：Binning 开销、中途读回帧缓冲导致的 Flush

10.1 两种架构

为什么手机要搞得这么复杂？因为访问 DRAM 是移动 SoC 上最耗电的操作之一：读写一次 DRAM 的能耗比片上 SRAM 高一到两个数量级，而手机的散热和电池都极其有限。桌面 GPU 有几百 GB/s 的独立显存和几百瓦的功耗预算，可以用大缓存和压缩硬扛；手机 GPU 只有几十 GB/s，还和 CPU 共享，于是选择从架构上减少带宽。

10.2 实测：一帧的显存流量

E12 用 E7 的统计数据（400 个随机方块、640×360）估算一帧的 DRAM 流量。模型很简化——IMR 每次深度读、深度写、颜色写都按 4 字节打到 DRAM，忽略缓存和压缩；TBR 只在每个 Tile 结束时写回 4 字节/像素的颜色：

soft_raster.exe · E12（简化模型）
画法（来自 E7）               IMR 流量 KB  TBR 流量 KB    IMR/TBR
Late-Z 随机顺序                         29173            900      32.4x
Early-Z 随机顺序                        29173            900      32.4x
Early-Z 前->后                            25162            900      28.0x
Early-Z 后->前                            70224            900      78.0x
Z-Prepass                                   50576            900      56.2x
MSAA4x Early-Z 随机（+Resolve）         121194            900     134.7x
按 60fps 换算：IMR(Early-Z 随机) ≈ 1709 MB/s，TBR ≈ 53 MB/s；移动端 DRAM 每 GB/s 约耗数百 mW，带宽就是功耗和发热。
🔬 怎么读这组数据
  • 这是上限估算：真实 IMR 有 L2 缓存、深度压缩（Hi-Z、平面方程压缩）和颜色压缩（DCC），实际流量会小得多；真实 TBR 还有 Binning 阶段读写图元列表的流量。但量级关系是可靠的。
  • Late-Z 和 Early-Z 随机顺序的 IMR 流量相同：深度测试的读取次数不变，Early-Z 省的是着色而不是深度带宽。
  • TBR 的流量与 Overdraw、绘制顺序、MSAA 都无关——这些都在片上消化了。这就是为什么在 TBR 上 MSAA 4× 几乎免费，而 IMR 上 MSAA 的流量是 4 倍。
  • 反过来，TBR 上 Overdraw 也不是零成本：它仍然消耗片上的 ALU 和纹理带宽（半透明片元每一层都要着色、都要采样纹理）。

10.3 Load / Store Action：告诉驱动哪些数据不用搬

TBR 在开始渲染一个 Tile 时，要决定 Tile 内存的初始内容；结束时要决定写不写回 DRAM。现代 API 让你显式声明：

动作选项带宽什么时候用
Load（开始）Clear0（片上直接清）每帧开始的颜色和深度（最常见）
DontCare0（内容未定义）确定会被完全覆盖，如全屏后处理的目标
Load读整个 RT需要在上一个 Pass 的结果上继续画
Store（结束）Store写整个 RT后面还要用：最终颜色、要采样的阴影贴图
DontCare / Memoryless0深度/模板（用完就扔）、MSAA 多采样缓冲（Resolve 后就不要了）
⚠️ 面试易错：每帧 Clear 是浪费吗？

在 IMR 上，Clear 要写整个缓冲（虽然有快速清除优化）；在 TBR 上 Clear 是最便宜的选择——它只是把 Tile 内存初始化，反而是"不 Clear"（Load）要把上一帧内容从 DRAM 读进来。所以移动端的规范是：每个 Pass 开始时颜色和深度都 Clear（或 DontCare），结束时深度 DontCare。Unity 里"相机不清除"或"Clear Flags = Don't Clear"在移动端是性能陷阱。

Vulkan 的 Subpass 和 Metal 的 Programmable Blending / Tile Shader（GLES 的 EXT_shader_framebuffer_fetch）更进一步：让后一个 Pass 直接读取当前像素在 Tile 内存里的值（例如 G-Buffer），整个延迟渲染可以在一个 Tile 里完成、G-Buffer 永远不写回 DRAM（Memoryless G-Buffer）。

10.4 HSR：硬件替你做 Z-Prepass

TBDR（PowerVR 的 HSR、Apple GPU、Mali 的 FPK—Forward Pixel Kill、Adreno 的 LRZ 等机制类似）在一个 Tile 的所有图元光栅化完之后、着色之前，先做一次完整的可见性判定，只为每个像素最终可见的那个不透明片元着色。效果相当于 E7 里"Z-Prepass"的结果，却不需要你多画一遍——所以：

  • 在 TBDR 上，不透明物体的前后排序收益变小（但仍建议大致排序，因为并非所有移动 GPU 的 HSR 都同样彻底，且 Binning 有容量上限）；
  • 手动 Z-Prepass 在 TBDR 上通常是纯开销；
  • Alpha Test（discard）和写深度会打断 HSR：硬件无法在着色前确定这个片元是否真的不透明，只能让它和它后面的东西都去着色。这就是"移动端少用 Alpha Test、多用 Alpha Blend 或者干脆用实体几何"的原因。

10.5 TBR 的代价与陷阱

Binning 开销

所有顶点要先处理一遍、结果（图元列表 + 变换后的顶点）写入 DRAM 再读回来。顶点越多，这部分越贵——TBR 对高面数场景比 IMR 更敏感。部分 GPU 只在 Binning 时计算位置（Position-only shading），把其他属性推迟到渲染阶段。

中途读回帧缓冲

在一个 Pass 中间去采样当前的颜色或深度（"抓屏"做扭曲、读深度做软粒子），会强制把所有 Tile 写回 DRAM 再重新开始（Flush / Resolve）。一帧里 RenderTarget 切来切去是移动端最常见的性能杀手。

巨大的三角形

一个全屏三角形会被登记到所有 Tile 里；大量覆盖全屏的半透明面片会让每个 Tile 的图元列表都很长。

Tile 内存容量

MRT 数量、像素格式（如 RGBA16F）、MSAA 倍数都会占用 Tile 内存；超过容量时驱动会自动缩小 Tile 尺寸，增加 Tile 数和开销。

10.6 游戏实战：移动端渲染清单

🎮 游戏实战：一个 MOBA 后处理的例子

一个常见的反模式：Bloom 需要降采样链（1/2、1/4、1/8……），每级一个 RT；再加上屏幕扭曲（要抓屏）、颜色校正、FXAA，每帧切换十几次 RT。在 TBR 手机上，这可能比整个场景渲染还贵。优化方向：Bloom 用更少的级数、在低分辨率 RT 上完成；扭曲特效用"预先渲染到单独 RT"而不是抓取主屏；颜色校正（LUT）、暗角、FXAA 合并成一个最终 Pass；能用 Framebuffer Fetch 的效果就别抓屏。

本章小结
  • IMR：三角形按提交顺序流过管线，深度/颜色直接读写 DRAM，靠大缓存和压缩扛带宽。
  • TBR/TBDR：先 Binning 把整帧图元分到 Tile，再逐 Tile 在片上完成光栅化、深度、混合、MSAA，只写回最终颜色；TBDR 还在着色前做 HSR。
  • E12 简化模型：IMR 流量是 TBR 的 28～78 倍，MSAA 4× 时 134 倍；TBR 的 DRAM 流量与 Overdraw、顺序、MSAA 无关。
  • Load/Store Action 决定 Tile 内存的进出；Clear 和 DontCare 在 TBR 上最便宜；Memoryless 让深度和 MSAA 缓冲根本不占系统内存。
  • TBR 的敌人：顶点过多（Binning）、中途读回帧缓冲（Flush）、Alpha Test（打断 HSR）、RT 频繁切换。
自测：同一个游戏，为什么 PC 上很流畅的"屏幕扭曲"特效在手机上掉帧严重？

扭曲需要采样"当前已经画好的屏幕颜色"（GrabPass / Opaque Texture）。在 IMR 上，这只是一次拷贝或直接采样已有 RT；在 TBR 上，它强制结束当前 RenderPass，把所有 Tile 的颜色（可能还有深度）写回 DRAM，再开一个新的 RenderPass 把内容读回来——两次整屏的带宽，还打断了 HSR 和 MSAA 的片上优势。手机上应限制扭曲的使用，或改用不需要读屏的近似做法。

自测：TBR 是不是在所有场景下都比 IMR 好？

不是。TBR 用 Binning 的开销换取帧缓冲带宽：顶点数极多、三角形极小的场景（高面数模型、大量曲面细分），Binning 的图元列表读写会变得很贵；需要在一帧中频繁读回帧缓冲的渲染方式也不适合 TBR。桌面 GPU 选择 IMR + 大缓存，是因为它们有足够的带宽和功耗预算，而且要应对极高的几何复杂度。实际上现代桌面 GPU 也引入了部分分块思想（如 NVIDIA 自 Maxwell 起的 Tiled Caching）。
