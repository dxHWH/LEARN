CHAPTER 01

一帧画面是怎么来的

16.6 毫秒里，CPU 准备"画什么"，GPU 决定"每个像素长什么样"。

本章目标
  • 说清一帧从游戏逻辑到屏幕显示的完整链路：游戏线程 → 渲染线程 → 驱动 → 命令缓冲 → GPU → 交换链
  • 理解 Draw Call 的真实开销在哪里，以及合批 / Instancing / SRP Batcher 分别在省什么
  • 理解 GPU 的 SIMT 执行模型：Warp、延迟隐藏、分支发散，以及它们对 Shader 写法的影响
  • 建立"光栅化管线 = 以物体为序"的直觉，并能和光线追踪对比

1.1 两颗处理器的接力：CPU 和 GPU 怎样分工

假设你在玩一局 MOBA，屏幕上有地图、10 个英雄、小兵、技能特效和 UI。每一帧，引擎都要回答两个问题：

  1. 画什么、按什么顺序画——这是 CPU 的工作。游戏线程更新逻辑（移动、技能、动画），渲染线程据此做视锥剔除、按材质排序、合批，再把"设置状态 + 绘制"翻译成图形 API 调用。
  2. 每个像素是什么颜色——这是 GPU 的工作。它接收命令，把成千上万个三角形变换、光栅化成几百万个像素，并为每个像素运行着色器。

两者之间隔着一条命令缓冲（Command Buffer）：CPU 往里写命令，GPU 从里读命令，两边是异步的。CPU 调用 Draw 时 GPU 并不会马上开始画——命令只是被记录下来，稍后才被提交、执行。

这张图有两个直接的工程含义：

  • 帧率取决于最慢的那条泳道。游戏线程慢叫"逻辑瓶颈"，渲染线程/驱动慢叫"CPU 渲染瓶颈"（通常是 Draw Call 太多），GPU 慢叫"GPU 瓶颈"（顶点、填充率或带宽）。优化之前必须先知道是哪一条——第 12 章专门讲定位方法。
  • CPU 读 GPU 的结果代价极高。如果 CPU 在帧 N+1 里同步读回帧 N 的渲染结果（比如 ReadPixels、遮挡查询立即取结果），就会让流水线"排空"：CPU 停下来等 GPU 画完，GPU 画完又等 CPU 发新命令。这就是为什么遮挡查询结果通常延迟一两帧使用。

1.2 Draw Call：一条命令为什么会贵

一次 Draw Call 就是 CPU 对 GPU 说"用当前的状态，画这些三角形"。真正贵的不是 Draw 这一下本身，而是它前面要准备的东西和驱动做的工作：

开销来源具体是什么典型优化
状态切换换 Shader 程序、混合/深度状态、渲染目标；驱动可能要重新编译/链接管线状态按材质/Shader 排序，减少 SetPass；DX12/Vulkan 预编译 PSO
资源绑定绑定纹理、常量缓冲、顶点缓冲；上传每个物体的矩阵等常量SRP Batcher（常量常驻 GPU，只更新变化的部分）、Bindless
驱动校验旧 API（GL/DX11）每次调用都要检查状态合法性、跟踪资源依赖换现代 API，命令缓冲多线程录制
提交与同步命令缓冲刷新、用户态到内核态切换减少 flush，批量提交

减少 Draw Call 的三种常见手段，省的东西各不相同：

静态合批

离线把共享材质的静态网格合并成一个大网格。省 Draw Call，代价是内存变大（每份实例的顶点都复制了一份）、无法单独剔除。

动态合批

每帧在 CPU 上把小网格的顶点变换到世界空间后拼起来。省 Draw Call，但CPU 要做顶点变换，只适合顶点很少的物体。

GPU Instancing

一次 Draw 画 N 份同一网格，每份的矩阵/颜色放在实例缓冲里，由顶点着色器用 SV_InstanceID 读取。适合草、树、小兵这种同网格大量重复的物体。

SRP Batcher

不减少 Draw Call 数量，而是让每个 Draw Call 变便宜：材质常量常驻显存，只在变化时更新，相同 Shader 变体的物体之间不再重复设置状态。

⚠️ 面试易错

"合批就是为了减少 Draw Call"只说对了一半。更准确的说法是：合批是为了减少 CPU 端每次绘制的准备开销（主要是状态切换和常量上传）。在 DX12/Vulkan/Metal 下单次 Draw 本身已经很便宜，真正的成本更多在 SetPass（换材质/Shader）。所以面试官常追问："SRP Batcher 不减少 Draw Call，为什么也能提速？"——答案就是它减少的是每次 Draw 之间的状态设置。

1.3 GPU 为什么快：成千上万个"慢而简单"的线程

CPU 为了让一个线程尽可能快，花大量晶体管做分支预测、乱序执行和大缓存；GPU 反其道而行：把晶体管堆成大量简单的计算单元，同时跑成千上万个线程，用"线程多"来掩盖"内存慢"。

这个模型直接解释了 Shader 编写里的几条经验：

  • 分支发散（Divergence）：同一 Warp 的线程如果走了 if 的不同分支，硬件只能两条分支都执行，用掩码屏蔽不该写结果的线程。所以"按像素随机的分支"很贵，而"按材质/按 Draw Call 一致的分支"（uniform branch）几乎免费。
  • 寄存器压力与 Occupancy：一个复杂 Shader 用了很多寄存器，SM 上能同时驻留的 Warp 就变少，掩盖延迟的能力就下降。这是"Shader 变复杂，即使 ALU 不是瓶颈也变慢"的常见原因。
  • 像素着色器按 2×2 Quad 打包：一个 Warp 的 32 个线程其实是 8 个 2×2 像素块。第 6 章会看到，这是导数 ddx/ddy 能工作的前提，也是小三角形浪费的根源。
🧠 深入：统一着色器架构

早期 GPU（DX9 时代）有专门的"顶点单元"和"像素单元"，场景顶点多时像素单元闲着，反之亦然。从 DX10 / Xbox 360 开始，GPU 改为统一着色器架构：同一批计算单元按需运行顶点、像素、计算着色器。今天说"管线有 VS、PS 两个阶段"指的是逻辑阶段，物理上它们跑在同一批 SM 上。

1.4 可编程与固定功能：哪些能写代码，哪些只能配置

回到图 0-1，管线里的阶段分两类：

类型阶段你能控制什么
可编程顶点着色器、（外壳/域/几何着色器）、像素着色器、计算着色器；新架构下的任务/网格着色器任意代码：变换、光照、采样、discard、写深度
固定功能、可配置输入装配、裁剪、透视除法、视口变换、背面剔除、光栅化、深度/模板测试、混合只能设置状态：剔除模式、深度函数、混合因子、模板操作、多重采样数……

固定功能阶段之所以不开放编程，是因为它们是极高频、极规则的操作（每秒数十亿次的覆盖测试、深度比较），做成专用硬件比通用 ALU 快一到两个数量级、也更省电。这也解释了为什么"在 PS 里 discard"或"在 PS 里写深度"会破坏性能：你让一个本可以在固定硬件里提前完成的决定，被迫推迟到可编程阶段之后（第 8 章）。

1.5 两种画法：光栅化与光线追踪

光栅化的核心优势是数据访问高度规则：一个三角形覆盖的像素在屏幕上是连续的一片，访问的纹理也在一小块区域里，缓存命中率极高；光线追踪的光线会四散到场景各处，访存随机。这正是光栅化能在手机上以 60fps 跑的原因，也是本书只讲光栅化管线的原因。

1.6 游戏实战：一局 MOBA 的一帧里有什么

以一款移动端 MOBA 为例，一帧通常由十几个 Pass 组成（不同项目差异很大，下面是一种典型结构）：

#Pass做什么本书对应
1Shadow Map从主光源方向只写深度（英雄、小兵、建筑）第 11 章
2不透明物体（前向）地形、建筑、角色；从前往后排序以利用 Early-Z第 8 章

6UI血条、技能按钮、小地图；大量半透明、Overdraw 高第 9、12 章
🎮 游戏实战：为什么 MOBA 手游这么在意 Overdraw 和带宽

MOBA 镜头是固定俯视角，屏幕中央经常同时出现十几个技能特效叠在一起，团战时半透明粒子的 Overdraw 能达到十几层；而手机 GPU 的带宽只有桌面显卡的几分之一、还要和 CPU 共享、发热就降频。所以手游渲染优化的第一优先级通常是"少写像素、少读写显存"，而不是"少算几条 ALU 指令"。第 10 章的 TBR 架构和第 12 章的优化清单都是从这个约束出发的。

本章小结
  • CPU 决定画什么（剔除、排序、录制命令），GPU 决定每个像素长什么样；两者通过命令缓冲异步协作，通常错开 1～2 帧。
  • 帧率由最慢的泳道决定；CPU 同步读 GPU 结果会让流水线排空。
  • Draw Call 贵在状态切换、资源绑定和驱动校验；静态合批、动态合批、Instancing、SRP Batcher 省的东西各不相同。
  • GPU 用 SIMT + 大量驻留 Warp 来掩盖访存延迟；分支发散和寄存器压力是 Shader 性能的两大隐形杀手。
  • 固定功能阶段（光栅化、深度测试、混合）比可编程阶段快得多，破坏它们的"提前决定"会付出代价。
自测：GPU Instancing 和静态合批都能减少 Draw Call，什么情况下选哪个？

看是否是同一个网格和内存预算。大量重复的同一网格（草、树、小兵）用 Instancing：只存一份顶点，实例数据很小，还能逐实例剔除。不同网格但同材质的静态物体（场景摆件）用静态合批：能合成一次绘制，但要付出顶点数据复制的内存，且合并后整体剔除。

自测：为什么说"一个 Shader 里写了 if 不一定慢"？

分支的代价取决于同一 Warp 内的线程是否走同一条路。如果条件来自常量（材质参数、关键字），整个 Draw Call 的所有线程走同一分支，只执行一侧，几乎没有代价；如果条件按像素随机变化（例如依赖噪声纹理），同一 Warp 内两侧分支都要执行，代价接近两侧之和。
