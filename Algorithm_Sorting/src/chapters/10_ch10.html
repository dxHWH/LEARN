PART SIX

第六部分　游戏客户端里的排序

面试官问完原理，往往会接一句“你在项目里怎么用排序”。这一部分给出六个真实场景：每个场景里排序都不只是“调一下 std::sort”。

CHAPTER 10

六个实战场景

渲染队列、透明物体、UI 层级、帧同步、排行榜、碰撞粗检测，再加上小栈线程和内存分配这两条工程约束。

本章目标
  • 能设计一个 64 位渲染 sort key，并解释每个字段的排序意图
  • 能说清帧同步里排序导致不同步的原因和解决办法
  • 知道帧间相干性（数据在帧与帧之间变化很小）怎么用于加速排序

10.1 渲染队列：64 位 sort key + 基数排序

每帧要提交几千到几万个 draw call。提交顺序会影响三件事：

  • 状态切换开销：切换 shader、材质、纹理都很贵。相同材质的物体排在一起，就能少切换几次。
  • Overdraw：不透明物体从近到远绘制，后画的远处像素会被深度测试（Early-Z）提前剔除，省掉片元着色。
  • 正确性：半透明物体必须从远到近绘制，否则混合结果是错的。

这几个目标有优先级：先分渲染层（背景、世界、特效、UI），层内先不透明后透明；不透明物体优先按材质归并，透明物体只能按深度。经典做法是把这些字段按优先级从高到低压进一个 64 位整数，只对这个整数排序：

uint64_t make_key(uint32_t layer, bool transparent, float depth01, uint32_t mat, uint32_t mesh) { uint32_t d = uint32_t(depth01 * 0xFFFFFF); // 深度量化到 24 bit（depth01 ∈ [0,1]） uint64_t k = (uint64_t(layer & 0xF) << 60) | (uint64_t(transparent) << 59); if (transparent) k |= (uint64_t(0xFFFFFF - d) << 35) | (uint64_t(mat & 0x7FFF) << 20) | (mesh & 0xFFFFF); // 远 → 近 else k |= (uint64_t(mat & 0x7FFF) << 44) | (uint64_t(d) << 20) | (mesh & 0xFFFFF); // 材质优先 return k; } struct SortItem { uint64_t key; uint32_t index; }; // 16 字节，只排它，不排 64 字节的 DrawItem // 每帧：items[i] = { make_key(...), i }；radix_sort_u64(items, tmp, n, [](auto& x){ return x.key; }); // 提交：for (auto& it : items) submit(drawList[it.index]);
  • 只排 (key, index)，不排大结构体：交换 16 字节比交换 64 字节便宜。本例中 DrawItem 只有 64 字节，差距约 10%；结构体越大、拷贝越贵（比如带 std::string），差距越大。
  • 基数排序非常适合 sort key：键定长、数据量大、每帧都要排。缓冲区用帧分配器（frame allocator）每帧复用，不要每帧 new。高位字节经常全部相同（比如所有物体都在同一层），可以跳过这些趟，demo 里就是这样做的。
  • 深度只量化成 24 bit 是有意为之：远处物体的精确先后对 Early-Z 影响很小，省下的位可以留给材质。
  • 引擎里的对应物：UE 的 FMeshDrawCommand 带有排序键，Unity 按 Sorting Layer、Order in Layer、Render Queue、距离等依次决定顺序，思路是一致的。

10.2 透明物体与粒子：排序只能解决一部分

  • 按物体排序（画家算法）只能保证物体之间的先后。两个相互穿插的透明物体，无论谁先画都会有一部分是错的；要彻底解决得用 OIT（顺序无关透明），或者在美术上避免穿插。
  • 排序依据一般用“包围盒中心到相机的距离平方”，不需要开方，因为平方保持大小顺序。
  • 大规模粒子在 GPU 上排序：双调排序（bitonic sort，O(n log² n)，但比较的位置是固定的，适合大规模并行）或 GPU 基数排序。数量大但精度要求不高时，也可以用第 7 章的深度分桶做近似排序。
  • 帧间抖动：两个透明物体距离很接近时，相机稍微一动，它们的顺序就来回交换，画面出现闪烁。可以给距离加一个滞后阈值，或者用稳定的次级键（如实体 id）决出平局。

10.3 UI 层级：稳定性决定遮挡关系

UI 节点先按 layer（或 sortingOrder）排，同一层内必须保持创建或层级顺序，后创建的盖在上面。用不稳定排序时，同层节点的先后会被打乱，表现为弹窗被背景盖住、点击穿透、每次打开顺序不一样。

E6 · 64 个 UI 节点，layer 只有 0/1/2，按 layer 排序
std::sort    layer0: N00 N21 N57 N03 N30 N54 N06 N39 N24 N09 N33 N51 ...
stable_sort  layer0: N00 N03 N06 N09 N12 N15 N18 N21 N24 N27 N30 N33 ...
两种结果有 57 / 64 个位置不同（同层遮挡关系被打乱 → UI 闪烁 / 层级错乱）

两种修法：①用 std::stable_sort；②把原始顺序放进键里，用 std::tie(layer, siblingIndex) 比较，这样任何排序算法都会得到同一结果。第二种更好：结果不依赖算法是否稳定，也避开了 stable_sort 的内存分配。

面试注意：元素少时 std::sort 也“看起来稳定”

元素个数不超过插入排序阈值（MSVC 32、libstdc++ 16）时，std::sort 实际上只做了一遍插入排序，结果恰好是稳定的。所以测试时 10 个节点一切正常，上线后 100 个节点就乱了。E6 特意用了 64 个节点。“这次碰巧稳定”不等于“保证稳定”。

10.4 帧同步：平局顺序必须在所有客户端一致

帧同步（lockstep）的 MOBA 中，所有客户端只交换玩家输入，各自运行同一套逻辑，要求每帧的计算结果逐位一致。如果某段逻辑“按威胁值排序，攻击第一个敌人”，而两个敌人的威胁值相等，那么谁排第一取决于排序算法如何处理平局：

E10 · 2000 个单位按威胁值排序（威胁值只有 10 档，大量平局）
只比 score（有平局）：
  std::sort (MSVC)         hash=0867a2906420d9bb  首个目标 id=1115
  快排-工程 (另一种实现)    hash=a9fd6e705baa4d93  首个目标 id=1228
  堆排序                   hash=1dddafa554ba0db7  首个目标 id=1161
  stable_sort              hash=32655e286d26c10b  首个目标 id=1
score 相同再比 id（全序）：
  std::sort / 快排-工程 / 堆排序 / stable_sort   hash 全部 = 32655e286d26c10b  首个目标 id=1

帧同步排序检查清单

  1. 比较器必须是全序：最后一个比较字段用逻辑 id（网络 id / 创建序号）兜底，保证不存在“谁也不小于谁”的两个元素。
  2. 不要用 Entity 的内存地址或运行时句柄排序：地址受 ASLR 和分配顺序影响，各端不同；客户端独有的实体（特效、本地 UI 实体）会让槽位编号错开。
  3. 不要遍历哈希容器的顺序：std::unordered_map 的遍历顺序取决于哈希函数、桶数和插入历史，不同 STL 实现各不相同。要么先收集到数组里按 id 排序，要么用有序容器。
  4. 排序键里不要有浮点运算的结果：距离等浮点值在不同编译器、不同指令集下可能有末位差异，平局判断会不同。帧同步逻辑一般使用定点数。
  5. 想要绝对保险，就各端用同一份自己实现的排序（例如一份固定的归并排序），不依赖平台 STL。
游戏客户端视角：这类不同步最难查

平局只在特定数据下出现，两端大多数时候结果一致，只有偶尔一局在某一帧分叉。排查时要在每帧对关键状态做哈希，不一致时把前后几帧的“排序输入 + 输出”都 dump 出来对比。本系列 Q04（ECS 怎么 debug）里“按 NetId 决胜”的修复思路，解决的也是同一类问题。

10.5 排行榜与 Top-K

  • 只显示前 K 名：用 partial_sort 或大小为 K 的堆（E9：100 万人取前 100 名，0.22 ms / 0.41 ms，全量排序 58.61 ms）。
  • 只要第 K 名的分数线（例如“前 10% 的分数线”）：用 nth_element，平均 O(n)。
  • 单个玩家分数变化：不必整体重排。在有序数组里删掉旧位置、二分找到新位置插入，O(log n) 查找 + O(n) 移动；如果改动很频繁，就换成平衡树、跳表这类有序结构（服务端常用 Redis 的 ZSet，底层是跳表）。
  • 好友榜：好友数量一般不超过几百，直接 std::sort 就行。这时可读性比优化更重要。
struct Entry { int score; int id; }; void top_k(std::vector& v, size_t k) { k = std::min(k, v.size()); std::partial_sort(v.begin(), v.begin() + k, v.end(), [](const Entry& a, const Entry& b) { return a.score != b.score ? a.score > b.score : a.id < b.id; // 全序：名次稳定可复现 }); // v[0..k) 就是前 k 名，且已经有序；v[k..) 的顺序不确定 }

10.6 Sweep and Prune：利用帧间相干性

碰撞检测的粗检测阶段要找出“包围盒可能相交的物体对”。Sweep and Prune（SAP）把每个物体的 AABB 投影到 x 轴上，得到一个区间 [min, max]。把所有端点排序，然后从左到右扫一遍：遇到 min 就把物体加入“活动集”，遇到 max 就移出；加入时与活动集里的每个物体都构成候选对。

物体在一帧内只移动很小的距离，所以上一帧排好的端点序列这一帧几乎仍然有序。用插入排序增量更新，代价约为 O(n + 交换次数)，而且每发生一次相邻交换，就对应一对区间开始或停止重叠，可以顺便增删候选对。Bullet 物理引擎的 btAxisSweep3 就是这样增量维护的。这与 E8 的结论一致：近乎有序时插入排序 0.005 ms，std::sort 0.062 ms。

注意它的退化

大量物体同时剧烈运动（爆炸、传送、场景切换）时，相干性没有了，插入排序会退化成 O(n²)。稳妥的做法是：如果一帧的交换次数超过阈值，或者检测到大规模传送，就改用 std::sort 整体重排。

10.7 两条工程约束：栈和内存

小栈线程不能深递归

E4：朴素快排 + 有序输入，64 KB 栈大约 500 层就溢出，1 MB 栈 2 万个元素就溢出。Job 线程、纤程、协程的栈往往只有几十 KB。

对策：用 std::sort（深度有限）；自己实现时递归短边、加深度限制，或者改成迭代。

每帧分配是性能杀手

std::stable_sort 会尝试分配 O(n) 的临时缓冲；归并和基数排序都需要 O(n) 缓冲。

对策：缓冲区放在帧分配器或成员变量里复用；或者用“键 + 原始下标”的全序比较，配合 std::sort 得到确定的结果。

本章速记
  • 渲染队列：64 位 sort key（层 → 透明 → 材质 / 深度 → 网格）；只排 (key, idx)；基数排序（E8：20 万条 1.72 ms 对 9.66 ms）。
  • 透明物体从远到近，不透明物体从近到远；穿插问题排序解决不了。
  • UI 同层必须稳定：stable_sort 或在键里加 siblingIndex；n ≤ 16/32 时 std::sort 碰巧稳定，这是陷阱。
  • 帧同步：比较器必须是带 id 兜底的全序；不按地址排序，不依赖哈希容器的遍历顺序。
  • Top-K 用 partial_sort / 堆；SAP 用插入排序做增量更新，剧烈变化时退回整体排序。
