CHAPTER 20

手感：输入缓冲、宽容窗口与反馈时机

问题 ④：“当前没有输入 / 输出缓冲，怎么优化手感？”——手感不是玄学，它可以拆成三条可以量化的链：输入什么时候被接受（宽容窗口：预输入、土狼时间）、动作怎么响应（跳跃曲线、取消窗口、强制时间）、反馈什么时候出现（预表现、动画、镜头、顿帧）。本章用“成功率曲线”量化 Demo 现状，再给出一套不写代码也能讲清楚的改造方法。

本章目标
  • 把“手感好不好”拆成输入延迟、宽容窗口、动作曲线、反馈时机四个可调的部分
  • 用 F2 / F3 讲清土狼时间和跳跃缓冲对“按了没反应”比例的影响
  • 用 F4 讲清可变跳高、下落加重、顶点悬停分别改变了什么
  • 说清“输出侧”的反馈设计：预表现、动画过渡、镜头缓冲、顿帧，以及它们为什么要由同一个事件驱动

20.1 口径：30 秒怎么讲 · 现状 vs 理想

面试口播

现状Demo 现状：各状态在按键的那一帧直接读按键，只在“当前状态允许”时生效——跑出平台边缘的下一帧就切到下落、按跳无效；落地前按的跳会被丢掉；跳跃高度固定，轻按和长按一样高；动作之间没有预输入。

量化：我用模型算过，假设玩家在跑出边缘后平均 20 ms（标准差 40 ms）按跳，没有土狼时间时只有 [[f2.p0.c0|.0f]]% 能跳起来，加 0.1 s 土狼时间是 [[f2.p0.c100|.0f]]%；落地前平均 30 ms 按跳的玩家，没有缓冲只有 [[f3.p0.b0|.0f]]% 能连跳，加 0.12 s 缓冲是 [[f3.p0.b120|.0f]]%。

理想正确做法：输入先变成带时间戳的“意图”进入缓冲；状态机在可以响应的时候消费最近 0.1~0.15 s 的意图；离开地面 / 墙后保留 0.1 s 的宽限；跳跃做成可变高度并加重下落；所有反馈（尘土、音效、镜头、震动）由同一个“起跳 / 落地 / 命中”事件在同一帧触发。

20.2 手感的四条链

① 输入延迟从哪里来

环节Demo 中的情况（60 fps、物理 50 Hz）最大延迟怎么降
按下 → 被读到在下一帧的 Update 里读到1 帧（16.7 ms）无法避免；高帧率降低
读到 → 逻辑生效状态切换在当帧；但 Fall 落地帧切到 Idle 后，Idle 要下一帧才检查跳跃0~1 帧请求-提交后立即补一次本帧更新；状态检查顺序合理
逻辑 → 物理生效Update 里设速度，下一个物理步才产生位移1 个物理步（20 ms）起跳这类一次性动作可以同时修正当前位置；或提高物理频率
物理 → 画面刚体插值让画面落后物理最多一步≤ 20 ms对玩家角色可以考虑外插或关闭插值 + 提高物理频率（取舍）
画面 → 显示垂直同步、渲染队列、显示器1~3 帧限制预渲染帧数、低延迟模式（平台相关）

Demo 里“按跳 → 画面里角色开始上升”最坏要经过 1 帧 + 1 帧 + 1 个物理步 + 插值，约 50~70 ms，这还没算显示链路。所以宽容窗口不是“放水”，而是在补偿玩家看不到的那几十毫秒。

20.3 早按：跳跃缓冲（预输入）

场景：玩家在快落地时按跳，想落地即起跳。Demo 的规则是：落地那一帧下落状态切到待机，待机下一帧才检查“跳跃键是否在这一帧按下”——所以按键必须恰好落在落地之后的帧上，早一帧都不行。用模型扫按键时刻（相对着地时刻 0，60 fps，帧相位均匀取 400 个）实测 F3 模型：

做法：输入采样成“意图 + 时间戳”放进缓冲；每个可以起跳的时刻（着地、滑墙、二段跳可用）去缓冲里找“最近 N 秒内的跳跃意图”，找到就消费掉。缓冲长度常见 0.1~0.15 s：太短没效果，太长会出现“我早就不想跳了它还跳”。同一套缓冲也服务于攻击连段、冲刺、技能（第 3 章“取消窗口”）。

20.4 晚按：土狼时间

场景：玩家跑出平台边缘之后才按跳（人的反应 + 显示延迟让这非常常见）。Demo 在离地的那一帧就切到下落，下落状态不响应跳跃 实测 F2 模型：

做法：感知层记录“离开地面多久了”（第 17 章）；跳跃判定从“现在着地”改成“离地时长 < 土狼时间 且 本次离地不是因为起跳”。常见 0.08~0.12 s。同样的思路用于墙（墙宽限，第 18 章）和攀爬边缘。

两个窗口一起用时的细节

① 起跳后立即清空土狼计时，否则在土狼时间里可以“二段跳”；② 跳跃缓冲与土狼时间同时生效时，“落地前按的跳”在着地那一刻被消费，不要再等待下一帧；③ 窗口长度都按“时间”而不是“帧数”配置，否则高帧率玩家的窗口会变短。

20.5 动作曲线：同样的初速度，不同的“手感”

20.6 输出侧：反馈的时机与“缓冲”

“输出缓冲”可以理解为：逻辑结果与玩家感知之间的时间管理。原则只有一条——玩家的输入要在当帧得到可见、可听的回应，哪怕逻辑结果稍后才确定。

手段做法Demo 现状
预表现按下的那一帧就播起跳尘土、挥刀音效的起音、角色姿态的第一帧；联网游戏里这是“客户端预测”的表现部分动画由状态切换驱动，基本是当帧；没有尘土 / 音效
动画过渡逻辑状态立即切换，动画用极短的过渡（0~50 ms）或直接切；需要平滑时用“姿态匹配”而不是长混合所有转移过渡时间为 0，干脆利落 ✔
挤压拉伸起跳时纵向拉伸、落地时横向压扁 0.1 s无
镜头缓冲死区、前瞻、竖直方向只在落地后跟随、平滑阻尼——让镜头“跟着意图”而不是“跟着每一帧的位置”Cinemachine 默认跟随
顿帧与震屏命中瞬间攻防双方减速 50~100 ms，镜头脉冲震动无（且需要先有速度修正器栈，第 7 章）
震动与音效手柄短震、分层音效（起音 + 本体 + 尾音）无
为什么所有反馈要由同一个事件驱动

如果尘土由动画事件播、音效由状态 Enter 播、镜头由速度变化触发，它们会在不同的帧出现（第 4 章说过动画事件按帧量化、可能被打断）。正确的结构是：状态机产生语义事件（起跳、落地、命中、被弹反），一个“反馈导演”订阅这些事件，在同一帧触发所有表现，并统一做节流（同一帧多次命中只震一次）。这也让“关闭震屏”“降低特效”这类设置只改一处。

20.7 改造路线：不写代码也能讲清楚的五步

怎么验证：① 调试 HUD 实时显示缓冲队列、离地时长、当前状态；② 录制输入回放，同一段操作在改动前后各跑一次；③ 像本章一样画“成功率曲线”——这比“感觉好多了”有说服力；④ 小范围试玩时记录“按了没反应”的次数（输入被丢弃的日志）。

20.8 面试防守

Q20-1　你怎么理解手感？

L2　我会拆成四件可调的事：输入延迟（多快生效）、宽容窗口（多宽容）、动作曲线（加速度、跳跃弧线、取消窗口）、反馈（玩家能不能立刻看到和听到）。“手感差”通常可以落到其中一项上，比如“按了没反应”多半是宽容窗口问题，“飘”多半是动作曲线问题。

Q20-2 → Q20-3　土狼时间和跳跃缓冲是什么？会不会让游戏变简单？

L2　土狼时间：离开平台后一小段时间内仍允许起跳；跳跃缓冲：落地前按的跳在落地时生效。它们补偿的是人的反应和显示链路的几十毫秒延迟。我算过：按键平均晚 20 ms 的玩家，没有土狼时间只有约四分之一能跳起来，加 0.1 s 后超过 95%。

L3　不会变简单，因为它们只修正“玩家意图正确、但时机差了几十毫秒”的情况，不改变跳跃能力本身；真正的难度由关卡度量决定。窗口过长才有问题：土狼时间 0.15 s 时角色已经跑出边缘 1 m，看起来像在空中起跳。

Q20-4　缓冲多长合适？用帧还是秒？

L2　用秒配置，常见 0.1~0.15 s；用帧数会让 144 Hz 玩家的窗口只有 60 Hz 玩家的一半。具体长度按动作调：跳跃缓冲可以略长，攻击连段的预输入要配合取消窗口，太长会出现“不想出的招也出了”。最好用成功率曲线 + 试玩数据定。

Q20-5　为什么跳跃要可变高度？怎么做？

L2　让玩家用一个键表达“小跳”和“大跳”，这是精确平台跳跃的基础。常见两种做法：松键时如果还在上升，把上升速度乘一个系数（如 0.5）；或者按住期间维持上升速度一段时间（约 0.2 s），松键后才开始受重力减速。再配合下落加重，让弧线“上升灵活、下落干脆”。Demo 是一次性给速度，所以轻按和长按都是约 3.9 m。

Q20-7　输入在 Update 还是 FixedUpdate 读？

L2　在 Update 读（“按下”只在一帧为真，FixedUpdate 可能这一帧不执行而漏掉），读到后存成带时间戳的意图，由物理步或状态机在合适的时机消费。新输入系统也支持在固定步里处理事件，但同样要注意不能丢失只持续一帧的按下事件。

常见错误回答

错误：“手感就是调参数，多试几次就好了。”

问题：没有方法，面试官无法判断你能不能把手感做好。

更好的回答：“我先把手感拆成延迟、窗口、曲线、反馈四部分，先补结构（意图缓冲、带时间的感知、反馈事件），再用成功率曲线和录制回放去调参数。”

20.9 发散场景题

场景 20-1　格斗游戏的“搓招”（↓↘→ + 拳）怎么识别？

考点：输入缓冲的进阶——指令序列识别。

输入缓冲保存最近约 0.5 s 的方向与按键历史（带帧号）；每帧从最新输入往回匹配指令模板（允许中间夹杂其他方向、每一步有时间上限）；多个指令同时匹配时按优先级（必杀技 > 特殊技 > 普通技）；为了宽容，按键可以比最后一个方向稍早或稍晚几帧。

场景 20-2　移动端虚拟摇杆的平台游戏，手感怎么补？

考点：触屏的输入特性。

触屏没有触觉反馈、方向不精确：加大宽容窗口（土狼、缓冲适当加长）、方向输入加死区和吸附（八方向量化）、跳跃按钮区域大于视觉区域、关键操作给强烈的视觉 / 震动反馈；必要时增加辅助（自动抓边、自动冲刺）。

场景 20-3　联机对战的动作游戏，宽容窗口还能用吗？

考点：手感与网络的结合。

能，而且更重要：本地先预测执行（含土狼、缓冲），服务器用相同规则校验（服务器也要知道“离地多久”这类状态）；规则必须在两端一致且可确定，否则会频繁回滚纠正。窗口的时间基准要用逻辑帧 / 服务器时间，而不是本地渲染时间。

自测 1：为什么 Demo 里“落地那一帧按跳”也会失败？落地帧是下落状态在更新里切到待机，待机要到下一帧才检查跳跃，而“按下”事件只在按下的那一帧为真；需要缓冲把按键保留到可以起跳的那一帧。
自测 2：土狼时间为什么要在起跳后立即清零？否则起跳后的 0.1 s 内仍满足“离地时长 < 土狼时间”，可以再跳一次，形成意外的二段跳。
自测 3：动画过渡时间设为 0 是好是坏？对动作游戏通常是好的：逻辑切换后画面立即响应；需要平滑时用极短过渡或姿态匹配，长时间混合会让动作“拖泥带水”。
