PART III

数值、技能与 AI

数值系统决定“打多疼”，技能系统决定“怎么打”，AI 决定“谁来挨打”。这三章的共同主题是：多个系统同时写同一份数据，以及名字像查询的函数在偷偷改世界。

CHAPTER 07

属性、伤害公式与异常状态

伤害公式、Buff、属性修正器是 RPG 方向必问的三件套。项目的 Stat / CharacterStats 结构清楚，但实测出四个数值问题：暴击率凭空多 1%、冰冻判定看错了对象、等级成长是复利、多个冻结效果互相抵消；元素伤害整条链路写好了却没有接线。

本章目标
  • 说清 14 项属性怎么派生出闪避率、暴击率、暴击倍率、最终伤害
  • 用 E3 / E4 的数字讲清 off-by-one、写错判定对象、复利成长三个数值 bug
  • 讲清“多个系统写同一字段”的危害，并用 E8 量化重叠冻结的失效比例
  • 设计 Modifier（Flat / PercentAdd / PercentMult）与 Buff（叠层、刷新、来源、到期）系统

7.1 30 秒面试版 · 现状 vs 理想

30 秒回答

Stat 是“基础值 + 整数修正列表”，装备穿上加修正、卸下按值移除；CharacterStats 的物理伤害按“闪避 → 暴击 → 减护甲 → TakeDamage”结算，元素伤害取最高元素施加点燃 / 冰冻 / 感电。实测有四个问题：暴击用 <= 比较 0~99 的整数，暴击率 0 也有 1% 暴击；冰冻破甲判断的是攻击者而不是目标；敌人每级 +25% 是在“当前值”上加，10 级是 [[e4.10.mul|.2f]] 倍而不是 [[e4.10.lmul|.2f]] 倍；冻结、减速、死亡三个系统都直接写 moveSpeed 和 animator.speed，多段冻结时实际只冻住 [[e8r.min|.0f]]%~[[e8r.max|.0f]]% 的时间。另外受伤没有死亡保护，死后再受伤会重复掉落；元素伤害函数 DoMagicalDamage 没有任何调用方。改进是 Modifier 栈 + 脏标记缓存，异常状态做成统一的 Buff。

7.2 属性派生关系

[System.Serializable] public class Stat { [SerializeField] private int baseValue; public List modifiers = new List(); public int GetValue() { int v = baseValue; foreach (int m in modifiers) v += m; return v; } // 每次都重新求和 public void SetDefaultValue(int _value) => baseValue = _value; public void AddModifier(int m) => modifiers.Add(m); public void RemoveModifier(int m) => modifiers.Remove(m); // 按“值”删第一个相等的 }
派生量公式（源码）场景值（玩家 / 骷髅）
最大生命maxHealth + vitality × 5（GetMaxHealth）1000 / 100
闪避率(evasion + agility)%，判定 Random.Range(0,100) < 值0 / 0
暴击率(critRate + agility)%，判定 Random.Range(0,100) <= 值0 / 0（实际 1%）
暴击倍率(critPower + strength) × 1%，critPower 在 Start 里被 SetDefaultValue(150) 覆盖150%
物理伤害damage + strength，减去目标 armor（冰冻时 ×0.85），下限 01000 − 0 / 0 − 10 → 0
魔法伤害fire + ice + lightning + intelligence，减去目标 magicResistance + intelligence × 310 / 20（但从未被调用）

两个容易被追问的细节：① critPower 的基础值在 Inspector 里配多少都没用，Start 会改成 150——“代码默认值”应该放在字段初始化器或 Reset() 里，而不是在运行时覆盖序列化数据；② RemoveModifier 按值删除，装备 A 和 B 都给 +5 力量时卸下 A 也只会删掉“某一个 5”，结果数值上正确，但没有“来源”就做不到“移除某个 Buff 的全部效果”或“UI 显示加成来源”。

暴击率 off-by-one

7.4 死亡结算：没有保护，掉落会重复

public virtual void TakeDamage(int _damage) { DecreaseHealthBy(_damage); if (currentHealth <= 0) Die(); // 已经死了还会再 Die } protected override void Die() // EnemyStats { base.Die(); enemy.Die(); // → ChangeState(deathState)：Exit + Enter 再来一遍 myDropSystem.GenerateDrop(); // → 再掉一次 }

问题 P1 近战打不到死掉的骷髅（死亡状态关了碰撞体），所以平时不会触发。但两条路径能绕过碰撞体：① 弹跳剑在第一次接触时把半径 10 m 内的敌人 Transform 存进列表，之后按列表依次飞过去造成伤害——目标中途死亡也会被继续“弹”到，每次都重新 Die + 掉落；② 雷击 Controller_ThunderStrike 持有目标引用，飞行途中目标死亡，到达时照样 TakeDamage。修法：if (isDead) return; 放在 TakeDamage 最前面，Die 只执行一次；死亡时从所有“目标列表”里注销（发 OnDeath 事件）。

同一段代码里还有一个“上限变了血量不变”的问题：装备 Nice_Armor（+10 health）后 GetMaxHealth 变成 1010，currentHealth 还是 1000，血条也只在下一次受伤时才刷新上限 问题 P2。常见规则是“上限增加时当前值按比例 / 按差值增加，上限减少时截断”，并立刻通知 UI。

7.5 E4：每级 +25% 是复利

private void Modify(Stat _stat) { for (int i = 1; i < level; i++) { float modifier = _stat.GetValue() * percantageModifier; // GetValue 包含了前几轮加上去的修正 _stat.AddModifier(Mathf.RoundToInt(modifier)); } }

复利本身不是错——很多游戏的怪物成长就是指数的——问题是它没有被当作设计决定写下来：变量名 percantageModifier、注释“将基础属性实现等级修正”都暗示“每级加基础值的 25%”。数值成长应该由曲线表驱动（等级 → 系数），代码只查表，策划能直接看到第 10 级是多少。当前场景的骷髅 level = 0、percantageModifier = 0，这段代码还没有生效。

7.6 元素伤害与异常状态：写好了，没接线

DoMagicalDamage 的唯一调用是 DoDamage 里被注释掉的一行（“测试用”），所以点燃、冰冻、感电、连锁雷击在当前版本里都触发不了。代码本身值得读，因为它有几个设计点和几个 bug：

环节源码行为评价
选元素三种元素伤害放进 List 按值降序排序；唯一最大者施加对应异常；并列时 50% 概率从非零项里随机选一个可扩展的写法；但每次调用都 new 一个 List（并列时 FindAll 再分配一个），并列分支里判断感电用的是 damages[0] 而不是随机选中的那一项（CharacterStats.cs:226）——List.Sort 不稳定，并列时 damages[0] 是谁不确定
互斥规则点燃 / 冰冻：身上没有任何异常时才能上；感电：没有点燃和冰冻时可上“同一时间只有一种异常”是清晰的规则；感电可以叠加到感电上，用于触发连锁
点燃伤害每 0.3 s 扣 fire × 10%（取整）首跳在第一帧；周期受帧率影响（第 5 章 E10）
冰冻减速 20%，持续 2 s通过 SlowEntityBy 直接改 moveSpeed（见 7.7）
感电连锁已感电再被感电：25 m 内找最近的其他敌人召唤雷击；找不到就劈自己Controller_ThunderStrike 到达后调用 TakeDamage(1)——传进来的 shockDamage 完全没用；目标在飞行途中被销毁时 if (!targetStats) return; 让雷击永远停在半空不销毁

7.7 多个系统写同一个字段：E8 量化

最容易被观察到的是飞剑冻结：每次命中都 StartCoroutine("FreezeTimeFor", 0.7f)，协程开头冻结、0.7 s 后解冻。多段命中时，第一个协程到点就把敌人解冻了，后面命中的“冻结 0.7 s”被截断；协程又在 Update 之后才恢复（R1），如果某一帧既有新命中又有旧协程到期，解冻会覆盖冻结。用旋转剑的命中节奏（持续 2 s）跑一遍 实测 E8 模型 R1：

float frozenUntil; // 冻结：不开协程，只维护截止时间 public void Freeze(float seconds) => frozenUntil = Mathf.Max(frozenUntil, Time.time + seconds); bool IsFrozen => Time.time < frozenUntil; readonly List<(object source, float mul, float until)> speedMods = new(); public void AddSpeedMod(object src, float mul, float sec) => speedMods.Add((src, mul, Time.time + sec)); float SpeedMultiplier() // 每帧求一次：过期的删掉，其余相乘 { speedMods.RemoveAll(m => Time.time >= m.until); float k = IsFrozen || isDead ? 0f : 1f; // 冻结 / 死亡是“硬覆盖”，优先级最高 foreach (var m in speedMods) k *= m.mul; return k; } // moveSpeed、animator.speed 都由 base × SpeedMultiplier() 推导，任何系统都不再直接赋值

7.8 改进：Modifier 与 Buff

设计点做法解决了项目里的什么
修正类型Flat（+5）、PercentAdd（+10%，同类相加）、PercentMult（×1.1，相乘），按固定顺序：(base + ΣFlat) × (1 + ΣPercentAdd) × ΠPercentMult现在只有整数加法，做不了“+20% 伤害”
来源每个修正带 source（装备实例、Buff 实例），可按来源批量移除按值删除无法区分来源；UI 无法显示“加成来自哪里”
缓存修正列表变化时置脏，GetValue 只在脏时重算每次 DoDamage 调 7~9 次 GetValue（暴击时 9 次），每次遍历列表
Buff 生命周期OnApply / OnTick（固定逻辑帧）/ OnRemove；持续时间、叠层上限、刷新策略（刷新时长 / 叠加时长 / 独立实例）点燃 / 冰冻 / 感电三套 bool + timer 各写一遍；周期伤害随帧率漂移
互斥与免疫Buff 带标签，规则表声明“A 存在时 B 不能上 / 覆盖 / 共存”互斥规则硬编码在 ApplyAilments 的三个 bool 表达式里
死亡与清理死亡时移除所有 Buff（触发 OnRemove 恢复速度等）死亡时只把三个 bool 置假，变色 Invoke 和减速恢复仍在跑

7.9 面试追问

伤害公式是怎么算的？（Q7-1） ├─ 暴击率怎么判定？会不会有偏差？（Q7-2 → E3） ├─ 护甲用减法还是百分比？（Q7-3） ├─ 装备加属性怎么实现？卸下怎么撤销？（Q7-4） │ └─ 百分比加成怎么叠？顺序怎么定？（7.8） ├─ Buff 系统怎么设计？冻结和减速同时存在怎么办？（Q7-5 → E8） └─ 怪物成长曲线怎么定？（Q7-6 → E4）
Q7-1 → Q7-2　伤害怎么算？暴击判定有没有偏差？

L2　闪避判定 → 基础伤害（攻击 + 力量）→ 暴击判定，暴击时乘 (150 + 力量)% → 减目标护甲（下限 0）→ 扣血，血量 ≤ 0 则死亡。

L3 · 项目　我测出暴击判定用了 <=，而 Random.Range(0,100) 返回 0~99，所以实际暴击率是 (c+1)%，暴击率 0 也有 1%；闪避用的是 <，是对的。两处写法不一致说明概率判定应该收敛到一个函数里。

L4 · 攻击　“1% 无所谓吧？”→ 对普通战斗无所谓，但它破坏了“配置 0 = 绝不发生”的约定；而且同样的 off-by-one 我在掉落里也找到了：dropChance 填 0 的物品仍有 1% 掉率（第 10 章）。

Q7-3　护甲用减法还是百分比？

L2　减法（伤害 − 护甲）直观，但低伤害攻击会被完全免疫、高伤害攻击护甲几乎无效，数值容易失控——项目里骷髅的伤害 0 减玩家护甲 10 就是 0。百分比减伤常用 减伤 = armor / (armor + K)（K 与等级相关），护甲收益递减、永远不会 100% 免伤，便于平衡。

L3　也可以混合：先百分比再减一个小的固定值，让“刮痧”攻击仍有最低伤害（例如至少 1 点或 5%）。

Q7-4　装备加属性怎么实现？

L2　ItemData_Equipment 的 AddModifiers 把 14 项数值逐个加到玩家对应 Stat 的修正列表，RemoveModifiers 按值删除；EquipItem 先卸下同部位旧装备再穿新的。

L3　两个问题：装备数据（ScriptableObject）直接通过 PlayerManager 单例去改玩家组件，依赖是隐式的；修正没有来源，只能按值删。我会让修正带上来源（装备实例），由 PlayerStats 自己订阅“装备变化”事件来应用；同时上限变化时同步调整当前血量并通知 UI。

Q7-5　冻结和减速同时存在怎么办？

L2　我原来的写法是每个效果直接给 moveSpeed、animator.speed 赋值，恢复时也赋“默认值”，于是冻结期间减速到期会直接解冻；多段冻结时第一个协程结束就解冻，我建模算过，旋转剑场景下应当全程冻结的时间里只冻住了 [[e8r.min|.0f]]%~[[e8r.max|.0f]]%。

L3　改成修正器栈：每个效果是一个带来源和到期时间的修正，最终速度 = 基础 × 所有修正之积；冻结、死亡这种“硬覆盖”放在最高优先级；同类效果按规则合并（冻结取最晚截止时间）。这样任何效果的加入和移除都不需要知道别的效果。

Q7-6　怪物成长曲线怎么定？

L2　由曲线表驱动：等级 → 生命 / 伤害系数，策划在表里看到每一级的绝对值；代码只查表。常见是“分段线性 + 每 N 级一个台阶”，或者指数但有上限。

L3 · 项目　我的 Modify 循环里每级取 GetValue() × 25%，GetValue 包含了前几轮的修正，于是成了复利：10 级 [[e4.10.mul|.2f]] 倍而不是线性的 [[e4.10.lmul|.2f]] 倍。复利不一定错，但必须是显式决定。

常见错误回答

错误：“我的 Buff 用协程实现，每个 Buff 开一个协程计时，到点恢复。”

问题：重叠的同类 Buff 会互相截断；恢复时“赋默认值”会抹掉其他 Buff；对象死亡或禁用时协程停止，恢复代码永远不执行；协程计时还受帧率量化。

更好的回答：“Buff 是数据：开始时间、持续时间、叠层、来源；由一个系统在固定逻辑帧统一推进和到期；属性由所有生效 Buff 推导，而不是被 Buff 改写。”

7.10 发散场景题

场景 7-1　设计一个 Buff 系统，要求支持“中毒可叠 5 层、每层独立计时”“加速只刷新时长”“净化移除所有负面效果”。

为什么会问：RPG / MOBA 客户端必考的系统设计题。

数据：BuffConfig（id、标签、持续、周期、叠层上限、叠加策略：Refresh / Extend / Independent、互斥组、属性修正列表、周期效果）。运行时：BuffInstance（config、来源、层数、开始帧、下次 tick 帧）。管理器按固定逻辑帧推进：到期移除、到点 tick、层数变化时重算属性修正。中毒用 Independent（每层一个实例，或一个实例记录每层的到期帧），加速用 Refresh，净化按“负面”标签批量移除。表现（图标、特效）订阅 Buff 增删事件，不参与逻辑。

场景 7-2　玩家抱怨“暴击率 30% 却连续 10 次不暴击”，怎么办？

为什么会问：真随机的体验问题，引出伪随机分布。

独立 30% 连续 10 次不暴击的概率是 0.7^10 ≈ 2.8%，玩得多了一定会遇到。可以用伪随机分布（PRD）：第 N 次未暴击时概率为 C × N，暴击后重置为 C，C 由目标期望 30% 反解（约 0.084），既保持期望又压缩连败。也可以用“抽卡式”保底：每 K 次至少一次。注意 PRD 需要每个单位独立维护计数，且必须由权威端计算。

场景 7-3　改成联网后，伤害在哪里算？客户端显示的伤害数字从哪来？

为什么会问：数值的权威性与防作弊。

状态同步：服务器算伤害（随机数只在服务器），客户端收到“命中事件（攻击者、受击者、结果、数值）”后播放表现，伤害数字以服务器下发为准；为了手感可以先播命中特效，数字晚一个 RTT 出现。帧同步：每个客户端算同一份确定性逻辑，随机数用同一个种子的确定性 RNG，数值用定点数——项目里的 Mathf.RoundToInt(float) 和 UnityEngine.Random 都不能用。

场景 7-4　策划想在 Excel 里配所有数值，你怎么接？

为什么会问：工具链与数据驱动。

Excel → 导出工具（校验类型、范围、外键）→ 生成 ScriptableObject 或二进制表 + 强类型访问代码；运行时只读。项目里散落在场景序列化字段的数值（玩家移速、骷髅攻击距离、技能参数）都应该进表，组件只保存“表 id”。导出时就能检查 dropChance 是否在 0~100、等级曲线是否单调，把 off-by-one 这类问题挡在运行之前。

本章速记
  • E3：暴击 <= → (c+1)%；闪避 < 正确；冰冻破甲判了攻击者；RoundToInt 是银行家舍入。
  • TakeDamage 无死亡保护 → 弹跳剑 / 雷击可让尸体重复 Die、重复掉落（#7）。
  • E4：每级 +25% 当前值 = 复利，10 级 [[e4.10.mul|.2f]]× vs 线性 [[e4.10.lmul|.2f]]×。
  • E8：多个写者赋绝对值 → 重叠冻结只冻住 [[e8r.min|.0f]]%~[[e8r.max|.0f]]%；改成截止时间取最大 + 速度修正器栈。
  • DoMagicalDamage 没有调用方；雷击伤害写死 1。
自测 1：为什么 critPower 在 Inspector 里配了也没用？CharacterStats.Start 里 critPower.SetDefaultValue(150) 覆盖了序列化的基础值；默认值应放在字段初始化器或 Reset()。
自测 2：RemoveModifier 按值删除会算错吗？只要加和删成对、且值不在中途被改，结果数值正确（多重集合语义）；但若装备的 ScriptableObject 在穿戴期间被修改（编辑器里调数），卸下时删的是新值，旧值会永久残留。
自测 3：E8 修正版为什么能 100% 冻结？不再为每次命中开协程，只维护 frozenUntil = max(frozenUntil, now + 0.7)，冻结状态由“当前时间 < 截止时间”推导，不会被早到期的旧效果截断。
