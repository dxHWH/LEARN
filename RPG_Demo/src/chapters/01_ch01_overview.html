1.1 30 秒面试版 · 现状 vs 理想

30 秒回答

项目按“实体 + 状态机 + 子系统单例”组织：玩家和骷髅继承 Entity，在 Start 里缓存刚体、动画机、特效、属性组件；行为由普通 C# 状态类驱动，状态只在 Enter 时设 Animator bool；命中、动画结束、掷剑这些时刻由动画事件回调到 *AnimationTrigger 组件；技能挂在 SkillManager 上，玩家数据通过 PlayerManager 单例被技能、装备、怪物访问；属性在 CharacterStats，物品在 Inventory 单例。优点是上手快、各系统边界直观；代价是依赖都汇聚到“玩家”这个单点、状态类直接读输入、数据写在组件字段里，扩展和测试都难。

1.7 架构评价：做对了什么、代价是什么、理想架构

✔ 状态是对象，不是 switch

每个状态一个类，Enter / Exit 成对设置 Animator bool，新增状态不碰其他状态的代码。源码 PlayerState.cs:25-44

✔ 关键帧交给美术时间轴

命中、结束、掷剑由动画事件触发，改动画节奏不用改代码。

✔ 数值与资源分离的雏形

物品用 ScriptableObject，Stat 用“基础值 + 修正列表”，装备卸下能精确撤销。

✔ 自己做过的重构

异常状态计时器抽成 HandleStatus(ref…)；元素伤害改成排序选最大；掉落改成无放回抽样。

理想 把上表六条代价倒过来，就是理想架构的六条规则：依赖只向下（规则层 → 能力组件 → 只读配置，没有谁伸手去拿“唯一的玩家”）；写入口唯一（只有状态机能切状态、只有属性集能改属性、只有容器操作能改物品）；表现层只订阅（Animator、特效、UI 不回写逻辑）；数据只读（组件只存配置 id）；输入与 AI 走同一个意图接口（缓冲、回放、AI 托管都接在这里）；组装根注入（取代 3 个单例）。与图 1-5 对照看：箭头从“全部指向 Player”变成“分层向下 + 事件向上”。

1.9 面试追问

介绍一下项目架构（1.1） ├─ 为什么 Player/Enemy 用继承？什么时候该用组合？（Q1-1） │ └─ 如果要加“会飞的弓箭手”和“可召唤的宠物”呢？（场景 1-1） ├─ 状态为什么是普通 C# 类而不是 MonoBehaviour？（Q1-2） ├─ 模块之间怎么通信？为什么用单例？（Q1-3 → 第 2 章） │ └─ 不用单例怎么拿到玩家？依赖注入 / 服务定位器 / 事件？（Q1-4） └─ 一帧里先执行什么？命中发生在哪个阶段？（Q1-5 → 第 4、6 章）
Q1-1　为什么用继承 Entity？

L1 · 30 秒　玩家和怪物共享组件缓存、地面 / 墙检测、翻转、击退和受击表现，抽到 Entity 里避免重复。

L2 · 正常回答　Entity 提供的是“所有可战斗角色都有的能力”，并用虚函数留了扩展点：DamageEffect 玩家重写成“反击状态下先尝试弹反”，Die 各自切到死亡状态，SlowEntityBy 玩家多改跳跃和冲刺速度。

L3 · 深入　继承的问题在“能力组合”出现时暴露：想要一个不会受击闪白的木桩、一个会墙滑的怪物，就得在继承树上开岔或塞开关。组合的做法是把“地面检测”“击退”“受击闪白”做成独立组件（Unity 本身就是组件模型），角色按需挂载；状态机通过接口拿能力（IMover、IDamageable），而不是拿具体的 Player。

L4 · 面试官攻击　“那你为什么不一开始就用组合？”→ 两个角色的规模下继承最省事，我也确实复用了一大块代码；但我在 Entity 里已经看到了坏味道：SlowEntityBy 的基类实现只调了一个 Invoke、什么都没减速，子类各自重写——这说明“减速”并不是所有实体的共同行为，它更适合成为一个修正器组件（第 7 章）。

Q1-2　状态为什么不是 MonoBehaviour？

L2　状态只是行为的切片，不需要 Transform、生命周期和 Inspector；做成普通类可以在 Awake 里一次性 new 出来、零 GetComponent、切换时没有 enable / disable 的开销，也方便做成可测试的纯逻辑。代价是状态里不能直接用协程和 Invoke，所以代码里会看到 player.StartCoroutine("BusyForSeconds", .1f) 这样借宿主组件跑协程的写法。

L3　更进一步可以让状态完全不认识 Player，只依赖一个“上下文”接口（输入快照、移动能力、动画参数），这样同一套状态能给玩家、AI 托管、回放共用。

Q1-3 → Q1-4　模块怎么通信？为什么用单例？不用单例怎么办？

L2　三种方式并存：直接引用（状态持有 Player）、单例（技能、装备、怪物通过 PlayerManager 拿玩家）、委托（onFlipped、onHealthChanged 通知血条）。单例的好处是写起来快，坏处是隐式依赖：看 ItemData_Equipment 的签名完全不知道它会去改玩家属性。

L3　替代方案按“侵入性”从低到高：① 在场景组装处显式注入（SkillManager 在 Awake 里把 player 传给每个 Skill）；② 服务定位器加接口（Services.Get<IPlayerProvider>()，可在测试里替换）；③ 事件总线（装备变化发 EquipmentChanged，由 PlayerStats 自己订阅修改属性）；④ DI 框架（VContainer / Zenject）。对这个规模我会选 ①+③：依赖显式、写操作收口到属性所有者。

L4 · 攻击　“事件总线不是也是全局的吗？”→ 是，但它把“谁改玩家属性”收口到了 PlayerStats 自己；单例的问题不在全局，而在任何人都能写。

Q1-5　一帧里先执行什么？命中发生在哪个阶段？

L2　FixedUpdate（物理）→ Update（脚本，状态机在这里）→ 协程恢复 → 动画更新（动画事件在这里触发，命中判定就在这时做）→ LateUpdate → 渲染。所以“按键在 Update 里被读到、速度在本帧设置、位移在下一帧的物理步才发生、命中在本帧或之后某帧的动画阶段”。

L3　这个顺序会直接影响结论：第 6 章算弹反窗口时，玩家的反击状态是在 Update 里退出的，而怪物的 AttackTrigger 在动画阶段触发——同一帧里玩家先退出、怪物后命中，窗口的右边界就差了一帧。

常见错误回答

错误：“我用了 MVC 架构，Player 是 Model，状态机是 Controller，Animator 是 View。”

问题：Player 里既有数据又有行为还有协程，状态类直接读输入也直接写刚体——套名词会被一行代码问倒。

更好的回答：“它是 Unity 常见的组件 + 状态机结构；数据和表现没有严格分层，例如状态在 Enter 里直接设 Animator 参数。如果要分层，我会先把输入抽成快照、把伤害抽成事件。”

1.10 发散场景题

场景 1-1　策划要加“会飞的弓箭手”和“玩家的召唤宠物”，你要改哪些文件？

为什么会问：考察你对继承结构的扩展成本有没有概念。

弓箭手：新建 Enemy_Archer + 一套状态类（照抄骷髅的 6 个，Battle 改成保持距离、Attack 改成发射投射物），新写投射物控制器；“会飞”要绕开 IsGroundedDetected 和 Move 状态里的边缘检测——状态类与具体子类强绑定（Enemy_SkeletonMoveState 持有 Enemy_Skeleton），几乎无法复用。宠物：它既不是 Player 也不是 Enemy，却要能攻击敌人、被敌人攻击、跟随玩家；现有的“敌人只打 Player 组件”“玩家攻击只认 Enemy 组件”需要换成阵营 / 接口判断。结论：先引入 IDamageable + 阵营（Team），再把感知、移动、攻击拆成可组合的组件或行为树节点（第 9 章）。

场景 1-2　新人接手这个项目，你会先让他读哪三个文件？

为什么会问：考察你能不能抓住系统的“主干”。

① Player.cs（状态在哪里创建、Update 里先做什么）；② PlayerGroundedState.cs（大部分输入分支在这里，读懂它就读懂了操作逻辑）；③ CharacterStats.cs（伤害、异常状态、死亡全在这里）。再配一张图 1-4，告诉他“命中在动画事件里”，否则他会在 Update 里找半天攻击判定。

场景 1-3　如果要做成 ECS（DOTS），哪些部分最容易迁移，哪些最难？

为什么会问：考察数据与行为分离的理解。

最容易：Stat / 伤害公式（纯数据 + 纯函数）、异常状态计时（可以是一个 System 批量递减）、掉落概率（纯函数）。最难：动画事件驱动的命中（ECS 里通常改成“技能时间轴组件 + System 在固定逻辑帧判定”）、状态类里读输入和直接写刚体的写法、依赖单例的所有代码。迁移顺序也就是重构顺序：先把数据和计算从 MonoBehaviour 里拔出来。

自测 1：为什么说“读 Unity 项目必须同时读场景”？数值（移速、伤害、掉率、技能类型）几乎都序列化在场景和 SO 里，代码只给出公式；例如骷髅 damage=0、分身 canAttack=1、飞剑类型 Regular，这些都决定了 bug 是否会触发。
自测 2：一次近战命中的伤害结算发生在 Update 里吗？不是。Update 里只是进入攻击状态；伤害在动画更新阶段由 AttackTrigger 事件触发的 OverlapCircleAll + DoDamage 完成。
自测 3：图 1-5 里，哪条依赖最该先拆？ItemData_Equipment → PlayerManager → PlayerStats：数据资源直接修改运行时对象，既隐式又无法测试；改成装备系统发事件、PlayerStats 自己应用修正。
