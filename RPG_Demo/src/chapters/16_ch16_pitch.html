PART VI

方法论篇：Demo 只是起点，如果重新实现应该怎么做

面试官看不到你的 Demo，只能通过你的语言理解它。这一部分把每个功能讲成“需求场景 → 我在 Demo 里怎么做的 → 这类功能最容易踩的坑（以我踩过的为例）→ 更好的实现方法 → 取舍”，只讲思路与方法，不讲代码。第 16 章先统一口径；第 17~21 章依次回答五个问题：状态判定怎么做、滑墙怎么设计、平台关卡怎么搭（Tilemap 原理与操作）、没有输入缓冲时手感怎么优化、背包 / 装备 / 技能系统为什么这样设计。

CHAPTER 16

面试口径：面试官看不到 Demo 时怎么讲

同一个 Demo，讲成“我做了冲刺、连招、背包”和讲成“我做了一个 2D 动作原型，复盘时总结出状态判定、输入宽容、数据分层三类常见坑，并设计了对应的正确做法”，在面试官心里是两个完全不同的候选人。这一章给出口播稿、术语对齐表和“把 bug 讲成经验”的转换表。

本章目标
  • 知道面试官“看不到 Demo”带来的三个风险，以及对应的讲法
  • 能用 60 秒把关卡画面、操作和系统结构“讲出画面”，必要时在白板上画出来
  • 把项目内的命名换成行业通用术语，避免面试官听不懂
  • 把 Demo 里的问题统一讲成“这类功能常见的坑 + 根因 + 正确做法”，而不是自曝 bug

16.1 30 秒：为什么要专门对齐口径

核心观点

面试官对项目的判断完全来自你的叙述，所以要同时让他看到三样东西：画面（玩起来是什么样）、结构（系统怎么组织）、判断力（哪里是难点、哪里有坑、正确做法是什么）。Demo 本身只是原型级实现，它的价值不在于“做得多完善”，而在于你能以它为例讲清楚“这类功能应该怎么做、为什么”。因此本部分所有章节都按同一个五句式组织：场景 → 我的做法 → 常见的坑 → 更好的实现 → 取舍。

风险表现对策
① 听不懂满口项目内命名：“我的 AnimationTrigger 里调 DoDamage”“isBusy 期间不能 Move”换成通用术语（16.4）：“在动画的命中帧事件里做伤害判定”“动作后摇期间锁住移动输入”
② 看不出深度功能清单式介绍：“有冲刺、三段连招、弹反、飞剑、背包、合成”每个功能只用一句话描述，然后挑 2~3 个讲“难点在哪、坑是什么、怎么做才对”
③ 自毁或夸大“我的代码有 36 个 bug”或“我实现了一套完整的技能系统”讲成“复盘时总结出的几类典型坑”（16.5），并明确区分“Demo 里已实现的”和“我设计好的改进方案”

16.3 五句式：每个功能都这样讲

句子回答什么例：滑墙（第 18 章）
① 场景这个功能解决玩家的什么问题“横版动作里，滑墙给玩家在空中‘抓住’的机会，也是垂直移动的手段。”
② 我的做法 现状Demo 里怎么实现的（一两句，不念代码）“空中下落时用一条腰部射线检测前方墙面，碰到就进入滑墙状态，把下落速度压到 2 m/s；按跳就向反方向蹬出。”
③ 坑这类功能常见的问题，用 Demo 的现象举例“滑墙最容易漏的是退出条件和检测覆盖：我一开始只有一条腰部射线，墙在半空结束时角色会对着空气继续滑；接近墙顶时脚还贴着墙、射线已经越过墙顶，就出现‘贴着墙却滑不了’的死区。”
④ 正解 理想更好的实现方法（分层、流程、参数）“墙检测至少用脚、腰两条射线或一个盒子投射，按法线判断是墙；状态的出口必须覆盖‘进入条件不再成立’；再加粘墙时间、墙宽限时间和蹬墙后的强制离墙时间。”
⑤ 取舍代价与适用范围“检测多了有成本，但每帧几条射线可以忽略；更重要的是先决定‘单墙能不能爬’，这是设计决定，不应该是参数的副作用。”
为什么第 ③ 句要用“这类功能常见的坑”开头

面试官想考察的是“你知不知道这里有坑”，而不是“你的代码有没有 bug”。用“常见的坑是……，我在 Demo 里就遇到了……”的说法，既诚实，又把话题从“你的失误”转到“你的经验”。再配一个你量化过的数字（比如“墙顶附近有一段 1.3 m 的死区”），可信度最高。

你要讲的东西时态与句式例：滑墙
现状 Demo 里做了的过去时 + 证据：“我当时是……，后来测到……”“我当时用一条腰部射线判墙，后来发现接近墙顶时会有一段贴着墙却滑不了的死区。”
模型验证 只在移植模型里验证过的完成时 + 限定范围：“我把规则放进移植模型对比过……”“我在 C++ 移植模型里加了一条脚部射线，反应慢到 100 ms 也能翻上墙——这是模型结论，Unity 工程里还没改。”
理想 只设计、没实现的条件句 + 理由：“如果重做，我会……因为……”“如果重做，我会把检测抽成每个物理步只跑一次的感知层，状态机只读结果。”

三种时态对应第 0 章 0.2 的标记：橙色 = 过去时，绿徽标“模型验证” = 限定范围的完成时，绿色 = 条件句。最危险的是把第三行说成第一行——面试官只要追问一个细节（参数、调试过程、遇到的问题），就能分辨“做过”和“想过”。

16.5 把 bug 讲成经验：12 条“坑 → 正解”口径

下表左列是 Demo 里实际出现的现象（前 15 章和本部分实验测出来的），中间列是你在面试里应该说的“这类功能的坑”，右列是正确做法。面试时只说中间和右边两列，左列作为例子带一句即可。

现状：Demo 里的现象抽象成的“坑”理想：正确做法（一句话）章
死亡后按冲刺能“复活”状态切换入口分散，没有打断优先级所有切换走一个带守卫的请求入口，死亡是只接受“复活”的吸收态3
落地瞬间贴墙，一帧切两次状态切换后旧状态的代码还在执行请求-提交：本帧只记录请求，帧末统一切换一次3
斜坡超过约 [[F1.a1|.1f]]° 就判定离地单点单射线做地面判定每个物理步一次的感知层：形状投射 / 接触法线分类地面、墙、天花板17
墙在半空结束，角色对着空气继续滑状态缺少“进入条件不再成立”的出口每个状态的出口覆盖进入条件的否定；滑墙检测用多条射线 + 覆盖率3 · 18
能不能单墙爬上去取决于手速可玩性规则成了参数的副作用先定设计（允许 / 禁止单墙攀爬），再用强制离墙时间、推力把它做成稳定规则18
跑出平台边缘的下一帧按跳没反应没有输入宽容（土狼时间、预输入）离地 0.1 s 内仍可起跳；落地前 0.1~0.15 s 的跳跃键缓冲生效20
冲刺距离随帧率和卡顿变化用渲染帧计时去控制物理位移需要严格时长的位移按物理步计数，周期计时用累加5
弹反窗口实测宽达 1 s，还能“预按”窗口由状态持续时间而非按键时刻决定完美窗口从按键时刻起算（约 0.15 s），落空有收招硬直6
闪避了还闪白，弹反了还掉血表现与结算分开调用，没有唯一裁决点攻击方构造伤害信息，受击方统一裁决并返回结果，表现只读结果6
多段冻结只冻住 [[e8r.min|.0f]]%~[[e8r.max|.0f]]% 的时间多个系统直接改同一个字段修正器栈：效果只登记修正，最终值由所有修正推导7

“+5 的剑”无处存放以物品定义作键，没有物品实例定义 / 实例 / 容器 / 操作四层分离10 · 21
口径红线

① 不报没测过的数字：本书的实测来自“把逻辑移植成 C++ 逐帧复现”，面试时就这样说（“我把状态机逻辑抽出来做了逐帧复现”），不要说成“我在 Unity Profiler 里测的”。② 不把方案说成已实现：第 17~21 章的“更好的实现”是设计方案，说“我设计了 / 我会这样改”，不要说“我实现了”。③ 不贬低教程：说“骨架参考了一门教程，我在此基础上改了弹反判定、异常状态、掉落和背包”，比“教程写得很烂”更专业。

16.6 方法论版的项目介绍

1 分钟版

“这是一个 Unity 2D 横版动作 RPG 原型：一段城堡关卡，玩家能跑、跳、滑墙蹬墙、冲刺、三段连招、弹反，还能掷出可召回的飞剑；骷髅会巡逻、追击、出刀，死亡掉落装备和材料，可以穿戴和合成。

实现上，角色用有限状态机驱动，命中、动作结束这些关键帧放在动画事件里，属性、技能、背包各是一个子系统。

做完之后我做了一次系统性的复盘，把问题归成三类：一是状态与判定——切换入口分散、地面和墙只用单射线判断；二是手感——没有输入宽容、计时依赖帧率；三是数据组织——物品没有实例层、多个系统直接改同一份数据。每一类我都设计了更合理的做法，也用逐帧复现的方式量化过问题的影响。”

3 分钟版：在 1 分钟版之后，按面试官的兴趣展开其中两类

如果对方关心手感（动作 / 平台类岗位）：讲第 17、18、20 章——“着地判定我原来是脚底一条 0.15 m 的射线，真正伸出脚底的只有 4 cm，坡度超过约 [[F1.a1|.1f]]° 就判定离地；更好的做法是每个物理步做一次感知，用形状投射或接触法线区分地面、墙和天花板。滑墙我原来只有一条腰部射线，墙顶附近有一段死区，导致单墙攀爬能不能成功取决于手速；正确做法是多射线 + 明确的设计规则。手感上我量化过：在‘跑出平台边缘后 20 ms 左右按跳’的玩家里，没有土狼时间只有 [[f2.p0.c0|.0f]]% 能跳起来，加 0.1 s 土狼时间是 [[f2.p0.c100|.0f]]%。”

如果对方关心系统（RPG / 通用客户端岗位）：讲第 21 章——“背包、装备、技能我会统一成配置、实例、规则、表现四层，装备和 Buff 都通过属性修正器影响属性，技能是‘配置 + 实例 + 激活管线 + 效果’。Demo 里没有实例层，所以‘+5 的剑’做不了；合成不是事务，少扣了一份材料，这些都是分层能直接解决的问题。”

16.7 面试防守：关于 Demo 本身的追问

介绍一下你的 Demo ├─ 我看不到 Demo，你怎么证明是你做的？（Q16-1） ├─ 你说的这些改进，你都实现了吗？（Q16-2） ├─ 为什么用教程的框架？你自己做了什么？（Q16-3） ├─ 最得意的部分是什么？（Q16-4） └─ 最大的不足是什么？如果重做你会先改什么？（Q16-5）
Q16-1　我看不到 Demo，你怎么证明是你做的？

L2　用只有作者才知道的细节：参数（移速 7、跳跃初速 20、重力倍率 5、冲刺 25 × 0.2 s、蹬墙速度 (4, 18)）、关卡几何（立柱 7 m 高、跳跃顶点只有约 3.9 m，所以设计成必须蹬墙）、实现选择的原因（为什么弹反改成“受击时判定”）、以及踩过的坑的具体现象（墙顶附近贴着墙却滑不了）。面试官判断真假靠的是“细节密度”和“因果链”。

Q16-2　你说的改进都实现了吗？

L2　如实区分：“Demo 里是原型实现；改进方案是我复盘之后设计的，其中关键的判断我做过验证——比如把状态机和计时逻辑抽出来逐帧复现，确认了问题存在、量化了影响。下一步按优先级先修会导致错误结果的问题，再做结构性改造。”

L3　如果对方追问“为什么不直接改好”：说明取舍——Demo 的目标是验证玩法和练习系统设计，复盘的价值是把经验抽象出来；真正改的时候要先补回归测试，再动结构（第 12 章的路线）。

Q16-3　为什么用教程的框架？你做了什么？

L2　“框架参考了一门 Unity 2D RPG 教程，好处是能快速搭出可玩的东西；我自己改动的有：弹反从‘每帧检查’改成‘受击时判定’，异常状态计时抽成通用函数，元素伤害改成按最大值选择，掉落改成‘先筛选再无放回抽样’，背包、装备、合成是最后一次提交自己加的。更重要的是，做完之后我把它当成一份‘别人的代码’来做 Code Review，这个过程让我真正理解了每个设计的代价。”

Q16-4 → Q16-5　最得意的部分？最大的不足？

得意　选“动画事件驱动命中 + 弹反”这条链：它把动画、状态机、判定、数值四个系统串起来，能讲出时序（第 6 章的窗口推导）。

不足　选“状态与判定”：“我的状态切换没有统一入口，地面和墙的判定也太简单，所以出现了死亡可被打断、墙顶死区这类问题。重做的话我会先建感知层和带守卫的状态机，这两样是动作游戏手感的地基。”——不足要选有通用价值、你能讲出正解的，不要选“美术不好”“没时间”。

本章速记
  • 面试官看不到 Demo：要让他看到画面、结构、判断力；白板上画关卡草图 + 操作表。
  • 五句式：场景 → 我的做法 → 常见的坑 → 更好的实现 → 取舍。
  • 说通用术语：探测点 / 射线传感器、动作后摇输入锁、动画事件、可弹反窗口、属性修正器、物品配置。
  • 红线：不报没测过的数、不把方案说成已实现、不贬低教程。
