CHAPTER 05

时间与帧率：Update、FixedUpdate 与“帧率无关”

“为什么要乘 deltaTime”“Update 和 FixedUpdate 有什么区别”是 Unity 面试的开胃菜。这个项目给了三个会被追问到底的实例：冲刺距离随帧率跳动、点燃和旋转剑的伤害次数随帧率变化、瞄准虚线和剑的真实轨迹对不上。

本章目标
  • 画出“渲染帧 + 固定物理步”两条时间线，说清 Update 里设的速度何时生效
  • 区分三类时间代码：一次性设速度（与帧率无关）、Update 计时决定持续时长（会量化）、计时器重置丢余量（会漂移）
  • 用 E10 的数字说明冲刺 / 点燃 / 旋转剑在 30~240 fps 下的差异，以及一帧卡顿的后果
  • 推导半隐式欧拉的离散轨迹，算出瞄准虚线与剑的偏差，并给出“完全对得上”的写法

5.1 30 秒面试版 · 现状 vs 理想

30 秒回答

Update 每渲染帧一次、间隔不定；FixedUpdate 按固定 0.02 s 一步、一帧里可能 0 次或多次，物理在它之后积分。项目的移动是“在 Update 里设 rb.velocity、由物理步积分”，持续移动没问题；但持续时长在 Update 里用 deltaTime 计时的动作（冲刺 0.2 s）会被量化：120 / 144 fps 下冲刺距离在 4.5~5.0 m 间跳，冲刺中卡一帧 250 ms 能冲到 [[e10.hitch.250.max|.1f]] m。计时器用“到点就重置为冷却值”而不是“累加”，点燃在 30 fps 下 2 秒只跳 [[e10.ign.30.ticks]] 次（60 fps 是 [[e10.ign.60.ticks]] 次），冷却为 0 的旋转剑命中次数直接等于帧数。瞄准虚线用连续抛物线，物理是离散积分，同一 x 处剑比虚线低 ½·g·s·Δt·t，1 秒时约 [[e9.45_100.ady|.2f]] m。

5.2 两条时间线

类别项目中的例子与帧率的关系
① 一次性设速度，交给物理跳跃 SetVelocity(vx, 20)、墙跳、弹反击退、接剑反冲无关：物理按固定步积分
② 每帧设同一个速度，持续移动Move、WallSlide、骷髅追击基本无关（速度在帧间不变，物理步数 ∝ 时间）
③ Update 计时决定持续时长冲刺 0.2 s、攻击位移 0.15 s、弹反 1 s、骷髅待机 1 s量化：时长被向上取整到帧，物理步数随之跳动
④ 到点重置的周期计时器点燃 0.3 s 一跳、旋转剑 hitCoolDown、Skill 冷却漂移：每次丢掉超出的那一点，周期变长
⑤ 每帧按 dt 缩放的连续量分身淡出 alpha -= dt·speed、剑回收 MoveTowards(…, speed·dt)无关（误差在最后一帧）
⑥ 协程 / Invoke 的等待WaitForSeconds(0.2) 闪白、Invoke("DestroyMe", 7)量化到帧（最多晚一帧）

5.3 E10：冲刺距离随帧率与卡顿变化

public override void Enter() { base.Enter(); stateTimer = dashDuration; /* 0.2 */ ... } public override void Update() { base.Update(); // stateTimer -= Time.deltaTime ... player.SetVelocity(player.dashDir * player.dashSpeed, 0); // 25 m/s if (stateTimer < 0f) stateMachine.ChangeState(player.idleState); // Exit 里把 vx 设回 0 }

冲刺距离 = 25 m/s × 0.02 s × “看到 vx = 25 的物理步数”。物理步数取决于冲刺持续了几帧、每帧落了几个物理步。用 PlayerLoop 模型（R1、R4，物理步相位在 [0, 0.02) 内取 400 个值）扫一遍 实测 E10 模型：

两个现象各有原因：

  • 120 / 144 fps 偶尔短 0.5 m：冲刺在 Update 里共持续 [[e10.dash.120.frames]] / [[e10.dash.144.frames]] 帧，扣掉进入那一帧，速度只在 0.2 s 的“大约”时间里生效；0.2 / (1/120) 恰好是 24，float 累减 24 次后的结果落在 0 的哪一侧，决定了冲刺多一帧还是少一帧——这是 R4（float 计时）的典型边界效应。60 fps 恰好落在另一侧，所以稳定 5.00 m。
  • 卡顿冲得更远：卡顿帧的 deltaTime 很大，状态在这一帧的 Update 里结束，但物理在这一帧的开头已经以 25 m/s 补跑了整段积压时间。卡 250 ms 时多冲 30%~40%，在平台边缘就是“冲刺掉下悬崖”。Maximum Allowed Timestep = 0.333 把 500 ms 卡顿也截成了 0.333 s，否则会更远。
改法：让“时长”和“位移”用同一个时钟

① 冲刺在 FixedUpdate 里按物理步计数：Enter 记 remainSteps = round(0.2 / fixedDeltaTime) = 10，FixedUpdate 里每步减 1，减到 0 结束——任何帧率、任何卡顿都是 10 步 5.00 m；② 或者干脆不用速度，用 MovePosition 沿预先算好的曲线走完 5 m，碰墙提前结束；③ 至少在逻辑上对单帧 dt 做上限（例如 1/20 s），避免卡顿放大位移。

5.4 E10：周期计时器“到点重置”会漂移

igniteDamageTimer -= dt; if (igniteDamageTimer < 0) { igniteDamageTimer = igniteDamageCooldown; // 0.3：直接覆盖，丢掉了超出的那部分 DecreaseHealthBy(igniteDamage); } // 旋转剑：同样的写法，hitCoolDown 在场景里配的是 0 → 每帧都命中 hitTimer -= Time.deltaTime; if (hitTimer <= 0) { hitTimer = hitCoolDown; /* OverlapCircleAll + 伤害 + 冻结 */ }

到点重置时，实际周期是“冷却时间向上取整到帧”，近似为 $T_{\text{实际}} = \lceil T / \Delta t \rceil \cdot \Delta t$（float 累减让“恰好整除”的情况落在哪一侧不确定）。点燃持续 2 s、冷却 0.3 s：

场景里的飞剑类型是 Regular，旋转模式目前不会触发；但 hitCoolDown = 0 是一个“换个枚举值就爆炸”的配置。改法与冲刺相同：累加而不是覆盖（timer += cooldown，一帧内用 while 处理多次），或在固定步里计数；伤害类周期效果最好放进固定逻辑帧（Buff 系统统一 tick，第 7 章）。

5.5 E9：瞄准虚线为什么总比剑高一点

// 虚线：连续时间抛物线 p(t) = p0 + v0·t + ½·g·s·t² Vector2 position = (Vector2)player.transform.position + new Vector2( AimaDirection().x * launchForce.x * t, AimaDirection().y * launchForce.y * t) + 0.5f * (Physics2D.gravity * swordGravityScale) * (t * t); // 实际：rb.velocity = finalDir（= 方向 ⊙ launchForce），rb.gravityScale = swordGravityScale，交给 Box2D 积分

Box2D 用半隐式欧拉：先用重力更新速度，再用新速度更新位置。把它展开成闭式解：

水平方向没有加速度，两者的 x 完全相同，所以“同一时刻的差”就是“同一 x 处的差”。代入场景值（gravityScale 4.5、Δt 0.02、launchForce (35, 28)）实测 E9：

0.44 m（1 秒处）在 2D 横版里大约是角色身高的五分之一，玩家会觉得“剑总是比瞄准的低一点”。修法：虚线直接用离散闭式解 $p_n = p_0 + v_0 n\Delta t + g s \Delta t^2 \frac{n(n+1)}{2}$，取 $n$ 为物理步数，就和 Box2D 逐步积分逐位一致（只要没有阻尼和碰撞）；需要考虑碰撞时，用 PhysicsScene2D 在一个隐藏的物理场景里 Simulate 预演。

另外三个与时间有关的细节
  • 插值：玩家和骷髅的刚体开了 Interpolate，渲染位置在物理步之间平滑；飞剑没开，在 144 fps 屏幕上它每 0.02 s 才跳一次位置，快速飞行时会有“抖动感” 推断。
  • 直接改 transform 的刚体：旋转剑停住后用 transform.position = MoveTowards(...) 移动一个带 Rigidbody2D 的物体（项目关闭了 Auto Sync Transforms），物理世界里的位置要到下一次模拟前同步——中间的 Overlap 查询会用旧位置。应改用 rb.MovePosition。
  • 隧穿：飞剑刚体是 Discrete 碰撞检测，速度约 35 m/s，每步移动 0.7 m，而剑的触发器半径只有 0.35 m——薄墙和瘦小的敌人可能被直接穿过。玩家和骷髅用的是 Continuous，飞剑也应该改。

5.6 面试追问

Update 和 FixedUpdate 的区别？（Q5-1） ├─ 为什么移动要乘 deltaTime？设 velocity 也要乘吗？（Q5-2） ├─ 冲刺 / 攻击位移在高帧率下距离会变吗？卡顿时呢？（Q5-3 → E10） ├─ 计时器怎么写才帧率无关？（Q5-4） ├─ 固定步长游戏循环怎么写？为什么要插值？（Q5-5） └─ 轨迹预测怎么和物理对上？（Q5-6 → E9）
Q5-1　Update 和 FixedUpdate 的区别？

L1　Update 每渲染帧一次，间隔是 deltaTime、不固定；FixedUpdate 按 fixedDeltaTime（默认 0.02 s）固定间隔，一帧里可能执行 0 次或多次，物理模拟紧跟在它后面。

L2　所以输入在 Update 读（GetKeyDown 只在一帧为真，FixedUpdate 可能漏掉），物理相关的力和持续推进放 FixedUpdate；在 Update 里直接设 velocity 是可以的，它在下一个物理步生效。

L3 · 项目　我的冲刺在 Update 里计时、靠物理积分位移，测出来 120 / 144 fps 下距离会少 0.5 m，冲刺中卡顿 250 ms 能多冲 30%；改成按物理步计数后任何帧率都是 10 步 5 m。

Q5-2　为什么移动要乘 deltaTime？设 velocity 也要乘吗？

L2　直接改 position 时，每帧位移 = 速度 × 这一帧经过的时间，不乘就变成“每帧固定位移”，帧率翻倍速度翻倍。设 velocity 不用乘——velocity 本来就是“每秒”的量，由物理按时间积分；反而乘了才是错的。AddForce 在 FixedUpdate 里调用是“每步一次”，放在 Update 里会随帧率变化（ForceMode.Impulse 的一次性冲量例外）。

Q5-3 → Q5-4　计时器怎么写才帧率无关？

L2　周期性的计时器用累加：timer -= dt; while (timer <= 0) { timer += period; Fire(); }，保留超出的余量，一帧里该触发几次就触发几次；只关心“过没过”的一次性计时器，到点触发即可，但要接受最多一帧的量化。

L3 · 项目　点燃用的是“到点重置”，30 fps 下周期从 0.3 变成 0.333，2 秒少跳一次；旋转剑冷却配成 0 时命中次数等于帧数，240 fps 玩家的伤害是 30 fps 的 8 倍。这类伤害应该放到固定逻辑帧里统一结算。

L4 · 攻击　“累加写法在卡顿时会一口气触发很多次，不是更糟吗？”→ 对伤害来说“总量正确”比“平滑”更重要；如果担心一帧里触发太多，可以给 while 设上限，把剩余的丢弃或延后，这是有意识的取舍，而不是漂移。

Q5-5　固定步长的游戏循环怎么写？

L2　累加器模式：acc += frameDt; while (acc >= step) { Simulate(step); acc -= step; } Render(lerp(prev, curr, acc / step));。逻辑永远以固定步推进，渲染用两个逻辑状态之间的插值，代价是显示比逻辑晚最多一步。还要给 frameDt 设上限防止“死亡螺旋”（Unity 的 Maximum Allowed Timestep 就是这个）。

L3　帧同步游戏把这个循环推到极致：逻辑帧率固定（如 15 Hz），只用定点数，渲染层插值和预表现；这样不同设备、不同帧率得到逐位相同的结果。

Q5-6　轨迹预测怎么和物理对上？

L2　连续抛物线和物理引擎的离散积分不一样：Box2D 是半隐式欧拉，位置比连续解多一项 ½·g·s·Δt·t。没有阻尼和碰撞时，用离散闭式解按物理步数画点就能逐位一致；有碰撞、阻尼、反弹时，在隐藏的物理场景里用 PhysicsScene2D.Simulate 预演若干步。

常见错误回答 ①

错误：“在 Update 里改 rb.velocity 是错的，所有物理操作都必须放 FixedUpdate。”

问题：设速度在 Update 里是安全的；真正有问题的是“在 Update 里施加持续力”和“用 Update 计时决定物理持续时长”。

更好的回答：“输入在 Update 读、意图存下来；持续的力和需要严格时长的推进放在 FixedUpdate；一次性的速度变化放哪都行。”

常见错误回答 ②

错误：“乘了 deltaTime 就帧率无关了。”

问题：乘 deltaTime 只解决“速率”，不解决“离散事件的次数”和“持续时长的量化”——点燃少跳一次、冲刺少走半米，都发生在乘了 deltaTime 的代码里。

5.7 发散场景题

场景 5-1　120 Hz 手机和 60 Hz 手机的玩家，跑图速度、冲刺距离、DPS 一样吗？

为什么会问：移动端高刷普及，帧率差异是真实的公平性问题。

跑图速度一样（类别 ②）；冲刺距离在 120 Hz 下有一部分情况短 0.5 m（类别 ③）；点燃、旋转剑这类周期伤害取决于计时写法（类别 ④），冷却为 0 的技能 DPS 直接翻倍。排查方法：把所有“Update 里计时 + 结果有数值意义”的代码列出来，逐个改成累加或固定步。PVP 游戏还要求逻辑帧完全与渲染帧解耦。

场景 5-2　加入“子弹时间”（Time.timeScale = 0.3），哪些系统会出问题？

为什么会问：考察 scaled / unscaled 时间的边界。

deltaTime、WaitForSeconds、Invoke、FixedUpdate 的步长（fixedDeltaTime 也随 timeScale 缩放，但物理步的间隔不变 → 每秒物理步数减少）都会变慢，这是想要的；需要不受影响的是 UI 动画、输入缓冲窗口（否则预输入时间变长 3 倍）、相机震动等，要改用 unscaledDeltaTime / WaitForSecondsRealtime。Animator 的 Update Mode 要决定是 Normal 还是 Unscaled Time。注意项目里的 Time.time 比较（连招窗口、攻击冷却）是缩放时间，子弹时间里连招窗口会“变长”。

场景 5-3　低帧率时玩家冲刺穿墙，你怎么解释和修复？

为什么会问：隧穿是物理 + 帧率的综合题。

玩家刚体已经是 Continuous，单纯的物理隧穿不太会发生；但卡顿时冲刺多走的那 1~2 m（E10）可能让角色越过平台边缘；而飞剑是 Discrete，每步 0.7 m，薄墙可能被穿过。修复：飞剑改 Continuous；冲刺改成固定步计数；冲刺前用 Rigidbody2D.Cast 预测最远可达位置。

场景 5-4　要做“录像回放”，回放时结果和实战不一致，可能是哪些原因？

为什么会问：回放是确定性的试金石，自然引向帧同步。

本项目里至少有四个不确定源：① 逻辑依赖帧率（冲刺、点燃、旋转剑）；② UnityEngine.Random 没有固定种子且被很多地方共用（暴击、闪避、掉落、分身攻击编号）；③ 动画事件的触发帧依赖渲染；④ 物理引擎在不同帧时序下结果不同。要做输入回放，必须先把逻辑放进固定步、随机数按系统分流并记录种子、命中改成逻辑时间轴；否则只能录“状态”（位置、血量）而不是录“输入”。

自测 1：跳跃高度会随帧率变化吗？基本不会：跳跃只在 Enter 时设一次 vy = 20，之后由物理积分（理论高度 v²/(2gs) = 400/98.1 ≈ 4.08 m）。
自测 2：为什么 60 fps 冲刺稳定 5.00 m，而 120 fps 不稳定？两者都是“0.2 恰好是帧间隔的整数倍”，float 累减后余量落在 0 的哪一侧决定多一帧还是少一帧；60 fps 落在“多一帧”一侧（13 帧），120 fps 落在“少一帧”一侧（24 帧），少的那一帧让部分相位只覆盖 9 个物理步。
自测 3：分身的淡出写法为什么与帧率无关？alpha -= dt · speed 是连续量按时间缩放，总耗时 ≈ 1/speed 秒，误差只在最后一帧。
