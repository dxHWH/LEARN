CHAPTER 02

Unity 生命周期、单例与对象存亡

Awake 和 Start 各该做什么、单例怎么写才对、Destroy 之后对象“什么时候真的没了”、为什么这个项目在编辑器里能跑而打包会失败——这些都是 Unity 客户端面试的必考地基。

本章目标
  • 按“自我初始化 / 跨对象连接 / 首帧运行”三段说清 Awake、OnEnable、Start 的分工，并指出项目里哪里放错了
  • 看懂两个单例为什么写反、会在哪种场景切换下出事；默写正确的模板
  • 说清 fake null、Destroy 延迟、Script Execution Order 不继承这三个“坑”
  • 知道运行时代码里引用 UnityEditor 为什么会让打包失败

2.1 30 秒面试版 · 现状 vs 理想

30 秒回答

Awake 做“只依赖自己”的初始化（取自身组件、建内部数据），Start 做“依赖别人”的连接（拿单例、订阅事件），因为所有 Awake 都在任何 Start 之前；OnEnable / OnDisable 成对做订阅。项目里 Entity 把取组件放在 Start，导致对象在 Awake 和 Start 之间被访问会空引用；两个单例写反了——发现已有实例时销毁的是旧的、新的也不登记；脚本执行顺序配在父类 CharacterStats 上，对挂在场景里的子类无效；Inventory 和骷髅战斗状态 using 了 UnityEditor 命名空间，编辑器里能跑，打包会编译失败。

2.2 Awake / Start 在项目里的分工

位置源码评价
Entity.StartEntity.cs:45-52 取 Rigidbody2D、Animator、EntityFX、CharacterStats、Collider问题 这些只依赖自身，应放 Awake。放在 Start 意味着：运行时 Instantiate 的怪物，在 Awake 之后、Start 之前被打中，fx / stats 都是 null。当前场景只有预置的一只骷髅，所以没暴露。
Player.Awake → StartPlayer.cs:59-89：Awake 里 new 状态，Start 里先 base.Start() 再 Initialize(idleState)源码 顺序是对的：Idle.Enter 会读 player.rb，必须在 base.Start 取完组件之后。但这个约束只写在“调用顺序”里，换个人把两行对调就坏了。
Player.Startskill = SkillManager.Instance，而 SkillManager 在它自己的 Start 里才 GetComponent 三个技能能工作是因为 Player.Start 只缓存了“管理器引用”，真正访问 skill.clone 发生在冲刺时（第 1 帧之后）。如果有人在 Player.Start 里写 skill.dash.xxx，就会随两个 Start 的先后随机空引用。
EnemyStats.Start先 ApplyLevelModifiers() 再 base.Start()（EnemyStats.cs:17-23）源码 刻意的顺序：先加等级修正，再按修正后的上限回满血。写成 base.Start() 在前就会满血少一截。
UI_HealthBar.Start读 GetCurrentHealth() 并订阅（UI_HealthBar.cs:13-25）依赖 CharacterStats.Start 先把 currentHealth 设满——作者用 Script Execution Order（400）保证了这一点，见 2.5。
一句话规则

Awake：我自己。Start：我和别人。OnEnable / OnDisable：我和事件。对象池复用时 Awake / Start 都不会再调，所以“每次出场都要重置的状态”只能放 OnEnable 或池的 OnTakeFromPool 回调里（第 12 章）。

2.3 单例：两个写反了，一个写对了

public static PlayerManager _instance; // public 字段：谁都能改写 private void Awake() { if (_instance != null) Destroy(_instance.gameObject); // ← 销毁的是“已经登记的旧实例” else _instance = this; // ← 新实例只有在没有旧实例时才登记 } private void Awake() { if (instance == null) instance = this; else Destroy(gameObject); // 销毁“后来的自己” }

写反的版本在“只有一个实例”时表现正常，所以平时测不出来。出问题的三种情形：

情形源码行为正确模板的行为
① 场景里误放了两个 SkillManager（复制粘贴、预制体嵌套）A.Awake 登记 A；B.Awake 发现 A，销毁 A 的整个 GameObject（连同上面的 Skill_Dash / Clone / ThrowSword），B 不登记 → 帧末之后 Instance 指向已销毁的 AB 销毁自己，A 继续工作
② 给单例加了 DontDestroyOnLoad，重新加载场景新场景里的副本把常驻的旧实例毁掉，自己又不登记 → 两边都没了新场景的副本自毁，常驻实例保留
③ 叠加加载（Additive）另一个也带 PlayerManager 的场景同 ①：主场景的管理器被毁后加载的自毁
④ 单场景切换（不常驻）旧场景卸载时 A 已销毁，_instance != null 因 Unity 重载的 == 返回 false → 新实例正常登记同左

图 2-2 的结论标为 推断，验证方法在附录 B：复制一个 SkillManager 进场景，按两次 Shift 观察第二次是否打印 “Skill [Dash] is on CoolDown” 且之后再也冲不出去。这个推断恰好是面试的好素材——它把“单例写反”这种看似无害的笔误，和 fake null、销毁对象不再 Update 两个引擎规则串在了一起。

public abstract class SceneSingleton : MonoBehaviour where T : SceneSingleton { public static T Instance { get; private set; } // 只读属性，外部不能改写 protected virtual void Awake() { if (Instance != null && Instance != this) { Destroy(gameObject); return; } // 后来者自毁 Instance = (T)this; } protected virtual void OnDestroy() { if (Instance == this) Instance = null; // 只清理“自己” } } // 子类重写 Awake 时必须先 base.Awake()，并在 base 返回后检查 Instance == this 再继续初始化

2.4 fake null 与 Destroy 延迟：项目里三处依赖它们

代码依赖的规则说明
if (!player.sword)（GroundedState.cs:57）UnityEngine.Object 重载了 bool 转换 / ==：已销毁的对象“等于 null”源码 飞剑被 Invoke("DestroyMe", 7) 销毁后，player.sword 这个 C# 引用并没有清空，但判空返回 true，所以又能掷剑——能工作，但靠的是引擎魔法。如果写成 player.sword is null 或 player.sword?.GetComponent…，C# 层面的判空会认为它还在。
CatchTheSword()：先 ChangeState(catchSwordState) 再 Destroy(sword)（Player.cs:138-142）Destroy 在帧末才生效CatchSword.Enter 读 player.sword.transform 判断朝向。即使两行对调也能工作，因为 Destroy 之后本帧对象仍然存在——但别依赖这一点。
PickupItem()：AddItem 后 Destroy(gameObject)（ItemObject.cs:39-43）同上风险 如果同一物理步里触发器收到两次进入回调（例如玩家根物体上有两个碰撞体），两次都会 AddItem——Destroy 拦不住同一帧的第二次。当前玩家根物体只有一个胶囊体（血条上那个 Trigger 在子物体上，GetComponent<Player>() 取不到），所以没触发；做法是拾取时先置 picked = true 并关掉碰撞体。
扩展：fake null 到底是什么

UnityEngine.Object 是“C# 壳 + C++ 本体”。Destroy 释放的是 C++ 本体，C# 壳要等没人引用后被 GC 回收。为了让壳在本体消失后“看起来像 null”，Unity 重载了 == 和 bool 转换，检查本体指针。因此：① ?.、??、is null 不走重载，会把已销毁对象当成活的；② 编辑器里 GetComponent 找不到组件时返回的也是一个“假 null”壳（为了给出更友好的报错），会产生少量托管分配，打包后不会。

2.5 Script Execution Order：配了 4 个，只有 1 个起作用

脚本（meta 中的 executionOrder）场景里实际挂的组件是否生效
CharacterStats　300PlayerStats、EnemyStats（子类，各自的 MonoScript 顺序为默认 0）否：执行顺序按“具体脚本”记录，不会被子类继承（社区实测；代码里用 [DefaultExecutionOrder] 特性则会继承）
UI_HealthBar　400UI_HealthBar ×2是：它的 Start 晚于默认顺序的 PlayerStats / EnemyStats.Start，所以第一次读到的就是满血
ItemData　500ScriptableObject否：执行顺序只对 MonoBehaviour 的事件函数有意义
ItemDrop　600ItemDrop（没有 Awake / Start / Update）无可排序的函数

看得出作者遇到过“血条初始显示为 0”的问题，并用执行顺序修好了——这是个值得在面试里讲的经历，但要讲到下一层：执行顺序是全局配置，是“隐式契约”。更稳的做法是显式初始化：血条在 OnEnable 里订阅，并在 Stats 初始化完成时由 Stats 发一次 onHealthChanged；或者由一个 Bootstrap 组件按顺序调用各系统的 Init()。

2.6 打包会失败：运行时代码引用了 UnityEditor

using static UnityEditor.Progress; // Inventory.cs：IDE 自动补全带进来的 using UnityEditor.Experimental.GraphView; // Enemy_SkeletonBattleState.cs：同上

问题 P0 编辑器里所有程序集都能看到 UnityEditor.dll，所以 Play Mode 一切正常；打包时运行时程序集（Assembly-CSharp）不引用编辑器程序集，这两行会报“找不到命名空间 UnityEditor”，构建直接失败。两处都没有真正用到其中的类型，删掉即可。

工程上怎么提前发现

① 用程序集定义（.asmdef）把运行时代码和编辑器代码分开，运行时 asmdef 不勾 Editor 平台，误用会在编辑器里就报错；② 必须混写时用 #if UNITY_EDITOR … #endif 包住；③ CI 每天跑一次真打包（哪怕只打 Windows）——“编辑器能跑 ≠ 能打包”是最常见的提测事故之一。另外几处 using Unity.VisualScripting;（Entity、Player、Skill、SkillManager 等）没用到任何类型，虽不致命，但会让代码隐式依赖 Visual Scripting 包。

2.7 面试追问

Awake 和 Start 的区别？（Q2-1） ├─ 为什么取组件要放 Awake？放 Start 会出什么问题？（Q2-1 L3） ├─ 单例怎么写？你的单例有没有问题？（Q2-2） │ ├─ 场景切换 / DontDestroyOnLoad / 叠加加载时怎样？（2.3 表） │ └─ 单例的缺点？怎么替代？（Q1-4、Q2-5） ├─ Destroy 之后马上访问会怎样？什么时候真正销毁？（Q2-3） │ └─ 为什么 obj == null 是 true 但 obj?.x 还能执行？（Q2-4 fake null） └─ 多个脚本的初始化顺序怎么控制？（Q2-5）
Q2-1　Awake 和 Start 的区别？

L1　Awake 在对象实例化（且所在 GameObject 激活）时立刻调用，Start 在该脚本第一次 Update 之前调用；同一批加载的对象，所有 Awake 都先于任何 Start。

L2　所以 Awake 做自我初始化，Start 做跨对象连接。脚本被禁用时 Awake 仍会执行而 Start 不会，直到它被启用。

L3 · 项目　我的 Entity 把 GetComponent 放在了 Start，现在没出问题是因为怪物都是场景预置的；如果改成刷怪，刷出来的那一帧被飞剑打到，DamageEffect 里的 fx 就是空的。应该挪到 Awake。

L4 · 攻击　“运行时 Instantiate 的对象，Start 什么时候调？”→ Instantiate 返回前 Awake / OnEnable 已经执行；Start 推迟到它的第一次 Update 之前——在 Update 里创建的对象，社区实测是本帧 Update 之后补调 Start、下一帧才第一次 Update。所以“生成后立刻配置参数”应该在 Instantiate 之后、Start 之前完成，Start 里不要覆盖这些参数（项目里 SetupClone、SetupSword 正是在 Instantiate 之后立刻调用的）。

Q2-2　单例怎么写？

L2　Awake 里：已有实例且不是自己 → 销毁自己并 return；否则登记自己；OnDestroy 里只在 Instance 是自己时清空；Instance 做成只读属性。需要跨场景就在登记后 DontDestroyOnLoad。

L3 · 项目　我项目里 PlayerManager 和 SkillManager 写反了：发现旧实例时销毁的是旧实例，新的还不登记。只有一个实例时看不出来；场景里多放一个就会把旧的连同上面的技能组件一起毁掉，按我的推断冲刺会变成只能用一次——因为被毁的组件不再 Update，冷却不再递减，而 C# 字段还读得到。

L4　“那你为什么不用 static class？”→ 管理器需要 Inspector 配置（技能预制体、数值）和 Unity 生命周期（Update 递减冷却），所以是 MonoBehaviour；纯逻辑的工具（伤害公式）才适合 static。

Q2-3 → Q2-4　Destroy 什么时候生效？fake null 是什么？

L2　Destroy 把对象标记为待销毁，当前帧的更新循环结束后才真正销毁（DestroyImmediate 立即销毁，只建议编辑器代码用）。所以 Destroy 后本帧内对象仍然可用，回调还会继续收到。

L3　销毁后 C# 壳还在，Unity 重载了 == 让它等于 null；?. / ?? 不走重载，会把它当成活对象。我项目里 if (!player.sword) 能在飞剑自动销毁后正确返回“没有剑”，靠的就是这个重载。

Q2-5　多个脚本的初始化顺序怎么控制？

L2　三种手段：Script Execution Order（全局配置）、[DefaultExecutionOrder]（写在代码里，可被子类继承）、显式初始化（一个入口按顺序调用 Init，或依赖方在被依赖方就绪事件里再初始化）。

L3 · 项目　我用执行顺序 400 让血条的 Start 晚于属性组件，解决了初始显示 0 的问题；但我把 300 配在了父类 CharacterStats 上，对场景里的 PlayerStats / EnemyStats 并不生效。现在我更倾向显式初始化：执行顺序是隐式契约，人一多就没人记得为什么是 400。

常见错误回答 ①

错误：“Start 在 Awake 之后调用，所以在 Start 里访问别的对象一定安全。”

问题：只保证“所有 Awake 先于任何 Start”，不保证 A.Start 先于 B.Start；运行时生成的对象也不在同一批里。

更好的回答：“Start 里访问别人在 Awake 里准备好的东西是安全的；访问别人在 Start 里才准备的东西不安全，需要执行顺序或显式初始化。”

常见错误回答 ②

错误：“Destroy 之后对象就是 null 了。”

问题：本帧内它还活着；之后 == null 为真，但 C# 引用并未清空，?. 仍会执行。

更好的回答：“Destroy 在帧末生效；销毁后用 Unity 的 == 判空，自己持有的引用最好在 OnDestroy 或回调里手动置空。”

2.8 发散场景题

场景 2-1　主菜单 → 战斗 → 主菜单，玩家的背包和属性怎么保留？

为什么会问：项目只有一个场景，Inventory 和 PlayerStats 都跟场景同生共死。

把“数据”和“表现”拆开：背包、装备、属性基础值放进一个跨场景的纯数据对象（常驻的 GameSession / 存档服务，或 ScriptableObject 运行时容器），场景里的 Inventory / PlayerStats 只是视图和行为，在 OnEnable 时从数据层加载、OnDisable 时写回。不要给整个玩家 GameObject 加 DontDestroyOnLoad——它会把相机跟随、UI 引用、场景内对象引用全部带到新场景里变成悬空引用。

场景 2-2　改成刷怪笼，刷出来的骷髅在出生那一帧被旋转剑命中，会发生什么？

为什么会问：考察你能否把 Awake / Start 的区别落到具体的空引用上。

如果是在 Update 里 Instantiate，按社区实测 Start 会在本帧 Update 之后才补调；而飞剑的 SpinLogic 在 Update 里调用 ThrowSwordDamage(enemy) → player.stats.DoDamage(enemy.stats)——骷髅的 stats 是在 Entity.Start 里赋值的，此时可能还是 null，同帧的 enemy.DamageEffect() 里 fx 也可能为 null。修法：取组件挪到 Awake；或者刷怪后先置为“无敌 / 不可选中”一帧。

场景 2-3　加了对象池以后，复用的骷髅“满血复活”失败、弹反提示还亮着，为什么？

为什么会问：对象池是第 12 章的重构方向，面试官会提前埋雷。

池化对象第二次出场不会再调 Awake / Start：currentHealth = GetMaxHealth() 在 Start 里、CloseCounterAttackWindow() 在 Awake 里，stateMachine.Initialize(idleState) 在 Start 里，都不会重跑；死亡状态把 cd.enabled = false、animator.speed = 0 也不会恢复。所有“出场重置”要集中到一个 OnSpawn()（由池在取出时调用），并且和 OnDespawn() 成对。

场景 2-4　为什么同一份代码在同事电脑上偶现血条显示 0？

为什么会问：执行顺序未定义的经典表现。

两个默认顺序的脚本之间先后不确定（官方文档明确说不要依赖），可能随机器、构建、Unity 版本变化。我的项目恰好用执行顺序 400 消除了血条与属性的竞争；如果别人把它从列表里删掉，或者新增一个默认顺序、又依赖 currentHealth 的脚本（比如 Boss 血条），问题就会回来。根治是让“谁先初始化”显式化。

本章速记
  • Awake 我自己、Start 我和别人、OnEnable/OnDisable 我和事件；池化对象只会重复 OnEnable/OnDisable。
  • 单例：后来者自毁 + 只读属性 + OnDestroy 只清自己；项目里 PlayerManager / SkillManager 写反（#4）。
  • fake null：Destroy 后 == null 为真，?. 不认；Destroy 在帧末生效。
  • 执行顺序不被子类继承（CharacterStats 300 无效）；运行时代码 using UnityEditor → 打包失败（#1）。
自测 1：Player.Start 里如果先 Initialize(idleState) 再 base.Start()，会怎样？Idle.Enter 执行 rb = player.rb 时 rb 还没取，后面 rb.velocity = … 空引用。
自测 2：情形 ① 里为什么不是立刻空引用，而是“冲刺只能用一次”？Instance 指向已销毁的 A，读 C# 字段（dash、coolDownTimer）不会抛异常；但被销毁的组件不再 Update，冷却停在 1，于是第二次起永远在冷却中（推断，附录 B 验证）。
自测 3：怎样让基类上的执行顺序对所有子类生效？在基类上加 [DefaultExecutionOrder(n)] 特性（社区实测会被子类继承），或在 Project Settings 里逐个添加子类。
