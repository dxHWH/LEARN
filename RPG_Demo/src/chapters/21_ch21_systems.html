CHAPTER 21

系统设计：背包、装备与技能为什么这样设计

问题 ⑤：“讲一讲整个背包、装备乃至技能系统的设计思路，为什么这么设计？”——这是 RPG 方向最常见的系统设计题。好的回答不是罗列类名，而是先说清分层原则，再说三个系统各自的模型，最后说它们通过哪几条共享通道协作。Demo 里的问题在这里都变成了“为什么要分这一层”的论据。

本章目标
  • 用“配置 / 实例 / 规则 / 表现”四层和“属性修正 / 效果 / 标签与事件”三条通道讲清整体设计
  • 分别给出背包、装备、技能的数据模型和关键设计决策，并能说出每个决策的理由
  • 用一个端到端例子（穿上火焰剑 → 普攻点燃敌人）演示三个系统如何协作
  • 知道什么时候 Demo 式的简单实现就够了，什么时候必须升级——避免被问成“过度设计”

21.1 口径：30 秒怎么讲 · 现状 vs 理想

面试口播

现状Demo 现状：物品是 ScriptableObject 配置，背包、材料仓库、装备栏各用“列表 + 以物品配置为键的字典”；穿装备时物品配置直接给玩家的各项属性加修正；技能是挂在技能管理器上的组件，基类只管冷却。

理想设计思路：我会把三个系统统一成四层——配置（策划配的不变数据）、实例（运行时会变的状态，能存档、能同步）、规则（所有修改都通过有校验的操作完成）、表现（UI、特效只订阅变化）；三个系统之间只通过三条通道交流：属性修正（装备、Buff、技能都只登记修正，最终属性由修正推导）、效果（伤害、治疗、上 Buff 都是“效果”）、标签与事件（阻断、触发、刷新 UI）。

为什么：Demo 里的问题几乎都是缺了某一层——没有实例层，“+5 的剑”存不了；操作不是事务，合成少扣了材料；配置直接改玩家属性，没有来源、做不了属性预览；技能参数写在组件上，新增技能就要写新类。

21.2 总纲：四层与三条通道

通道谁写谁读解决什么
属性修正装备（穿戴时注册）、Buff（生效时注册）、被动技能、等级成长伤害公式、移动速度、UI 属性面板多个系统影响同一属性时不互相覆盖（第 7 章 E8 的根因）；可按来源撤销；可做属性预览
效果技能时间轴、武器命中、道具使用、环境（陷阱）伤害管线、Buff 系统“造成伤害、施加 Buff、治疗、召唤”统一成数据配置的效果，技能只是效果的编排
标签与事件状态机（Dead、Stunned）、Buff（Frozen）、装备（Armed）技能能否释放、AI、任务成就、UI跨系统的条件判断不需要互相引用（“眩晕时不能放技能”由标签表达）

21.3 为什么这样分：六个设计原则

原则含义Demo 里的反例
单一数据源同一份状态只有一个拥有者，其他地方只读或订阅属性被装备配置、冰冻、冻结、死亡多处直接修改
配置与状态分离配置只读、可共享；会变化的东西放实例以物品配置作字典键 → 无法表达同种物品的不同状态
修改走操作每次修改都有校验、要么全成要么全败、有结果码合成先校验后扣料，但扣料只扣一份；失败只打日志
依赖方向向下表现依赖规则，规则依赖实例与配置，反之不行物品配置（资源）通过单例直接改玩家组件
扩展靠数据，不靠子类新增内容主要是配新数据，不写新类每个技能一个组件类；飞剑四种模式写成标志位分支
可存档、可同步、可测试实例层是纯数据，能序列化、能在服务器上跑、能单测数据散在 MonoBehaviour 字段里，只能进 Play Mode 手测

21.4 背包：数据模型与关键决策

层内容设计要点
物品定义稳定 id、类型、堆叠上限、品质、图标、标签、可交易 / 可出售id 必须稳定（存档、网络、表格都用它），不能用资源路径或数组下标
物品实例唯一 id、定义 id、数量、实例数据（耐久、强化等级、随机词条、绑定、获取时间）可堆叠的材料可以“只有数量没有实例数据”；装备每件一个实例
容器容量、格子数组、过滤规则（只能放材料 / 只能放某部位装备）背包、仓库、装备栏、商店、邮件附件都是容器，一套代码
操作添加、移除、移动、交换、拆分、合并、使用、丢弃、合成、整理每个操作先只读校验、再一次性提交；返回结果码（成功 / 背包满 / 数量不足 / 不可放入）
事件与视图“第 i 格变化了”事件；格子视图只持有（容器, 下标）增量刷新；格子多时用虚拟列表
关键决策选项怎么选
格子制 or 列表制格子制：固定格子、允许空洞、玩家可以摆放；列表制：按类型自动排序，没有“格子”需要玩家管理空间（生存、MMO）用格子制；以收集为主（动作 RPG 的材料）用列表制
堆叠规则同定义即可堆叠 / 同定义且实例数据相同才堆叠 / 不可堆叠按物品类型配置；有耐久、词条的物品不可堆叠
满了怎么办拒绝 / 进溢出邮箱 / 掉在地上写进规则，返回明确结果码，UI 给提示
谁是权威单机：本地；联网：服务器客户端只发“意图”（用第 3 格的药），服务器执行操作后回包；客户端可乐观预表现
Demo 里对应的坑

现状以配置作键（没有实例）→ “+5 的剑”无处存放；三套“列表 + 字典”复制了三份代码 → 应抽象成容器；任何变化都全量刷新所有格子、一次装备刷新三次 → 应发格子级事件；合成每种材料只扣一份 → 操作不是事务；格子的物品字段被序列化，开局时是一个“空壳对象”导致点空格空引用 → 视图不该拥有数据（第 10 章）。

21.5 装备：有槽位规则的容器 + 修正来源

  • 修正带来源、分层级：每条修正记录“来自哪件装备实例 / 哪个 Buff”，并区分固定值、加算百分比、乘算百分比三类，按固定顺序合成（第 7 章）。卸下时按来源整体移除，不会误删别人的同值修正。
  • 属性预览：属性推导做成纯函数“基础值 + 一组修正 → 最终属性”。UI 想显示“换上这件后攻击 +12”，只需用“当前修正 − 旧装备 + 新装备”算一次，不需要真的穿上再脱下——Demo 的做法（配置直接改玩家属性）做不到这一点。
  • 套装与条件属性：作为“根据当前装备集合计算出的额外修正来源”，装备变化事件触发重算。
  • 表现分离：换外观、换武器动作集由装备变化事件驱动，属性系统不知道模型的存在。

21.6 技能：定义 + 实例 + 激活管线

部件内容为什么
技能定义消耗、冷却、充能、需求标签、阻断标签、目标方式、时间轴、效果列表、表现提示新增技能 = 新增一份配置；平衡调整不改代码
技能实例等级、冷却剩余、充能层数、临时修正（冷却缩减）同一技能在不同角色身上状态不同；可存档、可同步
激活管线能否释放 → 提交 → 执行 → 结束；查询和提交分开避免“检查即消耗”（Demo 的 CanUseSkill）；被状态守卫拒绝时不扣冷却
时间轴前摇、位移、判定窗口、霸体 / 无敌区间、可取消窗口、后摇与动画对齐但不依赖动画播放（第 4 章）；可编辑、可预览
效果伤害、治疗、施加 / 移除 Buff、位移、召唤、生成投射物可组合：飞剑的“弹跳 / 穿刺 / 旋转”就是不同效果与投射物行为的组合（第 8 章）
标签技能给自己加、需要、被谁阻断、会取消哪些技能跨系统条件不需要互相引用；和状态机的打断等级是同一个思想

技能与状态机的关系：角色状态机管“移动层”（地面、空中、滑墙），技能系统是“动作层”——技能释放时向状态机申请进入“施法”状态（带打断等级），时间轴结束再释放。这样冲刺、攻击、掷剑不再是状态机里的十几个特殊状态，而是同一种“施法”状态执行不同的技能数据。

Demo 里对应的坑

现状冷却查询带副作用；技能参数（冲刺速度、时长、飞剑 20 个字段）在组件和角色上，无法复用；冲刺在角色每帧更新里全局检测，没有经过“能否释放”的统一入口，所以死亡后也能冲刺；分身的伤害来源靠层级查找、结果为空（第 8 章 P0）——技能产生的效果应该在创建时就带上“来源”。

21.7 三个系统怎么协作：一个端到端例子

这条链路在 Demo 里也“存在”，但每一步都是直接调用：物品配置直接改玩家属性、动画事件回调里直接算伤害、元素异常在伤害函数里直接施加（而且这条调用被注释掉了，第 7 章）、表现与结算分开调用（第 6 章）。分层之后，链路上任何一环都可以单独替换、单独测试、单独搬到服务器上。

21.8 取舍：什么时候简单实现就够了

信号出现前（Demo 规模）出现后必须升级的部分
物品需要“个体差异”（耐久、强化、随机词条）以配置作键的堆叠就够实例层 + 唯一 id
需要存档 / 跨场景数据放组件上也能跑实例层纯数据化 + 稳定 id + 版本迁移
多个来源影响同一属性（装备 + Buff + 被动）直接加减可以凑合修正器栈 + 来源
技能超过 10 个 / 策划要自己配每个技能一个类也能写数据驱动定义 + 效果组合 + 时间轴编辑器
联网本地即权威操作改成请求 / 回包，随机与结算放服务器，实例层可序列化同步
多人协作开发一个人记得所有约定操作的结果码、事件契约、单元测试
回答“会不会过度设计”

“Demo 的规模下，直接实现是合理的，我也是这么做的；但我知道每一层是为哪个需求准备的——比如出现‘物品个体差异’就必须有实例层、出现‘多来源改属性’就必须有修正器。分层不是一开始全部做完，而是在信号出现时按这个方向演进，并且一开始就别做会挡路的事（比如以配置作字典键、让配置直接改玩家）。”

21.9 面试防守

① 澄清需求：单机还是联网？要不要存档？物品有没有个体差异？技能多少个、谁来配？ ② 先给分层：配置 / 实例 / 规则 / 表现，画图 21-1 ③ 数据模型：每层有哪些字段，id 怎么定，谁是权威 ④ 关键操作：以“穿装备 / 合成 / 释放技能”为例走一遍流程，强调校验与事务 ⑤ 跨系统协作：属性修正、效果、标签与事件三条通道 ⑥ 非功能：存档与版本、网络同步、性能（虚拟列表、脏标记）、可测试 ⑦ 取舍：现阶段做到哪一层，哪些信号出现时再升级
Q21-1　背包为什么要分配置和实例？

L2　配置是“这种物品是什么”，实例是“这一件物品现在怎样”。一把剑的名字、图标、基础攻击是配置；它被强化了几次、还剩多少耐久、随机出了什么词条是实例。只有配置时，同种物品永远完全相同，个体差异无处存放——我的 Demo 就是以配置作字典键，“+5 的剑”做不了。

L3　实例还带来两个好处：存档和网络只需要序列化实例（定义 id + 实例数据），配置随版本发布；同一份配置可以被成千上万个实例共享，内存也省。

Q21-2　装备的属性怎么加？卸下怎么撤销？属性对比怎么做？

L2　装备不直接改属性，而是在属性集里注册一组“来自这件装备”的修正；卸下按来源整体移除；最终属性由“基础值 + 所有修正”按固定顺序推导，并用脏标记缓存。属性对比用同一个推导函数，在一组“假设的修正”上算一次即可，不需要真的穿脱。

Q21-3　技能系统为什么要数据驱动？

L2　技能多了以后，差异主要在数据（数值、时间轴、效果组合），而不在逻辑结构。数据驱动后新增技能是配置工作，策划能自己调；逻辑只写一次（激活管线、时间轴执行器、效果执行器），测试也只测这几个通用部件。

L4 · 攻击　“全部数据驱动，特殊技能怎么办？”→ 留扩展点：效果类型可以注册自定义实现，时间轴可以插“脚本事件”节点；目标是 90% 的技能纯配置，10% 的特殊技能写少量自定义效果，而不是反过来。

Q21-4　Buff 和技能是什么关系？

L2　技能是“什么时候发生什么”的编排，Buff 是“持续一段时间的状态”。技能通过效果施加 Buff；Buff 通过修正影响属性、通过标签影响技能能否释放（眩晕 Buff 带“禁止施法”标签）、也可以周期性地产生效果（点燃每 0.3 s 一次伤害效果）。两者通过效果和标签解耦，互相不直接引用。

Q21-5　联网以后这三个系统怎么改？

L2　实例层由服务器持有和修改；客户端只发意图（装备第 3 格、释放技能 X 朝方向 d），服务器执行操作、结算效果，再把实例变化同步回来。客户端为了手感做预表现：技能动作和特效先播，伤害数字和背包变化以服务器为准；操作带请求 id 防止重发造成双扣。因为四层已经分开，改动集中在“规则层由谁执行”和“实例层怎么同步”，配置和表现几乎不用动。

常见错误回答

错误：“背包用 List，装备用 Dictionary，技能每个写一个类继承 Skill。”

问题：只讲了容器类型，没有讲分层、权威、事务、跨系统协作；面试官追问“+5 的剑”“多来源改属性”“新增 50 个技能”就会卡住。

更好的回答：按 21.9 的模板，从需求澄清讲到分层、模型、操作、协作、取舍。

21.10 发散场景题

场景 21-1　做随机词条装备（暗黑类）：掉落时随机出 1~4 条属性。

考点：实例数据与生成规则。

配置层存“词条池”（每条：属性、数值范围、权重、可出现的部位与品质）；掉落时由服务器（或单机时的权威逻辑）按品质决定条数、按权重无放回抽词条、在范围内随机数值，写进物品实例；穿戴时实例里的每条词条变成一条修正。随机过程用可记录种子的随机数，便于排查“为什么出了这件”。

场景 21-2　加入天赋树：点了“冲刺后 2 秒暴击 +20%”。

考点：被动效果如何接入事件与 Buff。

天赋是一种“被动技能”：解锁时注册一个事件监听（技能“冲刺”结束），触发时给自己施加一个 2 秒的 Buff，Buff 携带“暴击率 +20%”的修正。整个过程只用到技能事件、Buff、修正三样已有部件，不需要改冲刺技能本身。

场景 21-3　商城、邮件、交易都要“给玩家物品”，怎么避免各写一套？

考点：容器与操作的复用。

所有“给物品”都走同一个操作：向目标容器添加实例，返回结果码（成功 / 满了）；满了的处理（进邮箱、拒绝、掉地上）由调用方按场景决定。交易是两个容器之间的原子交换（双方物品先锁定，确认后一次性移动）。这样“背包满了怎么办”这类规则只写一次，日志与防刷也只做一处。

本章速记
  • 四层：配置（只读）/ 实例（可存档可同步）/ 规则（操作即事务）/ 表现（只订阅）。
  • 三条通道：属性修正（带来源）、效果（统一伤害 / 治疗 / Buff）、标签与事件。
  • 背包：定义、实例、容器、操作、视图；装备 = 容器间移动 + 修正来源；技能 = 定义 + 实例 + 激活管线（能否 → 提交 → 时间轴 → 效果）。
  • Demo 的问题都是“缺了一层”：无实例、非事务、配置直改属性、查询带副作用、参数在组件上。
  • 取舍：不必一开始全做，但别做会挡路的事；按信号演进。
自测 1：为什么说背包、仓库、装备栏、邮件附件都是“容器”？它们都是“有容量和放置规则的物品集合”，差别只在过滤规则（装备栏只能放对应部位的装备）；统一成容器后，移动、交换、事务、事件、存档只需实现一次。
自测 2：属性预览为什么要求属性推导是纯函数？预览需要在“假设的修正集合”上计算属性而不改变真实状态；只有推导函数不依赖也不修改外部状态，才能安全地算出“换上之后会怎样”。
自测 3：技能“能否释放”和“提交”为什么要分开？因为能否释放之后还可能被拒绝（状态守卫、网络校验）；如果检查时就扣冷却和消耗，被拒绝时资源已经白白损失。
