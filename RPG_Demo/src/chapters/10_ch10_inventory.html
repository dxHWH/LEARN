物品、UI 与工程化

最后一次提交 “IventorySystem” 加入了背包、装备、合成、掉落和格子 UI。这是 RPG 客户端面试里最容易被追问到“数据结构 + 事务 + 防刷 + 存档”的部分；第 11、12 章再看表现层和整个工程的性能与规范。

CHAPTER 10

背包、装备、合成与掉落

背包用“List 保序 + Dictionary 查找”的双结构，以 ScriptableObject 作键堆叠；装备通过修正器加属性；合成先校验后扣料；掉落先按概率筛选再无放回抽样。实测发现：合成每种材料只扣一份，10 皮 10 铁能做 [[e6.10_10.bc]] 件而不是 [[e6.10_10.fc]] 件；掉落判定多 1%，掉率填 0 的物品也会掉。

本章目标
  • 说清背包双结构的取舍，以及“ScriptableObject 当键”意味着没有物品实例
  • 走一遍装备流程，找出两处点击空格就空引用的原因（含 Unity 序列化器的一个特性）
  • 用 E6 / E5 量化合成少扣料和掉落概率偏差
  • 设计一个可存档、可联网校验的物品系统：定义 / 实例 / 容器 / 事务

10.1 30 秒面试版 · 现状 vs 理想

30 秒回答

物品定义是 ScriptableObject（类型、名称、图标、掉率；装备再加 14 项属性和配方）；背包、仓库、装备栏各用一个 List 保持显示顺序、一个 Dictionary 以 ItemData 为键找堆叠，任何变化后全量刷新格子 UI。装备时先卸同部位旧装备放回背包，再把新装备的属性加到玩家 Stat 上。合成先检查每种材料数量够不够，再扣料加成品；掉落先让每个候选按掉率独立判定，再从入选的里无放回抽最多 3 个。问题：以定义作键意味着没有物品实例（耐久、随机词条都做不了）；合成每种材料只调一次 RemoveItem，需要 2 张皮只扣 1 张；掉落用 <= 比较 0~99，每件都多 1%，且“最多 3 件”的截断让真实掉率低于配置；点空的装备格和首次刷新前点空背包格都会空引用。

10.2 数据模型：双结构 + 定义作键

设计点项目做法好处代价
双结构List 保序 + Dictionary 查找堆叠查找 O(1)，显示顺序稳定两个结构要同步增删，任何一处漏写就不一致；删除时 List.Remove 是 O(n)
定义作键Dictionary<ItemData, InventoryItem>同类物品自动堆叠，引用比较极快没有“这一把剑”的概念：耐久、强化等级、随机属性、绑定状态、获取时间都无处存放
全量刷新每次增删都清空所有格子再按 List 重画简单，不会不同步一次装备操作刷新 3 次（AddItem、RemoveItem、EquipItem 末尾各一次）；格子多时浪费；格子数少于物品种类时直接越界
InventoryItem 复用为配方Nice_Armor 的配方是 List<InventoryItem>（材料 + 数量）少写一个类运行时“堆叠”和设计期“配方条目”语义不同，构造函数里的 AddStack 对配方毫无意义

10.3 装备流程与两个空引用

问题 P1 两处点击空格的空引用原因不同：

  • 装备格：UI_EquipmentSlot.OnPointerDown 直接 item.data as ItemData_Equipment，卸下后 CleanUpSlot() 把 item 置为 null，再点一次就空引用。基类 UI_ItemSlot 有 if (item == null) return;，子类重写时丢了。
  • 背包格，首次刷新之前：public InventoryItem item 是一个 [Serializable] 普通类字段。Unity 序列化器不支持自定义类字段为 null，会为它构造一个默认实例——ItemSlot.prefab 里就序列化着 item: {data: {fileID: 0}, stackSize: 0}。于是开局时每个格子的 item 都“不为 null 但 data 为 null”，基类的判空拦不住，点击空格走到 item.data.itemType 空引用。第一次拾取物品触发 UpdateSlotUI 之后，所有格子被 CleanUpSlot 置为真正的 null，问题就消失了——典型的“只在开局出现一次”的 bug。
怎么避免

格子不要把数据对象序列化进 Inspector：字段加 [System.NonSerialized] 或做成 private；判空写成 item?.data == null 一并检查；更根本的是格子只持有“容器 + 下标”，数据从容器读——UI 不拥有数据。

10.4 E6：合成只扣一份材料

public bool CanCraft(ItemData_Equipment _itemToCraft, List _requiredMaterials) { List materialsToRemove = new List(); foreach (var need in _requiredMaterials) { if (stashDictionary.TryGetValue(need.data, out InventoryItem have) && have.stackSize >= need.stackSize) materialsToRemove.Add(have); // 校验的是“够不够 need.stackSize 个” else { Debug.Log("not enough materials"); return false; } } foreach (var m in materialsToRemove) RemoveItem(m.data); // ← 每种材料只移除 1 个 AddItem(_itemToCraft); return true; // 名字是 Can，实际已经合成了 }

问题 P1 这是一个经济漏洞：在有交易或数值成长的游戏里，合成成本减半会直接破坏产出平衡。修法一行：for (int k = 0; k < need.stackSize; k++) RemoveItem(need.data);，更好的是给容器一个 TryRemove(def, count)。另外这个函数还有三个设计问题值得一起说：名字叫 Can 却完成了合成（应拆成 CanCraft + Craft）；校验和扣除分两步，单线程下没问题，但联网后必须在服务器上作为一个事务执行；失败时只打日志，UI 拿不到“缺什么”。

10.5 E5：掉落概率与“最多 3 件”

for (int i = 0; i < possibleDrop.Length; i++) if (Random.Range(0, 100) <= possibleDrop[i].dropChance) // 0~99 的整数 <= 84.8 → 85 个值命中 dropList.Add(possibleDrop[i]); int itemsToDrop = Mathf.Min(PossibleItemDrop, dropList.Count); // 最多 3 件 for (int i = 0; i < itemsToDrop; i++) { int randomIndex = Random.Range(0, dropList.Count); // 无放回抽样 DropItem(dropList[randomIndex]); dropList.RemoveAt(randomIndex); } // DropItem：new Vector2(Random.Range(-5, 5), Random.Range(15, 20)) —— int 版，x ∈ {-5..4}

骷髅的 5 个候选掉率合计 261.7%，平均有 2.6 个通过筛选，经常超过 3 个而被截断。精确解（枚举 2⁵ 种筛选结果）与 100 万次蒙特卡洛 实测 E5：

  • 配置值不是实际掉率：策划在 Inspector 里看到 35.4%，实际 [[e5.Nice_Armor.final|.1f]]%。只要有“最多 N 件”，各物品就不再独立；要么文档写清“掉率 = 入选概率”，要么改成权重表一次抽 N 件。
  • 小数位无效：Random.Range(0,100) 是整数，84.8 和 84.0 效果相同（都是 85 个值）；dropChance 填 0 仍有 [[E5.zero]]% 掉率。
  • 掉落向左偏：x 初速度来自 int 版 Random.Range(-5, 5)，取值 −5~4，向左 [[E5.vneg]]%、向右 [[E5.vpos]]%、0 占 [[E5.vzero]]%，均值 [[E5.vmean]] m/s——掉落物整体偏左。应写 Random.Range(-5f, 5f)。
  • 其他：item 字段序列化了却没用；每次掉落 Debug.Log(_itemData)；ItemObject 每帧检查 M 键（调试代码遗留，每个掉落物一份）。

10.6 改进：定义 / 实例 / 容器 / 事务

public bool TryCraft(Recipe r, Container stash, Container bag) { foreach (var need in r.inputs) // 1. 只读校验（含成品是否放得下） if (stash.Count(need.defId) < need.count) return false; if (!bag.CanAdd(r.output, 1)) return false; foreach (var need in r.inputs) // 2. 提交：已校验过，不会半途失败 stash.Remove(need.defId, need.count); bag.Add(ItemInstance.Create(r.output, 1)); Events.Raise(new Crafted(r.id)); // 3. 通知（UI、任务、成就） return true; }

10.7 面试追问

背包用什么数据结构？（Q10-1） ├─ 为什么 List + Dictionary？删除的复杂度？（Q10-1 L2） ├─ 一把“+5 的剑”和一把“+0 的剑”怎么区分？（Q10-2 → 定义 vs 实例） ├─ 合成怎么保证不出错？联网后在哪做？（Q10-3 → E6） ├─ 掉落概率怎么做？策划配 35% 实际是多少？（Q10-4 → E5） └─ 背包怎么存档？改了物品表旧存档怎么办？（场景 10-3）
Q10-1　背包用什么数据结构？

L2　List 保持显示顺序，Dictionary 以物品定义为键找到对应堆叠，加物品时 O(1) 判断是否已有堆叠；删除时字典 O(1)、List.Remove O(n)。三个容器（背包、仓库、装备栏）各一套。

L3　如果背包是“格子制”（物品放在固定格子里、允许空洞），更自然的结构是定长数组 slots[capacity] + “defId → 格子下标集合”的索引；堆叠满了要找下一个同类格子或空格子。我项目里没有容量规则，UI 只有 4 格，物品种类超过 4 就会越界——现在只有 3 种装备，所以没触发。

Q10-2　“+5 的剑”和“+0 的剑”怎么区分？

L2　现在区分不了：字典以 ScriptableObject 定义为键，同一定义的物品会被合并成一个堆叠。要支持实例数据，必须引入 ItemInstance（唯一 id + 定义 id + 实例属性），可堆叠的材料按定义合并，不可堆叠的装备每件一个实例。

L3　实例数据还决定了装备修正的来源：修正器挂“装备实例”，强化等级变化时重算该实例的修正；存档存实例列表。

Q10-3　合成怎么保证不出错？

L2　先只读校验全部条件（材料数量、成品放不放得下），再一次性提交；提交阶段不应该有可能失败的步骤。我原来的代码校验是对的，但提交时每种材料只 RemoveItem 一次，需要 2 张皮只扣 1 张，测出来 10 皮 10 铁能做 [[e6.10_10.bc]] 件而不是 [[e6.10_10.fc]] 件。

L3　联网后合成必须在服务器执行：客户端只发“合成配方 X”，服务器按自己的背包数据做事务并回包；客户端可以预表现（先播特效）但背包以服务器为准。重复请求要用请求 id 去重，防止网络重发造成双扣或双得。

Q10-4　掉落概率怎么做？

L2　我的做法是每个候选独立判定，再从入选的里无放回抽最多 3 个。测出来两个偏差：判定用 <= 比较 0~99 的整数，每件多 1%，掉率填 0 也会掉；“最多 3 件”的截断又让每件实际掉率比配置低 3~5 个点，比如 Nice_Armor 配 35.4% 实际 [[e5.Nice_Armor.final|.1f]]%。

L3　按需求选模型：独立掉落（每件按概率，不设上限）、权重表（一次抽 N 件，概率 = 权重 / 总权重）、分组（先抽品质再抽物品）、保底（连续 K 次未出就必出，计数存在玩家身上）。权威端（服务器）抽取，客户端只表现。

常见错误回答

错误：“背包用 Dictionary 存，查找 O(1)，性能最好。”

问题：只回答了查找。面试官真正想听的是堆叠规则、实例数据、容量与格子、事务、存档和联网校验。

更好的回答：从“定义 / 实例 / 容器 / 事务”四层回答，再用自己项目的 bug 举例说明为什么需要每一层。

10.8 发散场景题

场景 10-1　设计一个 MMO 背包：200 格、可堆叠、可拆分、可整理、可交易。

为什么会问：最常见的客户端系统设计题之一。

数据：slots[200] 存 ItemInstance 引用（或 uid），索引 defId → 格子集合；操作：Add（先填同类未满堆叠再找空格）、Split（从堆叠拆出 n 个到空格）、Merge、Move / Swap、Sort（按规则排序后重排，注意稳定排序与锁定格子）；交易：物品在交易期间被“锁定”，服务器以交易单为事务原子交换。客户端：所有操作发请求，服务器回包后应用（可做乐观预表现 + 回滚）；UI 用虚拟列表只渲染可见格子（场景 10-4）。

场景 10-2　有人用加速器 / 改包刷合成材料，你在客户端能做什么？

为什么会问：防刷的边界意识。

客户端几乎做不了“防”，只能“不信任”：所有产出（掉落、合成、拾取）由服务器决定；客户端提交的只是意图。能做的是减小攻击面（不在客户端计算掉落、不在本地存可修改的权威数据）、上报异常（短时间大量请求）、协议加签和重放保护。项目里掉落在本地随机、合成在本地扣料，联网化时这两处都必须搬到服务器。

场景 10-3　物品表改版（删了一个物品、改了堆叠上限），旧存档怎么办？

为什么会问：存档兼容是线上事故高发区。

存档里存稳定的 defId（GUID 或数字 id，不能存数组下标或资源路径）；存档带版本号，加载时按版本逐级迁移（删除的物品转换成补偿货币、堆叠超上限的拆成多格）；ScriptableObject 引用在存档里要转换成 id，不能直接序列化对象引用。项目里背包以 ScriptableObject 引用为键，直接序列化的话换个资源 GUID 就全丢。

场景 10-4　背包 1000 格，打开界面卡 200 ms，怎么优化？

为什么会问：UI 性能的经典题。

① 虚拟列表 / 循环滚动：只实例化可见的 30~40 个格子，滚动时复用并重新绑定数据；② 增量刷新：容器发 SlotChanged(i)，只更新变化的格子，而不是像项目这样全量 CleanUp + Update；③ 图标异步加载、图集合批；④ 把背包 Canvas 与常驻 HUD 分开，避免格子变化触发整张 Canvas 重建；⑤ 打开时分帧填充。

自测 1：为什么点空背包格的空引用“只出现在开局”？开局时格子的 item 是序列化器构造的默认实例（data 为 null），第一次 UpdateSlotUI 会对所有格子 CleanUpSlot，把 item 置为真正的 null，之后基类判空就能拦住。
自测 2：10 皮 10 铁时，为什么源码版最后剩 1 皮 1 铁？每件只扣 1 皮 1 铁，但校验要求皮 ≥ 2：做到第 9 件后剩 1 皮 1 铁，皮不满足 2，停止。
自测 3：怎样让“配置掉率 = 实际掉率”？去掉“最多 N 件”的截断，每件独立判定，并用 Random.value * 100 < chance；需要上限时改用权重表，并在文档里写清“概率 = 权重 / 总权重”。
