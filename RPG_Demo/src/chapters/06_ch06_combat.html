CHAPTER 06

战斗判定：攻击检测、受击反馈与弹反窗口

“攻击判定怎么做”“弹反怎么实现”“为什么会多段命中”——这一章把一次命中拆成检测、结算、反馈三步，指出项目里“反馈和结算分家”导致的两个怪现象：闪避了也闪白击退、弹反成功照样掉血；再把弹反窗口按帧算清楚。

本章目标
  • 说清 Hitbox / Hurtbox / LayerMask / 命中去重这四个概念，并对照项目里缺了哪些
  • 理解“表现先行、结算在后、二者不通气”带来的两个 bug
  • 用 E2 的数字讲清弹反成功窗口：本项目 [[e2.60.cw|.2f]] s、原教程写法 [[e2.60.ow|.2f]] s，以及为什么都偏宽
  • 给出 DamageInfo → HitResult 的伤害管线，把弹反、闪避、无敌帧、霸体放进同一个判定入口

6.1 30 秒面试版 · 现状 vs 理想

30 秒回答

攻击判定在动画的命中帧用 OverlapCircleAll 取攻击点周围的碰撞体，对其中的敌人先调 DamageEffect()（闪白 + 击退协程），再调 DoDamage()（闪避 → 暴击 → 护甲）。问题有三：查询没有 LayerMask、每次分配数组、同一目标多个碰撞体会重复命中；反馈和结算是两个互不知情的调用，所以闪避时照样闪白击退，弹反成功时伤害照样结算；击退方向用的是“受击者自己的朝向”，背后挨打会被打向攻击者。弹反的判定是“受击那一刻处于反击状态、且怪物正在出手窗口内”，实测按键成功窗口约 [[e2.60.cw|.2f]] s。改进是统一成一个伤害管线：攻击方构造 DamageInfo，受击方返回 HitResult（Evaded / Parried / Blocked / Hit），反馈根据结果播放。

6.2 检测：一个圆、没有过滤、没有去重

private Player player => GetComponentInParent(); // 属性：每次访问都向上查一次 private void AttackTrigger() { Collider2D[] colliders = Physics2D.OverlapCircleAll(player.attackCheck.position, player.attackCheckRadius); foreach (Collider2D collider in colliders) { Enemy enemy = collider.GetComponent(); if (enemy != null) { enemy.DamageEffect(); // ① 先播受击表现 player.stats.DoDamage(enemy.stats); // ② 再结算（可能被闪避） } } }
概念项目现状后果改法
Hitbox（攻击判定区）一个圆：attackCheck（本地 x 1.2）、半径 0.9；三段攻击共用三段攻击动作幅度不同却同一判定；空中 / 地面也同一判定判定形状随技能数据配置（圆 / 盒 / 扇形 + 偏移 + 持续帧）
Hurtbox（受击区）直接用物理胶囊体受击区与“推挤 / 站地面”的物理体绑死；想做“只打头”“蹲下躲刀”都做不了单独的 Trigger 碰撞体，放在 Hurtbox 层
LayerMask9 处 OverlapCircleAll 全都没传结果里混着地面 Tilemap、玩家自己的血条 Trigger（Queries Hit Triggers 开着）、掉落物触发器，每个都要 GetComponent 一次只查 Hurtbox 层；用 ContactFilter2D 统一配置
去重按碰撞体遍历一个敌人挂两个碰撞体就挨两刀（加头部判定、加盾牌碰撞体时立刻出现）本次攻击维护 HashSet<受击者>，按“实体”而不是“碰撞体”去重
分配每次 new 一个数组一刀一次 GC 分配；旋转剑冷却为 0 时每帧一次（第 12 章）NonAlloc / 带 List 结果的重载，复用缓冲

6.3 反馈与结算分家：两个怪现象

问题 P1 两个现象是同一个设计缺陷：“这次攻击的结果是什么”没有一个唯一的裁决点。表现层（闪白、击退、弹反）和数值层（闪避、伤害）各自判断，互不知道对方的结论。修法见 6.6 的伤害管线。

击退的两个细节

protected virtual IEnumerator HitKnockBack() { isKnocked = true; rb.velocity = new Vector2(knockBackDistance.x * -facinDir, knockBackDistance.y); // 方向 = 自己朝向的反方向 yield return new WaitForSeconds(knockBackDuration); isKnocked = false; } public void SetVelocity(float _xVelocity, float _yVeloctiy) { if (isKnocked) return; ... } // 击退期间状态改不了速度
  • 问题 P2 击退方向取决于受击者面朝哪边，而不是攻击来自哪边。骷髅背对玩家时被砍，会被击退到玩家怀里。应传入攻击者位置：dir = sign(victim.x − attacker.x)。
  • 推断 玩家的 knockBackDistance 是 (0, 0)、持续 0 s：每次受击都会把速度设成 (0, 0) 并锁住 SetVelocity 一帧——空中被打会瞬间失去上升 / 下落速度，表现为“顿一下再掉”。这可能被当成“受击硬直”接受了，但它是零值配置的副作用，而不是设计。
  • 多次受击会叠加多个 HitKnockBack 协程，最早结束的那个把 isKnocked 置假——和 isBusy、冻结一样的“重叠协程最早者赢”问题（第 7 章 E8 量化）。

6.4 弹反：判定逻辑与 E2 成功窗口

public override void DamageEffect() // Player：受击时先看是不是在反击 { if (stateMachine.currentState == counterAttack) { counterAttack.CounterAttack(); return; } base.DamageEffect(); } public void CounterAttack() // 以自己的攻击点找“正在出手”的敌人 { foreach (var c in Physics2D.OverlapCircleAll(player.attackCheck.position, player.attackCheckRadius)) if (c.GetComponent() is Enemy e && e.CanbeStunned()) { player.animator.SetBool("SuccessfulCounterAttack", true); stateTimer = 10; // 之后只能靠成功动画的事件退出 player.isSuccessfulCounterAttacking = true; } } public virtual bool CanbeStunned() // “查询”带副作用：关窗 + 子类里切到眩晕 { if (canBeStunned) { CloseCounterAttackWindow(); return true; } return false; }

作者把教程的写法（反击状态每帧检查“附近有没有正在开窗的敌人”，代码还以注释形式留在 Update 里）改成了“被打中的那一刻才检查”。两种写法的成功条件不同：

  • 本项目：骷髅的 AttackTrigger（0.4167 s）触发时，玩家仍处于反击状态。反击状态持续 1 s，所以 Q 必须在命中前 1 s 以内按下。
  • 原教程写法：反击状态的任意一帧 Update 里，骷髅的窗口开着（0.0833 s 开、0.4167 s 关）。反击状态与窗口有重叠即可。

用逐帧模型扫按键时刻 τ（相对骷髅进入攻击的那一帧，1 ms 步长，24 个子相位取公共部分）实测 E2 模型 R1~R3：

三点结论：

  1. 窗口宽度 ≈ 反击状态持续时间（1 s），而不是骷髅的“破绽”时长。把 counterAttackDuration 调短会同时缩短“摆架子等弹反”的时间，这才是真正控制难度的旋钮。
  2. 可以无脑预按：骷髅进入攻击前约 0.6 s 就按 Q，仍会成功。原写法更宽（只要求反击状态与 0.33 s 的窗口有重叠），提前 0.9 s 都行。
  3. 没有失败代价：Q 落空只是在原地站 1 s（反击状态每帧 SetVelocity(0,0)），没有硬直或冷却；配合第 2 点，弹反几乎是“看到骷髅靠近就按”。
别忘了 6.3 的情形 B

即使弹反成功，骷髅的 AttackTrigger 在调用 player.DamageEffect() 之后照样执行 enemy.stats.DoDamage(player.stats)。另外，弹反成功的判定还依赖第 4 章说的“同一时刻 AttackTrigger 排在 CloseCounterAttackWindow 之前”——这是一个只存在于 .anim 文件事件顺序里的契约。

6.5 无敌帧、霸体与多段命中

项目里没有任何“免疫”概念：冲刺没有无敌帧，受击后没有短暂无敌，攻击没有霸体。在只有一只骷髅、伤害为 0 的场景里看不出来；一旦多个敌人同时攻击，玩家会在同一帧被多次结算、被多个击退协程拉扯。动作游戏里通常这样组织：

机制实现方式放在哪里
闪避无敌帧冲刺的某一段给受击者挂 Invulnerable 标签技能时间轴的区间轨道（第 4 章）
受击后无敌被击中后 0.3~0.5 s 内对同类攻击免疫（常见于平台跳跃）受击方的状态 / 修正器
霸体 / 削韧受击只扣血不打断；韧性值归零才进入硬直受击方的“打断等级”（第 3 章的 InterruptLevel）
同一攻击不重复命中每个攻击实例一个 HashSet<受击者>攻击方的命中记录
多段攻击每段一个命中组，组内去重、组间不去重；或按间隔重置记录技能数据（命中次数上限、间隔）

6.6 改进：一个裁决点的伤害管线

public struct DamageInfo { public Entity source; public Vector2 origin; // 击退方向 = sign(victim.x - origin.x) public int physical, fire, ice, lightning; public bool parryable; public int hitGroup; // 同组只命中一次 } public enum HitResult { Hit, Evaded, Parried, Blocked, Immune } public interface IDamageable { HitResult Receive(in DamageInfo info); } // 受击方（玩家）：所有“这次算不算”的判断都在这里，按优先级 public HitResult Receive(in DamageInfo info) { if (tags.Has(Tag.Invulnerable)) return HitResult.Immune; if (info.parryable && parry.IsPerfect(Time.time)) { info.source.OnParried(); return HitResult.Parried; } if (stats.RollEvade()) return HitResult.Evaded; stats.Apply(info); // 暴击、护甲、元素、异常状态 fx.PlayHit(info.origin); // 反馈在结论之后 return HitResult.Hit; }

“完美弹反”的窗口 parry.IsPerfect 应该从按下的时刻算起（例如按下后 0.15 s 内），而不是“整个反击状态”；超过完美窗口但仍在架势中可以算格挡（减伤、扣耐力），落空则进入 0.3 s 的收招硬直——这三个参数就是弹反手感的全部旋钮。

6.7 面试追问

攻击判定怎么做的？（Q6-1） ├─ 为什么用 Overlap 不用碰撞回调 OnTriggerEnter？（Q6-2） ├─ 一刀会不会打中同一个敌人两次？（Q6-3 去重） ├─ 弹反怎么实现？窗口多宽？（Q6-4 → E2） │ └─ 弹反成功为什么还掉血？（Q6-5 → 6.3 情形 B） ├─ 闪避 / 无敌帧 / 霸体怎么做？（Q6-6 → 6.5） └─ 打击感怎么做？（Q6-7）
Q6-1 → Q6-2　攻击判定怎么做？为什么用 Overlap 不用 OnTriggerEnter？

L2　在动画命中帧做一次 OverlapCircle 查询，是“瞬时判定”：在哪一帧判、判多大范围完全由逻辑控制，结果立刻可用。OnTriggerEnter 是“持续判定”：需要一个跟随武器的触发器，回调在物理步之后发生，进入后不会再次触发（同一敌人站在里面不会被第二段攻击命中），而且时机受物理步与帧的对齐影响。近战挥砍多用瞬时查询，投射物多用触发器——项目里飞剑正是用 OnTriggerEnter2D。

L3　无论哪种都要做三件事：只查 Hurtbox 层、按实体去重、结果交给唯一的裁决点。我项目里三件都没做全。

Q6-3　一刀会不会打中同一个敌人两次？

L2　按碰撞体遍历就会：敌人有身体和头两个碰撞体，就会被结算两次。我的骷髅现在只有一个胶囊体所以没出现；正确做法是取 collider.attachedRigidbody 或向上找实体组件，放进本次攻击的 HashSet 去重。

L3　多段攻击（旋转剑）是另一回事：需要“同一目标间隔 x 秒才能再次命中”，记录表要带时间戳；我项目里旋转剑的间隔是全局的 hitTimer，对所有目标同时生效，而且冷却在场景里配成了 0。

Q6-4 → Q6-5　弹反怎么实现？窗口多宽？为什么成功了还掉血？

L1　怪物出手前用动画事件开“可被弹反”窗口；玩家按 Q 进入 1 s 的反击架势；被打中时如果在架势里、且怪物窗口开着，就眩晕怪物。

L2　我用逐帧模型算过：成功的按键时刻是命中前约 1 s 到命中帧，宽 [[e2.60.cw|.2f]] s；教程原来的“每帧检查重叠”写法更宽，[[e2.60.ow|.2f]] s。两者都允许在怪物抬手前就按好等着，所以难度很低。

L3　成功还掉血，是因为怪物的命中事件先调玩家的 DamageEffect（这里完成了弹反），再调 DoDamage——两次调用互不知道结果。我会把它改成一个 Receive 返回 HitResult，Parried 时不结算伤害，并把“完美窗口”改成从按键时刻起算的 0.15 s。

L4 · 攻击　“1 s 的窗口是你故意设计的吗？”→ 不是，它是反击状态持续时间的副产品；我确认之后才意识到真正的难度旋钮在 counterAttackDuration 上。这也是我后来坚持“先量化再调参”的原因。

Q6-7　打击感怎么做？

L2　按时间顺序叠加：命中瞬间顿帧 50~100 ms（攻击方和受击方动画减速）、受击闪白（项目有）、击退 / 浮空（项目有但方向有误）、镜头震动（Cinemachine Impulse）、命中特效与音效、伤害数字、手柄震动。关键是“同一帧开始”且“顿帧期间其他反馈不停”。

L3　顿帧会和冻结、减速抢写 animator.speed（第 7 章），所以要先有速度修正器栈；镜头震动和顿帧要用不受 timeScale 影响的时间。

常见错误回答

错误：“弹反就是在怪物攻击的时候按键。”

问题：没有回答“按键和命中的时间关系”，也没有区分“架势持续时间”和“完美窗口”。

更好的回答：“弹反由三个参数决定：完美窗口（从按键起算多久内被打中算完美）、架势持续时间（之后算格挡或落空）、落空惩罚（收招硬直）。我的项目里只有第二个，所以窗口宽达 1 s；改进是把完美窗口单独做出来。”

6.8 发散场景题

场景 6-1　同一帧里玩家和骷髅互相砍中，谁先结算？

为什么会问：同帧事件顺序是实时战斗的经典难题。

现状：两边的命中都在各自 Animator 的事件里，执行顺序取决于 Animator 的更新顺序，不确定；先结算的一方可能把对方打死（骷髅死亡后关碰撞体），后结算的就落空。设计上要明确规则：① 同帧互相命中都生效（“相杀”）；② 按优先级（弹反 > 攻击）；③ 按攻击发起时间。实现上把命中“收集”到本帧的队列，帧末统一按规则结算，而不是在回调里立刻扣血。

场景 6-2　一刀砍中 20 个小怪，帧率掉了，怎么办？

为什么会问：考察战斗峰值的性能意识。

热点：OverlapCircleAll 分配、每个碰撞体 GetComponent、每个受击者启动两个协程（闪白、击退）+ 改材质、伤害数字 UI 实例化。优化：NonAlloc + 层过滤、受击者组件缓存在 Hurtbox 上、受击表现用 MaterialPropertyBlock 和统一的计时器而不是协程、飘字对象池并合批、超过 N 个受击者时只对最近的 K 个播放完整表现。

场景 6-3　改成联机（状态同步），近战命中在哪里判定？

为什么会问：从单机判定发散到网络。

服务器权威判定；客户端为了手感先播放挥刀和命中特效（预表现），但伤害数字和受击硬直等服务器结果。高延迟下“我看到砍中了却没伤害”的矛盾用延迟补偿缓解：服务器把受击者回溯到攻击者看到的时刻再做 Overlap。弹反这种“受击方按键”的机制更难：受击方的按键要发到服务器，服务器以“它看到的攻击时间”判定，窗口需要考虑 RTT——这也是很多联机动作游戏把弹反做成“预判架势”而不是“精确时机”的原因。

场景 6-4　策划要“背刺双倍伤害”，你会怎么加？

为什么会问：检验伤害管线是否可扩展。

在 DamageInfo 里已经有 origin，受击方 Receive 里根据 origin 与自身朝向判断是否背后，乘以修正系数——一处修改。现状下要同时改 DoDamage（数值）和 DamageEffect（表现），而且击退方向本身就是按朝向算的，背刺时还会被打向攻击者。

  • 反馈与结算分家 → 闪避也闪白击退、弹反成功仍掉血（#5）；击退方向用了受击者朝向（#26）。
  • E2：本项目弹反成功窗口 [[e2.60.cw|.2f]] s（命中前 ~1 s 到命中帧），原写法 [[e2.60.ow|.2f]] s；都能“预按”。

自测 1：为什么 30 fps 下最晚按键时刻（[[e2.30.chi|.3f]] s）比事件时间 0.4167 s 还晚？命中事件在“片段时间首次 ≥ 0.4167 s”的那帧触发（R2），30 fps 下这一帧是 0.433 s；只要按键在这一帧的 Update 之前发生就会被读到（R3），玩家在同一帧里先进入反击状态、动画阶段再挨打，所以仍然成功。
自测 2：CanbeStunned 有哪些副作用？基类里关闭弹反窗口并隐藏提示图标；骷髅子类里还会直接把骷髅切到眩晕状态。名字像查询，实际是命令。
自测 3：只把 DamageEffect 和 DoDamage 的调用顺序对调能修好闪避闪白吗？不能。DoDamage 没有返回值，调用方仍然不知道是否闪避；必须让结算返回结果，再据此决定表现。
