CHAPTER 12

性能、GC 与工程化：热点地图与两周重构路线

“你的项目有哪些性能问题？怎么定位？”“如果给你两周重构，你先做什么？”——这一章把前 11 章散落的性能与工程问题汇总成一张热点地图，再给出按风险排序的重构路线，最后讲对象池、程序集、版本管理这些“项目之外”的工程素养。

本章目标
  • 能报出项目里每一类热点 API 的调用次数、位置和替代方案
  • 说清 Unity 里哪些写法会产生 GC 分配，以及用 Profiler 验证的步骤
  • 设计一个不会踩“复用后状态没重置 / 旧引用指向新对象”的对象池
  • 给出两周重构计划：先修 P0、再修数值与状态、最后做结构性重构

12.1 30 秒面试版 · 现状 vs 理想

30 秒回答

规模小，帧率没问题，但写法里有会随规模放大的热点：9 处 OverlapCircleAll 每次分配数组且不过滤层；骷髅战斗时因自转移每秒 [[E7.A.fps|.0f]] 次 GameObject.Find；分身、飞剑、雷击、掉落物都是 Instantiate / Destroy；19 处按字符串反射调用（协程、Invoke）；8 处 Debug.Log 留在游戏逻辑里（冷却失败每次按键都打）；瞄准时每帧 50 次屏幕转世界坐标。工程上运行时代码引用了 UnityEditor（打包失败），.gitignore 的写法让 Logs 和 UserSettings 进了仓库。重构顺序：先修打包与 P0 逻辑，再修数值和状态守卫，最后做输入层、伤害管线、Buff、物品实例和对象池这些结构性改动，并配上纯逻辑单元测试。

12.3 Unity 里哪些写法会分配（扩展）

来源例子项目里有没有
返回数组的引擎 APIOverlapCircleAll、GetComponentsInChildren、Mesh.vertices有（9 处 Overlap；Inventory.Start 里 GetComponentsInChildren 只调一次，可以接受）
字符串拼接、ToString()、格式化有：Debug.Log 拼接、itemText.text = stackSize.ToString()、gameObject.name = "Item object - " + …
new 引用类型new List、new WaitForSeconds有：DoMagicalDamage 每次 new List、CanCraft 每次 new List、每次命中 new WaitForSeconds
闭包捕获lambda 捕获局部变量 / thisDoMagicalDamage 的两个 lambda 不捕获，编译器会缓存委托，不分配
装箱值类型转 object、枚举作 Dictionary 键（旧 Mono）Dictionary 以 ScriptableObject 为键，不涉及装箱
协程每次 StartCoroutine 生成一个迭代器对象有：每次受击 2 个

验证步骤：Profiler → CPU 模块打开 GC Alloc 列，按帧找分配峰值 → 开 Deep Profile 或加 Profiler.BeginSample 定位到函数 → 修复后用同一段录制对比。项目的 Player Settings 里 gcIncremental = 1（增量 GC 已开启），单次停顿被摊到多帧，但分配总量不变；移动端更要关注总量和频率。

12.4 对象池：三个必须处理的坑

对照项目：飞剑有 Invoke("DestroyMe", 7)——池化后必须在归还时 CancelInvoke，否则一把被复用的新剑会在 7 秒后被旧的 Invoke 归还；player.sword 是裸引用，剑被归还又被别人取出后，玩家按右键会召回“别人的剑”。这正是“句柄 + 代数（generation）”要解决的问题：持有方保存 (id, gen)，访问前比较当前代数，不一致即视为已失效。

12.6 两周重构路线

面试里怎么讲重构

不要说“我会全部重写”。说“我会按风险排序：先保证能打包、不崩溃（1 天），再保证逻辑正确（3 天，每个修复配一个测试），再保证帧率无关（1 天），最后才做结构性重构（5 天），每一步都可以单独上线”。面试官要听的是排序的理由和回归的手段。

12.7 面试追问

项目有哪些性能问题？（Q12-1） ├─ 你怎么定位的？用了什么工具？（Q12-2） ├─ OverlapCircleAll 为什么不好？NonAlloc 有什么坑？（Q12-3） ├─ 对象池怎么设计？复用后出过什么问题？（Q12-4 → 12.4） ├─ Debug.Log 打包后还会执行吗？（Q12-5） └─ 给你两周你先做什么？（Q12-6 → 12.6）
Q12-1 → Q12-2　项目有哪些性能问题？怎么定位？

L2　按“频率 × 单次成本”排序：每帧发生的（骷髅自转移带来的 Find、瞄准时 50 次坐标转换）优先于每次命中发生的（Overlap 数组分配、两个协程），再优先于偶发的（冲刺时实例化分身）。定位用 Profiler：CPU 时间线找最贵的帧、GC Alloc 列找分配、Deep Profile 下钻；内存用 Memory Profiler 看材质实例（sr.material 克隆）和泄漏的对象。

L3　我会先确认问题是否真实：一只骷髅每秒 25 次 Find 在 PC 上测不出差异，但它的成本和场景对象数、怪物数成正比，所以我把它定性为“结构问题顺带的性能隐患”，而不是“性能瓶颈”。

Q12-3　OverlapCircleAll 为什么不好？NonAlloc 有什么坑？

L2　每次返回新数组，频繁调用产生 GC；不传 LayerMask 时结果包含所有碰撞体（项目开了 Queries Hit Triggers，触发器也算）。NonAlloc 版本要预分配缓冲区，缓冲区满了会静默截断，结果数量要看返回值而不是数组长度，缓冲区里还残留着上次的引用。较新的版本推荐带 ContactFilter2D 和 List 结果的重载，List 会自动扩容。

Q12-5　Debug.Log 打包后还会执行吗？

L2　会。Release 包里 Debug.Log 仍然执行：参数字符串照样拼接、照样采集堆栈（可在 Player Settings 里把 Stack Trace 设为 None 降低成本），只是没有编辑器 Console 显示。项目里冷却中每按一次冲刺就拼接一次字符串。做法是封装一个带 [System.Diagnostics.Conditional("UNITY_EDITOR")] 或自定义宏的日志函数，调用点连同参数表达式一起在发布构建中被编译器移除。

常见错误回答

错误：“GetComponent 很慢，所以我把所有 GetComponent 都缓存了。”

问题：GetComponent 单次很快，真正的问题是“在循环、属性、每帧里重复调用”；不加区分的“全部缓存”也会带来生命周期问题（缓存了被销毁的组件）。

更好的回答：“我用 Profiler 找到热点里的重复查找，把它们挪到 Awake 缓存，或者让 Hurtbox 直接持有实体引用；不在热点里的就保持原样。”

12.8 发散场景题

场景 12-1　移动端玩 10 分钟后发热降频，帧率从 60 掉到 40，你怎么排查？

为什么会问：移动端性能是客户端岗的硬技能。

先区分 CPU / GPU / 热：Profiler（连真机）看主线程、渲染线程、GPU 时间；看是否“逐渐变慢”（泄漏：对象数、内存、协程数持续增长——本项目的骷髅尸体不回收、材质实例不释放都属于这一类）还是“一直很重”。CPU 侧查 GC 频率与分配峰值、物理查询数量、动画数量；GPU 侧查 Overdraw（2D 透明叠层多）、分辨率、后处理。降频应对：限帧 30 / 动态分辨率 / 降低特效 LOD。

场景 12-2　QA 报告“玩一小时后内存涨了 300 MB”，怎么定位？

为什么会问：内存泄漏是线上高频问题。

用 Memory Profiler 在两个时间点各抓一次快照做 Diff：看哪类对象数量增长（GameObject、Material、Texture、托管对象）。项目里可疑点：每个角色 sr.material 克隆的材质（对象销毁后不释放）、不销毁的尸体、静态委托或单例持有已销毁对象的回调、Debug.Log 的日志缓冲。托管侧看谁持有引用链（静态字段 → 事件 → 对象）。

场景 12-3　新人提交了一行 using UnityEditor，第二天出包失败，如何从流程上避免？

为什么会问：工程化与团队协作。

① asmdef：运行时程序集不引用编辑器程序集，编辑器里就会编译报错；② 提交前钩子 / CI：每次提交跑一次脚本编译（可用 batchmode 只编译不打包），每日跑真打包；③ 代码评审清单加一条“Editor 代码放 Editor 目录”；④ IDE 设置关闭自动 using 补全的部分命名空间。

本章速记
  • 热点：Overlap 9 · GetComponent 59 · Find 2 · Instantiate/Destroy 5/11 · 字符串反射 19 · Debug.Log 8；按“频率 × 单次成本”排序。
  • 分配来源：返回数组的 API、字符串、new 引用类型、协程；用 Profiler 的 GC Alloc 验证，不报没测过的数。
  • 对象池三坑：状态没重置、旧引用指向新对象（用代数句柄）、残留 Invoke / 协程。
  • 工程：UnityEditor using 打包失败（#1）、.gitignore 字符集写法（#35）、无 LFS、无测试。
  • 重构：先错后构——P0 → 逻辑 → 帧率 → 结构，每步配测试。
自测 1：/[Logs]/ 匹配什么？匹配根目录下名为单个字符 L、o、g 或 s 的目录（方括号是字符集）；想忽略 Logs 应写 /[Ll]ogs/。
自测 2：飞剑池化后，Invoke("DestroyMe", 7) 会带来什么问题？归还时若不 CancelInvoke，旧的 Invoke 会在 7 秒后作用于已经被复用的新剑，把它提前归还或销毁。
自测 3：为什么重构要先修“错”再改“结构”？结构性改动风险大，需要回归测试兜底；先修错误的过程正好产出这些测试用例，并且每个修复都能单独上线。
