“实测”的边界与四条模型规则

本机没有 Unity，C# 编译器被安全策略禁用，所以纯逻辑（状态转移、计时器、概率、合成扣料）逐行移植成 C++ 验证；依赖 Unity 运行时的部分写成模型规则，书里遇到时标 模型：

  • R1 帧顺序：FixedUpdate × N（含物理步）→ 所有 Update → 协程 WaitForSeconds 恢复 → 动画更新（触发动画事件）→ LateUpdate → 渲染。
  • R2 动画事件：进入状态那一帧记为片段 0 时刻；事件在“片段时间首次 ≥ 事件时间”那一帧的动画阶段触发。
  • R3 延迟：Destroy 在帧末生效；两帧之间的按键在下一帧的 Update 里被读到。
  • R4 精度：Time.deltaTime 与所有计时器都是 float，移植时同样用 float。

依赖 C# 运行时的结论（某次调用到底分配多少字节、协程对象的开销）只标 源码 或 扩展，不冒充实测——面试时说“我推断会分配，并在 Profiler 的 GC Alloc 列验证过”比报一个没测过的数字安全得多。

0.2 两条线：现状 vs 理想（全书读法）

这本书讲的每个功能都有两种状态，必须分开看：现状 是 Demo（commit 822270c）里真实存在的做法——包括它的问题，可以演示、能给出文件和行号；理想 是“如果重做 / 做成上线项目应该怎么做”的设计方案——它不在 Demo 里。两条线一旦混在一起，读者会把设计当成已实现，面试时也会把“我会怎么做”说成“我做过”。所以全书每讲一个功能，都按下图从左走到右。

读对照表的顺序：先看红列

每一行先读“当前做法”，再读“存在的问题”，最后看“理想方案”是不是正好解决了这个问题——如果理想方案解决的不是红列里写的问题，它就是过度设计。面试时也是这个顺序：“我当时这样做 → 后来发现它会导致……（证据）→ 所以正确做法是……”。缺陷（P0~P3）要讲证据，局限要讲“在什么条件下才会成为问题”，不要把局限说成 bug。

理想格的落地徽标含义面试时能说到什么程度
设计方案 · 未实现只是方案：Demo 里没有，本书也没写成可运行代码“如果重做，我会……”——讲思路和取舍，不报数字
模型验证：Ex / Fx把理想规则写进了 C++ 移植模型，和现状对拍过（实验里的“修正版 / 理想版”就是它）“我把修正规则放进移植模型对比过：现状 X，修正后 Y”——仍要说明是模型，不是 Unity 里改好的工程
保持 · 现状已正确现状就是对的，理想方案沿用可以当亮点主动讲（“这一处我是有意这样做的”）
公开参考理想参数来自公开资料（例如 Celeste 的强制离墙 0.16 s），不是本书测的注明出处：“参考了某游戏公开的数值”
理想不等于“全都要做”：分三档

同一个功能从现状走到理想，中间其实有三档：修正（在现有结构里只修错，例如冰冻破甲改成判断目标）→ 重构（改结构，例如属性改成带来源的修正器栈；这是“重做这个 Demo 就该做到”的理想）→ 上线级（规模化或联网才值得，例如服务器裁决、行为树、技能编辑器）。各章对照表的“理想重构方案”列以前两档为主，第三档出现在“代价”列和追问里。附录 D 用一张阶梯图把 12 个模块的四档并排画出来。

讲的时候用不同的时态

现状用过去时 + 证据：“我当时用一条腰部射线判墙，后来测到它在脚底上方 [[F1.wallH|.2f]] m，接近墙顶时会有一段死区”；理想用条件句 + 理由：“如果重做，我会用脚、腰两条射线按覆盖率判，因为……”。不要把理想说成做过——面试官追问一句“这个参数你在 Demo 里调的是多少？”就会露馅（口径见第 16 章 16.3 的三种时态）。

脚本执行顺序meta 里设置了 CharacterStats 300、UI_HealthBar 400、ItemData 500、ItemDrop 600（第 2 章会讲其中两个其实没起作用）

它的骨架来自一门流行的 Unity 2D RPG 教程（Entity → 状态机 → Skill → Stats → Inventory 的组织方式、命名和数值都高度一致），作者在此基础上做了自己的改动：弹反改成“受击时判定”、状态效果计时器重构成通用函数、魔法伤害改成“排序选最大元素”、掉落改成“先筛选再无放回抽样”。面试时主动说明来源，再重点讲“我改了什么、为什么改、改完发现了什么问题”——这比假装全部原创可信得多，也正是本书的组织方式。

0.4 项目介绍：一句话、一分钟、三分钟

一句话

“一个 Unity 2D 横版动作 RPG Demo：用有限状态机组织玩家和怪物行为，用动画事件驱动命中，做了冲刺分身、三段连招、弹反、可回收的飞剑技能，以及属性 / 异常状态 / 掉落 / 装备 / 合成这一套数值与物品系统。”

一分钟版（按“结构 → 亮点 → 反思”组织）

结构　所有角色继承 Entity（组件缓存、地面 / 墙检测、翻转、击退），行为由状态机驱动：玩家 13 个状态、骷髅 6 个状态，每个状态是一个普通 C# 类，Enter / Update / Exit 三段式，进入时把同名 Animator bool 置真。

亮点　命中、结束、掷剑这些关键帧都放在动画事件里，逻辑和美术对齐；弹反我改成了“受击瞬间若处于反击状态且怪物正在出手就眩晕它”；伤害走闪避 → 暴击 → 护甲三步，魔法伤害按最高元素施加点燃 / 冰冻 / 感电，感电二次命中会召唤追踪雷击。

反思　后来我用 C++ 把关键逻辑移植出来逐帧回放，发现了一批问题：状态转移缺守卫（死亡后还能冲刺“复活”）、怪物战斗状态每帧自己切换到自己、多个系统同时写移动速度、合成只扣一份材料。我知道怎么修，也知道这些问题在更大的项目里会变成什么。

三分钟版：在一分钟版基础上，每段多给一个“数字”

① 状态机：落地瞬间贴墙会在一帧内连续切两次状态（Fall→Idle→WallSlide，E1）；② 时间：冲刺在 Update 里计时、在 FixedUpdate 里位移，120 / 144 fps 下距离会在 4.5~5.0 m 之间跳，冲刺中卡一帧 250 ms 能冲出 [[e10.hitch.250.max|.1f]] m（E10）；③ 判定：弹反成功窗口实测 [[e2.60.cw|.2f]] s，比原教程写法的 [[e2.60.ow|.2f]] s 更严，但仍远宽于动作游戏常见的零点几秒，而且弹反成功时伤害照样结算（E2）；④ 数值：暴击判定用 <=，暴击率 0 也有 1% 暴击（E3）；⑤ AI：骷髅战斗时每秒执行约 [[E7.A.fps|.0f]] 次 GameObject.Find（E7）；⑥ 物品：合成 Nice_Armor 需要 2 张皮却只扣 1 张，10 皮 10 铁能做 [[e6.10_10.bc]] 件而不是 [[e6.10_10.fc]] 件（E6）。最后说重构方向：转移表 + 守卫、DamageInfo 管线、Modifier 栈、物品实例化、对象池。

面试官看不到 Demo

上面两个版本偏“复盘”；面向看不到 Demo 的面试官，第 16 章给出了讲出画面的口播稿、术语对齐表、把问题讲成“坑与正解”的转换表和方法论版的 1 分钟 / 3 分钟介绍，建议面试前以第 16 章为准。

介绍项目时最常见的三个坑

① 只报功能清单：“我做了冲刺、连招、弹反、背包……”——面试官听不到你的判断力。② 夸大：“我设计了一套完整的技能系统”——第一个追问“技能数据怎么配？”就会露馅（技能参数全在 MonoBehaviour 的序列化字段里）。③ 回避问题：被问到“有什么不足”只说“美术不好看”。更好的做法是主动抛出 1~2 个你测过的问题，把追问引到你准备好的地方（第 13 章专门练这个）。
