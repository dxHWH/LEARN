CHAPTER 05

问 ④：子弹同步与换弹

“子弹同步”其实是三件事：弹药数怎么同步、别人怎么看到你开枪、子弹（命中）怎么同步。换弹则是一个必须由服务器驱动的小状态机。

本章目标
  • 弹药的复制条件、预测与对账：为什么直接用 OnRep 覆盖会让 UI 回跳（E5）。
  • 逐节点复现原 Demo 的换弹 bug，并给出守恒的写法（E4）。
  • 换弹状态机：本机预测、服务器计时、别人看到动画、打断与取消。
30 秒版

弹药服务器权威，COND_OwnerOnly 只发给持枪者；本机预测扣弹，显示 = 服务器弹数 − 未确认发数，被拒的发数会自动纠正。别人看到开枪靠 COND_SkipOwner 的 BurstCounter，命中靠服务器的伤害结果复制。换弹：本机立刻播动画并预测状态 → ServerStartReload → 服务器校验后 bPendingReload=true（SkipOwner 给别人播动画）→ 计时器到点一次性 take = min(空位, 备弹) → 复位；期间开火被拒，切枪 / 死亡取消计时器且不改弹药。

原 Demo 的换弹：逐节点移植后跑一遍

把第 1 章的 Server_Change 与 剩余子弹计算 按节点一一翻译成 C++（包括“false 分支没有 Return 时返回 0”的蓝图语义），与修正版对比：

// 原蓝图 BP_Weapon.剩余子弹计算（#120~#187） int origRemain(Gun& g) { int need = g.maxMag - g.saved; if (g.total - need > 0) { g.total -= need; g.saved = g.maxMag; return g.saved; } // #123 Return g.saved = g.saved + g.total; g.total = 0; return 0; // 没经过 Return 节点：输出参数保持默认值 0 } // 原蓝图 BP_Weapon.Server_Change（#105） bool origReload(Gun& g) { if (!(g.total > 0) || g.maxMag == g.cur || g.reloading) return false; g.saved = g.cur; g.cur = 0; g.reloading = true; // 一开始就把弹匣清零 /* Multicast_Change + Delay(蒙太奇时长) */ g.reloading = false; g.cur = origRemain(g); return true; } // 修正版：一次性计算转移量，总数守恒 bool fixedReload(Gun& g) { if (g.total <= 0 || g.cur >= g.maxMag || g.reloading) return false; int take = std::min(g.maxMag - g.cur, g.total); g.cur += take; g.total -= take; return true; }
面试注意：这是逻辑 bug，不是网络 bug

被问到“换弹怎么实现”时，如果拿原 Demo 举例，要主动说出这一点：它在单机里也会发生，只是联机后 UI 本来就会跳，把它掩盖了。顺带还有两个设计问题：① 换弹一开始就把 当前子弹数量 置 0，换弹被打断（死亡）时子弹凭空消失；② 换弹中客户端仍可能发出 Server_Fire（它读的 正在换弹 是晚一个 RTT 的复制值），服务器先多播开火动画（bStopAllMontages = true）把换弹动画打断，然后才发现没子弹。

弹药怎么复制：条件、预测、对账

复制条件

原 Demo 的 5 个弹药变量全部无条件复制给所有人，但另一个玩家根本不需要知道你还剩几发。弹药只对持枪者有意义：COND_OwnerOnly。需要给别人看的只有“他在开枪”和“他在换弹”，分别用 COND_SkipOwner 的 BurstCounter 和 bPendingReload（拥有者自己已经本地预测过了）。

USTRUCT() struct FAmmoState { GENERATED_BODY() UPROPERTY() int16 InClip = 10; UPROPERTY() int16 Reserve = 30; UPROPERTY() uint16 AckSeq = 0; // 服务器已处理到的开火序号（接受或拒绝都会推进） }; UPROPERTY(ReplicatedUsing = OnRep_Ammo) FAmmoState Ammo; // 一个结构体：三者同一次到达，不会撕裂 UPROPERTY(ReplicatedUsing = OnRep_BurstCounter) uint8 BurstCounter; // 只增不减，OnRep 里看增量 UPROPERTY(ReplicatedUsing = OnRep_PendingReload) bool bPendingReload; void ACoopWeapon::GetLifetimeReplicatedProps(TArray& Out) const { Super::GetLifetimeReplicatedProps(Out); DOREPLIFETIME_CONDITION(ACoopWeapon, Ammo, COND_OwnerOnly); DOREPLIFETIME_CONDITION(ACoopWeapon, BurstCounter, COND_SkipOwner); DOREPLIFETIME_CONDITION(ACoopWeapon, bPendingReload, COND_SkipOwner); } int32 ACoopWeapon::GetDisplayedAmmo() const { // UI 和本机开火判断都用它 const uint16 Unacked = LocalShotSeq - Ammo.AckSeq; // uint16 回绕也正确 return FMath::Max(0, Ammo.InClip - (int32)Unacked); }

为什么不能让 OnRep 直接覆盖本地预测值

本机按下就扣一发（预测），但服务器的弹数要一个 RTT 后才回来，回来的是“服务器处理完某一发时”的值。如果 OnRep 直接 LocalAmmo = 服务器值，此时本机往往已经又多打了一两发，显示会先往回跳一下再继续减：

别人怎么看到你开枪：BurstCounter

另一端需要的不是弹数，而是“他又开了一枪”。复制属性只发最新值，所以不能用布尔 bFiring（同一网络帧里开两枪会被合并成一次），而是用一个只增不减的计数器：

void ACoopWeapon::OnRep_BurstCounter(uint8 OldValue) { const uint8 Shots = BurstCounter - OldValue; // 一个网络帧内可能有多发（uint8 回绕也正确） for (uint8 i = 0; i < FMath::Min(Shots, 3); ++i) PlayFireCosmetics(/*bFirstPerson*/ false); // 3P 蒙太奇、枪口火焰、声音、沿枪口方向画一条曳光 } // 晚加入的客户端第一次收到 BurstCounter 时 OldValue = 0，会误播几次： // 用 COND_SkipOwner + “首次复制不播放”（记录一个 bHasReceivedFirst 标志）即可。

ShooterGame 就是这么做的；Lyra 走 GAS，开火是一个 Gameplay Ability，表现用 Gameplay Cue 在各端播放。原 Demo 的 Multicast_Fire（Unreliable）也能达到“另一端看到”的效果，问题只在于它排在弹药检查之前，而且开火者自己也要等它。

换弹：服务器状态机 + 本机预测

void ACoopWeapon::StartReload() { // 本地输入（拥有者） if (!CanReloadLocal()) return; // 用显示值判断：备弹 > 0 且显示弹数 < 弹匣 bLocalReloading = true; PlayReloadCosmetics(/*bFirstPerson*/ true); // 立即播 1P 换弹蒙太奇，不等服务器 if (HasAuthority()) ServerStartReload_Implementation(); else ServerStartReload(); // Reliable } void ACoopWeapon::ServerStartReload_Implementation() { if (bPendingReload || Ammo.Reserve <= 0 || Ammo.InClip >= ClipSize || !IsOwnerAlive()) { ClientCancelReload(); // 被拒：通知本机停掉预测的动画（Reliable Client RPC） return; } bPendingReload = true; // SkipOwner 复制：另一端播 3P 动画 if (!IsOwnerLocallyControlled() && GetNetMode() == NM_ListenServer) PlayReloadCosmetics(false); GetWorldTimerManager().SetTimer(ReloadTimer, this, &ACoopWeapon::ReloadWeapon, ReloadDuration, false); } void ACoopWeapon::ReloadWeapon() { // 仅服务器，计时器到点 const int32 Take = FMath::Min(ClipSize - Ammo.InClip, Ammo.Reserve); Ammo.InClip += Take; Ammo.Reserve -= Take; // 总数守恒：InClip + Reserve 不变 bPendingReload = false; } void ACoopWeapon::CancelReload() { // 服务器：切枪、死亡时调用 if (!bPendingReload) return; GetWorldTimerManager().ClearTimer(ReloadTimer); // 弹药一发都不动 bPendingReload = false; ClientCancelReload(); } // 本机：OnRep_Ammo 到达时 bLocalReloading = false（服务器已经完成或拒绝）； // 换弹期间的开火在本地就被 IsReloadingLocal() 挡住，不会发出请求。
换弹时长用计时器还是蒙太奇里的 AnimNotify？

很多教程用蒙太奇的“弹匣插入”通知来加子弹。在服务器上这有两个风险：Dedicated Server 默认不刷新不可见网格的动画，通知可能不触发或延迟；蒙太奇被其他动作打断时通知也不会来。更稳妥的做法是服务器用数据配置的时长计时，动画只负责表现（蒙太奇时长按同一个数据缩放播放速率）；用 GAS 的话，就是 Ability 里 WaitDelay 或服务器端的 WaitGameplayEvent 加超时。原 Demo 用 Delay(GetPlayLength(蒙太奇)) 其实是对的思路，只是放在了 RPC 事件里，没有办法取消。

原实现 vs 正确实现

本章速记
  • 弹药：服务器权威、COND_OwnerOnly、结构体带 AckSeq；显示 = InClip − (LocalSeq − AckSeq)。
  • 别人看到开枪：COND_SkipOwner 的 BurstCounter，OnRep 看增量；主机看客户端开火要在服务器上手动播。
  • 换弹：本机预测动画 → ServerStartReload 校验 → bPendingReload（SkipOwner）→ 计时器到点一次性转移 → 复位；取消不动弹药。
  • E4：原蓝图在备弹不够补满时吞弹匣（3/7 → 0/0）；E5：直接覆盖会回跳，序号对账不会。
自测：为什么 BurstCounter 用 COND_SkipOwner，而弹药用 COND_OwnerOnly？ BurstCounter 是给“别人”播开火表现用的，开火者自己已经在本机预测播过了，再收到就会播两次，所以跳过拥有者。弹药只有持枪者需要看，发给别人既浪费带宽又泄露信息（PvP 里对手能知道你还剩几发），所以只发拥有者。
自测：用一个 bool bIsFiring 复制给别人，别人在 OnRep 里每次播一发，会有什么问题？ 复制属性只发最新值：服务器在一个网络帧里开了两枪（true→true）根本不会产生变化，别人一发都看不到；连射时 bIsFiring 一直是 true，也只会触发一次 OnRep。要表达“发生了几次”，必须用计数器，或者用 Unreliable Multicast 逐发通知。
