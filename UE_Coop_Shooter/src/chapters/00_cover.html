CHAPTER 00

先背这个：四道题的 30 秒面试版答案

面试官拿着简历上的这个 Demo 往下问，先用 30 秒给出“正确做法”的骨架，再主动说出原实现哪里不对、后来怎么改的——这比假装原实现没问题加分得多。

问 ①：从按下开火到击中僵尸，中间发生了什么？

当前做法原 Demo 没有射线检测：本机每 0.12 秒发一条 Server_Fire，服务器先组播开火动画、再查弹药，然后生成一颗复制的子弹 Actor；子弹在服务器和客户端各飞一份，撞到僵尸后在碰撞事件里调用 Apply Damage（客户端那次被引擎的 Authority Only 拦下，伤害实际只在服务器生效）。下面是重构后的做法。

存在的问题① 按下后约 {{v:E1[s=0,rtt=200].own:.0f}} ms 才看到自己开枪（表现等组播，E1）；② 组播排在弹药检查之前，打空也播，还会打断换弹动画；③ 远端看到子弹凭空出现在约 {{v:E1[s=0,rtt=200].pop:.1f}} m 外，每发一个复制 Actor（E7：约 {{v:E7.0.4}} vs {{v:E7.1.4}} B/s）；④ 伤害写在每一端都会触发的碰撞里、Instigator 为空——客户端没扣血只是被引擎拦下；⑤ 后坐力只对主机生效；⑥ 没有延迟补偿，横移僵尸命中率只有 {{v:E3[v=480,rtt=200].none:.1f}}%（E3）。

理想方案本机：Enhanced Input 触发武器的 StartFire；本地先检查本地记录的弹药和状态，立刻播开火动画、枪口火焰、声音，并预测扣一发（这些都是表现，不是结果）。然后把这一发的信息发给服务器：Server_FireShot(序号, 起点, 方向, 客户端时间, 命中目标)。

服务器：校验（活着、没在换弹、射速、弹药、起点和方向是否合理）→ 扣弹 → 做射线检测（PvP 要按客户端时间回溯目标，PvE 打僵尸可以放宽成“客户端判定 + 服务器容差校验”）→ 命中后 ApplyPointDamage，Instigator 填开火者的 Controller、DamageCauser 填武器。僵尸的 TakeDamage 只在服务器改血量；血量归零就进入死亡状态、停 AI、给开火者的 PlayerState 加分。

回到各端：弹药按 COND_OwnerOnly 复制回开火者，用序号对账，UI 不回跳；开火计数 BurstCounter 按 COND_SkipOwner 复制给另一端，让对方播开火表现；僵尸的血量 / 死亡标志通过 OnRep 让每一端播受击和倒地。本机感觉零延迟，另一端大约晚“半个 RTT + 一个网络帧”看到，伤害和死亡只以服务器为准。

问 ②：控制的角色、控制器、武器应该怎么绑定？

当前做法原 Demo 在角色 BeginPlay 里由服务器生成武器（生成时 Owner 为空，之后补 SetOwner），武器引用复制后挂到第一人称手臂上；角色只有手臂模型，输入映射用 0 号控制器添加，没有自定义 PlayerController / PlayerState。

存在的问题① 武器的 BeginPlay 早于 SetOwner，初始化拿不到持有者，只能靠 for_server 补丁；② 0 号控制器在服务器上永远是主机的——客户端玩家死亡时禁用输入传进去的是主机的控制器，不生效，死者仍能操作；③ 对方看到的是一双漂浮的手臂；④ 准备列表存的是 PC 引用，复制到客户端为空。

理想方案GameMode 在服务器为每个登录的 PlayerController 生成 Pawn 并 Possess；Possess 会把 Pawn 的 Owner 设成这个 PC。PC 只存在于服务器和它自己的客户端，所以 Owner 链“武器 → Pawn → PC → 网络连接”决定了：谁能在这个 Actor 上调用 Server RPC、COND_OwnerOnly 发给谁、Client RPC 去哪。

武器在服务器生成，生成参数里直接给 Owner = Pawn、Instigator = Pawn（不要先生成再 SetOwner，BeginPlay 会早于 SetOwner）；挂到第三人称模型的手部 Socket，另一份挂到只有自己看得见的第一人称手臂；CurrentWeapon 复制并在 OnRep 里做挂接和动画层切换。输入映射在“成为本地控制者”时添加（NotifyControllerChanged / PawnClientRestart），不要在 BeginPlay 里用 GetPlayerController(0)。分数、是否准备这类跟人走的数据放 PlayerState。

问 ③：弱网造成卡顿，应该怎么优化？

当前做法原 Demo 没有做任何弱网处理：开火、换弹的表现都等服务器组播回来；冲刺标志只在服务器生效，客户端持续被拉回；每发子弹一条 Reliable RPC 加一个复制 Actor；也没有延迟补偿。

存在的问题RTT 200 ms 时按下开火约 {{v:E1[s=0,rtt=200].own:.0f}} ms 才有反应（E1）；冲刺时每秒被纠正 {{v:E6[c=0,rtt=100].cps:.1f}} 次、平均拉回 {{v:E6[c=0,rtt=100].avg:.1f}} cm（RTT 100 ms，E6）；丢包 10% 时伤害请求 P99 延迟 {{v:E2[rtt=200,loss=0.1].p99:.0f}} ms（E2）；不补偿时横移僵尸命中率 {{v:E3[v=480,rtt=200].none:.1f}}%（E3）——而且这些在 PIE 零延迟下全都看不出来，原版从没在网络模拟下测过。

理想方案先测再改：PIE 打开网络模拟（100~200 ms、5~10% 丢包），用 stat net、p.NetShowCorrections 1、Networking Insights 判断是哪一类问题。

① 操作反馈慢 → 客户端预测：开火表现、弹药、换弹动画本地先播，服务器确认后对账；② 移动被拉回 → 所有影响移动速度的状态（冲刺、瞄准、下蹲）必须进 CharacterMovement 的 SavedMove 一起预测，不能另走 RPC，更不能两端各算各的（实测：冲刺只在服务器生效时每秒纠正 {{v:E6[c=0,rtt=100].cps:.1f}} 次）；③ 明明瞄准了却没打中 → 服务器按开火时刻回溯目标，或客户端判定 + 服务器容差（实测：目标 4.8 m/s、RTT 200 ms 时不补偿命中率只有 {{v:E3[v=480,rtt=200].none:.1f}}%）；④ 消息堆积、带宽高 → 逐发 Reliable 改为计数器 / 带序号的 Unreliable，表现类消息一律不用 Reliable，降低 NetUpdateFrequency、用休眠和相关性，抛射物用“假子弹”。远端角色靠插值平滑，服务器 Tick 和带宽上限按需要调整。

问 ④：子弹同步、换弹是怎么实现的？

当前做法原 Demo 的“子弹同步”就是复制子弹 Actor（每发一个，带移动复制），不是射线；5 个弹药变量无条件复制给所有人、只在服务器扣；换弹是“先清零 → 组播动画 → Delay → 计算”的一段脚本，计算函数漏连返回节点，备弹不够补满时吞掉整个弹匣。

存在的问题① 弹匣 3 / 备弹 7 时换弹，换完变 0 / 0，一局打空再换只能打出 {{v:E4.session.0.2}} / 40 发（E4）；② Delay 不可取消，换弹中途死亡，已清零的子弹就没了；③ 弹药只在服务器扣，UI 晚一个往返才变，本机按旧值判断还能不能打；④ 弹药广播给所有人；⑤ 换弹动画等组播，晚加入看不到对方在换弹。

理想方案弹药：服务器权威，COND_OwnerOnly 只复制给持枪者；本地预测扣弹，显示值 = 服务器弹数 − 还没被服务器确认的发数，避免 OnRep 把 UI 拉回去（实测：直接覆盖每次连射平均回跳 {{v:E5.1.rb:.0f}} 次，序号对账 {{v:E5.2.rb:.0f}} 次）。别人看到的子弹：命中扫描武器只同步“开了几枪 + 打在哪”，各端本地画曳光和弹孔；真抛射物由服务器权威生成并按射手延迟快进，开火者本地先放一颗不复制的假子弹，命中只认服务器那一颗；高射速不要每发生成一个复制 Actor（第 5B 章）。

换弹是服务器上的一个小状态机：Server_StartReload → 检查“备弹 > 0 且弹匣未满且不在换弹” → bPendingReload = true（SkipOwner 复制给别人播动画）→ 服务器计时器到点后一次性计算 take = min(弹匣空位, 备弹) 再加减 → 状态复位。换弹期间开火被拒；切枪或死亡要取消计时器且不改弹药。本机立即播换弹蒙太奇，不等服务器。

面试注意：这个 Demo 原来的实现，面试官最可能抓住的五处
  • 子弹是复制 Actor，结果写在每一端都会执行的地方：没有射线检测，子弹的 ReceiveHit 在服务器和每个客户端都会触发，里面直接 ApplyDamage、不填 Instigator——客户端那次只是被引擎的 Authority Only 拦下才没扣血；同样的写法下，僵尸死亡组播里的“补刷”就真的在每一端都执行了，客户端多出只有自己看得到的僵尸（第 1、4 章，K0）。
  • 开火表现要等服务器多播回来：按下后约一个 RTT 才看到枪口动画；多播还排在弹药检查之前，打空了也会“空放”动画（E1）。
  • 换弹会吞子弹：备弹不够补满时，“剩余子弹计算”函数的 false 分支没有连到返回节点，返回 0，弹匣被清空（E4：换弹前 3/7，换完 0/0）。
  • 冲刺 / 瞄准两端不一致：冲刺标志只在服务器、瞄准标志只在本机，MaxWalkSpeed 两端不同，持续被服务器拉回（E6）。
  • 大量“本地当全局”：GetPlayerController(0)、UI 里的倒计时、客户端的 SetGamePaused、OpenLevel 重开——单机写法在联机下全部会错到别人身上（第 9、13 章）。

面试时怎么介绍这个 Demo

推荐口径（约 1 分钟，完整版见口径篇 K1）

“这是我早期的一个 UE 5.5 纯蓝图 Demo：两个人在咖啡店地图里合作打僵尸，撑 3 分钟获胜。先做成单机，后来改成双人 Listen Server。当时对 UE 网络不熟，基本是‘哪里不同步就补一个 Multicast’，结果出现了开火延迟、伤害在客户端被重复结算、换弹吞子弹、冲刺被拉回这些问题。后来我系统复盘了一遍：把蓝图逐节点读出来定位问题，归纳成几类根因；按服务器权威 + 本机预测 + 状态复制重新设计——开火本机先演、服务器校验、计数器复制，换弹做成服务器状态机，冲刺放进 CharacterMovement 的移动预测；关键结论在 200 ms / 10% 丢包的网络模型实验里做了对比。”

要点：先给画面、再承认问题、再讲原理、最后给数据；并且按时态说话——原版是“做过的”，复盘和模型实验是“验证过的”，重构是“设计的”（已经在引擎里做完的部分才说“做了”）。面试官看不到这个 Demo，他想考的是你能不能看出问题，而不是 Demo 本身做得多完整。

关于证据等级与实测

书中用三种标签区分说的是哪一套：当前做法原 Demo 真实的实现；最小修复保留原结构只改错误；存在的问题当前做法的问题，A# 指附录 A 的问题编号；理想方案重构设计（第三部分的全部图表）。对照总表见 K0。

再用三种标签区分可信度：源码事实蓝图里确实这么连的；推断根据 UE 运行规则推出的运行时后果（没有在编辑器里实跑，附录 A 给出验证方法）；实测 Ex来自 demos/coop_net_demo.cpp 的离散事件模拟——它不跑 UE，而是按 UE 的默认参数（服务器网络 Tick 30 Hz、Reliable 有序重传、MAXPOSITIONERRORSQUARED=3 等）复现与本 Demo 相关的网络行为，用来比较方案的相对好坏，不代表某台机器上的绝对值。
