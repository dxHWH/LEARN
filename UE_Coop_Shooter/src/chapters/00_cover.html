CHAPTER 00

先背这个：四道题的 30 秒面试版答案

面试官拿着简历上的这个 Demo 往下问，先用 30 秒给出“正确做法”的骨架，再主动说出原实现哪里不对、后来怎么改的——这比假装原实现没问题加分得多。

问 ①：从按下开火到击中僵尸，中间发生了什么？

本机：Enhanced Input 触发武器的 StartFire；本地先检查本地记录的弹药和状态，立刻播开火动画、枪口火焰、声音，并预测扣一发（这些都是表现，不是结果）。然后把这一发的信息发给服务器：ServerFire(序号, 射线起点, 方向, 客户端时间)。

服务器：校验（活着、没在换弹、射速、弹药、起点和方向是否合理）→ 扣弹 → 做射线检测（PvP 要按客户端时间回溯目标，PvE 打僵尸可以放宽成“客户端判定 + 服务器容差校验”）→ 命中后 ApplyPointDamage，Instigator 填开火者的 Controller、DamageCauser 填武器。僵尸的 TakeDamage 只在服务器改血量；血量归零就进入死亡状态、停 AI、给开火者的 PlayerState 加分。

回到各端：弹药按 COND_OwnerOnly 复制回开火者，用序号对账，UI 不回跳；开火计数 BurstCounter 按 COND_SkipOwner 复制给另一端，让对方播开火表现；僵尸的血量 / 死亡标志通过 OnRep 让每一端播受击和倒地。本机感觉零延迟，另一端大约晚“半个 RTT + 一个网络帧”看到，伤害和死亡只以服务器为准。

问 ②：控制的角色、控制器、武器应该怎么绑定？

GameMode 在服务器为每个登录的 PlayerController 生成 Pawn 并 Possess；Possess 会把 Pawn 的 Owner 设成这个 PC。PC 只存在于服务器和它自己的客户端，所以 Owner 链“武器 → Pawn → PC → 网络连接”决定了：谁能在这个 Actor 上调用 Server RPC、COND_OwnerOnly 发给谁、Client RPC 去哪。

武器在服务器生成，生成参数里直接给 Owner = Pawn、Instigator = Pawn（不要先生成再 SetOwner，BeginPlay 会早于 SetOwner）；挂到第三人称模型的手部 Socket，另一份挂到只有自己看得见的第一人称手臂；CurrentWeapon 复制并在 OnRep 里做挂接和动画层切换。输入映射在“成为本地控制者”时添加（NotifyControllerChanged / PawnClientRestart），不要在 BeginPlay 里用 GetPlayerController(0)。分数、是否准备这类跟人走的数据放 PlayerState。

问 ③：弱网造成卡顿，应该怎么优化？

先测再改：PIE 打开网络模拟（100~200 ms、5~10% 丢包），用 stat net、p.NetShowCorrections 1、Networking Insights 判断是哪一类问题。

① 操作反馈慢 → 客户端预测：开火表现、弹药、换弹动画本地先播，服务器确认后对账；② 移动被拉回 → 所有影响移动速度的状态（冲刺、瞄准、下蹲）必须进 CharacterMovement 的 SavedMove 一起预测，不能另走 RPC，更不能两端各算各的（实测：冲刺只在服务器生效时每秒纠正 {{v:E6[c=0,rtt=100].cps:.1f}} 次）；③ 明明瞄准了却没打中 → 服务器按开火时刻回溯目标，或客户端判定 + 服务器容差（实测：目标 4.8 m/s、RTT 200 ms 时不补偿命中率只有 {{v:E3[v=480,rtt=200].none:.1f}}%）；④ 消息堆积、带宽高 → 逐发 Reliable 改为计数器 / 带序号的 Unreliable，表现类消息一律不用 Reliable，降低 NetUpdateFrequency、用休眠和相关性，抛射物用“假子弹”。远端角色靠插值平滑，服务器 Tick 和带宽上限按需要调整。

问 ④：子弹同步、换弹是怎么实现的？

弹药：服务器权威，COND_OwnerOnly 只复制给持枪者；本地预测扣弹，显示值 = 服务器弹数 − 还没被服务器确认的发数，避免 OnRep 把 UI 拉回去（实测：直接覆盖每次连射平均回跳 {{v:E5.1.rb:.0f}} 次，序号对账 {{v:E5.2.rb:.0f}} 次）。别人看到的子弹：命中扫描武器只同步“开了几枪 + 打在哪”，各端本地画曳光和弹孔；真抛射物由服务器权威生成，开火者本地先放一颗不复制的假子弹，不要每发生成一个复制 Actor。

换弹是服务器上的一个小状态机：ServerStartReload → 检查“备弹 > 0 且弹匣未满且不在换弹” → bPendingReload = true（SkipOwner 复制给别人播动画）→ 服务器计时器到点后一次性计算 take = min(弹匣空位, 备弹) 再加减 → 状态复位。换弹期间开火被拒；切枪或死亡要取消计时器且不改弹药。本机立即播换弹蒙太奇，不等服务器。

面试注意：这个 Demo 原来的实现，面试官最可能抓住的五处
  • 伤害在每一端都算了一遍：子弹是复制 Actor，它的 ReceiveHit 在服务器和每个客户端都会触发，里面直接 ApplyDamage，客户端会本地扣僵尸血、本地触发死亡（第 1、4 章）。
  • 开火表现要等服务器多播回来：按下后约一个 RTT 才看到枪口动画；多播还排在弹药检查之前，打空了也会“空放”动画（E1）。
  • 换弹会吞子弹：备弹不够补满时，“剩余子弹计算”函数的 false 分支没有连到返回节点，返回 0，弹匣被清空（E4：换弹前 3/7，换完 0/0）。
  • 冲刺 / 瞄准两端不一致：冲刺标志只在服务器、瞄准标志只在本机，MaxWalkSpeed 两端不同，持续被服务器拉回（E6）。
  • 大量“本地当全局”：GetPlayerController(0)、UI 里的倒计时、客户端的 SetGamePaused、OpenLevel 重开——单机写法在联机下全部会错到别人身上（第 9、13 章）。

面试时怎么介绍这个 Demo

推荐口径（约 1 分钟）

“这是我早期的一个 UE 5.5 蓝图 Demo，先做成单机打僵尸，后来改成双人 Listen Server 合作。当时对 UE 网络不熟，基本是‘哪里不同步就补一个 Multicast’，结果出现了开火延迟、伤害在客户端被重复计算、换弹吞子弹、冲刺被拉回这些问题。后来我把它系统复盘了一遍：明确了服务器权威和 Owner 链，开火改成客户端预测 + 服务器校验 + 计数器复制，换弹改成服务器状态机，冲刺放进 CharacterMovement 的预测里，并在 200 ms / 10% 丢包下做了对比测试。”

要点：先承认问题、再讲原理、最后给数据。面试官问“你的 Demo”时真正想考的是你能不能看出问题，而不是 Demo 本身做得多完整。

关于证据等级与实测

原工程：github.com/dxHWH/-demo，快照 commit d7e5c75，UE 5.5，纯蓝图（没有 Source 目录）。仓库里大量美术资产与逻辑无关，只拉取了 Content/Blueprints、Content/UI、主地图与 Config。蓝图用自写的解析脚本 tools/bpdump.py 从 .uasset 读出节点、引脚连线、RPC 标志和复制设置，导出在 audit/*.txt，书中节点编号（如 #150）都能在里面查到。

书中用三种标签区分可信度：源码事实蓝图里确实这么连的；推断根据 UE 运行规则推出的运行时后果（没有在编辑器里实跑，附录 A 给出验证方法）；实测 Ex来自 demos/coop_net_demo.cpp 的离散事件模拟——它不跑 UE，而是按 UE 的默认参数（服务器网络 Tick 30 Hz、Reliable 有序重传、MAXPOSITIONERRORSQUARED=3 等）复现与本 Demo 相关的网络行为，用来比较方案的相对好坏，不代表某台机器上的绝对值。
