CHAPTER 06

问 ③：弱网造成卡顿，应该怎么优化

“卡”有四种：按了没反应、走路被拉回、明明瞄准了打不中、消息堆积一起到。先用工具分清是哪一种，再对症下药。

本章目标
  • 会用 UE 自带工具复现弱网、定位问题类型。
  • 讲清 CharacterMovement 的预测与纠正，以及为什么冲刺必须进 SavedMove（E6）。
  • 讲清延迟补偿的两种做法和代价（E3），Reliable 的队头阻塞（E2），带宽优化手段（E7）。
当前做法
原 Demo 没有做任何弱网处理：开火、换弹的表现都等服务器组播；冲刺标志只在服务器（Server RPC）、开镜标志只在本机，两端每帧各算一个最大速度，客户端持续被纠正；每发子弹一条 Reliable RPC 加一个复制 Actor；没有延迟补偿——服务器的子弹沿客户端的瞄准方向飞，而客户端瞄的是晚到的僵尸画面（E3 “不补偿”一列）。
存在的问题
  1. P0冲刺只在服务器生效、开镜只在本机：RTT 100 ms 时冲刺每秒被纠正 {{v:E6[c=0,rtt=100].cps:.1f}} 次、平均拉回 {{v:E6[c=0,rtt=100].avg:.1f}} cm（A#5，E6）。
  2. P1开火反馈 ≈ RTT + 网络帧：RTT 200 ms 时约 {{v:E1[s=0,rtt=200].own:.0f}} ms（A#9，E1）。
  3. P1逐发 Reliable 排队：丢包 10% 时 P99 {{v:E2[rtt=200,loss=0.1].p99:.0f}} ms（A#11，E2）。
  4. P1每发一个复制 Actor：约 {{v:E7.0.4}} B/s（A#12，E7）。
  5. 没有延迟补偿：横移僵尸命中率 {{v:E3[v=480,rtt=200].none:.1f}}%（E3）。
  6. 从没在网络模拟下测过：上面这些在 PIE 零延迟、主机视角下全都看不出来。
理想方案
本章正文：先分类定位，再分别用本机预测 + 对账、移动预测、延迟补偿（PvE 客户端判定 + 容差 / PvP 回溯）、消息与带宽优化处理。
30 秒版

先复现、再定位：PIE 网络模拟 / NetEmulation.PktLag、PktLoss，配合 stat net、p.NetShowCorrections 1、Networking Insights。然后分四类处理：反馈慢→本机预测 + 服务器对账；被拉回→影响移动的状态全部进 CMC 的 SavedMove，两端用同一套输入算速度；打不中→服务器按开火时刻回溯目标，或客户端判定 + 服务器容差，限制最大回溯；堆积 / 带宽→表现不用 Reliable，事件用计数器，降低更新频率、用相关性和休眠、子弹不做复制 Actor。远端角色用插值平滑。

1. 按了没反应：预测（第 4、5 章回顾）

原 Demo 的开火、换弹、后坐力全部在服务器触发，本机等一个往返（E1：RTT 200 ms 时 {{v:E1[s=0,rtt=200].own:.0f}} ms）。改成本机预测后自己的延迟为 0；被服务器拒绝的操作用序号对账纠正。预测只适用于“错了能纠正、纠正代价小”的东西：开火表现、弹药数、换弹动画可以预测；击杀、掉落、分数不能预测（或只能做“未确认”的提示）。

2. 走路被拉回：CharacterMovement 的预测与纠正

CMC 的移动是 UE 自带的客户端预测：拥有者客户端每帧本地移动，把这一帧的输入（加速度、时间、少量标志位）存成一个 FSavedMove 并通过 ServerMove 发给服务器；服务器用同样的输入、自己的状态重新模拟一遍，误差超过 MAXPOSITIONERRORSQUARED（默认 3，即约 1.73 cm）就回一个 ClientAdjustPosition；客户端收到后回到服务器给的位置，再把之后还没确认的 SavedMove 重放一遍。

这套机制成立的前提是：两端用同样的输入能算出同样的结果。原 Demo 违反了它：

  • 冲刺：IA_Run 调用 Server_StartSprint，只在服务器把 IsRunning 设为 true，这个变量不复制，本机永远是 false——服务器按 500 算，本机按 150 算。
  • 瞄准：是否瞄准 只在本机的 AnimBP 上设置，服务器那份永远是 false——本机按 120 算，服务器按 150 算。
  • 两端都在 Tick 里用 FInterpTo(当前速度, 目标速度) 改 MaxWalkSpeed，结果还依赖各自的帧率。

“半修复”（本机也切换速度，同时发 Server RPC）在不丢包时看起来完全正常，所以很容易被当成正确答案；但 RPC 和移动包走的是不同的路径，一旦切换消息晚到，两端就有一段时间用不同的速度模拟（表 6-1：10% 丢包时每秒仍有 {{v:E6[c=2,rtt=200,loss=0.1].cps:.2f}} 次纠正）。正确做法是把冲刺标志放进 SavedMove，和这一帧的输入一起发给服务器，服务器在重放这一帧时用的就是同一个标志：

别人的角色和僵尸：模拟代理的平滑

模拟代理（SimulatedProxy）不预测，只接收服务器的位置并做平滑：CMC 默认 NetworkSmoothingMode = Exponential，网格从旧位置向新位置追赶，胶囊体直接到位。远端一顿一顿时先看两件事：该 Actor 的 NetUpdateFrequency 是否太低（10 只僵尸可以 10~20 Hz，玩家保持默认）、动画是否用复制下来的速度驱动（原 Demo 的 AnimBP 用 GetVelocity()，这是对的）。

3. 明明瞄准了却打不中：延迟补偿

客户端看到的别人 / 僵尸，是服务器“过去某一时刻”的位置再加上外推。开火请求到达服务器时，目标已经又走了半个 RTT。目标横移越快、延迟越大，服务器在“现在”做射线就越容易打空：

两种做法

服务器回溯（Server-Side Rewind）客户端判定 + 服务器校验（ShooterGame）
做法服务器每个网络帧记录目标的位置 / 碰撞体，收到开火时按“客户端看到的时刻”插值回去再射线客户端射线打中后上报 (目标, 命中点)；服务器检查目标包围盒扩大容差后是否包含命中点、视线是否被墙挡、方向是否合理
优点结果由服务器算，防作弊实现简单，开火者手感最好
代价每帧存历史（内存 + CPU）；要限制最大回溯时间；高延迟玩家的命中会让别人“躲到墙后还挨打”信任客户端，容差就是外挂的空间
适合PvP 竞技PvE 合作（本 Demo）：僵尸不会抱怨不公平

4. 消息堆积：Reliable 的队头阻塞

Reliable RPC 保证顺序：第 n 条丢了，第 n+1 条即使先到也要等第 n 条重传成功才执行。原 Demo 每 0.12 s 一条 Reliable 的 Server_Fire，丢包时会出现“卡一下然后几发一起打出去”：

面试注意：Reliable 的三条规则
  • 只给低频、必须到达的消息用：开始 / 停止开火、换弹、切枪、准备就绪、命中上报。
  • 表现类一律 Unreliable 或计数器：开火特效、受击特效、脚步声。原 Demo 的 Multicast 都是 Unreliable，这点是对的。
  • 不要每帧发 Reliable：可靠缓冲区被塞满时引擎会直接断开这个连接。Tick 里发 Reliable RPC 是面试必扣分项。

本章速记
  • 先复现再定位：NetEmulation + stat net + p.NetShowCorrections + Networking Insights。
  • 拉回的本质是两端模拟不一致：冲刺 / 瞄准进 SavedMove，GetMaxSpeed 统一算，不另发 RPC、不在 Tick 写 MaxWalkSpeed（E6：原方案每秒纠正 {{v:E6[c=0,rtt=100].cps:.1f}} 次 → 0）。
  • 打不中：服务器回溯（PvP，限最大回溯）或客户端判定 + 容差（PvE）（E3：480 cm/s、RTT 200 不补偿 {{v:E3[v=480,rtt=200].none:.0f}}% → 回溯 {{v:E3[v=480,rtt=200].rew:.0f}}%）。
  • Reliable 有序 → 丢包时队头阻塞（E2）；按“丢了怎么办”选 Reliable / Unreliable。
  • 带宽：不复制短命 Actor、复制条件、降频、休眠、相关性、量化。
自测：为什么“本机切换速度 + Server RPC 通知服务器”在 PIE 里测不出问题？ PIE 默认没有延迟和丢包，RPC 和移动包几乎同时到达，两端切换速度的时刻一致。开启网络模拟、尤其是丢包后，切换 RPC 会比移动包晚到（或先到），这段时间两端速度不同，服务器就会纠正。把标志放进 SavedMove 后，服务器重放每一帧时用的就是这一帧客户端的标志，时序天然一致。
自测：服务器回溯为什么要设上限？上限设多少合适？ 不设上限，高延迟（或故意制造延迟的）玩家能打中服务器上“很久以前”的位置，被打的人体验极差，也给了作弊空间；同时历史缓冲区要无限增长。常见取 150~250 ms，超过的部分不补偿（E3 里 RTT 300 ms 时回溯命中率掉回 {{v:E3[v=480,rtt=300].rew:.0f}}%），并在 UI 上提示网络差。
