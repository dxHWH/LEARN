CHAPTER 16

64 道面试追问与速记卡

按“基础 → 绑定 → 开火命中 → 弹药换弹 → 弱网 → 项目本身 → Gameplay 框架与蓝图实现 → 执行端与复制标注 → 当前做法与理想方案 → 实体子弹 → 问题与取舍”排列。每题先给能直接说出口的答案，括号里是本书对应位置。

一、网络基础（1~9）

1. UE 的网络模型是什么？Listen Server 和 Dedicated Server 区别？服务器权威的 C/S 模型：真实状态只在服务器，客户端通过属性复制得到近似状态，通过 Server RPC 发请求。Listen Server 的主机同时是服务器和一个玩家（有渲染、有本地输入）；Dedicated Server 无本地玩家、不渲染，适合正式联机但多一份部署成本。双人合作通常用 Listen Server。（第 2 章）
2. GameMode、GameState、PlayerState、PlayerController 分别在哪几端存在？GameMode 只在服务器；GameState、PlayerState 在所有端（复制）；PlayerController 在服务器和它自己的客户端，别人的 PC 在你的客户端上不存在；HUD / UMG 只在本地。（第 2 章表）
3. Role 有哪几种？主机玩家的角色在主机上是什么 Role？Authority、AutonomousProxy、SimulatedProxy、None。主机玩家的角色在主机上是 Authority，同时 IsLocallyControlled 为 true——所以“权限判断”和“本地控制判断”要分开写。（第 2 章）
4. 能不能在一个 Actor 上调用 Server RPC，取决于什么？取决于调用端是不是这个 Actor 的拥有者连接：Owner 链最终要连到这个客户端的 PlayerController。和 Role 无关。关卡里摆放的 Actor、僵尸、关卡蓝图都不属于任何客户端，客户端调用会被丢弃（No owning connection）。（第 2、3 章）
5. 客户端调用 Multicast 会怎样？服务器调用 Client RPC 但 Actor 没有拥有者会怎样？客户端调用 Multicast 只在本地执行；没有拥有者的 Actor 上服务器调用 Client RPC，会在服务器本地执行。（RPC 可达性表）
6. Reliable 和 Unreliable 怎么选？Reliable 滥用会怎样？按“这条消息丢了怎么办”选：必须到达且低频的用 Reliable（开始开火、换弹、命中上报），表现类和高频的用 Unreliable 或复制计数器。Reliable 有序，丢包时后面的要排队（队头阻塞，E2）；发得太快会塞满可靠缓冲区，连接被断开。（第 6 章）
7. 属性复制有哪些特点？为什么“事件”不适合用普通复制属性表达？只从服务器到客户端、只发最新值、按网络帧和 NetUpdateFrequency 发、可以按条件发。一个网络帧内多次变化只会被看到最后一次，布尔 true→false→true 可能根本看不到变化；事件要用只增不减的计数器（BurstCounter）或 RPC。（第 2、5 章）
8. C++ 的 OnRep 和蓝图的 RepNotify 有什么区别？C++ 的 ReplicatedUsing 只在客户端收到新值时调用，服务器改值不触发，需要手动调用；蓝图 RepNotify 变量在服务器 Set 时服务器自己也会执行 OnRep。（第 2 章）
9. 常用的复制条件有哪些？各举一个例子。COND_OwnerOnly（弹药、背包）、COND_SkipOwner（开火计数、换弹状态——拥有者已经本地预测过）、COND_InitialOnly（出生时的外观种子）、COND_SimulatedOnly（只给模拟代理的插值数据）、COND_AutonomousOnly。（第 5 章）

二、角色、控制器、武器（10~15）

10. 讲一下 Possess 的过程。服务器：GameMode RestartPlayer → SpawnDefaultPawnFor → PC->Possess → Pawn->PossessedBy（SetOwner(PC)、设 AutonomousProxy、关联 PlayerState）→ ClientRestart（Client RPC）。客户端：AcknowledgePossession → PawnClientRestart → SetupPlayerInputComponent。（第 3 章表）
11. 武器应该在哪生成？Owner 和 Instigator 分别设成什么、有什么用？在服务器生成（PossessedBy 或带 HasAuthority 的 BeginPlay），SpawnParams 里 Owner = Pawn（让武器进入 Owner 链：能发 Server RPC、OwnerOnly 属性发给持有者、相关性跟随持有者），Instigator = Pawn（伤害统计、友伤、仇恨）。不要先生成再 SetOwner：BeginPlay 在 SpawnActor 内部就执行了。（第 3 章）
12. 武器挂到角色手上，挂接信息会自动复制吗？挂接信息（AttachmentReplication）只在 Actor 开启 bReplicateMovement 时复制。武器通常不复制移动，所以要复制 CurrentWeapon，并在 OnRep 里各端自己挂。（第 3 章）
13. 第一人称射击联机后，为什么要两套模型？自己看到的是贴脸的手臂和枪（1P，OnlyOwnerSee），别人看到的是完整人物（3P，OwnerNoSee）；两者的动画、Socket、蒙太奇都不同。只有手臂的话，别人看到漂浮的手臂——原 Demo 就是这样，属于工作量取舍，同步本身没错；要给对方展示完整角色时才做两套（完整版）。（第 3 章）
14. Enhanced Input 的映射应该在哪里添加？为什么不放在 BeginPlay？在本地控制者拿到控制权时：NotifyControllerChanged / PawnClientRestart，并判断 IsLocalController。BeginPlay 在每端每个副本都会执行，客户端 BeginPlay 时 Controller 可能还没复制下来。（第 3 章）
15. 在服务器上调用 GetPlayerController(0) 拿到的是什么？服务器这台机器的第一个本地玩家（Listen Server 的主机玩家），不是“当前 Pawn 的控制器”。原 Demo 用它在服务器上禁用死亡玩家的输入：客户端玩家死时传入的是主机 PC，Pawn 的 DisableInput 只接受自己的 Controller，于是只打错误日志、不生效；而且服务器上关输入本就管不到客户端。服务器只改状态 + 校验，关输入放到拥有者客户端的 OnRep 里。（第 3、10 章）

三、开火到命中（16~23）

16. 从按下开火到僵尸扣血，完整说一遍。理想方案（原 Demo 的实际流程是“服务器生成复制子弹、表现等组播”，见第 57 题与 K0 图 K0-2）本机：检查预测弹药 → 扣一发、Seq+1 → 立即播 1P 表现和后坐力 → 本地射线播命中特效 → Server_FireShot(Seq, 起点, 方向, 时间, 命中目标)。服务器：校验 → 扣弹、推进 AckSeq、BurstCounter+1 → 判定命中（PvE 容差校验 / PvP 回溯）→ ApplyPointDamage(Instigator, Causer)。僵尸 TakeDamage 只在服务器改 Health，死亡设 bIsDead。各端：OnRep 播开火、受击、死亡。（第 4 章）
17. 为什么开火表现要本机先播？只用 Multicast 有什么问题？只用 Multicast 时开火者要等一个往返（E1：RTT 200 ms 时 {{v:E1[s=0,rtt=200].own:.0f}} ms）。本机先播，Multicast / BurstCounter 只给别人；开火者跳过（SkipOwner），避免播两次。（第 4 章）
18. 服务器需要校验客户端开火的哪些内容？开火者存活、不在换弹、射速（令牌桶：允许短时突发、长期平均不超过射速；不能比较到达间隔，丢包重传后请求会扎堆到达）、弹药 > 0、起点离服务器上的眼睛位置不太远、方向与服务器视角夹角不太大；若客户端上报了命中，再校验目标包围盒 + 容差、视线是否被墙挡。（第 4 章代码）
19. 命中扫描和抛射物各适合什么？抛射物怎么做到本机不延迟？飞行时间很短的武器（步枪、手枪）用命中扫描；慢速武器（火箭、榴弹）用抛射物：服务器生成权威抛射物负责伤害，开火者本地先生成一个不复制的假抛射物，别人看到的是服务器复制下来的（可按 RTT/2 向前外推）。原 Demo 20000 cm/s 的子弹本质是命中扫描。（第 4 章表）
20. 原 Demo 的子弹伤害会不会在客户端也算一次？当前做法子弹是复制 Actor，ProjectileMovement 在客户端副本上也模拟、也碰撞，ReceiveHit 在每端触发，每端都会走到 ApplyDamage。但 Apply Damage 和 Event AnyDamage 都是 Authority Only，客户端上的子弹副本不是权威端，这次调用不执行（Pawn 的 TakeDamage 也会再查一次权限），所以僵尸只在服务器扣血。这是被引擎拦住，不是写对了：写法依赖引擎保护、Instigator 为空、客户端子弹副本的血花可能和服务器判定对不上。真正在每端执行的是死亡组播里的补刷。（第 1 章、K0；本书早先版本把这条误判为“客户端也扣血”，已勘误）
21. 僵尸的死亡应该怎么同步？服务器 TakeDamage 判定死亡 → bIsDead = true（复制），OnRep 里关碰撞、开布娃娃；同时停 AI、清所有计时器、给击杀者 PlayerState 加分、通知 GameMode 补刷、SetLifeSpan 交给服务器销毁。也可以 TearOff 让各端接管尸体。不要只发一次 Multicast（晚加入的人看不到）。（第 4 章）
22. Dedicated Server 上爆头判定可能出什么问题？服务器不渲染，默认不刷新不可见网格的骨骼，骨骼碰撞体停在旧姿势。需要把网格的 VisibilityBasedAnimTickOption 设为 AlwaysTickPoseAndRefreshBones，或用简化碰撞体判定。（第 4 章）
23. Listen Server 主机看客户端开火，SkipOwner 的 BurstCounter 有什么坑？OnRep 只在客户端触发，服务器（主机）不会收到自己的复制，所以服务器在接受客户端那发时要自己播远端开火表现（NM_ListenServer 且开火者非本地控制时）。（第 4 章代码）

四、弹药与换弹（24~29）

24. 弹药应该怎么复制？服务器权威，一个结构体 {InClip, Reserve, AckSeq}，COND_OwnerOnly。本机预测扣弹，显示 = InClip − (LocalSeq − AckSeq)。（第 5 章）
25. 预测扣弹后 OnRep 直接覆盖本地值，会出现什么？怎么解决？服务器值反映的是“处理完某一发时”的弹数，本机此时已经多打了几发，覆盖会让 UI 往回跳（E5：每次连射回跳 {{v:E5.1.rb:.0f}} 次）。用序号对账：服务器回传已处理的最后序号，本机减去尚未确认的发数。（第 5 章）
26. 换弹的流程？期间开火、切枪、死亡怎么处理？本机预测播动画 → Server_StartReload（Reliable）→ 服务器校验后 bPendingReload=true（SkipOwner）、启动计时器 → 到点 take = min(空位, 备弹) 一次性转移 → 复位。期间开火本地挡住、服务器 ProcessShot 也拒绝；切枪 / 死亡调用 CancelReload：ClearTimer、弹药不变。（第 5 章状态机）
27. 原 Demo 的换弹 bug 是什么？怎么发现的？“剩余子弹计算”在备弹不够补满时走 false 分支，该分支没有连 Return 节点，函数返回默认值 0，弹匣被清零（3/7 → 0/0）。把蓝图逐节点移植成 C++ 跑表驱动测试（E4）发现；整局打空再换只能打出 {{v:E4.session.0.2}}/40 发。（第 5 章）
28. 换弹加子弹应该挂在蒙太奇的 AnimNotify 上吗？不推荐在服务器依赖动画通知：Dedicated Server 动画可能不更新，蒙太奇被打断时通知不来。服务器用数据配置的时长计时，动画按同一时长播放，只负责表现。（第 5 章）
29. 另一端怎么看到“他在开枪”？为什么不用复制的 bIsFiring？BurstCounter（只增不减，SkipOwner），OnRep 里按增量播。bIsFiring 在连射时一直为 true，只会触发一次 OnRep，一个网络帧内的多发也无法区分。（第 5 章）

五、弱网与性能（30~37）

30. 弱网“卡”有哪几种？分别用什么工具定位？帧卡（stat unit / Insights CPU，不是网络）、操作反馈慢（RTT 相关）、移动拉回（p.NetShowCorrections）、远端顿挫（看更新频率与到达间隔）、打不中（移动目标 + 高延迟）、消息扎堆（Networking Insights 看 RPC 时间）、带宽饱和（stat net）。复现用 PIE 网络模拟或 NetEmulation.PktLag / PktLoss。（第 6 章表）
31. 讲一下 CharacterMovement 的客户端预测和纠正。拥有者每帧本地移动并保存 SavedMove，ServerMove 发给服务器；服务器用同样输入重放，误差超过 MAXPOSITIONERRORSQUARED（默认 3）就发 ClientAdjustPosition；客户端回到服务器位置并重放未确认的 SavedMove。纠正发送有最小间隔（NetworkMinTimeBetweenClientAdjustments）。（第 6 章）
32. 冲刺为什么会被拉回？正确做法？冲刺标志只在一端生效，两端用不同速度模拟（E6：每秒纠正 {{v:E6[c=0,rtt=100].cps:.1f}} 次，平均回拉 {{v:E6[c=0,rtt=100].avg:.0f}} cm）。“本地切换 + Server RPC”在丢包时仍会纠正。正确做法：标志放进 SavedMove（CompressedFlags / FCharacterNetworkMoveData），GetMaxSpeed 统一计算。（第 6 章）
33. 什么是延迟补偿？有哪些做法？补偿“客户端看到的是过去”的误差，让服务器按开火者看到的时刻判定。服务器回溯：记录目标历史位置，按客户端时间插值回去射线，需限制最大回溯；客户端判定 + 服务器容差校验：简单、手感好，但信任客户端。PvE 多用后者。（第 6 章，E3）
34. 延迟补偿的副作用是什么？被打的一方会遇到“已经躲到掩体后还被打中”（E3 的受害者位移，RTT 200 ms、480 cm/s 时平均 {{v:E3[v=480,rtt=200].victim:.0f}} cm）；高延迟玩家占便宜；服务器要存历史、做回溯，有 CPU 和内存开销。（第 6 章）
35. 远端角色 / 僵尸移动一顿一顿的，怎么查？看 NetUpdateFrequency 和实际到达间隔、是否丢包；CMC 模拟代理的平滑模式（默认 Exponential）和参数；动画是否用复制的速度驱动；是否有人在客户端改它的位置。（第 6 章）
36. 有哪些降低带宽的手段？不复制短命 Actor（子弹、特效）、复制条件、降低 NetUpdateFrequency、休眠（Dormancy）、相关性（NetCullDistance、OwnerRelevancy）、量化（FVector_NetQuantize）、Push Model、合并事件为计数器。（第 6 章表）
37. 为什么即使 RTT 为 0，原 Demo 的开火反馈也有约 20 ms？属性和多播要等服务器下一个网络帧（默认 30 Hz，平均等半帧左右）才发出；RTT 0 时 E1 测得 {{v:E1[s=0,rtt=0].own:.0f}} ms。这也说明“本机表现等服务器”在局域网里同样有延迟。（第 2、4 章）

六、关于这个项目本身（38~40）

38. 这个 Demo 最大的问题是什么？你会先改哪三处？根因是单机思维：代码在错误的一端执行。先改（最小修复）：① 换弹函数补上 Return，改成到点一次性 take 计算；② 把补刷、清计时器从死亡组播里挪出来，只在服务器执行，失败判定挪到服务器（规则可保留）；③ 开火时本机先播表现、组播挪到弹药检查之后，子弹伤害显式加权限判断并填 Instigator。再往后才是理想方案：命中扫描、序号对账、冲刺进移动预测。（第 1 章、K0 表 K0-2）
39. 你是怎么验证这些问题的？先静态审计：把 .uasset 解析成节点和连线（导出伪代码），逐张图确认每段逻辑在哪一端执行；再把关键逻辑（换弹、开火时序、移动纠正、命中判定）移植成离散事件模拟，在不同 RTT / 丢包下对比方案；最后在 PIE 用网络模拟、Dedicated Server 模式、晚加入复测。（附录 A）
40. 如果做成正式项目，你会怎么组织网络代码？C++ 打底：Character + 自定义 MovementComponent（预测状态）、Weapon（预测开火 / 换弹）、GameMode / GameState / PlayerState 分工；或直接用 GAS（技能预测键、GameplayEffect 伤害、GameplayCue 表现），参考 Lyra。从第一天起就在 Bad 网络和 Dedicated Server 模式下测试。（第 8、14 章）

七、Gameplay 框架与蓝图实现（41~50）

41. GameInstance、World、Level 是什么关系？切地图时谁会被销毁？GameInstance 进程级，一个进程一份，持有 LocalPlayer 和跨地图的本地数据；World 是当前地图的运行时容器，持有 PersistentLevel 和流送关卡，Actor 的 Outer 是 Level。Open Level / ServerTravel 时 World 及其中所有 Actor（包括 GameMode、GameState、PlayerController、PlayerState）都会重建，GameInstance、LocalPlayer 保留；无缝漫游下 PC 会被保留、PlayerState 通过 CopyProperties 拷贝。（第 7 章）
42. Outer、Owner、AttachParent、Instigator 分别管什么？Outer 管内存归属（对象路径、GC、随谁卸载）；Owner 管网络归属（Server RPC 能否发出、OwnerOnly 发给谁、相关性）；AttachParent 管变换层级（跟着谁动）；Instigator 管责任（伤害是谁造成的）。武器：Outer 是 Level，Owner 和 Instigator 是角色，AttachParent 是角色手上的插槽。（第 7 章）
43. 服务器上一个 PlayerController 的 IsLocalController 为 false 说明什么？它的 Player 是 UNetConnection 而不是 ULocalPlayer——它是远端客户端玩家在服务器上的代理。在它上面建 UI、加输入映射没有意义；在它上面调 Client RPC 会发到那个客户端。PC 的 BeginPlay 在这种 PC 上也会执行，所以建 UI 前要判断。（第 7、9 章）
44. 一个玩家 Pawn 的生命周期里，哪些蓝图事件只在服务器、哪些在拥有者、哪些在所有端？Construction Script、BeginPlay、Tick、EndPlay、Destroyed 在所有端；Event Possessed / Unpossessed 只在服务器；Receive Controller Changed 在服务器和拥有者客户端；RepNotify 在客户端收到时执行（蓝图在服务器 Set 时也执行）；输入事件只在本地控制端。（第 7 章表）
45. 覆写 GameMode 的 HandleStartingNewPlayer 要注意什么？它是 BlueprintNativeEvent，覆写后默认实现（RestartPlayer → 生成 Pawn → Possess）不再执行，需要显式调用 Parent 节点；本 Demo 在对局进行中加入时不调用父类，而是让新玩家观战。（第 9 章）
46. UMG 能直接调用 Server RPC 吗？不能。Widget 不是 Actor，没有 Owner 链和网络连接；用 Get Owning Player 拿到本地 PlayerController，调用它上面的 Server RPC（PC 属于这个客户端的连接）。（第 13 章）
47. 蓝图的 RepNotify 和 C++ 的 OnRep 在使用上有哪些差别？① 蓝图在服务器 Set 时也执行 OnRep，C++ 不执行；② 蓝图 OnRep 没有旧值参数，需要自己保存上次的值（如 LastSeenBurst），C++ 可以声明一个旧值参数；③ 蓝图结构体复制变量用 Make → Set 整体赋值更稳妥，Set Members in Struct 不一定触发服务器端 RepNotify。（第 10、11 章）
48. 为什么换弹用 Set Timer by Event 而不是 Delay？Delay 是 Latent 节点，没有句柄，无法从外部取消，同一事件再次进入时会被忽略；换弹被死亡、切枪打断时必须能取消并保证弹药不变，所以用计时器句柄（Clear and Invalidate Timer）。（第 11 章）
49. 如果希望僵尸的随机外观和动作在各端一致，怎么做？原 Demo 不一致算问题吗？不算问题：原 Demo 的速度变体在服务器设置后随移动复制，各端一致；只有动画姿势客户端用默认值，攻击 / 受击动作在组播里各端各自随机——纯表现差异，伤害判定只在服务器，属于可接受的设计取舍。要求画面一致时：服务器在 BeginPlay 生成一个整数种子 VariantSeed（复制条件 Initial Only，RepNotify），各端在 OnRep 里用它构造 Random Stream，按相同顺序抽取速度档位、移动 / 待机动画；攻击动作用 AttackInfo {Counter, Index} 由服务器选、各端播。（第 12 章）
50. 你认为一个“合格”的联机 Demo 的标准是什么？五个维度：权威清晰（伤害、死亡、弹药、阶段、刷怪只在服务器）、手感跟手（开火 / 换弹 / 冲刺本机零等待，弱网不回跳不拉回）、状态完整（持续状态是复制属性，晚加入正确，随机一致）、职责单一（框架类各司其职，无上帝对象，UI 只读）、可验证（Listen / Dedicated / 独立进程 / 弱网 / 晚加入都测过，有录屏和数据）。（第 8 章）

八、执行端、复制与组播（51~56）

51. 一个事件在哪端执行，你怎么判断？先看它是不是 RPC：Run on Server 在服务器执行、Run on owning Client 在拥有者客户端执行、服务器调用的 Multicast 在服务器和所有相关客户端执行。不是 RPC 的普通事件没有自己的执行端，跟随调用者：由 Possessed、HandleDamage 这类服务器事件调用就在服务器，由输入事件调用就在本地控制端，由 OnRep 调用就在“服务器（蓝图 Set 时）+ 收到的客户端”。再看对象存在于哪端：GameMode、AIController 只在服务器，Widget 只在本机。（第 8 章表 8-6、第 9 章图 9-1a）
52. Listen Server 的主机会“收到”复制吗？主机是怎么看到客户端玩家开火表现的？不会。主机进程就是服务器，持有的是权威值，复制只从服务器发往客户端。主机能看到客户端的 3P 开火，是因为蓝图 RepNotify 在服务器 Set w/ Notify 时会在服务器本地执行一次 OnRep_BurstCounter；C++ 的 OnRep 不会，C++ 里要在服务器手动调用。也因此 OnRep 对主机自己的武器也会执行，要用 NOT Owner.IsLocallyControlled 过滤掉已预测的那份。（第 8 章表 8-4、第 11 章图 11-4）
53. Owner Only、Skip Owner、Initial Only 分别发给谁？本 Demo 哪些变量用了？Owner Only 只发拥有者连接：Ammo（只有持枪者需要对账）；Skip Owner 发给除拥有者外的所有人：BurstCounter、bPendingReload、bIsAiming（拥有者已本地预测）；Initial Only 只在 Actor 首次复制给某个连接时发：VariantSeed（生成后不变，晚加入者加入时也会收到）。引擎的 ReplicatedMovement 用的是 SimulatedOrPhysics，拥有者靠移动预测，不收。（第 8 章 4.1）
54. 什么时候用组播，什么时候用 RepNotify？原 Demo 的 8 个组播你怎么处理的？持续状态（阶段、死亡、换弹中、外观）用 RepNotify：晚加入能看到、丢包会被下一次更新纠正。组播只用于同时满足四条的：由服务器调用、一瞬间、晚加入不需要、丢了无所谓——本 Demo 只剩僵尸惨叫和低吼两个 Unreliable 组播。原来的 8 个：开局 → GS.Phase；开火 → BurstCounter（Skip Owner）；换弹 → bPendingReload；受击 → LastHit；攻击 → AttackInfo；玩家 / 僵尸死亡 → bIsDead + GameMode 判定；关卡蓝图里那个直接删除。（第 8 章表 8-5、第 12 章 4.5）
55. 在蓝图里让一个变量复制要勾哪几处？为什么有人勾了 RepNotify 却在客户端收不到？三层：Actor 的 Replicates；变量所在组件的 Component Replicates；变量自己的 Replication（Replicated / RepNotify）和 Condition。常见漏法：变量放在 ActorComponent 里却没勾 Component Replicates；Actor 是运行时在客户端本地 Spawn 的（不是服务器生成的复制 Actor）；在客户端 Set 了变量（只改本地，不会发出去，下次复制还会被覆盖）。（第 8 章 4、第 10 章 AC_Health）
56. 客户端调用 Multicast 会怎样？客户端在不属于自己的 Actor 上调用 Server RPC 会怎样？客户端调用的 Multicast 只在这台客户端本地执行，不会发给服务器和别人。原 Demo 的 8 个组播其实都在服务器上调用（这点没错），它的问题是组播里做了补刷这类规则、用组播表达持续状态。在没有拥有者连接的 Actor（关卡蓝图、僵尸、别人的角色）上调 Server RPC 会被丢弃，日志里是 No owning connection——原 Demo 关卡蓝图的 Server_SetStart 就是这样失效的。请求一律从自己的 PC 或自己 Possess 的 Pawn / 武器发出。（第 1、2 章、第 8 章表 8-5）

九、当前做法 vs 理想方案（57~60）

57. 你的 Demo 里命中是射线还是子弹实体？为什么重构要换？当前做法实体：服务器生成的复制子弹 Actor（ProjectileMovement，200 m/s，寿命 1 秒），没有射线检测，靠子弹碰撞判断打中。问题：开火者要等一个往返才看到表现、远端看到子弹凭空出现在几米外、每发一个 Actor 通道、服务器和客户端两份子弹各撞各的、伤害写在每一端都会触发的碰撞里。理想方案步枪改命中扫描：子弹飞行时间只有几帧，和射线几乎没区别；本机先播并做射线，服务器校验后结算，别人靠开火计数播表现、本地画曳光。（K0 第 3 节、第 4 章）
58. 如果一定要保留抛射物（比如火箭筒），正确的联机做法是什么？服务器生成权威子弹，伤害只在它的碰撞里结算，并先判断权限、填 Instigator；开火者按下时本机立刻生成一颗不复制的假子弹做表现；服务器子弹对开火者隐藏，其他端收到它时按网络延迟向前快进一段，避免“突然出现”；射速高时不要每发一个复制 Actor，改为只复制开火计数、各端本地生成表现弹。（K0 表 K0-3、第 5B 章）
59. 不重构、只给你一天，你会怎么改原 Demo？最小修复只改会出错的地方，不动结构：换弹补 Return 并改成到点一次性计算；补刷和清计时器挪出死亡组播；失败判定挪到服务器（GameMode）后广播一次（“任一人阵亡即失败”的规则不用改）；Multicast_Fire 挪到弹药检查之后、本机先播开火动画；伤害节点前加权限判断、填 Instigator；暂停只开菜单、重开用 servertravel；冲刺按键时本机和服务器同时切换。手感和带宽问题（等组播、子弹突现、逐发 Actor）这一步解决不了，要靠重构。（K0 表 K0-2 的“最小修复”列）
60. 面试官问“你说的这些是 Demo 里做了的，还是你设计的？”怎么答？按三种时态如实分开：原版（复制子弹、组播同步、单机式整局流程）是做过的；把蓝图逐节点读出来定位问题、用网络模型实验对比方案是验证过的；命中扫描、序号对账、换弹状态机、移动预测、GameMode / GameState 分工是设计的——已经在引擎里实现的部分才说“做了”，并给出录屏或 stat net 数据。说清楚这一点，后面的追问才不会把你逼到前后矛盾。（K1 第 4 节）

十、实体子弹（61~62）

61. 实体子弹的“快进”（catch-up）是什么？做了快进还要延迟补偿吗？服务器收到开火请求时，射手的假弹已经飞了约半个 RTT，服务器就把真弹沿弹道往前推这么一段再生成（蓝图里先对快进段做一次射线，再在快进点生成），让真弹和假弹对齐。它只追回“子弹出发晚”；射手瞄准时看到的目标本身就是过去的，这部分要靠服务器按射手看到的时刻回溯目标（PvP），或客户端上报命中、服务器容差校验（PvE）。模型实验：200 m/s 子弹、RTT 200 ms，只做快进命中率 {{v:E9[vp=200,rtt=200].s2:.0f}}%（和不做一样），加回溯 {{v:E9[vp=200,rtt=200].s3:.0f}}%。快进还要设上限（50~150 ms），否则高 ping 玩家的子弹在别人屏幕上瞬移，被瞄准的人来不及躲。（第 5B 章）
62. 射速很高、又要子弹下坠，为什么不建议每发生成一个复制的子弹 Actor？每发都要开关一条 Actor 通道、生成和销毁 Actor，带宽和 CPU 开销随射速线性增长（E10：两人步枪连射，复制 Actor 加复制移动约 {{v:E10[w=rifle].b0}} B/s，只发首包也要约 {{v:E10[w=rifle].b1}} B/s，数据化弹道约 {{v:E10[w=rifle].b3}} B/s）；而且步枪弹太快，远端前推后会出现在目标后面，显示真弹没有意义。改成数据化弹道：服务器把子弹当数据逐帧分段射线，各端按开火计数和种子本地生成不复制的表现弹（可以用对象池）。（第 5B 章）

十一、问题还是取舍，理想方案拆多细（63~64）

63. 面试官说：“一人阵亡就全员失败、对方只看到一双手臂，这些不也是问题吗？”怎么答？不是问题，是取舍。一人阵亡即失败是玩法规则——可以讨论改成“全灭才失败”会不会更好玩，但它不是 bug；只做第一人称手臂是单机改联机时的工作量妥协，同步本身没错；僵尸动作各端随机是纯表现差异，伤害判定只在服务器。我判断的标准是：会不会让结果出错或各端结果不一致、会不会违背设计意图；只影响画面或只是还没做的，算取舍。真正的问题是判定写在角色组播里、补刷在每一端执行、换弹吞弹匣这类“结果错了”的地方。（K0 第 4 节）
64. 你的理想方案有 14 个类，两人 Demo 需要拆这么细吗？不需要。两人 Demo 先做精简版：沿用原有的 GameMode、GameState、角色、武器、僵尸、界面 6 个类，只把职责放对——规则进 GameMode、全局状态进 GameState、开局从关卡蓝图挪出来、结果只在服务器、表现本机先播。14 个类的完整版是工程化参考：要做大厅名单和记分板时加 PlayerState、PlayerController 子类，要打包给别人玩时加 GameInstance 会话，僵尸行为变复杂时换行为树，种类变多时用数据资产。拆不拆看需求，不是越细越好。（K0 第 1 节）

速记卡

四个问题

这个对象在哪几端？这段代码在哪端执行？谁能调这个 RPC？这个变量发给谁？

一条总规则

状态用复制属性，瞬时事件用 RPC 或计数器，表现各端本地做，结果只认服务器。

两个判断

改状态看 HasAuthority；播本地表现看 IsLocallyControlled。主机玩家两个都是 true。

Owner 链

Weapon → Pawn → PC → Connection。决定 Server RPC 可达、OwnerOnly 发给谁。

开火三段

本机预测表现 + 发请求；服务器校验、扣弹、判定、伤害；各端 OnRep / 计数器播表现。

弹药

OwnerOnly 结构体带 AckSeq；显示 = InClip − 未确认发数；别人用 SkipOwner 的 BurstCounter。

换弹

服务器计时器状态机；到点 take = min(空位, 备弹)；取消不动弹药；本机预测动画。

移动

影响速度的状态进 SavedMove；两端用 GetMaxSpeed 同一规则算；不另发 RPC。

命中

PvE：客户端判定 + 容差校验；PvP：服务器回溯，限最大回溯时间。

Reliable

低频必达才用；表现类 Unreliable；Tick 里发 Reliable 必扣分。

整局流程

规则 GameMode、全局 GameState、个人 PlayerState；倒计时复制结束时刻；重开 ServerTravel。

框架职责

GameInstance 进程 · GameMode 规则 · GameState 全局 · PlayerState 人 · PC 灵魂与 UI · Pawn 身体 · Component 能力。

五种关系

Outer 管内存、Owner 管网络、AttachParent 管变换、Instigator 管责任、Possess 管控制。

蓝图三坑

OnRep 无旧值；结构体整体赋值；需要取消的等待用计时器不用 Delay。

测试

Dedicated Server 模式、独立进程、Bad 网络、晚加入、谁先死、同时击杀。

问题 vs 取舍

结果出错或各端结果不一致、违背设计意图 = 问题；只影响画面、玩法规则、还没做的范围 = 取舍。一人阵亡即失败、只有 1P 手臂、僵尸动作各端随机都是取舍。

精简版 vs 完整版

精简版沿用原有 6 个主要类、把职责放对，解决全部 P0；完整版 14 个类是工程化参考，按需再拆。

实体子弹

本机假弹 + 服务器真弹快进（设上限）+ 射手隐藏真弹 + 命中只认服务器、ImpactInfo 复制、延迟销毁；快进追子弹，回溯追目标；高射速用数据化弹道。

当前 vs 理想

当前：复制子弹 Actor、没有射线、表现等组播；理想：命中扫描、本机先演、服务器裁决、状态复制。先说当前，再说为什么换。

讲 Demo

是什么 → 难在哪 → 踩了什么坑 → 怎么改、怎么证明；做过 / 验证过 / 设计的分开说；模型实验不说成引擎实测。

六类根因

结果在客户端算、表现等服务器、两端各算各的、本地当全局、把状态当事件发、把时序当成必然。

执行端

RPC 看类型；普通事件跟调用者；OnRep = 服务器（蓝图 Set 时）+ 收到的客户端；GameMode / AI 只在服务器，Widget 只在本机。

复制三层 + 三条件

Actor Replicates → Component Replicates → 变量 Replicated / RepNotify。OwnerOnly 只给自己，SkipOwner 给别人，InitialOnly 只发一次。

组播四条件

服务器调用、一瞬间、晚加入不需要、丢了无所谓 → Unreliable 组播；否则用 RepNotify。原 8 个：7 个换 RepNotify、1 个删。
