1.2 复制标注：这个 Set 会不会、发给谁

复制标注条的读法：“⇄ 复制 · RepNotify · Owner Only → 拥有者 OnRep_Ammo”
  • ⇄ 复制 · RepNotify：这个变量在 Details → Replication 里选了 RepNotify。服务器 Set 之后，引擎在下一个网络帧把新值发出去；收到的客户端执行 OnRep_X；蓝图里服务器这次 Set 本身也会立即执行一次 OnRep_X（C++ 不会）。
  • ⇄ 复制 · Replicated：只复制、没有回调。适合“UI 每隔一会儿读一次”的值，例如结束时刻、僵尸数。
  • ○ 不复制：Replication = None，只改本端的这一份。服务器上的不复制变量（如 GameMode 的 SpawnPoints）客户端永远看不到；客户端上的（如 LocalShotSeq）服务器永远看不到。
  • Owner Only / Skip Owner / Initial Only：Replication Condition，决定发给哪些客户端（表 8-4 给出了双人局里每个变量的接收方）。
  • 三个前提：① 只有服务器上的写入会被复制，客户端 Set 复制变量只改了自己的副本；② 所属 Actor 必须勾 Replicates（组件还要勾 Component Replicates）；③ 只发最新值，一个网络帧里改多次只发最后一次。
组播在重做版里只剩 2 个

原 Demo 有 8 个 Multicast（开局、开火、换弹、受击、攻击、死亡…），重做后只有僵尸的两个一次性音效还用组播；其余全部换成 RepNotify。原因和逐一对照见第 8 章 5.1“组播去哪了”（表 8-5）。每张图下方的网络摘要都有一行“组播”，没有就写“无”。

面试注意：原 Demo 根本没有“联机入口”

原工程只在 PIE 里用“Play As Listen Server”跑过，没有任何会话节点，GameMode 里两个 servertravel 节点也没接线。打包后两台机器无法互联。合格的 Demo 至少要能“主持 → 局域网查找 → 加入 → 断线回菜单”。会话测试建议用两个 Standalone 进程或打包版本，PIE 单进程下的会话行为与真实情况不完全一致。

4. GM_Coop：规则只在这里

项内容
父类GameModeBase（想用自带比赛阶段可换成 GameMode，见下方提示）
存在于仅服务器；客户端上 Get Game Mode 返回 None
类默认值DefaultPawnClass = BP_CoopCharacter · PlayerControllerClass = PC_Coop · PlayerStateClass = PS_Coop · GameStateClass = GS_Coop · HUD = None

对外接口CheckAllReady · OnZombieKilled(Zombie, Killer) · OnPlayerDied(PC) · RestartMatch——都只会被服务器上的对象调用
规则说明：本节示范的是“全灭才失败”

原 Demo 的规则是“任一人阵亡即失败”——这是玩法设计，不是 bug，保留完全可以：这时下图的 OnPlayerDied 直接调用 EndMatch(Lost)，PC_Coop 的观战逻辑（Client_StartSpectating）也可以不做。本节示范“全灭才失败、死者观战”这一变体，是为了多展示一个“服务器通知单个客户端”的 Client RPC 用法。无论哪种规则，要点都一样：判定只在 GameMode 做一次，结果写进 GameState 广播。

GameModeBase 还是 GameMode？

AGameMode（不是 Base）自带一套比赛阶段 MatchState（WaitingToStart → InProgress → WaitingPostMatch），配合 AGameState 复制，有 ReadyToStartMatch、StartMatch、EndMatch 可以覆写，还提供断线玩家的 PlayerState 暂存（InactivePlayerArray）。本 Demo 用 GameModeBase + 自定义 Phase，是为了把流程画得一目了然；面试时提一句“正式项目可以直接用 AGameMode 的 MatchState”是加分项。

为什么复制“结束时刻”而不是“剩余秒数”

GetServerWorldTimeSeconds 由 GameState 周期性复制服务器时间（ServerWorldTimeSecondsUpdateFrequency，默认 0.1 s）得到差值估计，各端用同一条时间轴，显示平滑、只需复制一次结束时刻。它没有扣除单程延迟，客户端估计会偏慢约半个 RTT 并随抖动波动——用来显示倒计时足够，“时间到”的判定由服务器计时器决定；如果要拿它做命中回溯这种精度要求高的事，需要自己做带 RTT 补偿的时钟同步。

当前做法（原 Demo）为什么“能跑”哪里会坏理想方案
准备 RPC 放在角色上角色属于客户端连接 ✓—放到 PC（不依赖 Pawn 是否存在）
GameMode 上的 AddReadyPlayer 标成 Server RPC在服务器上调用 = 普通函数无意义的标志，误导读者普通函数 CheckAllReady
“游戏是否开始”是 GameState 上的非复制布尔，由关卡蓝图多播设置关卡脚本在客户端能收到多播晚加入的人永远是 false，开不了火GS.Phase 复制 + OnRep

本章速记
  • GameInstance：会话与断线，本机专用，这里用 PC(0) 是对的。
  • GM_Coop：HandleStartingNewPlayer（覆写要调父类）、CheckAllReady → StartMatch、SpawnZombie / OnZombieKilled、OnPlayerDied（按规则判输）、EndMatch（只改状态）、RestartMatch（servertravel）。
  • GS / PS：只存复制状态、OnRep 里广播分发器；倒计时复制结束时刻。
  • PC_Coop：BeginPlay 判断 IsLocalController 再建 UI；UI 操作 → Server RPC（先校验）；观战 → Client RPC。
自测：为什么 EndMatch 里不写“禁用所有玩家输入”？那玩家结算后还能开枪吗？ 在服务器上对远端玩家的 Pawn 调 DisableInput 改的是服务器那份的标志，客户端的输入照常处理，等于没写。正确的分工是：服务器在 Server_FireShot 等请求里校验 Phase == Playing（结算后一律拒绝）；客户端在 OnRep_Phase 里切到 UI Only 输入模式、弹出结算界面——本地输入由本地关，结果由服务器挡。
自测：Server_RequestRestart 里为什么判断 IsLocalController 就能识别“主机”？ 这个 RPC 在服务器上执行，self 是发起请求的那个玩家在服务器上的 PC。主机玩家的 PC 在服务器上是本地的（Player 是 ULocalPlayer），客户端玩家的 PC 在服务器上不是（Player 是 UNetConnection）。所以 IsLocalController 为 true 就说明请求来自主机本人。
