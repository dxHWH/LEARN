BRIEFING · K1

把 Demo 讲清楚：项目描述与统一口径

讲一个对方看不到的项目，要让他在一分钟内脑子里有画面、有边界、有难点、有证据。本章给出项目档案、三种长度的讲法、“做过 / 验证过 / 设计的”三种时态、全书统一的数字与术语，以及一张可以现场画的白板图。

本章目标
  • 用玩家视角一句话描述玩法，让对方脑子里先有画面，再谈技术。
  • 准备 10 秒 / 1 分钟 / 3 分钟三种讲法：结构相同，只是详略不同。
  • 分清做过的、验证过的、设计的三种时态，不夸大，也不过度自我否定。
  • 全书数字、术语、关键问题的答案统一，被追问时前后一致。
  • 能在白板上用一张图讲完“一发子弹”的完整链路。
30 秒版：这个 Demo 是什么

这是一个 UE 5.5 纯蓝图的双人合作射击：两名玩家在一张咖啡店地图里用步枪抵御僵尸，坚持 3 分钟获胜。它先做成单机，后来我把它改成了 Listen Server 双人联机。第一版我对 UE 网络还不熟，基本是“哪里不同步就补一个组播”，结果出现了开火延迟、伤害在客户端被重复结算、换弹吞子弹、冲刺被拉回等问题。后来我做了一次系统复盘：把全部蓝图读成伪代码逐条定位，归纳成几类根因，再按服务器权威 + 本机预测 + 状态复制重新设计了开火、换弹、伤害、移动和整局流程，关键结论用网络模型实验做了对比。

1. 面试官脑子里需要的四样东西

对方听你讲项目时，在心里填的是一张表：这是什么、难在哪、你踩了什么坑、你怎么解决并证明。按这个顺序讲，每段一两句，他就不用打断你去问“所以这到底是个什么东西”。

2. 项目档案：先让对方脑子里有画面

项口述内容
一句话UE 5.5 纯蓝图的双人合作 FPS，两人一起在咖啡店里打僵尸，坚持 3 分钟获胜。
一局怎么玩主菜单 → 两人都确认准备 → 镜头切入、开始计时 → 僵尸从 4 个刷怪点涌出，追击最近的玩家并近战攻击，同时保持 10 只、死一只补一只 → 时间到胜利；原版里任一玩家阵亡即失败 → 结算后可以重开或退出。
玩家能做什么移动、冲刺、开镜、射击、换弹、暂停。步枪弹匣 10、备弹 30，约 8 发 / 秒；爆头 100、身体 40；僵尸和玩家都是 100 血，僵尸一击 10 点；被打时有镜头抖动和屏幕效果。
联机方式Listen Server：一名玩家做主机（既是服务器也是玩家），另一名作为客户端连进来。原版只在编辑器里用两个窗口联机测试，没有做主持 / 加入流程。
关键实现（当前做法）命中由服务器生成的复制子弹 Actor 撞出来（ProjectileMovement 200 m/s），没有射线检测；开火、换弹、受击、死亡的表现靠服务器组播；开局、计时、胜负写在关卡蓝图和 UI 里。

我负责全部：单机玩法和蓝图、单机改双人联机、之后的复盘和重构设计。

3. 三种长度的讲法

10 秒（自我介绍里顺带一提）

“我做过一个 UE5 纯蓝图的双人合作打僵尸 Demo。第一版用组播补同步踩了不少坑，后来我复盘了一遍，按服务器权威、本机预测、状态复制重新设计了联机部分。”

1 分钟（面试官说“介绍一下这个项目”）

是什么“这是一个 UE 5.5 纯蓝图的双人合作 FPS，两个人在咖啡店地图里打僵尸，撑 3 分钟获胜，Listen Server 联机。”

难点“它是从单机改过来的，难点在于单机里默认只有一台机器、一个玩家：谁算伤害、谁先看到动画、谁决定胜负这些问题，单机里根本不存在。”

踩坑“第一版我基本是哪里不同步就加一个组播，子弹也是服务器生成的复制 Actor、没有用射线。问题可以归成几类：结果在客户端算——僵尸死亡组播里的补刷在每一端都执行，客户端会多出只有自己看得到的僵尸；表现等服务器——RTT 200 ms 时按下开火要两百多毫秒才看到动画；两端各算各的——冲刺只在服务器生效，客户端持续被拉回；本地当全局——用 0 号控制器、UI 里算倒计时、客户端调用暂停。还有一个纯逻辑 bug：换弹在备弹不够时会吞掉整个弹匣。”

改进“复盘时我把蓝图全部读成伪代码逐条定位，然后重新设计：伤害、弹药、胜负只在服务器；步枪从复制子弹改成命中扫描，开火和换弹本机先播、服务器校验后用序号对账；持续状态都改成复制属性加 RepNotify，组播只留给一次性音效；冲刺放进 CharacterMovement 的移动预测。”

证据“关键结论我用网络模型实验对比过，比如冲刺只在服务器生效时每秒被纠正 {{v:E6[c=0,rtt=100].cps:.0f}} 次左右，放进移动预测后为 0。”

3 分钟（面试官说“详细讲讲”）

结构不变，每一段展开一层，按下表控制时间。每段末尾都给面试官留了一个“钩子”，他顺着追问，你就在自己准备好的路上。

时间讲什么留下的钩子（对方大概率追问）
0:00–0:20玩法画面、规模、Listen Server、纯蓝图“Listen Server 和 Dedicated Server 有什么区别？”（链 8）
0:20–0:50第一版的实现思路：功能先在单机做完，联机时“哪里不同步补哪里”，大量使用组播；子弹是服务器生成的复制 Actor（不是射线）“组播和复制属性怎么选？”（场景 02、08）
0:50–1:40几类根因，各举一个玩家能看到的现象（六类根因见 K2 图 K2-1）“你的子弹是射线还是实体？”（K0 第 3 节）“伤害会不会在客户端多算？”（K0 勘误）
1:40–2:30正确做法：权威在服务器、本机预测 + 序号对账、状态复制、移动预测、GameMode / GameState 管整局“预测失败了怎么办？”（场景 06）“冲刺为什么要进移动预测？”（场景 10）
2:30–2:50怎么验证：读蓝图定位问题 + 网络模型实验对比方案（说清是模型实验）“模型和真实引擎差多少？”（链 11）
2:50–3:00不足和下一步：只做了 2 人局域网、PvE 的命中用客户端判定 + 容差、纯蓝图做不到彻底的移动预测“如果是 PvP 你怎么做？”（链 2）

4. 时态口径：做过的、验证过的、设计的

同一个项目里有三种不同性质的内容。面试官判断真实性靠追问细节：你说“做过”，他会问实现时遇到了什么；你说“设计”，他会问取舍。说错时态，比说错一个知识点代价大得多——一处被戳穿，整个项目都不可信。

时态指什么可以这样说不要这样说
做过的原版：玩法、全部蓝图、单机改联机、编辑器里两人能打完一局；书中标为 当前做法“我做了……；当时我的做法是……，因为我以为……”“原版没什么问题”
验证过的复盘：从资产里读出全部蓝图节点逐条定位；把换弹、开火时序、移动纠正、命中判定移植成网络模型实验“我把蓝图逐节点读出来确认过”“在网络模型实验里，RTT 200 ms 时……”“我在引擎里实测……”（模型实验不是引擎实测）
设计的重构方案：类划分、复制表、RPC 表、每个类的事件流程（第 7~13 章）；书中标为 理想方案“正确的做法是……”“我重构的方案是……”“我已经全部改完上线了”（除非真的改完）

表 K1-3　三种时态。本书第三部分是“设计的”，附录 A 与实测 E1~E7 是“验证过的”

如果你已经在 UE 里把重构做完了

把做完的那部分从“设计的”升级成“做过的”，同时补上引擎里的证据：PIE 网络模拟下的录屏、p.NetShowCorrections 1 的截图、stat net 数据、Networking Insights 里 RPC 的到达时间（第 14 章清单）。只做完一部分，就只升级那一部分，比如“开火和换弹已经按方案改完并实测；移动预测还是方案”。

面试注意：别把“失败”讲成“我不行”

自己私下叫它“极度失败的 Demo”没关系，面试里要说“第一版联机实现”“早期版本”。面试官想听的不是这个 Demo 有多烂，而是：你能不能看出问题、说清根因、给出正确做法、并证明它是对的。每个坑都按“现象 → 我怎么发现的 → 根因 → 正确做法 → 怎么验证”讲，坑就变成了加分项。

表 K1-4　统一数字。所有实测都是网络模型实验（离散事件模拟），口述时说“模型实验里”，不说“引擎里实测”

统一术语指的是不要混用成
服务器权威伤害、死亡、弹药、比赛阶段、刷怪只在服务器修改，客户端只发请求“服务器同步”
本机预测拥有者先播表现、先改显示用的数值，不等服务器“客户端同步”
序号对账每次操作带递增序号，服务器回传“已处理到第几号”，显示 = 服务器值 − 未确认的部分“校正”“回滚”
状态复制持续状态（阶段、死亡、换弹中、外观）用复制变量 + RepNotify，晚加入也能看到“用组播同步”
计数器复制一次性事件（开了一枪、挨了一下）用递增计数复制，OnRep 里看增量播表现“开火组播”
移动预测冲刺、开镜等影响速度的标志随移动输入一起保存、发送、重放“冲刺 RPC”
命中容差校验PvE：客户端判命中，服务器校验射速、弹药、起点、方向、目标包围盒 + 容差、视线“客户端判定”（只说一半）

为什么不用组播同步开火 / 死亡？开火者已经预测过，组播没有“跳过拥有者”；死亡是持续状态，晚加入收不到组播。组播只用于服务器发起、一瞬间、晚加入不需要、丢了无所谓的事第 8 章 5.1
你 Demo 里的子弹是射线还是实体？实体：服务器生成的复制子弹 Actor（ProjectileMovement，200 m/s），没有射线。重构时步枪改命中扫描；慢速武器才用抛射物，且伤害只在服务器那颗子弹上结算、开火者本机放一颗不复制的假子弹K0 第 3 节

7. 讲 Demo 时最常见的六个失误
