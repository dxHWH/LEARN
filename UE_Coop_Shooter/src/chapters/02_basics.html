CHAPTER 02

只讲用得到的 UE 网络基础

四个问题：这个对象在哪几端存在？这段代码在哪一端执行？谁能调用这个 RPC？这个变量会发给谁？答清楚这四个，原 Demo 的问题就都能解释。

本章目标
  • 能画出 Listen Server 双人局里 GameMode / GameState / PlayerState / PC / Pawn / 武器 / UI 各在哪一端存在。
  • 分清 Role（权限）和 Owner（所有权），背出 RPC 可达性表。
  • 知道属性复制的四个性质：单向、只发最新值、按网络帧发、可以按条件发。

服务器权威，以及 Listen Server 的“主机也是玩家”

UE 的联机是服务器权威：世界的真实状态只在服务器上；客户端看到的是服务器复制过来的近似值，客户端想改变世界只能通过 Server RPC 请求服务器去改。双人合作最常用 Listen Server：主机进程既是服务器又有一个本地玩家；Dedicated Server 则没有本地玩家、不渲染。

面试注意：主机玩家同时满足“有权限”和“本地控制”

很多人写 if (HasAuthority()) { 服务器逻辑 } else { 本地表现 }，在 Listen Server 上主机玩家永远走不到 else，于是主机看不到自己的开火表现、UI 不刷新。“要不要播本地表现”看 IsLocallyControlled()，“要不要改游戏状态”看 HasAuthority()，两个判断互相独立。原 Demo 用了大量 SwitchHasAuthority，而几乎没用 IsLocallyControlled。

每个对象在哪几端存在

对象主机（服务器 + 玩家 1）客户端（玩家 2）放什么
GameMode有没有规则：刷怪、开局条件、胜负判定、重生。客户端拿到的是 nullptr

PlayerController两份只有自己那份输入、相机、UI、Client RPC 的落点；别人的 PC 在客户端不存在

AIController / 行为树有没有僵尸的决策只在服务器

Owner：谁能调用 Server RPC

每个 Actor 可以有一个 Owner，Owner 的 Owner……一路往上，如果最终是某个 PlayerController，这个 Actor 就“属于”那个 PC 背后的网络连接。Possess 时 Pawn 的 Owner 被设成 PC；武器的 Owner 设成 Pawn，就挂在同一条链上。

Server在服务器本地执行发到服务器执行丢弃（日志：No owning connection）
Client发到拥有者客户端执行；没有拥有者时在服务器执行在本地执行在本地执行
NetMulticast服务器 + 所有相关的客户端执行只在本地执行只在本地执行

RPC 可达性（与 Role 无关，只看调用端和 Owner 连接）。原 Demo：关卡蓝图的 Server_SetStart 由客户端调用 → 关卡脚本 Actor 不属于任何客户端连接 → 被丢弃；客户端调用的 Multicast 只在本地执行（原 Demo 的组播都由服务器调用，没有踩到这一条；它的问题是组播里做了补刷这类规则，见第 1 章）

Reliable 与 Unreliable
  • Reliable：保证到达、按顺序执行。丢包时后面的 Reliable 要等前面的重传成功（队头阻塞）；发得太快会把可靠缓冲区塞满，引擎会直接断开连接。适合低频且必须到达的事：开始 / 停止开火、换弹请求、准备就绪。
  • Unreliable：可能丢、可能被合并，Multicast 还会受相关性影响（不相关的客户端收不到）。适合高频且“丢一个无所谓”的事：开火特效、脚步声。
  • 两者共同的问题：RPC 只对当时在线且相关的客户端生效，晚加入的人收不到。持续存在的状态（是否死亡、是否在换弹、比赛阶段）必须用复制属性表示。

属性复制的四个性质

  1. 单向：只从服务器到客户端。客户端改复制变量只改了自己的副本；服务器不会因此重发，直到服务器端的值再次变化（原 Demo 在客户端写 MouseY、在多播里写 正在攻击 = false，都是这种“只改了本地”）。
  2. 只发最新值：服务器在一个网络帧里把值从 10 改成 9 再改成 8，客户端只会收到 8。所以“状态”适合复制，“事件”不适合——要用复制属性表达事件，就用一个只增不减的计数器（如 BurstCounter），客户端在 OnRep 里看增量。
  3. 按网络帧发：服务器网络 Tick 默认 30 Hz（NetServerMaxTickRate），每个 Actor 再按 NetUpdateFrequency 决定多久检查一次。本机改了变量，最快也要等到下一个网络帧才发出去（E1 中 RTT=0 时仍有约 {{v:E1[s=0,rtt=0].own:.0f}} ms 的反馈延迟，就是在等网络帧）。
  4. 可以按条件发：COND_OwnerOnly（只发给拥有者，适合弹药）、COND_SkipOwner（除了拥有者都发，适合拥有者已经本地预测过的表现计数器）、COND_InitialOnly、COND_SimulatedOnly 等。
RepNotify：蓝图和 C++ 不一样

C++ 的 ReplicatedUsing=OnRep_X 只在客户端收到新值时调用，服务器改值不会调用，需要的话手动调一次。蓝图的 RepNotify 变量在服务器上用 Set 节点赋值时，服务器自己也会调用 OnRep 函数。从蓝图迁到 C++ 时常因为这点导致主机玩家的 UI 不刷新。

一条总规则：状态用属性，瞬时事件用 RPC，表现各端本地做

本章速记
  • GameMode 只在服务器；别人的 PlayerController 在客户端不存在；跟人走的数据放 PlayerState。
  • Role 决定能不能改状态，Owner 决定能不能调 Server RPC；能否调 Server RPC 不看 Role。
  • 客户端调用 Multicast 只在本地执行；客户端调用不属于自己的 Actor 的 Server RPC 会被丢弃。
  • 复制属性：单向、只发最新值、按网络帧发、可按条件发；事件用计数器表达。
  • 主机玩家既 HasAuthority 又 IsLocallyControlled，两个判断要分开用。
自测：客户端玩家的武器在客户端上是 SimulatedProxy，为什么还能在武器上调用 Server RPC？ 能不能发 Server RPC 只看这个 Actor 的 Owner 链是否最终连到这个客户端的 PlayerController（即属于这条网络连接），与 LocalRole 无关。武器 Owner = Pawn，Pawn Owner = PC，所以可以。反过来，关卡里摆放的 Actor、僵尸、关卡蓝图都不属于任何客户端，在上面调 Server RPC 会被丢弃。
自测：为什么“死亡”不能只用一个 Reliable Multicast 通知？ RPC 只对当时相关的客户端执行一次：晚加入、或者当时因为距离不相关的客户端永远收不到，看到的僵尸会一直站着。死亡是持续状态，应该是复制属性 bIsDead（OnRep 里播倒地 / 布娃娃），或者用 TearOff() 让各端接管尸体；Multicast 最多用来补一个一次性的音效。
