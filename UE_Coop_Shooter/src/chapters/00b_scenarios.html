BRIEFING · K2

十四个功能场景：容易踩的坑 → 怎么避免 → 正确实现

面试官真正想考的不是“你的蓝图怎么连”，而是“这类需求你会怎么做”。本章把原版的每个问题当作这类需求最容易踩的坑，按功能场景讲：需求是什么、坑长什么样、为什么会踩、玩家会看到什么、怎么避免、正确的实现方法——全部用文字讲方法，不讲节点、不贴代码。

本章目标
  • 把 19 个问题归到六类根因，并分清哪些是设计取舍、不算问题，看到一个新需求时先想“它会踩哪一类”。
  • 对 14 个典型功能场景，各说出一套不依赖代码的正确实现步骤。
  • 记住一个通用落地模板（预测 → 请求 → 裁决 → 复制），能迁移到拾取、开门、技能这类没做过的需求。
30 秒版：联机功能的坑都是同一种思维造成的

单机思维默认只有一台机器、一个玩家、一条时间线。改联机时，这三个默认都不成立：有两台机器，所以要问“这段在哪端跑、谁有权改”；有两个玩家，所以不能用“0 号玩家”指代“我”；有网络延迟，所以要问“本机要不要等、别人怎么知道、晚到或丢了怎么办”。原版的坑归成六类：结果在客户端算、表现等服务器、两端各算各的、本地当全局、把状态当事件发、把时序当成必然。正确做法也只有一个套路：本机先演、服务器裁决、状态按需复制。

3. 场景 01~03：进入一局之前

场景 01联机入口：主持、加入、断线根因 F 把时序当成必然
需求

一名玩家主持，另一名通过局域网或平台加入；主机退出、断线时有明确提示，能回到主菜单。

当前做法（坑）

没有会话流程，只能在编辑器里开两个窗口联机；“按任意键开始”的主菜单是对局地图关卡蓝图里的一个界面，菜单和对局写在同一个地方，而且这段关卡逻辑在每一端各跑一份。

为什么会踩

单机游戏没有“进入一局”的概念，打开地图就是开始；联机多出了“连接、等待、断开”这些阶段，它们不属于任何一张地图。

存在的问题

主菜单和开局逻辑写在对局地图的关卡蓝图里、每一端各跑一份：客户端调用的 Server RPC 被丢弃，开局还依赖初始化时序。

对应附录 A：#15 开局标志不复制〔P1〕、#16 依赖初始化时序〔P1〕

设计取舍

没有主持 / 加入流程、只在编辑器里联机：Demo 阶段只用来自测和录屏，这是合理的范围取舍，不算问题。要打包给别人玩时才需要下面的完整做法。

怎么避免

先分清“进程级”和“对局级”：会话、断线原因这类跨地图的事属于 GameInstance（每个进程一份、切地图不销毁）；对局规则属于地图里的 GameMode / GameState。

理想实现
  1. （以下属于完整版，打包展示时再做）准备两张地图：主菜单地图（只有界面）和对局地图。
  2. GameInstance 提供四个操作：主持（创建会话，以 listen 方式打开对局地图）、查找、加入（加入会话后由引擎完成连接和换图）、离开（销毁会话、回主菜单）。
  3. GameInstance 监听网络错误和换图失败，记下原因；回到主菜单时由菜单显示一次。
  4. 服务器侧，GameMode 在玩家登录前可以拒绝（满员、已开局），在玩家断开时处理他的角色（判定阵亡或结束对局）。
面试这样说

“会话放 GameInstance，因为它跨地图存活；规则放 GameMode。原版两者都塞在关卡蓝图里，而且每一端各执行一份，这是我第一个拆掉的东西。”

场景 02大厅准备与开局根因 E 把状态当事件发 · D 本地当全局
需求

两人都确认准备后同时开局：切镜头、显示 HUD、开始计时、开始刷怪；中途进来的人也要看到正确的阶段。

当前做法（坑）

每个玩家通过自己的角色上报“我准备好了”（这一步是对的）；GameMode 把玩家控制器存进 GameState 的复制数组；人齐后 GameMode 对每个角色调一次“开始游戏”组播，每一端的关卡蓝图收到后执行开局流程；关卡蓝图里还有一个客户端调用的 Server RPC，用来写“游戏是否开始”。

为什么会踩

把“开局”当成一个瞬间的事件去广播，而它其实是一个会一直存在的状态；同时不知道玩家控制器只存在于服务器和它自己的客户端、关卡蓝图不属于任何客户端。

存在的问题

开局只靠“关卡 BeginPlay 时绑在本地角色上的委托”触发：客户端角色如果晚于关卡 BeginPlay 到达就绑不上，开局流程不执行（时序问题，PIE 里通常看不出）；组播按角色发了两次，只有本地角色那一次有人接；客户端写“游戏是否开始”的请求被直接丢弃；客户端上的准备列表全是空引用；晚加入的人永远停在“未开始”。

对应附录 A：#15 开局标志不复制〔P1〕、#16 依赖初始化时序〔P1〕、#18 复制 PC 引用〔P2〕

怎么避免

先问两句：“晚加入的人需要知道吗？”——需要，就是状态，用复制变量 + RepNotify；“谁能写？”——只有服务器。列举玩家用 PlayerState，不用 PlayerController。

理想实现
  1. “是否准备”是这个人的状态，放在 PlayerState（它复制给所有人，大厅名单直接读）。
  2. 准备按钮调用本地玩家控制器的 Server RPC；服务器确认当前还在等待阶段后才写入。
  3. GameMode 在有人准备、加入或离开时检查：人数够且全部准备 → 把 GameState 的“比赛阶段”设为进行中、写入结束时刻、启动刷怪。
  4. 各端在“比赛阶段”的 RepNotify 里切界面、镜头和音乐：每端只执行一次，晚加入的人收到初始复制时也会执行。
面试这样说

“开局是状态不是事件：GameState 复制一个阶段枚举，各端在 OnRep 里切界面。原版用按角色循环的组播加委托触发开局，依赖初始化时序，晚加入的人还收不到。”

场景 03角色、控制器、武器怎么绑定根因 F 把时序当成必然 · D 本地当全局
需求

每个玩家控制自己的角色、手里一把枪；自己看到第一人称手臂和枪；别人看到完整的身体和枪（完整版，Demo 可以只做手臂）。

当前做法（坑）

武器在服务器生成（对），但生成时没有指定持有者，之后才补设——武器的初始化早于“设持有者”执行，于是又补了一个修补函数；角色只有第一人称手臂；输入映射在初始化时通过“0 号玩家控制器”获取。

为什么会踩

单机里只有一个玩家，“0 号控制器”就是自己；“先生成、再设持有者”只隔两行，单机下看不出时序差别。

存在的问题

初始化偶发拿不到持有者；在服务器上，0 号控制器永远是主机的，所有本该作用于客户端玩家的逻辑都会作用到主机身上。

对应附录 A：#4 死者仍能操作〔P0〕、#16 依赖初始化时序〔P1〕、#23 补丁与死代码〔P3〕

设计取舍

只有第一人称手臂、别人看到漂浮的手臂：单机 FPS 改联机时的工作量妥协，不影响同步正确性，不算问题（A#17）。要给对方展示完整角色时再做下面第 3 步。

怎么避免

记住 Owner 链：武器 → 角色 → 玩家控制器 → 网络连接。它决定谁能在这个对象上发 Server RPC、“只发给拥有者”的数据发给谁。只属于某个玩家的东西，都顺着这条链找人，而不是用 0 号。

理想实现
  1. GameMode 为每个登录的玩家控制器生成角色并 Possess；Possess 会把角色的持有者设成这个控制器。
  2. 服务器在角色被 Possess 时生成武器，生成参数里就指定持有者和发起者为这个角色，再把武器写入一个复制变量（当前武器）。
  3. 各端在“当前武器”的 RepNotify 里挂接（完整版有两套模型时：一份挂到只有自己看得见的第一人称手臂，一份挂到别人看得见的第三人称身体）。挂接关系不随武器复制，必须各端自己挂。
  4. 输入映射在“成为本地控制者”时添加（控制器变化时判断是不是本地控制），不在初始化时找 0 号控制器。
  5. 分数、是否准备、是否存活放 PlayerState——角色死了会被销毁，人还在。
面试这样说

“服务器 Possess → 生成武器时就带上 Owner → 复制武器引用，各端在 OnRep 里挂 1P / 3P。Owner 链决定 RPC 能不能发出去，所以必须在生成那一刻给。”

4. 场景 04~07：一把枪

场景 04开火与命中判定根因 B 表现等服务器 · A 结果在客户端算
需求

按下就开枪，没有延迟；打中僵尸扣血，爆头伤害更高；结果不能被客户端随便改。

当前做法（坑）

本机只开一个射速计时器，每发发一条可靠的 Server RPC；服务器先组播开火动画，再检查弹药，然后生成一颗复制的子弹 Actor——没有射线检测，命中靠子弹自己碰撞；伤害写在子弹的碰撞事件里，每一端都会走到，也没有填伤害来源。

为什么会踩

单机里“播动画”和“算伤害”写在一起没有问题；改联机时只想着“让别人也看到”，就把整段搬到服务器再广播，又让复制出来的子弹自己去算伤害。

存在的问题

RTT 200 ms 时按下后约 {{v:E1[s=0,rtt=200].own:.0f}} ms 才看到自己开枪；打空了还会播一次开火动画；远端看到子弹凭空出现在几米外；客户端的子弹副本按自己的轨迹碰撞，偶尔血花和扣血对不上（伤害本身只在服务器结算——客户端那次被引擎的 Authority Only 拦下，属于碰巧没错）。

对应附录 A：#9 开火表现等组播〔P1〕、#10 空放 / 打断换弹〔P1〕、#11 逐发 Reliable〔P1〕、#2 伤害写在每端碰撞里〔P2〕、#19 伤害来源为空〔P2〕

怎么避免

把一发子弹拆成三件事分开放：表现（本机立刻做）、结果（只在服务器做）、通知（复制回去）。任何造成伤害的调用之前都先问“这里是服务器吗？”

最小修复

保留子弹 Actor：Multicast_Fire 挪到弹药检查之后，组播里跳过开火者，开火者按键时本机先播 1P 动画；伤害节点前加 Switch Has Authority，填上 Instigator / Causer。不会再空放、结果写法正确，但开火者仍要等子弹复制回来、远端子弹仍会突现。

理想实现
  1. 本机：按住时本地按射速出膛；每一发先查本地的弹药和状态，立刻播第一人称动画、枪口火焰和声音，显示弹药减一，并在本地做一次射线，得到命中的目标和部位。
  2. 把这一发的序号、起点、方向、命中目标和部位发给服务器。它会造成伤害，用可靠 RPC。
  3. 服务器校验：还活着、没在换弹、射速没超（用令牌桶，容忍丢包重传后请求扎堆到达）、还有弹药、起点离眼睛不远、方向和服务器视角夹角不大、射线确实穿过目标包围盒加容差、中间没有被墙挡住。
  4. 通过：扣弹、记下“已处理到第几号”、开火计数加一；命中则对目标施加点伤害，并填好伤害来源（开火者的控制器）和伤害物（武器）。不通过：只更新“已处理到第几号”，本机据此把多扣的弹药加回来。
  5. 如果是 PvP：把“相信客户端命中 + 容差”换成“服务器按开火时刻回溯目标位置再判定”，并限制最大回溯时间。
面试这样说

“本机先演、服务器裁决、状态回传。客户端只报‘我打了哪’，伤害只在服务器发生；PvE 用容差校验，PvP 用回溯。原版没有射线，是服务器生成复制子弹：表现全等服务器组播，伤害写在每一端都会触发的子弹碰撞里——位置都放错了。”

场景 05别人看到的开枪、子弹和弹孔根因 A 结果在客户端算
需求

队友能看到我开枪的动作、枪口火焰和曳光；僵尸被打中有血花。

当前做法（坑）

每发子弹生成一个复制的子弹 Actor（带移动复制，速度 200 m/s，寿命 1 秒），别人靠它看到子弹；弹孔和伤害都写在子弹的碰撞事件里。

为什么会踩

单机里用一颗“真子弹”最直观；改联机时以为“子弹复制了，大家就都看到了”。

存在的问题

远端看到子弹时，它已经飞出约 {{v:E1[s=0,rtt=200].pop:.1f}} m，像是凭空出现；每秒网络消息量约 {{v:E7.0.4}} B（推荐方案约 {{v:E7.1.4}} B，量级估算）；再加上每一端都在子弹碰撞时扣血。

对应附录 A：#12 每发一个复制子弹〔P1〕、#2 伤害写在每端碰撞里〔P2〕

怎么避免

按武器类型选方案：命中扫描武器（步枪）不需要子弹实体，只需要同步“开了一枪”和“打中了谁”；只有真正有飞行时间的抛射物才需要服务器生成实体。

最小修复

生成子弹时填 Owner / Instigator；客户端上的子弹副本只播弹孔和血花，不参与任何结算。射速不高时可以接受，带宽和“远端子弹突现”问题仍在。

理想实现
  1. 步枪不生成子弹 Actor。服务器每接受一发，把武器上的“开火计数”加一；这个计数只复制给开火者以外的人（开火者已经自己播过了）。
  2. 其他端在计数变化时播第三人称开火动画、枪口火焰、声音，并沿枪口方向在本地画一条曳光。
  3. 僵尸身上的血花和受击由僵尸的“最近一次被击中”复制信息驱动（场景 08），所有端一致；打在墙上的弹孔只在开火者本地生成——这是有意的取舍，队友少看到几个弹孔不影响玩法。
  4. 火箭、榴弹这类抛射物：服务器生成复制的弹体，结果以它为准；开火者本地先放一颗不复制的“假弹”，掩盖往返延迟；服务器按射手延迟快进真弹并设上限，命中只认真弹（完整做法见第 5B 章）。
面试这样说

“命中扫描武器只同步‘开了几枪’和‘打中谁’，曳光和弹孔各端本地画；抛射物才由服务器生成，开火者本地放假弹。”

场景 06弹药显示根因：“复制 = 同步”的误解
需求

开枪时弹药数字立刻变、不往回跳；弹药只有自己需要知道。

当前做法（坑）

当前弹量、弹匣容量、备弹、换弹中等 5 个变量全部无条件复制给所有人；只在服务器扣弹；HUD 每帧去读复制下来的值。

为什么会踩

以为“勾上复制就同步了”，没有问“谁需要它”“本机是不是已经知道了”。

存在的问题

数字整体晚一个往返才变；如果改成本机先扣、再被服务器值覆盖，连射时数字会往回跳（模型实验：平均每次连射回跳 {{v:E5.1.rb:.2f}} 次）；别人的弹药白占带宽，还能被外挂读到。

对应附录 A：#20 弹药广播给所有人〔P2〕、#10 空放 / 打断换弹〔P1〕

怎么避免

每个复制变量都回答两个问题：发给谁（复制条件）、本机预测过没有（预测过就要对账，不能直接覆盖）。

理想实现
  1. （精简版）弹药变量的复制条件改成 Owner Only，只发给持枪者。
  2. （完整版，以下三步）弹药做成一个结构：弹匣数、备弹、服务器已处理的开火序号、换弹次数；只复制给持枪者自己。
  3. 本机每开一发，本地序号加一；显示值 = 服务器弹匣数 −（本地序号 − 服务器已处理序号）。
  4. 收到复制时不覆盖显示值，只按上式重新算；被服务器拒绝的那几发会自然“加回来”。
  5. HUD 订阅“弹药变化”事件，变化时才刷新。
面试这样说

“弹药 Owner Only，带已处理序号对账：显示 = 服务器弹数 − 未确认发数，数字单调变化，模型实验里回跳 {{v:E5.2.rb:.0f}} 次。”

场景 07换弹根因 B 表现等服务器 · E 把状态当事件发
需求

按下换弹立刻播动画；时间到弹药正确转移；中途被打死或打断不丢子弹；换弹时不能开枪。

当前做法（坑）

服务器一开始就把当前弹量存进临时变量并清零，组播换弹动画，等待一段固定时长，再调用一个“剩余子弹计算”函数；这个函数在“备弹不够补满”的分支没有走到返回节点，于是返回 0；等待用的是不能取消的延迟。

为什么会踩

把换弹写成一段顺序脚本，而不是一个可以被打断的状态；蓝图函数没走到返回节点时输出是默认值——这一条单机下就会错，只是联机后 UI 本来就跳，把它掩盖了。

存在的问题

弹匣 3、备弹 7 时换弹，换完变成 0 / 0；一局打空再换只能打出 {{v:E4.session.0.2}} / 40 发；动画要等一个往返才开始；换弹中途死亡，已经清零的子弹就没了。

对应附录 A：#1 换弹吞弹匣〔P0〕、#10 空放 / 打断换弹〔P1〕

怎么避免

规则只在“结束那一刻”一次性结算，过程中不碰数据；所有等待都必须可以取消；关键计算写成能单独测试的规则——这个 bug 就是把蓝图逐节点移植出来测试时发现的。

最小修复

补上“剩余子弹计算”false 分支的返回节点，并改成到点才改弹药、一次性 take = min(空位, 备弹)（不先清零）；Delay 换成可取消的计时器。

理想实现
  1. 本机：条件满足（有备弹、弹匣没满、没在换弹、活着）就立刻播第一人称换弹动画，标记“本地换弹中”，发换弹请求。
  2. 服务器：再校验一次，设置“正在换弹”（只复制给别人，用来播第三人称动画），按武器数据里的换弹时长开一个可取消的计时器。
  3. 计时器到点：一次性算转移量 = min(弹匣空位, 备弹)，弹匣加、备弹减，清除“正在换弹”。
  4. 被打断（死亡、切枪、请求被拒）：清计时器、清状态，弹药一发不动，并通知拥有者停掉本地动画。
  5. 换弹期间服务器拒绝开火请求，本机也不发。
面试这样说

“换弹是服务器上的一个小状态机：开始 → 计时 → 一次性 take = min(空位, 备弹) → 复位，打断不动弹药。原版先清零再算、还漏连了返回节点，备弹不够时吞掉整个弹匣。”

5. 场景 08~09：伤害、死亡与胜负

场景 08僵尸受伤、受击与死亡根因 A 结果在客户端算 · E 把状态当事件发
需求

僵尸被打扣血、有受击动作和血花；血量归零倒地、停止攻击，过一会儿消失并补刷；两个人看到的结果一样（血量、倒地、补刷）。

当前做法（坑）

伤害写在每一端都会触发的子弹碰撞里（客户端那次被引擎拦下，僵尸实际只在服务器扣血）；受击和死亡都用组播，组播里各端各自随机挑受击动作；死亡组播里清除了一个名字写错的计时器，找目标和攻击检测还在跑；补刷调用在每一端执行，而且绕过了权限判断。

为什么会踩

把“死亡”当成一个瞬间广播，把规则（停 AI、补刷）和表现（布娃娃）写进同一个组播。

存在的问题

倒地的僵尸几秒内还能打人；客户端刷出只有自己看得到的僵尸；晚加入的人看不到尸体。

对应附录 A：#2 伤害写在每端碰撞里〔P2〕、#3 补刷每端执行〔P0〕、#14 死后计时器还在跑〔P1〕

设计取舍

同一刀两端看到的受击动作不同：受击动作是纯表现，伤害判定只在服务器，不影响结果，属于可接受的差异（A#22）。

怎么避免

规则和表现分开：规则只在服务器执行一次；表现由复制下来的状态在各端驱动。需要各端一致的随机结果由服务器决定一次，再复制出去。

最小修复

把补刷和清计时器从 Multicast_Death 里挪出来，只在服务器执行（清掉这个对象的全部计时器）。

理想实现
  1. 血量做成一个组件，玩家和僵尸共用；伤害事件只在服务器上绑定，只有服务器扣血。
  2. 组件复制三样东西：血量；“最近一次被击中”（递增计数 + 命中点 + 是否爆头，计数保证连续两次一样的命中也能触发）；是否死亡。
  3. 各端在“最近一次被击中”的 RepNotify 里播受击动作和血花，部位由服务器给（完整版：动作也由服务器选，各端一致）；在“是否死亡”的 RepNotify 里开布娃娃、关碰撞——晚加入的人也会看到尸体。
  4. 服务器判定死亡时：停 AI、清掉这个对象的全部计时器、通知 GameMode（给击杀者加分、按上限补刷）、设置寿命自动销毁。
  5. 一次性的惨叫用服务器调用的不可靠组播：晚加入不需要，丢了也无所谓。
面试这样说

“伤害只在服务器；受击和死亡是复制状态，各端在 OnRep 里播表现；停 AI、补刷这类规则只在服务器做一次。尸体是状态，惨叫是事件。”

场景 09玩家死亡与胜负根因 D 本地当全局 · E 把状态当事件发
需求

撑到时间结束胜利；有人阵亡时按规则结算——原 Demo 是“任一人阵亡即失败”（玩法设计），也可以改成“全灭才失败、死者观战队友”；两端结算一致，死者不能再操作。

当前做法（坑）

玩家受伤在服务器结算（对）；但死亡时在服务器上用“0 号控制器”禁用输入、播 2D 惨叫；随后组播“死亡”，每一端弹出失败界面并暂停；倒计时由每一端的 HUD 自己数，数到 0 时在本地暂停并弹出胜利。

为什么会踩

单机里玩家死了游戏就结束；“0 号控制器”就是自己；在 HUD 里数倒计时最省事。

存在的问题

客户端玩家死后仍能移动和开火（服务器上传入的不是它自己的控制器，引擎只记一条错误日志，而且服务器本来就管不到客户端的输入），惨叫却在主机那边响；两端倒计时可能差一两秒，各自判胜。

对应附录 A：#4 死者仍能操作〔P0〕、#6 倒计时各端自算〔P0〕

设计取舍

任一人阵亡两人一起失败是玩法规则，不是 bug（A#7）。可以改进的只是写法：失败判定写在角色的死亡组播里，规则不在 GameMode。

怎么避免

胜负是规则，只能由 GameMode 判定一次；时间是全局状态，放 GameState；“禁用输入”是拥有者本地的事，服务器能做的是拒绝它的请求。

最小修复

保留“任一人阵亡即失败”的规则：失败判定挪到服务器（GameMode）后广播一次结算；死者的输入和惨叫改在他自己的客户端上执行（发给本人的 Client RPC）。

理想实现
  1. 死亡时服务器设置“是否死亡”（复制变量），停掉他的武器，通知 GameMode（完整版用血量组件，并在 PlayerState 里记“是否存活”）。
  2. GameMode 按规则判定：任一人阵亡即失败（原 Demo 的规则）→ 直接把比赛阶段设为“失败”；全灭才失败（规则变体）→ 还有活着的玩家时让阵亡者观战队友（发给单个客户端的 Client RPC），全部阵亡才设为“失败”。
  3. 开局时 GameMode 把“结束时刻”写进 GameState；各端显示剩余时间 = 结束时刻 − 估算的服务器时间；时间到由服务器计时器触发，阶段设为“胜利”。
  4. 各端在比赛阶段的 RepNotify 里显示结算界面；阵亡者自己的客户端在“是否死亡”的 RepNotify 里关本地输入、播死亡镜头和音效。
  5. 服务器在每个请求里校验“是否存活”：就算客户端没关输入，也打不出伤害。
面试这样说

“胜负由 GameMode 判、GameState 广播——不管规则是一人阵亡即失败还是全灭才失败；倒计时复制‘结束时刻’，不是每秒同步剩余秒数；死亡后服务器拒绝请求，拥有者本地关输入。”

6. 场景 10~12：移动、手感与僵尸

场景 10冲刺、开镜与移动根因 C 两端各算各的
需求

按住冲刺加速、开镜减速；弱网下角色不被拉回。

当前做法（坑）

冲刺标志通过 Server RPC 只在服务器设置，也不复制；开镜标志只在本机的动画蓝图里设置；两端每帧各自根据自己看到的标志算最大速度。

为什么会踩

以为“服务器改了速度，客户端自然跟着跑”。实际上角色移动是客户端先预测、服务器用同样的输入重放、误差大就纠正，两端算出来的速度不一样，就一定会被纠正。

存在的问题

冲刺时一顿一顿地被拉回（模型实验：冲刺只在服务器生效时每秒纠正 {{v:E6[c=0,rtt=100].cps:.1f}} 次，平均拉回 {{v:E6[c=0,rtt=100].avg:.1f}} cm）；开镜时客户端减速而服务器不减，同样被纠正。

对应附录 A：#5 冲刺 / 开镜两端不一致〔P0〕

怎么避免

一条原则：所有影响移动结果的状态，都必须和移动输入走同一条路，在同一帧被两端看到。另发一个 RPC，时序永远对不齐。

最小修复

按键时本机和服务器同时切换冲刺 / 开镜标志，两端用同一个函数算速度；不丢包时不再被纠正。

理想实现
  1. 把冲刺、开镜当作移动输入的一部分：本机每帧把这两个标志和移动一起保存、一起发给服务器；服务器重放每一帧时用那一帧的标志。在 UE 里这是给 CharacterMovement 的“保存的移动”加标志位，需要一个约 60 行的 C++ 移动组件子类。
  2. 两端用同一个规则算最大速度（读这两个标志）。
  3. 开镜姿势要给别人看：服务器从移动数据里得到开镜标志后，写入一个“跳过拥有者”的复制变量，其他端的动画读它。
  4. 纯蓝图的次优解：按键时本机和服务器同时切换，两端用同一个函数算速度。不丢包时不纠正，丢包时仍会偶发（模型实验：10% 丢包每秒 {{v:E6[c=2,rtt=200,loss=0.1].cps:.2f}} 次）。面试时要主动说出这个局限。
面试这样说

“影响速度的状态必须进移动预测，和输入同帧、同路；另发 RPC 时序对不上就会被拉回。纯蓝图做不彻底，这是整个项目里唯一必须用 C++ 的地方。”

场景 11后坐力与散布根因 B 表现等服务器 · C 两端各算各的
需求

连射时镜头上跳；腰射散布大、开镜散布小；主机和客户端的手感一样。

当前做法（坑）

后坐力曲线在服务器上播放，并对角色的控制器加镜头输入；散布读的是服务器上动画蓝图里的“是否瞄准”——而开镜只在本机设置，服务器上它永远是否。

为什么会踩

单机里“谁来执行”都一样；联机后，只有本地控制的控制器才会响应镜头输入。

存在的问题

主机有后坐力，客户端玩家没有；客户端开了镜，散布仍按腰射算。

对应附录 A：#13 后坐力 / 散布〔P1〕

怎么避免

区分“手感”和“结果”：镜头上跳是拥有者本地的手感；散布影响打不打得中，是结果，必须能被服务器复现。

理想实现
  1. 后坐力在拥有者本地、播开火表现的那一步加到本地控制器上。
  2. 散布由本机根据本地状态（是否开镜、是否移动）算出范围，用这一发的序号做随机种子得到偏移，序号随请求发给服务器。
  3. 服务器用同一个序号、同一套规则，以及自己知道的状态（开镜标志来自移动数据）复现散布范围，用来校验上报的方向是否合理。
面试这样说

“后坐力是本地手感，在拥有者本机加；散布是结果，用序号做种子，服务器能复现、能校验。”

场景 12僵尸 AI、刷怪与外观根因 A 结果在客户端算
需求

僵尸追最近的玩家、靠近就攻击；同时保持 10 只，死一只补一只；每只的外观、速度、攻击动作有变化（各端画面是否必须一致，由设计决定）。

当前做法（坑）

AI 用计时器加简单寻路、只在服务器跑（对）；但找目标时会把已经死掉的玩家当目标；速度和动画变体只在服务器随机，客户端用默认值；攻击动作在组播里各端各自随机，攻击结束时各端都去写“正在攻击”这个复制变量；刷怪器的补刷在每一端执行。

为什么会踩

单机里随机一次就是“事实”；联机后要么每端各随机一次，要么只在一端随机却没告诉别人。

存在的问题

客户端上多出只有自己看得到的僵尸。

对应附录 A：#3 补刷每端执行〔P0〕

设计取舍

主机上是冲刺僵尸、客户端上同一只用普通跑姿，同一次攻击两端挥的不是同一只手：速度由服务器设置并随移动复制，各端一致，差别只在动画，属于不影响判定的表现差异（A#21、A#22）。找目标时把已阵亡玩家算进去，在“任一人阵亡即失败”的规则下不会发生影响。这些都不算问题。

怎么避免

每个随机结果都问：它是规则还是表现？谁决定？别人怎么知道？——影响判定的（伤害、命中、掉落）由服务器决定；只影响表现的，各端不一致可以接受，要求画面一致时再把结果或种子复制出去。

理想实现
  1. （完整版；原 Demo 的计时器 AI 在服务器运行也可以）AI 控制器和行为树只在服务器存在：服务节点选目标（规则改成全灭才失败时，过滤 PlayerState 里已阵亡的玩家），任务节点追击、攻击；攻击判定只在服务器。
  2. 刷怪归 GameMode：开局按上限在刷怪点生成；僵尸死亡时由 GameMode 决定是否补刷。
  3. （可选，要求画面一致时）外观变体：服务器生成时决定一个随机种子，复制条件为“只在首次复制时发送”；各端用同一个种子、按相同顺序抽取速度档位和待机 / 移动动画。
  4. （可选，同上）攻击动作：服务器每次攻击时选好动作编号，和一个递增计数一起复制，各端播同一个动作；“正在攻击”只在服务器维护。
面试这样说

“AI 和刷怪只在服务器——原 Demo 的计时器 AI 本来就在服务器，问题只出在补刷；外观和动作各端随机是表现差异，可以接受，要求一致时外观复制种子（Initial Only）、攻击复制‘计数 + 动作编号’。”

7. 场景 13~14：整局流程与界面

场景 13计时、暂停、重开与离开根因 D 本地当全局
需求

显示剩余时间；能打开暂停菜单；结算后可以再来一局或退出。

当前做法（坑）

倒计时在各端 HUD 里自己数；暂停调用“暂停游戏”；重开用本地“打开关卡”；退出直接关闭程序。

为什么会踩

这些全是单机的标准写法。

存在的问题

客户端按暂停没反应，主机按暂停冻结所有人；任何一方点“重开”就断开了联机，各自回到一张单机地图；两端倒计时不一致。

对应附录 A：#6 倒计时各端自算〔P0〕、#8 本地暂停 / 重开〔P0〕

怎么避免

联机里“世界”只有一个，在服务器上。任何改变世界的操作（暂停、换图）只能由服务器发起；本地只能改自己的界面和输入。

最小修复

暂停只打开菜单、不调用 SetGamePaused；重开改由服务器执行 servertravel；倒计时由服务器计时，到点广播一次结算。

理想实现
  1. 计时：同场景 09，GameState 复制“结束时刻”，各端自己算显示。
  2. 暂停：联机下不暂停世界，只打开本地菜单、切换到界面输入模式。真要全员暂停（比如剧情），由服务器发起并同步给所有人。
  3. 重开：只允许主机请求（服务器判断请求者是不是本地玩家），服务器用“服务器换图”让所有客户端一起进入新的一局。
  4. 离开：销毁会话、回主菜单；服务器在玩家断开时由 GameMode 处理。主机离开就是对局结束，客户端收到网络错误，回主菜单并提示原因。
面试这样说

“暂停和换图都是改世界，只有服务器能做，客户端只开自己的菜单。重开用 ServerTravel，不用 OpenLevel。”

场景 14HUD 与界面根因 D 本地当全局 · F 把时序当成必然
需求

显示血量、弹药、剩余时间、僵尸数、命中提示、大厅名单、结算统计。

当前做法（坑）

血条、弹药、颜色都用 UMG 的属性绑定函数，每帧通过“0 号玩家角色”取数据，再读武器上的复制变量；界面由关卡蓝图和角色各自创建。

为什么会踩

属性绑定是单机教程里最常见的写法；“0 号玩家”在单机下就是自己；单机里武器总是在界面之前就存在。

存在的问题

每帧类型转换白白消耗性能；客户端上武器还没复制到时访问空引用报错；在主机上读到的“0 号角色”不一定是想要的那个。

对应附录 A：#16 依赖初始化时序〔P1〕

怎么避免

界面只在本机、只读不算；数据从本地控制器和它控制的角色来，变化时才刷新；要处理“东西还没到”的情况。

理想实现
  1. 由本地玩家控制器在开始时创建界面；服务器上代表远端玩家的控制器不创建。
  2. 角色成为本地控制时把自己交给 HUD；HUD 订阅血量组件和武器的“变化”事件（这些事件在 RepNotify 里广播），只在变化时刷新；武器换了就重新订阅。
  3. 剩余时间、僵尸数从 GameState 读，每秒刷新几次就够。
  4. 按钮不能直接发 RPC（界面不是 Actor，没有网络连接），一律通过本地玩家控制器的 Server RPC 发请求。
面试这样说

“UI 在本机、只读、事件驱动；请求统一经 PlayerController 发出。原版的属性绑定每帧取 0 号玩家，既浪费又会在武器还没复制到时报空引用。”

8. 通用落地模板：没做过的需求也能这样答

十四个场景里，凡是“玩家发起的操作”（开火、换弹、准备、重开），结构都一样。面试官换一个你没做过的需求（拾取道具、开门、放技能），就套这个模板答。

模板的三个例外
  • 移动：CharacterMovement 已经内置了预测、重放和纠正，要做的是扩展它（把状态塞进它的输入），而不是另写一套 RPC（场景 10）。
  • 服务器自己发起的事（AI、刷怪、计时、胜负）：没有第 ①② 步，直接从第 ③ 步开始（场景 08、09、12）。
  • 需要多人一致同意的事（全员准备、投票重开）：第 ③ 步要收集多个请求，状态放在 PlayerState，由 GameMode 汇总判断（场景 02）。

表 K2-2　七问自查。面试官问“你怎么保证联机功能没问题”时，按这七条说，比说“我测了很多遍”有说服力

本章速记
  • 六类根因：结果在客户端算、表现等服务器、两端各算各的、本地当全局、把状态当事件发、把时序当成必然。
  • 一发子弹三件事：表现（本机立刻）、结果（只在服务器）、通知（按谁需要复制）。
  • 持续状态 → 复制变量 + RepNotify；一次性事件 → 计数器或不可靠组播；影响判定的随机 → 服务器决定；只影响表现的随机，各端不同可以接受。
  • 影响移动的状态必须进移动预测；改世界的事（暂停、换图）只有服务器能做；UI 只读、请求经 PlayerController。
  • 没做过的需求套模板：预测 → 请求 → 裁决 → 复制。
自测：面试官问“如果要做一个联机的拾取道具，你怎么做？” 套模板：① 玩家按交互键，本机先播拾取动作（道具先不隐藏，或只做半透明，避免被拒后“消失又出现”）；② 通过自己的角色发 Server RPC，带上道具引用；③ 服务器校验：道具还在、距离够近、背包有空位、玩家活着；通过后把道具加进背包（背包只复制给拥有者），销毁地上的道具（销毁会复制给所有人）；④ 拥有者的背包 RepNotify 刷新界面，其他人看到道具消失。两人同时捡同一个时，服务器先处理的那个成功，另一个被拒，本机把预测的动作收回——这就是“结果只在服务器产生”的好处。
自测：面试官问“做一扇两个人都能开的门，要注意什么？” 门不属于任何客户端，不能在门上发 Server RPC（会被丢弃，日志提示没有拥有连接——原版关卡蓝图的问题一模一样）；请求要从玩家自己的角色或控制器发出，服务器校验距离后改门的“开 / 关”复制变量；各端在 RepNotify 里播开门动画，晚加入的人看到的门也是开着的。如果门的开合会挡路、影响移动，还要让门的碰撞以服务器为准。
