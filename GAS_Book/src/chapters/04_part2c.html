CHAPTER 08

GameplayAbility：技能的生命周期

GE 是"改什么"，GA 是"做什么"。本章讲 GA 从授予到结束的完整生命周期、Tag 规则、消耗与冷却，以及决定联网行为的四个策略。

8.1 生命周期全图

⚠️ 坑点：忘记 EndAbility

技能不会自动结束。如果某个分支（例如 Montage 被打断的回调）没有调用 EndAbility，技能会一直处于激活状态：ActivationOwnedTags 不会移除，InstancedPerActor 技能也无法再次激活，表现为"技能按了没反应"。每个 Task 的每个出口回调（Completed / Interrupted / Cancelled）都要检查是否需要结束技能。

8.2 Tag 规则：十个字段

GA 上有十个 Tag 容器，组合起来可以描述几乎所有"技能之间能否并存"的规则：

字段作用对象含义例子（冲锋斩）
AssetTags（老名 AbilityTags）本技能技能自己的身份标签Ability.Hero.Q、Ability.Type.Dash
CancelAbilitiesWithTag其他技能激活时打断正在运行、带这些 Tag 的技能Ability.Type.Channel（打断自己的引导技能）
BlockAbilitiesWithTag其他技能运行期间阻止带这些 Tag 的技能激活Ability.Type.Attack（冲刺中不能普攻）
ActivationOwnedTags拥有者运行期间给自己加上这些 TagState.Dashing
ActivationRequiredTags拥有者拥有者必须有这些 Tag 才能激活（变身后才能用的技能填 State.Transformed）
ActivationBlockedTags拥有者拥有者有这些 Tag 时不能激活State.Debuff.Stun、State.Debuff.Root、State.Dead
Source/Target Required/Blocked来源 / 目标由事件或 TargetData 激活时，检查来源和目标的 Tag（"只能对敌方英雄释放"）
✅ 实践建议：Block 与 ActivationBlockedTags 的区别

BlockAbilitiesWithTag 是技能之间的互斥（通过 ASC 的 BlockedAbilityTags 计数实现）；ActivationBlockedTags 检查的是角色状态。"眩晕时所有技能都不能放"有两种做法：①所有技能的 ActivationBlockedTags 都填 Stun；②眩晕 GE 加一个 BlockAbilityTagsGameplayEffectComponent，阻止 Ability 根 Tag 下的所有技能。②只需改一处，更好维护。别忘了还要打断正在运行的技能（见 4.4 的 Tag 监听示例）。

8.3 消耗与冷却

在 GA 上配置 CostGameplayEffectClass 和 CooldownGameplayEffectClass：

  • Cost GE：Instant，Modifier 为 Mana AddBase −30。CheckCost 会模拟施加，判断属性是否会小于 0。
  • Cooldown GE：HasDuration，必须通过 TargetTags 组件授予一个冷却 Tag（例如 Cooldown.Hero.Q）。CheckCooldown 只检查拥有者身上是否有这个 Tag。
  • 在 ActivateAbility 中调用 CommitAbility()，并检查返回值：激活之后，资源可能已经被其他效果改变。

默认做法要求每个技能各配一个冷却 GE，技能多了很难维护。常见的做法是所有技能共用一个冷却 GE，冷却时长和冷却 Tag 在运行时注入：

// 头文件中： // UPROPERTY(EditDefaultsOnly, Category="Cooldown") FScalableFloat CooldownDuration; // 按技能等级取值 // UPROPERTY(EditDefaultsOnly, Category="Cooldown") FGameplayTagContainer CooldownTags; // 例如 Cooldown.Hero.Q // UPROPERTY(Transient) FGameplayTagContainer TempCooldownTags; const FGameplayTagContainer* UMyGameplayAbility::GetCooldownTags() const { // CheckCooldown 用它来判断是否处于冷却中 FGameplayTagContainer* Mutable = const_cast(&TempCooldownTags); Mutable->Reset(); if (const FGameplayTagContainer* Parent = Super::GetCooldownTags()) { Mutable->AppendTags(*Parent); } Mutable->AppendTags(CooldownTags); return Mutable; } void UMyGameplayAbility::ApplyCooldown(const FGameplayAbilitySpecHandle Handle, const FGameplayAbilityActorInfo* ActorInfo, const FGameplayAbilityActivationInfo ActivationInfo) const { if (UGameplayEffect* CooldownGE = GetCooldownGameplayEffect()) // 共用的 GE_Cooldown（时长使用 MMC_Cooldown） { FGameplayEffectSpecHandle Spec = MakeOutgoingGameplayEffectSpec(CooldownGE->GetClass(), GetAbilityLevel()); Spec.Data->DynamicGrantedTags.AppendTags(CooldownTags); // 动态授予本技能的冷却 Tag Spec.Data->SetSetByCallerMagnitude(MyTags::SetByCaller_Cooldown, CooldownDuration.GetValueAtLevel(GetAbilityLevel())); ApplyGameplayEffectSpecToOwner(Handle, ActorInfo, ActivationInfo, Spec); // 会带上预测键 } }
🕒 版本差异

FGameplayEffectSpec::DynamicGrantedTags 在 5.3 之后仍然可用，但引擎更推荐通过 Spec.AddDynamicGrantedTag() 之类的接口访问（不同小版本的接口名有差异，以头文件为准）。思路不变：同一个 GE，在运行时授予不同的 Tag。

即使设置了 ReplicateYes，GA 实例也只存在于服务器和拥有者客户端。其他客户端（模拟端）上没有技能实例，它们看到的动画来自 Montage 复制，特效来自 Cue，状态来自 Tag。这一点决定了第三部分的很多设计。

🔬 深入源码：CommitAbility 做了什么

CommitAbility = CommitCheck（再次检查冷却和消耗，因为激活之后状态可能已经变化）+ CommitExecute（调用 ApplyCooldown 和 ApplyCost）。你也可以分开调用 CommitAbilityCost 和 CommitAbilityCooldown，例如"引导技能开始时扣蓝，结束后才进入冷却"。EndAbility 和 CancelAbility 都不会自动提交。

本章小结
  • 生命周期：Give → TryActivate → CanActivate → PreActivate → ActivateAbility → Commit → Tasks → End / Cancel。每个出口都必须调用 EndAbility。
  • 十个 Tag 字段描述技能之间以及技能与角色状态之间的互斥关系，眩晕、沉默等控制效果都通过它们实现。
  • 消耗和冷却都是 GE；冷却通过 Tag 判断，常见做法是所有技能共用一个冷却 GE，在运行时注入时长和 Tag。
  • 默认使用 InstancedPerActor + LocalPredicted + ReplicateNo。
CHAPTER 09

AbilityTask 与 TargetData：技能中的异步

技能几乎都要"等待"：等动画、等出手帧、等玩家松手、等选择目标。AbilityTask 就是 GAS 用来处理这些等待的工具。

9.1 Task 是技能里的 await

与普通的计时器或委托相比，Task 有三点好处：①生命周期与技能绑定，技能结束时自动清理；②与预测系统集成，部分 Task 会在回调时开启新的预测窗口；③在蓝图中显示为带多个输出引脚的异步节点，策划也能看懂。

9.2 常用的内置 Task

Task作用网络说明
PlayMontageAndWait播放 Montage，等待完成 / 中断 / BlendOut通过 ASC 的 RepAnimMontageInfo 复制给模拟端
WaitGameplayEvent等待发给自己的 GameplayEvent两端各自等待；事件一般来自两端都会执行的 AnimNotify
WaitTargetData生成 TargetActor 让玩家选择目标客户端产生的 TargetData 通过 RPC 发给服务器
WaitInputPress / WaitInputRelease等待再次按下或松开激活键客户端回调时会开启新的预测窗口，并把输入事件同步给服务器
WaitGameplayTagAdded / Removed等待自身 Tag 变化两端独立判断
WaitAttributeChange等待属性变化客户端以复制值为准
WaitDelay延时两端各自计时
ApplyRootMotionConstantForce 等Root Motion 位移（冲刺、击退）接入 CharacterMovement 的移动预测，详见 13.3
WaitNetSync两端互相等待对方执行到同一位置会增加一个往返的延迟，按需使用
WaitConfirmCancel等待确认或取消输入配合 TargetData 使用

9.3 自定义 Task：蓄力

DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam(FChargeDelegate, float, ChargeRatio); UCLASS() class UAbilityTask_Charge : public UAbilityTask { GENERATED_BODY() public: UPROPERTY(BlueprintAssignable) FChargeDelegate OnProgress; // 每帧回调：蓄力进度 0~1 UPROPERTY(BlueprintAssignable) FChargeDelegate OnFullyCharged; // 蓝图节点工厂函数：DefaultToSelf/HidePin 让蓝图里不显示 OwningAbility 引脚 UFUNCTION(BlueprintCallable, Category = "Ability|Tasks", meta = (HidePin = "OwningAbility", DefaultToSelf = "OwningAbility", BlueprintInternalUseOnly = "true")) static UAbilityTask_Charge* WaitCharge(UGameplayAbility* OwningAbility, float MaxChargeTime); virtual void Activate() override; virtual void TickTask(float DeltaTime) override; private: float MaxTime = 1.f; float Elapsed = 0.f; }; UAbilityTask_Charge* UAbilityTask_Charge::WaitCharge(UGameplayAbility* OwningAbility, float MaxChargeTime) { UAbilityTask_Charge* Task = NewAbilityTask(OwningAbility); Task->MaxTime = FMath::Max(0.01f, MaxChargeTime); Task->bTickingTask = true; // 需要每帧 Tick return Task; } void UAbilityTask_Charge::Activate() { Elapsed = 0.f; } void UAbilityTask_Charge::TickTask(float DeltaTime) { Super::TickTask(DeltaTime); Elapsed += DeltaTime; const float Ratio = FMath::Min(Elapsed / MaxTime, 1.f); // 技能可能已经结束：这里统一检查后再广播 if (ShouldBroadcastAbilityTaskDelegates()) { OnProgress.Broadcast(Ratio); } if (Ratio >= 1.f) { if (ShouldBroadcastAbilityTaskDelegates()) { OnFullyCharged.Broadcast(1.f); } EndTask(); } }
⚠️ 坑点
  • 在 C++ 中创建 Task 后必须调用 ReadyForActivation()，否则 Activate 不会执行（蓝图节点会自动调用）。
  • 广播委托之前检查 ShouldBroadcastAbilityTaskDelegates()，避免技能结束后回调还在执行。
  • "按住蓄力、松手释放"应该组合使用 WaitInputRelease 和这个 Task。松手的时机由 WaitInputRelease 同步给服务器，不要在 Task 里自己读取输入。

9.4 TargetData：技能的"选择目标"

FGameplayAbilityTargetDataHandle 是一个可复制的多态容器，里面可以装命中结果（FGameplayAbilityTargetData_SingleTargetHit）、Actor 列表（_ActorArray）、位置信息（_LocationInfo），也可以装自定义结构体。它主要解决一个问题：目标只有客户端最清楚（玩家的准星、点击的位置），但结算必须在服务器进行。

ConfirmationType含义
Instant立即生成 TargetData（射线检测、自身周围范围）
UserConfirmed等待玩家确认（地面指示器 → 点击释放）
Custom / CustomMulti由 TargetActor 自己决定何时产出（例如可以多次产出的锁定类技能）
✅ 实践建议

内置的 AGameplayAbilityTargetActor 体系比较笨重（每次都要生成 Actor）。射击类游戏可以参考 Lyra 的 LyraGameplayAbility_RangedWeapon：客户端自己做射线检测，打包成 TargetData，通过 ServerSetReplicatedTargetData 发给服务器，服务器校验后再结算。完整流程见 13.4。

本章小结
  • Task 是技能里的异步步骤，生命周期与技能绑定，并且与预测系统集成。
  • 自定义 Task 的要点：工厂函数用 NewAbilityTask 创建，需要 Tick 时设置 bTickingTask，广播前检查，结束时调用 EndTask。
  • TargetData 把"客户端选择的目标"安全地交给服务器结算。
CHAPTER 10

GameplayCue：逻辑与表现分离

特效、音效、震屏、受击闪白都属于表现。Cue 让表现资源和逻辑代码完全解耦，并提供了一套省带宽、可预测的同步方式。

10.1 工作原理

Cue 通过 Tag 路由：所有 Cue Tag 必须以 GameplayCue. 开头。UGameplayCueManager 在启动时扫描配置的目录，建立"Tag → Notify 类"的映射表。逻辑层只需要说"触发 GameplayCue.Hero.Q.Hit"，不需要知道具体播放什么粒子或音效。

[/Script/GameplayAbilities.AbilitySystemGlobals] ; 只扫描这些目录，能明显缩短启动时间 +GameplayCueNotifyPaths="/Game/GAS/Cues"

10.2 四种事件

✅ 实践建议

循环特效放在 WhileActive 中启动，而不是 OnActive。否则后加入游戏或者刚进入视野的玩家，看不到已经在燃烧的目标身上的火焰。OnActive 只用于"施加瞬间"的一次性表现。

10.3 Notify 的类型

类型实例化适合
UGameplayCueNotify_Static不实例化，在 CDO 上执行一次性 Executed：命中火花、跳字、音效
UGameplayCueNotify_Burst同上，可在编辑器里直接配置粒子、音效、震屏一次性表现，不需要写代码
AGameplayCueNotify_Actor在目标上生成 Actor，可以保存状态持续表现：燃烧、护盾、光环。bAutoDestroyOnRemove，支持对象池回收

10.5 网络视角：Cue 是怎么到达每个客户端的

🌐 三条同步路径
  • Executed（一次性）：服务器调用 ASC 上的 NetMulticast_InvokeGameplayCueExecuted* 系列 Unreliable 多播。网络拥塞时可能丢失，这对表现来说是可以接受的。
  • 持续型（Add / Remove）：拥有者通过复制下来的 ActiveGE 得知；模拟端通过 ASC 上的 MinimalReplicationGameplayCues（Mixed / Minimal 模式）得知，后者是可靠的属性复制，保证最终一致。
  • 预测去重：本地预测的客户端已经提前播放了 Cue。服务器多播时会带上预测键，拥有者识别出这是自己预测过的 Cue，就会跳过，避免重复播放。
⚠️ 坑点：同一帧大量 Cue 被丢弃

AOE 一次命中 20 个目标时，每个目标都会发出一个 Executed 多播，可能被网络层的 RPC 限流丢掉。可以考虑：①合并成一个 Cue，在参数中携带多个目标；②改为本地非复制 Cue，由每个客户端根据复制下来的结果自己判断；③检查项目中与多播 RPC 数量相关的网络配置。

✅ 实践建议：皮肤特效替换

同一个技能在不同皮肤下要播放不同特效时，逻辑层的 Cue Tag 应该保持不变，由表现层做映射。GAS 提供了 GameplayCueTranslator 机制，可以按条件把 GameplayCue.Hero.Q.Hit 翻译成 GameplayCue.Hero.Q.Hit.Skin01；也可以在 Notify 内部根据 Instigator 的皮肤配置选择资源。这样逻辑和数值完全不需要关心皮肤。

本章小结
  • Cue 由 Tag 驱动，逻辑层只负责触发 Tag，具体表现由 Notify 实现。
  • 事件分为 OnActive / WhileActive / Removed / Executed；循环表现放在 WhileActive 中。
  • 一次性 Cue 走 Unreliable 多播，持续型 Cue 走可靠复制；预测过的 Cue 会自动去重。
  • 首选在 GE 上配置 Cue，以获得自动参数和预测支持。
