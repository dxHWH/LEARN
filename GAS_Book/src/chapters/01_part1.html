CHAPTER 01

为什么需要 GAS

先看清楚问题，才能理解 GAS 那些乍看很"重"的设计是在解决什么。

本章目标
  • 说清楚"不用 GAS 时，一个技能要写多少东西"
  • 理解 GAS 的四条设计原则：数据驱动、组合优先、Tag 作为通用语言、网络内建
  • 判断你的项目该不该用 GAS

1.1 一个火球术，要写多少代码？

策划的需求很简单："按 Q 放火球，耗 30 蓝，冷却 6 秒，命中造成 100 点火焰伤害，并附加 3 秒燃烧，每秒 10 点。"直接写的话，第一版大概是这样：

void AMyHero::CastFireball() { if (Mana < 30.f) return; // 蓝量检查 if (GetWorld()->GetTimeSeconds() < FireballReadyTime) return; // 冷却检查 Mana -= 30.f; FireballReadyTime = GetWorld()->GetTimeSeconds() + 6.f; PlayAnimMontage(FireballMontage); SpawnFireball(); // 命中后 Target->TakeDamage(100) }

看上去还行。但需求会一条条追加上来：

  1. "被眩晕时不能放技能。"于是加 bIsStunned。之后又来了沉默、击飞、冰冻，每种控制对哪些技能生效还不一样。
  2. "装备 +20% 法强，Buff +30%，两者叠加。"需要一套修饰器系统，还要能正确撤销：Buff 结束时减掉的值必须和当初加上的一样。
  3. "燃烧最多叠 3 层，重复命中刷新持续时间。"要写 DOT 管理器，处理计时、层数和刷新规则。
  4. "冷却缩减 20%，冷却期间 UI 要显示转圈。"冷却时长得能动态计算，UI 需要能查询剩余时间。
  5. "联网对战，延迟 100ms 时按键也要立即有反馈。"这是最难的一条：客户端得先扣蓝、先播动画，服务器否决时还要回滚。

一个月后，AMyHero 里塞满了 bool、计时器和 RPC，每个技能都在重复写同样的检查。新人加一个"免疫控制"的 Buff，要改十几处 if。

1.2 GAS 的四条设计原则

① 数据驱动

冷却、消耗、伤害、Buff 都写成数据资产（GameplayEffect），策划可以在编辑器里配置，不必改代码。

② 组合优于继承

"眩晕"不是一个类，而是"一个 GE 给目标加上 State.Stunned Tag"，加上"技能声明被这个 Tag 阻挡"。规则之间靠组合产生联系。

③ Tag 是通用语言

Ability、Effect、Cue、免疫、打断全部用层级化的 GameplayTag 描述，系统之间只依赖 Tag，不需要互相引用类。

④ 网络内建

属性复制、Effect 复制、技能激活 RPC、客户端预测与回滚都已经实现好。你只需要选择正确的策略。

用 GAS 重写火球术，只需要一段几乎不变的 Ability 逻辑和几份数据：

需求GAS 中的表达方式需要写代码吗

1.3 该不该用 GAS

适合

RPG、ARPG、MOBA、射击（Lyra、堡垒之夜都在用）、多人动作游戏。也就是技能、Buff 多，数值规则复杂，并且需要联网的项目。

慎用

只有一两个技能的单机小游戏；帧同步 / 锁步架构的项目（GAS 基于 UE 的 C/S 状态同步）；团队完全没有 C++ 能力（初始化必须写 C++）。

🌐 网络视角：与帧同步项目的关系

GAS 构建在 UE 的 服务器权威 + 属性复制 + RPC 模型之上，预测机制也是为这个模型设计的。帧同步项目（所有客户端用相同输入跑相同逻辑）一般不会直接采用 GAS 的网络部分，但它的数据建模思想（Tag、Modifier 聚合、Effect 生命周期、Stacking）可以直接借鉴到自研技能系统中。

本章小结
  • 直接写技能时，难点不在单个技能，而在规则之间的组合和联网后的同步与回滚。
  • GAS 把规则拆成 Tag / Attribute / Effect / Ability / Cue 五类可组合的数据，以 ASC 作为中枢。
  • 大部分新需求只需要配数据；需要写代码的通常是一次性的框架部分（伤害公式、初始化、输入绑定）。

2.5 逻辑与表现分离

GAS 有一条贯穿始终的界线：GE、Attribute、Tag 是逻辑层，由服务器权威决定；GameplayCue 是表现层，可以丢包、可以延迟、可以只在本地播放，丢了也不影响游戏结果。

⚠️ 坑点：不要在 Cue 里写逻辑

Cue 走的是 Unreliable 多播，而且只在客户端执行（专用服务器默认不跑表现）。在 Cue 里扣血、加 Buff，结果一定会不同步。反过来，Ability 也只存在于服务器和"拥有者客户端"，在 Ability 里用 Multicast RPC 播特效是错误做法，应该交给 Cue 去做。

本章小结
  • ASC 是中枢；AttributeSet 存数值，GE 改数值，GA 写流程，Task 处理异步，Tag 管规则，Cue 管表现。
  • 记住三层概念：Class（定义）→ Spec（运行时实例）→ Handle（句柄）。
  • 逻辑在服务器权威执行，表现交给 Cue，二者不要混用。
CHAPTER 03

最小可运行工程

从零接入 GAS。这一章的每个决定（ASC 放哪、何时初始化）都直接影响后面的联网表现，不要跳过。

3.1 启用插件与模块依赖

在编辑器 Edit → Plugins 中启用 Gameplay Abilities，然后在模块的 Build.cs 中添加依赖：

PublicDependencyModuleNames.AddRange(new string[] { "Core", "CoreUObject", "Engine", "InputCore", "EnhancedInput", "GameplayAbilities", // ASC / GA / GE / AttributeSet "GameplayTags", // FGameplayTag "GameplayTasks" // AbilityTask 的基类 UGameplayTask });
🕒 版本差异：InitGlobalData

老教程会要求在 UAssetManager::StartInitialLoading() 中手动调用 UAbilitySystemGlobals::Get().InitGlobalData()，否则 TargetData 等功能会报错。新版本的插件模块会自行完成全局初始化。如果你的项目是从 UE4 升级上来的，可以保留这行调用，它内部有防重复初始化的判断。

3.2 第一个关键决定：ASC 放在哪里

ASC 所在的 Actor 叫 OwnerActor，ASC 在世界中作用的"身体"叫 AvatarActor。两者可以是同一个 Actor，也可以分开：

场景ASC 放置复制模式说明
玩家角色（要保留状态）PlayerStateMixedLyra 与 Epic 官方最佳实践的推荐方案
玩家角色（每条命完全重置）PawnMixed实现简单，死亡即清空
大量 AI 小兵Pawn（Owner = Avatar = 自己）Minimal节省带宽，小兵不需要把 GE 细节同步给任何客户端
需要和玩家统一处理的 AI（Bot）PlayerState（AIController 设 bWantsPlayerState = true）MixedBot 与玩家共用同一套代码
可破坏物、宝箱自身Minimal同样可以被 GE 打
联网游戏❌ 不要放 PlayerController—PC 不会复制到其他客户端
⚠️ 坑点：一个 Actor 只放一个 ASC

ASC 初始化时会自动收集 OwnerActor 上所有 AttributeSet 子对象。放两个 ASC 会导致属性集被重复注册，IAbilitySystemInterface 的返回值也变得不确定。

3.3 PlayerState：创建 ASC 与 AttributeSet

UCLASS() class AMyPlayerState : public APlayerState, public IAbilitySystemInterface { GENERATED_BODY() public: AMyPlayerState(); // IAbilitySystemInterface：让 GAS 以 O(1) 找到 ASC（未实现时会退化为遍历组件） virtual UAbilitySystemComponent* GetAbilitySystemComponent() const override { return AbilitySystemComponent; } UMyAttributeSet* GetAttributeSet() const { return AttributeSet; } protected: UPROPERTY(VisibleAnywhere, Category = "GAS") TObjectPtr AbilitySystemComponent; // 必须用 UPROPERTY 持有，否则会被 GC UPROPERTY() TObjectPtr AttributeSet; }; AMyPlayerState::AMyPlayerState() { AbilitySystemComponent = CreateDefaultSubobject(TEXT("AbilitySystemComponent")); AbilitySystemComponent->SetIsReplicated(true); // Mixed：GE 细节只同步给自己，其他客户端只收到 Tag 和 Cue（第 11 章详解） AbilitySystemComponent->SetReplicationMode(EGameplayEffectReplicationMode::Mixed); // 在构造函数中作为子对象创建：客户端无需等待复制就能拿到属性集 AttributeSet = CreateDefaultSubobject(TEXT("AttributeSet")); // PlayerState 默认同步频率很低，会导致技能/属性响应迟缓 SetNetUpdateFrequency(100.f); // UE5.5 之前写作 NetUpdateFrequency = 100.f; }
🌐 网络视角：为什么要调高 NetUpdateFrequency

属性、ActiveGE 等通过属性复制下发，而属性复制受所在 Actor 的 NetUpdateFrequency 限制。PlayerState 默认的更新频率很低，不调高的话，服务器扣血后客户端要等很久才看到。ASC 的 RPC（激活、Cue）不受这个频率限制，所以表现为"特效出来了，血条半天才动"。

3.4 第二个关键决定：何时初始化 ActorInfo

InitAbilityActorInfo(Owner, Avatar) 会把 Owner、Avatar、PlayerController、动画实例、移动组件等缓存到 FGameplayAbilityActorInfo 中，技能运行时都从这里读取。服务器和客户端必须各自调用一次，而且要在双方都"准备好"之后调用：

// 服务器：Controller 附身时 void AMyCharacter::PossessedBy(AController* NewController) { Super::PossessedBy(NewController); InitAbilitySystem(); if (HasAuthority()) { GrantStartupAbilitiesAndEffects(); // 技能只能在服务器授予 } } // 客户端：PlayerState 复制到达时（此时 Pawn 也一定已经存在） void AMyCharacter::OnRep_PlayerState() { Super::OnRep_PlayerState(); InitAbilitySystem(); } void AMyCharacter::InitAbilitySystem() { AMyPlayerState* PS = GetPlayerState(); if (!PS) return; AbilitySystemComponent = PS->GetAbilitySystemComponent(); // 角色缓存一个指针，便于访问 // Owner = PlayerState（持久），Avatar = 当前角色（身体） AbilitySystemComponent->InitAbilityActorInfo(PS, this); } // 角色同样实现 IAbilitySystemInterface，返回 PS 上的 ASC UAbilitySystemComponent* AMyCharacter::GetAbilitySystemComponent() const { return AbilitySystemComponent; } void AMyPlayerController::OnRep_PlayerState() { Super::OnRep_PlayerState(); // PC 可能晚于 PS/Pawn 到达；这里保证 ActorInfo 中缓存到了 PlayerController if (IsNetMode(NM_Client)) { if (UAbilitySystemComponent* ASC = UAbilitySystemGlobals::GetAbilitySystemComponentFromActor(PlayerState)) { ASC->RefreshAbilityActorInfo(); } } }
⚠️ 坑点：本地预测技能"按了没反应"

症状是：Listen Server 上正常，纯客户端上 LocalPredicted 技能激活不了，或者全部走了服务器。原因通常是 ActorInfo.PlayerController 为空，ASC 认为自己"不是本地控制的"。按上面的写法补上 PC 端的 Refresh 即可。Lyra 在 5.6 中也修复了同样的问题。

🌐 网络视角：OwnerActor 的 Owner 链

客户端要能调用 ASC 上的 Server RPC，ASC 所在 Actor 的 NetOwner 必须是该客户端的连接。PlayerState 的 Owner 默认就是 PlayerController，天然满足；ASC 放在 Pawn 上时，Possess 会把 Pawn 的 Owner 设为 Controller，同样满足。Mixed 复制模式还额外要求 OwnerActor 的 Owner 是 Controller，否则 GE 无法正确同步给拥有者。

3.5 AI / 小兵：Owner 与 Avatar 是同一个 Actor

AMyMinion::AMyMinion() { AbilitySystemComponent = CreateDefaultSubobject(TEXT("ASC")); AbilitySystemComponent->SetIsReplicated(true); AbilitySystemComponent->SetReplicationMode(EGameplayEffectReplicationMode::Minimal); // 小兵用 Minimal AttributeSet = CreateDefaultSubobject(TEXT("AttributeSet")); } void AMyMinion::BeginPlay() { Super::BeginPlay(); AbilitySystemComponent->InitAbilityActorInfo(this, this); // 两端都在 BeginPlay 初始化即可 if (HasAuthority()) { GrantStartupAbilitiesAndEffects(); } }

3.6 授予技能与初始化属性

void AMyCharacter::GrantStartupAbilitiesAndEffects() { UAbilitySystemComponent* ASC = GetAbilitySystemComponent(); if (!ASC || bStartupGranted) return; // 重生时 ASC 在 PS 上，避免重复授予 for (const TSubclassOf& AbilityClass : StartupAbilities) { // Spec(类, 等级, InputID, SourceObject) ASC->GiveAbility(FGameplayAbilitySpec(AbilityClass, 1, INDEX_NONE, this)); } // 用一个 Instant GE（Override 各项属性）初始化属性，而不是直接 Set FGameplayEffectContextHandle Ctx = ASC->MakeEffectContext(); Ctx.AddSourceObject(this); FGameplayEffectSpecHandle Spec = ASC->MakeOutgoingSpec(GE_InitAttributes, CharacterLevel, Ctx); ASC->ApplyGameplayEffectSpecToSelf(*Spec.Data.Get()); bStartupGranted = true; }
✅ 实践建议：属性初始化的三种方式
  • Instant GE + Override：最直观，可以按等级读曲线表，推荐入门使用。
  • DataTable：InitStats(AttributeSetClass, DataTable)，简单但不支持等级。
  • FAttributeSetInitter + CurveTable：堡垒之夜使用的方式，在项目设置 GlobalAttributeSetDefaultsTables 中配置曲线表，按"组名 + 等级"初始化，适合有大量单位的项目。

3.7 输入绑定：Enhanced Input + InputTag

引擎内置的 BindAbilityActivationToInputComponent 依赖旧版输入系统和一个枚举，大项目一般不用。现在的主流做法（Lyra）是让技能在 DynamicTags 中声明自己响应哪个 InputTag，输入组件只负责把 InputTag 转发给 ASC：

// 授予时：Spec.GetDynamicSpecSourceTags().AddTag(InputTag_Ability_Q); (5.5 之前为 Spec.DynamicAbilityTags) void UMyAbilitySystemComponent::AbilityInputTagPressed(const FGameplayTag& InputTag) { for (FGameplayAbilitySpec& Spec : GetActivatableAbilities()) { if (!Spec.Ability || !Spec.GetDynamicSpecSourceTags().HasTagExact(InputTag)) continue; AbilitySpecInputPressed(Spec); // 让 WaitInputPress 等 Task 能收到 if (Spec.IsActive()) { // 技能已经在运行：把"按下"事件同步给服务器上的同一个技能实例 InvokeReplicatedEvent(EAbilityGenericReplicatedEvent::InputPressed, Spec.Handle, Spec.GetPrimaryInstance()->GetCurrentActivationInfo().GetActivationPredictionKey()); } else { TryActivateAbility(Spec.Handle); // 会根据 NetExecutionPolicy 自动走预测/RPC } } }
🕒 版本差异

FGameplayAbilitySpec::DynamicAbilityTags 在 5.5 中改为通过 GetDynamicSpecSourceTags() 访问；GetPrimaryInstance() 是 5.5 之后获取 InstancedPerActor 实例的推荐接口（之前一般用 GetAbilityInstances() 取最后一个）。旧接口仍可编译，但会给出废弃警告。

3.8 验证：showdebug abilitysystem

运行游戏，在控制台输入 showdebug abilitysystem，屏幕上会列出当前目标的属性、Owned Tags、已授予技能和激活中的 GE。用 AbilitySystem.Debug.NextCategory 切换显示类别，用 PageUp / PageDown 切换查看对象。看到属性值和技能列表，说明接入已经成功。

本章小结
  • 玩家的 ASC 推荐放在 PlayerState（Mixed 模式，调高 NetUpdateFrequency），AI 小兵放在自身（Minimal 模式）。
  • InitAbilityActorInfo 两端都要调用：服务器在 PossessedBy，客户端在 OnRep_PlayerState，PC 端再做一次 Refresh 兜底。
  • 技能只能在服务器授予；属性用 GE 初始化；输入用 InputTag 转发给 ASC。
思考题：ASC 放在 PlayerState 上，角色死亡时"正在燃烧"的 DOT 该怎么处理？

ASC 不随 Pawn 销毁，所以 DOT 会一直保留。一般做法是：死亡时由服务器调用 RemoveActiveEffectsWithGrantedTags（或给 GE 打上 Effect.RemoveOnDeath 之类的 AssetTag，再按 Tag 查询移除），同时 CancelAllAbilities()。需要跨命保留的效果（例如永久天赋）不要打这个 Tag。这正是官方文档说的"移除部分效果，比在 ASC 之间迁移效果容易得多"。
