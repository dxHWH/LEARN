✅ 选择建议
  • 玩家：Mixed（默认选择）。自己的 Buff 列表、剩余时间在 UI 上要显示完整信息，别人只需要知道状态和特效。
  • AI 小兵 / 野怪：Minimal。没有任何客户端需要它们的 GE 细节。
  • Full：只有在必须显示"其他玩家 Buff 的剩余时间"时才使用（例如 MOBA 中点击敌方英雄查看 Buff 倒计时），并且要做带宽分析。

11.3 FastArray：增量复制

ActiveGE 列表和技能 Spec 列表都使用 FFastArraySerializer，只复制新增、修改、删除的元素，而不是每次复制整个数组。客户端通过元素上的回调感知变化：

FastArray 回调ActiveGE 在客户端上做的事
PostReplicatedAdd把 Modifier 加入本地聚合器、添加 Granted Tag、触发 OnActive / WhileActive Cue（如果这个 GE 是自己预测过的，则跳过 OnActive）
PostReplicatedChange层数、持续时间变化：重新计算、广播层数变化委托
PreReplicatedRemove移除 Modifier 和 Tag、触发 Removed Cue
🔬 深入源码：客户端的 CurrentValue 是怎么算出来的

AttributeSet 复制下来的是整个 FGameplayAttributeData（Base 和 Current 都在里面）。GAMEPLAYATTRIBUTE_REPNOTIFY 宏会调用 SetBaseAttributeValueFromReplication：如果客户端上存在这个属性的聚合器（也就是本地知道有哪些 Modifier，包括预测中的），就用服务器的 Base 加上本地已知的 Modifier 重新计算 Current；否则直接使用复制下来的值。这就是拥有者客户端能"预测属性"的基础。

11.4 时间：持续时间与冷却

ActiveGE 复制时带有服务器上的开始时间。客户端计算剩余时间时，用的是 GameState 同步的服务器时间（GetServerWorldTimeSeconds()），因此不同客户端看到的倒计时大致一致。GetActiveEffectsTimeRemainingAndDuration 已经处理好了这一点，UI 直接使用即可，不要自己用本地时间去推算。

11.5 RPC 的前提：NetOwner

ASC 上所有的 Server RPC（ServerTryActivateAbility、ServerSetReplicatedTargetData 等）只有在客户端拥有这个 ASC 所在的 Actor 时才能发出。所以：

  • 玩家去攻击一个宝箱时，不能直接激活宝箱 ASC 上的技能（客户端不拥有宝箱）。应该在玩家自己的 ASC 上激活"开宝箱"技能，由这个技能对宝箱施加效果。
  • AI 的 ASC 没有拥有者客户端，所有技能都由服务器激活。
本章小结
  • 服务器有全部数据；拥有者有自己的技能和 GE；模拟端只有属性、最小化 Tag、Cue 和 Montage。
  • 玩家用 Mixed，小兵用 Minimal，Full 要谨慎。
  • 客户端的 Current = 服务器 Base + 本地已知的 Modifier（包括预测中的），这是属性预测的基础。
CHAPTER 12

客户端预测：PredictionKey 全流程

GAS 最有价值的部分。本章按时间顺序跟踪一次预测从生成、执行、确认到对账的过程，以及被拒绝时如何回滚。

12.1 为什么需要预测

没有预测时，玩家按下技能键，要等请求到达服务器、服务器执行完、结果回到客户端，才能看到反应，至少要经过一个 RTT（往返时间）。100ms 的延迟就足以让操作感觉"发黏"。预测的思路是：客户端先按自己的判断执行，同时告诉服务器；服务器执行后告诉客户端结果是否正确，客户端再按服务器结果对账。

12.2 核心概念

FPredictionKey

一个由客户端生成的整数 ID。客户端在预测期间做的每一件事（施加 GE、加 Tag、播 Montage、触发 Cue）都会关联这个 Key。服务器执行同样的操作时使用同一个 Key，客户端据此把"自己预测的"和"服务器发来的"对应起来。

预测窗口（FScopedPredictionWindow）

一个 RAII 作用域。只有在窗口内，ASC 才有一个"当前有效的预测 Key"。技能激活时引擎会自动打开窗口；部分 Task 回调（WaitInputRelease、WaitTargetData 等）会打开新的窗口。

确认（Confirm）与追平（CatchUp）

服务器处理完带 Key 的请求后，把 Key 写入 ReplicatedPredictionKeyMap 复制给客户端。客户端收到后触发 CaughtUp 委托：移除自己预测的副作用，以服务器复制下来的版本为准。

拒绝（Reject）

服务器判断激活失败时，发送 ClientActivateAbilityFailed，客户端触发 Rejected 委托，撤销该 Key 关联的所有预测副作用。

🌐 Key 只对两端有意义

FPredictionKey 的 NetSerialize 只会把真实的值发给生成它的那个客户端连接，发给其他客户端的是无效 Key。所以模拟端完全不知道预测的存在，它们只会看到服务器的最终结果。

12.3 成功的预测：时序图

🔬 深入源码：关键函数

客户端：InternalTryActivateAbility 中创建 FScopedPredictionWindow(this, true) 生成新 Key，先调用 CallServerTryActivateAbility，再调用 CallActivateAbility；服务器：ServerTryActivateAbility_Implementation → InternalServerTryActivateAbility，用收到的 Key 构造 FScopedPredictionWindow(this, PredictionKey)，窗口析构时把 Key 写入 ReplicatedPredictionKeyMap。GameplayPrediction.h 文件头部有 Epic 写的长篇设计说明，强烈建议通读一遍。

12.4 对账：蓝量为什么不会扣两次

这是理解预测最好的例子。Cost GE 是 Instant，会修改 Base；但客户端预测的修改必须是可以撤销的。GAS 的做法是：客户端预测的 Instant GE 会被当作 Infinite GE 处理，它不修改 Base，而是作为一个 Modifier 挂在聚合器上。

⚠️ 这就是 REPNOTIFY_Always 的原因

由于有预测，客户端本地的属性值可能已经等于服务器复制下来的值。默认的复制规则是"值没变就不触发 OnRep"，这样 GAMEPLAYATTRIBUTE_REPNOTIFY 就不会执行，聚合器中的 Base 得不到更新。之后预测的 Modifier 被移除时，Current 会按旧的 Base 计算，结果就错了。REPNOTIFY_Always 保证每次复制都会把服务器的 Base 写入聚合器。

12.5 被拒绝的预测：回滚

✅ 实践建议：让回滚不那么突兀

回滚在玩家看来是"技能放了一半就消失了"。减少回滚的办法是让客户端的判断尽量准确：控制效果的 Tag 要尽快同步（调高 NetUpdateFrequency），冷却 UI 留一点容差，激活条件尽量依赖拥有者本地就能得到的数据。完全消除回滚是不可能的，这是预测的固有代价。

12.6 依赖 Key 与新的预测窗口

一个技能在运行过程中，可能需要再次预测：例如"按住蓄力、松手发射"，松手时要预测发射。这时 WaitInputRelease 在客户端的回调中打开一个新的预测窗口，生成一个依赖于原始 Key 的新 Key（FPredictionKey 中的 Base 字段指向原始 Key），并通过 ServerSetReplicatedEvent 把松手事件和新 Key 一起发给服务器。如果原始 Key 被拒绝，依赖它的 Key 也会一起被拒绝。

⚠️ 坑点：在预测窗口之外施加 GE

在技能中通过 SetTimer、普通委托或者自己写的异步回调去施加 GE，这时已经不在任何预测窗口内。客户端调用 ApplyGameplayEffectSpecToSelf 时会因为没有有效 Key 而被直接忽略（HasNetworkAuthorityToApplyGameplayEffect 返回 false）；服务器正常施加。结果是"客户端没有预测，要等复制"。需要预测的操作，请放在 ActivateAbility 的同步代码中，或者放在会打开预测窗口的 Task 回调中。

12.7 能预测什么、不能预测什么

能预测 ✅不能预测 ❌
• 技能激活（包括由事件触发的激活）
• GE 施加：属性修改、Tag 授予
• Cost / Cooldown（在窗口内 Commit 时）
• GameplayCue（随 GE 或单独触发）
• Montage 播放
• 移动（由 CharacterMovement 自身的预测系统负责，包括 RootMotion Task） 		• GE 的移除
• Periodic GE 的周期跳动（DOT 每秒掉血）
• Execution 计算（伤害公式只在服务器运行）
• 在窗口外执行的任何操作
• 对其他 Actor 的伤害结算（应以服务器为准）
• 投射物的生成（需要额外实现"假弹道"等方案）

12.8 在代码中区分执行端

// 是否在服务器上（权威） if (HasAuthority(&CurrentActivationInfo)) { /* 生成投射物、施加伤害、随机数 */ } // 是否是"正在预测"的客户端（服务器确认前） if (IsPredictingClient()) { /* 只做本地表现 */ } // 是否本地控制（Listen Server 主机玩家也返回 true） if (IsLocallyControlled()) { /* 摄像机抖动、准星动画、本地 UI */ } // 当前激活模式：Authority / NonAuthority / Predicting / Confirmed / Rejected switch (GetCurrentActivationInfo().ActivationMode) { /* ... */ }
本章小结
  • 客户端在预测窗口中生成 Key，所有副作用都关联到这个 Key；服务器用同一个 Key 执行。
  • 成功时：确认 → Key 追平 → 用服务器复制的数据替换预测的数据。失败时：Rejected 委托撤销所有副作用。
  • 预测的 Instant GE 在客户端被当作 Infinite 处理，所以可以撤销；这也是属性要使用 REPNOTIFY_Always 的原因。
  • GE 移除、Periodic tick、Execution 都不能预测；在预测窗口外施加的 GE 在客户端会被忽略。
CHAPTER 13

网络专题：十个常见问题

每个专题都对应实际项目中经常出现的一类网络问题，给出原因和解决方法。

13.1 专题一：冷却预测与 UI 抖动

现象：冷却圈在技能释放约 0.1 秒后"跳"了一下；或者冷却刚转完就按键，技能放出来又被撤回。

原因：客户端比服务器早 RTT/2 开始冷却。Key 追平时，预测的冷却 GE 被移除，改用服务器的版本，而服务器版本的开始时间更晚，剩余时间就会变长一点。同理，客户端的冷却也会比服务器早结束，玩家这时按键，服务器上冷却还没结束，于是拒绝了这次激活。

对策：

  • UI 统一用 GetActiveEffectsTimeRemainingAndDuration 读取剩余时间（它基于服务器时间），并对显示值做平滑处理，不要直接显示突变。
  • 冷却结束前一小段时间内（例如 RTT/2）的按键先缓存，冷却结束后再激活，即"输入缓冲"。这也是动作游戏常用的手法。
  • 对于时长很短、要求高频释放的技能（例如普攻），可以在服务器上留一点容差：服务器上冷却剩余时间小于某个阈值时，仍然允许激活。

13.2 专题二：Montage 是怎么同步的

✅ 实践建议

在技能中播放动画，请始终使用 PlayMontageAndWait（底层是 ASC::PlayMontage），不要直接调用 AnimInstance::Montage_Play。后者既不会同步给模拟端，被拒绝时也不会回滚。

13.3 专题三：位移技能与移动预测

现象：冲刺技能在高延迟下"拉回"，或者模拟端看到的冲刺轨迹不对。

原因：GAS 的预测不包括移动。角色移动由 CharacterMovementComponent（CMC）自己的预测系统负责（SavedMoves + 服务器校正）。在技能中直接调用 SetActorLocation 或 LaunchCharacter，CMC 不知道这次位移，服务器校正时就会把角色拉回去。

做法是否可预测说明
ApplyRootMotionConstantForce / MoveToForce 等 Task是创建 RootMotionSource，交给 CMC 预测和同步，推荐
带 RootMotion 的 Montage是CMC 原生支持 Montage RootMotion 的预测
修改 MoveSpeed 属性（加速 Buff）部分CMC 的 GetMaxSpeed 读取属性时，属性变化不在 SavedMove 中，高延迟下会出现轻微校正。要求严格时，应该扩展 CMC 的 SavedMove 标志位
SetActorLocation / LaunchCharacter否只在服务器调用时会表现为延迟和拉扯

13.4 专题四：TargetData 的同步与校验

void UGA_Fire::ActivateAbility(...) { UAbilitySystemComponent* ASC = CurrentActorInfo->AbilitySystemComponent.Get(); if (HasAuthority(&CurrentActivationInfo) && !IsLocallyControlled()) { // 服务器（且不是 Listen 主机自己）：等待客户端的 TargetData OnTargetDataReadyHandle = ASC->AbilityTargetDataSetDelegate(CurrentSpecHandle, CurrentActivationInfo.GetActivationPredictionKey()) .AddUObject(this, &ThisClass::OnTargetDataReady); ASC->CallReplicatedTargetDataDelegatesIfSet(CurrentSpecHandle, CurrentActivationInfo.GetActivationPredictionKey()); } else if (IsLocallyControlled()) { FGameplayAbilityTargetDataHandle Data = TraceAndBuildTargetData(); // 本地射线检测 FScopedPredictionWindow Window(ASC, IsPredictingClient()); if (IsPredictingClient()) { ASC->CallServerSetReplicatedTargetData(CurrentSpecHandle, CurrentActivationInfo.GetActivationPredictionKey(), Data, FGameplayTag(), ASC->ScopedPredictionKey); } OnTargetDataReady(Data, FGameplayTag()); // 本地也执行一次：客户端只做表现，服务器（Listen 主机）做结算 } } void UGA_Fire::OnTargetDataReady(const FGameplayAbilityTargetDataHandle& Data, FGameplayTag Tag) { UAbilitySystemComponent* ASC = CurrentActorInfo->AbilitySystemComponent.Get(); if (HasAuthority(&CurrentActivationInfo)) { if (ValidateHits(Data)) // ★ 反作弊：不要盲目相信客户端 { ApplyGameplayEffectToTarget(CurrentSpecHandle, CurrentActorInfo, CurrentActivationInfo, Data, DamageGE, GetAbilityLevel()); } ASC->ConsumeClientReplicatedTargetData(CurrentSpecHandle, CurrentActivationInfo.GetActivationPredictionKey()); } PlayLocalHitEffects(Data); // 本地表现（非复制 Cue） }

13.5 专题五：RPC 批处理

一个"点一下就打完"的射击技能，正常要发三个 RPC：激活、TargetData、结束。连发武器每秒十几发时，开销很可观。GAS 提供了 RPC 批处理，把这些合并成一个 ServerAbilityRPCBatch：

// 1) 自定义 ASC 中开启 virtual bool ShouldDoServerAbilityRPCBatch() const override { return true; } // 2) 在激活技能的地方开启批处理作用域 { FScopedServerAbilityRPCBatcher Batcher(ASC, AbilitySpecHandle); ASC->TryActivateAbility(AbilitySpecHandle); // 技能内部同步完成：发送 TargetData + EndAbility } // 作用域结束时，三个 RPC 合并成一个发出
⚠️ 适用前提

批处理只在技能在同一帧内同步完成（激活 → TargetData → 结束）时才有意义。需要等待动画或输入的技能，没法合并。

13.6 专题六：GameplayEvent 不会自动同步

现象：客户端发送了 SendGameplayEventToActor，服务器上的 WaitGameplayEvent 一直收不到。

原因：GameplayEvent 只是本地函数调用，本身不会走网络。唯一的例外是：事件触发了一个本地预测技能的激活，这时 Payload 会随 ServerTryActivateAbilityWithEventData 一起发给服务器。

对策：需要两端都收到的事件，应该让两端各自产生（例如来自两端都会播放的 Montage 中的 AnimNotify，注意 13.2 中提到的专用服务器问题）；或者使用 ServerSetReplicatedEvent / 自定义的 Reliable RPC 传递。

13.7 专题七：WaitNetSync

有时需要保证两端执行到同一位置后再继续，例如"客户端决定了某个值，服务器必须先收到这个值再继续执行"。WaitNetSync 有三种模式：

模式行为
OnlyServerWait客户端发出信号后立即继续（打开新的预测窗口）；服务器等待收到信号后再继续
OnlyClientWait服务器发出信号后继续；客户端等待
BothWait两端互相等待（会产生一个完整 RTT 的停顿）

官方建议：GA 中不要使用 Replicated 属性传值（5.5 已废弃），因为属性复制和激活 RPC 之间没有顺序保证。同一 Actor 上的 Reliable RPC 之间是有序的，用 RPC + WaitNetSync 才能得到可靠的时序。

13.8 专题八：命中特效的预测

伤害结算在服务器，但射击游戏的命中火花必须立即出现。常见做法是：客户端根据本地射线检测的结果，用非复制的本地 Cue 播放命中效果；服务器结算后，模拟端通过服务器的 Cue 看到同样的效果，拥有者则跳过（避免重复）。伤害数字等依赖结算结果的表现，等服务器结果到达后再显示。

13.9 专题九：安全与反作弊

服务器会重新检查

即使是 LocalPredicted 技能，服务器收到激活请求后也会重新执行 CanActivateAbility（冷却、消耗、Tag）。客户端改内存跳过冷却，服务器仍会拒绝。

敏感技能由服务器激活

使用 NetSecurityPolicy = ServerOnlyExecution，或者 NetExecutionPolicy = ServerOnly / ServerInitiated，客户端无法请求激活。

校验 TargetData

客户端发来的命中目标必须校验：距离、视线、射速、目标是否存活。数值计算全部放在服务器的 Execution 中。

事件 Payload 不可信

由客户端事件激活的技能，Payload 来自客户端。不要直接把 Payload 中的数值（例如 EventMagnitude）当作伤害使用。

13.10 专题十：带宽、相关性与测试

  • PlayerState 始终相关：PlayerState 默认 bAlwaysRelevant，ASC 放在 PlayerState 上时，属性和 Cue 会同步给所有客户端，与距离无关。玩家很多的模式（例如大逃杀）需要评估这部分带宽：把只有自己需要的属性设为 COND_OwnerOnly，或者让部分逻辑走 Pawn 上的数据。
  • 属性复制条件：蓝量、能量、经验等只需要自己看到的属性使用 COND_OwnerOnly。
  • 小兵使用 Minimal 模式，并且尽量少挂常驻 GE；可以用 Tag 表示的状态就不要用 GE。
  • Iris：UE5 新的复制系统 Iris 已经对 GAS 做了适配，新项目可以评估，但请以所用引擎版本的实际支持情况为准。
  • 测试：PIE 中选择 Play As Client，并开启 Network Emulation（Bad 预设），或者在控制台输入 Net PktLag=150、Net PktLoss=5。p.NetShowCorrections 1 可以显示移动校正。所有技能都应该在 150ms 延迟、5% 丢包的环境下测试一遍。
本章小结
  • 冷却：客户端比服务器早开始、早结束，用服务器时间显示，配合输入缓冲。
  • 动画用 PlayMontageAndWait；位移用 RootMotion Task；专用服务器要确保动画 Tick。
  • TargetData：客户端瞄准，服务器校验后结算；GameplayEvent 本身不同步。
  • 上线前，所有技能都要在高延迟、丢包的模拟环境下测试。
