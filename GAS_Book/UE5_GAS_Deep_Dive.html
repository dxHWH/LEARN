    1.1 一个火球术，要写多少代码？

    策划的需求很简单："按 Q 放火球，耗 30 蓝，冷却 6 秒，命中造成 100 点火焰伤害，并附加 3 秒燃烧，每秒 10 点。"直接写的话，第一版大概是这样：

    第一版：直接写在角色里
    void AMyHero::CastFireball()
{
    if (Mana < 30.f) return;                         // 蓝量检查
    if (GetWorld()->GetTimeSeconds() < FireballReadyTime) return; // 冷却检查
    Mana -= 30.f;
    FireballReadyTime = GetWorld()->GetTimeSeconds() + 6.f;
    PlayAnimMontage(FireballMontage);
    SpawnFireball();                                  // 命中后 Target->TakeDamage(100)
}

    看上去还行。但需求会一条条追加上来：

    1. "被眩晕时不能放技能。"于是加 bIsStunned。之后又来了沉默、击飞、冰冻，每种控制对哪些技能生效还不一样。
    2. "装备 +20% 法强，Buff +30%，两者叠加。"需要一套修饰器系统，还要能正确撤销：Buff 结束时减掉的值必须和当初加上的一样。
    3. "燃烧最多叠 3 层，重复命中刷新持续时间。"要写 DOT 管理器，处理计时、层数和刷新规则。
    4. "冷却缩减 20%，冷却期间 UI 要显示转圈。"冷却时长得能动态计算，UI 需要能查询剩余时间。
    5. "联网对战，延迟 100ms 时按键也要立即有反馈。"这是最难的一条：客户端得先扣蓝、先播动画，服务器否决时还要回滚。

    一个月后，AMyHero 里塞满了 bool、计时器和 RPC，每个技能都在重复写同样的检查。新人加一个"免疫控制"的 Buff，要改十几处 if。

    1.2 GAS 的四条设计原则

    ① 数据驱动

    冷却、消耗、伤害、Buff 都写成数据资产（GameplayEffect），策划可以在编辑器里配置，不必改代码。

    ② 组合优于继承

    "眩晕"不是一个类，而是"一个 GE 给目标加上 State.Stunned Tag"，加上"技能声明被这个 Tag 阻挡"。规则之间靠组合产生联系。

    ③ Tag 是通用语言

    Ability、Effect、Cue、免疫、打断全部用层级化的 GameplayTag 描述，系统之间只依赖 Tag，不需要互相引用类。

    ④ 网络内建

    属性复制、Effect 复制、技能激活 RPC、客户端预测与回滚都已经实现好。你只需要选择正确的策略。

    用 GAS 重写火球术，只需要一段几乎不变的 Ability 逻辑和几份数据：

    需求GAS 中的表达方式需要写代码吗
    耗 30 蓝Cost GE：Instant，Mana AddBase −30否
    冷却 6 秒（受冷却缩减影响）Cooldown GE：持续 6 秒，授予 Cooldown.Skill.Fireball；时长用 SetByCaller 或 MMC 计算一次性
    眩晕 / 沉默时不能放Ability 的 ActivationBlockedTags 填 State.Debuff.Stun、State.Debuff.Silence否
    +20% / +30% 法强叠加装备与 Buff 各自是 Infinite / Duration GE 上的 Modifier，由聚合器自动计算，自动撤销否
    100 点火焰伤害（算抗性）Damage GE + ExecutionCalculation（伤害公式写一次，全游戏复用）一次性
    燃烧 3 层、刷新时长Burn GE：Duration 3s、Period 1s、Stacking 上限 3、刷新策略否
    命中特效、燃烧特效GameplayCue：GameplayCue.Fireball.Hit / GameplayCue.Burn只做表现
    联网 + 按键立即反馈Ability 设为 LocalPredicted否

    1.3 该不该用 GAS

    适合

    RPG、ARPG、MOBA、射击（Lyra、堡垒之夜都在用）、多人动作游戏。也就是技能、Buff 多，数值规则复杂，并且需要联网的项目。

    慎用

    只有一两个技能的单机小游戏；帧同步 / 锁步架构的项目（GAS 基于 UE 的 C/S 状态同步）；团队完全没有 C++ 能力（初始化必须写 C++）。

    🌐 网络视角：与帧同步项目的关系

    GAS 构建在 UE 的 服务器权威 + 属性复制 + RPC 模型之上，预测机制也是为这个模型设计的。帧同步项目（所有客户端用相同输入跑相同逻辑）一般不会直接采用 GAS 的网络部分，但它的数据建模思想（Tag、Modifier 聚合、Effect 生命周期、Stacking）可以直接借鉴到自研技能系统中。

    本章小结
    • 直接写技能时，难点不在单个技能，而在规则之间的组合和联网后的同步与回滚。
    • GAS 把规则拆成 Tag / Attribute / Effect / Ability / Cue 五类可组合的数据，以 ASC 作为中枢。
    • 大部分新需求只需要配数据；需要写代码的通常是一次性的框架部分（伤害公式、初始化、输入绑定）。

    对象一句话类比典型例子
    AbilitySystemComponent挂在 Actor 上的组件，管理该 Actor 所有的 GAS 状态角色的"战斗中枢"每个英雄、小兵、防御塔各一个

    2.5 逻辑与表现分离

    GAS 有一条贯穿始终的界线：GE、Attribute、Tag 是逻辑层，由服务器权威决定；GameplayCue 是表现层，可以丢包、可以延迟、可以只在本地播放，丢了也不影响游戏结果。

    ⚠️ 坑点：不要在 Cue 里写逻辑

    Cue 走的是 Unreliable 多播，而且只在客户端执行（专用服务器默认不跑表现）。在 Cue 里扣血、加 Buff，结果一定会不同步。反过来，Ability 也只存在于服务器和"拥有者客户端"，在 Ability 里用 Multicast RPC 播特效是错误做法，应该交给 Cue 去做。

    本章小结
    • ASC 是中枢；AttributeSet 存数值，GE 改数值，GA 写流程，Task 处理异步，Tag 管规则，Cue 管表现。
    • 记住三层概念：Class（定义）→ Spec（运行时实例）→ Handle（句柄）。
    • 逻辑在服务器权威执行，表现交给 Cue，二者不要混用。

    🕒 版本差异：InitGlobalData

    老教程会要求在 UAssetManager::StartInitialLoading() 中手动调用 UAbilitySystemGlobals::Get().InitGlobalData()，否则 TargetData 等功能会报错。新版本的插件模块会自行完成全局初始化。如果你的项目是从 UE4 升级上来的，可以保留这行调用，它内部有防重复初始化的判断。

    3.2 第一个关键决定：ASC 放在哪里

    ASC 所在的 Actor 叫 OwnerActor，ASC 在世界中作用的"身体"叫 AvatarActor。两者可以是同一个 Actor，也可以分开：

    场景ASC 放置复制模式说明
    玩家角色（要保留状态）PlayerStateMixedLyra 与 Epic 官方最佳实践的推荐方案
    玩家角色（每条命完全重置）PawnMixed实现简单，死亡即清空
    大量 AI 小兵Pawn（Owner = Avatar = 自己）Minimal节省带宽，小兵不需要把 GE 细节同步给任何客户端
    需要和玩家统一处理的 AI（Bot）PlayerState（AIController 设 bWantsPlayerState = true）MixedBot 与玩家共用同一套代码
    可破坏物、宝箱自身Minimal同样可以被 GE 打
    联网游戏❌ 不要放 PlayerController—PC 不会复制到其他客户端
    ⚠️ 坑点：一个 Actor 只放一个 ASC

    ASC 初始化时会自动收集 OwnerActor 上所有 AttributeSet 子对象。放两个 ASC 会导致属性集被重复注册，IAbilitySystemInterface 的返回值也变得不确定。

    3.3 PlayerState：创建 ASC 与 AttributeSet

    MyPlayerState.h
    UCLASS()
class AMyPlayerState : public APlayerState, public IAbilitySystemInterface
{
    GENERATED_BODY()
public:
    AMyPlayerState();
    // IAbilitySystemInterface：让 GAS 以 O(1) 找到 ASC（未实现时会退化为遍历组件）
    virtual UAbilitySystemComponent* GetAbilitySystemComponent() const override { return AbilitySystemComponent; }
    UMyAttributeSet* GetAttributeSet() const { return AttributeSet; }

protected:
    UPROPERTY(VisibleAnywhere, Category = "GAS")
    TObjectPtr<UMyAbilitySystemComponent> AbilitySystemComponent;

    // 必须用 UPROPERTY 持有，否则会被 GC
    UPROPERTY()
    TObjectPtr<UMyAttributeSet> AttributeSet;
};
    MyPlayerState.cpp
    AMyPlayerState::AMyPlayerState()
{
    AbilitySystemComponent = CreateDefaultSubobject<UMyAbilitySystemComponent>(TEXT("AbilitySystemComponent"));
    AbilitySystemComponent->SetIsReplicated(true);
    // Mixed：GE 细节只同步给自己，其他客户端只收到 Tag 和 Cue（第 11 章详解）
    AbilitySystemComponent->SetReplicationMode(EGameplayEffectReplicationMode::Mixed);

    // 在构造函数中作为子对象创建：客户端无需等待复制就能拿到属性集
    AttributeSet = CreateDefaultSubobject<UMyAttributeSet>(TEXT("AttributeSet"));

    // PlayerState 默认同步频率很低，会导致技能/属性响应迟缓
    SetNetUpdateFrequency(100.f);   // UE5.5 之前写作 NetUpdateFrequency = 100.f;
}
    🌐 网络视角：为什么要调高 NetUpdateFrequency

    属性、ActiveGE 等通过属性复制下发，而属性复制受所在 Actor 的 NetUpdateFrequency 限制。PlayerState 默认的更新频率很低，不调高的话，服务器扣血后客户端要等很久才看到。ASC 的 RPC（激活、Cue）不受这个频率限制，所以表现为"特效出来了，血条半天才动"。

    3.4 第二个关键决定：何时初始化 ActorInfo

    InitAbilityActorInfo(Owner, Avatar) 会把 Owner、Avatar、PlayerController、动画实例、移动组件等缓存到 FGameplayAbilityActorInfo 中，技能运行时都从这里读取。服务器和客户端必须各自调用一次，而且要在双方都"准备好"之后调用：

    MyCharacter.cpp —— 两端初始化

void AMyCharacter::PossessedBy(AController* NewController)
{
    Super::PossessedBy(NewController);
    InitAbilitySystem();
    if (HasAuthority())
    {
        GrantStartupAbilitiesAndEffects();     // 技能只能在服务器授予
    }
}

// 客户端：PlayerState 复制到达时（此时 Pawn 也一定已经存在）
void AMyCharacter::OnRep_PlayerState()
{
    Super::OnRep_PlayerState();
    InitAbilitySystem();
}

void AMyCharacter::InitAbilitySystem()
{
    AMyPlayerState* PS = GetPlayerState<AMyPlayerState>();
    if (!PS) return;
    AbilitySystemComponent = PS->GetAbilitySystemComponent();   // 角色缓存一个指针，便于访问
    // Owner = PlayerState（持久），Avatar = 当前角色（身体）
    AbilitySystemComponent->InitAbilityActorInfo(PS, this);
}

// 角色同样实现 IAbilitySystemInterface，返回 PS 上的 ASC
UAbilitySystemComponent* AMyCharacter::GetAbilitySystemComponent() const { return AbilitySystemComponent; }

    Super::OnRep_PlayerState();

    ⚠️ 坑点：本地预测技能"按了没反应"

    症状是：Listen Server 上正常，纯客户端上 LocalPredicted 技能激活不了，或者全部走了服务器。原因通常是 ActorInfo.PlayerController 为空，ASC 认为自己"不是本地控制的"。按上面的写法补上 PC 端的 Refresh 即可。Lyra 在 5.6 中也修复了同样的问题。

    🌐 网络视角：OwnerActor 的 Owner 链

    客户端要能调用 ASC 上的 Server RPC，ASC 所在 Actor 的 NetOwner 必须是该客户端的连接。PlayerState 的 Owner 默认就是 PlayerController，天然满足；ASC 放在 Pawn 上时，Possess 会把 Pawn 的 Owner 设为 Controller，同样满足。Mixed 复制模式还额外要求 OwnerActor 的 Owner 是 Controller，否则 GE 无法正确同步给拥有者。

    3.6 授予技能与初始化属性

    授予初始技能 / 初始属性（只在服务器）
    void AMyCharacter::GrantStartupAbilitiesAndEffects()
{
    UAbilitySystemComponent* ASC = GetAbilitySystemComponent();
    if (!ASC || bStartupGranted) return;      // 重生时 ASC 在 PS 上，避免重复授予

    for (const TSubclassOf<UGameplayAbility>& AbilityClass : StartupAbilities)
    {
        // Spec(类, 等级, InputID, SourceObject)
        ASC->GiveAbility(FGameplayAbilitySpec(AbilityClass, 1, INDEX_NONE, this));
    }

    // 用一个 Instant GE（Override 各项属性）初始化属性，而不是直接 Set
    FGameplayEffectContextHandle Ctx = ASC->MakeEffectContext();
    Ctx.AddSourceObject(this);
    FGameplayEffectSpecHandle Spec = ASC->MakeOutgoingSpec(GE_InitAttributes, CharacterLevel, Ctx);
    ASC->ApplyGameplayEffectSpecToSelf(*Spec.Data.Get());

    bStartupGranted = true;
}
    ✅ 实践建议：属性初始化的三种方式
    • Instant GE + Override：最直观，可以按等级读曲线表，推荐入门使用。
    • DataTable：InitStats(AttributeSetClass, DataTable)，简单但不支持等级。
    • FAttributeSetInitter + CurveTable：堡垒之夜使用的方式，在项目设置 GlobalAttributeSetDefaultsTables 中配置曲线表，按"组名 + 等级"初始化，适合有大量单位的项目。

    3.7 输入绑定：Enhanced Input + InputTag

    CHAPTER 04

    GameplayTags：系统之间的通用语言

    Tag 是 GAS 中最简单、也最重要的概念。Tag 体系设计得好，后面大部分规则可以只靠配置完成。

    4.1 Tag 是什么

    FGameplayTag 本质上是一个注册过的 FName，用点号表示层级，例如 State.Debuff.Stun。它比 FName 和枚举更适合描述状态，原因有三点：

    • 层级匹配：查询 State.Debuff 时，State.Debuff.Stun 也会命中。"驱散所有负面效果"只需要一行。
    • 全局注册：所有 Tag 都在 TagManager 中注册，编辑器里可以下拉选择，拼错名字会在加载时报错。
    • 网络友好：复制时传的是索引而不是字符串（开启 Fast Replication 后），带宽开销很小。

    5.4 钳制与 Meta 属性：伤害的标准写法

    为什么不让伤害 GE 直接 Health −= X？因为扣血之前往往还有很多步骤：护盾吸收、伤害反弹、吸血、击杀判定、伤害数字显示。Meta 属性（例如 IncomingDamage）就是一个临时中转站：GE 只往它里面写数值，在 PostGameplayEffectExecute 中统一处理后清零。

    MyAttributeSet.cpp —— 钳制与伤害结算
    void UMyAttributeSet::PreAttributeChange(const FGameplayAttribute& Attribute, float& NewValue)
{
    Super::PreAttributeChange(Attribute, NewValue);
    if (Attribute == GetHealthAttribute())
    {
        NewValue = FMath::Clamp(NewValue, 0.f, GetMaxHealth());
    }
}

void UMyAttributeSet::PostAttributeChange(const FGameplayAttribute& Attribute, float OldValue, float NewValue)
{
    Super::PostAttributeChange(Attribute, OldValue, NewValue);
    // MaxHealth 变化时，按比例调整当前血量（例如 500/1000 → 加装备后 600/1200）
    if (Attribute == GetMaxHealthAttribute() && OldValue > 0.f)
    {
        UAbilitySystemComponent* ASC = GetOwningAbilitySystemComponent();
        if (!ASC || !ASC->IsOwnerActorAuthoritative()) return;   // 只在服务器修正，客户端等复制
        const float NewHealth = GetHealth() * NewValue / OldValue;
        ASC->ApplyModToAttribute(GetHealthAttribute(), EGameplayModOp::Override, NewHealth);
    }
}

bool UMyAttributeSet::PreGameplayEffectExecute(FGameplayEffectModCallbackData& Data)
{
    // 无敌：直接拒绝本次伤害执行
    if (Data.EvaluatedData.Attribute == GetIncomingDamageAttribute()
        && Data.Target.HasMatchingGameplayTag(MyTags::State_Buff_Invulnerable))
    {
        return false;
    }
    return true;
}

void UMyAttributeSet::PostGameplayEffectExecute(const FGameplayEffectModCallbackData& Data)
{
    Super::PostGameplayEffectExecute(Data);

    if (Data.EvaluatedData.Attribute == GetIncomingDamageAttribute())
    {
        const float Damage = GetIncomingDamage();
        SetIncomingDamage(0.f);                         // Meta 属性用完立即清零
        if (Damage <= 0.f) return;

        const float NewHealth = FMath::Clamp(GetHealth() - Damage, 0.f, GetMaxHealth());
        SetHealth(NewHealth);

        // 来源信息都在 Context 里：谁打的、用什么打的、命中点
        const FGameplayEffectContextHandle& Ctx = Data.EffectSpec.GetContext();
        AActor* Instigator = Ctx.GetOriginalInstigator();

        if (NewHealth <= 0.f && !Data.Target.HasMatchingGameplayTag(MyTags::State_Dead))
        {
            // 通知"死亡"：发 GameplayEvent，由死亡技能去处理（掉落、计分、复活计时）
            FGameplayEventData Payload;
            Payload.Instigator = Instigator;
            Payload.EventMagnitude = Damage;
            Data.Target.HandleGameplayEvent(MyTags::Event_Death, &Payload);
        }
    }
}

    CHAPTER 06

    GameplayEffect（上）：时长、修饰器与聚合公式

    GE 是 GAS 中"改变世界"的唯一正规途径。本章讲 GE 的结构，以及多个 Modifier 叠加时的计算方式。

    6.1 GE 的结构

    GE 是一个纯数据类：一般在蓝图中继承 UGameplayEffect 并配置字段，不写逻辑。需要逻辑的部分（复杂公式、条件判断）通过插件类挂进来，例如 MMC、Execution 和 GEComponent。

    6.2 三种时长策略

    ⚠️ 坑点：DOT 加速 Buff 的区别

    一个 HasDuration GE 没有 Period 时，Modifier 修改 Current，到期后自动撤销（例如加速）；有 Period 时，Modifier 在每次 tick 时永久修改 Base，到期后不会撤销（例如燃烧掉的血）。"中毒 5 秒、每秒 −10 血"必须配置 Period = 1。

    🔬 深入源码：Period 与 Ongoing Tag Requirements

    持续型 GE 可以配置"持续期间需要满足的 Tag 条件"（5.3+ 使用 TargetTagRequirementsGameplayEffectComponent 的 Ongoing 部分）。条件不满足时 GE 会被抑制（Inhibited）：Modifier 暂时从聚合器中移除，GE 本身仍然存在。周期效果被抑制后重新激活时，按 PeriodicInhibitionPolicy（NeverReset / ResetPeriod / ExecuteAndResetPeriod）决定计时方式。

    6.3 Modifier 的四个要素

    字段含义
    Attribute要改的属性。属性下拉列表来自所有 AttributeSet；属性加 meta=(HideFromModifiers) 可以从列表中隐藏
    Modifier Op运算方式：AddBase / MultiplyAdditive / DivideAdditive / MultiplyCompound / AddFinal / Override
    Magnitude数值来源，有四种计算方式（见 6.4）
    Source / Target TagsModifier 级别的条件。例如"仅当目标处于燃烧状态时 +30% 伤害"，条件不满足时该 Modifier 不参与聚合

    6.4 数值（Magnitude）的四种计算方式

    类型原理典型用途
    Scalable Float常数 × 曲线表[Spec 等级]"1 级 50 伤害，5 级 150 伤害"
    Attribute BasedCoefficient × (Attr + PreMultiplyAdditive) + PostMultiplyAdditive，Attr 可以取 Source 或 Target 的属性，可选 Current / Base / Bonus（Current − Base）"治疗量 = 施法者法强 × 0.6"、派生属性
    Custom Calculation Class (MMC)继承 UGameplayModMagnitudeCalculation，在 C++ / 蓝图中计算一个 float依赖多个属性或 Tag 的单值计算，例如受冷却缩减影响的冷却时长
    Set By Caller施加前由代码用 Tag 作为键写入 Spec由技能逻辑决定的数值：蓄力伤害、按距离衰减
    🔬 深入源码：Snapshot（快照）是什么

    捕获属性时可以选择是否快照。Source 快照在 Spec 创建时记录施法者的属性值，之后施法者属性变化不影响已发出的效果（例如火球已经飞出去，再加攻击力也不影响这颗火球）。不快照时，持续型 GE 会实时跟随属性变化（例如光环随施法者属性变化）。Target 属性通常在 GE 施加时才捕获。

    6.5 聚合公式：多个 Modifier 怎么叠加

    同一个属性上可能同时存在十几个 Modifier。GAS 先把同类运算汇总，再按固定顺序计算：

    Current = ((Base + ΣAddBase) × MulAdd ÷ DivAdd × ΠMulCompound) + ΣAddFinal
    （存在生效的 Override 时，直接返回 Override 的值）
    🧪 交互实验：聚合器计算器

    在每类中填入多个数值，用逗号分隔。MultiplyAdditive / Compound / Divide 填倍率（例如 1.2 表示 +20%）。

    🕒 版本差异

    老版本只有 Additive / Multiplicitive / Division / Override 四种，公式是 ((Base + Additive) × Multiplicitive) ÷ Division。新版本把它们改名为 AddBase / MultiplyAdditive / DivideAdditive（枚举值不变，老资产无需迁移），并新增了 MultiplyCompound 和 AddFinal。在老版本中要实现"独立乘区"，需要借助 Evaluation Channel 或者 Execution。

    ⚠️ 坑点：Override 和多个 Override

    Override 会让其他 Modifier 全部失效，而且多个 Override 同时存在时，结果取决于聚合器中 Modifier 的顺序。除了"初始化属性"这种一次性的 Instant 用法，尽量不要在持续型 GE 上使用 Override。"定身（速度为 0）"应该用 MultiplyCompound ×0，或者授予一个让移动组件读取的 Tag。

    本章小结
    • GE = Duration + Modifiers + Executions + Components + Stacking + Cues，是纯数据。
    • Instant 和 Period tick 修改 Base；不带 Period 的持续型 GE 只往聚合器中添加 Modifier。
    • 聚合顺序：AddBase → MultiplyAdditive → DivideAdditive → MultiplyCompound → AddFinal，"Additive" 类乘法是先把增量相加。

    FAggregatorEvaluateParameters Params;

void UExecCalc_Damage::Execute_Implementation(const FGameplayEffectCustomExecutionParameters& ExecParams,
                                              FGameplayEffectCustomExecutionOutput& Out) const
{
    const FGameplayEffectSpec& Spec = ExecParams.GetOwningSpec();
    FAggregatorEvaluateParameters P;
    P.SourceTags = Spec.CapturedSourceTags.GetAggregatedTags();
    P.TargetTags = Spec.CapturedTargetTags.GetAggregatedTags();

    float AP = 0, Pen = 0, Crit = 0, Armor = 0;
    ExecParams.AttemptCalculateCapturedAttributeMagnitude(DamageStatics().AttackPowerDef,      P, AP);
    ExecParams.AttemptCalculateCapturedAttributeMagnitude(DamageStatics().ArmorPenetrationDef, P, Pen);
    ExecParams.AttemptCalculateCapturedAttributeMagnitude(DamageStatics().CritChanceDef,       P, Crit);
    ExecParams.AttemptCalculateCapturedAttributeMagnitude(DamageStatics().ArmorDef,            P, Armor);

    // 技能基础伤害 + 攻击力加成系数，都由技能通过 SetByCaller 传入
    const float BaseDmg = Spec.GetSetByCallerMagnitude(MyTags::SetByCaller_Damage, false, 0.f);
    const float Coef    = Spec.GetSetByCallerMagnitude(MyTags::SetByCaller_AttackCoef, false, 1.f);
    float Damage = BaseDmg + AP * Coef;

    // 护甲减伤：有效护甲 = 护甲 × (1 − 穿透)，减伤乘数 = 100 / (100 + 有效护甲)
    const float EffArmor = FMath::Max(0.f, Armor * (1.f - FMath::Clamp(Pen, 0.f, 1.f)));
    Damage *= 100.f / (100.f + EffArmor);

    // 暴击（Execution 只在服务器运行，随机数是权威结果）
    if (FMath::FRand() < Crit) { Damage *= 2.f; /* 可以写入自定义 Context，供 UI 显示暴击 */ }

    if (Damage > 0.f)
    {   // 输出到 Meta 属性，由 AttributeSet::PostGameplayEffectExecute 结算（新版本中 Additive 即 AddBase）
        Out.AddOutputModifier(FGameplayModifierEvaluatedData(
            UMyAttributeSet::GetIncomingDamageAttribute(), EGameplayModOp::Additive, Damage));
    }
}

    GameplayAbility：技能的生命周期

    GE 是"改什么"，GA 是"做什么"。本章讲 GA 从授予到结束的完整生命周期、Tag 规则、消耗与冷却，以及决定联网行为的四个策略。

    8.1 生命周期全图

    ⚠️ 坑点：忘记 EndAbility

    技能不会自动结束。如果某个分支（例如 Montage 被打断的回调）没有调用 EndAbility，技能会一直处于激活状态：ActivationOwnedTags 不会移除，InstancedPerActor 技能也无法再次激活，表现为"技能按了没反应"。每个 Task 的每个出口回调（Completed / Interrupted / Cancelled）都要检查是否需要结束技能。

    8.2 Tag 规则：十个字段

    GA 上有十个 Tag 容器，组合起来可以描述几乎所有"技能之间能否并存"的规则：

    字段作用对象含义例子（冲锋斩）
    AssetTags（老名 AbilityTags）本技能技能自己的身份标签Ability.Hero.Q、Ability.Type.Dash
    CancelAbilitiesWithTag其他技能激活时打断正在运行、带这些 Tag 的技能Ability.Type.Channel（打断自己的引导技能）
    BlockAbilitiesWithTag其他技能运行期间阻止带这些 Tag 的技能激活Ability.Type.Attack（冲刺中不能普攻）
    ActivationOwnedTags拥有者运行期间给自己加上这些 TagState.Dashing
    ActivationRequiredTags拥有者拥有者必须有这些 Tag 才能激活（变身后才能用的技能填 State.Transformed）
    ActivationBlockedTags拥有者拥有者有这些 Tag 时不能激活State.Debuff.Stun、State.Debuff.Root、State.Dead
    Source/Target Required/Blocked来源 / 目标由事件或 TargetData 激活时，检查来源和目标的 Tag（"只能对敌方英雄释放"）
    ✅ 实践建议：Block 与 ActivationBlockedTags 的区别

    BlockAbilitiesWithTag 是技能之间的互斥（通过 ASC 的 BlockedAbilityTags 计数实现）；ActivationBlockedTags 检查的是角色状态。"眩晕时所有技能都不能放"有两种做法：①所有技能的 ActivationBlockedTags 都填 Stun；②眩晕 GE 加一个 BlockAbilityTagsGameplayEffectComponent，阻止 Ability 根 Tag 下的所有技能。②只需改一处，更好维护。别忘了还要打断正在运行的技能（见 4.4 的 Tag 监听示例）。

    8.3 消耗与冷却

    在 GA 上配置 CostGameplayEffectClass 和 CooldownGameplayEffectClass：

    • Cost GE：Instant，Modifier 为 Mana AddBase −30。CheckCost 会模拟施加，判断属性是否会小于 0。
    • Cooldown GE：HasDuration，必须通过 TargetTags 组件授予一个冷却 Tag（例如 Cooldown.Hero.Q）。CheckCooldown 只检查拥有者身上是否有这个 Tag。
    • 在 ActivateAbility 中调用 CommitAbility()，并检查返回值：激活之后，资源可能已经被其他效果改变。

    默认做法要求每个技能各配一个冷却 GE，技能多了很难维护。常见的做法是所有技能共用一个冷却 GE，冷却时长和冷却 Tag 在运行时注入：

void UGA_Fireball::ActivateAbility(const FGameplayAbilitySpecHandle Handle, const FGameplayAbilityActorInfo* ActorInfo,
                                   const FGameplayAbilityActivationInfo ActivationInfo, const FGameplayEventData* TriggerEventData)
{
    // ① 提交：扣蓝 + 进冷却（在预测窗口内，客户端会预测执行）
    if (!CommitAbility(Handle, ActorInfo, ActivationInfo))
    {
        EndAbility(Handle, ActorInfo, ActivationInfo, true, true);
        return;
    }

    // ② 播放施法动画（本地立即播放；服务器播放后通过 Montage 复制给其他客户端）

    10.5 网络视角：Cue 是怎么到达每个客户端的

    🌐 三条同步路径
    • Executed（一次性）：服务器调用 ASC 上的 NetMulticast_InvokeGameplayCueExecuted* 系列 Unreliable 多播。网络拥塞时可能丢失，这对表现来说是可以接受的。
    • 持续型（Add / Remove）：拥有者通过复制下来的 ActiveGE 得知；模拟端通过 ASC 上的 MinimalReplicationGameplayCues（Mixed / Minimal 模式）得知，后者是可靠的属性复制，保证最终一致。
    • 预测去重：本地预测的客户端已经提前播放了 Cue。服务器多播时会带上预测键，拥有者识别出这是自己预测过的 Cue，就会跳过，避免重复播放。
    ⚠️ 坑点：同一帧大量 Cue 被丢弃

    AOE 一次命中 20 个目标时，每个目标都会发出一个 Executed 多播，可能被网络层的 RPC 限流丢掉。可以考虑：①合并成一个 Cue，在参数中携带多个目标；②改为本地非复制 Cue，由每个客户端根据复制下来的结果自己判断；③检查项目中与多播 RPC 数量相关的网络配置。

    ✅ 实践建议：皮肤特效替换

    同一个技能在不同皮肤下要播放不同特效时，逻辑层的 Cue Tag 应该保持不变，由表现层做映射。GAS 提供了 GameplayCueTranslator 机制，可以按条件把 GameplayCue.Hero.Q.Hit 翻译成 GameplayCue.Hero.Q.Hit.Skin01；也可以在 Notify 内部根据 Instigator 的皮肤配置选择资源。这样逻辑和数值完全不需要关心皮肤。

    本章小结
    • Cue 由 Tag 驱动，逻辑层只负责触发 Tag，具体表现由 Notify 实现。
    • 事件分为 OnActive / WhileActive / Removed / Executed；循环表现放在 WhileActive 中。
    • 一次性 Cue 走 Unreliable 多播，持续型 Cue 走可靠复制；预测过的 Cue 会自动去重。
    • 首选在 GE 上配置 Cue，以获得自动参数和预测支持。

    • AI 的 ASC 没有拥有者客户端，所有技能都由服务器激活。

    CHAPTER 12

    客户端预测：PredictionKey 全流程

    GAS 最有价值的部分。本章按时间顺序跟踪一次预测从生成、执行、确认到对账的过程，以及被拒绝时如何回滚。

    12.1 为什么需要预测

    没有预测时，玩家按下技能键，要等请求到达服务器、服务器执行完、结果回到客户端，才能看到反应，至少要经过一个 RTT（往返时间）。100ms 的延迟就足以让操作感觉"发黏"。预测的思路是：客户端先按自己的判断执行，同时告诉服务器；服务器执行后告诉客户端结果是否正确，客户端再按服务器结果对账。

    🧪 交互实验：延迟对手感的影响

    12.2 核心概念

    FPredictionKey

    一个由客户端生成的整数 ID。客户端在预测期间做的每一件事（施加 GE、加 Tag、播 Montage、触发 Cue）都会关联这个 Key。服务器执行同样的操作时使用同一个 Key，客户端据此把"自己预测的"和"服务器发来的"对应起来。

    预测窗口（FScopedPredictionWindow）

    一个 RAII 作用域。只有在窗口内，ASC 才有一个"当前有效的预测 Key"。技能激活时引擎会自动打开窗口；部分 Task 回调（WaitInputRelease、WaitTargetData 等）会打开新的窗口。

    确认（Confirm）与追平（CatchUp）

    服务器处理完带 Key 的请求后，把 Key 写入 ReplicatedPredictionKeyMap 复制给客户端。客户端收到后触发 CaughtUp 委托：移除自己预测的副作用，以服务器复制下来的版本为准。

    拒绝（Reject）

    服务器判断激活失败时，发送 ClientActivateAbilityFailed，客户端触发 Rejected 委托，撤销该 Key 关联的所有预测副作用。

    🌐 Key 只对两端有意义

    FPredictionKey 的 NetSerialize 只会把真实的值发给生成它的那个客户端连接，发给其他客户端的是无效 Key。所以模拟端完全不知道预测的存在，它们只会看到服务器的最终结果。

    客户端：InternalTryActivateAbility 中创建 FScopedPredictionWindow(this, true) 生成新 Key，先调用 CallServerTryActivateAbility，再调用 CallActivateAbility；服务器：ServerTryActivateAbility_Implementation → InternalServerTryActivateAbility，用收到的 Key 构造 FScopedPredictionWindow(this, PredictionKey)，窗口析构时把 Key 写入 ReplicatedPredictionKeyMap。GameplayPrediction.h 文件头部有 Epic 写的长篇设计说明，强烈建议通读一遍。

    12.4 对账：蓝量为什么不会扣两次

    这是理解预测最好的例子。Cost GE 是 Instant，会修改 Base；但客户端预测的修改必须是可以撤销的。GAS 的做法是：客户端预测的 Instant GE 会被当作 Infinite GE 处理，它不修改 Base，而是作为一个 Modifier 挂在聚合器上。

    ⚠️ 这就是 REPNOTIFY_Always 的原因

    由于有预测，客户端本地的属性值可能已经等于服务器复制下来的值。默认的复制规则是"值没变就不触发 OnRep"，这样 GAMEPLAYATTRIBUTE_REPNOTIFY 就不会执行，聚合器中的 Base 得不到更新。之后预测的 Modifier 被移除时，Current 会按旧的 Base 计算，结果就错了。REPNOTIFY_Always 保证每次复制都会把服务器的 Base 写入聚合器。

    12.5 被拒绝的预测：回滚

    ✅ 实践建议：让回滚不那么突兀

    回滚在玩家看来是"技能放了一半就消失了"。减少回滚的办法是让客户端的判断尽量准确：控制效果的 Tag 要尽快同步（调高 NetUpdateFrequency），冷却 UI 留一点容差，激活条件尽量依赖拥有者本地就能得到的数据。完全消除回滚是不可能的，这是预测的固有代价。

    12.6 依赖 Key 与新的预测窗口

    一个技能在运行过程中，可能需要再次预测：例如"按住蓄力、松手发射"，松手时要预测发射。这时 WaitInputRelease 在客户端的回调中打开一个新的预测窗口，生成一个依赖于原始 Key 的新 Key（FPredictionKey 中的 Base 字段指向原始 Key），并通过 ServerSetReplicatedEvent 把松手事件和新 Key 一起发给服务器。如果原始 Key 被拒绝，依赖它的 Key 也会一起被拒绝。

    ⚠️ 坑点：在预测窗口之外施加 GE

    在技能中通过 SetTimer、普通委托或者自己写的异步回调去施加 GE，这时已经不在任何预测窗口内。客户端调用 ApplyGameplayEffectSpecToSelf 时会因为没有有效 Key 而被直接忽略（HasNetworkAuthorityToApplyGameplayEffect 返回 false）；服务器正常施加。结果是"客户端没有预测，要等复制"。需要预测的操作，请放在 ActivateAbility 的同步代码中，或者放在会打开预测窗口的 Task 回调中。

    12.7 能预测什么、不能预测什么

    能预测 ✅不能预测 ❌
    • 技能激活（包括由事件触发的激活）
    • GE 施加：属性修改、Tag 授予
    • Cost / Cooldown（在窗口内 Commit 时）
    • GameplayCue（随 GE 或单独触发）
    • Montage 播放
    • 移动（由 CharacterMovement 自身的预测系统负责，包括 RootMotion Task）     		• GE 的移除
    • Periodic GE 的周期跳动（DOT 每秒掉血）
    • Execution 计算（伤害公式只在服务器运行）
    • 在窗口外执行的任何操作
    • 对其他 Actor 的伤害结算（应以服务器为准）
    • 投射物的生成（需要额外实现"假弹道"等方案）

    技能中常用的执行端判断

    CHAPTER 13

    网络专题：十个常见问题

    每个专题都对应实际项目中经常出现的一类网络问题，给出原因和解决方法。

    13.1 专题一：冷却预测与 UI 抖动

    现象：冷却圈在技能释放约 0.1 秒后"跳"了一下；或者冷却刚转完就按键，技能放出来又被撤回。

    原因：客户端比服务器早 RTT/2 开始冷却。Key 追平时，预测的冷却 GE 被移除，改用服务器的版本，而服务器版本的开始时间更晚，剩余时间就会变长一点。同理，客户端的冷却也会比服务器早结束，玩家这时按键，服务器上冷却还没结束，于是拒绝了这次激活。

    对策：

    • UI 统一用 GetActiveEffectsTimeRemainingAndDuration 读取剩余时间（它基于服务器时间），并对显示值做平滑处理，不要直接显示突变。
    • 冷却结束前一小段时间内（例如 RTT/2）的按键先缓存，冷却结束后再激活，即"输入缓冲"。这也是动作游戏常用的手法。
    • 对于时长很短、要求高频释放的技能（例如普攻），可以在服务器上留一点容差：服务器上冷却剩余时间小于某个阈值时，仍然允许激活。

    13.2 专题二：Montage 是怎么同步的

    ✅ 实践建议

    在技能中播放动画，请始终使用 PlayMontageAndWait（底层是 ASC::PlayMontage），不要直接调用 AnimInstance::Montage_Play。后者既不会同步给模拟端，被拒绝时也不会回滚。

    13.3 专题三：位移技能与移动预测

    现象：冲刺技能在高延迟下"拉回"，或者模拟端看到的冲刺轨迹不对。

    原因：GAS 的预测不包括移动。角色移动由 CharacterMovementComponent（CMC）自己的预测系统负责（SavedMoves + 服务器校正）。在技能中直接调用 SetActorLocation 或 LaunchCharacter，CMC 不知道这次位移，服务器校正时就会把角色拉回去。

    做法是否可预测说明
    ApplyRootMotionConstantForce / MoveToForce 等 Task是创建 RootMotionSource，交给 CMC 预测和同步，推荐
    带 RootMotion 的 Montage是CMC 原生支持 Montage RootMotion 的预测
    修改 MoveSpeed 属性（加速 Buff）部分CMC 的 GetMaxSpeed 读取属性时，属性变化不在 SavedMove 中，高延迟下会出现轻微校正。要求严格时，应该扩展 CMC 的 SavedMove 标志位
    SetActorLocation / LaunchCharacter否只在服务器调用时会表现为延迟和拉扯

    13.5 专题五：RPC 批处理

    一个"点一下就打完"的射击技能，正常要发三个 RPC：激活、TargetData、结束。连发武器每秒十几发时，开销很可观。GAS 提供了 RPC 批处理，把这些合并成一个 ServerAbilityRPCBatch：

    开启批处理
    // 1) 自定义 ASC 中开启
virtual bool ShouldDoServerAbilityRPCBatch() const override { return true; }

// 2) 在激活技能的地方开启批处理作用域
{
    FScopedServerAbilityRPCBatcher Batcher(ASC, AbilitySpecHandle);
    ASC->TryActivateAbility(AbilitySpecHandle);   // 技能内部同步完成：发送 TargetData + EndAbility
}   // 作用域结束时，三个 RPC 合并成一个发出
    ⚠️ 适用前提

    批处理只在技能在同一帧内同步完成（激活 → TargetData → 结束）时才有意义。需要等待动画或输入的技能，没法合并。

    13.6 专题六：GameplayEvent 不会自动同步

    现象：客户端发送了 SendGameplayEventToActor，服务器上的 WaitGameplayEvent 一直收不到。

    原因：GameplayEvent 只是本地函数调用，本身不会走网络。唯一的例外是：事件触发了一个本地预测技能的激活，这时 Payload 会随 ServerTryActivateAbilityWithEventData 一起发给服务器。

    对策：需要两端都收到的事件，应该让两端各自产生（例如来自两端都会播放的 Montage 中的 AnimNotify，注意 13.2 中提到的专用服务器问题）；或者使用 ServerSetReplicatedEvent / 自定义的 Reliable RPC 传递。

    13.7 专题七：WaitNetSync

    有时需要保证两端执行到同一位置后再继续，例如"客户端决定了某个值，服务器必须先收到这个值再继续执行"。WaitNetSync 有三种模式：

    模式行为
    OnlyServerWait客户端发出信号后立即继续（打开新的预测窗口）；服务器等待收到信号后再继续
    OnlyClientWait服务器发出信号后继续；客户端等待
    BothWait两端互相等待（会产生一个完整 RTT 的停顿）

    官方建议：GA 中不要使用 Replicated 属性传值（5.5 已废弃），因为属性复制和激活 RPC 之间没有顺序保证。同一 Actor 上的 Reliable RPC 之间是有序的，用 RPC + WaitNetSync 才能得到可靠的时序。

    13.8 专题八：命中特效的预测

    伤害结算在服务器，但射击游戏的命中火花必须立即出现。常见做法是：客户端根据本地射线检测的结果，用非复制的本地 Cue 播放命中效果；服务器结算后，模拟端通过服务器的 Cue 看到同样的效果，拥有者则跳过（避免重复）。伤害数字等依赖结算结果的表现，等服务器结果到达后再显示。

    13.9 专题九：安全与反作弊

    服务器会重新检查

    即使是 LocalPredicted 技能，服务器收到激活请求后也会重新执行 CanActivateAbility（冷却、消耗、Tag）。客户端改内存跳过冷却，服务器仍会拒绝。

    敏感技能由服务器激活

    使用 NetSecurityPolicy = ServerOnlyExecution，或者 NetExecutionPolicy = ServerOnly / ServerInitiated，客户端无法请求激活。

    校验 TargetData

    客户端发来的命中目标必须校验：距离、视线、射速、目标是否存活。数值计算全部放在服务器的 Execution 中。

    事件 Payload 不可信

    由客户端事件激活的技能，Payload 来自客户端。不要直接把 Payload 中的数值（例如 EventMagnitude）当作伤害使用。

    13.10 专题十：带宽、相关性与测试

    • PlayerState 始终相关：PlayerState 默认 bAlwaysRelevant，ASC 放在 PlayerState 上时，属性和 Cue 会同步给所有客户端，与距离无关。玩家很多的模式（例如大逃杀）需要评估这部分带宽：把只有自己需要的属性设为 COND_OwnerOnly，或者让部分逻辑走 Pawn 上的数据。
    • 属性复制条件：蓝量、能量、经验等只需要自己看到的属性使用 COND_OwnerOnly。
    • 小兵使用 Minimal 模式，并且尽量少挂常驻 GE；可以用 Tag 表示的状态就不要用 GE。
    • Iris：UE5 新的复制系统 Iris 已经对 GAS 做了适配，新项目可以评估，但请以所用引擎版本的实际支持情况为准。
    • 测试：PIE 中选择 Play As Client，并开启 Network Emulation（Bad 预设），或者在控制台输入 Net PktLag=150、Net PktLoss=5。p.NetShowCorrections 1 可以显示移动校正。所有技能都应该在 150ms 延迟、5% 丢包的环境下测试一遍。
    本章小结
    • 冷却：客户端比服务器早开始、早结束，用服务器时间显示，配合输入缓冲。
    • 动画用 PlayMontageAndWait；位移用 RootMotion Task；专用服务器要确保动画 Tick。
    • TargetData：客户端瞄准，服务器校验后结算；GameplayEvent 本身不同步。
    • 上线前，所有技能都要在高延迟、丢包的模拟环境下测试。

    UAbilitySystemComponent* ASC = GetAbilitySystemComponentFromActorInfo();

    const int32 Stacks = ASC->GetAggregatedStackCount(Q);

    if (Stacks >= 3)

        FGameplayEffectSpecHandle Spec = MakeOutgoingGameplayEffectSpec(DamageGE, GetAbilityLevel());
        Spec.Data->SetSetByCallerMagnitude(MyTags::SetByCaller_Damage, 60.f);
        Spec.Data->SetSetByCallerMagnitude(MyTags::SetByCaller_APCoef, 0.4f);
        Spec.Data->AddDynamicAssetTag(MyTags::Damage_Type_Magic);
        if (UAbilitySystemComponent* TargetASC = UAbilitySystemGlobals::GetAbilitySystemComponentFromActor(Payload.Target.Get()))
        {
            ASC->ApplyGameplayEffectSpecToTarget(*Spec.Data.Get(), TargetASC);
        }
        ASC->RemoveActiveEffects(Q);
    }
    else
    {
        // GE_BlazeStack：HasDuration 5s · AggregateByTarget · 上限 3 · 刷新持续时间 · 授予 State.Buff.Blaze
        ApplyGameplayEffectToOwner(CurrentSpecHandle, CurrentActorInfo, CurrentActivationInfo,
                                   BlazeStackGE.GetDefaultObject(), GetAbilityLevel());
    }
}

    14.8 R · 烈焰领域：地面选择 + 周期伤害

    1. 技能激活后使用 WaitTargetData，TargetActor 选用 GameplayAbilityTargetActor_GroundTrace，ConfirmationType = UserConfirmed，地面显示范围指示器。
    2. 玩家确认后，客户端把落点打包成 TargetData 发给服务器（13.4）；按右键取消则调用 CancelAbility，此时还没有 Commit，所以不会进入冷却。
    3. 收到 TargetData 后 Commit（扣蓝、进冷却），服务器校验施法距离，然后生成复制的 AFlameFieldActor（持续 4 秒）。领域的视觉效果由这个 Actor 自己的 Niagara 组件负责，因为 Actor 本身就是复制的。
    4. 领域 Actor 每 0.5 秒在服务器上检测范围内的敌人，施加 GE_Burn：HasDuration 1 秒、Period 0.5 秒、AggregateBySource、上限 1 层、刷新持续时间。站在领域里时持续时间不断被刷新；离开后最多再烧 1 秒。
    5. GE_Burn 上挂 GameplayCue.Status.Burn（Looping），目标身上会出现火焰；伤害数字由每次周期执行时的跳字 Cue 显示。
    ✅ 为什么用"刷新的短 DOT"而不是"进入时施加、离开时移除"

    "离开时移除"需要可靠地检测离开（目标死亡、传送、领域消失都要处理），而且 GE 的移除不能预测。用"持续时间很短、不断刷新"的 GE，在离开后自然过期，没有遗漏状态的风险，逻辑也更简单。

    15.3 性能要点

    GE 数量

    每个 ActiveGE 都占用内存和复制开销。能用一个 GE 加 Stacking 实现的，不要创建多个独立 GE；能用 Tag 表示的简单状态，不需要一个空的 Infinite GE。

    聚合器重算

    不快照的 Attribute Based Modifier 会在源属性每次变化时重新计算。依赖链很长时（A → B → C），一次修改会引发多次重算，要控制派生属性的层数。

    Tick 型 Task

    bTickingTask 的 Task 每帧都会执行，大量单位同时使用时开销明显。能用事件或计时器解决的，不要用 Tick。

    InstancedPerExecution

    每次激活都创建一个 UObject，会增加 GC 压力。普攻这类高频技能必须使用 InstancedPerActor。

    Cue 加载

    GameplayCueManager 默认会加载配置目录下的所有 Cue。Cue 多的项目应限制 GameplayCueNotifyPaths，并按需异步加载（Lyra 的 ULyraGameplayCueManager 就是这样做的）。Actor 类 Cue 开启对象池复用。

    复制

    AI 使用 Minimal；只有自己需要的属性设为 COND_OwnerOnly；Full 模式要先做带宽分析；PlayerState 始终相关这一点要纳入评估（13.10）。

    PredictionKey客户端生成的预测 ID，用于关联预测副作用与服务器结果
    Prediction Window存在有效预测 Key 的代码作用域
    CaughtUp / Rejected预测 Key 被服务器确认追平 / 被拒绝
    Replication ModeFull / Mixed / Minimal，决定 GE 信息的复制范围
    TargetData可复制的目标信息容器
    GameplayCue由 Tag 驱动的表现层回调

    流程速查卡

    技能激活

    TryActivate
    → CanActivate（Tag / Cost / CD / Block）
    → PreActivate（OwnedTags / Cancel / Block）
    → ActivateAbility
    → CommitAbility
    → Tasks…
    → EndAbility / CancelAbility

    GE 施加

    MakeOutgoingSpec（源快照）
    → SetByCaller
    → Apply → 免疫 / 条件 / 概率
    → Instant：Execute → 改 Base → Executed Cue
    → Duration：叠层 or 新建 ActiveGE
    　→ Modifier 入聚合器 → Tags → OnActive/WhileActive

    属性回调

    PreGEExecute
    → PreAttributeBaseChange → Base
    → PreAttributeChange → Current
    → PostAttributeChange
    → PostGEExecute

    预测

    客户端：窗口生成 Key → RPC → 本地执行
    服务器：用同一 Key 执行 → Succeed/Failed
    　→ 窗口结束写入 KeyMap
    客户端：CaughtUp → 换成服务器版本
    　　　　Rejected → 撤销全部副作用

    ((Base + ΣAddBase)
    × (1+Σ(M−1)) ÷ (1+Σ(D−1))
    × ΠCompound) + ΣAddFinal

    Full：所有人收到完整 GE
    Mixed：拥有者完整，其他人 Tag + Cue
    Minimal：所有人只有 Tag + Cue
