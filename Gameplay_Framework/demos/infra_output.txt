
==================== G1 多播委托：一个监听者抛异常，同一事件后面的监听者也收不到 ====================
第 1 帧：UI分数 成就系统(抛异常) → 异常逃出 Update 
第 2 帧：（无派发：被打断时剩下的事件还留在旧 front，这一帧 swap 后它变成了 back）
第 3 帧：[另一事件的监听者] 
→ “音效”永远收不到这一次事件；同一帧排在后面的另一个事件晚了 2 帧

==================== G2 事件延迟：Trigger 在 World.Update 中发出，A→B→C 三级事件链各在第几帧被处理 ====================
World.Update 先执行      ：A 在第 0 帧，B 在第 1 帧，C 在第 2 帧（Trigger 发生在第 0 帧）
EventSystem.Update 先执行：A 在第 1 帧，B 在第 2 帧，C 在第 3 帧（Trigger 发生在第 0 帧）
→ 每多一级“回调里再发事件”，就多 1 帧；起点延迟 0 或 1 帧取决于未定义的脚本执行顺序

==================== G3 优先级：Logic 洪水下 Appearance 是否被饿死、各级容量是否独立 ====================
单帧 Trigger Logic×2500 + Appearance×10：派发 Logic 2000、Appearance 10，丢弃 500（只丢 Logic 级的溢出）
派发顺序前 4 个：L L L L；Max 级队列长度 0（分配了 2×2000 槽但永远为空）

==================== G4 RingBuffer：回绕与满/空判断（capacity=3） ====================
初始                 head=0 tail=0 size=0
入队 1,2,3（满）  head=0 tail=0 size=3
再入队 4 → false（满）
出队 → 1           head=1 tail=0 size=2
入队 4（tail 回绕到 0） head=1 tail=1 size=3
全部出队 → 2 3 4  head=1 tail=1 size=0
→ “满”和“空”时都是 head==tail，靠 size 区分；若不存 size，就要浪费一个槽或用单调递增计数

==================== G5 出队不清槽：T 是“含引用的结构体”时，payload 被缓冲区钉住 ====================
T=struct{int, ref}，按源码 IsValueType=true 不清槽：出队并丢弃后 payload 仍存活=true
若改为“含引用就清槽”：出队并丢弃后 payload 仍存活=false

==================== G6 下标回绕：% capacity vs & (capacity-1)（每次入队+出队，ns/次） ====================
capacity=2000  取模 2.20 ns  （不是 2 的幂，不能用位与）
capacity=2048  取模 2.18 ns  位与 0.40 ns
→ 容量是运行期变量时编译器无法把 % 优化掉；差距在纳秒级，对每帧几十个事件无意义

==================== G7 线程安全队列：lock 版（源码移植）vs 无锁 SPSC，传递 400 万个 int（容量 1024） ====================
lock 版  1 生产者 1 消费者：  167.8 ms（ 23.8 M/s） 每个生产者内 FIFO=OK 校验和=OK
lock 版  4 生产者 1 消费者：  722.2 ms（  5.5 M/s） 每个生产者内 FIFO=OK 校验和=OK
无锁 SPSC 1 生产者 1 消费者：   17.7 ms（226.6 M/s） FIFO=OK 校验和=OK
→ 源码 RingBufferStressTest 只计数且入队值恒为 1，验证不了 FIFO；这里给每个值编号后逐个校验

==================== G8 false sharing：两个线程各自累加自己的计数器 5000 万次 ====================
两个计数器相邻（同一 cache line）：540 ms
各自对齐到 64 字节：            182 ms  → 慢 3.0 倍只因为共享了 cache line

==================== G9 ObjectPool：LIFO 复用、扩容、容量 0、错配回收 ====================
容量 4：先取 a=3 b=2，归还 a 后再取 c=3 → Stack 让刚归还的槽立刻被复用（LIFO）
容量 2 连取 5 个：槽位依次 1 0 3 2 7 ，共 new 了 8 个对象（2→4→8 两次扩容，每次预先 new 满新容量）
容量 0：Acquire=false（0×2=0，ReAllocate 返回 true 却什么也没分配，永远取不到）
用 {a 的对象, b 的槽位} 回收：Recycle=true → a 的对象被 OnRecycle（inUse=false），b 的槽位被标记可用但 b 仍在用（inUse=true）
    再 Acquire 一次拿到槽位 2，它的对象就是 b 正在用的那个（同一对象被两人持有=true）

==================== G10 日志落盘（Windows 11 + NTFS，含杀毒实时扫描，数字只看量级）：每行打开-追加-关闭 vs 攒满 2048 字符再写（10000 行，每行约 60 字符） ====================
