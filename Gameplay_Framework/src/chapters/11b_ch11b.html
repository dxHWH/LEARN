11B.3 池放在哪一层：三种方案

方案谁拥有池优点问题
A · GameMode 自己持有（原代码的思路）SurvivalGameMode直观每个 GameMode 重写一遍；Pawn / Controller 死亡时得反过来找 GameMode（RecycleObject + _activeWrappers 字典）；规则对象兼做工厂，职责混乱
B · 全局 PoolManager 单例DontDestroyOnLoad 的单例任何地方都能用闲置对象是场景物体，切场景要么被销毁、要么全部跨场景常驻；World 是场景级的，池里的 Actor 会引用已销毁的 World；单例的所有问题（第 6 章）

11B.4 L0：带 generation 的 ObjectPool<T>

在原 ObjectPool 的基础上改四件事：借条带代数；工厂由调用方提供（不再要求 new() 和 IPoolable，从而可以池化 MonoBehaviour）；归还时先失效再回调；闲置数有上限。思路和第 9 章 TimerSystem 的 Slot Map 一致，只是不需要 dense 数组（池子不需要每帧遍历）。

public readonly struct PoolHandle : IEquatable { public readonly int Index, Generation; // Generation 从 1 开始：default(0,0) 永远无效 public PoolHandle(int index, int generation) { Index = index; Generation = generation; } public bool Equals(PoolHandle o) => Index == o.Index && Generation == o.Generation; public override int GetHashCode() => HashCode.Combine(Index, Generation); } public sealed class ObjectPool where T : class { private struct Slot { public T Item; public int Generation; public bool InUse; } private Slot[] _slots = new Slot[8]; private int _slotCount; private readonly Stack _free = new Stack(); // 仍是 LIFO：刚还的最先借出（缓存友好） private int _idleItems; private readonly Func _create; private readonly Action _onRelease, _onDestroy; private readonly int _maxIdle; public ObjectPool(Func create, Action onRelease = null, Action onDestroy = null, int prewarm = 0, int maxIdle = 64) { _create = create ?? throw new ArgumentNullException(nameof(create)); _onRelease = onRelease; _onDestroy = onDestroy; _maxIdle = maxIdle; for (int k = 0; k < prewarm; k++) { int i = NewSlot(); T item = _create(); _slots[i].Item = item; _free.Push(i); _idleItems++; } } private int NewSlot() { if (_slotCount == _slots.Length) Array.Resize(ref _slots, _slots.Length * 2); _slots[_slotCount].Generation = 1; return _slotCount++; } public PoolHandle Acquire(out T item) { int i = _free.Count > 0 ? _free.Pop() : NewSlot(); if (_slots[i].Item != null) _idleItems--; else { T created = _create(); _slots[i].Item = created; } // 先求值再写回：见下方说明 _slots[i].InUse = true; item = _slots[i].Item; return new PoolHandle(i, _slots[i].Generation); } public bool IsValid(PoolHandle h) => (uint)h.Index < (uint)_slotCount && _slots[h.Index].InUse && _slots[h.Index].Generation == h.Generation; public bool TryGet(PoolHandle h, out T item) { bool ok = IsValid(h); item = ok ? _slots[h.Index].Item : null; return ok; } public bool Release(PoolHandle h) { if (!IsValid(h)) return false; // 旧借条 / 默认借条 / 重复归还 → 拒绝 T item = _slots[h.Index].Item; _slots[h.Index].InUse = false; if (++_slots[h.Index].Generation == 0) _slots[h.Index].Generation = 1; // 回绕时跳过 0 _onRelease?.Invoke(item); // 回调在失效之后：回调里重入 Release 同一借条会被拒绝 if (_idleItems >= _maxIdle) { _slots[h.Index].Item = null; _onDestroy?.Invoke(item); } else _idleItems++; _free.Push(h.Index); return true; } }
原 ObjectPool.cs新设计为什么
where T : class, IPoolable, new()Func<T> create + 回调MonoBehaviour 不能 new；回调非侵入，T 不必实现接口（与 UnityEngine.Pool 的设计一致）
PoolObject { elem, index }PoolHandle { Index, Generation }，对象由池按句柄取出借条里不放对象引用，也就不会出现“elem 和 index 来自不同租借”的错配（第 11 章 G9）
只检查 IsAvailable检查 InUse + Generation拦截旧拷贝和默认借条（H1-a、H1-b）
先 OnRecycle，再标记可用先失效（代数 +1），再回调回调里重入归还不会让槽位入栈两次（H1-c）
容量翻倍时预先 new 满按需创建 + 可选预热扩容那一帧不再集中分配；预热数量由业务决定
只增不减maxIdle：超出的直接销毁峰值过后内存能还回去
两个容易写错的细节（都和第 10 章的“ref 跨扩容”是同一类问题）

① _slots[i].Item = _create(); 不安全。C# 对数组元素赋值时，会先读取 _slots 字段和下标 i，再执行右边的 _create()，最后写回。如果工厂里间接触发了同一个池的扩容（Array.Resize 替换了 _slots），结果会写进旧数组，新数组里这一格仍然是 null。所以先用局部变量接住，再写回。

② 不要在回调前后持有 ref Slot。Release 里调用 _onRelease 之后，如果用之前取到的 ref 去写 Item = null，同样可能写进旧数组。上面的骨架每次都用 _slots[h.Index] 重新索引。

【实测 H1】同一组操作，原池与新池的对比：

操作原 ObjectPool新 ObjectPool
a) 借 a → 拷贝借条 → 归还 a → 借 b（LIFO 拿到同一槽）→ 用旧拷贝归还成功：b 正在用的对象被回收拒绝：a=(0,1)、b=(0,2)，代数对不上
b) 槽 0 在用时归还 default 借条通过检查，对 null 调 OnRecycle（C# 中 NullReferenceException）拒绝：代数从 1 开始
c) OnRecycle 回调里再归还同一个对象槽位入栈两次，接下来两次借出拿到同一对象内层归还被拒绝
d) 同一借条归还两次拒绝（IsAvailable）拒绝

11B.5 Actor 的池化生命周期

11B.5.1 先确认三条 Unity 规则

【Unity 规则】对设计的影响
挂在未激活 GameObject 上的脚本，Awake 要等到 GameObject 第一次被激活时才调用；OnEnable / OnDisable 随 SetActive 触发工厂必须先 SetActive(false) 再 AddComponent，否则预热出来的对象会立刻 Awake、Start，并在 Start 里被 World 当成活 Actor 注册（原 AActor.Start 无条件注册）
Start 每个组件一生只调用一次不能靠 Start 做“每次出池”的初始化，也不能靠它注册——池化 Actor 的注册要由 SpawnActor 显式完成
SetActive(false) 不会触发 OnDestroy不能靠 OnDestroy 注销——回收时 World 要显式注销

11B.5.2 AActor 新增的成员

public enum EEndPlayReason { Destroyed, ReturnedToPool, LevelUnload } public class AActor : MonoBehaviour { public bool HasBegunPlay { get; private set; } public bool IsTickEnabled { get; set; } = true; // ---------- 新增：销毁与池化 ---------- public bool IsPendingKill { get; private set; } // 已被 DestroyActor，等待帧末处理：不 Tick、不参与结算 public PoolHandle PoolHandle { get; internal set; } // default = 不来自对象池（或已归还） internal ActorPool OwnerPool { get; set; } // null = 普通 Actor，帧末走 Destroy protected virtual void Start() { if (OwnerPool == null) World.RegisterAActor(this); // ★ 池化 Actor 只由 SpawnActor 注册 } protected virtual void OnDestroy() { if (World.HasInstance) World.UnregisterAActor(this); } // 不变 public virtual void BeginPlay() { HasBegunPlay = true; } public virtual void EndPlay(EEndPlayReason reason) { HasBegunPlay = false; } // ★ 与 BeginPlay 成对；下次出池会再次 BeginPlay protected internal virtual void OnTakeFromPool() { } // 出池：SetActive(true) 之后、BeginPlay 之前 protected internal virtual void OnReturnToPool() { } // 入池：EndPlay 之后、SetActive(false) 之前——复位并清掉引用 internal void MarkPendingKill() => IsPendingKill = true; internal void ClearPendingKill() => IsPendingKill = false; } // APawn：离开游戏前先解除附身（Pawn 死了，灵魂必须知道） public override void EndPlay(EEndPlayReason r) { if (Controller != null) Controller.UnPossess(); base.EndPlay(r); } // AController：灵魂离开游戏，肉体变回无主 public override void EndPlay(EEndPlayReason r) { if (ControlledPawn != null) UnPossess(); base.EndPlay(r); }

三个钩子分工明确，面试时最好能一句话说清：

钩子何时调用负责什么SoulDecay 里放什么
EndPlay(reason)销毁和入池都会调用“离开游戏”：解除 Possess、停止计时器、注销事件——和是否池化无关的清理CombatPawn 停寿命计时器；APawn / AController 解除附身
OnReturnToPool()只在入池时“清理残留”：复位字段、去掉对外引用，让闲置对象不钉住别的东西isDying、碰撞体、名字、颜色、阵营
OnTakeFromPool()只在出池时“准备上场”：与位置相关、必须在激活后做的设置清刚体速度
BeginPlay()每次出池后的下一次 World.Update游戏逻辑的初始化（和非池化 Actor 完全一样）SimpleAIController 重新随机 Perlin 偏移
复位放在入池时还是出池时

两种都有人用。这里的建议是：清引用放在入池时（否则闲置对象会钉住它引用的东西，第 10 章 E13、第 8 章 G5 是同类问题），与新位置、新主人相关的设置放在出池时。只在一处复位也可以，但要保证覆盖所有字段——漏掉一个，就是“上一任的残留”。

11B.6.1 为什么回收要延迟到帧末

原代码之所以“在 Tick 里 Destroy 没出事”，是因为 Unity 的 Destroy 本身就是延迟到帧末的——OnDestroy（进而 List.Remove）不会在 World 的遍历中途发生。池化之后如果立即 SetActive(false) + 注销，就等于在倒序遍历中途修改 _actors，第 3 章的问题全部回来。【实测 H2】：

场景（Tick 中回收）立即回收标记 PendingKill，帧末回收
A3 回收 A1（玩家夺舍 → 被踢出的 AI 灵魂回收）A3 被 Tick 2 次每个 Actor 至多 1 次；A1 已“逻辑死亡”，本帧不再 Tick
A4 一次回收 A0、A1、A2越界，本帧 World.Update 中止，A3 没有被 Tick正常结束，A3、A4 各 1 次
A2 回收自己正常正常

同样的道理也适用于另外两个调用时机：物理回调（OnCollisionEnter 里碾碎对方）和计时器回调（寿命到期 → Die）。在帧末统一处理，这三处都不用关心“我现在是不是在别人的遍历里”。这和 Unity 的 Destroy、UE 的“标记待销毁、之后再真正清理”是同一个思路。

IsPendingKill 顺带修好了第 15 章的“重复计分”

第 15 章指出：同一物理步里两具大肉体撞同一具小肉体，Die 会被调用两次、加两次分。现在 Die 和 OnCollisionEnter 都先检查 IsPendingKill，第二次结算直接返回；DestroyActor 本身也是幂等的。

11B.7 延迟回收与 ABA：尸体为什么要用借条

原代码里玩家抛弃的旧肉体用 Destroy(gameObject, 3.0f) 延迟销毁。Unity 的延迟销毁没有 ABA 问题，因为被销毁的对象永远不会回来。池化之后，“3 秒后回收这个对象”就变成了“3 秒后回收这个槽位上的东西”——如果这 3 秒内它被提前回收并借给了别人，到期时回收的就是别人。

同样需要用借条（或 generation）的地方，在这个项目里还有：UI 持有的寿命 TimerHandle（已经有 generation，所以安全）；以后如果 GameMode 用列表记录“场上所有 AI”，列表里也应该存句柄而不是引用。

11B.8 ActorPool：GameObject 怎么出池、入池

public sealed class ActorPool { private readonly ObjectPool _pool; private readonly Transform _root; // 闲置对象挂在 “[Pool] key” 下，Hierarchy 整洁 public string Key { get; } public ActorPool(string key, Func factory, int prewarm, int maxIdle) { Key = key; _root = new GameObject($"[Pool] {key}").transform; // 场景物体：随场景卸载一起销毁 _pool = new ObjectPool( create: () => { AActor a = factory(); a.transform.SetParent(_root, false); return a; }, onRelease: a => { a.OnReturnToPool(); a.gameObject.SetActive(false); a.transform.SetParent(_root, false); }, onDestroy: a => { if (a) Object.Destroy(a.gameObject); }, prewarm: prewarm, maxIdle: maxIdle); } internal AActor Take(Vector3 pos, Quaternion rot) { PoolHandle h = _pool.Acquire(out AActor a); a.PoolHandle = h; a.OwnerPool = this; a.ClearPendingKill(); a.transform.SetParent(null, false); a.transform.SetPositionAndRotation(pos, rot); // 先摆好位置再激活，避免物理在旧位置上跑一帧 a.gameObject.SetActive(true); // 第一次：Awake → OnEnable（Start 稍后）；之后：只有 OnEnable a.OnTakeFromPool(); return a; } internal void Return(AActor a) { PoolHandle h = a.PoolHandle; a.PoolHandle = default; _pool.Release(h); } internal bool IsAlive(PoolHandle h) => _pool.IsValid(h); }

ActorPool 只做三件和 Unity 有关的事：父节点、位置、激活状态。复位逻辑通过 OnReturnToPool 交给 Actor 自己——ActorPool 不知道 CombatPawn 有哪些字段。

11B.12 还有哪些替代做法

做法说明取舍
OnEnable / OnDisable 自动注册注销AActor 在 OnEnable 里注册、OnDisable 里 EndPlay + 注销，SetActive 自动驱动生命周期改动更少；但会改变所有 Actor 的注册时机（OnEnable 在创建调用内部就执行，比 Start 早），影响第 2 章“先 Possess 后 BeginPlay”的时序；场景卸载时 OnDisable 也会触发 EndPlay，需要区分原因
用 UnityEngine.Pool.ObjectPool 作为 L0createFunc / actionOnRelease / maxSize 都现成少写代码；但它直接返回对象、没有句柄。可以在 AActor 上加一个每次出池自增的 SpawnSerial，对外用 (对象, 序号) 作为句柄——这正是 UE 弱对象指针的思路
预制体为键RegisterPool(prefab) 代替字符串 key真实项目里 Actor 来自 Prefab，用 Prefab 引用做键更安全；Demo 是代码生成的原始体，用字符串更直接

11B.13 分四步迁移（每一步都能运行）

  1. 替换 L0：新 ObjectPool + PoolHandle，补 EditMode 单元测试（清单见 11B.14）。此时不接入任何东西。
  2. 统一死亡出口：AActor / APawn / AController 加 EndPlay 和 IsPendingKill，World 加 DestroyActor + LateUpdate；把项目里所有对 Actor 的 Destroy 换成 World.DestroyActor。这一步还没有池化，但已经修好了 Die 不幂等、Tick 中销毁的问题。
  3. 接入池：World 加 RegisterPool / SpawnActor 和 ActorPool；SurvivalGameMode 改为 SpawnActor（先不预热）；CombatPawn / SimpleAIController 实现 OnReturnToPool / OnTakeFromPool。
  4. 调参与清理：记录峰值后设定预热和 maxIdle；用 Profiler 确认 GC Alloc 和创建次数；删除 GameObjectWrapper 和 SurvivalGameMode 里的死代码。

Q11B-1 / Q11B-2　怎么设计？池放在哪？

L1 · 30 秒　分四层：底层是带代数的通用池，借条是槽位加代数；上面是按类型的 Actor 池，负责激活和父节点；再上面是 World 的 SpawnActor 和 DestroyActor，作为 Actor 唯一的出生和死亡入口；业务层只调用这两个函数，不知道对象是不是来自池。

L2 · 正常回答　池归 World 所有、由 GameMode 在 BeginPlay 里配置。归 World 是因为生命周期一致——都是场景级的，闲置对象是场景物体，切场景一起销毁；而且 World 本来就管 Actor 的注册注销。不放全局单例，是因为闲置对象跨场景会引用已经销毁的 World；不放 GameMode，是因为 Pawn 和 Controller 死亡时还得反过来找 GameMode，原来的接入代码就卡在这里，RecycleObject 一直没有调用方。

L3 · 深入　关键改动在 Actor 生命周期：加 EndPlay，与 BeginPlay 成对，销毁和入池都调用，负责解除附身、停计时器；加入池和出池两个钩子负责复位；加 IsPendingKill，DestroyActor 只做标记，真正的回收在 World 的 LateUpdate 统一执行。

L4 · 面试官攻击　“World 越来越胖了。” → 同意，它现在同时是注册表、调度器和工厂。我会把工厂和池拆成 World 持有的一个子系统（类似 UE 的 WorldSubsystem），World 只暴露 SpawnActor 和 DestroyActor 两个入口。接口不变，内部可以拆。

Q11B-3 / Q11B-4　出池后怎么重新 BeginPlay？为什么不用 OnEnable？

L2　EndPlay 把 HasBegunPlay 清回 false，入池时 World 把它从名单里注销；出池时 SpawnActor 重新注册到 pending，下一次 World.Update 就会再次 BeginPlay，和新生成的 Actor 走同一条路径。池化 Actor 的注册只走 SpawnActor，AActor.Start 里遇到池化对象就不注册，避免它被重复注册或者在闲置时被注册。

L3　OnEnable / OnDisable 自动注册改动最少，但会改变所有 Actor 的注册时机：OnEnable 在 AddComponent 调用内部就执行，比 Start 早，会影响现在“先 Possess 后 BeginPlay”的时序；而且场景卸载时 OnDisable 也会触发，要另外区分。显式的入口更容易推理。

Q11B-5 / Q11B-6　在 Tick 里回收会怎样？

L2　如果立即 SetActive(false) 并从名单里移除，就是在倒序遍历中途修改列表：回收一个下标更小的 Actor，当前 Actor 会被 Tick 两次；一次回收多个，会越界、整帧中止。我用移植版测过这两种情况。所以 DestroyActor 只做标记：被标记的 Actor 本帧不再 Tick、不参与碰撞结算，在 LateUpdate 统一回收。

L3　原来用 Destroy 没出事，是因为 Unity 的 Destroy 本身就推迟到帧末，OnDestroy 不会在遍历中途发生。池化相当于把这个保护去掉了，所以要自己补回来。顺带 DestroyActor 变成幂等的，原来“两具大肉体同时撞一具小肉体会重复加分”的问题也一起修了。

Q11B-7　旧肉体 3 秒后回收，这 3 秒里它被复用了怎么办？（压力题）

L2　延迟回收的计时器不能捕获对象引用，要捕获安排那一刻的借条。到期时用借条问池子“它还是不是那一任”，代数不对就忽略。我测过：如果尸体在这 3 秒内被提前回收、又被刷怪借走变成一只红队 AI，只检查“对象是否活跃”的写法会把这只活着的 AI 回收掉；用借条的写法会忽略。

L3　池是 LIFO 的，刚还回来的对象最先被借出，所以一旦有提前回收的路径，这个问题几乎必然发生。这和计时器句柄是同一个问题：只要“延迟操作”指向一个可能被复用的东西，就需要代数。Unity 的 Destroy(obj, 3) 没这个问题，是因为被销毁的对象永远不会回来。

Q11B-8 / Q11B-9　复位放哪？业务要不要知道对象来自池？

L2　分两类：离开游戏的清理放 EndPlay，销毁和入池都调用；清残留引用放入池时，避免闲置对象钉住别的东西；与新位置相关的放出池时。漏字段的问题靠两件事兜：一张按资源列的清理清单；一个冒烟测试——同一对象复用多次后检查关键状态。业务层不需要知道：CombatPawn 只调用 DestroyActor，是销毁还是入池由 World 根据它有没有归属的池决定。

Q11B-10　这个 Demo 真的需要对象池吗？

L2　不需要。每 3 秒刷一只，不池化也不会卡。我按源码的刷怪规则、加上存活时间和夺舍频率的假设模拟了一局 10 分钟：不池化要创建约 400 次、销毁约 390 次；池化后只创建 21 次，按峰值预热后局内是 0。这说明的是次数，真实耗时要在 Profiler 里看。我做这件事的目的是让框架支持池化，以后接子弹、特效这种高频对象时可以直接用。

Q11B-11　多线程能从池里借对象吗？（发散）

L2　Actor 池不行：激活、改父节点、改位置都是 Unity API，只能在主线程。纯数据的池（比如网络消息包、寻路请求）可以做成线程安全的：最简单是加锁；高频时用每线程一个本地缓存、批量和全局池交换，这就是 tcmalloc 这类分配器“线程本地缓存”的思路，也和第 12 章“每个工作线程一个 SPSC 队列”是一个道理。

常见错误回答 ①

错误：“对象池就是 SetActive(false) 存起来、SetActive(true) 拿出来。”

问题：只说了激活状态。没说生命周期（Start 不会再调用、OnDestroy 不会触发）、状态复位、对外引用清理、借条安全——原 GameObjectWrapper 就停在这一步，H4 显示第二轮起出池的肉体已经是“死的”。

常见错误回答 ②

错误：“回收时我立刻把它放回池里，这样最省事。”

问题：回收经常发生在别人的遍历中（World 的 Tick、物理回调、计时器回调），立刻修改名单会重复 Tick 或越界（H2）。要么延迟到帧末，要么由遍历方保证安全。

本章速记
  • 半成品四个缺口：借条无代数、生命周期没接上、状态无复位点、死亡出口写死 Destroy；后三个是框架问题。
  • 四层：L0 ObjectPool<T>（槽位 + 代数，从 1 开始）→ L1 ActorPool → L2 World.SpawnActor / DestroyActor → L3 Demo；World 提供机制，GameMode 配置策略。
  • Actor 新增：EndPlay（销毁与入池共用）、OnReturnToPool（清残留）、OnTakeFromPool（准备上场）、IsPendingKill；池化 Actor 只由 SpawnActor 注册；工厂先失活再挂组件。
  • DestroyActor 只标记、幂等，LateUpdate 统一回收（H2）；延迟回收捕获借条（H3）。
  • SoulDecay：生成换成 SpawnActor，三处 Destroy 换成 DestroyActor，补复位；一局 10 分钟创建 401 次 → 21 次（H5）。
自测 1：工厂里如果不先 SetActive(false) 就 AddComponent<CombatPawn>()，预热 8 个对象会发生什么？

GameObject 处于激活状态，Awake、OnEnable 立即执行，Start 随后执行。在新 AActor.Start 中，这时 OwnerPool 还没有被设置（Take 之前），会走 World.RegisterAActor，于是 8 个“闲置”的肉体进入 World 名单、执行 BeginPlay 并开始 Tick，而且还显示在场景里。之后出池时 SpawnActor 再注册一次会被去重，但它们从未经过正确的状态机。

自测 2：入池时 APawn.EndPlay 调用 Controller.UnPossess()，CombatPawn.OnUnPossess 又调用 World.DestroyActor(this, 3f)。为什么不会出问题？

EndPlay 发生在 LateUpdate 的回收流程里，此时该 Actor 的 IsPendingKill 已经是 true，DestroyActor 开头的幂等检查直接返回，不会再建延迟计时器。

自测 3：ScheduleDestroy 里的 lambda 会分配吗？要不要优化？

会：它捕获了 h、pool、actor，每次调用分配一个闭包对象和一个委托。它只在玩家每次夺舍时发生一次，频率很低，不值得优化；需要时可以在 Actor 上存“待回收借条”字段，用一个缓存好的实例方法作为回调。
