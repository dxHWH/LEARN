CHAPTER 05

GameMode / GameState：规则、权威与可观察状态

裁判和计分板为什么要分成两个对象；“Authority”在一个单机项目里到底意味着什么；为什么场景里放两个 GameMode 并不会“忽略后注册的裁判”；以及名叫 ServerWorldTimeSeconds 的字段，离“服务器世界时间”有多远。

本章目标
  • 说清 GameModeBase / GameMode / GameStateBase / GameState 四个类各自负责什么，以及与 UE 的对应关系
  • 逐步讲出开局流程：注册裁判 → 反射生成计分板 → 担保注册 → 比赛状态机
  • 区分“注册时的权威校验”和“写入路径的权威收口”，并列出项目里绕过 GameMode 的写入口
  • 用实测说明两个 GameMode 并存时会发生什么、ServerWorldTimeSeconds 会偏多少
  • 回答“为什么 UI 读 GameState 不读 GameMode”，并延伸到状态同步、帧同步与 PlayerState

5.1 这一章解决什么问题

“GameMode 和 GameState 的区别”是 UE 面试的高频题，标准答案是“GameMode 只在服务器、管规则；GameState 复制给所有人、存状态”。但这个项目是单机，面试官一定会追问：单机里为什么还要分？你说 GameMode 是“权威”，权威体现在哪里？本章用源码回答：分开的价值是真实的，但当前实现里“权威”只体现在注册环节，写入路径并没有收口。

5.2 四个类的分工

5.3 开局流程逐步看

// AGameModeBase public override void BeginPlay() { base.BeginPlay(); World.RegisterGameMode(this); // “一定要先注册自身，再去注册 GameState” InitGameState(); StartPlay(); } // AGameMode override protected void InitGameState() { Type stateType = GameStateClass; // 子类 override：typeof(SurvivalGameState) GameObject gsObj = new GameObject($"GameState_{GetType().Name}"); base.GameState = gsObj.AddComponent(stateType) as AGameState; // 反射版 AddComponent if (World.HasInstance) World.Instance.RegisterGameState(this, GameState); // 裁判亲自担保 } SurvivalGameMode.BeginPlay └ AGameModeBase.BeginPlay ├ World.RegisterGameMode(this) → AuthorityGameMode = this ├ AGameMode.InitGameState → new GameObject + AddComponent(SurvivalGameState)（Awake 立即执行） │ └ World.RegisterGameState(this, gs) → authority == AuthorityGameMode ✓ → World.GameState = gs └ AGameMode.StartPlay → gs.SetMatchState(WaitingToStart) → Trigger(MatchStateChanged) ├ StartMatch() → gs.SetMatchState(InProgress) → Trigger(MatchStateChanged) ├ 生成玩家肉体 + 灵魂，Possess └ CreateTimer("AISpawner", 3 s, loop) 帧 1：SurvivalGameState 才 BeginPlay（广播三个阵营 0 分），才开始累加 ServerWorldTimeSeconds

三个容易被问到的细节：

  • 为什么“先注册自己”：RegisterGameState 会检查 authority == AuthorityGameMode，裁判没登记，计分板就会被当成越权注册而销毁。顺序依赖写在注释里，没有写在代码结构里。
  • GameState 在 BeginPlay 之前就被改了状态：EnteringMap → WaitingToStart → InProgress 都发生在帧 0，而 GameState 自己的 BeginPlay 在帧 1。和第 2 章的“先 Possess 后 BeginPlay”是同一个现象。
  • 同一帧连发两次状态事件：如果有 UI 监听，它会在派发时依次收到 WaitingToStart 和 InProgress，中间状态只停留了“零帧”。SoulDecay 没有监听者，EventSystem 的 Trigger 在找不到监听者时直接 return，这两个事件根本没进队列。

5.4 GameStateClass：Type + 反射，以及三个同名属性

5.4.1 用 Type 指定类，没有编译期约束

public virtual Type GameStateClass => typeof(AGameState); 返回的是任意 System.Type。如果子类写成了一个不继承 AGameState 的类型，AddComponent(stateType) as AGameState 会得到 null（不是 MonoBehaviour 的类型则直接抛异常），随后 RegisterGameState 在打印日志时访问 newGameState.GetType() 抛空引用。错误要到运行时才暴露。

写法约束发生在例子
Type + 反射（本项目）运行时override Type GameStateClass => typeof(SurvivalGameState)
泛型参数 + where 约束编译期GameMode 带一个“TState : AGameState”的类型参数
UE 的 TSubclassOf<AGameStateBase>编辑器选择时 + 编译期GameMode 的 GameStateClass 属性，只能选派生类

5.4.2 三个同名属性：new 隐藏而不是 override

AGameModeBase public AGameStateBase GameState { get; protected set; } AGameMode public new AGameState GameState => base.GameState as AGameState; SurvivalGameMode public new SurvivalGameState GameState => base.GameState as SurvivalGameState;

new 是“隐藏”：调用哪个属性取决于引用的静态类型，不是对象的实际类型。World.Instance.AuthorityGameMode.GameState 的静态类型是 AGameModeBase，拿到的永远是 AGameStateBase。项目里大家都改用 World.Instance.GameState is SurvivalGameState gs 来取，这又引出了第二个问题：World 和 GameMode 各存了一份 GameState 引用（5.5 节）。UE 用模板函数 GetGameState<T>() 解决“按需向下转型”，只有一份存储。

5.5 “Authority”：校验了注册，没有收口写入

World 的字段名是 AuthorityGameMode，RegisterGameState 里有“越权警告”。但看一下 SoulDecay 里所有改变比赛结果的地方：

改了什么谁改的代码位置经过 GameMode 吗
玩家夺舍得分SoulPlayerControllergameState.AddScore(EFaction.Player, 1)（SoulPlayerController.cs:59-63）否
碾压得分CombatPawngameState.AddScore(mySoul.FactionId, 1)（CombatPawn.cs:145-148）否
结束比赛CombatPawnWorld.Instance.AuthorityGameMode.EndMatch()（CombatPawn.cs:164）调用了，但“该不该结束”是 Pawn 决定的
比赛阶段任何人AGameState.SetMatchState 是 public（注释：“供裁判调用的唯一修改接口”）没有限制
World 的计分板引用任何人World.GameState { get; set; }（World.cs:21）setter 是 public，可绕过担保注册

结果就是第 15 章 15.8 节记录的现象：玩家死亡、比赛进入 WaitingPostMatch 之后，AI 之间仍然在碾压、仍然在加分——因为“比赛结束后不再计分”这条规则没有地方可以写：AddScore 不校验阶段，加分的决定也不是 GameMode 做的。

面试注意：单机里的 Authority 该怎么说

不要说成“网络权威”。准确的说法：“在单机里，GameMode 的 Authority 指它是规则的唯一裁决者：其它对象只上报事实（我撞到了谁、我的寿命到了），由 GameMode 判断要不要加分、要不要结束比赛，再写入 GameState。我的实现里只做到了注册环节的校验，写入路径还散在 Pawn 和 Controller 里，这是我复盘时最想改的设计问题。”——同时承认现状、给出原则，面试官通常会接着问“那联网之后呢”，正好进入 5.9 节。

5.6 实测：场景里放了两个 GameMode

RegisterGameMode 里写着“场景中存在多个裁判！将忽略后注册的裁判！”。但它只是 return 了自己，调用它的 BeginPlay 并没有停下来。移植版 F4 复刻了 AGameModeBase / AGameMode / World 的注册逻辑和 SurvivalGameMode.BeginPlay 的后续步骤：

GM_A.BeginPlay World.RegisterGameMode：成为 AuthorityGameMode World.RegisterGameState：注册 GameState_GM_A GameState_GM_A：EnteringMap → WaitingToStart → EventSystem.Trigger GameState_GM_A：WaitingToStart → InProgress → EventSystem.Trigger 生成玩家肉体 + SoulPlayerController 并 Possess CreateTimer("AISpawner")：新建 GM_B.BeginPlay World.RegisterGameMode：已有裁判 → Log.E 并 return（但 BeginPlay 继续执行） World.RegisterGameState：越权 → Destroy(GameState_GM_B)（延迟），return GameState_GM_B：EnteringMap → WaitingToStart（已被拒绝，帧末才消失）→ EventSystem.Trigger GameState_GM_B：WaitingToStart → InProgress（已被拒绝，帧末才消失）→ EventSystem.Trigger 生成玩家肉体 + SoulPlayerController 并 Possess CreateTimer("AISpawner")：同名计时器仍有效 → 先 Stop 旧的（属于 GM_A）再新建
“被忽略”的 GM_B 实际造成了原因
MatchStateChanged 多 Trigger 2 次（共 4 次）被拒绝的 GameState 因为 Destroy 延迟，本帧仍能 SetMatchState 并发事件
多出一具玩家肉体和一个 SoulPlayerControllerBeginPlay 照常执行；两个 Controller 读同一份输入，两具肉体同步移动
AISpawner 的回调换成了 GM_B 的同名 CreateTimer 会停掉旧的再新建（第 10 章 10.2 #7）
GM_B 的“比赛结束就不刷怪”检查永远不成立它的 GameState 帧末已销毁，base.GameState != null 为 false，跳过了阶段判断（好在 EndMatch 按名字停掉了 AISpawner）

这说明“拒绝注册”和“让这个对象停止工作”是两回事。拒绝之后至少要让 BeginPlay 停止执行（返回一个是否成功的结果），或者直接禁用 / 销毁多余的 GameMode。

5.7 为什么 UI 读 GameState，而不读 GameMode

GameMode（规则）GameState（可观察状态）
回答的问题“该怎么办”：何时开始、谁得分、何时结束、生成什么“现在怎样”：第几阶段、几分、过了多久
谁需要它只有做决策的一方所有要显示或响应状态的一方（UI、音效、AI）
联网时只在服务器存在，客户端拿不到复制给所有客户端
本项目里 UI 怎么拿不读SurvivalUIController 监听分数事件（push）；寿命则拿到句柄后每帧向 TimerSystem 拉取（pull）

单机里分开的价值是依赖方向：UI 只依赖“状态”，规则怎么改都不影响 UI；以后改成联网，UI 代码不用动。项目的 SoulDecay UI 确实只依赖 GameState 发出的事件和 TimerSystem，这一点是做对了的。

【问题】计分板的“状态”其实不完整

寿命剩余时间不在 GameState 里，UI 要先从事件里拿到计时器句柄，再每帧问 TimerSystem；比赛结束（WaitingPostMatch）SoulDecay 的 UI 也没有监听，界面上只能靠寿命文字变成“DIE”间接看出来。“所有 UI 需要的状态都在 GameState 上”这个原则只做到了一半。

5.8 实测：ServerWorldTimeSeconds 离“服务器时间”有多远

AGameStateBase.Tick 里只有一行：ServerWorldTimeSeconds += deltaTime;。名字借自 UE（那里是服务器通过复制同步给客户端的世界时间），这里却是：本地的、scaled 的、被 maximumDeltaTime 截断的、从 GameState BeginPlay 才开始的 float 累加。移植版 F5：

真实经过 120.017 s → ServerWorldTimeSeconds = 109.476 s （差 10.541 s：暂停 10 s + 两次 0.6 s 卡顿各被截断成 0.333 s + 少算第 1 帧） 连续 1 小时 60fps：float 累加 = 3597.21 s，double = 3600.00 s，误差 2.79 s（0.078%） 连续 10 小时 60fps：float 累加 = 36544.82 s，double = 36000.00 s，误差 −544.82 s（−1.513%） 连续 100 小时 60fps：float 累加 = 418445.66 s，double = 360000.00 s，误差 −58445.66 s（−16.235%）

这里有两类偏差：语义偏差（暂停、截断、晚一帧开始），这是选择了 scaled 时间的结果，作为“游戏内时间”可能正是想要的，但名字会误导；数值偏差，float 有效位只有 24 位，数值越大，每次加 1/60 被舍入得越厉害，而且误差方向随数值所在区间变化（10 小时时反而多算了 545 秒）。第 10 章 E14 的计时器在约 6 天处“停止前进”，是同一个原因。

【扩展知识】UE 的做法

UE 的 GameStateBase 在服务器上取世界时间，周期性地复制给客户端，客户端记录本地与服务器的时间差，GetServerWorldTimeSeconds() 返回“本地时间 + 差值”。时间本身由引擎用 double 维护（UE5 的世界时间是 double），不是每帧 float 累加。

5.9 延伸：做成联网之后，GameMode / GameState 怎么变

状态同步（服务器权威，UE 默认）帧同步（lockstep，许多 MOBA 采用）
规则在哪里执行只在服务器的 GameMode每个客户端都执行同一份确定性逻辑，服务器只转发输入
GameState 怎么到达客户端属性复制（变化时同步）不同步状态，每端自己算出来，靠校验和检查是否一致
Authority 的含义服务器“确定性模拟”本身；作弊靠校验和与服务器复算发现
对本项目的要求规则写入收口到 GameMode（5.5 节），Pawn 只发请求逻辑用整数帧和定点数；不能依赖 Unity 物理回调和 float deltaTime；同帧回调顺序必须确定
需要补的PlayerState、RPC、复制属性输入帧缓冲、确定性的计时器和随机数（第 10 章 Q10-14）

两种方案都要求同一件事：规则只能有一个执行入口。所以 5.5 节的“写入路径没有收口”，在单机里是代码组织问题，到了联网就是正确性问题。

5.10 Code Review：GameMode / GameState 相关问题

当前设计问题影响改进方向（不写代码）
AddScore / SetMatchState 是 public，Pawn 和 Controller 直接调用规则散落，权威只体现在注册时比赛结束后仍计分；联网时无法收口Pawn / Controller 只上报事实（事件或调用 GameMode 的接口），GameMode 裁决后写入；GameState 的写方法只对 GameMode 开放

Q5-1 → Q5-3　区别？单机为什么还要分？

L1 · 30 秒　GameMode 是裁判，决定规则：何时开始、谁得分、何时结束；GameState 是计分板，存所有人都需要看到的状态：阶段、分数、时间。

L2 · 正常回答　我的实现里 GameMode 在 BeginPlay 时先向 World 注册为裁判，再用 GameStateClass 反射生成 GameState 并亲自去 World 担保注册，然后驱动比赛状态机；GameState 的状态变化通过 EventSystem 广播给 UI。单机里分开的价值是依赖方向：UI 只依赖状态，不依赖规则，规则改了 UI 不用动。

L3 · 深入　在 UE 里这还关系到网络：GameMode 只在服务器存在，客户端根本没有，所以 UI 只能读复制下来的 GameState；每个玩家的个人数据放在 PlayerState，也复制给所有人。我的项目是单机，分数按阵营存在 GameState，阵营存在 Controller，所以没有 PlayerState；扩展到多人对战时需要补上。

L4 · 面试官攻击　“单机里分开就是过度设计吧？” → 如果只看 SoulDecay 的规模，确实可以合在一起。但我分开的目的是验证这套结构能不能承载“规则可替换”：GamePlayTest2 和 SoulDecay 用的是同一个 AGameMode 基类，只换了子类和 GameStateClass，UI 都不依赖 GameMode。代价是多了注册流程和两份引用，这部分我承认还不够干净。

Q5-4 → Q5-6　权威体现在哪？

L1　目前只体现在注册：World 只接受当前裁判担保的 GameState。

L2　写入路径没有收口：玩家夺舍得分是 Controller 直接调 AddScore，碾压得分是 Pawn 直接调，比赛结束是 Pawn 判断“死的是玩家”后调 EndMatch；SetMatchState 和 World.GameState 的 setter 也都是 public。所以比赛结束后 AI 之间还在加分——“结束后不计分”这条规则没有地方写。

L3　改法是让 Pawn 和 Controller 只上报事实：“我撞碎了谁”“我的寿命到了”“我夺舍了谁”，GameMode 根据当前阶段和规则决定是否加分、是否结束，再写 GameState；GameState 的写接口只对 GameMode 开放。这样联网时只要把“上报”换成发给服务器的请求，结构不用变。

Q5-7　场景里放了两个 GameMode？

L2　注释说会忽略后注册的，但实测不是：RegisterGameMode 只是 return，BeginPlay 继续执行。第二个 GameMode 生成的 GameState 会被 World 拒绝并 Destroy，但 Destroy 是延迟的，它本帧照样切了两次状态、发了两次事件；然后它还生成了第二个玩家、第二个 PlayerController，两个 Controller 读同一份输入，两具肉体一起动；它还用同名 CreateTimer 把刷怪计时器的回调换成了自己的。拒绝注册不等于让它停止工作，至少要让注册返回失败、BeginPlay 停止并禁用自己。

Q5-8　GameStateClass 为什么用 Type？

L2　为了像 UE 的 GameStateClass 那样“子类只声明类型，父类负责生成”。代价是没有编译期约束：写一个不继承 AGameState 的类型，要到运行时 as 出 null、注册时空引用才发现。更好的写法是泛型基类加 where 约束，编译期就能检查；UE 用 TSubclassOf，在编辑器里只能选派生类。另外我有三层用 new 隐藏的 GameState 属性，拿到哪个取决于引用的静态类型，这也是想合并成一份存储加泛型取值方法的原因。

Q5-9 → Q5-10　世界时间准吗？联网怎么改？

L2　不准，而且名字有误导性：它是本地 scaled deltaTime 的 float 累加，暂停时不走、卡顿被截断、从 GameState BeginPlay 才开始；我用移植版测过，真实 120 秒里有 10 秒暂停和两次卡顿，它只走了 109.5 秒；连续跑 10 小时 float 累加会差 545 秒。UE 的服务器世界时间是服务器用 double 维护、复制给客户端再补偿时间差。

L3　联网方面：状态同步下，规则只在服务器 GameMode 执行，GameState 和 PlayerState 复制给客户端，客户端只发请求；帧同步下，每个客户端都执行同一份确定性逻辑，GameState 不同步而是各自算出来，所以逻辑必须用整数帧和定点数，不能依赖 float deltaTime 和物理回调。两种都要求规则只有一个执行入口，这正是我现在缺的那一步。

常见错误回答 ①

错误：“GameMode 是权威，所以所有规则都由它执行。”

问题：与源码不符——加分和结束比赛的决定都在 Pawn / Controller 里，被追问一行代码就会露馅。

更好的回答：“设计上 GameMode 是规则的唯一裁决者；当前实现只在注册环节做了校验，写入路径还散在 Pawn 和 Controller，我知道怎么收口。”

常见错误回答 ②

错误：“GameState 存的是服务器时间，所以可以用来做倒计时同步。”

问题：本项目的 ServerWorldTimeSeconds 只是本地 scaled 时间的 float 累加，没有服务器，也不同步（实测 F5）。

更好的回答：“它目前是本地游戏时间，名字借自 UE；真要做同步倒计时，应该由服务器下发开始时刻，客户端用对时后的时间计算剩余量。”

5.12 发散：面试官会从这里追到的知识

命令-查询分离

“改状态的方法”和“读状态的方法”分开，并且只给特定的一方改的权限。GameState 只读暴露给所有人、写接口只给 GameMode，就是这个原则。为什么会追过去：规则散落本质上是“谁都能写”。

MVC / MVVM

GameState 像 Model，UI 像 View，事件是变更通知。UI 只观察 Model，不调用 Controller 的逻辑——和“UI 不读 GameMode”是同一个依赖方向。

属性复制与 RepNotify

UE 里 GameState 的属性标记为复制，变化时客户端收到并触发 OnRep 回调更新 UI。它和本项目“SetMatchState 后 Trigger 事件”是同一个模式，只是事件来源从本地变成了网络。

对时

客户端发出请求时记下本地时间 t0，服务器回复它的时间 ts，客户端收到时是 t1，估算偏移 ts + (t1 − t0)/2 − t1；多次采样取延迟最小的一次。NTP 用的是同一思路。

帧同步的确定性

浮点运算在不同 CPU / 编译选项下可能不同，所以逻辑层常用定点数；随机数用同一个种子的伪随机；遍历容器的顺序也必须确定（哈希表遍历顺序就不能依赖）。

反射与类型系统

C# 的 AddComponent(Type) 依赖运行时反射；C++ 没有内建反射，UE 靠 UHT 生成的 UClass 信息实现 TSubclassOf 和按类生成对象。为什么会追过去：GameStateClass 一问就会问到“C++ 里怎么按类型名创建对象”。

本章速记
  • GameMode = 规则（何时开始、谁得分、何时结束），GameState = 可观察状态（阶段、分数、时间）；单机里分开的价值是依赖方向，联网里还关系到“GameMode 只在服务器”。
  • 开局：RegisterGameMode → 反射生成 GameState → 担保注册 → WaitingToStart → InProgress，都在 GameState 的 BeginPlay 之前。
  • Authority 只校验了注册，没有收口写入：AddScore / SetMatchState / World.GameState 都是 public，加分和结束比赛由 Pawn / Controller 决定 → 比赛结束后仍计分。
  • 两个 GameMode（F4）：后注册的没有被忽略——多发 2 次事件、多一个玩家、接管刷怪计时器。
  • ServerWorldTimeSeconds（F5）：120 s 里只走 109.5 s；10 小时 float 累加误差 545 s。
自测 1：为什么 AGameModeBase.BeginPlay 里必须先 RegisterGameMode 再 InitGameState？调换顺序会怎样？

RegisterGameState 会检查 authority == AuthorityGameMode。先 InitGameState 的话，AuthorityGameMode 还是 null，校验失败，World 会打印越权警告并 Destroy 刚生成的 GameState，GameMode 自己的 GameState 引用指向一个帧末就会销毁的对象。

自测 2：World.Instance.AuthorityGameMode.GameState 在 SoulDecay 里拿到的是什么类型？为什么？

静态类型是 AGameStateBase。AuthorityGameMode 的声明类型是 AGameModeBase，而 AGameMode / SurvivalGameMode 的 GameState 属性是用 new 隐藏的，不是 override，编译器按静态类型选择 AGameModeBase.GameState。对象实际是 SurvivalGameState，需要再向下转型。

自测 3：把“比赛结束后不再计分”这条规则加进当前代码，最小的改动放在哪里？为什么这仍然不是好的设计？

最小改动是在 SurvivalGameState.AddScore 开头判断 MatchState 是否为 InProgress。它能让行为正确，但规则写在了计分板里：计分板开始“决定”什么时候可以加分，而 Pawn 和 Controller 仍然直接调用它。好的设计是让 GameMode 接收事实、根据阶段裁决后再写 GameState。
