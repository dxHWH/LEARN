9.1 这一章解决什么问题

Gameplay 里到处是“过一会儿再做”：技能冷却、Buff 持续时间、刷怪间隔、UI 倒计时、延迟销毁。一个计时器系统至少要满足五个要求：

#要求为什么
R1创建、删除都是 O(1)技能和 Buff 会在一帧里大量增删
R2每帧遍历要快所有计时器每帧都要累加时间
R3外部持有一个“票据”，可以随时暂停、查询、停止UI 要查剩余时间，Pawn 死亡要取消自己的计时器
R4票据过期后不能误操作别人的计时器计时器结束后，持有方往往还留着那张票据
R5回调里可以安全地增删计时器回调里停止自己、开启下一个计时器非常常见（第 10 章）

9.2 从 List<Timer> 出发：朴素方案为什么不够

方案删除遍历外部票据问题
List<TimerData> + 下标当票据RemoveAt O(n)连续，快下标删一个元素，后面所有元素的下标都变了，票据全部失效
List<Timer>（class）+ 对象引用当票据Remove O(n)指针数组，元素散在堆上引用每个计时器一次堆分配；删除后持有方的引用依然“能用”，只能靠标志位判断；一旦为了省 GC 把 Timer 对象池化，旧引用就会指向别人的计时器（ABA）
Dictionary<int, TimerData> + 自增 idO(1) 均摊遍历哈希桶，且 struct 值不能原地修改id每帧修改 elapsed 都要“读出—改—写回”；遍历中不能修改字典
Slot Map（本项目）O(1)dense 连续数组 + ref 原地修改(index, generation)需要维护三份映射；删除打乱顺序

Slot Map 的核心思路是一次间接寻址：外部拿到的不是数据的位置，而是一个“槽位号”；槽位号通过一张表找到数据当前在哪。数据可以随便搬家（为了保持紧凑），只要更新这张表即可。

TimerHandle(Index=1, Generation=0) ← 外部持有，永远不变 │ _generations[1] == 0 ? ← 版本校验：不相等就是过期票据 ▼ _handleToIndex[1] = 3 ← 稀疏映射：槽位 1 的数据现在在 dense[3] │ ▼ _timers[3] = { duration, timeElapsed, ... } ← 紧凑数组：每帧从 0 线性遍历到 _timerCount-1 ▲ _indexToHandle[3] = 1 ← 反向映射：搬家时用来找到“它属于哪个槽位”

9.3 当前项目怎么做：5 个数组 + 3 个辅助结构

public readonly struct TimerHandle : IEquatable { public readonly int Index; // 槽位号（不是 dense 下标！） public readonly int Generation; // 槽位的代数 public static readonly TimerHandle Invalid = new TimerHandle(-1, -1); } public struct TimerData { public float duration, timeElapsed, interval, intervalElapsed; public Action onTrigger, onComplete; // ← 两个引用类型字段 public bool isLoop, isPaused, isUnScaled, isChase; public int timerId; // 名字的 hash，0 = 匿名 } private TimerData[] _timers = new TimerData[128]; // ① dense：热数据 private int _timerCount = 0; private readonly List _handleToIndex; // ② 槽位 → dense 下标 private readonly List _indexToHandle; // ③ dense 下标 → 槽位 private readonly List _generations; // ④ 槽位 → 当前代数 private readonly Queue _freeIndices; // ⑤ 空闲槽位（FIFO） private readonly Dictionary _idToHandle; // 名字 hash → 句柄 private readonly List _expiredTimersCache; // 本帧到期 private readonly List _intervalTimersCache; // 本帧 interval 触发
为什么 dense 用数组 TimerData[] 而不是 List<TimerData>

【源码事实】Tick 里写的是 ref TimerData timer = ref _timers[i];，直接改数组里的那一份。如果换成 List<TimerData>，索引器返回的是副本，list[i].timeElapsed += dt 连编译都过不了（修改的是临时值）；只能“读出、改、写回”，多两次 40 字节的拷贝。Unity 2022 的 .NET Standard 2.1 里也没有 CollectionsMarshal.AsSpan 可以拿到 List 内部数组。这是“用数组”最实在的理由，比“数组更快”更站得住。

【问题】同一个文件里 SetPaused 却用了“读出—改—写回”，风格不统一（功能没错）。

9.4 CreateTimer：逐行看分配一个计时器

if (!string.IsNullOrEmpty(timerName)) { timerId = timerName.GetHashCode(); // ① 名字 → int hash if (_idToHandle.TryGetValue(timerId, out var oldHandle)) { if (IsHandleValid(oldHandle)) StopTimer(oldHandle); // ② 同名覆盖：停掉旧的 _idToHandle.Remove(timerId); } } int handleIndex; if (_freeIndices.Count > 0) handleIndex = _freeIndices.Dequeue(); // ③ 优先复用空闲槽 else { handleIndex = _handleToIndex.Count; // 否则新开一个槽 _handleToIndex.Add(-1); _indexToHandle.Add(-1); _generations.Add(0); // ← 代数从 0 开始 } TimerHandle handle = new TimerHandle(handleIndex, _generations[handleIndex]); // ④ 代数在创建时不变 EnsureCapacity(_timerCount + 1); // ⑤ 不够就翻倍 Array.Resize _timers[_timerCount] = data; int realIndex = _timerCount; _timerCount++; // ⑥ 追加到 dense 末尾 _handleToIndex[handleIndex] = realIndex; // ⑦ 建立双向映射 if (realIndex >= _indexToHandle.Count) _indexToHandle.Add(handleIndex); else _indexToHandle[realIndex] = handleIndex; if (timerId != 0) _idToHandle[timerId] = handle; // ⑧ 登记名字
  • ③④：代数在停止时加一（StopTimer 里），创建时只读取。所以一个从没被回收过的槽位，代数永远是初始值 0——这是 9.8 节默认句柄漏洞的根源。
  • ⑦【源码事实】_indexToHandle 在新开槽位时就已经 Add(-1)，它的长度永远等于槽位数，而 realIndex < _timerCount ≤ 槽位数，所以 Add 分支实际上不可达。这是一个隐含不变式，写成断言比写成分支更清楚。
  • ②【问题】同名覆盖是静默的：调用方不知道旧计时器被停了，也拿不到任何回调；加上 hash 碰撞（9.8.5），两个不同名字也可能互相覆盖。

9.5 StopTimer：Swap-and-Pop 的完整推导

if (!IsHandleValid(handle)) return; int handleIndex = handle.Index; int realIndex = _handleToIndex[handleIndex]; // 要删的数据在哪 int lastRealIndex = _timerCount - 1; if (realIndex != lastRealIndex) { _timers[realIndex] = _timers[lastRealIndex]; // ① 末尾数据填洞（40 字节结构体拷贝） int lastHandleIndex = _indexToHandle[lastRealIndex]; // ② 末尾数据属于哪个槽位 _indexToHandle[realIndex] = lastHandleIndex; // ③ 修反向映射 _handleToIndex[lastHandleIndex] = realIndex; // ④ 修正向映射 } _timerCount--; // ⑤ 逻辑删除末尾（数组不清空） _generations[handleIndex]++; // ⑥ 旧句柄失效 _freeIndices.Enqueue(handleIndex); // ⑦ 槽位进入 free list

逐步解释第 5 步“Stop B(1,0)”：

  1. realIndex = _handleToIndex[1] = 1，last = 3，不是末尾，需要搬家。
  2. _timers[1] = _timers[3]：D 的数据被拷到 1 号位置。
  3. _indexToHandle[3] = 3：D 属于槽位 3；于是 _indexToHandle[1] = 3、_handleToIndex[3] = 1。D 的句柄 (3,0) 没有变，但它现在能找到 dense[1]。
  4. _timerCount = 3；_generations[1] = 1；槽位 1 入队。
  5. 灰色格子：_timers[3] 还留着 D 的副本、_handleToIndex[1] 还留着 1——它们逻辑上无效，但内存里还在，9.8.2 和第 10 章的 GC 审计都会用到这两个“残留”。
对比List.RemoveAt（保序）Swap-and-Pop
时间复杂度O(n − i)：后面的元素整体前移O(1)：一次拷贝 + 两次映射修改
顺序保持插入顺序打乱：末尾元素跳到中间
映射维护后面所有元素的 dense 下标都变了，要改 n − i 条映射只改被搬动的那一个元素的两条映射
内存行为memmove 一大段，大 n 时会扫过很多 cache line只碰两个位置
什么时候选它需要稳定的执行顺序（例如按创建顺序回调、帧同步要求确定顺序且直观）顺序无所谓、删除频繁
面试注意：swap-and-pop 打乱顺序的后果

【实测 E4】按 1、2、3、0（重建）的顺序创建、同一帧到期的四个计时器，回调顺序是 0 1 2 3——和创建顺序不同，因为删除/重建把元素搬到了别的位置。如果业务依赖“先创建先回调”（例如两个 Buff 同帧到期，先移除哪个决定了最终属性），就必须显式排序（例如按 (到期时间, 创建序号)），不能依赖 dense 顺序。

9.6 Free List：为什么需要它，为什么是队列

没有 free list，每次 CreateTimer 都要新开槽位，_generations 等三张表只增不减，一个跑了一小时的战斗会积累成千上万个空槽。free list 让槽位被复用，三张稀疏表的长度等于“历史上同时存在的计时器数量峰值”。

它和 generation 是一对：free list 负责复用，generation 负责让复用安全。复用意味着同一个槽位号先后属于不同的计时器，必须有东西区分“这是第几任主人”。

空闲结构复用顺序对句柄安全的影响本项目
Queue（FIFO）最早释放的槽最先复用同一槽位两次复用间隔更长；代数自增被分摊到更多槽位，单个槽位回绕更慢✔
Stack（LIFO）刚释放的槽立刻复用热点槽位代数涨得快；但稀疏表访问更集中（cache 友好）ObjectPool 用的是它
侵入式链表（槽位里存下一个空闲槽号）任意不需要额外容器，零分配常见于 C++ 的 slot map
【实测 E5】FIFO 让测试用例变得“依赖执行顺序”

仓库里的 Test_GenerationIncrement 和 Test_IndexReuse 断言“停止后再创建，会拿到同一个槽位、代数 +1”。这只在 free list 里恰好没有其他空闲槽时成立：预留 0 或 1 个空闲槽时两个用例 PASS，预留 2 个时都 FAIL（新计时器拿到的是更早释放的槽）。它们在当前测试顺序下能过，是因为前面的用例恰好没有留下多余的空闲槽——这是“测试依赖全局状态”的典型反面教材（第 20 章）。

9.7 Index + Generation：它到底解决了什么

9.7.1 用 (5,3) → (5,4) 讲清 stale handle

时刻 t0 Timer A 创建 → 拿到槽位 5，_generations[5] = 3 → 句柄 Handle(5, 3) Pawn 把 Handle(5,3) 存进字段 _decayTimer 时刻 t1 A 到期 / 被停止 → _generations[5]++ → 4，槽位 5 进 free list Pawn 不知道，字段里还是 Handle(5,3) ← 这就是 stale handle（过期句柄） 时刻 t2 Timer B 创建 → 从 free list 取到槽位 5 → 句柄 Handle(5, 4) 时刻 t3 Pawn 死亡，调用 StopTimer(Handle(5,3)) IsHandleValid: _generations[5] = 4 ≠ 3 → false → 直接 return，B 安然无恙 如果没有 generation（句柄只有 Index=5）： StopTimer(5) → 找到槽位 5 → 删掉的是 B ！ —— A 的主人误杀了 B 的计时器

这类问题叫做ABA 式槽位复用：持有方看到的“槽位 5”从 A 变成了 B（中间经历了“空”），但只看槽位号无法察觉变化。名字借自无锁编程里的 ABA 问题：CAS 只比较值，值从 A 变 B 再变回 A，CAS 以为什么都没发生。两者的共同解法都是给值附加一个只增不减的版本号。

只用这个当票据为什么不够
dense 下标swap-and-pop 一次，别人的 dense 下标就变了
槽位号 Index槽位会被复用，旧票据会指向新主人（上面的例子）
对象引用（C#）不会悬垂（GC 保证对象还活着），但会“逻辑过期”：对象已被移出系统，持有方仍可调用它；一旦为了省 GC 池化对象，就退化成槽位复用问题
原生指针（C++）对象释放后成为悬垂指针（use-after-free）；内存被重新分配给同类对象时还是 ABA
Index + GenerationIndex 定位，Generation 确认“还是不是同一任主人”；代价是每次访问多一次比较

9.7.2 IsHandleValid 只做了两件事

public bool IsHandleValid(TimerHandle handle) { if (handle.Index < 0 || handle.Index >= _generations.Count) return false; // 越界 return _generations[handle.Index] == handle.Generation; // 代数相等 }

注意它没有检查“这个槽位现在是不是正在被使用”。正常情况下这两件事等价：槽位被释放时代数已经 +1，旧句柄的代数必然对不上。但只要能构造出“空闲槽位的当前代数”，校验就会通过——下一节的漏洞 2 就是这个。

9.8 这套句柄的四个漏洞（实测）

9.8.1 漏洞 1：default(TimerHandle) = (0,0) 是合法句柄

C# 的结构体字段默认值是全零。CombatPawn 里写的是 private TimerHandle _decayTimer;，没有初始化为 Invalid。只有被玩家附身时才会创建寿命计时器，所以 AI 肉体的 _decayTimer 一直是 (0,0)。而代数从 0 开始，第一个被创建的计时器恰好也是 (0,0)。

【实测 E1】三种情况：

  • A（当前 Demo 顺序）：玩家寿命计时器 (0,0) 被 AI 的死亡停掉 → UI 显示 DIE，玩家永不爆炸。
  • B（如果先创建刷怪器）：刷怪器变成 (0,0)，任意 AI 死亡后刷怪停止。
  • C（槽位 0 被复用过一次之后）：代数已经变成 1，(0,0) 永久失效——这就是当前 Demo 能侥幸跑通的原因：玩家第一具肉体寿命 5 秒，第一只 AI 3 秒出现、第二只 6 秒出现，5 秒内不可能发生 AI 之间的碰撞；而玩家一旦夺舍或爆炸，槽位 0 就被回收过了。
【改进方案】两层防线

① 系统侧：代数从 1 开始，让“全零”永远无效（也可以把 Index 存成 index+1）。② 使用侧：句柄字段一律显式初始化为 TimerHandle.Invalid，停止后立刻重置（CombatPawn.OnUnPossess 里已经这样做了，但声明处漏了）。只改使用侧不够——任何一个新写的类忘了初始化，问题就会回来。

9.8.2 漏洞 2：残留映射 + 不检查槽位在用 → 伪造句柄能删掉别人

StopTimer 之后，_handleToIndex[槽位] 没有被重置为 −1（图 9-2 的灰色格子）。如果有人构造出 (空闲槽位, 当前代数) 的句柄，IsHandleValid 会通过，StopTimer 会顺着残留映射去删一个不属于它的 dense 元素：

正常使用拿不到这样的句柄，所以这是一个“防御深度”问题而不是日常 bug。但它会在两种情况下自然出现：代数回绕（9.8.4）之后，以及跨实例使用句柄（9.8.3）时。面试里说清“IsHandleValid 只比代数，不检查槽位是否在用，停止后也不清映射”，再给出修复——停止时把映射置 −1，校验时额外检查 h2i[index] >= 0 && h2i[index] < count——就足够了。

9.8.3 漏洞 3：句柄不知道自己属于哪个 TimerSystem

TimerSystem 是场景级的懒单例，切场景时会被销毁、在新场景里重新创建，新实例的槽位和代数又从 0 开始。【实测 E10】旧场景里保存下来的句柄 (0,0)，在新场景的 TimerSystem 上 IsHandleValid = true，读到的是新场景第一个计时器的剩余时间；用它 StopTimer 会把新计时器停掉。谁会跨场景持有句柄？挂了 DontDestroyOnLoad 的对象——比如以后真正有职责的 GameInstance。

【改进方案】句柄里带一个“系统实例 id”（或者每个实例的代数起点随机化 / 全局递增），校验时一起比较。UE 的做法是序列号由 TimerManager 全局递增分配（LastAssignedSerialNumber），不同槽位之间也不会重号。

9.8.4 漏洞 4：generation 溢出

C# 的 int++ 默认是 unchecked，到 int.MaxValue 之后回绕成 int.MinValue【实测 E6：-2147483648】。同一个槽位要复用 2³² 次，代数才会回到原值：

同一槽位每秒复用回到同一代数所需时间（实测 E6）判断
1 次约 4.97 万天（136 年）可忽略
60 次（每帧一次）约 829 天客户端可忽略；7×24 服务器需要考虑
1000 次约 49.7 天需要处理

而且回绕后要真出事，还需要“某个持有方恰好在 2³² 次复用之前拿了句柄、一直没用、刚好在回绕那一刻使用”。所以正确的面试回答是：先估算，再说明风险窗口，最后给方案——64 位代数；或者像 UE 那样 64 位句柄拆成 24 位下标 + 40 位序列号（2⁴⁰ 次分配才回绕）；或者代数到达上限的槽位直接“退役”不再复用。

9.8.5 附：名字 → string.GetHashCode() 的问题

  • 碰撞：32 位 hash 必然有碰撞。两个不同名字 hash 相同时，第二次 CreateTimer 会把第一个“同名覆盖”掉，StopTimer("X") 可能停掉 Y。
  • 不稳定：.NET 文档明确说字符串 hash 不保证跨进程、跨运行时版本一致（.NET Core 默认按进程随机化）；Mono / IL2CPP 下碰巧稳定，也不能拿去持久化或网络同步。
  • 0 的歧义：timerId == 0 表示匿名，若某个名字的 hash 恰好是 0，它就无法按名查找。
  • 注释不符：注释说“使用 Unity 内置的高效 Hash”，代码用的是 string.GetHashCode()。

【改进方案】Dictionary<string, TimerHandle> 直接以字符串为键（字典内部会处理碰撞）；或者把名字收敛成编译期常量 / 枚举 / 预先注册的 id 表。

9.9 Dense Array 与 cache：什么时候“数组更快”才成立

所以“数组一定比链表快”是错的说法。正确的说法有三个前提：

  1. 访问模式是顺序遍历：Tick 从 0 扫到 count−1，硬件预取器能提前把下一批 cache line 拉进来。随机按句柄访问单个计时器时，dense 数组和指针数组都是一次（或两次）随机访问，差别不大。
  2. 数据量超过缓存：数据全部在 L1/L2 时，指针追逐（pointer chasing）的代价被缓存掩盖了。几百个计时器的客户端场景，布局带来的差异是纳秒级的。
  3. 对象确实是散的：C# 的 class 对象分配在托管堆上，刚分配时往往是连续的（“按序”那一列）；长时间运行、分配释放交错后才会散开。Unity 用的 Boehm GC 不压缩（non-moving），散开之后不会被整理回来——这是“托管语言里也要关心数据布局”的理由。
更进一步：热冷分离

每帧 Tick 真正要读写的只有 timeElapsed / duration / isPaused / interval...，两个委托引用只在触发时才用到，却占了 40 字节里的 16 字节。把回调挪到另一个按 dense 下标对齐的数组（Structure of Arrays 的思路），Tick 每个 cache line 能装下更多计时器；顺带让热数据数组不含引用，GC 标记时可以跳过（第 10 章）。

9.10 交互实验：自己操作一次 Slot Map

建议操作：新建 A、B、C、D → 选中 B 停止（看 swap-and-pop）→ 再新建 E（看槽位复用、代数 +1）→ 用 B 的旧句柄再停一次（被拒绝）→ 点“StopTimer(default)”（删掉了 A！）→ 勾选“generation 从 1 开始”后重复一遍。

9.13 Production 版本会怎么设计（只讲思路）

  1. 句柄：64 位，包含“系统实例 id + 槽位 + 代数”，代数从 1 开始；停止时清空映射；校验时同时检查“槽位在用”。
  2. 名字：用 Dictionary<string, Handle> 或预注册 id，绝不用 hash 当唯一键；同名覆盖要么报错、要么返回旧句柄让调用方决定。
  3. 存储：热冷分离；停止时清掉回调引用（第 10 章 E13）。
  4. 调度：少量计时器线性扫描；数量大时按“到期时间”建堆或用时间轮；暂停的计时器移出活动集合。
  5. 所有者：创建时登记 owner，owner 销毁时批量取消（对应 UE 的 ClearAllTimersForObject），避免回调到已销毁的 MonoBehaviour。
  6. 时机：由 World / GameLoop 显式调用 Tick，固定在 Actor Tick 之前或之后，而不是自己 Update。

Q9-1 → Q9-5　为什么不用 List<Timer>？句柄怎么找到元素？搬家后怎么维护？

L1 · 30 秒　List 删除中间元素是 O(n)，而且下标会变，没法当票据。我用 Slot Map：外部拿“槽位号 + 代数”，槽位号经稀疏映射找到 dense 数组位置；删除时把末尾元素搬进空洞，只改被搬那个元素的两条映射，整体 O(1)。

L2 · 正常回答　有三张表：_handleToIndex（槽位 → dense 下标）、_indexToHandle（dense 下标 → 槽位）、_generations（槽位 → 代数）。删除 B 时：用 B 的槽位查到它在 dense[1]；把 dense[3] 的 D 拷过来；用反向表查到 D 属于槽位 3，于是把 _handleToIndex[3] 改成 1、_indexToHandle[1] 改成 3；count 减一。D 的句柄 (3,0) 没变，但现在指向 dense[1]——外部完全无感。

L3 · 深入　反向表是 swap-and-pop 必需的：没有它，搬动末尾元素时不知道该改哪个槽位的映射，只能 O(n) 搜索。维护的不变式是 h2i[i2h[k]] == k（k 在 count 内）。代价是删除会打乱顺序，同帧回调顺序不再等于创建顺序（实测 E4）。

L4 · 面试官攻击　“你这三张表都是 List<int>，每次访问都有边界检查和间接寻址，真的比直接 List.RemoveAt 快吗？” → 修正回答：几十个计时器时确实差不多（实测 N=100 时两者分别约 26 ns 和 3 ns，都可以忽略）；swap-and-pop 的价值在规模上去之后——N=1 万时保序删除约 1 µs、N=10 万时约 49 µs，而 swap-and-pop 始终约 3～4 ns。更重要的是语义：RemoveAt 会让所有后续元素的位置改变，句柄体系要么跟着改 n 条映射，要么根本做不了。

Q9-6 / Q9-7　槽位被复用怎么办？generation 为什么能解决？是不是 ABA？

L1　槽位回收时代数加一；句柄里存着创建时的代数，校验时不相等就拒绝。比如 A 的句柄是 (5,3)，A 停止后槽位 5 的代数变成 4，B 复用槽位 5 拿到 (5,4)；A 的主人再用 (5,3) 访问会被拒绝，不会误伤 B。

L2　这和无锁编程里的 ABA 是同一类问题：只比较“位置/值”无法察觉中间发生过的变化，所以给它附加一个单调递增的版本号。区别在于：无锁 ABA 是并发下的竞态，这里是单线程里“持有方的信息过期”。

L3　严格说，generation 防住的是“旧句柄访问新主人”；它不能防住“伪造句柄”，因为 IsHandleValid 只比代数、不检查槽位是否在用，停止后映射也没清（实测 E2）。

L4 攻击　“那为什么不直接用自增的全局 id 当句柄，再用 Dictionary 找？” → 也可以，这就是“id + 哈希表”方案：id 全局唯一天然没有 ABA，代价是每次访问一次哈希查找、遍历时要走哈希桶。Slot Map 用数组下标代替哈希，用代数代替“全局唯一”，是用一点安全余量换常数级性能。UE 的 FTimerHandle 其实是两者结合：下标 + 全局递增的序列号。

Q9-8　generation 溢出怎么办？

L2　先估算：32 位代数要同一个槽位复用 2³² 次才回绕，每帧复用一次也要约 829 天；然后指出风险窗口——还需要有人恰好持有一个 2³² 次之前的句柄。所以客户端可以接受。

L3　要彻底解决有三种做法：64 位代数；UE 式 24 位下标 + 40 位序列号；代数到上限的槽位退役不再进入 free list（代价是槽位数缓慢增长）。另外要注意 C# 默认 unchecked，int.MaxValue + 1 会静默变成负数，不会抛异常。

Q9-9　default(TimerHandle) 是合法句柄吗？（压力题）

L1　在我的实现里是，这是我复盘时发现的 bug。代数从 0 开始，第一个计时器的句柄就是 (0,0)，而结构体字段的默认值也是 (0,0)。

L2　Demo 里正好踩到：CombatPawn 的 _decayTimer 没初始化成 Invalid，AI 肉体从不创建计时器，死亡时 StopTimer(_decayTimer) 实际是 StopTimer(0,0)，会停掉槽位 0 上的计时器。我把逻辑移植出来测过：按 Demo 的创建顺序，被停掉的是玩家的寿命计时器。当前参数下不会触发，是因为槽位 0 在第一次碰撞前一定已经被回收过一次。

L3　修复分两层：系统侧代数从 1 开始，让全零永远无效（UE 的 FTimerHandle 也是 0 表示无效）；使用侧句柄字段显式初始化为 Invalid。

L4 攻击　“那你的测试为什么没发现？” → 测试里的句柄都来自 CreateTimer 的返回值，没有“从未赋值的句柄”这种用例；而且测试是运行时脚本，没有覆盖 Demo 的组合流程。这类 bug 需要“默认值 / 未初始化”的边界用例，我会补成 EditMode 单元测试。

Q9-11　数组一定比链表快吗？

L1　不一定。顺序遍历、数据量超过缓存、对象在堆上分散，这三个条件同时成立时，连续数组才明显更快。

L2　我用 C++ 按 TimerData 的布局测过：1000 个计时器时，dense 数组、按序分配的指针数组、打乱的指针数组每个元素都是 0.4 ns 左右，没有区别；100 万个时分别是 0.9、3.7、6.1 ns。客户端里同时存在的计时器一般是几百个，布局不是瓶颈，选数组更多是为了 ref 原地修改、零额外分配和 swap-and-pop。

L3　C# 里还要加一层：class 对象之间是引用，Unity 的 Boehm GC 不压缩堆，长时间运行后对象会越来越散；而 struct 数组天然连续，并且只占一次分配。

Q9-13　为什么不用小顶堆？

L2　堆的优势是 Tick 只处理到期的计时器，适合“很多长计时器、大多数帧没有到期”的场景，UE 就是按到期时间建堆。我的场景计时器少、每帧都要累加 elapsed（因为支持暂停、scaled/unscaled 混用、interval），线性扫描更简单。

L4 攻击　“那如果计时器多到 10 万个呢？” → 那我会把“绝对到期时间”作为存储方式（不再逐个累加），按时间流速分组（scaled 一组、unscaled 一组，暂停的移出），每组一个堆或时间轮；句柄体系不用变，堆里存句柄即可。

常见错误回答 ①

错误：“数组肯定比 List 快，因为数组是连续内存。”

问题：C# 的 List<T> 内部就是数组，也是连续的；真正的差别在于 List 的索引器返回副本，不能 ref 原地修改 struct。至于“连续内存更快”，要看访问模式和数据规模（实测 B1）。

更好的回答：“在每帧线性遍历、需要原地修改 struct 的场景下，裸数组可以用 ref 直接改元素，避免 List 索引器的副本拷贝；连续布局在数据量超过缓存时能减少 pointer chasing，但几百个计时器的规模下这个收益很小。”

常见错误回答 ②

错误：“generation 解决了所有句柄安全问题。”

问题：它只防“旧句柄访问新主人”。默认句柄、伪造句柄、跨实例句柄、代数回绕都不在它的防御范围内（9.8 节四个漏洞）。

更好的回答：“generation 解决的是槽位复用带来的 stale handle；另外还需要让全零句柄无效、停止时清映射并检查槽位在用、句柄带系统实例 id，才能覆盖其他边界。”

常见错误回答 ③

错误：“C# 有 GC，不会有悬垂引用，所以不需要 generation。”

问题：GC 只保证内存不被提前释放，不保证“逻辑上它还是你的那个计时器”。本项目的句柄是值（槽位号），不是引用，复用后照样指向新主人；就算用 class 引用，一旦池化也是同样的问题。

9.15 发散：同一个思想在别处的样子

ECS 的 Entity

Unity Entities 的 Entity 是 (Index, Version)；实体销毁后 Version+1，旧 Entity 查询组件会失败。EnTT 把版本号编码在 32 位 id 的高位。和 TimerHandle 一模一样。

UE 的弱指针

FWeakObjectPtr 存的是 ObjectIndex + ObjectSerialNumber：对象数组的槽位被复用后序列号不同，弱指针就失效。面试问“TWeakObjectPtr 怎么知道对象没了”，答案就是 generation。

渲染资源句柄

纹理、缓冲区、渲染目标常放在资源池里，上层只拿“池下标 + 代数”的句柄；资源被异步释放、槽位复用后，旧句柄不会误用新资源。

操作系统：fd 与 PID 复用

close 一个文件描述符后，下一次 open 会拿到最小的空闲号——持有旧 fd 的线程会写错文件。PID 回绕复用导致“kill 错进程”，Linux 后来引入 pidfd 解决。都是“只有 index 没有 generation”的事故。

无锁编程的 ABA

无锁栈 pop 时 CAS 比较栈顶指针，若栈顶节点被弹出又被重新压入，CAS 误以为没变。解法：指针旁边带一个计数（tagged pointer / 双字 CAS），本质就是 generation。

数据库乐观锁

行上带 version 字段，更新时 WHERE version = 旧值，被别人改过就失败重试。也是“用版本号检测中间发生过的变化”。

本章速记
  • 五个数组：dense _timers、_handleToIndex、_indexToHandle、_generations、_freeIndices（FIFO）；两套下标：槽位号对外不变，dense 下标对内会变。
  • 删除 = 末尾填洞 + 修被搬元素的两条映射 + count−1 + 代数+1 + 槽位入队；O(1)，不保序（实测 E4）。
  • generation 防的是旧句柄访问新主人（ABA 式复用）；防不住：默认句柄 (0,0)（E1）、残留映射 + 伪造句柄（E2）、跨实例（E10）、回绕（E6，829 天/每帧复用）。
  • “数组更快”有前提：顺序遍历 + 超出缓存 + 对象分散；1000 个时无差别，100 万个时打乱指针慢 6.7×（B1）。用数组的实在理由是 ref 原地改 struct。
  • UE：TSparseArray + 按到期时间的堆 + 64 位句柄（24 位下标 + 40 位序列号，0 = 无效）+ double 绝对时间。
自测 1：dense = [A,B,C,D]（槽位 0..3，代数全 0），依次 Stop(C)、Stop(A)、Create(E)，写出最后的 dense、_handleToIndex、_generations、_freeIndices 和 E 的句柄。

Stop(C)：C 在 dense[2]，末尾 D 填过来 → dense=[A,B,D]，h2i[3]=2，gen[2]=1，free=[2]。Stop(A)：A 在 dense[0]，末尾 D(dense[2]) 填过来 → dense=[D,B]，h2i[3]=0，i2h=[3,1]，gen[0]=1，free=[2,0]。Create(E)：从队头取槽位 2，代数 1 → 句柄 (2,1)，放到 dense[2] → dense=[D,B,E]，h2i=[0(残留),1,2,0]，gen=[1,0,1,0]，free=[0]。

自测 2：为什么 swap-and-pop 必须有反向映射 _indexToHandle？

搬动末尾元素时，需要知道它属于哪个槽位，才能改那个槽位的 _handleToIndex。没有反向映射只能遍历所有槽位查找，删除退化为 O(槽位数)。

自测 3：只把 CombatPawn 的 _decayTimer 初始化为 Invalid，算不算修好了默认句柄问题？

只修了这一个调用点。任何其他类声明 TimerHandle 字段时忘记初始化，问题都会重现；根本修复是系统侧让代数从 1 开始，使全零句柄永远无效。两层都做才稳妥。
