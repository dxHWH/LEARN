CHAPTER 06

Singleton / GameInstance / 初始化顺序

五个基础设施都继承同一个 MonoSingleton。它的懒查找、防重和退出标志各自解决了什么；为什么五个子类里只有一个调了 base.Awake；以及一个比它更隐蔽的问题——UI 在 OnEnable 里注册事件时，EventSystem 可能还没 Awake。

本章目标
  • 讲清 MonoSingleton 的四个部分：懒查找 / 懒创建、Awake 防重、OnDestroy 清理、退出标志
  • 说出“为什么每个子类各有一份单例”（C# 封闭泛型类型各自的静态字段）
  • 准确描述漏调 base.Awake 的后果，不夸大也不缩小
  • 解释 Awake / OnEnable 跨对象顺序不保证带来的初始化隐患，以及为什么 TimerSystem 没事而 EventSystem 有风险
  • 说清单例的代价，并对照 Service Locator、依赖注入、UE Subsystem 给出替代方案

6.1 这一章解决什么问题

单例是最常被追问“缺点是什么”的设计模式。这个项目让它更具体：有一个确定性的 bug（base.Awake 没调）、一个依赖未定义顺序的隐患（Awake 与 OnEnable 之间）、一个只在特定编辑器设置下出现的问题（关闭 Domain Reload）。能把这三件事讲清楚，“单例的缺点”就不再是背书。

6.2 两个模板

public class MonoSingleton : MonoBehaviour where T : MonoBehaviour { private static T _instance; private static bool _isApplicationQuitting = false; public static bool HasInstance => (_instance != null && !_isApplicationQuitting); protected virtual void Awake() // ② 防重：场景里预置了多个时，多余的自杀 { if (_instance == null) _instance = this as T; else if (_instance != this) Destroy(gameObject); } public static T Instance { get { if (_isApplicationQuitting) return null; // ④ 退出时不再创建 if (_instance == null) { _instance = FindObjectOfType(); // ① 懒查找 if (_instance == null) _instance = new GameObject(typeof(T).Name).AddComponent(); // 懒创建 } return _instance; } } protected virtual void OnDestroy() { if (_instance == this) _instance = null; } // ③ protected virtual void OnApplicationQuit() { _isApplicationQuitting = true; } // ④ }
部分解决什么注意
① 懒查找 / 懒创建没人放也能用；放了就用场景里那个任何代码第一次访问 Instance 都可能创建对象，包括 OnDestroy 里
② Awake 防重场景里预置了多个时只留一个需要子类调 base.Awake 才生效（6.4 节）；Destroy 的是整个 GameObject
③ OnDestroy 清理切场景后不留下指向已销毁对象的静态引用基类这一步做对了，World 的 OnDestroy 也调了 base
④ 退出标志退出过程中不再懒创建，避免“幽灵单例”每个 T 一份、只置不复位（6.6 节）
HasInstance只查询、不创建，给 OnDestroy 用_instance != null 走的是 Unity 重载的 ==，能识别已销毁
为什么“每个子类各有一份单例”

World : MonoSingleton<World> 这种写法常被叫作 CRTP（源码注释也这么写）。在 C# 里真正起作用的是：每个封闭泛型类型（MonoSingleton<World>、MonoSingleton<TimerSystem>……）都是独立的类型，各有一份静态字段。所以 _instance 和 _isApplicationQuitting 都是按 T 分开的。C++ 的 CRTP 也有同样效果（每个模板实例各有静态成员），但 C++ 的 CRTP 更常用于静态多态（基类通过 static_cast<T*>(this) 调用派生类）。

另一个模板 Singleton<T> where T : new() 是纯 C# 版，项目里没有任何类使用它。它有两个可以被追问的问题：new() 约束要求 T 有公开的无参构造函数，所以任何人都能 new T() 出第二个实例；_instance ??= new T() 不是线程安全的，两个线程同时首次访问可能各建一个（C# 的 Lazy<T> 或静态构造函数能解决）。

单例override Awake 调了 base 吗在哪些场景预置DontDestroyOnLoad
World否（Awake 是空的，只有注释）无，永远懒创建否（场景级）
TimerSystem否（只调 AllocateCapacity）SoulDecayScene否
EventSystem否（在 Awake 里创建缓冲区和监听字典）SoulDecayScene（Managers 下的子物体）否
ThreadSafeEventSystem否无；没有任何代码访问它否
GameInstance是，而且检查了自己是不是多余的MainMenuScene是

两个小事实：SoulDecayScene 里有两个都叫 “EventSystem” 的 GameObject——一个是 Unity UI 的事件系统，一个是项目的 EventSystem（挂在 Managers 下），层级面板里只能靠位置区分；GamePlayTest2Scene 没有预置任何单例，三个系统都在第一次被访问时懒创建。

6.4 确定性 bug：漏调 base.Awake

四个子类 override 了 Awake 却没调 base.Awake()，基类的防重逻辑对它们完全不执行。准确的后果是三条：

后果具体表现当前是否发生
预置实例不会在 Awake 登记在第一次有人访问 Instance（触发 FindObjectOfType）之前，_instance 为 null、HasInstance 为 false发生，但影响很小：SoulDecay 的 UI 在 OnEnable 里就访问了 EventSystem.Instance，GameMode 开局就访问了 TimerSystem.Instance
多余实例不会自杀场景里有两个 TimerSystem（复制了预制体、叠加加载两个场景）时，两个都会 Update；Instance 指向 FindObjectOfType 找到的那一个不发生：目前每个场景至多一个
先懒创建、后加载预置对象时出现双份如果某段代码在预置对象加载前访问了 Instance（例如上一个场景的对象在卸载时），会懒创建一个；之后加载的预置对象也不会自杀不发生：OnDestroy 里一律用 HasInstance

对比唯一做对的 GameInstance：

protected override void Awake() { base.Awake(); // 先调基类，如果我是多余的，基类会把我杀掉 if (this == null || Instance != this) return; // 多余的就不要继续执行 DontDestroyOnLoad(this.gameObject); }

这里有一个可以加分的细节：this == null 这个判断不会生效。基类调的是 Destroy(gameObject)，按规则 R3，销毁要等到本帧 Update 循环之后，Awake 返回时对象还没销毁，this == null 为 false。真正起作用的是第二个条件 Instance != this——它让多余的实例跳过 DontDestroyOnLoad。代码是对的，但注释里的理由不准确。

面试注意：说“确定性 bug”，但别夸大成“单例全坏了”

准确的说法：“World、TimerSystem、EventSystem 都 override 了 Awake 却没调 base，所以基类的防重和提前登记对它们不生效；现在每个场景至多一个实例，而且懒查找会兜底找到预置对象，所以没有表现出来。如果叠加加载两个带 Managers 的场景，就会有两个 TimerSystem 同时 Update。修复是子类第一行调 base 并在多余时 return，或者基类把 Awake 改成非虚、另给子类一个初始化钩子。”

6.5 更隐蔽的隐患：Awake 与 OnEnable 的跨对象顺序

// SurvivalUIController（普通 MonoBehaviour，场景预置） private void OnEnable() { if (EventSystem.Instance) // 懒查找：找到场景里预置的 EventSystem EventSystem.Instance.Register(OnScoreChanged); } // EventSystem override protected void Awake() { _frontBuffers = ...; _backBuffers = ...; _listenersDic = new Dictionary(); // 监听字典在 Awake 里才创建 } public void Register(Action listener) where T : IEventArgs { if (_listenersDic.ContainsKey(type)) ... // Awake 之前调用 → 空引用 }

场景加载时，Unity 对每个对象依次调用 Awake 和 OnEnable，不同对象之间的先后没有保证（没有配置 Script Execution Order 时）。如果 SurvivalUIController 排在 EventSystem 前面：

SurvivalUIController.Awake → OnEnable └ EventSystem.Instance：_instance 为空 → FindObjectOfType 找到场景里的 EventSystem（它还没 Awake） └ Register：_listenersDic == null → NullReferenceException → 两个监听都没注册成功：分数文字永远不更新，寿命文字因为拿不到句柄一直显示 “DIE” EventSystem.Awake（稍后）→ 创建字典，一切正常——但 UI 已经错过了注册

当前 Demo 能正常运行，说明在这个场景里 EventSystem 恰好先 Awake；这是加载顺序的偶然结果，不是代码保证的。验证方法：在 Project Settings → Script Execution Order 里把 SurvivalUIController 设为 −100（早于默认），进入 Play，应当在 Console 看到 Register 处的空引用异常。

为什么 TimerSystem 没有同样的风险

TimerSystem 的核心数组是字段初始化器创建的：private TimerData[] _timers = new TimerData[128];、_handleToIndex = new List<int>(128)……C# 的字段初始化器在构造函数里执行，Unity 反序列化创建对象时就已经完成，早于任何 Awake。Awake 里的 AllocateCapacity 只是再确认一次容量。所以即使在 TimerSystem.Awake 之前调用 CreateTimer，数据结构也是就绪的。EventSystem 把初始化全部放在 Awake 里，才有了这个窗口。

消除这类问题的方向原理代价
能用字段初始化器的就用构造时完成，早于所有 Awake不能访问其它对象和序列化字段
在 Instance getter 或方法内部做一次性初始化谁先访问谁触发，与 Awake 顺序无关每次访问多一次判断
注册放到 Start场景加载时所有 Awake 都先于任何 StartStart 之前发出的事件收不到（SoulDecay 的开局事件在 World.Update 里发，晚于 Start，没问题）
指定执行顺序[DefaultExecutionOrder(-100)] 让基础设施先初始化顺序成了隐式的全局配置
显式引导一个引导对象按顺序创建并初始化所有系统需要改造成“不依赖场景预置”

6.6 退出标志与 Domain Reload

  • 只置不复位：_isApplicationQuitting 在 OnApplicationQuit 里设为 true，之后没有任何地方设回 false。正常构建里无所谓（进程就要结束了）。
  • 每个 T 一份，只有存活实例才会置位：退出时没有存活实例的单例类型，标志不会被设置；如果退出过程中有代码访问它的 Instance，仍然会懒创建一个对象。项目里 OnDestroy 统一用 HasInstance，避开了这个问题。
  • 关闭 Domain Reload（Enter Play Mode Options）之后：静态字段在两次 Play 之间不会重置。第一次 Play 退出时被置位的类型，第二次 Play 时 Instance 直接返回 null——World.RegisterAActor 里 if (Instance == null) return; 会让所有 Actor 都不注册，整个游戏没有任何 BeginPlay 和 Tick（按源码推演）。修复方向是用 [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)] 在每次进入 Play 时重置静态状态。
【扩展知识】两个与版本相关的细节

① FindObjectOfType 在 Unity 2023.1 起被标记为过时，替代为 FindFirstObjectByType / FindAnyObjectByType；项目用的是 2022.3，没有警告。② _instance == null 走的是 UnityEngine.Object 重载的 ==，要检查原生对象是否存活，比纯引用比较慢一些；UI 的 Update 里每帧多次调用 TimerSystem.Instance，规模小时可以忽略。

6.7 GameInstance：名字有了，职责还没有

GameInstance 只放在 MainMenuScene，Awake 里 DontDestroyOnLoad 并打一行日志，唯一的成员是 CurrentWorld => World.Instance。它不持有 World、不管理任何系统；而且 CurrentWorld 如果在没有 Actor 的场景（比如主菜单）里被访问，会懒创建一个 World。从 SoulDecay 直接开始 Play（不经过主菜单）时，GameInstance 根本不存在。

UE 的 UGameInstance本项目的 GameInstance
生命周期引擎创建，跨关卡存在，整个进程一份只在从主菜单进入时存在
与 World 的关系World 由引擎创建和切换，GameInstance 可以访问当前 WorldWorld 各场景懒创建，GameInstance 只是转发 World.Instance
典型职责跨关卡数据、在线会话、持有 GameInstanceSubsystem无（日志落盘初始化被宏关闭）

6.8 单例的代价与替代方案

隐藏依赖

CombatPawn 依赖 TimerSystem、EventSystem、World 三个单例，这在它的字段和构造参数里看不出来，只能读代码发现。

初始化顺序

谁先访问谁创建，顺序随调用路径变化；6.5 节的隐患就是顺序问题的一个实例。

生命周期含糊

名字叫“单例”，实际是“每个场景一个”。TimerSystem 随场景销毁，计时器也一起消失——这是想要的行为，但不是从类型上看得出来的。

难以测试

MonoSingleton 必须挂在 GameObject 上，EditMode 单元测试里不能直接 new，也很难替换成假的实现（第 20 章）。

替代方案做法适合
Service Locator一个注册表按接口存取服务，启动时注册具体实现改造成本低，测试时能注册假实现；依赖仍然是隐式的
依赖注入（如 VContainer、Zenject）容器按作用域（项目 / 场景）创建服务，通过构造函数或字段注入依赖显式、作用域清晰；引入框架和学习成本
显式引导（Composition Root）一个引导对象按固定顺序创建、初始化、Tick 所有系统顺序完全可控，最适合解决 6.5 节的问题
UE Subsystem按宿主划分生命周期：Engine / GameInstance / World / LocalPlayer Subsystem，由引擎自动创建和销毁World 级的计时器和事件系统对应 WorldSubsystem；UE 的 FTimerManager 本来就挂在 World 上

Q6-1 → Q6-4　MonoSingleton 与 base.Awake

L1 · 30 秒　泛型基类，四部分：懒查找场景里的实例、找不到就创建；Awake 里登记自己、多余的自杀；OnDestroy 清空静态引用；退出时设置标志不再创建。每个子类各有一份，因为 C# 每个封闭泛型类型有独立的静态字段。

L2 · 正常回答　有一个我复盘时发现的确定性 bug：World、TimerSystem、EventSystem 都 override 了 Awake 但没调 base，防重和提前登记对它们不生效。现在每个场景至多一个实例，懒查找又会兜底找到预置对象，所以没表现出来；但叠加加载两个带 Managers 的场景，就会有两个 TimerSystem 同时 Update。唯一做对的是 GameInstance。

L3 · 深入　GameInstance 里还有个细节：它在 base.Awake 之后判断 this == null，但基类调的是 Destroy，销毁是延迟到帧末的，这时 this 还不是 null，真正起作用的是后面的 Instance != this。HasInstance 只查询不创建，所以所有 OnDestroy 里都用它——切场景时如果单例先被销毁，用 Instance 就会重新创建一个泄漏到下一个场景的对象。

L4 · 面试官攻击　“既然没表现出来，为什么叫 bug？” → 因为它让基类承诺的行为失效了，而失效的条件（多场景叠加、预制体复制）是正常的工程操作，不需要任何错误代码就能触发；而且 HasInstance 在首次访问前返回 false，会让依赖它的清理逻辑静默跳过。修复成本只有一行，没有理由留着。

Q6-5 → Q6-6　Awake / OnEnable 里能访问别的单例吗？

L2　不安全。Unity 只保证同一个对象 Awake 在 OnEnable 和 Start 之前，场景加载时所有 Awake 在所有 Start 之前；不同对象之间的 Awake 顺序不保证。我的 SurvivalUIController 在 OnEnable 里调 EventSystem.Instance.Register，而 EventSystem 的监听字典在它自己的 Awake 里才创建——如果 UI 先 Awake，懒查找能找到 EventSystem 对象，但字典还是 null，注册直接空引用，UI 永远收不到分数和寿命事件。现在能跑，是因为这个场景里 EventSystem 恰好先初始化。

L3　TimerSystem 没这个问题，因为它的数组是字段初始化器创建的，构造时就完成了，早于任何 Awake。所以修复可以是：EventSystem 也用字段初始化器；或者在 Register 内部做一次性初始化；或者 UI 改在 Start 里注册；或者给基础设施加 DefaultExecutionOrder。我更倾向于显式引导：一个启动对象按顺序初始化所有系统，不依赖场景里谁先被加载。

Q6-7　关闭 Domain Reload 之后？

L2　静态字段在两次 Play 之间不重置。退出标志在第一次退出时被置为 true、之后从不复位，第二次 Play 时 Instance 直接返回 null；World.RegisterAActor 遇到 null 就 return，所有 Actor 都不会注册，整个游戏没有 BeginPlay 和 Tick。解决办法是用 RuntimeInitializeOnLoadMethod 在每次进入 Play 时重置所有单例的静态状态。

Q6-8　单例的缺点？怎么替代？

L2　隐藏依赖（CombatPawn 用了三个单例，从接口上看不出来）、初始化顺序不确定、生命周期含糊（叫单例，实际每个场景一个）、难以测试（MonoBehaviour 不能在 EditMode 里直接 new，也不好换成假实现）。

L3　替代方案按改造成本排：Service Locator（按接口注册，测试时能替换）、显式引导（一个启动对象按顺序创建和驱动所有系统）、依赖注入框架（按项目 / 场景作用域管理）。UE 的思路是按宿主划分生命周期的 Subsystem：Engine、GameInstance、World、LocalPlayer 各有一类，由引擎自动创建销毁。我的 TimerSystem 和 EventSystem 本质上是“每个 World 一份”，对应 UE 的 WorldSubsystem——UE 的 FTimerManager 本来就挂在 World 上。

常见错误回答 ①

错误：“我的单例在 Awake 里会把多余的实例销毁，所以不会有多个实例。”

问题：四个子类都没调 base.Awake，这段逻辑对它们不执行。

更好的回答：“基类有防重逻辑，但 World / TimerSystem / EventSystem 漏调了 base.Awake，目前靠每个场景只放一个来保证唯一。”

常见错误回答 ②

错误：“Awake 一定比 OnEnable 和 Start 早，所以在 OnEnable 里访问别的系统是安全的。”

问题：顺序保证只针对同一个对象；跨对象时，别人的 Awake 可能还没执行。

更好的回答：“跨对象的依赖放在 Start 或 BeginPlay，或者让被依赖的系统在被访问时惰性初始化。”

6.11 发散：面试官会从这里追到的知识

C++ 的 Meyers 单例

函数内静态局部变量：static T& Get() { static T inst; return inst; }。C++11 起标准保证局部静态变量的初始化是线程安全的（编译器生成带锁或原子标志的“magic statics”）。为什么会追过去：游戏客户端岗大多是 C++，单例题几乎一定会转到 C++ 实现。

双重检查锁

“先判空、加锁、再判空、再创建”在没有内存屏障时可能让别的线程看到未构造完的对象；C++ 要用 std::atomic 配合 acquire / release，或者直接用 std::call_once。第 13 章的 Log 会遇到同样的问题。

静态初始化顺序

不同编译单元的全局对象构造顺序不确定，析构顺序与构造相反；一个全局对象的析构函数里访问另一个已析构的单例就是未定义行为——和“切场景时单例谁先 OnDestroy”是同一个问题。

C# 的 Lazy<T> 与静态构造函数

静态构造函数由运行时保证只执行一次且线程安全；Lazy<T> 提供可选的线程安全模式。它们解决了 Singleton<T> 的并发问题，但解决不了“公开构造函数”。

UE 的 Subsystem

继承 UWorldSubsystem 等基类即可，引擎在宿主创建时自动实例化、销毁时自动清理，通过 GetWorld()->GetSubsystem<T>() 访问。它把“全局唯一”换成了“宿主内唯一”，生命周期由类型直接表达。

依赖注入的作用域

Singleton（整个容器一份）、Scoped（每个作用域一份，例如每个场景）、Transient（每次注入新建）。项目里 TimerSystem 实际需要的是“场景作用域”，这正是 DI 框架能直接表达、而 MonoSingleton 只能靠约定实现的东西。

本章速记
  • MonoSingleton = 懒查找/懒创建 + Awake 防重 + OnDestroy 清空 + 退出标志；每个封闭泛型类型一份静态字段。
  • 五个子类只有 GameInstance 调了 base.Awake：防重和提前登记对 World / TimerSystem / EventSystem 不生效；现在靠“每场景至多一个 + 懒查找兜底”没有表现出来。
  • GameInstance 的 this == null 不生效（Destroy 延迟），起作用的是 Instance != this。
  • EventSystem 在 Awake 里建字典、UI 在 OnEnable 里注册：依赖不保证的跨对象 Awake 顺序；TimerSystem 用字段初始化器所以没这个问题。
  • 退出标志只置不复位：关闭 Domain Reload 后第二次 Play，Instance 返回 null，所有 Actor 都不注册。替代方案：Service Locator、显式引导、DI、UE Subsystem。
自测 1：在 GamePlayTest2 场景（没有预置任何单例）里，TimerSystem 第一次被创建是在什么时候？它的 Awake 漏调 base 会有影响吗？

第一次有人访问 TimerSystem.Instance 时：DemoGameMode.StartPlay 里 CreateTimer。getter 里 FindObjectOfType 找不到，就 new GameObject + AddComponent，Awake 在 AddComponent 内部执行，随后 getter 把 _instance 设为它。整个过程由 getter 完成登记，漏调 base 没有影响——这个 bug 只对“场景预置的实例”有意义。

自测 2：把 SurvivalUIController 的注册从 OnEnable 移到 Start，为什么能消除 6.5 节的隐患？会不会漏掉开局事件？

场景加载时，所有对象的 Awake / OnEnable 都先于任何对象的 Start，所以 UI 的 Start 执行时 EventSystem 一定已经 Awake、字典已创建。开局事件（分数、寿命句柄）是在 World.Update 里由 GameMode / GameState 的 BeginPlay 发出的，晚于所有场景对象的 Start，不会漏。代价是 UI 被禁用再启用时需要另外处理重新注册。

自测 3：为什么说 TimerSystem 对应 UE 的 WorldSubsystem，而不是 GameInstanceSubsystem？

它的生命周期是“每个场景一份、随场景销毁”，切场景时所有计时器都应该消失；GameInstanceSubsystem 会跨关卡存在，计时器就会带到下一个关卡。UE 的 FTimerManager 也挂在 World 上（GameInstance 另有一个用于跨关卡的计时器管理器）。
